# DigitCam — 한국 번호판 인식 → TCP 전송 앱 · 인터페이스 계약서

> **개정 2 (2026-08-13)** — 인식 대상이 **한국 자동차 번호판**으로 확정됐고,
> **정지 상태에서만 인식**하라는 요구가 추가됐다. §1·§4·§5·§6·§7·§9 가 바뀌었다.
> 개정 1 은 일반 인쇄체 숫자 기준이었다. **개정 1 을 읽고 시작했다면 다시 읽어라.**

루트가 정한 **경계 문서**다. 세 도메인이 서로를 기다리지 않고 동시에 작업할 수 있도록,
도메인 사이를 지나는 것(JNI 시그니처·결과 JSON·설정 키·전송 포맷)만 여기서 못박는다.
도메인 **안쪽** 구현은 각 담당의 재량이다.

계약을 바꿔야 한다면 고치지 말고 **루트에게 요청**하라. 한쪽이 조용히 바꾸면 반대쪽이 깨진다.

## 1. 무엇을 만드는가

카메라를 상시 켜 두고, 화면에 들어온 **한국 자동차 번호판**을 OpenCV 로 읽어
**TCP 서버로 전송**하는 안드로이드 앱. 실기기(보유 중인 폰) 실행이 목표다.

**대상 예시**: `123가4568` (신형 유럽형 장축 반사필름식, 왼쪽에 파란 KOR 띠)
샘플 이미지: `/Users/idong-u/Downloads/반사필름식번호판_국토교통부.jpg` (621×172 RGB)

**두 가지 확정 사항**

1. **한글까지 인식해서 번호판 문자열 전체를 보낸다.** `123가4568` — 숫자만 뽑지 않는다.
   번호판용 한글은 40자 내외로 닫힌 집합이다(§9.5).
2. **정지 상태에서만 인식한다.** 움직이는 동안에는 인식 자체를 건너뛴다.
   흔들린 프레임에서 억지로 읽어 틀린 값을 보내는 것보다, 안 보내는 게 낫다는 요구다.

**규격 범위**: 장축 8자리(3자리+한글+4자리)가 우선. 여기에는 **파란 KOR 띠가 있는 것과 없는 것이
둘 다 포함된다**(§9.3) — 승합·화물·특수 번호판에는 띠가 없다. 구형 단축(2자리+한글+4자리)도 같은
로직으로 받아들이되, 안 되면 나중으로 미룬다. 지역명 2단 번호판·노란 영업용판은 이번 범위 밖이다.

OpenCV 를 쓰는 이유는 인식 정확도 자체보다 **이 영상처리 코어를 나중에 임베디드로 그대로 옮기기
위해서**다. 따라서 다음 원칙이 최우선이다:

> **인식 로직은 전부 C++ 에 둔다. Android/JNI 헤더에 의존하지 않는 순수 OpenCV 코어로 분리한다.**
> Kotlin 은 프레임을 떠서 넘기고, 결과를 그리고, 소켓으로 보내는 일만 한다.
> **움직임 판정·안정화·전송 트리거도 전부 C++ 안이다** — 임베디드에서 똑같이 동작해야 한다.

**임베디드로 들고 갈 파일은 3개다** (개정 5에서 정정 — 2개인 줄 알았다):
`digit_pipeline.hpp` · `digit_pipeline.cpp` · **`plate_templates.hpp`**.
템플릿을 런타임 파일로 두지 않기로 했으므로(§9.5) 뱅크가 소스 안에 산다. 셋 다 `jni.h` 나
`android/*.h` 를 include 하지 않는다 — 이 조건이 깨지면 이식성 요구가 깨진 것이다.

## 2. 기준 프로젝트와 소유권

`android/` (기존 jnidemo)를 재사용한다. `opencv/` 스캐폴드는 이번 작업에서 건드리지 않는다.

| 영역 | 담당 | 경로 |
|---|---|---|
| Gradle·Manifest·Kotlin·리소스·assets | `android-engineer` | `android/app/build.gradle.kts`, `android/app/src/main/{AndroidManifest.xml,java,res,assets}/**` |
| OpenCV 영상처리 코어 + JNI 브리지 + CMake + 템플릿 생성기 | `cpp-engineer` | `android/app/src/main/cpp/**`, `cpp/**` |
| 전송 프로토콜 명세 + 테스트 TCP 서버 | `socket-engineer` | `docs/net/**`, `net/**` |

**패키지명을 바꾼다**: `com.example.jnidemo` → `com.example.digitcam`
(namespace / applicationId / 소스 디렉터리 / JNI 심볼 전부). 기존 `greetFromJNI` 데모는
툴체인 검증이 끝났으므로 제거한다 — git 이력에 남는다.

네이티브 라이브러리 이름: **`digitcam`** (`System.loadLibrary("digitcam")`).

## 3. OpenCV SDK 위치

루트가 내려받아 아래에 풀어 뒀다(확인함). 각자 다시 받지 마라.

```
~/opencv-android-sdk/OpenCV-android-sdk/sdk/native/jni/OpenCVConfig.cmake   ← CMake 진입점
~/opencv-android-sdk/OpenCV-android-sdk/sdk/native/staticlibs/<ABI>/        ← libopencv_core.a 등
~/opencv-android-sdk/OpenCV-android-sdk/sdk/native/libs/<ABI>/              ← libopencv_java4.so
```

- 버전: **4.14.0**
- ABI: `arm64-v8a`, `x86_64` 두 개만 (실기기 + 에뮬레이터). 기존 `abiFilters` 유지.
- 경로는 하드코딩하지 말고 `local.properties` 의 `opencv.dir` 또는 `-DOpenCV_DIR` 로 주입하되,
  없으면 위 기본 경로로 폴백한다.
- **정적 링크(core + imgproc)를 우선한다.** 24MB 짜리 `libopencv_java4.so` 를 APK 에 넣지 않아도
  되고 Java 바인딩을 아예 안 쓰게 된다(= 임베디드 이식에 더 가깝다). 막히면 공유로 가되
  **그 사실을 요청 결과에 적어라.**
- CMake 4.1.2 로 고정돼 있다. `OpenCVConfig.cmake` include 시 정책 에러가 나면
  `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` 를 먼저 시도하라.

## 4. JNI 계약 — Kotlin ↔ C++

**개정 2에서 `nativeConfigure` 가 바뀌었다.** 인자를 늘릴 때마다 시그니처가 깨지지 않도록
`key=value` 줄 묶음 문자열 하나를 받는다.

```kotlin
package com.example.digitcam

object DigitVision {
    init { System.loadLibrary("digitcam") }

    /** 파이프라인 인스턴스 생성. 반환값은 네이티브 핸들. 실패 시 0. */
    external fun nativeCreate(): Long

    /** 해제. 이후 해당 핸들 사용 금지. */
    external fun nativeDestroy(handle: Long)

    /**
     * 설정 주입. server.properties 의 `vision.` 으로 시작하는 줄을 **그대로** 넘긴다.
     * 형식: "vision.motion_threshold=0.6\nvision.stable_frames=3\n..."
     * 모르는 키는 C++ 가 무시한다. 값이 깨졌으면 그 키만 기본값을 유지한다.
     * Kotlin 은 파싱하지 않는다 — 임계값 해석은 전부 네이티브 몫이다.
     */
    external fun nativeConfigure(handle: Long, config: String)

    /**
     * 한 프레임 처리. y 는 YUV_420_888 의 Y 평면(그레이스케일) 복사본.
     * rowStride 는 width 보다 클 수 있다. rotationDegrees 는 0/90/180/270.
     * 반환값은 §5 의 JSON 문자열. 절대 null 을 반환하지 않는다.
     */
    external fun nativeProcessGray(
        handle: Long,
        y: ByteArray,
        width: Int,
        height: Int,
        rowStride: Int,
        rotationDegrees: Int,
    ): String

    /** 링크된 OpenCV 버전 문자열. SDK 연결 확인용(화면에 표시한다). */
    external fun nativeVersion(): String
}
```

**C 심볼 (cpp-engineer)** — `extern "C" JNIEXPORT`:

```
Java_com_example_digitcam_DigitVision_nativeCreate      (JNIEnv*, jobject)                        -> jlong
Java_com_example_digitcam_DigitVision_nativeDestroy     (JNIEnv*, jobject, jlong)                 -> void
Java_com_example_digitcam_DigitVision_nativeConfigure   (JNIEnv*, jobject, jlong, jstring)        -> void
Java_com_example_digitcam_DigitVision_nativeProcessGray (JNIEnv*, jobject, jlong, jbyteArray, jint, jint, jint, jint) -> jstring
Java_com_example_digitcam_DigitVision_nativeVersion     (JNIEnv*, jobject)                        -> jstring
```

`object` 선언이므로 두 번째 인자는 `jclass` 가 아니라 `jobject`(싱글턴 인스턴스)다.
정적 등록(심볼명 매칭)을 쓴다 — `RegisterNatives` 는 쓰지 않는다.
문자열은 UTF-8(`NewStringUTF`) 이다. **`value` 에 한글이 들어가므로 인코딩을 흘리지 마라.**

## 5. 인식 결과 JSON — C++ 가 만들고 Kotlin 이 읽는다

`nativeProcessGray` 반환 문자열. **키를 빼지 마라. 실패한 프레임에서도 전 키를 채운다.**

```json
{"value":"123가4568","conf":0.82,"stable":true,"fresh":false,
 "moving":false,"motion":0.31,"plate":true,"sharp":142.5,"format":"new",
 "reason":"ok",
 "quad":[[120,300],[460,296],[462,372],[118,376]],
 "chars":[{"c":"1","conf":0.93,"box":[14,18,34,62]}],
 "plateW":520,"plateH":110,"w":480,"h":640,"ms":18.3}
```

| 키 | 형 | 의미 |
|---|---|---|
| `value` | string | 번호판 문자열 `123가4568`. 못 읽으면 `""` |
| `conf` | number | 0.0~1.0. **문자별 신뢰도의 최소값**(가장 약한 고리) |
| `stable` | bool | 같은 `value` 가 `stable_frames` 회 연속 나왔는가 |
| `fresh` | bool | 이번 프레임이 그 값의 "새 관측"인가 — §5.1 |
| `moving` | bool | 움직임 게이트 판정. `true` 면 인식을 건너뛴 프레임이다 |
| `motion` | number | **프레임 이동량(화소, 160×120 기준).** 평균 차분이 아니다 — §9.1 |
| `plate` | bool | 번호판 사각형을 찾았는가 |
| `sharp` | number | 선명도 지표. 값의 정의는 §9.1.1 — **라플라시안 분산이 아니다** |
| `format` | string | `new`(3+한글+4) · `old`(2+한글+4) · `unknown` |
| `reason` | string | `ok`·`moving`·`no_plate`·`blurry`·`segment_fail`·`low_conf` 중 하나 — §5.2 |
| `quad` | array | 번호판 네 꼭짓점 `[[x,y]×4]`, **회전 보정된 프레임** 좌표계. 오버레이용 |
| `chars` | array | 문자별 `{c, conf, box}`. `box` 는 **정규화된 번호판** 좌표계(디버그용) |
| `plateW`,`plateH` | int | 정규화 번호판 크기. `chars[].box` 의 기준 |
| `w`,`h` | int | 회전 보정 후 프레임 크기. `quad` 의 기준 |
| `ms` | number | 이 프레임 처리 시간(ms) |

- 파싱은 `org.json.JSONObject` 로 한다(추가 의존성 없음).
- Kotlin 은 **모르는 키를 무시하고, 없는 키는 기본값**으로 처리한다. 계약이 또 늘어도 안 깨지게.

### 5.1 `fresh` — 전송 트리거는 C++ 가 만든다

`stable` 만으로 전송하면 번호판을 10초 비추는 동안 같은 값이 수백 번 나간다.
그래서 **상승 엣지**를 네이티브가 직접 알려준다. Kotlin 은 판단하지 않는다.

- `fresh=true` 는 **`stable` 이 거짓→참으로 바뀌는 그 한 프레임에만** 준다.
- **빈 값은 안정화되지 않는다.** `value==""` 인 프레임은 `stable=false, fresh=false` 다.
  따라서 **빈 문자열이 서버로 전송되는 일은 없다**(`plain` 모드에서 빈 줄이 나갈 수 없다).
  android-engineer 는 전송 조건을 `fresh == true && value.isNotEmpty()` 로 둔다.
- **재무장(re-arm)** — 다음 두 경우에 래치를 풀어 같은 값이 다시 `fresh` 가 될 수 있게 한다:
  1. 인식된 `value` 가 래치된 값과 달라졌을 때
  2. 번호판을 못 찾은 프레임(`plate=false`)이 `stable_frames` 회 연속일 때
     (= 차를 보냈다가 다시 같은 차를 비추는 경우)

### 5.2 `reason` — 왜 값이 안 나왔는지 화면에 띄운다

실패가 전부 `value:""` 로만 보이면 튜닝을 할 수가 없다. 어느 단계에서 걸렸는지 항상 남겨라.

| 값 | 의미 |
|---|---|
| `moving` | 움직임 게이트에서 걸림. 인식 안 함 |
| `no_plate` | 정지했지만 번호판 사각형을 못 찾음 |
| `blurry` | 번호판은 찾았으나 `sharp` 가 하한 미만 |
| `segment_fail` | 문자 분할이 기대 구조(3+1+4 / 2+1+4)와 안 맞음 |
| `low_conf` | 읽었으나 `conf < min_confidence` — 버림 |
| `ok` | `value` 유효 |

## 6. 서버 설정 파일 — `server.properties`

서버 IP·포트가 아직 미정이므로 **리빌드 없이 바꿀 수 있어야 한다.**

**로딩 순서 (뒤가 앞을 덮어씀)**
1. `assets/server.properties` — 앱에 번들되는 기본값
2. `getExternalFilesDir(null)/server.properties` — 있으면 이 값이 이김

앱 최초 실행 시 1을 2의 위치로 **자동 복사**한다(이미 있으면 건드리지 않는다).

```
# /sdcard/Android/data/com.example.digitcam/files/server.properties
adb push server.properties /sdcard/Android/data/com.example.digitcam/files/server.properties
```

**키 (전부 이 이름 그대로)**

```properties
server.host=                      # 비어 있으면 전송하지 않고 화면에 "서버 미설정" 표시
server.port=5500                  # ⚠ 5000 을 기본값으로 쓰지 마라 — 아래 참조
server.format=json                # json | plain
send.mode=on_fresh                # on_fresh(기본) | every_stable_frame
send.min_interval_ms=1000         # 연타 방지 하한
reconnect.interval_ms=3000
socket.connect_timeout_ms=3000
socket.keepalive=true

# 아래 vision.* 는 Kotlin 이 해석하지 않고 nativeConfigure 로 통째로 넘긴다
vision.min_confidence=0.70        # 문자별 최소 신뢰도의 하한
vision.stable_frames=3            # 같은 값 연속 몇 프레임이면 stable
vision.motion_threshold=2.0       # 프레임 이동량(화소) 이하이면 '정지'. 근거는 §9.1
vision.still_frames=3             # 정지로 인정하기까지 연속 프레임 수
vision.min_sharpness=40           # 선명도 하한. 지표 정의와 이 값의 근거는 §9.1.1
vision.min_plate_width_ratio=0.25 # 번호판 폭 / 프레임 폭 최소
vision.plate_format=auto          # auto | new | old
vision.gate_bypass=false          # true 면 움직임·선명도 게이트를 끈다(디버그용)
```

> ⚠ **기본 포트를 5000 으로 두지 마라.** macOS 의 AirPlay 수신기(ControlCenter)가 5000 을
> 점유한다 — 이 노트북에서 루트가 확인했다(`lsof -nP -iTCP:5000` → `ControlCe ... (LISTEN)`).
> 테스트 서버가 바인드에 실패하거나, 더 나쁘게는 앱이 **엉뚱한 프로세스에 붙어** 값을 보내고도
> 서버 로그가 비어 있게 된다. 그러면 인식기부터 의심하게 되는데 엉뚱한 곳이다.
> 기본값은 **5500**. (socket-engineer 가 REQ-0007 처리 중 먼저 발견해 문서에 적었고, 루트가 실측 확인했다.)

### 6.1 설정 화면 — 폰에서 파일을 고칠 방법 (개정 7 · 필수)

`getExternalFilesDir()` 는 **Android 11+ 실기기에서 폰만으로는 접근할 수 없다.** 파일 관리자도
다른 앱도 `Android/data/` 안을 못 연다(11에서 막고 13에서 굳혔다). adb 로는 되지만 그러면
**서버 IP 를 바꾸려고 노트북을 들고 다녀야 한다** — 리빌드 없이 바꾸자던 취지가 절반만 달성된다.

그래서 **앱 안에 설정 입력 화면을 둔다.** 다만 방식이 중요하다:

> **화면은 파일을 대체하지 않는다. 화면은 그 파일을 편집하는 도구다.**
> 저장을 누르면 `getExternalFilesDir()/server.properties` 에 써 넣고, 기존의 "설정 다시 읽기"
> 와 **같은 경로로** 재적용한다. adb 로 고치는 방법도 그대로 살아 있어야 한다.

**지켜야 할 것**

1. **주석과 모르는 키를 보존한다.** 파일을 통째로 다시 쓰지 말고 **값이 있는 줄만 제자리에서
   교체**하라. 이 파일은 설정이자 설명서다(각 키가 왜 있는지 주석에 적혀 있다). 저장 한 번에
   그게 날아가면 안 된다. 화면이 모르는 키가 파일에 있어도 **그대로 남겨야 한다.**
2. **`vision.*` 는 여전히 해석하지 마라.** 파일에 있는 `vision.` 줄을 **읽어서 그대로**
   `키 이름 + 자유 입력칸` 목록으로 그린다. 그러면 나중에 `vision.` 키가 늘어도 Kotlin 을
   고칠 필요가 없다 — `nativeConfigure` 를 문자열 하나로 받기로 한 것과 같은 이유다.
   반대로 `server.*`·`send.*`·`socket.*` 은 Kotlin 이 의미를 아는 값이므로 형식에 맞는 입력칸을 쓴다.
3. **입력 검증은 저장 시점에.** 포트 1~65535, `server.format` 은 `json|plain`, 숫자 칸에 숫자가
   아닌 값이면 저장을 막고 어디가 틀렸는지 말한다. 깨진 값을 파일에 써 놓고 나중에 기본값으로
   폴백하는 것보다, 애초에 못 쓰게 하는 편이 낫다.
4. **지금 실제로 적용된 값을 보여준다.** 화면을 열면 파일에서 다시 읽어 채운다. 화면에 뜬 값과
   네이티브에 들어간 값이 다르면 그 화면은 거짓말을 하는 것이다.
5. **"기본값으로 되돌리기"** — assets 사본으로 덮어쓴다. 값을 잘못 만져 못 쓰게 됐을 때의 탈출구다.
6. `server.host` 를 가장 위에 둔다. 제일 자주 바뀌는 값이고, 비어 있으면 전송이 꺼진다.

- 알 수 없는 키는 무시하고 로그만 남긴다. 값이 깨졌으면 기본값 폴백 + 화면 경고.
- 화면에 **"설정 다시 읽기"** 버튼을 둔다 — 앱을 껐다 켜지 않고 IP·임계값을 바꿔 시험한다.
- `vision.` 접두어가 붙은 줄만 골라 `nativeConfigure` 로 넘긴다. Kotlin 은 값을 해석하지 않는다.

## 7. 전송 프로토콜 — **확정. 이 절은 협의 대상이 아니다**

`socket-engineer` 의 일은 이 절을 "결정"하는 게 아니라 **이 절대로** 명세서를 쓰고
테스트 서버를 만드는 것이다. 바꿔야 할 이유가 보이면 직접 바꾸지 말고 **루트에게 요청을 발행**하라.

TCP, 클라이언트가 접속, **줄 단위(LF 종단) UTF-8**.

```
server.format=json  →  {"ts":1755080000000,"value":"123가4568","conf":0.82,"format":"new","seq":12,"device":"SM-S911N"}\n
server.format=plain →  123가4568\n
```

- ⚠ **`value` 에 한글이 들어간다.** UTF-8 멀티바이트다 — 테스트 서버가 ASCII 를 가정하면 깨진다.
  json 모드에서 `\uXXXX` 이스케이프를 쓰든 원문 UTF-8 을 쓰든 **수신 측이 둘 다 복원**해야 한다.
- `ts` 는 ms 단위 epoch, `seq` 는 앱 실행 후 1부터 증가, `format` 은 `new`/`old`.
- 서버 응답은 **요구하지 않는다**(fire-and-forget). 읽더라도 무시.
- 끊기면 `reconnect.interval_ms` 간격으로 재시도. 재시도 중에도 카메라·인식은 계속 돈다.
- 전송 실패분을 **큐에 쌓아 재전송하지 않는다.** 재접속 순간에 낡은 값이 쏟아지면 안 된다.
- 전송은 카메라 스레드에서 하지 않는다 — 별도 스레드/코루틴.

## 8. 화면 (android-engineer)

전체화면 프리뷰 + 오버레이 한 장이면 된다. 필요한 표시:

- 인식된 번호판 문자열(크게), `conf`, `stable` 여부
- **`quad` 로 번호판 사각형 그리기** (문자 박스는 정규화 좌표계라 프레임에 못 겹친다 — 안 그려도 된다)
- **정지/움직임 상태** — 움직이는 동안 인식을 건너뛴다는 걸 사용자가 알아야 한다.
  `moving=true` 면 "움직임 — 정지하면 인식", 아니면 "정지"
- `reason` 을 그대로 노출 — `no_plate` / `blurry` / `segment_fail` / `low_conf` 중 무엇에서 막혔는지
- 서버 연결 상태: `미설정 / 연결중 / 연결됨 / 끊김(재시도 n)`
- OpenCV 버전(`nativeVersion()`), 프레임 처리시간 `ms`, `motion`·`sharp` 실측값(임계값 튜닝용)
- 버튼: **설정**(§6.1 입력 화면), **설정 다시 읽기**, **샘플 이미지 모드** 토글
- 화면 꺼짐 방지(`FLAG_KEEP_SCREEN_ON`), 세로 고정

권한: `CAMERA` 런타임 요청, `INTERNET`.

## 9. 인식 파이프라인 — 이번 작업에서 가장 위험한 부분

사용자의 진짜 목적은 앱이 아니라 **"OpenCV 파이프라인이 실제로 도는가"** 의 확인이다.
따라서 인식기는 도메인 내부 디테일이 아니라 **이번 산출물의 본체**다.

단계 구성은 아래로 고정한다. **각 단계의 구체적 알고리즘은 `cpp-engineer` 재량**이되,
착수 전에 방법을 한 단락으로 답신한다.

### 9.1 움직임 게이트 (신규 · 필수)

"정지 상태에서만 촬영" 요구를 여기서 구현한다.

- 그레이 프레임을 작게(160×120) 줄여 이전 프레임과 **위상 상관**(`cv::phaseCorrelate`)으로
  **이동량(화소)** 을 잰다. 그 값이 `motion` 이다.
- `motion < motion_threshold` 인 프레임이 `still_frames` 회 연속이면 **정지**로 본다.

> **왜 평균 절대차분이 아닌가 (개정 8 · 실측)** — 개정 2~7 은 `absdiff` 평균을 쓰라고 적었다.
> cpp-engineer 가 308프레임(정지/손떨림±1px/손떨림±3px/실제이동 8~20px)으로 재 보니
> **어떤 임계도 손떨림과 실제 이동을 가르지 못한다.** 겹침이 4배 폭이다:
>
> | 열 | 종류 | 평균차분 | 위상 이동량 |
> |---|---|---|---|
> | scene-03-persp-60 | **손떨림** | **6.52** | 0.76 |
> | scene-07-negative | **실제 이동** | **4.71** | 3.48 |
>
> 무늬가 강한 장면의 손떨림이 무늬가 약한 장면의 실제 이동보다 큰 값을 낸다. 평균 차분은
> 이동량이 아니라 **이동량 × 장면의 무늬 세기**를 재기 때문이다. 위상 상관은 이동 자체를 재므로
> 뒤집히지 않는다(0.001~2.081 대 1.971~5.194).
>
> **옛 기본값 0.60 은 손에 든 폰의 프레임 67%(154/231)를 '움직임' 으로 버린다** — 삼각대에
> 올리지 않는 한 아무것도 못 읽는다. android-engineer 가 에뮬레이터 카메라를 가만히 둔 상태에서
> `motion` 1.6~3.3 을 관측한 것이 같은 사실을 가리킨다.
>
> **임계 2.0 의 근거**: 308프레임 중 오판 4개(1.3%). 2.1 로 올리면 손떨림 오판은 0이 되지만
> 실제 이동을 6/77 놓친다 — **틀린 번호를 보내는 쪽이 더 나쁘므로** 이동을 놓치지 않는 2.0 을
> 택했다. 현장에서 계속 '움직임' 으로만 뜨면 2.5~3.0 까지 올려도 되고, `server.properties` 로
> 리빌드 없이 조정된다.
>
> 비용은 프레임당 0.32ms(에뮬레이터 기준, DFT 두 번). 아래 1ms 예산 안이다.
>
> ⚠ **아는 한계**: 카메라를 홱 돌려 장면이 통째로 바뀌는 순간에는 위상 상관 정점이 엉뚱한 곳에
> 잡혀 이동량이 작게 나올 수 있다(→ '정지' 오판). 근거 없는 임계를 넣지 않으려고 보정을 안 넣었다.
> 다음 프레임부터는 정상 비교가 되고 전송까지 가려면 `stable_frames` 회 연속 같은 값이 또
> 필요하므로 위험은 낮다고 본다. 정석은 `phaseCorrelate` 의 응답값으로 거르는 것이다.
- 움직이는 동안에는 **뒤 단계를 아예 돌리지 않는다**(`moving:true, reason:"moving"` 으로 즉시 반환).
  프레임당 1ms 수준이어야 한다 — 이게 배터리와 발열을 좌우한다.
- 폰 흔들림과 차량 이동을 굳이 구분하지 않는다. 둘 다 "지금 읽으면 안 되는 상태"다.
- 가속도 센서는 쓰지 않는다 — 임베디드로 안 따라간다. **프레임 차분만으로 한다.**
- 첫 프레임은 이전 프레임이 없으므로 `moving:true` 로 둔다.

### 9.1.1 선명도 게이트 — 지표 정의 (개정 6에서 확정)

움직임 게이트는 **프레임 사이**의 움직임만 본다. 폰을 멈춘 직후 오토포커스가 안 잡힌 프레임은
차분이 0이라 그냥 통과한다 — 정지했지만 흐리다. 그때 흐린 글자가 운 나쁘게 8조각으로 갈리면
구조 검증을 통과해 **틀린 번호가 나간다.** 그걸 막는 것이 이 게이트다.

**지표는 라플라시안 분산이 아니다.** 개정 2~5 는 그렇게 적었지만, cpp-engineer 가 26장 실측으로
**그 지표에는 쓸 수 있는 임계가 아예 존재하지 않는다**는 것을 보였다(읽어야 하는 것 1373~16862,
거절해야 하는 것이 그 범위 안에 섞인다 — 해상도에 휘둘리기 때문). 확정된 지표는:

```
sharp = min(mean|Sobel_x|, mean|Sobel_y|) / stddev(정규화된 번호판) × 100
```

세 요소가 각각 이유를 갖는다:

- **정규화된 판(520×110)에서 잰다** — 번호판이 멀든 가깝든 같은 눈금이 된다. 원본 ROI 에서 재면
  해상도가 값을 지배한다.
- **그 판의 대비로 나눈다** — 저조도에서 값이 같이 내려가지 않는다. 45% 저조도 샘플 3장이
  이 정규화 덕분에 54.9~60.6 으로 살아난다(안 나누면 24.1~30.5 로 거절선까지 떨어진다).
- **x·y 중 작은 쪽을 쓴다** — 가로 모션블러는 세로 획을, 세로 블러는 가로 획을 먼저 뭉갠다.
  한 방향만 보면 반대 방향 블러를 통째로 놓친다.

사실상 **대비로 정규화한 방향별 Tenengrad 의 최솟값**이다.

**임계 40 의 근거** — 26장 실측 분포:

```
읽어야 하는 22장 : 52.4 ~ 79.2
거절해야 하는 4장 : 12.1 ~ 30.1
                    ↑ 30.1 ~ 52.4 가 비어 있다. 40 은 그 로그 중앙(39.7)이다.
```

⚠ **지표를 바꾸면 임계도 같이 바꿔야 한다.** 실제로 지표만 새것으로 빌드하고 설정에 옛 눈금의
60 이 남아 있어서, 읽혀야 하는 번호판 5장이 `blurry` 로 잘리는 일이 있었다(루트가 에뮬레이터에서
관측). 40 으로 내리자 리빌드 없이 그 자리에서 통과했다. **두 값은 한 쌍이다 — 따로 옮기지 마라.**

### 9.2 번호판 검출

- 신형 장축 실물 비율 520×110mm → **종횡비 ≈ 4.7**. 구형 단축 335×155mm → **≈ 2.2**.
  이 차이가 커서 `format` 판정에 그대로 쓸 수 있다.
- 후보 찾기는 재량이다(모폴로지 그래디언트 + 가로로 긴 커널 close → 윤곽, 또는 Canny + `approxPolyDP`).
  단 **기울어진 번호판을 받아야 하므로** `minAreaRect` / 4점 근사로 잡고
  `getPerspectiveTransform` + `warpPerspective` 로 **정규화 크기(예: 520×110)로 편다.**
  축 정렬 `boundingRect` 로 자르면 비스듬한 번호판에서 글자가 기울어 분류가 무너진다.
- `min_plate_width_ratio` 미만이면 버린다(너무 멀리 있는 번호판).
- **프레임 전체가 번호판인 경우의 폴백 (개정 4)** — 후보를 하나도 못 찾았는데 프레임 자체의
  종횡비가 번호판 비율(4.7 또는 2.2, ±20%)에 가까우면 **프레임 전체를 번호판으로 보고 진행한다.**
  카메라를 번호판에 바짝 붙이면 실제로 이 상황이 되고, `samples/plates/` 의 7장과 `variants/`
  12장이 정확히 이 모양이다. 폴백이 없으면 그 19장이 전부 `no_plate` 로 떨어진다.
- 반대로 `scenes/` 7장은 번호판이 프레임의 28~60% 만 차지한다. **검출 단계가 실제로 시험되는
  것은 이 7장뿐이다** — `scenes/scene-01-front-45.png` 부터 통과시켜라.

### 9.3 파란 KOR 띠 — **있는지 검사한 뒤** 조건부로 잘라내라 (함정 · 개정 3에서 수정)

번호판 왼쪽 약 **10~12%** 에 파란 띠(KOR + 태극 마크)가 있는 것과 **없는 것이 둘 다 존재한다.**
장축 8자리인데 띠가 없는 번호판이 실재한다(`samples/plates/kor8-*-plain.png` — 승합·화물·특수).

> ⚠ **개정 2 는 "왼쪽 12% 를 무조건 자른다"고 썼다. 그러면 띠 없는 번호판의 첫 글자
> (`700가4568` 의 `7`)가 통째로 날아간다.** 반드시 검사 후 조건부로 잘라야 한다.

띠는 그레이로 보면 어두운 덩어리라, 있는데 안 자르면 문자로 잡히거나 이진화 임계를 망가뜨린다.
색 정보는 없다(Y 평면만 받는다) — **밝기 분포로 판정한다.**

**루트가 샘플 7장에서 실측한 판정식** — 정규화된 번호판에서
`왼쪽 12% 스트립의 밝은 화소 비율 ÷ 나머지 영역의 밝은 화소 비율` (밝음 기준 = 140):

| 샘플 | 스트립 | 나머지 | 비(比) |
|---|---|---|---|
| `kor8-seunghap-band` | 42.7% | 76.3% | **0.56** |
| `kor8-hwamul-band` | 42.3% | 75.2% | **0.56** |
| `kor8-teuksu-band` | 42.1% | 75.3% | **0.56** |
| `kor8-reflective-hires` | 26.9% | 63.7% | **0.42** |
| `kor8-seunghap-plain` | 87.0% | 78.5% | **1.11** |
| `kor8-hwamul-plain` | 80.1% | 78.3% | **1.02** |
| `kor8-teuksu-plain` | 83.5% | 78.2% | **1.07** |

**비 < 0.8 이면 띠 있음 → 자른다. 아니면 자르지 않는다.** 0.56 과 1.02 사이라 여유가 넉넉하다.
(위 수치는 여백이 남은 크롭 기준이다. 투시보정으로 정확히 편 번호판에서는 분리가 더 벌어진다.)

> **개정 5 — 위 판정식은 출발점이었고, 구현에서 두 군데가 바뀌었다.** cpp-engineer 가 실측으로
> 잡은 것이고 **바뀐 쪽이 옳다.** 임베디드로 옮길 때 이쪽을 가져가라.
>
> 1. **밝음 기준을 140 고정에서 그 번호판의 Otsu 임계로 바꿨다.** 저조도 이미지에서는 흰 바탕도
>    140 밑으로 내려가 스트립·나머지 비율이 **둘 다 0** 이 되어 비가 무의미해진다.
> 2. **"띠가 있으면 왼쪽 12% 절단" 을 버리고, 왼쪽부터 어두운 열이 연속되는 구간만 자른다.**
>    검출이 이미 띠를 뺀 흰 판면만 잡아오는 경우가 많은데, 그때 비가 0.79 처럼 애매하게 나오면
>    **첫 글자가 통째로 날아간다**(`scene-01` 에서 실제로 `1` 이 잘렸다). 글자 앞에는 밝은 여백이
>    있으므로 어두운 열 연속 구간은 첫 글자에서 자연히 멈춘다. 띠 전체면 띠 끝까지, 띠 조각만
>    걸렸으면 그만큼만 잘린다. 띠 유무 두 종류가 같은 코드로 통과한다.
>
> 고정 비율 절단이 위험했던 이유가 핵심이다 — **검출 결과가 띠를 포함하는지 아닌지가 매번 다르다.**
> 비율은 그 사실을 모르고, 어두운 열은 안다.

띠를 자르든 안 자르든 **남는 문자 구조는 똑같이 3+한글+4** 다. 자릿수 판정에는 영향이 없다.

### 9.4 문자 분할 — 한글은 획이 떨어져 있다 (함정)

`가` 는 `ㄱ` 과 `ㅏ` 가 **붙어 있지 않다.** connectedComponents 로만 자르면 한 글자가 두 조각으로
쪼개져 "3+1+4" 구조 검증이 통째로 실패한다. 이번 파이프라인에서 가장 조용히 망가지는 지점이다.

- **세로 투영 프로파일(vertical projection)** 로 글자 열을 먼저 나누는 쪽을 권한다.
  글자 사이 간격이 `ㄱ`–`ㅏ` 간격보다 넓으므로 자연스럽게 한 글자로 묶인다.
- connectedComponents 를 쓴다면, 가로 범위가 겹치거나 간격이 임계 이하인 조각을 **병합**한 뒤
  구조를 판정하라.
- 번호판 테두리에 닿은 성분은 제거한다. **단 안전장치를 둬라(개정 4)** — 이 규칙은 정규화된
  번호판의 *바깥 테두리 선*을 지우려는 것이지 글자를 지우려는 것이 아니다. 번호판이 프레임을
  꽉 채운 이미지(위 폴백 경로)에서는 글자가 가장자리에 가까워 함께 지워질 수 있다.
  **제거 후 남은 성분이 기대 자릿수보다 적으면 제거를 되돌려라.** 전부 지우고 `segment_fail`
  을 내는 것이 이 단계에서 가장 흔한 조용한 실패다.
- 기대 구조: `new` = 숫자3 + 한글1 + 숫자4 (8자), `old` = 숫자2 + 한글1 + 숫자4 (7자).
  구조가 안 맞으면 `reason:"segment_fail"` 로 버린다 — **억지로 맞추지 마라.**
  틀린 값을 보내느니 안 보내는 게 이 앱의 요구다.

### 9.5 분류 — 숫자 10 + 한글 40 내외

한글 후보 집합(닫혀 있다. 이 밖은 안 나온다):

```
가 나 다 라 마
거 너 더 러 머 버 서 어 저
고 노 도 로 모 보 소 오 조
구 누 두 루 무 부 수 우 주
바 사 아 자          (영업용)
배                    (택배)
하 허 호              (렌터카)
```

- **템플릿 뱅크 + NCC 방식을 권한다.** cpp-engineer 가 개정 1 에 회신한 방법(다중 폰트 오프라인
  래스터화 → `.hpp` 로 소스에 박기 → 정규화 상호상관 + 2등 마진 신뢰도)은 **그대로 유효하다.**
  숫자에 더해 위 한글 집합을 같은 방식으로 넣으면 된다.
- 이 머신에 준비된 것(확인함): **Pillow 12.3.0**, 한글 폰트
  `/System/Library/Fonts/AppleSDGothicNeo.ttc`,
  `/System/Library/Fonts/Supplemental/AppleGothic.ttf`,
  `/System/Library/Fonts/Arial Unicode.ttf`
- ⚠ **`NotoSansGothic-Regular.ttf` 를 쓰지 마라 — 한글이 없다.** 이름의 "Gothic" 은 고딕체가
  아니라 **고트 문자**(고대 게르만 문자)다. 한글을 요청하면 전부 `.notdef` 네모를 돌려준다.
  개정 3에서 루트가 이름만 보고 목록에 넣었던 오류이고, cpp-engineer 가 실측으로 잡았다
  (`cpp/digitcam/tools/probe_fonts.py`). 루트도 재확인했다 — `가`·`나`·`힣`·사설영역 문자의
  렌더 비트맵 해시가 전부 같다. **빼지 않으면 빈 템플릿이 뱅크에 섞여 조용히 망가진다.**
  새 폰트를 추가할 때는 반드시 이 방식으로 글리프 존재를 확인하라. 이름은 근거가 못 된다.
  번호판 실제 서체는 이들과 다르지만 **굵은 고딕 계열**이라는 점은 같다. 여러 폰트를 넣고
  약간의 블러·스케일 변형을 섞어 뱅크를 두껍게 만들면 서체 차이를 흡수할 수 있다.
- `ml::KNearest` / `ml::SVM` 을 오프라인 학습해 FileStorage 문자열로 박는 방식도 허용한다.
  단 **런타임 모델 파일을 두지 마라** — 템플릿·모델은 소스에 컴파일해 넣는다(임베디드 이식성).
- 숫자 자리에서는 숫자 클래스끼리만, 한글 자리에서는 한글 클래스끼리만 비교한다.
  **자리 위치가 후보를 좁혀 준다 — 이 구조를 반드시 활용하라.** 정확도가 크게 올라간다.
- `conf` 는 문자별 신뢰도의 최소값. `min_confidence` 미만이면 `reason:"low_conf"` 로 버린다.

### 9.6 정지 이미지 디버그 경로 (필수)

**폰도 차도 없이 인식기를 반복 개선할 수 있어야 한다.**

**시험 이미지는 루트가 `samples/plates/` 에 준비해 뒀다** (개정 3). 각자 따로 만들지 마라 —
셋이 같은 이미지로 돌려야 결과를 비교할 수 있다. `samples/**` 는 소유권상 **전원 공용**이라
누구나 추가할 수 있고, 추가하면 `expected.json` 에 정답을 같이 적는다. 자세한 건 `samples/README.md`.

| 구성 | 장수 | 프레임 안에서 번호판이 |
|---|---|---|
| `plates/*.png` | 7 | **꽉 채운다** — 띠 없는 것 3 + 띠 있는 것 3 + 고해상 1 |
| `plates/variants/` | 12 | 꽉 채운다 — ±12° 기울기 · 저조도45% · 1/3축소 · 모션블러 2단계 |
| **`plates/scenes/`** | **7** | **일부만 차지한다 (640×480)** — 배경·방해물 있음. **검출 단계는 여기서만 시험된다** |
| `expected.json` | — | 파일명 → `{value, band, format, rule}` 정답표 |

**채점은 `rule` 로 한다** — 값만으로는 블러 이미지를 채점할 수 없다:

| `rule` | 뜻 | 장수 |
|---|---|---|
| `exact` | 값이 정확히 일치 | 18 |
| `exact_or_empty` | 일치하거나 빈 값. **다른 값이 나오면 실패** | 4 |
| `empty` | 반드시 빈 값 | 4 |

`exact_or_empty` 가 이 시험의 핵심이다. §9.4 의 **"틀린 값을 보내느니 안 보내는 게 낫다"** 를
그대로 옮긴 것이다. 애매한 이미지는 읽어도 되고 거절해도 되지만 **엉뚱한 번호를 만들어내면 실패다.**

- `scenes/scene-07-negative.png` 는 **번호판이 아예 없다.** 번호판 크기의 빈 사각형만 있다.
  여기서 값이 나오면 실사용에서 없는 번호를 서버로 보내는 사고다.
- `scenes/scene-01-front-45.png` 가 가장 쉬운 장면이다. **여기서 안 되면 뒤는 볼 것 없다.**
- `android-engineer`: `samples/plates/` 에서 골라 `assets/` 로 **복사**하고(원본은 그대로 둔다),
  화면에 **"샘플 이미지 모드"** 토글을 둔다. 켜면 카메라 프레임 대신 그 이미지를 그레이로
  디코딩해 **똑같은 `nativeProcessGray`** 로 보낸다. 경로가 갈라지면 의미가 없다.
  샘플을 하나씩 넘겨 보는 이전/다음 버튼이 있으면 훨씬 쓸모 있다.
- 정지 이미지는 프레임 차분이 0 이라 움직임 게이트를 자연히 통과한다(첫 프레임 제외).
- 이 경로 덕분에 에뮬레이터(`emulator-5554`, x86_64)만으로 인식기를 검증할 수 있다.
- `cpp-engineer`: 같은 코어를 데스크톱에서 `samples/plates/**` 전체에 돌려 `expected.json` 과
  대조하는 테스트 하네스를 자기 트리(`cpp/**`)에 둬라. **16/17 같은 점수가 바로 나오는 게
  이 작업에서 가장 값싼 피드백 루프다.** 강력히 권장한다.

## 10. 빌드 통합 책임

`build.gradle.kts` 는 android-engineer, `CMakeLists.txt` 는 cpp-engineer 소유라 빌드가 두 사람에
걸친다. **통합 빌드를 끝까지 책임지는 쪽은 `android-engineer` 다.**

- 완료 보고에 `./gradlew :app:assembleDebug` 실제 출력을 붙인다.
- 네이티브 쪽에서 깨지면 우회하지 말고 `cpp-engineer` 에게 요청을 발행한다.

### 10.1 어느 소스로 빌드했는지 반드시 기록한다 (개정 6에서 추가)

**두 담당이 같은 체크아웃을 공유하므로, 한쪽이 편집하는 중에 다른 쪽이 빌드할 수 있다.**
실제로 그렇게 됐다 — android-engineer 가 cpp-engineer 의 **분할 로직 수정 직전 스냅샷**으로
APK 를 빌드해 `24/26` 이 나왔고, 같은 시각 cpp-engineer 의 하네스는 `26/26` 이었다.
같은 코어라고 믿었기 때문에 "조건이 다른가"를 한참 뒤졌지만, 실은 **다른 코드였다.**

그래서 채점·성능 수치를 보고할 때는 **빌드에 쓴 네이티브 소스의 상태를 같이 적는다:**

```bash
stat -f "%Sm %N" -t "%H:%M:%S" android/app/src/main/cpp/*.cpp android/app/src/main/cpp/*.hpp
```

수치가 어긋날 때 이 한 줄이 있으면 "조건 차이인가 코드 차이인가"가 즉시 갈린다. 없으면
없는 문제를 며칠 쫓는다. **숫자를 보고할 때는 그 숫자를 낸 코드가 무엇이었는지 같이 말하라.**

## 11. 완료 기준

1. `./gradlew :app:assembleDebug` 통과.
2. **에뮬레이터(`emulator-5554`)에 설치·실행되고 화면에 `nativeVersion()` 이 4.14.0 계열로 표시된다**
   = 패키징 + 네이티브 로드 + OpenCV 링크가 동시에 증명된다.
3. **샘플 이미지 모드에서 `123가4568` 이 화면에 뜬다.** 이게 이번 작업의 핵심 증거다.
   추가로 `samples/plates/` 16장(블러 1장 제외)에 대한 데스크톱 하네스 점수를 보고한다 —
   **몇 장을 맞혔는지 숫자로 적어라.** "잘 된다"는 보고는 받지 않는다.
4. 실기기에서 앱을 켜면 즉시 프리뷰가 뜨고, 폰을 흔드는 동안에는 "움직임"으로 표시되며
   멈추면 번호판을 읽는다.
5. `server.properties` 에 노트북 IP/포트를 넣고 "설정 다시 읽기" 를 누르면, 노트북의 테스트
   TCP 서버에 `123가4568` 이 **한글이 깨지지 않은 채** 줄 단위로 찍힌다. 서버를 껐다 켜도 재접속한다.

4·5 는 폰 연결이 필요하므로 사용자와 함께 확인한다. **1~3 은 지금 바로 검증할 수 있다.**

**검증하지 않은 것을 "된다"고 보고하지 마라.** 빌드만 통과한 것은 "빌드 통과"라고 쓴다.
