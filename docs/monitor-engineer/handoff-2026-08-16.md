## 3. 발견 목록 — 근거 수치와 함께 (이 문서에만 남은 것이 많다)

### ① 옛 기준선의 "체크섬 실패 0.034%" 는 허상이었다

REQ-0092(socket-engineer)는 옛 구간 16건을 `0.034%` 로 집계했다. **원문 바이트를 열어 보니
16건 전부가 문자 그대로 `#`(0x23) 37~41개 연속**이었다. 바이트 손상이 아니다.

→ **실제 바이트 손상(`S,` 로 시작하는데 체크섬 틀림)은 양쪽 구간 통틀어 0건.**
정직한 대조는 `0 대 0` 이다.

> 서버는 비프로토콜 텍스트도 `! 체크섬 불일치` 로 센다(체크섬 검증이 타입 판별보다 먼저 돈다).
> 그래서 집계기는 **드롭 직전 `←ARD` 원문**을 붙잡아 `lone_K` / `noise` / `real_S` 로 갈라야 한다.

### ② 10:25~10:35 "환경 열화" 는 **팀이 만든 것**이었다 (내가 한 번 오판했다)

나는 중간보고 #3 에서 이 구간을 **"전원 사건"으로 특정**했다. **틀렸다.**
`arduino/INTERVENTIONS.md` 에 `10:27:44 시리얼 열기`, `~10:29–10:31 시리얼 열기 ×2` 가 있었다.
DTR 리셋이다.

**원인**: 개입 목록을 그 파일에서 읽지 않고 **내 스크립트에 손으로 베껴 적었다가 빠뜨렸다.**
→ `interventions.py` 로 그 파일을 **직접 파싱**하도록 고쳤다. 형식이 깨지면 조용히 넘어가지 않고
**멈춘다**("개입 없음"과 "못 읽었음"은 다르다).

**정정 후**: 팀 개입을 전부 걷어내면 **자발 MCU 재부팅은 0~1건**(15.9시간 전 구간).
잔존 1건(10:28:55)도 기록된 개입의 대략 경계 5초 앞이다.
**허용오차를 넓히면 0 이 되지만 그렇게 하지 않았다** — 원하는 답이 나올 때까지 기준을 넓히는 것은 분석이 아니다.

### ③ `TX-DROP` 은 "소실"이 아니라 "실패한 전송 시도"다

판정창에서 장치측 TX-DROP 218건. 프레임 수로 나누면 "상행 4.5% 소실"이 나온다. **아니다.**
그 시각 서버 로그를 직접 열어 확인했다:

```
11:53:31  seq 1399
11:53:35  seq 1400   ← 벽시계 4초 공백인데 seq 는 연속
```

장치는 **성공할 때만 seqNo 를 올린다.** 재시도로 결국 보낸다. 데이터 손실 0, 표본 시각만 건너뛴다.
(12:17 끊김에서도 장치가 멈춘 `seq=2693` 과 서버 수신 프레임 수 `2693` 이 정확히 일치했다.)

### ④ 🔑 `errno=54` 의 정체 — **장치가 스스로 끊는 것**이다

서버·장치를 처음으로 맞춰 봤다(루트가 "아무도 이 대조를 못 했다"고 한 그것):

```
장치                                        서버
12:17:51  [AT] resync
12:17:56  [AT] resync
12:17:57  [AT] resync
12:17:58  [AT] resync            ← 7초에 4회
12:17:58  [LINK] closed reason=send_fail_x3   ★ 장치가 의도적으로 끊었다
                                          12:18:07  errno=54 (9초 늦게 감지)
12:18:46  [LINK] reconnect ok 46847       12:18:46  세션#65 개시
```

- `errno=54`(ECONNRESET)는 "상대가 죽었다"가 아니라 **펌웨어의 정상 복구 동작**이다.
  연속 3회 전송 실패 → 링크 포기 → 재연결.
- **서버는 9초 늦게 안다.** 서버 로그만으로 시각을 논하면 최대 9초 오차.
- **장치측 링크 포기 4회 vs 서버 세션 종료 1회.** 재연결 소요가 갈랐다:
  `2973 · 2974 · 2975 · 46847 ms` — **빠른 3회는 TCP 세션이 살아남았고 느린 1회만 끊겼다.**
  → 서버 지표만 쓰면 링크 포기를 **4분의 1로 과소 계상**한다.

### ⑤ `[AT] resync 연발` — 선행 지표 **후보**(지표 아님)

판정창 resync 93회 중 연발(15초에 3회 이상) 5건, 그 중 4건이 링크 포기로 갔다.
**끊김 4건 전부 연발이 앞섰다(재현율 4/4).** 서버 지표는 전부 사후적인데 이건 **수 초 전에** 움직인다.

⚠ **표본 5건이다. 비율(80%)로 말하면 안 된다.** 내 도구가 처음엔 `67% (선행 지표로 쓸 만하다)`
라고 출력해서 **표본 10건 미만이면 판정 문구를 못 내도록 코드에 가드를 박았다.**
규칙을 사람 머리에만 두면 도구가 대신 성급한 결론을 낸다.

### ⑥ 11:15~11:26 무전송의 정체 — 사용자가 ESP 전원을 내렸다

캐패시터 교체(2200µF→100µF) 때문이다. 그 구간 `[TX-DROP]` 100% · `seq=0` 고정.

### 5.1 `soak_stats.py` 사양 (핵심 도구)

- **날짜 복원**: 로그는 `HH:MM:SS` 만 찍고 날짜가 없다. 시각이 **1시간 이상 뒤로 점프하면 다음 날**로
  세고, **마지막 줄을 기준일에 앵커링**한다(뒤에서 앞으로).
- **파싱 대상**(개별 이벤트 줄만. `⏱ 소크 …` 누적 요약은 **쓰지 않는다**):
  - `←ARD S,seq,occ,res,uptime,dev,cksum` → 프레임. **5번째 필드가 uptime(초)**
  - `! 체크섬 불일치 — 버림` → **직전 `←ARD` 원문 바이트를 붙잡아** `lone_K`/`noise`/`real_S` 분류
  - `-ARD 세션#N 종료(사유) — 지속 H:M:S · 프레임 N` → 사유 정규화(errno=54/60/재접속/상대가닫음/서버종료)
  - `↻ 재전송` · `! ACK 타임아웃 최종 실패` · `! 아두이노 오프라인 판정` · `= 아두이노 온라인 복귀 — 복구 X초`
  - `⏱ 소크 관측 시작` / `▣ 소크 종료` → **서버 재기동 감지**(구간 안에 있으면 경고)
- **필수 건전성 검사 3개**:
  1. 서버 로그 최신성
  2. 🔴 **마지막 S 프레임 경과**(120초 초과면 경고) — 서버는 프레임이 0 이어도 60초마다 요약을
     계속 찍어서 **장치가 죽어도 건강해 보인다.** 실제로 이 구멍에 빠졌다
  3. **무전송 누적시간**(120초 초과 공백의 합) — 열린 창은 죽은 시간을 빨아들여
     프레임/분이 서서히 떨어지고 **회귀처럼 보인다.** 벽시계 길이와 프레임이 흐른 길이를 갈라 적어라
- **기대값 표**: 기준 구간 발생률 × 대상 구간 길이. **기대값 1 미만이면 `0` 은 아무것도 증명 못 한다**를 명시

### 5.2 `esp_events.py` 사양

세션 종료마다 **직전 프레임 uptime** 과 **재접속 후 첫 프레임 uptime** 을 벽시계 경과와 비교:

```
uptime_after ≈ uptime_before + 벽시계경과   → ESP단독(MCU 는 계속 돌았다)
uptime_after 가 그보다 훨씬 작음            → MCU재부팅
uptime 이 뒤로 갔으면 → 허용오차 무관하게 재부팅  ★ 이 규칙이 없으면 짧은 공백에서 오분류난다
```

**팀 개입(점 ±60초 / 구간 겹침)이 걸리면 판정 보류.** 개입 목록은 `interventions.py` 로
`arduino/INTERVENTIONS.md` 에서 **직접 읽는다**(손으로 베끼지 마라 — §3-② 가 그 사고다).

검증용 앵커: uptime `49948` → 13.87시간 전 부팅 = **20:32:16**, INTERVENTIONS.md 의 재플래싱 시각과 일치.

### 5.3 `interventions.py` 사양

`arduino/INTERVENTIONS.md` 의 표를 파싱. `MM-DD HH:MM(:SS)` 은 **점**, `HH:MM~HH:MM` 은 **구간**.
`~` 접두는 대략. **표 줄은 있는데 시각을 하나도 못 뽑으면 예외를 던지고 멈춘다.**

### 5.4 `serial_stats.py` 사양

`[TX-DROP] … run=N` 은 속도 제한 형식이라 **`end run=N` 의 N 이 그 에피소드의 실제 시도 수**다
(시작 줄을 세면 안 된다). `[LINK] closed reason=` · `reconnect ok <ms>` · `[AT] resync` ·
`[RAM] free/min` · `[BOOT] n=`. **판정 문구는 표본 10건 미만이면 내지 마라**(§3-⑤).

### 5.5 `serial_tap.py` 사양

`arduino-cli monitor` 를 쓰지 마라 — **stdin 이 닫히면 즉시 죽어 0바이트 로그가 남는다.**
pyserial 로 직접 열고 **서버 로그와 같은 `HH:MM:SS` 타임스탬프를 붙여라**(대조가 목적이므로 필수).
원시 바이트 사본(`.raw`)도 같이 남긴다. 포트 오류 시 죽지 말고 3초 후 재시도.

### 5.6 재집계 명령 (판정창 확정)

```bash
python3 monitor/soak_stats.py \
  --win old=2026-08-15T18:42:39..2026-08-16T10:34:15 \
  --win verdict=2026-08-16T11:27:00..2026-08-16T15:27:00 \
  --baseline old --base-date 2026-08-16
```

**교정 기준**(파서가 맞는지 먼저 확인 — 어긋나면 펌웨어 발견이 아니라 파서 버그다):
옛 구간이 **15.86h · 47,571 프레임 · 체크섬드롭 16 · 세션종료 56 · errno54 12 · uptime역행 7** 이어야 한다.

## 7. 다시 밟지 말아야 할 함정 (오늘 실제로 밟은 것들)

| 함정 | 어떻게 드러났나 |
|---|---|
| `grep` 에 `-a` 안 붙임 | 결과가 조용히 숨는다. 넷이 당했다 |
| 집계 숫자만 보고 원문 안 봄 | 체크섬 "100배 악화"가 허상. **오늘만 4번 반복된 형태** |
| 개입 목록을 손으로 베낌 | 10:27:44 를 빠뜨려 "전원 사건"으로 오판(§3-②) |
| 열린 창이 죽은 시간을 삼킴 | 프레임/분이 떨어져 회귀처럼 보임 |
| 로그 최신성만 검사 | 서버는 프레임 0 이어도 요약을 계속 찍어 건강해 보임 |
| 작은 표본으로 비율 주장 | 내 **도구가** n=3 에 "쓸 만하다"를 출력. 코드에 가드를 박아 막았다 |
| 겹친 원인 중 하나가 밝혀지자 나머지를 지움 | "ESP 가 물려 있다" 추정을 과하게 철회했다. 실제로 맞았다(§3-⑥) |

**공통 형태: 원본이 있는데 요약만 봤다.** 오늘 팀이 낸 오판은 거의 전부 이것이다.
