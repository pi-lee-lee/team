# 설계 확정 — 반송파 슬롯 구조 (2026-08-17)

**사용자 결정이다.** 이 문서가 원본이고, 각 도메인 설계는 여기서 파생된다.

---

## 사용자가 정한 것 (원문 그대로)

> 1. 웹화면에서 사용자가 눌러서 보내는 전송은 1초 단위의 아이들로 막으면서 진행한다.
>    (사용자가 막 눌러서 이게 쌓여서 동작하는 방식은 사용자 경험에 어긋난다. **1액션 1피드백**이 적합하다.)
> 2. 서버에서 추가적으로 보내야 할 내용이 발생하면 사용자 이벤트 등과 **묶어서** 송신한다.
>    1.2초 인터벌 전송에 **모아서** 발송한다.
> 3. 서버와 esp01 구간의 송수신은 **1.2초 텀** 그리고 송수신 간 차이는 **0.6초**로 동작하도록 한다.
> 4. **이벤트가 발생한 시점에 전송이 아니라**, 전송 구간은 1.2초 간격으로 **계속 통신하고 있고**
>    해당 통신에 발생한 이벤트를 **실어 보내는** 구조로 작성한다.

## 4번이 이 설계의 전부다 — 왜 고장이 사라지는가

**지금까지 관측된 고장은 전부 양의 되먹임이었다.**

```
옛 구조 (이벤트가 전송을 만든다)
  이벤트 ↑ → 전송 ↑ → 귀 막힘 ↑ → 버퍼 넘침 ↑ → ACK 실패 ↑
         → 서버 재전송 ↑ → 하행 ↑ → ACK 송신 ↑ → (처음으로)
  ⇒ 스스로 커진다. 임계를 넘으면 리셋까지 간다.

새 구조 (전송은 상수, 이벤트는 화물)
  이벤트 ↑ → 전송 횟수 그대로 → 한 프레임의 크기만 ↑
  ⇒ 구조적으로 커질 수 없다.
```

부하가 바꿀 수 있는 것은 **화물의 크기**뿐이고, 크기는 거의 공짜다
(고정비용 ≈150ms/거래 대비, 64B→200B 는 실효 속도 **1.9배 이득**).

**그래서 이건 "빠르게 만드는" 설계가 아니라 "폭주할 수 없게 만드는" 설계다.**

## 구조

```
      슬롯 1.2초
├───────────────┬───────────────┤
│  0 ~ 600ms    │  600 ~ 1200ms │
│  장치 송신     │  장치 수신 전용 │
│  (서버 수신)   │  (서버 송신)   │
└───────────────┴───────────────┘
   ↑
   장치가 첫 프레임으로 슬롯 시작을 알린다 (시계 동기 없음)
```

- **슬롯 시작은 시계가 아니라 사건이다.** 장치의 프레임 도착이 t0.
  → 장치가 느려지면 서버 슬롯도 같이 밀린다. **자기교정된다.**
- **수신 창에는 한 바이트도 쓰지 않는다.** 이것이 손실 0 의 직접 원인이다
  (fdtest 1판 `gap=36 bad=32` → 2판 `gap=0 bad=0`).

## 방향별 규칙

### 상행 (장치 → 서버) — 슬롯당 정확히 1거래

- 슬롯마다 **반드시** 보낸다. 보낼 게 없어도 **상태 프레임이 나간다.**
  이 프레임 하나가 **세 가지를 겸한다**: 반송파 · 생존 신호 · 슬롯 시작 통보.
- 밀린 ACK 는 **전부 이 한 번에 실어 보낸다.**
  ```
  [CIPSEND] S,...\n@,3\n@,4\n@,7
  ```
- **프레임 형식은 안 바꾼다.** 한 줄 64바이트 상한(`client.ino:1508`)도 그대로.
  줄을 LF 로 이어 붙여 **한 거래에 여러 줄**을 넣을 뿐이다.
- **큐에는 바이트가 아니라 의도를 담는다**(arduino 판단).
  미뤄 둔 텔레메트리는 재생이 아니라 **재생성**해야 한다 — 옛 값을 나중에 보내면 틀린 값이다.

### 하행 (서버 → 장치) — 슬롯당 정확히 1거래

- 서버는 자기 창(600~1200ms)에 **큐에 있는 명령을 전부 묶어 한 번에** 보낸다.
- 이벤트가 발생한 시점에 보내지 않는다. **다음 창까지 큐에 담는다.**
- 창 폭 `W_srv = 600ms − RTT − 여유`, **RTT 는 측정값**(상수 아님).

### 🔴 ① 정정 — `free=1036` 은 컴파일 값이다 (arduino)

```
컴파일 표시 : 1036 B   (정적 여유)
실측 최저   :  782 B   ([RAM] 최저 여유, 13:05:44)
```

**스택은 런타임에 더 깊어진다.** 정적 값으로 잡으면 최악의 순간에 넘친다.

```
250B / 782 = 32%        300B / 782 = 38%
```

> **Uno 에서 버퍼 하나가 실측 최저 여유의 38% 면 여유가 아니다.**
> **"200~300B" 는 틀린 분모로 계산한 값이다. 굳게 두지 마라.**
> **arduino 가 782 기준으로 다시 잡는다 — 150~200B 로 내려갈 수 있고, 그러면 아래 표도 움직인다.**

### 🔴 고정비용이 실측됐다 — 그리고 **내가 뿌린 표는 과장이었다** (cipsize 프로브)

```
promptms = 3ms 고정        ← 상한 300ms 대비 100배 여유
okms     = 16~40ms         ← 상한 2000ms 대비 50배 여유
```

**내 추정(프롬프트+SEND OK = 55ms)은 실제(19~43ms)와 가까웠다. 문제는 다른 데 있었다:**

```
내가 쓴 고정비용 150ms  =  SEND_GAP 80  +  명령 15  +  왕복 55
                            ↑↑↑ 이 80 이 슬롯 설계에서는 0 이다
```

> ### 🔑 **`SEND_GAP_MS=80` 은 "연속 `CIPSEND` 사이 최소 간격"이다.**
> **슬롯 설계는 1.2초에 한 번만 보낸다 — 연속 전송이 아예 없다. 이 대기는 발생하지 않는다.**
> **즉 내가 계산한 고정비용의 절반 이상이 새 설계에는 존재하지 않는 값이었다.**

**실제 고정비용 ≈ 명령 15 + 프롬프트 3 + `SEND OK` 16~40 = 34~58ms (≈46ms)**

| 한 번에 | 내가 뿌린 값 (고정 150ms) | **실측 기반 (고정 46ms)** |
|---|---|---|
| 64 B | 295 B/s | **568 B/s** |
| 200 B | 559 B/s | **787 B/s** |
| 300 B | — | **836 B/s** |

```
64→200 배치 이득 :  1.9배 (내가 말한 것)  →  🔴 실제 1.4배
```

### ⚠ 그래서 배치의 근거가 바뀐다 — 약해지는 게 아니라 **다른 것으로 바뀐다**

**"묶으면 빠르다"는 내가 말한 것보다 약하다.** 그러나 슬롯 설계에서 배치의 이유는 속도가 아니다:

> ### **슬롯당 1거래가 규칙이다. 3건을 보내려면 묶는 것 말고 방법이 없다.**
> **안 묶으면 3건에 3.6초가 걸린다.** 배치는 최적화가 아니라 **구조적 필수**다.

**결론은 그대로고 근거가 더 강해졌다.** 다만 **1.9배라는 수를 인용하지 마라 — 1.4배다.**

## ✅ 하행 상한 확정 — **`rxmax` = 창당 540 바이트** (fdtest 4판 · REQ-0157 · 2026-08-17 19:5x)

```
확정값  :  rxmaxb = 540 B / 창          ← 이것을 쓴다
건수    :  9 ~ 32 건 (프레임 크기에 따라 갈린다)   ← 🔴 쓰지 마라
```

**4판이 바이트 불변량을 관측으로 확인했다.** arduino 가 **자료를 보기 전에 예측을 등록**했고
(`rxmaxb` 540~576 수렴 · 건수는 크게 갈림) 프레임 크기를 바꿔 가며 검증했다.
→ **건수 상한은 한 건의 크기가 바뀌는 순간 거짓이 된다. 바이트가 불변량이다.**

### 🔴 3판의 `600ms × 960B/s ÷ 40B = 14.4건` 은 **계산이 틀렸다** (arduino 정정)

프레임 크기를 40B 로 잡았는데 **실제는 33~34B** 였다. 바른 계산은 **16.9~17.5건**이고
실측 16 은 그 **92~95%** 다.

> ⚠ **틀린 것을 붙잡을 기회가 있었는데 문서가 놓쳤다.**
> **실측 16 이 계산 상한 14.4 를 넘은 것 자체가 "계산이 틀렸다"는 신호다.** 그런데 이 문서는
> 그걸 *"창 경계 걸침 포함"* 으로 흡수하고, 심지어 **"예측이 맞았다"고 승리 선언**까지 했다.
> **상한을 넘는 실측은 흡수할 것이 아니라 상한을 의심할 근거다.**

**결론은 살아남고 오히려 강해진다** — 실측이 회선 상한의 92~95% 이므로
**장치는 병목이 아니다. 회선이 병목이다.** (원장 §9.3 에 정정 기록)

### (참고 · 3판 원자료)

```
장치 : gap=0  bad=0  availhi=35/64  rxmax=16  defer=239  qdrop=99
```

### 🔴 `cap` 을 **건수로 잡지 마라. 바이트로 잡아라.**

`rxmax=16` 은 **40바이트 프레임**을 **하드웨어 UART**로 잰 값이다. 실기는 둘 다 다르다.

```
창당 회선 용량 = 600ms × 960 B/s = 576 바이트     ← 이게 진짜 상한이다
프레임 하나의 실제 비용 = 페이로드 + LF + "+IPD,<n>:" 접두(8~9B)
```

| 실제 명령 크기 | 프레임당 비용 | 창당 건수 |
|---|---|---|
| 19B (`R,1,A1,00000000,13`) | 19+1+8 = **28B** | **≈20건** |
| 40B (fdtest 프레임) | 40+1+8 = **49B** | **≈11.7건** |

**건수는 프레임 크기에 따라 20건도 되고 12건도 된다. 고정값이 아니다.**
`576 바이트`가 불변량이다.

### 🔑 그리고 배치가 하행에서도 접두를 없앤다

ESP 는 **받은 TCP 조각마다** `+IPD` 를 붙인다 — **줄마다가 아니다.**

```
따로 10번 보내면 :  "+IPD,19:" × 10  =  접두 80~90 바이트   (창의 15%)
묶어 1번 보내면  :  "+IPD,199:" × 1  =  접두  9 바이트
```

**상행에서 거래 횟수를 아끼는 것과 같은 이유로, 하행에서는 접두를 아낀다.**

⚠ **다만 한 줄 상한이 있다**: `RX_CAP=96`(`client.ino:368`)이고 **접두가 그 안에 포함된다**
→ **한 줄의 페이로드는 87바이트를 넘으면 안 된다.** 배치 전체 크기가 아니라 **줄 하나**의 제약이다.
(TCP 가 조각을 나눠 `+IPD` 가 여러 번 와도 파서는 LF 로 가르므로 문제없다.)

### ⚠ 이 값을 그대로 실기에 옮기지 마라 (arduino 경고)

**하드웨어 UART(맥 직결) 기준이다.** 실제 경로는 아직 `SoftwareSerial` 이고,
**슬롯이 겹침을 없애도 `cli()` 는 남는다.** 실기 재측정 전까지 **`576B` 는 상한이지 보장이 아니다.**

### 큐 깊이 — 새로 나온 제약

3판에서 `qdrop=99`(35슬롯 × 2.8)가 났다. 원인은 손실이 아니라 **큐가 얕아서**다.

> ### **깊이 ≥ 수신 창 ÷ 이벤트 간격**

실기로 옮기면 **한 슬롯의 수신 창에 도착할 수 있는 하행 수**가 그 값이다.
**현재 8바이트 설계(깊이 4)는 하행이 슬롯당 4건을 넘으면 버린다.**

### 계측 정정 (arduino 자진 철회)

- **2판의 맥 `gap=37` 은 "맥 쪽 문제"가 아니었다 — arduino 자신의 `seq` 버그**였다
  (큐에서 꺼내 보낼 때 `txSeq` 를 안 올려 같은 번호가 두 번 나갔다). 고쳐졌다.
- **3판의 맥 `gap=104` 는 `qdrop=99` 와 같은 사건이다.** 장치가 큐 넘침으로 의도를 버리면
  그 `seq` 는 영영 안 나가고, 맥은 번호 건너뜀으로 본다. **두 계기가 같은 것을 양쪽에서 셌다.**
  → **전송 경로에서 잃은 것은 하나도 없다.**
- 계측 결함 3건 전부 수정: `defer` 47,581→239 · `rxmax` 슬롯→창 기준 · `seq` 중복.

## 화면 (1번)

- **1액션 1피드백.** 누른 뒤 **1초 아이들**, 남은 시간이 눈에 보인다.
  조용히 무시하면 안 먹혔다고 생각해 더 세게 누른다 — 막으려는 것을 만든다.
- 전역이다(자리별이면 10칸을 돌아가며 눌러 통과한다). 같은 자리 연타는 서버 `has_pending_for` 담당.
- **실제로 나간 경우에만** 아이들 시작 — 실패까지 세면 복구 직후 1초를 못 누른다.
- 서버 응답에 `queued` 가 생겼다: **"받았고 아직 안 보냈다"**.
  이전엔 성공/실패 둘뿐이라 **밀어 넣는 쪽이 자기가 밀어 넣는 줄 몰랐다.**
- 화면 타임아웃은 서버가 준 `expires_ms` 에 묶는다 — 안 그러면 롤백 후 재클릭이 새 rid 로 또 쌓인다.

### ✅ `queued` 는 **구현됐다** (2026-08-17 20:0x · 아래 절이 낡았다)

> **아래 "미구현" 절 전체가 낡았다. 인용하지 마라.** web 이 REQ-0162 §② 로 정정을 올렸다.
>
> | 위치 | 이 문서가 적었던 것 | 실제 |
> |---|---|---|
> | 이 절 | `index.html` 에 `queued` **0건** | **커밋 `d2ae90a`(18:57:21)에 구현** · 현재 **6건** |
> | §배정 web 표 | `queued` 수신 처리 + `expires_ms` 🔴 미구현 | ✅ 구현 + REQ-0159 에서 실측 |
> | §배정 web 표 | 거짓 문구 "브라우저 재측정 미완" | ✅ **실제 WS 경로 3/3** (web FINDING §7.1) |
> | §배정 web 표 | 1초 아이들 "실제 WS 미확인" | ✅ **실측** (`blink.mjs --case D` · 1065ms 해제) |
>
> 🔴 **왜 이 오류가 생겼나 — 루트의 근거가 낡은 문서였다.**
> 이 문서를 쓴 시점(19:15 이전)에는 참이었다. 그런데 `d2ae90a` 가 **18:57 에 이미 들어와 있었다** —
> 즉 **쓰는 순간에도 이미 낡아 있었다.** 그리고 나는 REQ-0159 를 "🔴 미구현 — 지금 착수"로
> 발행했다. **이미 된 일을 시킨 것이다.**
>
> ⚠ web 도 같은 함정을 반대 방향으로 밟았다(REQ-0162 §①): 자기 원장의 낡은 문장을 인용해
> **끝난 일 둘을 "대기 중"으로 보고**했다. 원장은 append 가 기본이라 낡은 문장이 지워지지 않는다.
>
> **→ 규칙(web 이 §5.22 로 남겼고 여기서도 채택한다): "됐다/안 됐다"를 문서에서 인용하지 마라.
> 대상 파일의 커밋 시각을 봐라.** 문서는 시점의 스냅샷이고, 이 팀은 문서를 빨리 쓴다.

### 🔴 (낡음 · 2026-08-17 19:15 시점 기록) `queued` 는 계약만 합의됐고 화면은 미구현이다

초판 배정표에 `queued 표시 ✅` 로 적었던 것은 **오기다**(web 이 잡았다).
`조별과제샘플/index.html` 에 `queued` 문자열 **0건** — 루트가 직접 확인했다.
⚠ **그 확인 자체도 근거가 부실했다**: web 이 REQ-0159 §0 에 인용한 `git grep … HEAD~1 → 0건` 을
**아무도 실제로 돌리지 않았고**, 돌려 보니 6건이었다(web 이 §⑤ 로 자진 철회). 결론은
커밋 시각만으로 성립하므로 바뀌지 않지만, **돌리지 않은 명령을 근거로 적은 것**은 그대로 기록해 둔다.
REQ-0155 에서 한 것은 **socket↔web 계약 합의뿐**이고, socket 이 "값이 나오기 전에 만들지 마라"고
해서 일부러 안 만들었다. 지금은 **`queued` 가 와도 조용히 무시된다.**

**이게 표시 누락으로 안 끝나는 이유**(web 지적):
같이 안 된 것이 **`expires_ms` 타이머 연동**이라, 큐에서 6초를 넘긴 요청을 화면이
**"응답이 없어 되돌렸습니다"로 잘못 롤백한다** → 사용자가 다시 누른다 → **새 rid 로 큐에 한 건 더.**
**즉 우리가 닫으려던 증폭 고리가 바로 이 칸에서 아직 열려 있다.**

**순서 판정: `rxmax` 를 기다리지 않고 지금 만든다.**
`expires_ms` 는 **서버가 값으로 주는 것**이라 화면은 받은 값을 쓸 뿐 상수를 박지 않는다.
`rxmax` 에 걸린 것은 서버의 `cap`(큐 깊이 = 언제 `queue_full` 을 돌려주나)이지 **화면이 아니다.**
socket 의 "만들지 마라"는 **`cap` 에 대한 것이었고 화면에는 걸리지 않는다.**

#### 한 단계 더 — 서버의 `expires_ms` 도 `rxmax` 가 필요 없다 (socket 정정)

루트가 "화면 vs `cap`"으로 가른 것은 **덜 갈랐다.** 배치 확정이 의존성 자체를 바꿨다:

```
슬롯 N 중에 생긴 명령 → 슬롯 N 의 창에서 전부 한 번에 나간다
→ 정상 항목의 대기는 최대 한 슬롯(≈1.2초)
→ 바이트 한도를 넘을 때만 나머지가 다음 슬롯으로 밀린다
```

**`expires_ms` 의 상한이 슬롯 주기만으로 나온다.** `rxmax` 가 걸리는 것은
"한 배치에 몇 바이트를 싣나 → 그걸 넘을 때 `queue_full` 을 언제 돌려주나" **하나뿐이다.**

| 항목 | `rxmax` 필요? |
|---|---|
| `queued` 를 보내는 것 · `ahead` | ❌ |
| `expires_ms` | ❌ **슬롯 주기에서 나온다** |
| **`queue_full` 문턱(큐 깊이)** | ✅ |

**결정적 이유는 따로 있다**: 서버가 `queued` 를 **안 보내면 web 이 화면을 만들어도 끝까지 못 잰다.**
그리고 증폭 고리는 **`expires_ms` 가 실제로 흘러야 닫힌다** — 화면만 만들면 반쪽이다.

→ **`queued` · `ahead` · `expires_ms` 지금 구현. `queue_full` 문턱만 `rxmax` 뒤.**

🔴 **그동안 큐는 무한이다.** 임시 상수로 깊이를 막되 **값이 아니라 "임시라는 것"을 기록한다.**
아래 §미해결 5번에 올려 둔다 — **표시하지 않은 임시값은 영구값이 된다.** 이 문서가 방금 그걸로 한 번 데었다.

### ⚠ 남은 불일치 하나 (판단 필요, 급하지 않음)

**아이들 1.0초 < 슬롯 1.2초.** 이론상 사용자가 슬롯이 실어 나르는 것보다 빨리 만들 수 있다.
- 실제로는 문제 안 된다: 큐가 흡수하고 `queued` 로 **보이게** 된다(조용히 사라지지 않는다).
- 정확히 맞추려면 아이들을 **슬롯 주기와 같게** 하면 된다. 한 줄 변경이다.
- **지금은 1.0초로 간다** — web 이 이미 만들고 크롬으로 확인했다. 재작업 가치 없음.

   ### ✅ ③ 판정 — **조용한 잘림은 없다** (2026-08-17 19:15 · 커밋 `1299286`)

   서버 쪽에서 수신 바이트를 대조해 닫았다. **18/18 전부 `rx+1 == sent`**, 뒤쪽 대조군도 앞쪽과 같다.

   🔴 **범위를 넘겨 인용하지 마라**: **그 보드 · 그 AT 빌드 · 상행만**이다.
   **하행은 이 시험이 안 다뤘고, 576B 창 계산은 여전히 미검증이다.**

   > 이 시험이 성립하려면 **서버를 먼저 고쳐야 했다**: `MAX_LINE=64` 가 체크섬보다 먼저 버리고
   > `ard_buf` 를 도착 중에 비웠다. 그대로 갔으면 원인이 AT 잘림이 아니라 **우리 상수**인데
   > **관측이 같아서** 틀린 결론을 얻는다. 그리고 `rx=` 를 `verify_line` **앞**에 둔 것이 결정적이었다 —
   > 꼬리가 잘리면 체크섬이 사라지므로, 뒤였으면 **정확히 표적인 ③ 에서만 로그가 안 남는다.**

   **덤으로 얻은 ESP 사실 둘** (어느 계열이든 유효):
   - **`AT+CIPSTART` 응답은 `CONNECT` 가 아니라 `Linked`** 다. `CONNECT` 로 기다리면 8초를 헛기다리고
     그 사이 **서버의 미등록 소켓 마감(7초)** 이 걸린다. → 접속 직후 등록 프레임을 보내야 한다.
   - **체크섬은 마지막 쉼표를 포함**해 XOR 한다(서버 규칙). 제외하면 온전히 도착해도 서버가 버린다.

   > ⚠ **계측 도구가 대상의 규칙을 틀리게 구현하면 그 오차가 표적과 같은 칸에 들어온다**(arduino).
   > 체크섬을 안 맞췄으면 **정상 도착이 ③ 과 구별되지 않았다.** 오늘 `esprst` 오탐과 같은 형태다.

   **대조군(40B)이 즉시 값을 했다** — 맨 앞부터 실패해서 **"크기 문제가 아니라 설정 문제"가 1초 만에 갈렸다.**
   없었으면 **"40 도 실패"를 크기 결론으로 오독**했다. 크기마다 3회 반복도 같은 역할을 했다.

   🔴 **"깨진다"에 세 가지가 숨어 있고 위험도가 다르다:**
   ```
   ① '>' 가 안 온다        → 장치에서 보인다
   ② SEND OK 가 안 온다    → 장치에서 보인다
   ③ 둘 다 오는데 서버가 받은 바이트가 더 적다  → 🔴 장치에서 안 보인다
   ```
   **③ 이 실제로 위험한 것이고, 일부 AT 빌드의 알려진 동작이다.**
   장치 쪽만 보면 **조용한 잘림이 PASS 로 읽히고 배치 설계 전체가 거짓 바닥 위에 선다.**
   → **같은 회차에 서버 쪽에서 수신 바이트 수를 대조하는 것이 합격 조건이다.** ✅ 그렇게 했다(위 판정).
