**`슬롯` 을 쓰지 않는다.** 이 프로젝트에서 그 낱말이 **두 것**을 가리켰다 —

## 1. 세 층 — 자료 구조 `[확정: 루트 골격]` + `[내 판단: 필드 배치]`

```
Node   통신 단위. **지금 Server 에 전역으로 있는 상태를 여기로 내린다**
  devid                     전선의 장치 id (1~8자 · §2.3)
  sock · rxbuf · last_ms    수신 경로
  downq · downq_bytes       🔴 하행 큐 **한 벌**
  rtt_max_ms · rtt_n        그 노드의 왕복 실측(세션마다 초기화)
  win_skips · dmax_flushes · q_deferred · q_rejected · q_nodev · batch_count · batch_lines
  online · offline_since_ms  🔴 **노드별로 판정한다**(§4)
  modules: name → Module     그 노드가 가진 모듈들

Module 신원은 **복합 키 `(devid, name)`** 다
  name        🔴 **그 노드 안에서만 유효하다.** name 만으로 조회 금지
  kind        주차확인센서 · 안내등 · 유도등 · 차단봉 · 입출차센서
  idx         🔑 **상태 비트열에서 이 모듈이 차지하는 자리**(§5 등록이 정한다)

Zone   격자 위의 자리
  id          전역 고유
  kind        parking | entrance | exit
  modules: [(devid, name), …]   🔴 **여러 노드에 흩어질 수 있다**
```

**격자는 좌표 → `zone id` 사상이다. 좌표와 신원은 독립이다** `[확정]` —
자리를 옮겨도 같은 자리여야 하므로 **`zone id` 는 좌표에서 유도하지 않는다.**

### 🔴 자리 : 칸 = **1 : 1** `[확정: 사용자 2026-08-18]` — 그러나 **구조는 N:1 을 막지 않는다**

```
Zone
  id                        전역 고유 · **좌표에서 유도하지 않는다**
  kind                      parking | entrance | exit
  cells: [(row, col), …]    🔑 **지금은 항상 길이 1이다.** 목록인 것은 구조뿐이다
  modules: [(devid, name), …]
```
> ### **`cells` 를 목록으로 두되 `길이 1` 을 지금 코드가 강제한다.**
> **N:1 을 지금 구현하지 않는다** — 🔴 **쓰이지 않는 일반화는 검증되지 않은 코드다.**

🔑 **이렇게 하면 나중에 안 깨지는 이유**: 좌표를 `zone` 필드에 하나만 박아 두면(`row`·`col`)
큰 자리가 생길 때 **자료형이 바뀌고 그것을 읽는 모든 곳이 같이 바뀐다.** 목록이면 **길이 제한만 푼다.**
⚠ **그 대신 지금 검증을 넣는다**: 등록·설정 적재 시 `cells.size() == 1` 이 아니면 **거절하고 로그**.
**목록으로 두는 것과 아무 길이나 받는 것은 다르다** — 후자는 **검증되지 않은 경로를 여는 것**이다.

⚠ **격자 5×5 · 입구/출구 가장자리는 기본값이다** `[확정: 사용자]`. **설정으로 바뀐다.**
**구조가 5×5 에 묶이면 안 된다** — 코드에 `5` 를 박지 말고 **설정에서 읽은 `rows`·`cols`** 를 쓴다.

### ⚠ 모듈 `name` 은 **고유값이 아니라 명칭이다** `[확정: 사용자]`

**사람이 읽는 이름이다.** 그래서 **조회 키가 될 수 없고** 신원은 항상 **`(devid, name)`** 이다.
🔑 같은 `name` 이 다른 노드에 또 있을 수 있다 — **그게 정상이고, 그래서 복합 키다.**

> ### 🔴 `zone.modules` 를 `[name]` 으로 적으면 안 된다 `[확정: 루트]`
> `name` 은 노드 안에서만 유효하므로 **어느 장치인지 사라지고 보낼 곳을 모른다.**
> 반드시 **`(devid, name)`** 쌍으로 적는다.

## 2. 큐는 **노드마다 복제된다. 규칙은 한 글자도 안 바뀐다** `[확정: 사용자]`

> 사용자: *"1.2초내에 발생한 이벤트는 모아서 보내고, 모은 것보다 많은 데이터는 1.2초 뒤에 보내거나
> 1.2초 인터벌을 넘는 이벤트들을 0번 슬롯 보내는 것이다. **작동은 해야 한다!! 없애는 것이 아니다**"*

**현행 `flush_downq()` 가 이미 그 문장이다.** 바뀌는 것은 **그 상태 한 벌이 노드마다 있는 것**뿐이다.

```
지금 : Server 에 downq 한 벌            → 노드 하나만 대상이 된다
개정 : Node 마다 downq 한 벌            → 각 노드가 자기 주기·자기 창·자기 큐
```

### 🔴 약해지면 창4 기전이 돌아온다 — 지우지 말 것 목록 `[확정]`

| 항목 | 없으면 |
|---|---|
| `DOWN_BATCH_CAP_B`(바이트 상한) | 한 거래가 UART 를 너무 오래 붙잡아 장치 송신과 겹친다 |
| `q_deferred`(미룬 창 수) | 지연이 아무 데도 안 보인다(§5.2) |
| `D_max` 창 포기 **박자** | 침묵 구간에 200ms 버스트가 된다(§8.23-(28) 실측) |
| `queued` 응답 | 화면이 거짓 롤백하고 재클릭이 큐를 늘린다 |
| 배포 순서(큐를 `queued` 보다 먼저 올리지 않는다) | 그 사이 구간에 증폭 고리가 열린다 |

### 🔑 노드가 여럿이어도 **동시 전송은 자유다** `[확정: 사용자]`

**슬롯이 막는 것은 "같은 ESP 에게 주기 안에 두 번"이다.** 다른 ESP 는 **다른 UART·다른 소켓**이다.
→ 서버는 **N 개 소켓에 같은 순간에 write 한다. 시계 동기가 필요 없다.**
🔴 **위상 정렬을 설계하지 마라** — 그것은 `t0` 를 시계로 만드는 것이고 이 설계가 일부러 버린 것이다.

## 3. 하행 라우팅 `[확정: 루트]`

```
"zone A1 의 안내등을 켜라"
  → zone(A1).modules 에서 kind=안내등 인 (devid, name) 을 찾는다
  → Node(devid).downq 에 담는다                  ← **여기서 전송하지 않는다**
  → 그 노드의 S 가 도착하면 flush                ← 창당 1거래가 **노드별로** 지켜진다
```

⚠ **한 자리의 모듈이 여러 노드에 흩어져 있으면 하행이 여러 노드로 갈라진다.**
그러면 **그 명령의 완료 시각이 노드마다 다르다** `[내 판단]` — 그것을 하나의 "성공"으로 합치지 않는다.
**모듈 단위로 ACK 를 짝짓고, 자리 단위 상태는 그 합으로 표시한다.**

## 3.5 🔴 자리가 여러 노드에 걸칠 때의 **완료 판정** `[내 판단 · 내가 계산 주체다]`

> ### ⚠ **2026-08-19 — 이 절은 살아 있다. 다만 *아직 구현되지 않았다.***
> **지금 서버가 내보내는 것은 §7.2.1 의 `completion` 문자열 하나뿐이다.**
> `action_state`·`ok`·`total`·`missing[]` 은 **설계이고 코드가 없다.**
> 🔑 **화면은 실기에 맞춰 짜라.** 이 절은 **모듈이 여럿인 자리가 생길 때 넓힐 방향**이다.
> **지우지 않는 이유**: 여기 담긴 판단(*"하나라도 미확인이면 완료가 아니다"*, *"`partial` 은 일시 상태여야 한다"*)이
> **§7.2.1 의 `mismatch` 를 만든 근거**다. 결론만 바꾸면 다음 사람이 같은 길로 다시 간다.

**언제 생기나**: `reserve` 는 예약 상태를 바꾸고 서버가 **안내등·유도등**을 파생시킨다(§6.5 표).
그 모듈들이 **다른 노드에 있으면 한 조작이 하행 여럿으로 갈라진다.**

##### 규칙 — **"완료"라는 낱말은 전부 확인됐을 때만 쓴다**

```
done    = 대상 모듈 **전부** 의 에코가 기대값과 일치     ← 이때만 "완료"다
partial = 일부만 일치. **어느 것이 남았는지 함께 준다**
failed  = 재시도 소진 또는 그 모듈의 노드가 오프라인이라 더 갈 수 없다
pending = 아직 첫 창이 안 열렸다(큐에 있다)
```
🔴 **근거는 web 의 판정이다**(§6.5 에서 채택): **거짓 차단은 못 누르는 것으로 끝나지만
거짓 완료는 안 된 것을 됐다고 말한다.** → **하나라도 미확인이면 "완료"가 아니다.**
⚠ **그렇다고 `partial` 을 감추면 안 된다** — 감추면 **"미완료"가 "아무것도 안 됐다"인지
"일부만 됐다"인지 안 갈린다**(§5.2 의 그 자리).

##### 🔑 `partial` 은 **일시 상태여야 한다** — 아니면 그건 `partial` 이 아니다

에코가 있으므로 **서버가 남은 모듈만 재하달한다**(§8.21 자가 치유의 확장 · §6.5).
→ **정상 경로에서 `partial` 은 다음 창에 해소된다**(그 노드 기준 ≤1 주기).

> ### **`partial` 이 오래 지속되면 그것은 진행 중이 아니라 그 모듈이 막힌 것이다.**
> → **그 모듈을 `blocked_reason` 으로 내리고 자리는 `partial` + 그 사유를 함께 준다.**
> **"오래"의 문턱은 그 노드의 주기에서 유도한다**(값 박지 않는다 · `REG_TIMEOUT` 과 같은 규율).

##### 화면에 주는 것 — **판단은 서버, 표시는 web** `[web 합의 필요]`

```
zone.action_state = { state: done|partial|failed|pending,
                      ok: n, total: m,
                      missing: [(devid, name, blocked_reason?)]   ← partial/failed 일 때만
                    }
```
⚠ **표시량이 A(칸 안에 다 보이기)로 확정됐고 한 화면에 20~30 자리다.**
→ **`ok/total` 두 수만으로 칸 안에 들어간다.**

> ### 🔴 ~~`missing` 은 펼쳤을 때만 쓴다~~ → **틀렸다. A 에서는 그릴 대상이 아니라 *표식 입력* 이다** (web 정정)
> **A 는 모듈 행이 이미 전부 보인다.** 그러므로 `missing` 은 **"무엇을 더 그릴까"가 아니라
> "어느 행에 표식(`⏱`/`⚠`)을 붙일까"를 알려 주는 입력**이다. **계열은 `blocked_reason` 이 정한다.**
> 🔑 **내가 표시량 B(펼치기)를 전제로 문장을 썼다** — 사용자가 A 를 고르면서 **자료는 그대로인데
> 쓰임이 바뀌었다.** **계약(자료 모양)은 안 바뀌었고 그 자료를 무엇에 쓰는지가 바뀐 것**이다.
> ⚠ **web 지적**: B 였다면 *"부분 완료인데 어느 모듈인지 보려면 눌러야 한다"* 가 됐을 것이다.
🔑 **그리고 위 "일시 상태" 성질이 화면 부담을 줄인다** — **정상 운영에서 `partial` 이 화면에
머무는 시간은 한 주기 남짓**이다. **오래 보이면 그건 고장 신호이지 밀도 문제가 아니다.**
**문구·기호는 web 소유다**(§6.5 와 같은 분업).

✅ **`1/1` — web 이 정했다: 숨긴다.** 근거를 내 표에서 파생시켰다 — **`total === 1` 이면
`partial` 이 구조적으로 불가능**하므로(하나는 되거나 안 된다) 수가 정보를 더하지 않는다.
→ **`ok/total` 은 `partial` 일 때만 보인다.**

##### 🔑 그리고 이 규칙이 화면 쪽 휴리스틱 하나를 없앴다 (web)

> *"오래 남는 `partial` 은 계약상 존재하지 않는다"* → **화면이 "오래 남았다"를 스스로 판정하는
> 타임아웃 휴리스틱을 두지 않는다.** 두면 *"화면이 짐작하지 않는다"* 를 어기는 것이고,
> **오래 남으면 서버가 `blocked_reason` 으로 말해 준다.** **판정이 한 곳에 남는다.**

## 4. 장치 독립 — 고장이 번지지 않게 `[확정: 사용자]`

> *"하나의 아두이노에 설치된 esp01이 와이파이를 잡지 못한다고 다른 아두이노 esp01에 영향을 주는 일은 없다."*

**지금은 그렇지 않다.** `OFFLINE_MS`·`ARD_IDLE_CLOSE_MS`·`first-S-wins` 가 전부
**"주차 노드가 하나"** 라는 전제 위에 있어 **그 하나가 죽으면 전체가 오프라인**이다.

```
개정 : online 판정을 Node 마다 한다
      → 한 노드의 오프라인은 **그 노드가 담당하는 모듈만** 미상으로 만든다
      → 다른 노드의 자리는 그대로 유효하다
```

✅ **`first-S-wins`·`aux_conflicts` 는 필요가 없어진다** `[확정: 루트]` — 그것이 있는 이유가
*"전선에 '내가 주차 노드다'라고 말하는 필드가 없다"* 인데 **모듈 등록이 장치를 명시하면 추측이 사라진다.**
**`AuxNode` 가 이미 `fd`·`buf`·`last_ms`·`frames` 를 갖고 있으므로 하행을 붙이면 곧 `Node` 다.**

⚠ **`OFFLINE_MS=3500` 은 노드별로 같은 값을 쓴다** `[내 판단]` — 노드마다 다르게 두면
"왜 저 노드만 안 끊기지"를 나중에 아무도 설명 못 한다(§1.10 과 같은 이유).

### 🔴 등록의 위험과 그 대책 — **이게 이 절의 본체다** `[내 판단 · arduino 합의 필요]`

> **등록이 유실되면 이후 모든 상태가 잘못 귀속된다.** 비트열은 **순서가 곧 계약**이기 때문이다.

**그래서 네 가지를 명세에 못 박는다:**

1. **순서가 계약이다.** 비트열 인덱스 `i` = 등록 목록의 `i` 번째 모듈. **암묵적 정렬 금지**
   (알파벳순·kind순 같은 것에 의존하면 한쪽이 정렬을 바꾸는 순간 조용히 어긋난다).
2. **폭을 명시한다.** 등록에 모듈 수 `n` 을 싣고, 상태 비트열 길이가 `n` 과 다르면 **그 프레임을 버리고 센다.**
   ⚠ **조용히 자르거나 채우지 않는다** — 그러면 어긋남이 정상 자료로 들어온다.
3. 🔴 **서버가 등록을 모르는 상태에서 상태 프레임이 오면 등록을 요청한다**(하행 `Q` 프레임 후보).
   **이유**: 서버 재기동은 장치 재접속이 아니다. 장치는 이미 붙어 있고 다시 등록하지 않는다.
   → **요청 경로가 없으면 서버 교체마다 그 노드가 영구 미상이 된다.**
   🔑 `resync_reservations()` 가 같은 문제를 이미 그렇게 풀고 있다(승격 시 서버가 먼저 말한다).
4. **미등록 상태 프레임을 조용히 버리지 않는다.** 카운터를 두고 로그에 남긴다 —
   §4.3 에서 승격 전 소켓의 줄이 **아무 카운터도 안 올리고 사라져** `버린줄 0` 이 증명이 못 됐던 그 자리다.

### ✅ arduino 합의 완료 (2026-08-18) — **내 권고 하나가 뒤집혔다**

**문자**: 하행이 받는 것은 `R`·`C`·`T`·`M` 넷뿐이다(`client.ino:2192` 확인) →
**등록 `D`(declare) · 질의 `Q`(query) 채택.** `M` 충돌 회피 확인됨.

**형식**: `D,<n>,<name1>:<k1>,…,<cksum>` · 항목 5B → **한 줄에 11개** · 여러 줄이면 **`n` 이 종료 조건**이다.
🔑 **`n` 하나가 폭 명시(위험 ②)와 종료 판정을 동시에 푼다** — 별도 "마지막 줄" 표시가 필요 없다.
⚠ 부분 유실은 **"`n` 개가 안 찼다"** 로 드러난다 → 타임아웃 + 카운터.

**🔴 `kind` 를 전선에 싣는다 — 내가 "설정으로 알면 전선이 싸진다"고 한 것을 철회한다.**
arduino 논거: **차단봉/안내등은 출력이고 센서는 입력이라 `pinMode` 가 달라 장치가 반드시 안다.**
> **장치가 이미 아는 것을 서버 설정에 복제하면 배선이 바뀔 때 두 곳을 고쳐야 하고,
> 한 곳만 고치면 조용히 어긋난다** — `SERVER_IP` 를 펌웨어에 박아 두고 IP 가 바뀌어
> 링크가 조용히 죽은 것(§5.7)과 같은 형태다.
→ **설정 파일이 진실의 두 번째 사본이 되면 안 된다.** 비용은 항목당 2B 다. **받는다.**

**비트열 폭**: 🔴 **고정 10 을 버린다. `n` 가변이다.**

### ✅ 등록 규약 확정 (arduino 합의 2026-08-18) — **마지막 합의 항목이었다**

```
① 접속 → 첫 슬롯은 `D` 만 · 둘째 슬롯부터 `S`      ← 순서가 구조적으로 보장된다
   🔑 `D` 여러 줄은 한 배치에 담긴다(LF 로 잇는 구조).
      ⚠ 그런데 `D 2줄 + S` 는 장치 상행 배치 상한을 넘으므로 **같이 못 담는다** — 그래서 슬롯이 갈린다
② 서버는 `n` 개를 다 받으면 완료. 안 차면 미완료 + 타임아웃
③ 미등록·미완료에서 `S` 가 오면 서버가 `Q` 를 보낸다 → 장치는 **다음 자기 송신 창**에 `D` 재전송
④ 미등록 상태의 `S` 를 조용히 버리지 않는다 — 카운터 + 로그
```

#### 🔴 타임아웃은 **상수가 아니라 유도값이다** — 내 `2초` 를 철회한다

내가 `2초` 를 제안했고 **arduino 가 빠듯하다고 반박했다. 맞다:**
```
접속 → 자기 송신 창까지 최대 1.2초 → `D` 송신 ≈115ms   →  총 ≈1.35초
2초면 여유 0.65초 — **재전송이 한 번 끼면 넘는다**(+1.2초). `due` 지터·게이트 대기가 그 위에 얹힌다
```
> ### **`REG_TIMEOUT = 3 × 슬롯주기`(현재 3600ms). 값으로 박지 않는다.**
> **슬롯 주기가 바뀌면 타임아웃이 따라 움직인다** — 상수로 박으면 다음에 어긋난다
> (§5.7 이 `SERVER_IP` 로 데인 그 형태 · `ack_budget_ms` 를 상수에서 계산한 것과 같은 규율).

#### ✅ `Q` 형식 — **인자 없음** `[socket 확정 · 보내는 쪽이 정본]`

```
Q,<ck>        ← 인자가 없다. 다른 프레임과 같은 체크섬 구조
```
**왜 `devid` 를 안 싣나**: `Q` 는 **특정 소켓으로 나간다. 주소는 소켓이 이미 갖고 있다.**
그리고 **이 시점의 `devid` 는 서버가 확신할 수 없는 값**이다(미등록·미완료라서 묻는 것이다) —
**확신 못 하는 값을 프레임에 실으면 그것이 대조 기준으로 쓰인다.**

🔴 **"몇 번째부터 다시 보내라"도 안 싣는다**(부분 재전송 금지). 대역은 아끼지만 **양쪽이 "몇 번째"의
뜻을 맞춰야 하고, 어긋나면 `idx` 가 밀려 비트 자리가 통째로 틀린다** — **길이도 체크섬도 통과하고
값만 틀리는** 그 부류(§hex ③)를 하나 더 만드는 것이다.
**등록은 118B · 접속당 1회다. 통째로 다시 받는 것이 싸다.**

#### ✅ **상한은 서버에만 둔다** `[arduino 판단 · socket 이 근거를 보강해 채택]`

arduino: *"둘 다 상한을 두면 교착이다 — 장치는 안 보내고 서버는 계속 묻는다."*
**결론은 맞다. 다만 그건 교착이 아니라 *상호 포기*다**(서버도 3회에 멈춘다). **더 정확한 근거가 있다:**

> ### **상한은 비용이 발생하는 쪽에 둔다.**
```
서버가 묻는 비용 : 🔴 **창당 1거래를 질의가 독점한다** — 그 노드의 하행이 그동안 못 나간다
장치가 답하는 비용: 배치 하나. **서버의 창을 먹지 않는다**
```
**→ 서버는 상한을 두고, 장치는 그냥 답한다. `regSends` 로 진단만 남긴다.**
🔑 **비용이 없는 쪽에 상한을 두면 "아무도 손해 안 보는 재시도"를 막는 것**이고, 그건 **복구 경로만 지운다.**

##### ⚠ 열린 자리 — **서버가 포기한 뒤 무엇이 다시 무장시키나**

`Q` 3회 뒤 `node_unregistered` 로 굳으면, **소켓이 계속 살아 있는 한 서버는 다시 묻지 않는다.**
```
✅ 자연 재무장 : **새 세션**(장치 재접속·재부팅). 지금 구조가 이미 그렇다
🔴 안 닫힌 것 : 소켓이 끊기지 않은 채 오래 미등록으로 남는 경우
```
⚠ **주기적 재질의를 지금 넣지 않는다** — 오늘 정한 규율(**재시도는 조건이 바뀌었을 때 뜻이 있다**)과
정면으로 부딪히고, **창을 먹는 쪽이 서버**라 비용도 서버가 문다.
**대신 그 상태가 화면에 `⏱ node_unregistered` 로 정직하게 보인다.** 실제로 오래 남는 것이 관측되면
그때 **무엇을 조건으로 재무장할지** 정한다. **지금 값 없이 주기를 박지 않는다.**

#### 🔴 `Q` 를 무한 반복하지 않는다 `[내 판단 · arduino 동의]`

**슬롯당 최대 1회 · 3회 연속 무응답이면 멈추고 그 노드를 `node_unregistered` 로 굳힌다.**
→ 화면은 `⏱`(미상 계열 · §6.5). 🔑 **끝없이 묻는 것보다 "모른다"를 확정하는 것이 낫다** —
안 그러면 그 노드가 **매 창을 `Q` 로 먹는다**(내 창당 1거래를 질의가 독점한다).

#### ⚠ 비대칭을 계약에 명시한다 — **장치는 등록 성공을 모른다**

등록에 ACK 이 없다. 서버가 `Q` 3회 뒤 포기해도 **장치는 그것을 모른다.**
**그래도 그대로 간다** — arduino 논거: **장치가 알아도 할 일이 없다.**
- 등록 성공을 알아도 **이미 보냈다.** 추가 행동이 없다
- `Q` 가 오면 다시 보내는 것이 유일한 행동이고 **그건 이미 규약에 있다**
- **서버가 포기해도 장치는 계속 살아 있어야 한다** — 다음 서버 재기동의 `Q` 를 받아야 한다

🔑 **그리고 이것이 `거짓 완료`와 다른 형태다**: 거기서는 **사람이 잘못 안다**(화면이 켜졌다고 한다).
여기서는 **사람이 정확히 안다**(`⏱` · `node_unregistered`). **모르는 것은 장치뿐이고 장치가 그걸
알아서 바꿀 동작이 없다.** → **공백이 아니라 명시된 비대칭이다.**

⚠ **낱말 주의**: arduino 의 `BATCH_CAP`(장치 **상행** 배치 상한)과 내 `DOWN_BATCH_CAP_B`(**하행**)는
**다른 값이다.** `D`·`S` 는 상행이라 arduino 쪽 상한이 걸린다.
🔴 **이름이 비슷해서 섞이기 쉽다** — §8.23-(16) 의 `cap` 사고가 정확히 그 형태였다. **방향을 이름에 붙여 부른다.**

### ✅ 확정 — **`D` 가 그 노드의 배출률을 같이 선언한다** `[socket 결정 · arduino 합의 2026-08-18]`

#### 왜 필요한가 — **서버가 그 값을 계산하면 사본이 생긴다**

서버의 하행 건수 상한은 장치의 **슬롯당 ACK 배출률 `D`** 에서 유도된다:
```
안정 조건 : 한 슬롯 놓쳐도 2슬롯 안에 회복  →  k = N ÷ (D − N) ≤ 2  →  **N ≤ 2D/3**
```
그런데 `D` 자체가 **장치 쪽 값들의 함수**다:
```
D = (BATCH_CAP − S_worst − 1) ÷ (ACK_worst + 1)
    ↑ arduino 소유    ↑ n 에 따라 변함    ↑ rid 자릿수
```
> ### 🔴 **서버가 이 식을 들고 있으면 `BATCH_CAP` 이 바뀔 때 같은 규칙이 두 곳에서 갈린다.**
> **파생값은 원본을 가진 쪽이 계산한다.** → **장치가 `D` 를 값으로 선언하고 서버는 유도식에만 넣는다.**

#### ✅ 형식 확정 (arduino 결정 2026-08-18)

```
슬롯 1 : S,…                  ← 🔑 **신원은 여기서 온다.** 승격이 여기서 일어난다
슬롯 2 : D,*,<drain>,<n>      ← 배출률 + **모듈 수**. 묶음의 맨 앞
         D,<name>,<kind>      ← 모듈들. **전부 같은 필드 수**
         D,<name>,<kind>
```
**`D` 는 devid 를 싣지 않는다. 실을 필요가 없다 — 이미 승격된 소켓으로 오기 때문이다.**

##### 🔴 `D,*` 가 **`n`(모듈 수)을 싣는다 — 없으면 "등록 완료"를 판정할 수 없다**

§5 는 *"서버는 `n` 개를 다 받으면 완료"* 라고 적어 놓고 **`n` 을 전선에 안 실었다.**
**내가 형식을 줄이면서 뺐다.** 대안을 따져 봤고 전부 깨진다:
```
(가) `S` 의 hex 폭에서 유도    → 🔴 **불가능.** 폭 `w` 는 `n ∈ [4w−3, 4w]` 만 준다(ceil 때문)
(나) 다음 `S` 가 오면 완료로 본다 → 🔴 ~~n 이 크면 D 가 두 슬롯에 걸친다~~ **틀렸다**(arduino 정정)
                                  **`buildRegistration` 은 상한을 넘으면 0 을 돌려준다. 안 나눈다** —
                                  즉 `n>13` 이면 두 슬롯이 아니라 **등록이 영영 안 된다**
                                  🔑 진짜 이유: **서버는 "몇 개가 와야 하는지"를 알 방법이 없다.**
                                  상한(`n≤13`)이 있다는 것 자체가 **장치 쪽 사실**이라 서버가 모른다
(다) `n` 을 싣는다              → ✅ +2~3B · 접속당 1회
```

##### 🔑 그리고 `n` 은 완료 판정보다 **교차 검산**에서 더 값을 한다

```
① 선언된 `n`            (D,* 가 말한다)
② 실제 `D` 모듈 줄 수    (서버가 센다)
③ `S` 의 hex 폭          (= ceil(n/4))
```
> ### **셋이 한 함수(`moduleCount()`)에서 나오므로 갈릴 수 없다. 갈리면 그 자체가 결함 신호다.**
**②③만으로도 검산이 되지만**(arduino 지적) **③은 ±3 의 여유가 있어 ②를 정확히 못 잡는다.**
**①이 있으면 세 값이 서로를 정확히 못 박는다** — 🔑 **비트 순서 계열(오류 신호 없이 값만 틀림)에
가장 잘 듣는 방어가 이런 다중 표현의 일치다.**

⚠ **`n` 이 ②와 다르면 등록을 완료로 치지 않고 로그 + 카운터.** **조용히 받아들이지 않는다.**

##### ✅ `drain = 7` 검산 (socket 독립 계산 · arduino 값과 일치)

```
S_worst   = "S,"2 + seq5 + occ4 + res4 + up10 + devid8 + tmask4 + 구분자6 + ck2 = **45B**
ACK_worst = "A,"2 + rid5 + slot2 + result1 + 구분자3 + ck2                      = **15B**
D = (160 − 45 − 1) ÷ (15+1) = 114/16 = 7.125 → **7**
확인 : S줄 46B + ACK 7 × 16B = **158B** ≤ 160   ·   8개면 **174B → 초과** ✅
```
**최악값 가정도 타당하다**: `up` 10자리(uint32 최대) · `devid` 8자(§2.3 상한) · `seq` 5자리(uint16) ·
`tmask` 는 시험 모드에만 나오지만 **넣어서 계산한 것이 보수적이라 맞다.**

##### 🔑 그런데 **`6 → 7` 이 내 하행 상한을 안 바꾼다** — 바뀌는 것은 *여유*다

```
D=6 → N ≤ 2D/3 = 4  ·  회복 k = N/(D−N) = **2.00 슬롯**
D=7 → N ≤ 2D/3 = 4  ·  회복 k =          **1.33 슬롯**
```
> ### **상한은 그대로 4 이고, 한 슬롯을 놓쳤을 때의 회복이 2슬롯에서 1.33슬롯으로 빨라진다.**
⚠ **그래서 이 값 변경은 급하지 않고 위험도 없다** — **하행 거동이 하나도 안 바뀐다.**
🔑 **hex 의 이득이 `n` 이 클 때 나온다는 것도 여기서 다시 확인된다**: 10진이었으면 `n=15` 에서
`D=5 → N=3` 이 됐을 것이다. **hex 는 `N=4` 를 지키는 값이지 `N` 을 올리는 값이 아니다.**

##### 🔴 **순서를 바꾼다: `S` 가 먼저다** `[socket 확정 · 루트 제기 · arduino 도 대안으로 냈다]`

**초안은 "첫 슬롯은 `D` 만 · 둘째 슬롯부터 `S`" 였다. 그러면 등록이 통째로 버려진다:**
```
슬롯 1 : D 11줄 → 🔴 **승격 전 버퍼에서 죽는다**(devid 가 없어 승격을 못 만든다)
슬롯 2 : S      → 승격 + 미등록 감지 → 서버가 `Q`
슬롯 3 : D 11줄 → ✅ 그제야 처리된다
```
**기능은 살지만 매 재접속마다 118B 낭비 · 3슬롯 지연 · `drop_unknown`/`승격전버림` 오염**이다.

##### 검토한 두 안과 **왜 순서 쪽을 골랐나**

```
(A) `D,*` 에 devid 를 싣는다   → 1슬롯에 완료 · +3B(그 한 줄만) · 🔴 **형식 변경**
(B) `S` 를 먼저 보낸다         → 2슬롯에 완료 · **형식 변경 0** · 낭비 0
```
> ### 🔴 **(A)는 우리가 `D,*` 를 별도 줄로 만들 때 쓴 논거를 다른 층에서 되살린다.**
`D,*` 형식을 고를 때 **"파서가 몇 번째 줄인지 알아야 하는가"** 로 (가)·(다)를 배제했다.
**(A)를 쓰면 이제 `D,*` 가 반드시 맨 앞이어야 승격이 된다** — **순서 의존이 파싱에서 승격으로 옮겨 갔을 뿐이다.**
**(B)의 순서 의존은 `S` 가 먼저라는 한 줄이고, 그건 이미 프로토콜의 성질이다**
(`S` 는 반송파·생존 신호·슬롯 시작 통보 셋을 겸한다. **첫 프레임이어야 할 이유가 원래 있다**).

🔑 **그리고 (B)는 "신원 없는 프레임이 승격 전에 도착하는 상황"을 *구조적으로 없앤다*.**
(A)는 그 상황을 남겨 두고 **한 줄만 예외**로 만든다. **예외를 만드는 것보다 상황을 없애는 것이 낫다.**

⚠ **루트 메모 정정**: (A)는 **`D,*` 한 줄에만** devid 가 붙는다. *"모든 `D` 줄에 반복"* 이 아니다.
**그래도 (B)를 고른다** — 비용이 아니라 위 구조 때문이다.

##### ⚠ (B)의 대가 — **등록 전 한 슬롯 동안 서버가 모듈 구성을 모른다** `[socket 확정]`

~~미등록 노드에는 하행을 보내지 않는다~~ → 🔴 **너무 넓었다. arduino 가 드러냈다.**

> arduino: *"나는 그 슬롯에 하행이 와도 처리한다 — **모듈 구성과 무관하다.**"*

**맞다. 지금 하행(`R`·`C`·`T`·`M`)은 *자리(슬롯 번호)* 로 주소를 정한다. 모듈 신원이 필요 없다.**
🔴 **내 규칙대로였으면 옛 펌웨어에 회귀가 난다** — 옛 노드는 영영 등록을 안 하므로
`REG_TIMEOUT`(3슬롯) 동안 **재접속마다 하행 구멍**이 생긴다. **재접속은 잦다.**
**그리고 REQ-0203 의 전제가 "거동 변경 0" 이다.**

##### ✅ 고친 규칙 — **기준은 등록 상태가 아니라 *그 명령이 요구하는 정보* 다**

```
자리(슬롯) 기반 명령  : `R` · `C` · `T` · `M`   → **등록과 무관하게 나간다**(종전 그대로)
모듈 신원 기반 명령    : (아직 없다 · §6.5 의 `open_gate` 계열이 그렇게 될 것) → **등록을 요구한다**
```
> ### **"등록 안 됐으니 아무것도 못 한다"가 아니라 "그 명령이 필요로 하는 것이 아직 없다"이다.**
🔑 **이러면 이행 규칙도 필요 없어진다** — 옛 노드는 자리 기반 명령만 받고, 그건 등록과 무관하다.
**`REG_TIMEOUT` 으로 옛 노드/새 노드를 가르는 분기를 안 만든다.** 분기가 없으면 어긋날 분기도 없다.

⚠ **화면은 그 사이 `⏱ node_unregistered`** 로 **모듈 기반 조작만** 막힌다(§6.5 `actions`).
**자리 기반 조작은 그대로 눌린다** — 🔑 **`actions` 가 조작별이라 이것이 표현된다.**
**`actionable: bool` 이었으면 자리 전체가 잠겼을 것이다** — 오늘 web 이 잡아 준 그 결정이 여기서 값을 한다.

##### ⚠ 이행 — ~~옛/새 노드를 `REG_TIMEOUT` 으로 가른다~~ → **가를 필요가 없어졌다**

위 규칙이 **명령의 요구 조건**으로 판정하므로 **노드를 두 계열로 나누는 분기가 안 생긴다.**
🔑 **옛 노드는 `D` 를 안 보낼 뿐이고, 자리 기반 명령은 등록과 무관하게 받는다.**
**등록 여부는 여전히 로그와 `node_unregistered` 로 관측된다** — 다만 **하행 경로를 가르지는 않는다.**
> ### **분기를 안 만들면 두 갈래가 갈릴 일도 없다.** 오늘 반복해서 확인한 것과 같은 규율이다.

##### ⚠ ~~`D,*` 가 devid 를 싣는다~~ — **(A) 는 채택하지 않았다**

**승격은 `devid` 를 가진 프레임이 있어야 일어난다.** 초안의 `D,*,<drain>` 에는 devid 가 없었다:
```
슬롯 1 : D 11줄 → 🔴 **승격 전 버퍼에서 죽는다**(devid 가 없어 승격을 못 만든다)
슬롯 2 : S      → 승격 + 미등록 감지 → 서버가 `Q`
슬롯 3 : D 11줄 → ✅ 그제야 처리된다
```
**기능은 산다. 다만 매 재접속마다 118B 가 버려지고 등록이 3슬롯(3.6초) 걸리며,
`drop_unknown`/`승격전버림` 이 세션마다 오른다** — 🔴 **그 계수는 "AT 잡음 유입 의심"으로 읽히는 칸이라
거짓 경보를 만든다.**
~~→ `D,*` 에 devid 를 실으면 슬롯 1에 등록이 끝난다~~ → **(B) 순서 변경으로 대체됐다.**

##### ⚠ `Q` 에 devid 를 안 실은 것과 **모순이 아니다 — 방향이 반대다** `[arduino 반론 · 채택]`

```
`Q` 는 **서버→장치** : 이 시점의 devid 는 **서버가 확신할 수 없는 값**이다(미등록이라 묻는 것)
`D` 는 **장치→서버** : 🔑 **등록이 곧 devid 선언이다.** 장치는 자기 id 를 확신한다
```
> ### **`S` 가 devid 로 승격을 만드는 것과 정확히 같은 자격이다.**
> **`D` 만 devid 를 안 실어 스스로 승격을 못 하는 것이 오히려 비대칭이었다.**

##### 🔑 그래도 남는 통찰 — **승격을 만드는 것은 `S` 가 아니라 *신원 선언*이다**

**승격을 만드는 것은 `S` 가 아니라 *신원 선언*이다.** `S` 는 상태 프레임인데 **devid 를 실어서**
승격을 만들 수 있었을 뿐이다. → **규칙의 이름은 그대로 두되(옛 로그와 맞춰야 한다) 뜻은 이렇다:**
```
**신원을 처음 선언한 노드가 주차 노드다.** 선언은 `D,*` 로도 `S` 로도 온다
```
⚠ **`S` 승격 경로를 없애지 않는다** — `D,*` 가 깨지거나 체크섬이 틀리면 **`S` 가 여전히 승격시킨다.**
**갈래가 둘인 것이 여기서는 이득이다**(하나가 실패해도 등록이 산다).
🔑 **그리고 IP 기반 자리 인수 판정(§REQ-0217)은 두 경로에 똑같이 걸린다** — 새 노출이 없다.
🔑 **왜 "마지막 줄에 붙이기"·"첫 줄에 붙이기"가 아닌가 — 비용이 아니라 확장이다.**
arduino 가 비용을 실측했다: 별도 줄 ≈8B 대 덧붙임 ≈2B, **차이 6B · 접속당 1회 · `BATCH_CAP` 160B 대비 무시할 수준.**
> ### **비용으로는 못 가른다. 가른 것은 "파서가 몇 번째 줄인지 알아야 하는가"다.**
> **덧붙이는 두 안은 같은 결함을 공유한다**(하나는 "마지막인가", 하나는 "첫 줄인가").
> 🔮 **모듈이 동적으로 추가돼 `D` 를 다시 보낼 때** *"이것도 첫 줄인가"* 가 애매해진다.
🔑 **`cells` 를 목록으로 두되 길이 1 을 강제한 것과 같은 규율이다** — **나중에 푸는 것이 제한이지 구조가 아니게** 만든다.

#### ✅ `kind` 전선 코드 표 `[arduino 제안 · socket 확정 · 셋이 같은 값을 쓴다]`

**명세 §1 은 낱말(한글)만 갖고 있었고 전선 값이 없었다.** 한글은 못 보낸다(UTF-8 3B/자 · 프레임은 ASCII).
arduino 가 `docs/net/`·`docs/web/`·당일 REQ 를 grep 해 **기존 표가 없음을 확인하고 새로 붙였다** —

##### 🔴 첫 글자의 뜻을 **"입력/출력"이 아니라 "명령을 받는가"로 정한다** `[socket 정정]`

arduino 제안은 첫 글자를 **입력/출력**으로 설명했다. **그 낱말이면 우리 결정 하나와 충돌한다:**
> §5 위험 다섯째: **출력 모듈도 비트열에 넣는다.** 차단봉·안내등의 "지금 열려 있나"를
> 서버가 알 길이 그것뿐이다.
**즉 출력도 상태를 보고한다. "입력/출력"은 분할이 아니다.**
🔑 **서버가 실제로 이 글자로 정하는 것은 하나뿐이다: 이 모듈에 하행 명령을 보내도 되는가.**
→ **`O` = 명령을 받는다 · `I` = 관측 전용.** **둘 다 비트열에는 들어간다.**

##### 🔑 왜 방향을 코드 *안에* 두나 — **모르는 종류를 받아도 절반은 안다**

```
새 종류가 온다 → 서버가 그 kind 를 모른다 → 🔴 그래도 첫 글자로 **명령 가능 여부는 안다**
```
> ### **모르는 값을 받았을 때 "아무것도 모른다"가 아니라 "절반은 안다"가 된다.**
🔴 **다만 실패 방향을 못 박는다: 첫 글자가 `O` 가 **아니면** 명령을 보내지 않는다.**
알 수 없는 글자(`X…`)도 **명령 금지 쪽으로 떨어진다** — **모르는 장치에 명령을 보내는 것이
안 보내는 것보다 위험하다.**

⚠ **한 글자로 안 하는 이유**(arduino): 방향이 안 실리고, `S`·`D`·`A`·`R`·`C`·`Q` 같은
**프레임 타입 글자와 눈으로 헷갈린다.** 파싱은 안 깨지지만 **로그를 읽는 사람이 헷갈린다.**
⚠ **비용**: 모듈당 +1B · 등록 시 1회 · `n=10` 이면 +10B. **`D` 는 첫 슬롯을 통째로 쓰므로 여유가 있다.**

⚠ **모르는 `kind` 를 거절하지 않는다.** 등록은 받고 **명령 가능 여부만 첫 글자로 정한다** —
거절하면 **새 모듈이 옛 서버에서 노드 전체를 미등록으로 만든다.**

#### 🔴 `*` 는 모듈 `name` 이 될 수 없다 — **받는 쪽이 거부한다** `[socket 확정]`

**안 막으면 `name="*"` 인 모듈이 배출률 선언으로 파싱된다.**
```
등록 중 `D,<name>,…` 의 name 이 `*` 면 → 🔴 그 줄을 버리고 카운터 + 로그. 등록은 미완료로 둔다
```
⚠ **arduino 도 만들지 않겠다고 했지만 그것은 보장이 아니다** — **검증은 받는 쪽 몫이다.**
🔑 **"상대가 안 보낸다"에 기대는 규칙은 규칙이 아니다.** 이 프로젝트에서 그 형태로 두 번 데었다
(`devid` 고유성 가정 · `S_worst` 가정).
**의미**: `drain` = **이 노드가 한 주기에 배출할 수 있는 ACK 개수의 보장 하한.**
🔴 **관측된 최대가 아니라 설계 보장값이다.** 2026-08-18 에 실측 `8` 이 있었지만
**`S` 가 짧고 rid 가 3자리일 때만 성립하는 조건부**였고, 확정값은 **`6`** 이었다.
**조건부 실측을 보장으로 승격시키지 않는다.**

#### 서버의 처리 `[socket 이 계산 주체]`

```
DOWN_BATCH_MAX_N(node) = 2 × node.drain ÷ 3          · 사용자 큐 깊이 = 그것 × (마감 ÷ 주기)
`drain` 이 없으면 → 🔴 **보수적 기본값을 쓰고 로그에 "선언 없음"을 남긴다**(조용히 넘어가지 않는다)
```
⚠ **범위**: 위 `N ≤ 2D/3` 은 **"한 슬롯 손실을 2슬롯 안에 흡수한다"는 목표에서 나온 값**이고,
그 `2` 는 **`DOWNQ_WAIT_CAP_MS` 의 절반**이라는 뜻이다. **마감이 바뀌면 이 계수도 다시 유도한다.**

#### ⚠ 이행 중의 전제 감시 — **선언이 없는 동안에도 전제가 깨지는 것을 본다**

`drain` 이 도입되기 전까지 서버는 `D=6` 을 가정한다. 그 전제는 **`S_worst ≤ 60B`** 위에 서 있다.
→ **서버가 볼 수 있는 것은 `S` 의 실제 길이뿐이고 그것이면 충분하다**:
```
`S` 실측 길이 > 가정치  →  🔴 "배출 6 의 전제가 깨졌다" 경고 + 주기 요약에 상주
```
🔑 **새 배출률을 서버가 계산하지 않는다**(사본을 안 만든다). **"전제가 깨졌다"까지만 말하고 값은 장치에 묻는다.**
⚠ **이 감시는 한 방향이다** — `S` 가 **커지면** 잡고 **작아지는 것은 안 잡는다.
감시는 "위험해졌다"를 잡는 것이지 "여유가 생겼다"를 잡는 것이 아니다.** 여유는 선언으로 받는다.

### ✅ 확정 — **`S` 자리 비트열의 hex 인코딩** `[arduino 결정 · socket 이 전선 형식 확정]`

#### 왜 바꾸나

10진 문자 1칸당 1비트라 폭이 `n` 에 비례해 커지고, 그만큼 `S_worst` 가 커져 **배출률이 떨어진다**:
```
n=10 10진 → S 60B → D 6        n=10 hex → S 39B → D **7**
n=15 10진 → S 75B → D 5        n=15 hex → S 42B → D **7**
```
> ### **hex 면 `n=15` 에서도 `D=7` 이라 `N=4` 가 유지된다.** `BATCH_CAP` 을 안 올리고 배치도 작아진다.

#### 🔴 전선 형식 — **넷을 못 박는다. 안 박으면 조용히 갈린다** `[socket 확정 · arduino 합의]`

| # | 항목 | 확정 | 안 박으면 |
|---|---|---|---|
| ① | **대소문자** | **대문자만**(`0-9A-F`) | 체크섬이 이미 `%02X` 다. 둘 다 받으면 정본이 흐려지고 로그 대조가 갈린다 |
| ② | **폭** | **`ceil(n/4)` 고정폭 · 왼쪽 0 채움** | 가변이면 **길이로 `n` 을 검증할 수 없다** |
| ③ | **비트 순서** | 전체를 `n` 비트 정수로 보고 **슬롯 `i` 는 비트 `(n−1−i)`** = 10진 문자열을 그대로 이진수로 읽은 값 | 🔴 어긋나도 **길이·체크섬이 다 통과하고 자리만 뒤집힌다** |
| ④ | **패딩 비트** | `n` 이 4의 배수가 아니면 남는 **상위 비트는 반드시 0** · **받는 쪽이 검증**한다 | 🔴 **길이도 체크섬도 통과하는데 값만 틀리는 두 번째 경로** |

> ### **③④ 가 이 절의 본체다. 둘 다 "오류 신호 없이 값만 틀리는" 부류다.**
> 10진 1칸=1비트는 순서가 **눈에 보여서** 이 함정이 없었다 — **압축과 함께 들어오는 위험이다.**

#### 왕복 예제 — **명세에 박고 시험으로 왕복시킨다** `[socket 이 시험 주체]`

```
n=10  0110001011        →  18B   →  0110001011        ✅
n=10  0000000000        →  000   →  0000000000        ✅
n=10  1111111111        →  3FF   →  1111111111        ✅
n=15  011000101100110   →  3166  →  011000101100110   ✅
n= 5  10101             →  15    →  10101             ✅
n=16  1000000000000001  →  8001  →  1000000000000001  ✅
```
🔴 **`0000…` 과 `1111…` 만으로는 ③을 검증할 수 없다** — **순서가 뒤집혀도 그 둘은 같다.**
**비대칭 패턴(`0110001011`)이 순서를 실제로 검증하는 유일한 것이다.**
⚠ **패딩 검증 예제도 넣는다**: `n=10` 에서 `58B`(상위 `01`)는 **프레임을 버리고 센다.**

⚠ **양쪽이 다 검사한다** — 인코딩할 때 상위 비트를 0 으로 강제하고, 디코딩할 때 0 인지 확인한다.
**한쪽만 검사하면 그쪽 버그만 잡힌다.**

#### 🔴 ④ 패딩 검증은 **`n` 의 함수로 켜지고 꺼진다** — 값에서 바로 읽어라

| 자리 수 `n` | hex 폭 `ceil(n/4)` | 총 비트 | 남는(패딩) 비트 | 패딩 검증 |
|---|---|---|---|---|
| 10 | 3 | 12 | **2** | 산다 (**지금 이 값**) |
| 11 | 3 | 12 | **1** | 산다 (약하다) |
| 🔴 **12** | 3 | 12 | **0** | **없다 — 검사할 대상 자체가 없다** |
| 13 | 4 | 16 | **3** | 산다 (⚠ 대신 `S` 가 1B 커진다) |
| 16 | 4 | 16 | **0** | **없다** |

> ### **`n % 4 == 0` 이면 이 방어는 존재하지 않는다.** 코드가 없어서가 아니라 **볼 비트가 없어서**다.

🔴 **가상 모듈과 무관하다.** 가상이든 실물이든 전선 형식이 같고, 서버는 `V` 접미 말고
가상/실물을 구분하지도 않는다. **실물 모듈 둘을 달아 `n=12` 가 돼도 똑같이 꺼진다.**
⚠ *"가상 모듈이 방어를 끈다"* 로 적으면 다음 사람이 **"실물로 바꾸면 돌아온다"** 로 읽는다. **안 돌아온다.**

⚠ **그리고 이 검사의 크기를 과대평가하지 마라.** 깨진 데이터가 **하필 그 패딩 비트를 건드렸을 때만**
잡는다. **주 방어는 체크섬이고 이건 보조다.** 그래서 `n=12` 는 *"방어가 하나 없다"* 이지
*"검증되지 않는다"* 가 아니다.

### 🔴 위험 다섯째 (arduino) — **출력 모듈도 비트열에 넣는다**

```
차단봉·안내등·유도등 = 출력.  "지금 열려 있나/켜져 있나"를 서버가 알 길이 그것뿐이다
```
> **명령이 실제로 반영됐는지 확인하는 유일한 경로다. ACK 은 "받았다"이지 "됐다"가 아니다.**

안 넣으면 **서버가 자기가 보낸 명령의 결과를 영영 못 본다** — 🔑 **오늘 `재전송` 에서 데인 것과
같은 형태다**(결말 칸만 보고 도중을 못 봄 · §8.23-(23)). **폭은 입력+출력 합이고 `n` 하나로 충분하다.**
⚠ 그리고 이것이 §3.1 의 규칙을 되살린다 — **도달 확인은 ACK 가 아니라 다음 `S` 의 마스크 변화로 한다.**

### ⚠ 위험 ①(순서가 계약)에 arduino 가 덧붙인 것

장치는 **등록한 순서 그대로** 비트를 만든다(`for (i=0..n)` 하나) → **정렬 개념이 안 들어간다.**
🔑 **암묵 정렬이 생길 자리가 구조적으로 없다** — 내가 "암묵 정렬 금지"를 규칙으로 적었는데
**구조로 없애는 것이 규칙보다 낫다.**

## 6. web 에 줄 계약 — ✅ **합의 완료** (web 원장 §5.32·§5.36 에 고정됨 · 2026-08-18)

⚠ **이 절의 "합의 아직" 표시는 낡은 것이었다. 갱신한다** — web 이 자기 원장에 내 계약을 고정했고
**값이 갈리면 원본(이 문서)이 이긴다**고 적어 뒀다. **다섯 다 채택됐다:**

1. **맵 정의를 상태와 별개로 준다**(격자·칸 목록·`kind`·모듈 목록).
   ✅ 동의. 지금 `slots[]` 하나가 정의와 상태를 겸해서 **"없는 ID"가 "자료 없음"인지 "존재하지 않음"인지 안 갈린다.**
2. **조작 가능성은 모듈 단위 판정**(`device.online` 단일 불리언 금지). ✅ 동의 — §4 가 그것을 가능하게 한다.
   🔑 web 이 *"거짓 허용이 더 나쁘다 — 닿지 않는 장치로 하행을 보낸다"* 고 한 것이 근거다.
3. **`known` 이 모듈 단위로 내려간다 — 일부만 아는 상태가 상시 정상이다.** ✅ 동의.
4. **`kind: parking|entrance|exit`** — 입구에 "예약됨"이 없다. ✅ **구조는 같고 상태 어휘가 다르다.**
5. 🔴 **기존 `slots[]` 항목에 필드를 넣어 뜻을 바꾸지 마라 — 별도 키로 추가한다.** ✅ 강하게 동의.
   **새 타입은 옛 화면이 조용히 무시해 안전하지만, 뜻이 바뀌면 서버 배포가 그 순간 옛 화면을 깨뜨린다** —
   `queued` 를 별도 타입으로 만든 것이 이미 그 배당을 냈다(§8.23-(6-A)).

## 6.5 🔴 `actionable` 은 **서버가 계산한다** `[합의: web REQ-0183 · 내가 채택]`

web 이 §3 의 *"조작 가능성은 모듈 단위로 판정한다"* 에서 **빈 자리**를 짚었다:
**그 문장이 누가 판정하는지를 말하지 않았고, 비어 있으면 기본값으로 화면이 하게 된다.**

**받는다. 서버가 계산해서 값으로 준다.**

```
zone 마다:  actionable: bool
            blocked_reason: <code>      ← 🔴 **코드**다. 문구는 화면 소유
```

### 왜 — 규칙이 두 곳에 생기면 그게 거짓 허용이다

화면이 모듈 목록으로 직접 판정하면 *"어떤 모듈이 살아 있어야 이 조작이 되나"* 라는 규칙이
**하행 라우팅(내 쪽)과 화면 두 곳**에 생긴다. **갈리는 순간 화면이 거짓 허용을 낸다** →
**닿지 않는 노드로 하행이 나가고 내 큐에 쌓여 창마다 재전송을 돈다.**
🔑 `ack_budget_ms`(§8.23-(6-A))와 **같은 형태이고 같은 해법**이다 — 화면이 짐작하지 않는다.

### 🔑 구조적 보장 — **라우팅과 같은 함수로 계산한다** `[내 판단]`

`ack_budget_ms` 를 리터럴이 아니라 상수에서 계산해 *"값이 바뀌면 조용히 틀린다"* 를 없앤 것처럼:

> **`actionable` 은 하행 라우팅이 쓰는 그 조회를 그대로 돌려 판정한다.**
> "이 조작의 하행이 갈 `(devid, name)` 을 찾을 수 있고 그 노드가 살아 있는가."
> **두 경로가 같은 함수라 갈릴 수 없다.** 모듈 종류가 늘거나 게이팅이 바뀌어도 한 곳만 바뀐다.

### `blocked_reason` 코드 — **서버가 실제로 아는 것만** `[합의 필요: web 문구]`

| code | 서버가 아는 사실 |
|---|---|
| `node_offline` | 그 모듈의 노드가 무프레임(노드별 판정 · §4) |
| `node_unregistered` | 등록을 못 받아 **모듈 사상이 없다**(§5-3 의 그 상태) |
| `module_absent` | 등록은 됐지만 그 `kind` 의 모듈이 그 자리에 없다 |
| `pending` | 그 자리에 진행 중인 하행이 있다(`has_pending_for`) |
| `queue_full` | 그 노드의 큐가 바이트 상한을 넘었다 |

⚠ **모르는 것은 코드로 만들지 않는다.** `node_unregistered` 와 `module_absent` 를 합치면
**"등록이 안 왔다"와 "그런 장치가 없다"가 같은 칸에 들어간다** — §5.2 의 그 자리다.

#### 🔴 계열을 코드에 실어 준다 — **화면이 `⏱`/`⚠` 를 계산 없이 고르게** `[web 요구]`

web: *"코드가 원인을 구분하지 않으면 화면이 다시 짐작하게 된다."* **맞다. 갈라 준다.**

| 계열 | 뜻 | 코드 | 화면 |
|---|---|---|---|
| **`unknown`**(미상) | **판정에 필요한 상태를 서버가 모른다** | `node_offline` · `node_unregistered` | `⏱` |
| **`fault`**(고장) | **살아 있는데 못 한다 / 확실히 없다** | `module_absent` | `⚠` |
| **`busy`**(진행 중) | 지금은 안 되지만 **곧 풀린다** | `pending` · `queue_full` | 재시도 안내 |

🔑 **`busy` 를 셋째로 갈랐다** — web 은 둘을 요구했지만 `pending`·`queue_full` 을 `fault` 에 넣으면
**"고장"으로 그려진다.** 그 둘은 **정상 동작 중의 일시 상태**다(§8.20 의 "거절은 버림이 아니다").
⚠ **이 셋째 계열이 필요한지는 web 판단이다** — 화면이 이미 재시도 안내를 갖고 있으면 코드만 쓰면 된다.

⚠ **`node_offline` 을 `fault` 가 아니라 `unknown` 에 넣은 이유**: 서버가 아는 것은
**"3.5초 무프레임"** 이지 **"장치가 죽었다"** 가 아니다(§4.1 — 기준선에서 36건 중 35건이
링크 재접속이었다). **이름이 결론을 담지 않게 계열도 측정값 쪽에 붙인다.**

### ✅ 액추에이터 상태 에코 — **REQ-0184 는 이미 닫혀 있다** `[합의: arduino + web]`

web 이 물었다: *"개정 뒤 안내등·유도등·차단봉의 **실제 상태**를 화면이 알 방법이 있나."*
지금 프레임에는 에코가 없고, **센서에 있는 자가 치유(≈1초 · web 실측)가 액추에이터에는
구조적으로 안 걸린다** — 비교할 값이 안 올라오기 때문이다.

> ### **답: §5 의 "위험 다섯째"가 그것이다. arduino 가 먼저 짚고 내가 받았다.**
> **출력 모듈도 상태 비트열에 넣는다.** `n` 이 입력+출력 합이다.

🔑 **web(화면 쪽)과 arduino(장치 쪽)가 같은 구멍을 독립으로 찾았다** — 한쪽은 *"화면이 거짓을
그릴 수 있다"*, 다른 쪽은 *"서버가 자기 명령의 결과를 못 본다"*. **같은 사실의 두 얼굴이다.**

**파생 — 자가 치유가 액추에이터로 확장된다** `[내 판단 · 🔴 파생 예측이고 실측이 아니다]`:
에코가 있으면 **§8.21 의 그 기전이 그대로 적용된다**(서버 상태 ≠ 장치 상태 → 다음 `S` 에서 감지 →
재하달). **센서에만 있던 성질이 액추에이터에도 생긴다.**
⚠ **web 이 실측한 ≈1초는 센서 방향의 값이다. 액추에이터 방향의 치유 시간은 아무도 안 쟀다**(루트 지적).
**"≈1초일 것"으로 인용하지 마라** — 재하달 대상이 다르고(등 하나 대 예약 마스크) 그 지연도 다를 수 있다.
🔑 **에코가 들어간 뒤 그것을 재는 것이 첫 검증 항목이다.**

#### 🔑 전선 예산 반박 — **에코가 여유 9B 를 먹지 않는다.** `n` 이 노드별이라서다 `[내 판단]`

루트의 비용표는 *"`S` 에 액추에이터 비트열을 추가하면 여유 9B 를 먹는다"* 로 봤다.
**그 계산은 현행 단일 노드 틀(마스크 고정 10칸)을 전제한다.** 개정에서는 아니다:

```
현행 : S,<seq>,<occ **10**>,<res **10**>,<uptime>,<devid>[,<ovr>],<ck>   ≈ 55B
       ← 한 노드가 자리 10개를 전부 갖는다는 전제. 마스크에 20B
개정 : 마스크 폭이 **그 노드의 모듈 수 `n`** 이다(§5 · 고정 10 폐기)
       노드가 6모듈이면 6+6=12B → **현행보다 8B 적다**
```

> ### **액추에이터를 넣어도 폭은 `n` 안에 흡수된다. 그 노드가 실제로 가진 만큼만 쓴다.**
> **여유를 먹는 것은 "에코 추가"가 아니라 "노드에 모듈이 많은 것"이다.**

**그러면 진짜 제약은 "한 노드가 몇 모듈까지인가"다** — 계산해 둔다:
```
프레임 고정부 ≈ "S," 2 + seq 5 + uptime 10 + devid 8 + 쉼표 5 + cksum 2 + LF 1 ≈ 33B
남는 것 31B ÷ 마스크 2개 → 🔑 **`n ≤ 15`**  (여유 1B 는 남긴다)
```
⚠ **`n > 15` 이면 상태를 한 줄에 못 싣는다** — 그때는 **모듈을 두 노드로 나누는 것이
프레임을 쪼개는 것보다 싸다**(쪼개면 멱등성·조립 문제가 생긴다 · §5 델타 방식과 같은 대가).
🔑 **등록(`D`)이 한 줄에 11개니 `n ≤ 15` 는 등록 2줄 안에 들어간다** — 두 제약이 정합한다.

→ **셋 중 첫 번째를 고른다. 그리고 "여유를 먹는다"가 그 선택의 대가가 아니다.**

#### ✅ 이것이 루트가 짚은 모호함도 푼다 — **`ack` 이 못 가르는 둘**

루트: *"`ack` 이 왔는데 핀 조작이 실패한 경우와 `ack` 이 늦게 온 경우를 서버가 못 가른다."*
**맞다. 그리고 에코가 그것을 가른다:**
```
ack 왔다 + 다음 S 의 그 비트가 바뀌었다   → 동작이 났다
ack 왔다 + 다음 S 의 비트가 안 바뀌었다   → 🔴 **받았지만 못 했다**(핀 조작 실패)
ack 안 왔다 + 비트가 바뀌었다             → ACK 만 유실됐다(동작은 났다)
```
🔑 **§3.1 의 규칙이 여기서 다시 값을 한다** — **도달 확인은 ACK 가 아니라 다음 `S` 의 마스크 변화로 한다.**
**에코 없이는 이 표의 세 줄이 한 칸으로 뭉개진다.**

#### ⚠ 그러나 에코가 말하는 것의 **한계를 명시한다** `[내 판단 · web 이 알아야 한다]`

```
에코가 말하는 것   : **장치가 그 핀을 그렇게 설정했다**
에코가 말하지 않는 것: 전구가 실제로 켜졌다 · 차단봉이 물리적으로 올라갔다
```
**전류 감지가 없으면 끊긴 배선·나간 전구는 에코에 안 나타난다.**
🔴 **그러니 화면이 "켜졌습니다"로 단정하면 그건 여전히 과한 주장이다** — 정확히는
**"장치가 켰다고 보고한다"** 다. §0 의 그 규칙이다 — **측정한 것을 이름으로 삼는다.**
⚠ **전류 감지를 넣을지는 하드웨어 결정이고 이 명세 밖이다.** 안 넣으면 **그 한계가 계약에 남아야 한다.**

### 🔴 그런데 web 의 요구에 **덜 갈린 것이 하나 있다** `[합의 필요: web]`

**`actionable: bool` 은 "자리에 조작이 하나"일 때만 충분하다.**
```
parking 자리 : 예약 · 취소            ← 같은 모듈에 걸리므로 하나로 묶여도 된다
entrance/exit: 차단봉 개방 · 안내등    ← 🔴 **서로 다른 모듈에 걸린다**
```
→ **한 자리가 조작을 둘 이상 가지면 `actionable` 하나로는 어느 것이 막혔는지 안 갈린다.**
**제안: `actionable` 을 조작별로 준다**(`actions: {reserve: {ok, reason}, …}`).

> ### ✅ **web 이 받았다**(REQ-0183 회신) — `bool` 을 버리고 `actions` 맵으로 간다
> web: *"내 명세가 이미 같은 것을 말해 놓고(§3.3 "입출구는 예약이 아니다") 자료 구조를
> 안 따라갔다 — 어긋난다."* 🔑 **화면 비용도 낮다**(`tileView` 가 이미 상태로 조작을 고른다).

**web 이 요구한 계약 조건 둘 — 받는다** `[합의 완료]`:

1. **조작 이름은 닫힌 집합이다.** 명세가 그 목록을 갖는다. **임의 문자열 금지.**

#### `kind` 별 유효 조작 표 `[내 판단 · 확인 필요]` — web 구현의 입력이다

| `kind` | **사용자 조작**(`actions` 에 나온다) | **서버가 파생시키는 것**(조작이 아니다) |
|---|---|---|
| `parking` | `reserve` · `cancel` | 🔑 **안내등 = 예약 상태에서 서버가 켠다** |
| `entrance` | `open_gate` · `close_gate` | 유도등 · 차단봉 자동 개방(번호판 인식 결과) |
| `exit` | `open_gate` · `close_gate` | 〃 |

> ### 🔴 **닫힌 집합 = `reserve` · `cancel` · `open_gate` · `close_gate`. 넷이다.**

**초안에 넣었던 `light_on`·`light_off` 를 뺀다** `[내 판단]`:
- **안내등은 예약 상태에서 서버가 파생시키는 출력**이다. 사용자 조작으로 열어 두면
  **화면이 서버의 자동 제어와 싸운다** — 눌러 켠 등이 다음 예약 변화에 꺼지고,
  그 원인이 화면에도 서버 로그에도 "누가 이겼나"로만 남는다.
- 🔑 **그리고 계약에 이름을 넣는 것 자체가 구현을 부른다.** **안 쓰는 이름을 닫힌 집합에 두지 않는다** —
  `queued ✅` 오기가 "합의됐으니 구현됐겠지"로 읽힌 것과 같은 형태다.

⚠ **확인이 필요한 자리다**: **정비용 수동 등 조작**이 필요하면 그건 **별도 모드**이고 이 표 밖이다.
**사용자가 "안내등을 손으로 켜고 싶다"고 하면 이 결정을 뒤집어야 한다** — 그때는
`light_on` 을 넣되 **"수동이 자동을 얼마나 오래 이기는가"를 같이 정해야 한다**(그 값 없이 넣으면 위 싸움이 난다).

#### 🔑 조작이 없는 모듈은 **표시만 한다**

유도등·안내등처럼 사용자 조작이 없는 모듈도 **모듈 목록에는 나온다**(§6-1 의 표시용 원자료).
→ **화면은 그것을 보여 주되 누를 것이 없다.** web 의 *"모르는 조작을 그릴 수 없다"* 가
**"조작이 없는 모듈은 그릴 수 있다"** 와 충돌하지 않게 이 구분을 명시한다.
2. **모르는 조작 키는 화면이 조용히 무시한다.** → **새 조작 추가가 옛 화면을 깨뜨리지 않는다.**
   🔑 `queued` 를 별도 타입으로 만든 것과 **같은 성질을 `actions` 안에서도 갖는 것**이다
   (§8.23-(6-A) — 모르는 것을 무시하는 쪽은 안전하고, 뜻을 바꾸는 쪽이 깨뜨린다).
   🔴 **그래서 서버는 조작을 추가할 때 기존 키의 뜻을 바꾸지 않는다.** 추가만 한다.

## 6.8 🔴🔴 **화면에 주는 봉투 — 이름과 전달 시점** `[socket 확정 · web REQ-0226 이 빈 곳을 찾았다]`

### 🔴 봉투를 **둘로 가른다.** 하나로 두면 낡거나 대역을 먹거나 둘 중 하나다

```
지형(map)  : 어떤 자리가 있고 어느 칸이며 어떤 모듈이 붙는가 · `rows`/`cols` · `idx`
             → **등록·설정 적재 때만 바뀐다.** 드물다
상태(state): 점유·예약·`actionable`·`blocked_reason`·완료 판정·모듈 값
             → **주기마다 바뀐다**
```
> ### **변화율이 다른 둘을 한 봉투에 담으면, 자주 보내면 낭비이고 드물게 보내면 낡는다.**

### 🔑 낡은 사본 문제는 **판(`epoch`)으로 구조적으로 닫는다**

web 의 지적이 정확하다 — *"접속 시 1회면 화면이 사본을 갖고, 사본은 낡는다"*
(§5.38.3 의 `9900`: **주입+자기단언이라 서버 값이 바뀌어도 절대 빨간불이 안 됐다**).
**그렇다고 매 스냅샷에 지형을 실으면 대역이 는다.** → **셋째 길:**

```
map   : {"type":"map",   "epoch":N, …}     지형이 바뀔 때마다 N 을 올려 **다시 보낸다**
state : {"type":"state", "epoch":N, …}     🔴 **자기가 계산될 때 쓴 지형의 판을 같이 싣는다**
```
> ### **화면은 사본을 갖되, 그 사본이 낡았는지를 *스스로 안다*.**
> `state.epoch != 내 map.epoch` → **그 상태를 그리지 않고 `map` 을 다시 요청한다.**

🔑 **`9900` 사고와 다른 점이 여기다**: 그때는 **사본이 낡은 것을 알 방법이 없었다.**
**판을 같이 실으면 사본은 남되 *탐지 가능*해진다.** 사본을 없애는 것보다 싸고 안전하다.
⚠ **화면이 `epoch` 를 비교하지 않으면 이 장치는 없는 것과 같다** — **비교는 web 의 몫이고 계약이다.**

### 🔴 **`epoch` 를 누가 올리나** — 이걸 안 적으면 같은 자리가 또 생긴다 `[socket 확정]`

```
소유자   : **서버 하나뿐이다.** 화면·장치·monitor 는 `epoch` 를 만들지도 올리지도 않는다
올리는 곳: 🔑 **지형을 바꾸는 함수 안에서, 바꾸는 그 줄 옆에서 올린다**
증가 규칙: **단조 증가 · 1씩.** 되감기지 않는다(서버 재기동 시에도 — 아래)
```
**올리는 사건**(지금 아는 것 전부 · 나중에 늘면 이 목록에 줄을 더한다):
```
· 노드 등록 완료(`D` 를 `n` 개 다 받음) — 모듈 목록과 `idx` 가 그때 정해진다
· 노드 등록 해제/재등록 · 노드가 `node_unregistered` 로 굳음
· 설정 재적재(격자 크기 · 자리 ↔ 칸 사상 · 자리 종류)
```
⚠ **상태만 바뀌는 것은 올리지 않는다** — 점유·예약·`actionable`·모듈 값은 `state` 의 몫이다.
**여기서 `epoch` 를 올리면 매 주기 지형을 다시 보내게 되고, 그러면 봉투를 가른 이유가 사라진다.**

🔴 **구현 규율**: `epoch` 증가와 지형 변경을 **같은 함수 안에 둔다.** 떨어뜨리면
**"바꿨는데 안 올린 경로"가 생기고, 그건 화면이 낡은 사본을 새것으로 믿는 형태다** —
**탐지 장치가 있는데 안 울리는 것이 아예 없는 것보다 나쁘다.**

⚠ **서버 재기동 시**: 지금은 메모리에만 있으므로 `epoch` 가 0 부터 다시 시작한다.
**그래도 안전하다** — 재기동이면 소켓이 끊겨 화면이 다시 붙고 **`map` 을 새로 받기 때문**이다.
🔑 **다만 그 안전은 "연결이 끊긴다"에 기대고 있다.** 연결을 유지한 채 지형만 갈아끼우는 경로가
생기면 **이 가정이 깨진다.** 그런 경로를 만들 때 이 문단을 다시 읽어라.

### 형식 `[socket 확정]`

```json
{"type":"map","epoch":7,
 "grid":{"rows":5,"cols":5},
 "zones":[{"id":"A1","kind":"parking","cells":[[0,0]],
           "modules":[{"devid":"P1","name":"sensor","kind":"IP","idx":0}]}]}

{"type":"state","epoch":7,"ts_ms":1755500000123,
 "zones":[{"id":"A1",
           "occupied":true,"reserved":false,
           "actions":{"reserve":{"ok":true,"reason":null}},
           "completion":"complete",
           "modules":[{"devid":"P1","name":"sensor","value":1,"known":true}]}]}

{"type":"state","epoch":7,"ts_ms":1755500000123,
 "zones":[{"id":"E1","kind":"entrance",
           "actions":{"open_gate" :{"ok":false,"reason":"node_offline"},
                      "close_gate":{"ok":true, "reason":null}},
           "completion":"partial",
           "modules":[…]}]}
```
🔴 **`entrance` 예제를 같이 둔 이유**: `parking` 만 보면 `actions` 와 `actionable:bool` 이
**같아 보인다.** **갈리는 것은 조작이 둘 이상인 자리**다. 예제 하나로는 그 차이가 안 보인다.
```
```
| 키 | 뜻 | 계산 주체 |
|---|---|---|
| `epoch` | 지형의 판 번호. **단조 증가** | 서버 |
| `grid.rows`/`cols` | 격자 크기. **기본 5×5 이지만 설정에서 온다** | 서버(설정 적재) |
| `cells` | `[[row,col], …]` — **지금은 항상 길이 1**(서버가 강제) | 서버 |
| `actions` | 🔴 **조작별** `{ok, reason}` 맵. **`bool` 하나가 아니다**(§6.5 에서 버렸다) | 🔴 서버(§6.5·§6.9) |
| `actions[x].reason` | 막힌 이유 **코드**(문구 아님) · `ok` 면 `null` | 서버 |
| `completion` | `complete`/`partial`/`unknown` (§3.5) | 서버 |
| `value`·`known` | 모듈 값과 **그 값을 아는가** | 서버 |
| `idx` | **비트열 자리** | 장치(등록 순서) |

### ④ 답 — 🔴 **`idx` 를 표시 순서로 쓰지 마라**

`idx` 는 **등록 순서 = 물리 배선 순서**다. 표시에 쓰면 **사용자가 보는 순서가 배선에 딸리고,
배선을 바꾸면 화면이 조용히 재배열된다.** **그건 사용자에게 이유 없는 변화다.**
→ **표시 순서는 `kind` 의 고정 순서로 한다**(의미 기반이라 안정적이다).
⚠ **그 순서를 정하는 것은 web 이다** — 표시는 web 소유다(§6.9 원칙). **서버는 `idx` 를 주되 "표시 순서 아님"을 계약에 적는다.**

### ⑤ 답 — **`cells` 는 목록으로 준다. 화면은 순회하는 쪽을 권한다**

**서버가 길이 1 을 강제하므로 `cells[0]` 은 지금 안전하다.** 다만 **순회하면 N:1 이 와도 화면이 안 바뀐다** —
1칸 목록을 도는 비용은 0 이고 **별도 경로가 아니다.** ⚠ **선택은 web 것이다**(표시 소유).
🔴 **`cells[0]` 을 쓰기로 하면 그 가정을 코드 주석에 적어라** — 안 적으면 N:1 이 왔을 때 **말없이 첫 칸만 그린다.**

### ✅ 낡음을 발견했을 때 — **재요청 타입과 그 사이의 화면** `[socket 확정 · web REQ-0226 보강이 짚었다]`

**web 지적**: 판 번호를 넣으면 *"낡았다는 것만 알고 고칠 수 없는"* 상태가 생긴다. 맞다.

```json
화면 → 서버 : {"type":"get_map","rid":"<화면이 만든 id>"}
서버 → 화면 : {"type":"map","epoch":N, …}            ← 같은 형식. 접속 시 보내는 것과 동일하다
```
🔑 **접속 시의 `map` 과 같은 봉투를 쓴다.** 다른 타입을 만들면 **같은 것을 두 형식으로 만들게 되고,
한쪽만 고치는 날이 온다.**

**서버 쪽 규율** `[socket]`:
```
· `get_map` 은 **즉시 답한다**(창을 기다리지 않는다). 이건 하행 전선이 아니라 화면 소켓이다
· 🔴 **연속 요청을 세고 상한을 둔다** — 화면이 `epoch` 비교를 잘못 구현하면 **무한 재요청**이 된다
  → 같은 화면이 1초 안에 N회를 넘기면 **거절 + 로그**. **막을 수 없으면 보이게 만든다**
```
⚠ **`get_map` 은 상태를 바꾸지 않는다.** 그래서 몇 번 와도 안전하고, **상한은 서버 보호용이지 정합성용이 아니다.**

**그 사이 무엇을 그리나** — **web 의 규율(`"모른다"` 로 그린다)이 맞다.** 채택한다.
> ### **옛 사본으로 계속 그리면 "화면의 정상이 서버의 정상"이 된다**(web §5.34).
> **낡았다는 것을 아는데 그대로 그리는 것은, 모르고 그리는 것보다 나쁘다** — **알고도 숨긴 것**이다.
🔑 **서버 쪽 몫은 그 창을 짧게 만드는 것**이다: `get_map` 즉답 · `map` 은 한 번에 완결(조각 내지 않는다).

### 🔴🔴 정정 — **내가 §6.5 에서 버린 `bool` 을 이 절에서 되살렸다** (web 이 잡았다)

첫 판의 §6.8 은 `"actionable":true,"blocked_reason":null` 로 적혀 있었다. **§6.5 는 이미
`bool` 을 버리고 `actions` 맵으로 간다고 합의돼 있었다.** → **`actions` 가 맞다. 위 형식을 고쳤다.**

> ### **결론을 적어 두고 그 결론을 자기 새 글에 적용하지 않았다.**
🔑 **이 형태를 우리 둘이 각자 한 번씩 밟았다** — web 은 *"입출구는 예약이 아니다"* 를 적어 놓고
자료 구조를 단일 `bool` 로 요구했고 내가 잡았다. **이번엔 반대다.**
⚠ **`parking` 만 보면 둘이 같아 보여서 놓치기 쉽다** — **갈리는 것은 입출구다.**
그래서 **예제에 `entrance` 를 같이 넣었다.** 예제가 하나면 다음 사람이 또 `bool` 로 줄인다.

### 🔴 **JSON 의 `kind` 는 전선 코드와 *같은 값*이다** `[socket 확정 · web REQ 가 물었다]`

내 예제가 `"kind":"parking_sensor"` 였다 — 🔴 **그러면 같은 개념에 이름이 셋이 된다:**
```
명세 산문 : 주차확인센서(한글)    전선 : IP    JSON : parking_sensor
```
> ### **서버가 번역하는 순간 사상이 두 벌 생기고, 한쪽만 고치는 날이 온다.**
**→ JSON 도 `IP`/`IX`/`OG`/`OL`/`OB` 를 그대로 쓴다. 서버는 번역하지 않는다.**
**한글은 *표시 이름*이고 화면이 한 번만 사상한다** — 두 홉이 아니라 한 홉이다.

##### 🔑 그래서 화면은 **액추에이터 표를 안 갖는다**

web 이 물은 것: *"어느 `kind` 가 출력인지 알아야 `*`(장치가 보고한 값) 를 붙인다."*
```
kind[0] === 'O'  →  명령을 받는 모듈  →  그 값은 **명령의 결과를 장치가 되비춘 것**
kind[0] !== 'O'  →  관측 전용         →  그 값은 측정값
```
**표가 필요 없다. 코드 첫 글자가 답이다** — 방향을 코드 안에 둔 값이 여기서 돌아온다.
🔴 **그리고 모르는 `kind` 는 자동으로 `*` 가 안 붙는다**(`O` 가 아니므로).
**web 이 이미 고른 보수적 처리와 같은 결론이고, 이제 그건 관용이 아니라 계약이다.**
⚠ **표시 *순서* 표는 여전히 web 것이다**(`kind` 기반 · §6.8 ④). **순서는 표시이고 방향은 계약이다.**

⚠ **`O` 를 "사용자가 누를 수 있다"로 읽지 마라.** 안내등(`OG`)은 명령을 받지만 **그 명령은 서버가
예약 상태에서 파생시킨다**(§6.5 에서 `light_on` 을 뺀 이유). **누를 수 있는가는 `actions` 가 답한다.**

### ✅ **조작 요청 형식 — 상행(화면 → 서버)** `[socket 확정 · web 이 빈 곳을 찾았다]`

**§6.9 표에 "조작 가능성"은 있는데 *그 조작을 어떻게 보내는지*가 없었다.** 방향은 적혔고 형식이 비었다.

```json
{"type":"open_gate","slot":"E1","rid":"<화면이 만든 id>"}
{"type":"close_gate","slot":"E1","rid":"…"}
```

##### ① 요청 `type` = **`actions` 의 키와 같은 이름**

🔑 **그래야 화면이 키를 그대로 `type` 에 쓸 수 있고, 조작이 늘어도 화면 코드가 안 바뀐다.**
**닫힌 집합 넷**(`reserve` · `cancel` · `open_gate` · `close_gate`)이 **요청 타입의 집합이기도 하다.**
⚠ **서버는 조작을 추가할 때 기존 키의 뜻을 바꾸지 않는다. 추가만 한다**(§6.5 합의 그대로).

##### ② 대상은 **자리 하나로 지목한다.** 모듈을 지목하지 않는다

```
✅ "slot":"E1"                      (자리)
❌ "devid":"P1","name":"gate1"      (모듈)
```
> ### **판정이 자리 단위(`actions` 가 자리마다 온다)이므로 요청도 자리 단위여야 한다.**
🔴 **화면이 모듈을 지목하면 "어느 모듈이 그 조작을 맡는가"라는 규칙이 화면에도 생긴다** —
그건 서버의 라우팅 규칙과 **같은 규칙이 두 곳**이고, 갈리면 **엉뚱한 모듈에 명령이 간다.**
**서버가 자리 → 모듈 라우팅을 갖는다**(§3).

##### ③ 응답 — **새 갈래를 만들지 않는다. `reserve`/`cancel` 과 같다**

```
성공   : {"type":"ack","rid":…,"result":…}
대기   : {"type":"queued","rid":…,"ahead":…,"expires_ms":…,"ack_budget_ms":…}
실패   : {"type":"error","rid":…,"code":<코드 다섯 중 하나>,"msg":"…"}
```
🔑 **화면이 `reserve` 에 쓰는 처리를 그대로 재사용한다.** 새 타입을 만들면 **같은 것을 두 형식으로**
만들게 되고 한쪽만 고치는 날이 온다(§6.8 `get_map` 에서 쓴 논거와 같다).

##### 🔴 자리 지시자는 **전선에서 `slot` 을 유지한다** — 개념 이름은 `자리(zone)` 인데도

web 이 물었다: *"낱말이 `zone` 으로 갈렸는데 요청 키도 바뀌나? 나중에 바꾸면 조용히 깨진다."*
**답: 안 바꾼다.** 근거와 **반대 논거**를 같이 적는다.
```
✅ 유지하는 이유 : 전선 키를 바꾸면 **옛 키와 새 키를 둘 다 받는 분기**가 생긴다.
                  기능은 하나도 안 늘고 **갈릴 자리만 는다**("분기를 안 만들면 갈릴 일도 없다")
🔴 반대 논거    : 우리는 **`슬롯`이라는 낱말을 금지했다**(§0). 두 것을 가리켰기 때문이다.
                  전선 키로 `slot` 을 쓰면 그 모호함을 다시 들이는 것 아닌가
✅ 그 반박      : 금지한 것은 **문서의 낱말**이다. 전선에는 **통신 주기를 가리키는 `slot` 키가 없다** —
                  전선 위에서 `slot` 은 **자리 하나만** 가리키고 모호함이 없다
```
> ### **그래서 못 박는다: 전선 키 `slot` = 개념 `자리(zone)`. 같은 것의 두 이름이고 번역은 없다.**
⚠ **문서에서는 `자리`/`zone` 을 쓰고 전선·JSON 에서는 `slot` 을 쓴다.** **이 한 줄이 명세에 없으면
다음 사람이 `zone` 키를 만든다.**
🔑 **`kind` 때와 결론이 다른 이유**: 거기서는 **값이 세 벌**(한글·`IP`·`parking_sensor`) 생길 뻔했고,
여기는 **키 하나의 이름**이다. **번역표가 생기느냐가 갈림점이지 이름이 같으냐가 아니다.**

### 🔴 **`actions` 에는 *지금 뜻이 있는 조작만* 넣는다** `[socket 확정 · web 이 빈 곳을 드러냈다]`

내 예제가 `"cancel":{"ok":false,"reason":"not_reserved"}` 였는데 **`not_reserved` 는 코드 다섯에 없다.**
그것을 코드로 추가하려다 **두 부류가 섞여 있다는 것**이 드러났다:
```
(가) 뜻은 있는데 **지금 못 한다** : node_offline · node_unregistered · module_absent · pending · queue_full
(나) 애초에 **뜻이 없다**         : 예약이 없는 자리의 `cancel`
```
> ### **(나)를 `ok:false` 로 보내면 화면이 "막힌 버튼"을 그리고, 사용자는 *풀리면 눌리겠지* 로 읽는다.**
> **그건 영영 안 풀린다.** `⏱`/`⚠` 계열을 붙일 자리도 아니다 — **이상이 아니라 해당 없음**이다.

**규칙**: **`actions` 에 그 조작이 *없으면* "지금 이 자리에 그 조작은 없다"** 이고,
**있는데 `ok:false` 면 "뜻은 있는데 막혔다"** 이다. → **`not_reserved` 같은 코드는 만들지 않는다.**
🔑 **이미 있는 규약과 맞는다**: *"모르는 조작 키는 화면이 조용히 무시한다"* · *"조작이 없는 모듈은 표시만 한다"*.
**키의 존재/부재가 이미 한 비트를 나르고 있었고, 그것을 쓰면 된다.**

### 🔴🔴 **세 번째 자기 회귀 — 결정은 산문에 있고 위반은 예제에 있었다**

한 문서에서 오늘 **세 번** 같은 형태가 나왔고 **셋 다 예제였다**:
```
① actionable:bool  ← §6.5 에서 버린 것을 §6.8 예제가 되살렸다
② set_sign          ← 닫힌 집합 넷에 없다. **`light_on` 을 뺀 그 결정을 내가 예제에서 어겼다**
③ not_reserved      ← 코드 다섯에 없다
```
> ### **산문은 검토를 받고 예제는 안 받는다. 그런데 구현하는 쪽은 예제를 본다.**
🔑 **규칙**: **닫힌 집합이 있으면 예제는 그 집합에서만 뽑는다.** 새 이름이 예제에 필요하면
**그 순간 집합을 고치는 것이지 예제에서 먼저 쓰는 것이 아니다.**
⚠ **셋 다 web 이 잡았다** — **받는 쪽이 밟아 봐야 드러나는 형태**이고, 그래서 **예제가 계약이다.**

### 🔑 판정/설명 분리가 두 도메인에서 같은 모양으로 나왔다 (web 확인)

```
socket(§6.9) : **판정 하나**(actionable) · **설명 여럿**(blocked_reason·모듈 상세)
web(§표시)   : **강조축 = 영향**(조작을 막는가) · **기호축 = 원인**(⏱/⚠)
```
**전선·라우팅에서 출발한 쪽과 표시에서 출발한 쪽이 같은 분리에 닿았다.**
🔴 **나중에 누가 이 둘을 합치려 하면**: 합치면 **판정이 여러 곳에 생기거나**(거짓 허용)
**설명이 뭉개진다**(원인을 못 가른다). **둘 다 오늘 우리가 실제로 겪은 형태다.**

### ⚠ 이 절이 닫지 않은 것

**`map` 재전송을 무엇이 촉발하는가**(등록 완료 · 설정 재적재 · 노드 재등록)는 §5 등록 규약과
같이 확정해야 한다. **지금은 "지형이 바뀌면"까지만 정의돼 있다.**

## 6.9 🔴🔴 **계산 주체 표 — 파생값마다 누가 계산해 누구에게 주나** `[socket 확정]`

> ### **규칙만 적고 주체를 비우면, 받는 쪽이 자기가 계산하게 되고 같은 규칙이 두 곳에 생긴다.**
> **두 구현이 갈리면 어느 쪽이 맞는지 알 수 없고, 관대한 쪽이 이기면 위험한 동작이 통과한다.**

**원칙 한 줄: 파생값은 *원본을 가진 쪽*이 계산해서 *값으로* 내려보낸다.**

| 파생값 | 원본을 가진 쪽 | **계산 주체** | 받는 쪽이 하는 일 |
|---|---|---|---|
| `drain`(슬롯당 ACK 배출 하한) | 장치(`BATCH_CAP`·`S_worst`·rid 폭) | 🔴 **장치** — `D` 로 선언 | 서버가 유도식에 넣기만 |
| `DOWN_BATCH_MAX_N`(창당 하행 건수) | 서버(`drain`·마감·주기) | **서버** | — |
| `ack_budget_ms` | 서버 상수 | **서버** — 값으로 내려보냄 | 화면은 **사본을 갖지 않는다** |
| `actionable`(조작 가능성) | 서버(라우팅·노드 생사) | 🔴 **서버** — §6.5 | 화면은 **조합하지 않는다** |
| `blocked_reason` | 서버 | **서버** — 코드로 | 화면은 **문구만** 매핑 |
| 자리 완료 판정(`complete`/`partial`) | 서버(§3.5) | **서버** | 화면은 표시만 |
| 자리 ↔ 칸 좌표 사상 | 설정 파일 | **서버**(적재 시) | 화면은 받은 좌표를 그린다 |
| `S` 비트열의 모듈 순서 | 등록 순서(`D`) | 🔴 **장치** — 등록한 순서 그대로 | 서버는 **정렬하지 않는다** |
| 프레임 도착·손실 판정 | 시리얼 탭 | **monitor** | 서버는 **자기 송신 수만** 준다 |

### 🔴 모듈이 여러 노드에 흩어질 때의 **조작 가능성** — **서버가 계산한다**

```
zone.actionable = 그 자리의 **조작에 필요한 모듈들**이 전부 살아 있는 노드에 있는가
```
🔑 **자리 단위로 서버가 계산해 값으로 준다.** 화면이 "모듈 목록 + 노드 생사"를 받아 **조합하지 않는다** —
조합 규칙이 화면에도 생기면 **서버와 화면이 다른 답을 낼 수 있고, 관대한 쪽이 이기면 죽은 노드에
명령이 나간다.**
⚠ **표시용 상세(어느 모듈이 왜 막혔나)는 따로 준다** — **판정과 설명은 다른 값이다.**
**판정은 하나여야 하고, 설명은 여러 개여도 된다.**

### ⚠ 이 표에 없는 파생값이 생기면 — **표에 줄을 먼저 넣어라**

**구현하면서 "이건 화면이 계산하는 게 편한데" 가 나오면 그 순간이 규칙이 두 곳에 생기는 자리다.**
🔑 편의는 근거가 아니다. **원본이 어디 있는지로 정한다.**

## 7. 이 명세가 **아직 답하지 않은 것** — 비워 두지 않고 적는다

1. ~~**등록 프레임 문자와 형식**~~ ✅ **닫혔다**(§5 등록 규약 확정 · `D`/`Q` · `n` 종료 조건 ·
   `REG_TIMEOUT = 3 × 슬롯주기` · `Q` 3회 상한 · 비대칭 명시).
2. ~~자리 하나가 여러 노드에 걸칠 때의 완료 판정~~ ✅ **아래 §3.5 에서 정했다**(에코 확정으로 답이 생겼다).
3. **노드 수의 상한** — 🔴 **답을 내지 않는다. 아는 것을 층으로 적는다** `[루트 지시]`

   | 층 | 내용 |
   |---|---|
   | **추론(근거 있음)** | 소켓·메모리는 계산된다. **왕복 1230ms 중 대부분이 슬롯 대기이고 전파 구간은 짧다**(arduino 계산 `d1+d2 ≈ 67ms`) → **N 이 작을 때는 전파가 병목이 아니다** |
   | **미측정** | 🔴 **보드가 한 대뿐이라 N≥2 를 한 번도 안 재 봤다.** WiFi 는 공유 매체라 **N 이 늘면 경합이 각 노드의 `S` 주기를 흔들고 그러면 내 창도 흔들린다** |
   | **뒤집힐 조건** | **`S` 도착 간격의 흔들림이 N 에 따라 커지면** 추론이 깨진다. 그때 상한은 소켓 수가 아니라 **위상 안정성**이 정한다 |

   ⚠ **계산값을 상한으로 쓰지 마라** — **소켓 상한은 "그 위로는 확실히 안 된다"이고
   "그 아래는 된다"가 아니다.**

   ##### 🔑 보드 두 대가 생기면 — **무엇을 어떻게 재는가** (절차)

   ```
   ① 한 대로 기준선 : `S` 도착 간격 분포(중앙·p99)를 무주입으로 30분
   ② 두 대로 같은 것 : 같은 조건 · 같은 시간대 · 두 노드 동시
   ③ 비교          : 간격 분포의 **꼬리(p99)** 가 커지는가. 중앙은 격자에 묶여 안 움직일 것이다
   ```
   🔴 **주입 없이 잰다.** 하행을 넣으면 그것이 경합을 만들어 **재려는 것을 스스로 바꾼다**(§8.9 의 형태).

   ##### 🔑 전파 구간만 따로 재는 법 — **`S` 도착 간격의 흔들림이 서버측 대리 지표다**

   **장치는 격자에 묶여 보낸다**(`due` 실측 0ms · 72/73). → **장치측 송신 시각은 거의 안 흔들린다.**
   ```
   내가 보는 도착 간격의 흔들림  ≈  망이 만든 흔들림  (+ 내 루프 지연)
   ```
   → **`S` 도착 간격 분포가 망 경합의 서버측 대리 지표다.** 🔑 **하행 없이 · 장치 계측 없이 · 지금 코드로 잰다.**
   ⚠ **한계**: 이것은 **d1 의 흔들림**이고 **`d1+d2` 의 절대값이 아니다.** 절대값은 여전히
   arduino 의 `[ACK] lag=` 과 짝지어야 나온다(§8.23-(31)). **흔들림으로 N 상한을 보고,
   절대값으로 창 폭을 본다 — 쓰임이 다르다.**
3-A. ~~`D` 프레임의 배출률 선언~~ ✅ **닫혔다**(§5 · 장치가 선언 · 서버는 유도식에만 넣는다).
3-B. ~~`S` 비트열 hex 인코딩~~ ✅ **닫혔다**(§5 · 대소문자·고정폭·비트순서·패딩 0 검증 + 왕복 예제).
   ⚠ **`D` 의 `drain` 을 어느 줄에 싣는지는 arduino 최종 합의가 남았다** — 의미는 확정, **형식만 열려 있다.**
4. **`cap` 이 노드마다 다를 수 있는가** — 회선 속도가 노드마다 다르면 그렇다. **지금은 전역 하나다.**

# §7. 자리 조작 전선 프레임 `G` — **확정** (2026-08-19 · REQ-0228)

🔴 **이 절이 없어서 형식이 내 머릿속에만 있었다.** arduino 는 이미 구현했고 나는 물으려던 참이었다 —
**그 사이 갈렸으면 아무도 몰랐을 것이다.** 형식은 **장치 파서에서 읽어 맞췄다**(말로 받지 않았다).

## 7.1 프레임

```
하행   G,<rid>,<idx>,<op>,<ck>
상행   A,<rid>,G<d>,<result>,<ck>          d = idx % 10
```

| 칸 | 값 | 비고 |
|---|---|---|
| `rid` | uint16 | **상관 키.** 재전송은 같은 `rid` → 장치가 멱등 캐시로 같은 ACK 을 돌려준다 |
| `idx` | uint16 | **모듈 인덱스** = 등록 `D` 의 순서. 장치는 `SLOT_N ≤ idx < moduleCount()` 만 받는다 |
| `op` | `0` = 닫기 · **0 이 아니면 열기** | 숫자다. 문자가 아니다 |
| `result` | `0` = 수행 · **`3` = 수행 불가** | 🔴 `3` 은 `ack_timeout` 과 **다른 칸에 센다**(7.3) |

⚠ **ACK 의 둘째 칸이 자리 이름이 아니다** — `G0`·`G1` 같은 값이다(`idx % 10`).
서버는 `slot_index()` 가 실패하면 `pend` 의 원래 자리로 되돌린다. **상관은 `rid` 로 한다.**
🔑 **`idx % 10` 은 사람이 로그에서 알아보기 위한 것이지 식별자가 아니다.** 그것으로 상관하지 마라.

## 7.2 🔴 완료는 **ACK 이 아니라 다음 `S` 의 에코 비트**로 판정한다

```
occ 비트 0 .. SLOT_N-1   자리 점유        (`kind` 가 `I*`)
occ 비트 SLOT_N ..       **모듈의 현재 상태** (`kind` 가 `O*`) — "지금 열려 있나"
```
> ### **같은 비트열인데 의미가 다르고, 그 구분은 `kind` 에 있다.**
> ### **그래서 이 칸은 "자리 점유"가 아니라 *모듈 상태* 다. 이름이 `occ` 인 것은 유래일 뿐이다.**

🔑 **에코를 위한 새 칸을 만들지 않았다.** 만들면 **같은 값이 두 곳에 생기고, 갈리는 순간
어느 쪽이 맞는지 알 방법이 없다.** (`drain` 을 장치가 선언하게 만든 것과 같은 이유 — §6.9)
✅ 그 결과 **전선 예산 증가 0** 이고, **매 슬롯 에코되므로 자가 치유가 성립한다**(원장 §8.21 의 조건).

### 7.2.0 🔴🔴 **§3.5 와 어휘가 두 벌이었다 — 화해시킨다** (web 이 찾음 · 2026-08-19)

**같은 문서 안에 완료 어휘가 둘이고 둘 다 `확정` 표시가 붙어 있었다:**
```
§3.5    action_state = { state: done|partial|failed|pending, ok, total, missing[] }   ← **먼저 있었다**
§7.2.1  completion   =          pending|settled|mismatch|unknown                      ← 🔴 **내가 오늘 새로 만들었다**
```
> ### **§7.2.1 을 쓸 때 §3.5 를 안 봤다. 같은 것을 두 번 설계했고 이름이 갈렸다.**

⚠ **web 의 코드에 이미 두 벌이 섞여 들어가 있었다** — 필드 이름은 §7.2.1 에서, 값은 §3.5 에서.
결과: `partial` 가지는 죽은 코드이고 **`mismatch`·`pending` 이 아무 표시 없는 평범한 라벨로 그려진다.**
🔑 **"사람이 봐야 한다"는 상태가 정상처럼 보이는 것** — 이 충돌이 만든 실제 피해다.
**한 문서 안에 두 어휘가 있으면 받는 쪽은 그것이 개정인지 다른 것인지 구분할 수 없다.**

#### 정본 — **§3.5 의 *모양* 이 정본이다. §7.2.1 은 그 좁은 판이다**

**§3.5 가 먼저 있었고 더 깊다** — 자리가 **여러 모듈**에 걸칠 때를 다루고 `ok/total`·`missing[]` 을 준다.
§7.2.1 은 **모듈이 하나인 경우**만 답한다. 🔑 **좁은 판이 넓은 판을 대체할 수 없다.**

#### ⚠ 그런데 **지금 서버가 내보내는 것은 좁은 판이다.** 이것이 실기다
```json
"completion": "pending" | "settled" | "mismatch" | "unknown"      ← 🔴 이것만 나간다
```
**`action_state`·`ok`·`total`·`missing[]` 은 아직 안 만들었다.** §3.5 는 **설계이지 구현이 아니다.**
🔴 **화면은 실기에 맞춰 짜라. 명세의 아직 안 만든 부분에 맞춰 짜지 마라.**

#### 🔴 그리고 지금 구현의 **한계를 명시한다** — web 의 물음 ②에 대한 답
```cpp
int gate_index_of(const Zone& z)   // **첫 번째** 명령 가능 모듈만 돌려준다
```
> ### **출력 모듈이 둘 이상인 자리는 지금 제대로 답하지 못한다. 첫째만 보고 판정한다.**
**지금 그런 자리가 없어서 드러나지 않는다**(E1·X1 이 각각 모듈 하나씩). **생기면 그때 §3.5 로 넓힌다.**
⚠ **그러니 `missing[]` 이 없는 것은 "없앴다"가 아니라 "아직 안 만들었다"이다** —
**web 이 모듈 행 표식을 안 붙이기로 한 것이 맞다. 없는 자료로 표식을 만들면 그게 짐작이다.**

#### `failed` 의 행방 · `mismatch` 와의 관계
```
§3.5 failed   = 재시도 소진 또는 노드 오프라인 — **더 갈 수 없다**
§7.2.1 mismatch = 장치가 ACK 했는데 **에코가 요청과 다르다**
```
🔑 **둘은 다른 것이다. `mismatch` 는 §3.5 에 없던 상태다** — §3.5 는 *"서버가 남은 모듈만 재하달한다"* 로
**저절로 해소되는 것을 전제**했다. **재하달을 아직 안 만들었으므로 그 상태가 머문다.**
⚠ **그래서 `mismatch` 는 임시 이름이 아니라 실재하는 상태다.** 재하달을 만들면 그때 `partial` 과 합칠지 정한다.
**`failed` 는 지금 서버가 안 보낸다** — 만들지 않았다. **보내지 않는 값을 화면이 기다리게 두지 마라.**

### 7.2.1 `completion` — **닫힌 집합 넷** · 계산 주체는 **서버**

| 값 | 뜻 | 화면이 할 일 |
|---|---|---|
| `pending` | 내가 건 명령이 아직 떠 있다 | 진행 표시 |
| `settled` | 마지막으로 **요청한 값과 에코가 같다** | 완료 |
| 🔴 `mismatch` | 요청과 에코가 **다르다** — 장치가 못 했거나 되돌아갔다 | **사람이 봐야 한다** |
| `unknown` | 이 세션에 명령한 적이 없거나 비트를 못 읽었다 | 아무 주장도 하지 않는다 |

> ### 🔴 **`settled` 는 "에코가 있다"가 아니라 "요청한 값과 같다"이다.**
**처음에 "그 모듈의 에코가 있으면 `settled`" 로 짰다가 뒤집었다** — 그러면 **열라고 했는데 닫혀 있어도
`settled`** 가 된다. **거짓 완료를 막으려던 값이 거짓 완료를 만든다.**
🔑 **`mismatch` 가 없으면 그 상태를 말할 단어가 없어서 `settled` 로 흘러간다.**

**계산 주체 = 서버**(§6.9). 서버가 요청값을 들고 있고 에코를 받으므로 **원본을 가진 쪽이 계산한다.**
⚠ **화면은 조합하지 마라** — `value` 와 마지막 요청을 화면이 비교하면 **판정자가 둘이 된다.**

#### 🔴 한계 — **서버는 "명령이 바꿨다"와 "저절로 바뀌었다"를 구분할 수 없다** (2026-08-19)

**가상 차단봉은 첫 `G` 전까지 스스로 토글한다.** 그리고 **보드가 리셋되면 다시 토글을 시작한다**
(monitor 실측: 탭 개방 DTR 리셋 뒤 3분 동안 **37회** 자율 변화).

```
서버가 보는 것 : occ 의 비트가 바뀌었다
서버가 못 보는 것 : 그것이 **내 명령 때문인가**
```
> ### 🔴 **자율 변화가 우연히 요청값과 맞으면 `completion` 이 `settled` 로 간다 — 명령이 아무것도 안 했어도.**

**즉 `settled` 는 *"요청값과 현재 값이 같다"* 까지이고 *"내 명령이 그렇게 만들었다"* 가 아니다.**
🔑 **monitor 의 문장이 이것을 정확히 짚었다**: *"자율이 도는 동안에는 명령과 에코의 짝짓기가
**원리적으로 불가능**하다. 값이 저절로 바뀌므로 '명령 때문'인지 알 수 없다."*

- ⚠ **인과를 재려면 자율이 멈춘 뒤여야 한다.** 첫 `G` 이후가 그 구간이고, **리셋하면 다시 열린다.**
- ⚠ **그리고 리셋을 만드는 것이 우리 자신일 수 있다**(시리얼 탭 개방의 DTR). **개입 기록이 그래서 필요하다.**
- 🔑 **이건 결함이 아니라 계약의 범위다.** 적어 두지 않으면 다음 사람이 `settled` 를 **인과의 증거**로 읽는다.

⚠ **세션이 끊기면 `unknown` 으로 돌아간다.** 요청값도 에코도 그 세션의 것이다.
**끊긴 뒤 낡은 값을 `known:true` 로 주장하지 않는다** — 모르면 덜 주장한다.

⚠ **ACK 으로 판정하면 안 되는 이유**: ACK 은 *"명령이 도착해 적용됐다"* 까지다.
장치가 받고 **못 움직였을 때** 화면이 "열렸다"로 그린다 — 그게 `거짓 완료` 다.

🔴 **그리고 서버가 10비트에서 자르고 있었다**(2026-08-19 발견·수정). 그러면 **이 값이 조용히 버려지고
화면은 영영 "진행 중"에 머문다.** 읽는 쪽은 반드시 **선언 `n` 만큼** 읽어야 한다.

## 7.3 `result=3` 과 `ack_timeout` 은 **다른 칸이다**

```
result=3      "장치가 못 한다"  → 🔴 재시도해도 같다
ack_timeout   "안 갔다"        → ✅ 재시도에 뜻이 있다
```
**합쳐 두면 `실패 N` 을 보고 재시도를 늘리는데 절반은 늘려도 소용이 없다.**
서버 요약의 `장치거절 N` 이 그 칸이다. ⚠ **화면 문구도 갈라야 한다 — 사용자가 할 일이 다르다.**

## 7.4 ⚠ `idx` 의 대가 — **순서에 딸린 식별자다**

> ### **`idx` 는 순서에 딸린 식별자다. 순서가 바뀌면 같은 `idx` 가 다른 모듈을 가리킨다.**
> ### **오류 없이 조용히 틀린다 — 체크섬도 길이도 통과한다.**

🔑 **`idx` 를 고른 이유는 "전선이 모듈 이름 길이에 안 딸린다"였다. 이것이 그 대가다.**
**대가를 적어 두지 않으면 다음 사람이 `idx` 를 무해한 최적화로 읽는다.**

**지금 이 대가가 실현되지 않는 이유**(arduino 확인 · REQ-0228):
```
MODULE_TABLE 은 PROGMEM **컴파일 상수** → 런타임에 순서가 안 바뀐다
순서를 바꾸려면 다시 굽는다 → 다시 구우면 새 세션 → 서버의 reg_reset() 이 돈다
```
✅ **그래서 전선에 세대(generation) 필드가 필요 없다.** ⚠ **다만 그 전제가 깨지면 필요해진다** —
**모듈 표가 런타임에 바뀌는 순간 이 절을 다시 열어라.**

**약속**: 🔴 **새 모듈은 목록 끝에만 붙인다. 중간에 끼우지 않는다.**
장치가 세 겹으로 박아 뒀고(주석·`static_assert`·리터럴 시험), **서버도 재등록 앞부분을 대조한다** —
**양쪽이 각자 확인한다.** ⚠ 서버 검사는 *"약속을 어겼나"* 를 잡지 *"왜 어겼나"* 는 못 준다.

# §8. 🔴 사유 코드는 **두 이름공간**이다 — 한 표로 다루지 마라 (2026-08-19 실측)

**코드에서 세어 확정한 값이다**(추정 아님). 두 곳이 서로 다른 집합을 쓴다.

| | 어디에 실리나 | 뜻 | 값 |
|---|---|---|---|
| `error.code` 🔴 | 요청에 대한 **거절 응답**(`{"type":"error","rid":…,"code":…,"message":…}`) | *"이번 요청을 못 받았다"* | `bad_request` · `device_offline` · `not_supported` · `module_absent` · `rate_limited` · `queue_full` · `already_pending` · `ack_timeout` |
| `actions[].reason` | `state` 의 **자리별 조작 가능성** | *"지금 이 조작이 막혀 있다"* | `module_absent` · `node_offline` · `node_unregistered` · `pending` · **`occupied`** |

## 🔴 같은 개념에 **다른 이름**이 붙어 있다
```
device_offline   (error.code)  ↔  node_offline   (actions[].reason)
already_pending  (error.code)  ↔  pending        (actions[].reason)
```
🔴 **봉투 이름도 다르다**: 거절은 `"type":"error"` 이고 **키는 `code`** 다. `"err"` 도 `"reason"` 도 아니다.
⚠ **내가 앞서 `err.reason` 이라고 세 번 적었다 — 전부 틀렸다.** 실측(2026-08-19):
```json
{"type":"error","rid":"q2","code":"pending","message":"지금은 조작할 수 없습니다"}
```
🔑 **이름을 코드에서 확인하지 않고 기억으로 적었다.** §(59) 의 *"기억이 답할 수 없는 것을 기억에게 물었다"* 와 같다.
> ### **화면이 이 둘을 한 표로 다루면 같은 상태가 두 칸에 들어간다.**
⚠ **왜 안 통일하나**: 통일하려면 **둘 중 한쪽의 전선 값을 바꿔야 하고, 그건 화면 코드를 깨뜨린다.**
**지금은 사실을 적어 두는 것이 값이 크다.** 통일은 다음 개정에서 **한 번에** 한다.

## ⚠ **`actions` 는 넷뿐이다** — 여섯이라고 적은 앞의 서술은 틀렸다
~~`queue_full`·`not_supported` 가 `actions` 에 실린다~~ → **안 실린다. `err` 전용이다.**
🔑 **`queue_full` 은 "요청을 지금 못 받는다"이고 `actions` 는 "구조적으로 막혀 있다"라 층이 다르다.**
**`not_supported` 도 조작을 실제로 시도했을 때만 나온다.**

## 🔑 그러니 화면은
```
① 두 표를 따로 둔다 — err 용 · actions 용
② 모르는 코드는 **⚠(사람이 봐야 함) + 원문 코드** 로 떨어뜨린다
   🔴 중립 라벨로 그리면 계약이 늘어날 때마다 화면이 조용히 거짓말을 한다 (web §5.6x)
```

# §9. 🔴 `occupied` — 차가 있는 자리는 예약할 수 없다 (REQ-0235 · 2026-08-19)

**web 이 찾았다**: 점유된 자리에 서버가 `reserve: {ok:true}` 를 주고 있었고,
**누르면 장치가 `result=1` 로 거절**했다. 사용자에게는 **"눌렀는데 안 되는 버튼"** 이다.

## 근거는 장치 코드다 — 추정이 아니다
```c
client.ino :  if (occMask & bit) result = 1;      // 이미 점유
```
**그리고 설계 의도가 그 위 주석에 있다:**
> **`occupied=1 ∧ reserved=1` 은 "예약하고 나서 주차한" 성공 상태다.**
🔑 **순서가 정해져 있다. 예약 → 주차이고, 주차 → 예약은 없다.**

## 🔑 규칙 — **여는 근거와 막는 근거가 다르면 반드시 창이 생긴다**
```
여는 쪽 : actions.reserve = ok:true      (서버 · 점유를 안 봤다)
막는 쪽 : 장치의 result=1                (점유를 본다)
→ 그 사이가 **눌렀는데 안 되는 버튼**이다
```
> ### **`actions` 가 있는 이유가 *실패할 것을 안 내놓는 것* 이다.**
**그 목적을 못 지키면 `actions` 는 장식이다.**

## 표현 — **키를 빼지 않고 `ok:false` 로 준다**
```json
"reserve": {"ok": false, "reason": "occupied"}
```
⚠ **차가 나가면 예약이 가능해진다** → *"뜻이 없다"*(키 부재) 가 아니라 *"뜻은 있는데 막혔다"* 다(§6.5).
🔑 **키를 빼면 화면이 버튼을 영영 안 그린다.** 일시 상태를 영구로 답하는 것이고, §"영구와 일시" 규칙 위반이다.

## ⚠ 우선순위
**자리 수준 차단(`node_offline`·`node_unregistered`·`module_absent`·`pending`)이 먼저다.**
그것들이 비어 있을 때만 `occupied` 를 본다 — **장치가 없으면 점유값 자체를 못 믿는다.**

## 🔑 이 결함은 **hex 수정 뒤에야 존재할 수 있었다** (web 관찰)
점유 해독이 틀렸을 때는 **모든 자리가 비어 보였고** 이 모순이 성립하지 않았다.
> ### **한 결함을 고치면 그 뒤에 가려져 있던 것이 드러난다. 고침이 새 상태 조합을 처음으로 가능하게 한다.**
⚠ **"고쳤으니 그 부분은 끝났다"가 아니다** — **고친 뒤 다시 재는 것이 새 자료를 만든다.**

# 8. 모듈별 값 계약 — `state.zones[].modules[]` `[socket 확정 · 2026-08-19 · REQ-0262]`

> ## 🔴 **구현 상태: 대부분 *이미 구현돼 있다*.** (2026-08-19 · web 이 잡았다 · 내가 코드로 확인)
>
> **나는 이 머리를 처음에 "확정 · 미구현"으로 썼다. 틀렸다.** `state_json()`(`server.cpp` ~2504~2519)이
> **이미 `modules[]` 에 `value`·`known` 을 싣고 있고 web 화면이 그것을 읽고 있다.**
> ```
> 실제로 나가는 것 : {"devid","name","idx","value":true|false|null,"known":true|false}
> ```
> 🔴 **§(92)를 내가 또 밟았다** — 확인 안 한 상태를 적고 거기에 *"§(93) 교훈"* 이라는 **근거까지 붙였다.**
> **참인 규칙이 틀린 상태 진술을 떠받쳤다.** 잡은 것은 내가 아니라 **그 코드를 매일 읽는 web** 이다.
> 🔑 **"내 도메인이라 안 찾았다"의 재발이다.** 서버는 내 것이고 그래서 안 봤다.
>
> **아래 §8.x 는 "새로 만들 계약"이 아니라 *이미 나가는 계약 + 빠진 자리*로 읽어라. §8.8 이 그 차이표다.**

## 8.0 🔴 먼저 — **이름을 새로 짓지 않았다**

REQ-0262 가 *"이름을 박아라"* 라고 했는데 **찾아보니 §7 의 계약표에 이미 있었다:**
```
state.zones[].modules[] = { devid, name, value, known }      ← §7 예제 · 계약표에 있다
zone.completion         = complete | partial | unknown (§3.5)
```
🔑 **web 이 기다린 것은 새 이름이 아니라 "그 이름이 정본인가"였다. 정본이다.**
⚠ **§(90) 그대로다 — 새 자료가 필요 없었고 가진 것을 안 대 봤을 뿐이다.**
**이 절은 그 위에 *빈 자리만* 채운다.**

## 8.1 값의 원천 — `S` 의 자리 비트열, `idx` 로 색인

**사용자 확정(REQ-0261): *"지금 주차확인센서와 같은 구조이다."***
```
S 의 자리 비트열[ idx ]  →  그 모듈의 value        (idx = 등록 순서 · 장치가 정한다)
```
🔴 **`idx` 는 표시 순서가 아니다**(§7-④). 서버는 `map` 에서 `idx` 를 주고 **"표시 순서 아님"을 계약에 적는다.**

### ⚠ 비트가 **실물 자리 수를 넘으면 뜻이 다르다** (§7.2)

```
idx <  실물 자리 수 : 그 자리의 **점유**            (kind=IP · 주차확인센서)
idx >= 실물 자리 수 : **차단봉/액추에이터 에코**    (kind=OBV · E1·X1)
```
> ### **같은 비트열인데 앞뒤가 다른 것을 잰다. 한 필드로 합치지 마라.**
**모듈의 `kind` 가 그 뜻을 나른다.** 화면은 `kind` 로 갈라 그린다.

## 8.2 🔴 "모름"의 표현 — **`known:false` 다. 키 부재가 아니다**

§6.5 의 존재/부재 규칙을 그대로 적용한다:
```
`modules` 키 자체가 없다 : 그 자리에 **모듈이 없다** (해당 없음 · 영구)
`modules` 는 있고 known:false : 모듈은 **있는데 지금 값을 모른다** (일시)
🔴 known:false 일 때 **`value` 를 싣지 않는다** — 뜻 없는 값을 실으면 `0` 이 "비었다"로 읽힌다
```
⚠ **일시 상태를 키 부재로 답하면 화면이 영영 안 그린다.** `occupied` 사유를 키 부재로 안 한 것이 그 판례다.

**`known:false` 에는 사유를 붙인다 — 이름은 `reason`, 어휘는 §6.5 의 코드 다섯을 그대로 쓴다:**
```
node_offline · node_unregistered · module_absent      ← 이미 있는 코드. 새로 만들지 않는다
```
🔴 **새 코드를 만들지 마라.** 오늘 `not_reserved`·`set_sign`·`actionable:bool` 이 **셋 다 예제에서** 되살아났다.

## 8.3 🔴 서버는 **"모듈이 고장났다"를 모른다** — 색을 셋으로 만들지 마라

사용자 지시는 *"동작상태가 녹색/적색등"* 이다. **서버가 아는 것은 `value` 와 `known` 뿐이다.**
```
✅ 서버가 말할 수 있는 것 : 값이 1 인가 0 인가 · **그 값을 아는가**
🔴 서버가 못 말하는 것   : 그 모듈이 **성한가 고장인가**. 그런 신호가 전선에 없다
```
> ### **`known:false` 는 "모듈이 고장"이 아니라 "서버가 모른다"이다. 둘을 같은 색으로 칠하지 마라.**
**화면은 `known:false` 를 제3의 표시(회색·물음표)로 그린다.** ⚠ **적색으로 칠하면 없는 고장이 보인다.**
🔑 **색을 정하는 것은 web 이다**(표시는 web 소유 · §6.9). **서버는 그 색의 *근거*만 준다.**

## 8.4 자리 `occupied` 와 모듈 값의 관계 — **서버가 유도한다. 화면이 조합하지 않는다**

REQ-0260 으로 **영역 하나에 모듈이 둘**이 된다(영역1 ← `A1`,`B1`). 그러면 두 값이 공존한다.
```
🔴 계산 주체 : **서버.** 화면은 표시만 한다 (§"파생 값은 원본을 가진 쪽이 계산한다" · ack_budget_ms 판례)
유도 규칙   : `occupied` = **known 인 IP 모듈 중 하나라도 1 이면 1**
신뢰도      : 그 유도가 얼마나 온전한지는 **`completion` 이 나른다** (§3.5 · 새로 만들지 않는다)
              complete = 그 자리의 IP 모듈이 **전부 known**
              partial  = 일부만 known   → `ok`/`total`/`missing[]` 이 어느 것이 빠졌는지 말한다
              unknown  = **하나도 known 이 아니다**
```
🔴 **`completion=="unknown"` 이면 화면은 `occupied` 를 그리지 마라.**
`occupied` 키는 **항상 있다**(§8.2 — 일시 상태를 키 부재로 답하지 않는다). **"모른다"는 `completion` 이 나른다.**

⚠ **`occupied` 를 OR 로 정한 것은 내 결정이고 사용자 확인을 안 받았다.**
근거: *"한 센서라도 차를 보면 그 영역은 비어 있지 않다"* — **안전한 쪽으로 틀린다**(빈 자리를 차 있다고 하는 것이
그 반대보다 낫다). 🔴 **AND 가 맞다면 이 줄을 고쳐라. 이 문장이 그 물음을 살려 둔다.**

## 8.5 전달 시점 — **매 `state` 마다 전부. 부분 갱신 없다**

```
🔴 `state` 를 보낼 때마다 그 자리의 `modules[]` 를 **전부** 싣는다
   부분 갱신·증분 없음 · "접속 시 1회"도 아니다
```
⚠ **"접속 시 1회"로 하면 받는 쪽이 사본을 갖게 되고 사본은 낡는다**(CLAUDE.md).
**값이 바뀌는 것이 이 필드의 존재 이유이므로 매번 보낸다.**
**대가**: `state` 가 커진다. 🔑 **`map` 은 지형(느리게 변함)이고 `state` 는 값(매번 변함)이다** —
**정적 필드(`devid`·`kind`·`idx`)는 `map` 에만, 변하는 것(`value`·`known`·`reason`)만 `state` 에 둔다.**

## 8.6 예제 — **정본이다. 예제가 산문을 어기면 예제가 틀린 것이다**

```json
{"type":"state","epoch":7,"ts_ms":1755500000123,
 "zones":[
   {"id":"영역1","occupied":true,"reserved":false,
    "actions":{"reserve":{"ok":true,"reason":null}},
    "completion":"complete",
    "modules":[{"devid":"P1","name":"A1","value":1,"known":true},
               {"devid":"P1","name":"B1","value":0,"known":true}]},

   {"id":"영역2","occupied":false,"reserved":false,
    "actions":{"reserve":{"ok":true,"reason":null}},
    "completion":"partial",
    "ok":1,"total":2,"missing":["B2"],
    "modules":[{"devid":"P1","name":"A2","value":0,"known":true},
               {"devid":"P1","name":"B2","known":false,"reason":"module_absent"}]},

   {"id":"출구","kind":"exit",
    "actions":{"open_gate":{"ok":false,"reason":"node_offline"}},
    "completion":"unknown",
    "modules":[{"devid":"P1","name":"X1","known":false,"reason":"node_offline"}]}
 ]}
```
🔴 **`영역2` 를 보라**: `known:false` 인 모듈에 **`value` 가 없다**. `completion:"partial"` 이고
`ok/total/missing[]` 이 **어느 것이 빠졌는지** 말한다. **화면은 `occupied:false` 를 그리되 부분임을 표시한다.**
🔴 **`출구` 를 보라**: `completion:"unknown"` 이므로 **`occupied` 자체가 없다** — 🔴 **이건 §8.4 와 어긋난다.**
**`kind:"exit"` 는 주차 영역이 아니라서 `occupied` 가 애초에 뜻이 없다**(§6.5 (나) 부류).
**주차 영역이면 `completion` 이 `unknown` 이어도 `occupied` 는 실린다.** 두 규칙이 다른 축이다.

## 8.7 ⚠ 이 절이 **아직 답하지 않는 것** — 분모를 먼저 적는다

```
· `occupied` 의 유도가 OR 인가 AND 인가  → §8.4. **사용자 확인 필요**
· 한 영역의 두 모듈이 **서로 다른 노드**에 있을 때 → 지금 전제는 한 노드다. REQ-0260(3b) 뒤에 다시 본다
· `known` 이 **언제 false 가 되는가의 시간 문턱** → 오프라인 판정(3.5초)을 쓸지 미정
· 🔴 **`kind` 의 닫힌 집합** — `IP`·`OBV` 둘뿐인가. 늘어나면 §8.1 의 뜻 가르기가 같이 바뀐다
```

## 8.8 🔴 **명세 대 실제 — 차이표** (2026-08-19 실측 · `server.cpp` `state_json()`)

**내가 §8.1~8.7 을 "새 계약"처럼 썼는데 대부분 이미 나가고 있다.** 갈라 적는다.
🔴 **web 화면이 이미 실제 모양을 읽고 있으므로, 다른 곳은 *명세를 코드에 맞춘다*. 전선을 바꾸지 않는다.**

| 항목 | 실제로 나가는 것 | 위 §8 이 쓴 것 | 판정 |
|---|---|---|---|
| 모듈 키 | `devid·name·idx·value·known` | `devid·name·value·known` | **실제가 정본.** `idx` 가 `state` 에도 있다 |
| 모름의 값 | `value:null` + `known:false` | *"`value` 를 싣지 않는다"* | 🔴 **§8.2 가 틀렸다. `value:null` 이 정본** |
| 사유 | **없다** | `reason` 을 붙인다 | ⏳ **미구현. 이것이 진짜 추가분이다** |
| `completion` | `pending·settled·mismatch·unknown` | `complete·partial·unknown` | 🔴 **§7.2.0 의 두 어휘가 아직 살아 있다** |
| `ok·total·missing[]` | **없다** | 있다 | ⏳ **미구현** |

### 🔴 8.8.1 `completion` 이 아직 두 벌이다 — **§7.2.0 에서 화해시켰는데 코드가 안 따라왔다**

```
코드가 내는 것 : pending | settled | mismatch | unknown   ← 조작 결과(액추에이터) 어휘
§3.5 가 정한 것 : complete | partial | unknown            ← 여러 모듈에 걸친 자리의 값 온전성
```
> ### **한 키가 두 뜻을 겸하고 있다. 겸하면 갈라야 정본이 생긴다.**
**둘은 다른 것을 잰다** — 앞은 *"내 명령이 먹었나"*, 뒤는 *"이 자리 값을 다 아나"*.
🔴 **한 자리에 둘 다 필요해질 수 있다**(차단봉 영역: 명령도 하고 값도 읽는다).
→ **이름을 갈라야 한다. 그 결정은 아직 안 했다.** §8.7 에 열린 항목으로 넣는다.
⚠ **그때까지 화면은 `completion` 을 `kind` 별로 다르게 읽어야 한다** — 그 사실을 web 에 알린다.

### 🔴 8.8.2 **다른 노드의 모듈은 항상 `known:false` 가 된다** (web 이 코드에서 찾았다)

```cpp
if (z.modules[m].first == park.devid)          // 🔴 park **한 대**만 본다
    for (k…) if (park.mods[k].first == …) { mi = (int)k; break; }
const bool known = (mi >= 0 && mi < mod_bits_n);
```
**`park.devid` 가 아닌 노드의 모듈은 `idx:-1 · known:false · value:null`.**
```

🔴 REQ-0260(7영역) : 영역1 ← A1·B1 이 **서로 다른 노드**에 있으면 그 자리가 통째로 미상으로 그려진다
```
🔑 **이건 `3b`(`map<devid,Node>`)가 없어서 생기는 것이다** — 내가 *"순수한 정리"* 로 미뤄 둔 그 항목이
**두 번째로 기능의 전제로 드러났다**(첫 번째는 가상 아두이노).
✅ **계약(키 이름)은 안 바뀐다. 채우는 범위만 넓히면 화면은 안 고쳐도 된다**(web 확인).

### ✅ 8.8.3 그래서 **실제로 할 일은 셋뿐이다**

```

③ 여러 모듈 자리의 온전성을 `ok/total/missing[]` 로 낸다 · `completion` 이름 갈래 정리
```
⚠ **①은 REQ-0260 과 같은 배포다**(같은 구조 변경). **②③은 화면 계약 추가라 그 뒤다.**

## 8.9 🔴🔴 **순서를 어기면 "모름"이 "거짓 확신"으로 바뀐다** — ① 을 ② 앞에 하지 마라

루트 지시는 *"① `idx` 를 그 모듈을 등록한 노드에서 찾아라(park 고정을 걷어낸다)"* 였다.
**그것만 하면 더 나빠진다.** 코드로 확인했다:

```
server.cpp:882  struct Server {
server.cpp:909      Node park;
server.cpp:932      int  mod_bits[REG_MODS_MAX];   ← 🔴 **Node 가 아니라 Server 의 것이다**
server.cpp:941      int  mod_bits_n;
```
> ### **비트열은 서버에 *한 벌*뿐이다. 노드마다 있는 것이 아니다.**

**그래서 ①만 하면**: 둘째 노드의 `mods` 에서 `idx` 를 찾아내고 그 `idx` 로 **주 노드의 비트열을 읽는다.**
```
지금        : known:false · value:null       → 화면 ⚪ 모름   (정직하다)
①만 한 뒤  : known:true  · value:true/false → 화면 🟢/🔴     🔴 **다른 노드의 비트를 그 모듈의 값이라고 말한다**
```
> ### **"모른다"가 "안다(틀림)"로 바뀐다. 이건 개선이 아니라 회귀이고, 화면에는 정상으로 보인다.**
🔑 **`known:false` 는 지금 구조에서 *옳은 답*이다.** 값 경로가 없는데 값을 만들어 내면 그게 지어내는 것이다.

**그러므로 순서는 뒤집힌다:**
```
② 먼저 : `mod_bits`·`mod_bits_n` 을 **`Node` 로 내린다** (= 3b `map<devid,Node>` 와 같은 작업)
① 다음 : `idx` 를 그 모듈의 노드에서 찾고 **그 노드의 비트열**을 읽는다
🔴 ①을 단독 배포하지 마라. 계약은 안 깨지는데 **값이 조용히 거짓이 된다**
```
⚠ **`map_json()` 은 이미 `all_nodes()` 를 훑는다**(같은 파일에서 두 곳이 다른 규칙을 쓴다).
**그건 `idx`·`kind` 만 쓰기 때문에 안전하다** — **비트열을 안 읽는다.** 그래서 그쪽은 고칠 것이 없다.
🔑 **"저기는 이미 그렇게 하는데 여기는 왜"가 항상 "여기를 저기처럼 고쳐라"는 아니다. 읽는 대상이 다르다.**

## 8.10 `known:false` 의 **사유 코드** `[socket 확정 · 이것이 이번에 내가 새로 정하는 유일한 이름]`

지금은 원인 셋이 **같은 모양으로 나온다**(`known:false · value:null`). **원인이 다른데 표시가 같으면 아무도 못 고친다.**
`modules[].reason` 에 싣는다. **§6.5 의 기존 코드를 먼저 쓰고, 없는 것만 새로 만든다:**

| 코드 | 뜻 | 출처 | 고치는 사람 |
|---|---|---|---|
| `node_offline` | 그 노드가 오프라인이다 | **§6.5 기존** | 없음(기다린다) |
| `node_unregistered` | 아직 등록 전이다 | **§6.5 기존** | 없음(기다린다) |
| `module_absent` | 등록은 됐는데 그 모듈이 목록에 없다 | **§6.5 기존** | 배선·설정 |
| `bits_undecoded` | 등록은 됐는데 **비트열을 해독 못 했다**(`mod_bits_n == 0`) | 🆕 | socket(파서) |
| `bits_out_of_range` | 모듈 `idx` 가 **비트 폭 밖**이다 | 🆕 | 폭 계약(socket·arduino) |

🔴 **`bits_unavailable` 이 지금 둘째 노드에서 나올 코드다.** 이름을 *"이 노드는 주 노드가 아니다"* 로
짓지 않은 이유: **그건 지금 구현의 사정이지 계약의 뜻이 아니다.** §8.9 ②를 하면 이 코드는 **안 나오게 된다** —
**코드는 남고 발생이 0 이 된다.** 🔑 **구현 사정을 이름에 박으면 구현이 바뀔 때 이름이 거짓이 된다.**

⚠ **`reason` 은 `known:false` 일 때만 싣는다.** `known:true` 면 **키가 없다**(§6.5 존재/부재 규칙).
⚠ **화면은 모르는 `reason` 코드를 조용히 무시하고 ⚪ 로 그린다** — 새 코드가 늘어도 화면이 안 깨진다.

```
`slots`·`base_*`·`pend`·`gate_want` 를 **`DEV_SENSORS`/`DEV_ACK` 를 통해** 넘기면
`on_ard_line` 은 **순수 파서**가 되고, 그때 비로소 **떼어 낼 단위**가 된다.

### 8.13.3 🔴 그러므로 **REQ-0263 과 REQ-0260 은 경쟁이 아니라 같은 분리다**

```
사용자 (REQ-0260) : "새 노드는 디바이스다. n 은 주차자리다. **개별 구조다. 연결되지 않는다**"
사용자 (REQ-0263) : "슬롯 경로를 떼고, 슬롯 아닌 수정에 안 흔들리게 하라"
```
> ### **후자를 성립시키는 경계가 바로 전자가 요구한 경계다. 노드와 자리를 가르지 않으면 뗄 수 없다.**
**`slots` 9회 참조가 그 증거다** — 노드 파서가 주차 자리를 직접 쓰고 있다.

### 8.13.4 순서 — **루트 판단(①추출 먼저)에 동의한다. 다만 앞에 한 조각을 붙인다**

```
0) ②-a  on_ard_line(Node&, …) — 호출부는 `park` 를 넘긴다
        🔴 **거동 변화 0 · hex 대조로 증명.** 이것이 추출의 *전제*다
        (park 32회 참조가 인자로 바뀌지 않으면 "노드 안에서 닫힌 파서"가 안 된다)
1) 효과를 이음매로 : slots·base_*·pend·gate_want → DEV_SENSORS/DEV_ACK
        ⚠ **한 종류씩.** 단계 C 가 정한 방식 그대로 — 매 조각이 동작한다
2) 파일 분리 + 잠금            ← 루트가 검사기를 만든다
3) 그 위에서 0260 · 0262
```
🔑 **0)과 1)을 건너뛰고 2)를 먼저 하면**: 잠근 파일이 **0260·0262 때마다 열려야 한다.**
**잠금이 매번 예외를 요구하면 그건 잠금이 아니다.**

### 8.13.5 ⚠ "거동 변화 0" 의 판정 — **산출물로 한다**

`espInit` 판례: *이름만 바꾼 줄 알았는데 `millis()` 시점이 29줄 앞당겨져 hex 15줄이 달랐다.*
```
-O2 빌드 산출물 대조 : 같으면 통과
🔴 다른 것 자체는 실패가 아니다 — **설명 없이 다른 것이 실패다**
⚠ **선후가 바뀐 곳을 따로 세라** — 앞당김은 눈에 띄고 **선후 교체는 안 띈다**(arduino §26)
```
⚠ **②-a 는 "모으는 것"이 아니라 "인자를 넘기는 것"이므로 산출물이 같아야 한다.**
**다르면 내 판단이 틀린 것이고, 그때 멈추고 왜 다른지부터 답한다.**

# 9. 7영역 · 센서 이중화 `[사용자 확정 (A) · 2026-08-19 · REQ-0260]`

> ## 🔴 **주차 자리는 5개다. 10개가 아니다.**
> 각 자리에 **주차확인센서가 둘**(앞/뒤 또는 이중화)이다: `영역1` ← 센서 `A1`(#0) · `B1`(#5).
> **사용자가 대가를 보고 골랐다** — 예약 가능 자리 10 → 5, `B*` 예약 버튼 사라짐.

## 9.1 확정 사항

```
지형 : A1~A5 (각 센서 둘) + E1(입구) + X1(출구) = **7영역**
id   : 🔴 **Zone.id 는 A1~A5 를 유지한다** — 전선 `R,<rid>,A1,<user>` · ACK 에코 · slots[] 색인 불변
       **전선 변경 0 · arduino 굽기 0.** 화면 라벨("영역1")은 web 이 붙인다
       ⏳ id 개명(영역1~5)은 **별건** — arduino 굽기와 같은 경계에서 나중에
slots[10] : **남는다.** 모듈 값의 원천이고 옛 `snapshot` 메시지가 그대로 쓴다
```

### ⚠ `cells` — **강제는 풀되 정의는 길이 1 로 둔다**

`build_default_zones()` 가 `cells.size()!=1` 을 **강제 resize** 하던 것을 푼다.
**다만 지형 정의는 여전히 자리마다 칸 하나다.**
🔑 **이유: 격자에서 두 센서를 한 칸으로 그릴지 두 칸으로 그릴지는 *표현* 이고 web 의 몫이다.**
**내가 물리 배치를 지어내지 않는다.** 강제를 푼 것은 **web 이 필요해지면 서버가 막지 않게** 하려는 것이다.

## 9.2 🔴 `occupied` 유도 — **서버가 계산한다. 화면이 조합하지 않는다**

한 자리에 센서가 둘이므로 두 값에서 하나를 만들어야 한다. **갈래를 정한다:**

```
known 인 센서만 본다
  · 하나라도 1 → occupied = true      🔑 **안전한 쪽으로 틀린다**
  · 전부 0     → occupied = false
  · known 이 하나도 없다 → 🔴 아래 참조
```

### 왜 **OR** 인가 — 대칭이 아니다

```
빈 자리를 "차 있다"고 하면 : 운전자가 그 자리를 안 간다. **손해는 자리 하나**
찬 자리를 "비었다"고 하면 : 운전자가 **가서 못 댄다.** 그게 이 화면이 존재하는 이유를 깨뜨린다
```
> ### **두 오류의 대가가 다르므로 중립이 아니다. 이중화 센서에서 하나가 감지하면 차가 있다고 본다.**
⚠ **AND 로 바꾸면 센서 하나가 죽었을 때 그 자리가 영영 "비었다"로 보인다.** 그게 더 나쁘다.

### 🔴 두 센서가 갈릴 때 — **감추지 않는다**

`value_state` 가 그것을 말한다(§8.11). **그리고 갈림 자체를 계수한다:**
```
value_known / value_total 로 **몇 개를 아는지** 그대로 낸다
🔴 둘 다 known 인데 값이 다르면 → `sensor_split` 을 센다. 요약 줄에 낸다
   ⚠ 이중화의 목적이 **고장 감지**인데 세지 않으면 이중화가 아무 일도 안 한다
```

### 🔴 `known` 이 **하나도 없을 때** — 여기가 함정이다

```
value_state = "unknown"  ·  value_known = 0
occupied 는 **false 로 나간다**(키를 빼지 않는다 — 옛 `snapshot`·`slots[]` 와 형태를 맞춘다)
🔴 **그 false 는 "비었다"가 아니라 "모른다"이다.** 화면은 `value_state` 를 반드시 봐야 한다
```
⚠ **이것이 이 계약에서 가장 위험한 자리다.** `value_state` 를 안 보는 화면은 **모르는 자리를 빈 자리로 그린다.**
🔑 **그래서 `value_state` 를 *모든* 자리에 항상 싣는다** — 있으면 보게 되고, 선택적이면 안 본다.

## 9.3 🔴 `B*` 예약 요청 — **거절한다. 조용히 성공으로 답하지 않는다**

`B1..B5` 는 이제 자리가 아니라 **센서**다. 그런데 `slot_index("B5")` 는 여전히 5를 돌려준다
(`slots[10]` 이 남으므로). **그대로 두면 예약이 성공하고 화면 어디에도 안 보인다.**

```
사유 코드 : 🆕 **`not_reservable`** — "이 id 는 예약 대상이 아니다"
```
⚠ **이름을 `slot_is_sensor` 로 짓지 않았다** — **구현 사정을 이름에 박으면 구현이 바뀔 때 이름이 거짓이 된다**(§8.10 과 같은 규율).
🔑 **`not_supported`(전선 명령이 없다)와 다르다.** 저건 *"할 수 있는 일인데 수단이 없다"* 이고
이건 *"애초에 그 대상이 아니다"* 다.

### ✅ 전환 안전성 — **실측으로 확인했다**

```
2026-08-19 11:32:59  →ARD R,244,B5,uzw07apd   ← 사용자가 화면에서 눌렀다
2026-08-19 11:33:04  →ARD C,245,B5            ← 5초 뒤 취소
전환 시점 살아 있는 B* 예약 : **0건** (reserved 마스크 0000000000)
```
🔑 **"코드에 없다"와 "쓰이지 않는다"는 다른 진술이다.** `grep` 은 전자를 답하고 **로그가 후자를 답했다.**
⚠ **배포 순간 화면의 예약 버튼이 10 → 5 로 줄어든다.** 잃는 예약은 없지만 **사용자가 물어올 자리다.**
**배포 시각을 기록한다.**

# 10. 조립 API — **쓰는 코드가 먼저다** `[socket 설계 · REQ-0272 · 2026-08-19]`

> ## 🔴 **구현 상태: 설계만. 코드 없음.**
> 사용자 지시: *"복잡한 구조는 기본적으로 **은닉화**하여 개발자에게는 **간단한 구조로 이용 가능**해야 한다. **매우 중요하다.**"*
> ### **바깥(쓰는 쪽)이 단순해지지 않으면 이 리팩터링은 실패다 — 안이 아무리 깔끔해도.**
> **그래서 이 절은 *사용 예시부터* 적는다. 그 예시가 곧 합격 판정이다.**

## 10.1 지금(전) — **공개 API 가 없다. 그것이 문제의 크기다**

**자리 배치를 바꾸려면 `server.cpp` 안에서 서로 맞아야 하는 곳이 여럿이다.** 실측:
```
SLOT_ID[10] 배열                      · `SLOT_ID` 참조 **26곳**
`10` 이 박힌 곳                        **35곳**
build_default_zones() 의 루프 상한(5)
zone_of_module() 의 B→A 규칙
decode 폭(n) 가정 · 격자 좌표 계산
🔴 그리고 **장치 펌웨어의 `D` 선언이 그 이름과 맞아야 한다**(arduino 축)
```
> ### **"자리를 하나 더 놓는다"에 합의해야 하는 곳이 일곱이다. 하나만 어긋나면 조용히 틀린다.**
⚠ **헤더만 읽고 쓸 수 있는 길이 없다.** 지금은 **구현을 열어야만** 바꿀 수 있다 — 그것이 은닉이 없다는 뜻이다.

## 10.2 뒤 — **쓰는 코드는 이만큼이어야 한다**

```cpp
#include "parking.h"          // ← 🔴 **이 헤더 하나만 읽으면 쓸 수 있어야 한다**

int main() {
    ParkingLot lot;
    lot.spot("A1").sensor("A1").sensor("B1");   // 자리 하나에 센서 둘(이중화)
    lot.spot("A2").sensor("A2").sensor("B2");
    lot.spot("A3").sensor("A3").sensor("B3");
    lot.spot("A4").sensor("A4").sensor("B4");
    lot.spot("A5").sensor("A5").sensor("B5");
    lot.gate("E1", Gate::IN);                   // 입구
    lot.gate("X1", Gate::OUT);                  // 출구

    ParkingServer srv(lot);                     // 끝. 나머지는 서버가 한다
    return srv.run();
}
```

### 🔴 이 예시가 통과해야 하는 조건 — **이것이 합격 판정이다**

| 조건 | 왜 |
|---|---|
| **순서가 없다** | `spot` 을 `gate` 보다 먼저 쓰든 나중에 쓰든 결과가 같다. 🔴 *"이걸 부르기 전에 저걸"* 이 **하나도 없어야** 한다 |
| **`build()`·`init()` 이 없다** | 그런 함수가 있으면 그것이 곧 순서 요구다. **생성자와 `run()` 뿐이다** |
| **널 검사가 없다** | `spot()`·`sensor()` 는 **참조를 돌려준다.** 호출자가 `if (p)` 를 쓸 일이 없다 |
| **자리 수를 안 적는다** | `10`·`5` 같은 수를 **호출자가 어디에도 안 쓴다.** 표가 곧 개수다 |
| **격자 좌표를 안 적는다** | 배치는 화면의 몫이다. 서버는 **어느 센서가 어느 자리인지**만 안다 |

### 🔴 호출자가 **몰라도 되는 것** (= 자동화된 것)

```
비트열 폭(n) · 비트 순서 · idx 계산 · hex 해독      → 등록(`D`)에서 유도한다
`SLOT_ID` 배열 · slot_index 색인                     → 이름으로 찾는다
zone_of_module 의 B→A 규칙                           → **표가 직접 말하므로 규칙 자체가 사라진다**
occupied 유도(OR) · value_state · 센서 갈림 계수     → 서버가 계산해 값으로 준다
등록 대기·재등록·승격 순서·재접속                     → 서버 내부
```
🔑 **`zone_of_module()` 이 없어지는 것이 이 설계의 핵심이다.** 지금은 *"B3 은 A3 의 둘째 센서"* 를
**코드가 추측**한다. 표가 `spot("A3").sensor("A3").sensor("B3")` 라고 적으면 **추측이 사실로 바뀐다.**
⚠ 오늘 내가 넣은 `이름충돌` 거절도 **그 추측을 지키려는 임시 규칙**이었다 — 표가 생기면 같이 사라진다.

## 10.3 공개 표면 — **세어서 줄인다**

```
공개(헤더에 나가는 것) :  ParkingLot · Spot · Gate · ParkingServer   = **4**
                          그 안의 공개 함수 : spot · sensor · gate · run  = **4**
🔴 나머지는 전부 내부다 — Node · Zone · Pending · Conn · Server(3,918줄) · 전선 파싱 · 큐 · 재전송
```
**판정**: 🔴 **`.cpp` 나 구현 헤더를 열어야 쓸 수 있으면 은닉이 안 된 것이다.**
`parking.h` 만 읽고 위 예시를 쓸 수 있어야 한다.

⚠ **은닉이 "감춘다"가 아니다.** 값이 왜 그런지는 **여전히 로그·계수로 보인다** —
`value_state`·`센서갈림`·`이름충돌`·`비자리예약` 은 그대로 나간다.
> ### **감출 것은 *복잡함* 이고 드러낼 것은 *상태* 다. 둘을 바꾸지 마라.**

## 10.4 ⚠ 이 설계가 아직 답하지 않은 것 — 구현 전에 답해야 한다

```
· 같은 센서 이름을 두 자리에 적으면?      → 거절 · 기동 실패 · 로그. **조용히 넘기지 않는다**
· 표에 없는 이름을 장치가 `D` 로 선언하면? → 지금은 `module_absent`. 표 기준으로 다시 정해야 한다
· 자리 0개로 만들면?                       → 🔴 기동을 막는다("0자리는 정상 상태가 아니다" — 내 TODO 에 이미 있다)
· 표와 장치 선언이 어긋나면 누가 이기나?    → **표다.** 장치는 자기가 무엇을 가졌는지만 말한다
  ⚠ 그 결정이 `D,*,<drain>,<n>` 의 `n` 의 뜻을 바꾼다 — **arduino 축이라 그쪽에 먼저 알린다**
```
🔑 **마지막 항목이 전선 계약을 건드린다.** 구현 전에 arduino 와 맞춘다.

## 10.5 🔴 **자기 시험 — 내 §10.2 예시를 새 판정에 대 봤다. 절반이 떨어진다**

**판정(루트·사용자)**: *"처음 보는 사람에게 사용 예시만 보여 주고 **'이걸 실행하면 무슨 일이 순서대로
일어나나'** 를 물었을 때 답할 수 있어야 한다."*

**내 §10.2 예시로 그 질문에 답해 봤다:**
```
✅ 답할 수 있는 것 : 주차장을 만든다 → 자리를 만들고 센서를 붙인다 → 입구·출구를 만든다 → 서버에 싣는다
🔴 답할 수 없는 것 : `srv.run()` 뒤에 **무슨 일이 어떤 순서로** 일어나는가
```
> ### **`run()` 은 루트가 탈락시킨 그 이름이다 — `setup()`·`init()`·`process()` 와 같은 부류.**
> **한 줄인데 언제 무엇이 일어나는지 안 보인다.**

### 고친다 — **단계의 *나열* 은 호출부에 남긴다**

```cpp
#include "parking.h"

int main() {
    // ① 주차장을 조립한다 — **배치가 호출부에 그대로 보인다**
    ParkingLot lot;
    lot.spot("A1").sensor("A1").sensor("B1");
    lot.spot("A2").sensor("A2").sensor("B2");
    lot.spot("A3").sensor("A3").sensor("B3");
    lot.spot("A4").sensor("A4").sensor("B4");
    lot.spot("A5").sensor("A5").sensor("B5");
    lot.gate("E1", Gate::IN);
    lot.gate("X1", Gate::OUT);

    // ② 서버에 싣는다
    ParkingServer srv(lot);

    // ③ 포트를 연다 — 아두이노 · 화면 · 폰
    srv.listen(Ports::standard());

    // ④ 한 박자마다 : 프레임 수신 → 자리 판정 → 하행 송신 → 화면 방송
    while (srv.serveOneTick()) { }
    return 0;
}
```

**바뀐 것 셋:**
```
`run()` → `listen()` + `serveOneTick()`   🔑 **포트를 여는 것과 도는 것을 갈랐다** — 둘은 다른 일이다
`while` 을 호출부에 남겼다                  🔑 **"이건 루프다"가 코드에 보인다.** 감추면 안 보인다
④ 주석이 **한 박자의 순서**를 적는다        🔑 그 넷이 이 시스템이 하는 일의 전부다
```
⚠ **자동 배선을 쓰지 않았다.** `lot.spot(...).sensor(...)` 가 한 줄로 줄어들 수 있었지만
**"언제 무엇이 붙는지"가 안 보이게 된다** — 루트가 지목한 그 함정이다. **배치는 호출부에 남긴다.**

### ⚠ 그래도 남는 한계 — 감추지 않고 적는다

```
`serveOneTick()` **안**은 여전히 안 보인다. 그 안에 재전송·격리·승격·재접속이 다 들어 있다
```
🔑 **그건 "어떻게"라서 감추는 것이 맞다**(루트의 갈라 읽기 그대로). **다만 "무엇을 어떤 순서로"는
④ 주석 한 줄로 드러난다.** 🔴 **주석이 아니라 코드로 드러내려면 박자를 넷으로 쪼개야 하는데,
그러면 호출자가 순서를 지킬 의무가 생긴다** — 그건 우리가 없애려던 것이다.
> ### **여기서 "흐름을 보이게"와 "순서를 요구하지 않게"가 처음으로 충돌한다. 넷으로 쪼개지 않는 쪽을 골랐다.**
⚠ **이 선택은 내 판단이다. 다르게 보면 바꿀 수 있게 근거를 적어 둔다.**

## 11.6 ⚠ `serveOneTick()` 에 코드를 더할 때 — **안전망이 무엇이었는지 적어 둔다**

`run()` 의 루프 몸통을 메서드로 옮긴 것은 **기계적 분할**이었고, 그 안전은 **한 가지 확인**에 걸려 있었다:
```
옮기기 전 확인 : 루프 몸통에 **최상위 `continue`/`break`/`return` 이 하나도 없다**
                 awk 'NR>=<시작> && NR<=<끝> && /^            (continue|break|return)/'  → 빈 출력
```
**그 확인이 안전망의 전부였다.** 다음 사람이 이 층에 코드를 더할 때 같은 함정에 빠질 수 있으므로 적는다.

### ✅ 그런데 옮긴 뒤로 **둘은 구조적으로 막혔다** — 실험으로 확인했다

```
최상위 `continue;` 를 넣고 컴파일 → **error: 'continue' statement not in loop statement**
`break;` 도 같다 — 루프가 아니므로 **컴파일러가 잡는다**
```
🔑 **분할이 위험 셋 중 둘을 "조용한 것"에서 "컴파일 실패"로 바꿨다.** 이건 분할의 부수 효과가 아니라 이득이다.

### 🔴 남는 위험은 `return` 하나다 — 그리고 그것이 가장 나쁘다

```
최상위 `return false;`  → **컴파일된다.** 그런데 뜻이 "이 박자를 건너뛴다"가 아니라 **"서버를 멈춘다"**
⚠ 옛 코드에서 `continue` 였을 자리에 무심코 쓰면 **서버가 조용히 죽는다**
✅ 이 박자를 건너뛰려면 **`return true;`** — 멈추는 것은 `g_stop` 이 정한다
```
**코드 주석에도 같은 문장을 박았다** — 명세만 적으면 코드를 고치는 사람은 안 읽는다.

## 11.7 ⚠ `git add -f` — **내 진단이 절반만 맞았다** (기록)

세 번 `-f` 를 썼고 매번 *"`.gitignore` 가 무시한다"* 라고 적었다. 루트가 재서 반박했고, **내가 다시 쟀다:**
```
지금 : git check-ignore -v <서버 소스 8개> → **전부 빈 출력**(무시 안 됨)
       양성 대조 `x.o` 는 `.gitignore:123` 에 정확히 걸린다 — 도구는 작동한다
🔴 그런데 : 첫 `add` 는 실제로 **거부 메시지**를 냈다("paths are ignored … 조별과제샘플/server")
       그 뒤 루트가 커밋 `71eb251` 로 **그 줄을 지웠다**
```
> ### **내 첫 진단은 그 시점에 맞았고, 둘째·셋째는 확인 없이 습관으로 붙인 것이다.**
> ### **`-f` 는 무시된 파일도 넣고 그냥 새 파일도 넣으므로 *어느 쪽이든 성공한다* — 그래서 틀린 진단이 매번 확증된다.**

🔴 **비용**: 습관이 된 `-f` 는 **언젠가 진짜 무시 규칙을 뚫는다.**
2026-08-16 에 `server_*` 규칙이 소스를 먹은 사고를 **`-f` 는 조용히 통과시킨다.**
✅ **앞으로**: `git add <경로>` 를 `-f` 없이 치고, **거부되면 그때 `git check-ignore -v` 로 이유를 본다.**
🔑 **"고쳐졌는지"를 다시 재지 않으면 남이 고쳐 준 것도 내 진단이 계속 참인 줄 안다** — §시점 진술.
