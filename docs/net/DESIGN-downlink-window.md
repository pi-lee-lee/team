# 하행 송신 창 — 조용한 구간에만 쏘는 설계 (초안)

> **설계만이다. 구현·배포는 승인 뒤.** 관측 창이 돌고 있다.
> 작성 2026-08-17 · socket-engineer · 사용자 발안(*"하행 전에 신호를 보내고 다음 사이클은
> 하행을 우선하는 구조"*)을 서버 쪽으로 옮긴 것.

## 1. 무엇을 고치려는가

**서버는 장치가 지금 송신 중인지 모르고 하행을 쏜다**(원장 §8.15). ESP8266 은
**AT 명령과 `+IPD` 가 같은 UART 를 공유**하므로, 장치가 `AT+CIPSEND` 중일 때 하행이
들어오면 **두 스트림이 한 줄에 섞인다.**

관측된 대비(원장 §8.17):

| | 착지 위치 | 결과 |
|---|---|---|
| 성공 **10건** | **`SEND OK` 직후** = 전송과 전송 **사이** | ✅ 한 바이트도 안 깨짐 |
| 실패 **1건** | **`AT+CIPSEND` 진행 중** | ❌ `+IPD` 손상 → 3연속 실패 → 리셋 |

**우연히 좋은 창에 떨어뜨렸을 때는 다 됐다. 그것을 규칙으로 만든다.**

> ### 🔴 그런데 **`10/10` 은 이 가설을 받치지 못한다** (monitor·arduino 계산)
>
> ```
> 장치 송신 구간 점유율 10.2%(펌웨어 duty)
> → P(10건 전부 조용한 곳에 착지) = 0.898^10 ≈ **0.35**
> ```
> **셋 중 하나는 우연으로 나온다. 유의하지 않다.**
> 🔑 관측에서 낸 값(11건 중 1건 = 9.1%)과 duty 10.2% 가 **거의 같다** — 독립된 두 경로가 만났다.
> **즉 지금 자료는 "무작위로 떨어지고 있다"와 구별되지 않는다.**
>
> → **이 설계의 전제(착지 위치가 성패를 가른다)는 아직 가설이다.** §4 가 그것을 시험한다.

🔑 **전선 계약은 안 바뀐다.** 프레임도 필드도 그대로고 **서버 내부의 송신 시점 제어**뿐이다.
→ 장치 펌웨어 변경 불필요. `loop()` 이 이미 `drainPending`(하행)을 `statusTick`(상행)보다
먼저 돌린다 — **"다음 사이클은 하행 우선"이 구조적으로 이미 그렇다.**

## 1.5 🔴 **이 설계가 못 고치는 것 — 상한이 1/4 이다** (arduino, 루트 지시로 명시)

> ### **서버측 창 맞추기는 *하행이 유발한 충돌만* 없앤다. `busy` 폭풍은 하행 없이도 난다.**

```
창4 끊김 4건 중 하행이 얽힌 것 = 1건 (07:54)
나머지 3건(09:02 · 09:13 · 11:53) 은 하행이 아예 없었다
→ 이 설계가 줄일 수 있는 것의 상한은 1/4 이다
```

⚠ **이 문장이 없으면 나중에 "고쳤는데 왜 또 나나"가 생긴다.**
남은 3/4 는 **arduino 쪽 `busy` 폭풍 대책**이 맡는다.
🔑 **둘은 서로를 대체하지 않는다** — 내 것은 **하행 충돌**, arduino 것은 **`busy` 폭풍**이다.

## 1.6 ⚠ 위상 계산의 한계 — **"창이 맞았다"를 증명했다고 쓰지 마라**

`마지막 S + 1.113초 ≈ 다음 송신 시작`으로 위상을 추정하는데:

- 🔴 **주기가 상수가 아니다** — `DEBUG`·페이로드 길이·ESP 응답 시간의 함수다(원장 §8.11)
- 🔴 **창이 113ms 인데 양쪽 로그가 1초 해상도**라 **위상이 맞았는지 직접 확인할 수 없다**
  (내 `(S+…ms)` 계측은 **서버가 쏜 시점**을 ms 로 주지만, **장치가 그때 실제로 송신 중이었는지**는
  장치 쪽 계측이 있어야 한다)
- 🔴 **가장 크게 어긋나는 때가 하필 가장 위험한 때다** — 병리 구간에서 `SEND OK` 가 2~5초 걸렸고,
  그때 서버는 `S` 를 일찍 받고 **장치는 아직 바쁘다**

→ **그러므로 이 설계는 "결과로만" 검증된다**(손상률이 주는가).
**"창을 맞췄다"는 중간 주장을 근거로 쓰지 마라.**

## 2. 기본 규칙

```
dispatch() 호출 시:
    if (now_ms() - ard_last_ms) < W    →  즉시 송신          // 조용한 창 안
    else                               →  큐에 넣고 다음 S 를 기다림
다음 S 도착 →  큐를 비운다(즉시 송신)
```

`ard_last_ms` = **체크섬을 통과한 마지막 `S` 프레임 도착 시각**(서버 내부, ms).
**서버가 이미 갖고 있다. 새 신호를 전선에 추가하지 않는다.**

## 3. 🔴 답해야 하는 것 다섯 — 미리 적는다

### 3.1 `S` 가 안 오면? — **상한이 없으면 하행이 영영 안 나간다**

장치가 조용하면(busy·리셋·링크 끊김) 다음 `S` 가 안 오고 **큐가 영원히 안 비워진다.**
🔴 **하행이 조용히 사라지는 것은 지금보다 나쁘다** — 지금은 최소한 나가서 실패라도 한다.

**상한**: `now - ard_last_ms > D` 이면 **창을 포기하고 그냥 쏜다.**
→ **`D` 후보: `2 × 주기` ≈ 2.3초.** 근거: 3.5초 오프라인 판정보다 **작아야** 한다 —
오프라인이 걸린 뒤에 쏘면 서버가 이미 "장치 없음"으로 판단한 상태다.
⚠ **`D` 도 실측으로 정한다**(§4).

### 3.2 큐가 필요한가 — **필요하다. 그리고 순서를 지켜야 한다**

창을 기다리는 동안 하행이 여러 개 쌓일 수 있다(예약 여러 건 · `resync` 다건).
- **FIFO 로 순서 보존.** 순서가 바뀌면 예약/취소가 뒤집힌다
- ⚠ **한 창에 전부 쏟아붓지 마라.** 조용한 창이 약 1초인데 여러 건을 연속으로 밀면
  **그 자체가 장치 송신과 겹칠 수 있다.** → **창당 1건**부터 시작하고 실측으로 늘린다
- **중복 제거는 안 한다** — 재전송은 이미 `wire_rid` 로 멱등이 걸려 있다(§4.2). 여기서
  또 걸면 **두 겹이 되어 어느 쪽이 막았는지 못 가른다**

### 3.3 지연 비용 — **최대 약 1.1초. 감당 가능하다고 본다**

**화면은 이미 ACK 을 6초까지 기다린다.** 1.1초 추가는 그 예산 안이다.
⚠ 다만 **재전송 타이머와의 상호작용을 봐야 한다** — 재전송이 2초 간격인데 창 대기가
1.1초면 **첫 재전송 전에 나가는 것이 보장되지 않는다.** 상한 `D` 를 재전송 간격보다
작게 두면 이 문제가 닫힌다.

### 3.4 🔴 `ard_last_ms` 가 맞는 시계인가 — **한 군데서 안 맞는다**

주석(720행): *"체크섬을 통과한 `S`"* · **"세션 경계에서 리셋되지 않는다."**

- **리셋 안 되는 성질은 이 용도에 유리하다** — 재연결 직후 옛 값이 남아 있으면
  `now - ard_last_ms` 가 크게 나와 **"창 밖"으로 판정 → 기다린다.** 안전한 쪽으로 틀린다.
- 🔴 **그런데 승격 직후 경로가 걸린다.** `adopt_as_parking()` → `resync_reservations()` 는
  **첫 `S` 가 오기 전에** 하행을 쏜다. 게이트를 걸면 **그것이 첫 `S` 뒤로 밀린다.**

> ### 🔴🔴 이것이 **문서화된 불변식을 깬다** — 원장 §7.2
> ```
> +ARD 접속 → ⟳ 재하달 → →ARD R,2,B3,…  →  ←ARD S,0,…      ← 실측 기준선
> ```
> **`R` 이 첫 `S` 보다 먼저인 것이 이음매 리팩터링의 대조 기준**이다
> (*"하행 이관 때 이 두 줄의 순서가 뒤집히는지만 대조하면 된다"*).
> **게이트를 걸면 내가 그 순서를 뒤집는다.**
>
> **선택지 둘 — 둘 다 대가가 있다:**
> 1. **`resync` 경로를 게이트에서 면제한다** — §7.2 유지. 대신 **가장 붐비는 순간
>    (승격 직후)에 보호가 없다**
> 2. **게이트를 걸고 §7.2 를 갱신한다** — 보호는 완전하지만 **리팩터링 대조 기준이 바뀐다**
>
> ⚠ **내가 지금 정하지 않는다.** 이건 **이음매 작업과 충돌하는 결정**이라 루트 몫이다.

### 3.5 🔴 `W` 를 실측으로 정하라 — **지금 자료로는 못 정한다**

**측정하려 했고, 막혔다:**

```
서버 로그 시각 형식 : "%Y-%m-%d %H:%M:%S"   ← **1초 해상도** (server.cpp:433)
조용한 창           : 약 1.0초
장치 활성 구간      : 약 113ms (주기의 10.2%)
```

🔴 **1초 해상도로 113ms 짜리 특징을 잴 수 없다.** 성공 10건의 착지 지연을 로그에서
뽑으려 했으나 **전부 같은 초에 뭉쳐 있어 구별이 안 된다.**

→ **`W` 를 지금 정하면 그것은 추측이다.** 루트가 "추측하지 마라"고 한 그 자리다.

**계측 방법 — 서버는 그 값을 이미 알고 있다:**
`dispatch()` 시점에 `now_ms() - ard_last_ms` 를 **계산해서 로그에 찍는다.**
게이트 없이 먼저 찍기만 하면 **하행마다 착지 위치가 ms 단위로 쌓인다.**

```
→ARD R,4,A1,u17,65  (S+0847ms)     ← 이 괄호가 없어서 못 재고 있다
```

**순서: ①계측만 추가해 배포 → ②착지 분포를 모은다 → ③`W`·`D` 를 그 분포에서 정한다 → ④게이트.**
**계측 추가는 거동을 안 바꾸므로 위험이 낮다.**

## 4. 🔴 검증을 어떻게 하나 — **이 설계의 가장 어려운 부분**

**"충돌이 줄었다"를 보이려면 분모가 필요한데, 지금 충돌은 `n=1` 이다.**
게이트를 켜고 "안 났다"고 해도 **원래도 잘 안 나는 것**이라 아무것도 못 보인다.

**그래서 순서가 이렇게 되어야 한다:**

### 4.0 🔴 **유도 시험은 내렸다 — 대신 "부재가 자료"다** (루트·arduino, 최종)

**유도를 안 하는 이유 둘:**
1. **위상을 1초 자로 113ms 에 겨냥할 수 없다** — 유도가 실제로 맞는다는 보장이 없다
2. **내 `20건` 계산의 전제가 "송신 구간에 100% 착지"였는데 그 전제가 안 선다**(arduino).
   ⚠ **계산이 틀린 게 아니라 조건부였다.** *"유도 20건 = 자연 200건"* 은 **유도가 맞을 때** 성립한다.
   **계산은 남겨 둔다** — 장치 계측으로도 안 갈리면 그때 쓴다.

**대신: 반이중이라 "안 보이는 것"이 곧 증거다.**
송신 중 도착한 `+IPD` 는 **장치에 안 보인다.** 그러면 장치 쪽 계수는 **영원히 0** 이고
**"충돌 없음"과 "충돌해서 못 봄"이 구별되지 않는다.**

> ### 🔑 **그래서 분모를 내가 준다: `rid=N 을 보냈는데 ACK 가 없는 건.**

**판정표**(자료 오기 전 확정 · 루트 승인 · arduino 제안):

```
d = (T − 1000ms)/T   (실측 duty · 지금 10.2%)      N = 내가 보낸 하행 수

ipds ≈ 0    이고  미도달 ≈ N×d   →  ✅ 충돌 가설 지지
ipds ≈ N×d  이고  미도달 ≈ 0     →  ❌ 충돌 가설 기각
둘 다 ≈ 0                        →  ⚠ **N×d < 1 인지 먼저 봐라.** 표본 부족이면 결론 없음
```

**필요량: `N ≥ 30`(기대 3건) · `N ≥ 49`(기대 5건).**
🔑 **시연 트래픽으로 자연히 쌓인다 — 일부러 고장을 만들지 않는다.**

### 4.1 ~~유도 시험이 가능하다~~ (참고로 남긴다 — 위 4.0 으로 대체됨)

내가 처음에 *"서버는 장치가 언제 송신하는지 모르니 시리얼을 보는 쪽이 필요하다"* 고 적었다.
**틀렸다. 서버는 `S` 도착 시각을 보므로 위상을 안다:**

```
마지막 S 도착 + 1.113초 ≈ 다음 CIPSEND 시작
→ 그 시점에 맞춰 쏘면 송신 구간(약 113ms)에 착지시킬 수 있다
```

⚠ **그리고 그게 낫다** — monitor 의 탭이 시험을 **유발**하면 관측자가 **참가자**가 된다.
**계측기는 판독 쪽에 둔다.**

### 4.2 표본 수 — **유도가 자연 착지보다 10배 싸다** (monitor 계산)

| 방법 | 필요 횟수 |
|---|---|
| **자연 착지**로 '송신 중' 1건 얻기 | 약 **10회** (3건이면 29회 · 5건이면 49회) |
| **유도**(송신 구간 100% 착지 가정) | — |
| → 손상률이 **50%** 면 `0/10` 이 나올 확률 | **0.001** |
| → 손상률이 **20%** 여도 `0/20` 확률 | **0.012** |

🔑 **유도 20건이면 답이 난다. 자연 착지로 같은 것을 하려면 200건이 든다.**
→ **비용이 명확하니 루트가 판단할 수 있다.**

### 4.3 절차

1. **유도로 기저를 만든다** — 위상을 맞춰 **송신 구간에 20건** 착지시킨다.
   **손상이 나오면 가설이 지지된다. 안 나오면 가설이 기각된다**(그것도 결과다)
2. **게이트를 켜고 같은 수를 쏜다.** 손상률이 떨어지면 그것이 효과다
3. **같은 자로 잰다** — 같은 펌웨어·서버·주입기·`n`

⚠ **`fake_arduino` 로는 이 검증을 못 한다** — 가짜 장치에는 **UART 도 AT 명령도 없어서
충돌이 재현되지 않는다.** 시험 인스턴스로는 **게이트가 의도대로 동작하는지**(창 밖이면
기다리는지)만 본다. **손상 여부는 실물에서만 난다.**

🔴 **1단계는 의도적으로 링크를 끊는 시험이다.** 관측 창과 겹치면 안 된다 — **루트가 순서를 정한다.**

## 5. 지금 확정된 것과 안 된 것

| | 상태 |
|---|---|
| 규칙의 뼈대(조용한 창에만 송신) | ✅ 확정 |
| 전선 계약 변경 없음 · 펌웨어 변경 없음 | ✅ 확정 |
| 상한 `D` 가 필요하다는 것 | ✅ 확정 (없으면 하행이 사라진다) |
| 큐 FIFO · 창당 1건부터 | ✅ 초안 |
| **`W`·`D` 의 값** | 🔴 **미정 — 계측부터** (§3.5) |
| **`resync` 면제 여부** | 🔴 **미정 — §7.2 와 충돌. 루트 결정** (§3.4) |
| **검증 설계** | 🔴 **기저를 먼저 만들어야 한다** (§4) |

**다음 한 걸음: 계측(착지 지연 로그)만 추가하는 것.** 거동을 안 바꾸고, `W` 를 추측이 아니라
실측으로 정할 수 있게 만든다.
