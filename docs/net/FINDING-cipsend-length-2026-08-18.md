# FINDING — `AT+CIPSEND=<n>` 길이 불일치가 "SEND OK 8초 초과"를 그대로 만든다

**작성** socket-engineer · 2026-08-18 · **근거** Espressif ESP-AT 공식 문서(context7 조회)
**상태** 🔮 **가설. 다만 판별이 싸고, 이미 있는 로그로 끝난다** — 새 관측 창이 필요 없다.

---

## 0. 왜 내가 쓰나

루트가 원문에서 두 줄을 뽑아 *"네 판단이 필요하면 요청해라"* 라고 남겼다.
**전선 위 바이트 순서와 프레이밍은 내 영역**이라 근거를 확인하고 적는다.
⚠ **고칠 코드는 arduino 쪽이다. 나는 판별 방법까지만 낸다.**

## 1. 루트가 뽑은 두 줄

```
15:41:56  [AT] " S,1735,…A,111,B1,2,31" (53)   ← 페이로드가 먼저 찍혔다
15:41:56  [AT] "AT+CIPSEND=54" (13)            ← 명령이 나중 · 길이도 54 대 53
15:41:55  [SLOT-OOW] +306ms                    ← 하행이 송신 창 306ms 지점에 도착
```

## 2. 🔴 공식 문서가 말하는 것 — 추측이 아니다

Espressif ESP-AT 문서(`TCP-IP_AT_Examples`, `faq`):
```
AT+CIPSEND=4  →  OK
              →  >            (프롬프트: 이제 정확히 4바이트를 보내라)
              →  Recv 4 bytes
              →  SEND OK
```
> *"the system strictly adheres to the specified byte length. If the input exceeds the
> defined length, the system will process only the first n bytes, return a busy status…"*

**즉 장치는 선언한 `n` 바이트를 정확히 센다.**

### 🔴 그래서 **적게 보내면 `SEND OK` 가 안 온다**

```
선언 54  ·  실제 53  →  장치는 **54번째 바이트를 기다린다**
                     →  `SEND OK` 안 옴 → 서버/스케치는 8초를 기다린다
                     →  🔴 그동안 장치는 **AT 모드가 아니라 데이터 모드**다
                     →  다음 AT 명령의 첫 바이트가 **페이로드로 먹힌다**
                     →  그 명령이 깨지고 → 리셋
```
> ### **`stuck` → `esprst` 1:1 이라는 monitor 의 관측이 이 사슬의 모양 그대로다.**

⚠ **한 바이트 어긋남이 8초 침묵과 리셋을 만든다.** 크기와 무관한 이유도 여기서 나온다 —
**용량 문제가 아니라 셈 문제**다. 36B 로 줄여도 셈이 어긋나면 똑같이 걸린다.
**"작게 실어도 같은 일이 난다"가 이 가설에서는 모순이 아니라 예측이다.**

## 3. 🔑 분당 1회라는 규칙성이 이 가설에 오히려 맞는다

**모든 전송이 어긋나면 아무것도 동작하지 않는다. 59초는 멀쩡하다.**
→ **특정 종류의 메시지 하나만 길이가 어긋나고, 그 종류가 분당 한 번 나간다면** 관측과 일치한다.

🔴 **그러니 60초 주기를 부하에서 찾지 말고 메시지 *종류*에서 찾아라.**
```
찾을 것 : 분당 한 번 나가는 프레임 종류가 무엇인가
          그 종류만 길이 계산이 다른가 (종단자·널·접두 공백 포함 여부)
```
⚠ 위 로그의 페이로드가 `" S,…"` 로 **앞에 공백이 하나 있는 것처럼 찍힌 것**도 같은 부류의 단서다 —
**셈에 들어가는 문자와 찍히는 문자가 다르면 정확히 이 증상이 난다.**

## 4. ✅ 판별 — **이미 있는 로그로 끝난다. 새 관측 불필요**

장치는 다 받으면 **`Recv <n> bytes`** 를 스스로 찍는다. 그것이 판별자다:
```
막힌 시각에 `Recv 54 bytes` 가 있다  → 🔴 가설 기각. 다 받았고 지연은 다른 데 있다
`Recv` 가 없거나 수가 다르다        → ✅ 가설 유지. 장치는 아직 세고 있었다
```
**한 사건만 봐도 갈린다.** 시리얼 캡처에 `Recv` 가 남는지부터 확인하면 된다.
⚠ **`grep -a` 를 써라** — 시리얼 캡처는 제어문자가 섞여 있어 `grep` 이 바이너리로 판정하면
매치를 안 찍고 조용히 끝난다(루트가 오늘 두 번 밟았다).

## 5. 순서 문제(페이로드가 먼저 찍힘)에 대한 내 판단

**실제 전송 순서가 아니라 로그 기록 순서로 본다.** 근거는 단순하다 —
**진짜로 페이로드를 명령보다 먼저 보냈다면 단 한 건도 성공하지 못한다.**
59초는 정상이므로 순서 자체는 맞다고 보는 것이 자료와 맞다.
⚠ **다만 이것도 monitor 의 판정 대상이고, 내 몫은 "이 줄로는 순서 결함을 못 세운다"까지다.**

## 6. 내가 하지 않은 것

- **코드를 안 고쳤다.** 고칠 자리는 스케치이고 내 소유가 아니다.
- **새 관측을 요구하지 않았다.** 위 판별은 있는 캡처로 끝난다.
- **분당 1회의 정체를 단정하지 않았다.** 종류에서 찾으라는 방향만 냈다.
