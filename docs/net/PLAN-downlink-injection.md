## 0. 왜 필요한가 — A 에서 하행은 **측정되지 않았다**

A 창 3.20시간 동안 하행 명령이 **1건**뿐이었고 그것도 서버 기동 유예(90초) 안이었다.
→ 도달률은 "건강"이 아니라 **D3(미실행)** 이다.

🔴 **하행은 저절로 발생하지 않는다.** 상행은 장치가 알아서 보내지만 하행은 사람이
트리거해야 생긴다 — 가만히 두면 8시간 뒤에도 0 이다(원장 §5.2).

## 1. 무엇을 쏘나 — **무장하지 않은 `T,S`**. 상태를 안 바꾸는 유일한 하행이다

| 후보 | 문제 |
|---|---|
| `R`/`C` (예약/취소) | **주차 상태가 바뀐다.** `slots[]`·`reserved` 마스크가 움직이고, 장치가 **즉시 추가 S 프레임**을 보낸다 → 측정 도구가 측정 대상을 흔든다 |
| `W` | **지금 칩이 버린다**(원장 §3.2). 경로가 아니라 파서를 재게 된다 |
| **`T,S` (무장 안 한 상태)** | ✅ 장치가 `result=4` 로 **거절하고 아무 상태도 안 바꾼다** |

**이 성질은 이미 실측으로 확립돼 있다** — 원장 §7.6 의 `DEV_ACK` 격리 검증이
정확히 이 조건을 썼다. 그때 확인한 것을 여기서 재사용한다.

### 실측 확인 (2026-08-16 23:56, 시험 인스턴스 +100)

```
23:56:41  ←WS {"type":"test_set","slot":"A1","occupied":"1","rid":"inj-1"}
23:56:41  →ARD T,1,S,A1,1,5B          ← ①
23:56:41  ←ARD A,1,A1,4,34            ← ③  result=4
23:56:42  ←ARD S,6,0000000000,0000000000,6,P1,-,33   ← 다음 S 는 **평시 1Hz 박자 그대로**
```

🔑 **확인된 것 셋:**
1. `occupied`·`reserved` 마스크가 **`0000000000` 그대로** — 상태 변화 없음
2. `tmask` 가 **`-`**(무장 없음) 그대로
3. ACK 뒤에 **추가 S 프레임이 안 생겼다** — 다음 S 는 평시 주기(+1초)에 왔다
   (예약을 쏘면 여기서 즉시 S 가 하나 더 붙는다. 그게 §7.6 의 가림막이었다)

⚠ **무장(`T,A`)을 절대 보내면 안 된다.** 무장하면 그 뒤 `T,S` 가 **실제로 상태를 바꾼다.**
→ 주입기(`net/downlink_inject.py`)에는 **무장 명령이 옵션으로도 없다.**

## 1.1 🔴 다음 설계 — **골격만. 핵심 칸은 비워 둔다** (2026-08-17)

> ⚠ **이 절을 완성하지 마라.** 비어 있는 칸은 **arduino 의 바이트 단위 판독이 채운다.**
> **판독 전에 명세를 쓰면 그 문서가 판독을 유도한다**(루트).

### 목적이 바뀌었다

| | 옛 목적 (창4) | **새 목적** |
|---|---|---|
| 묻는 것 | "기전 C 가 고쳐졌나" | **"하행을 어떻게 쏘면 온전히 도달하나"** |
| 왜 | — | **`+IPD` 가 온전히 도착하지 않으면 C 를 시험할 방법이 없다** |

**순서가 뒤집혔다**: `B`(도달 실패) → 그다음 `C`(도달 후 처리).
**받는 것이 안 되면 받은 뒤의 일은 잴 수 없다.**

### ❓ 비어 있는 칸 — **arduino 판독이 답할 것**

1. **정말 UART 충돌인가?** `AT+CIP\x86+I\x88…` 가 상행·하행 혼재인지, 다른 것인지
2. **깨지는 조건은 무엇인가?** 장치가 `AT+CIPSEND` 중일 때만인가, 더 넓은가
3. **장치가 스스로 막을 수 있나, 아니면 서버가 시점을 피해야 하나** ← **이 답이 내 일을 정한다**

### 답이 나오면 내가 정할 것 (지금은 후보만)

- **하행 송신 시점 제약** — 서버가 장치의 송신 중을 피해서 쏜다.
  ⚠ 그런데 **서버는 장치 송신 상태를 모른다.** 알려면 **전선에 신호가 필요**하고,
  그건 **와이어 계약 변경**이다(§6 — 이름·형식 변경은 계약 변경).
- **재전송 간격 조정** — 지금은 2초 간격 3회다. 충돌이면 **같은 자리를 세 번 밟을 수 있다.**
- **아무것도 안 바꾸는 선택** — 장치 쪽에서 닫히면 서버는 그대로 둔다. **이쪽이 더 싸면 이쪽이다.**

🔴 **어느 것도 지금 고르지 않는다.** 후보를 적어 두는 이유는 **판독이 왔을 때 무엇을 물을지**
미리 알아 두려는 것이지, **결론을 예약해 두려는 것이 아니다.**

### 안 바뀌는 것

- **주입기는 그대로**(`592ce4a`) — 도구를 바꾸면 비교가 깨진다
- **표본·중단 조건·성공 판정을 자료 보기 전에 적는다** — 이건 설계가 바뀌어도 유지한다
- **`n` 과 미실행 건수를 판정문에 그대로 적는다**

| 물음 | 답 |
|---|---|

(C-2 는 **소비자 쪽 한 줄**로 닫았고 `[8c]` 시험으로 증명). **적으면 나중에 diff 와 안 맞는다.**

### 무엇을 묻는가

**바뀌는 것은 펌웨어뿐이다.** 주입기·주기·명령·서버를 **전부 그대로** 둔다 —
**같은 자로 재야 비교가 성립한다.** 주입기는 `8d09cee`(주입 직후 소켓 닫음)를 쓴다.

🔑 **그래서 이번 귀속은 깔끔하다 — 단, 하행 끊김에 한해서다.**
창3→창4 사이에 바뀐 것이 **펌웨어뿐**이므로 `T` 주입의 끊김 유무는 그 2줄에 귀속된다.
⚠ **그러나 밤샘의 "무주입 끊김 0건"은 서버도 같이 바뀐 구간이라 여전히 못 가른다.**
**두 문장을 섞지 마라** — 하나는 귀속되고 하나는 안 된다.

| 결과 | 뜻 | 다음 |
|---|---|---|
| **6/6 안 끊긴다** | **기전 확정** — 언더플로가 원인이었다 | `R`/`C` 시험으로 (사용자와 함께) |
| **끊긴다** | 다른 것이 남아 있다 | 즉시 중단 → 시리얼로 기전 재확인 |
| **일부만 끊긴다** | **결정적이 아니라 타이밍 의존**이다 | 아래 ⚠ |

⚠ **"일부만"을 미리 이름 붙여 둔다.** 언더플로는 `lastTxOkAt > now` 이면 **항상** 터지는
결정적 결함이라 **부분 실패는 예측되지 않는다.** 그게 나오면 **우리 모형이 아직 틀린 것**이고,
"대체로 고쳐졌다"로 반올림하면 안 된다.

### `n = 6` · 주기 `60초` — 근거

**`n=6`:**
- 옛 펌웨어에서 이 결함은 **결정적**이다 — `drainPending()` 의 송신이 **0ms 가 아닌 한**
  언더플로가 난다(실측 송신 64ms). 즉 `p(끊김 | 하행) ≈ 1`.
- 실측도 **2/2** 였고, 대조는 **무주입 6.30시간 0건**(P=2.7e-9)이다.
- 보수적으로 `p = 0.5` 로 낮춰 잡아도 **6건 전부 살아남을 확률은 0.016** 이다.
  `p ≈ 1` 이면 사실상 0. → **6 이면 "안 끊긴다"를 말할 수 있다.**
- 더 늘리지 않는 이유: 이 시험은 **사람이 지켜보는 짧은 검증**이고,
  표본을 늘려 얻는 것보다 **창을 오래 여는 비용**이 크다.

**주기 `60초`:**
- 지난번 5분은 **8시간 창을 전제한 값**이다. 지금은 그 전제가 없다.
- 60초면 **재접속(2초)·오프라인 판정(3.5초)보다 충분히 길어** 사건이 겹치지 않는다.
- 6건 × 60초 = **약 6분**. 사람이 지켜보기에 맞다.
- 🔑 **짧은 간격이 귀속을 오히려 돕는다** — 주입 사이에 자연 끊김이 낄 여지가 줄어든다.

### 🔴 중단 조건 — **이번엔 반대 방향이다**

> **끊김이 1건이라도 나면 즉시 멈춘다.** 3건을 기다리지 않는다.
> 지난번 **2/2 로 효과가 이미 확정**됐으므로, **여기서 1건이 나오면 그것이 곧 "안 고쳐졌다"** 이다.

**정지 권한은 monitor 유지**(`kill <pid>`). 나도 보는 즉시 멈춘다.

### 성공 판정에 볼 것 — **"안 끊겼다"만으로 부족하다**

1. **주입 6건 전부 `result=4`** (하행이 실제로 왕복했다)
2. **세션이 안 바뀐다** — `-ARD 세션# 종료` 가 **0건**, 같은 세션이 6건 내내 유지
3. **`uptime` 연속** (재부팅 아님)
4. 🔑 **시리얼에 `[NET] ★ 정지 감지` 가 0건** — **이게 직접 증거다.**
   서버 쪽 "안 끊겼다"는 결과이고, **감시기가 안 울린 것이 원인 쪽 확인**이다. monitor 확인.

### 착수 조건

- monitor 가 **창4 `t0`·`t_start`** 를 확정해 통보한 뒤
- **`t_start` 이후**에 시작 (`t0+150초` 같은 옛 값을 재사용하지 않는다)

## 1.4 🔴 **확정 설계 — 국면 둘로 나눈다** (루트 2026-08-17 00:2x, 창3)

첫 실물 주입(00:21:21)과 **같은 초에 링크가 끊긴 것**(원장 §8.7) 때문에 설계를 바꿨다.

| 국면 | 시간 | 무엇 |
|---|---|---|
| **0** | 완료 | 탭 개방(monitor). **시리얼 없이는 또 못 읽는다** |
| **1** | `t_start` ~ **+60분** (00:24:57 ~ 01:24:57) | 🔴 **무주입 기준선.** 새 펌웨어 + 새 서버의 λ 를 처음 잰다 |
| **2** | 01:25:00 ~ 아침 | **주입 재개 · 5분 주기.** monitor 가 **±5초 좁은 창**으로 근접 계산 |

### 왜 이 설계가 인과를 가르는가

A 창에서 인과를 못 가른 이유는 개입이 창의 **16%** 를 덮었기 때문이다.
**주입은 순간 사건**이라 60건 × ±5초 = 창의 **약 1%** 만 덮는다.
→ **끊김이 거기 몰리면 압도적 증거이고, 안 몰리면 주입은 무죄다.**
별도 대조 구간이 길 필요가 없어서 국면 1 을 60분으로만 잡았다.

### 🔴 중단 조건 — **미리 정한다**

> **국면 2 에서 끊김 3건 이상이 주입 ±5초 안에 들면 즉시 주입을 멈추고 보고한다.**
> 그건 결론이고, 그 뒤 밤은 깨끗한 λ 로 쓴다.

**사후에 정하면 자료에 맞춰 고르게 된다.** 그래서 자료를 보기 전에 적었다.

### 왜 5분인가 — 위와 아래에서 눌린 값이다

**아래로(더 자주 못 하는 이유) — 🔴 주입이 λ 를 부풀릴 수 있다.**
관측 대상인 링크 끊김의 유력 기전이 **장치 TX 순간**(CIPSEND 프롬프트 대기)이다.
그런데 **주입은 장치에게 ACK 를 하나 더 보내게 만든다 = TX 를 하나 더 시킨다.**
즉 **측정 행위가 측정 대상을 늘릴 수 있다.**

- 실물 장치의 자연 송신 주기는 **약 1.113초**다(2026-08-17 실측 — monitor `frame_gaps.py`

- 5분이면 자연 송신 **약 270회**에 주입 ACK **1회** → **약 0.37% 증가.**
- 2분으로 줄이면 약 1%. 아직 작지만 **이득이 없다** — 아래 참조.

**위로(더 드물게 하지 않는 이유) — 표본이 결론을 못 받친다.**
96건이면 전건 도달 시 실패율 상한을 **약 3%(95%)** 로 조일 수 있다.
48건(10분)이면 약 6% 로 두 배 헐거워진다. **96건에서 이미 충분하고, 더 늘려도

## 3. 무엇으로 넣나 — `net/downlink_inject.py` (신규)

`ws_probe.py` 는 일회성 대화형 탐침이라 8시간 주기 주입에 안 맞는다. 전용 도구를 만들었다.

- **핸드셰이크·프레이밍을 다시 구현하지 않는다** — `ws_probe` 에서 import 한다.
  같은 것을 두 곳에 두면 갈라진다(원장 §5.5).
- **주입할 때마다 날짜 있는 한 줄을 남긴다**(원장 §1.1). 이것이 monitor 의 ①에 대한
  **독립 기록**이 된다 — 서버 로그가 잘려도 "무엇을 언제 넣었는지"가 남는다.
- **`result` 가 4 가 아니면 크게 찍는다.** 4 가 아니라는 것은 **무장 상태일 수 있다**는
  뜻이고, 그러면 상태가 바뀌었을 수 있다. 조용히 넘어가면 안 되는 자리다.
- 연결이 끊기면 **재접속한다**(8시간 동안 링크가 끊길 것이 확실하다).
  즉시 반복하지 않고 최소 10초를 둔다 — 서버가 죽어 있을 때 초당 수십 번 두드리지 않게.
- **위상 드리프트를 막는다**: 다음 주입 시각을 `next_at += interval` 로 절대 기준에서 잡는다.
  `sleep(interval)` 만 쓰면 왕복 시간이 누적돼 8시간 뒤에는 주기가 밀린다.

## 4. monitor 의 4칸에 어떻게 대응하나

| 칸 | 내 주입기가 보는 것 | monitor 가 가르는 것 |
|---|---|---|
| **D0 도달** | ACK `result=4` 수신 | ①②③ seq 일치 |
| **D1 받았는데 응답 없음** | ACK 없음(30초) | ②는 있고 ③ 없음 |
| **D2 못 받음** | ACK 없음(30초) | ②③ 둘 다 없음 |
| **D3 미실행** | 주입 0건 | ①이 0건 |

🔴 **내 기록만으로는 D1 과 D2 를 못 가른다.** 내가 보는 것은 서버 왕복(①③)뿐이고,
**②는 시리얼 로그에만 있다.** 그래서 주입기 요약에 그 한계를 명시해 뒀다.
**"ACK 없음 N건"을 "장치가 못 받았다"로 읽지 마라** — 그것이 D1/D2 를 합친 수다.

⚠ **seq 로 짝지을 때 인스턴스 경계를 넘지 마라.** seq 는 **인스턴스마다 1 부터 다시 시작한다**
(monitor 확인). 내 `rid`(`inj-N`)는 주입기 수명 동안 단조 증가하므로 **서버 재기동이
있으면 `rid` 와 seq 의 대응이 어긋난다** — 짝짓기는 **seq + 인스턴스**로 한다.

> ### 🔴 **적어 두는 것은 예측이지 방어가 아니다** (2026-08-17 추가)
>
> 아래 1번을 나는 **주입 전에 미리 적어 뒀다.** 그런데도 **첫 실물 주입과 같은 초에
> 링크가 끊겼고**, 게다가 **그것을 관측할 시리얼이 없는 상태에서 시작했다**(원장 §8.7).
>
> **위험을 문서에 적는 것과, 그 위험이 일어났을 때 볼 수 있게 해 두는 것은 다른 일이다.**
> 오늘 밤 절차서를 쓰다가 결함을 잡은 사례가 셋 있었지만 **이건 반대 사례다** —
> 적어 두고도 막지 못했다. 적었으면 그다음은 **관측 수단을 붙이는 것**까지 가야 한다.

1. **장치 TX 가 5분마다 1회 늘어난다**(자연 송신 대비 약 0.4%).
2. **WS 연결이 하나 상주한다**(주입기). 브라우저 한 대가 붙어 있는 것과 같다.
3. **A 창에는 이 둘이 없었다.** → **A 와 합산 금지**의 또 다른 이유다.
4. 🔴 **이 창이 나중에 펌웨어 A/B 의 A 팔이 되면, B 팔도 같은 주입을 받아야 한다.**
   한쪽만 주입하면 두 팔이 다른 부하를 받는다.

**배포 통보에 주기와 건수를 적는다**(루트 지시).
