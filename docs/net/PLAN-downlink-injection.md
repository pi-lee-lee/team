# 하행 주입 계획 — 새 기준선 창

> monitor `RECIPE-newbaseline-t0.md` §5.1(주입) · §8(도달 정의)에 맞춘 것.
> 작성 2026-08-16 23:5x · socket-engineer
> **아래 기전은 시험 인스턴스에서 실제로 돌려 확인했다.** 설계만 적은 것이 아니다.

## 0. 왜 필요한가 — A 에서 하행은 **측정되지 않았다**

A 창 3.20시간 동안 하행 명령이 **1건**뿐이었고 그것도 서버 기동 유예(90초) 안이었다.
→ 도달률은 "건강"이 아니라 **D3(미실행)** 이다.

🔴 **하행은 저절로 발생하지 않는다.** 상행은 장치가 알아서 보내지만 하행은 사람이
트리거해야 생긴다 — 가만히 두면 8시간 뒤에도 0 이다(원장 §5.2).

---

## 1. 무엇을 쏘나 — **무장하지 않은 `T,S`**. 상태를 안 바꾸는 유일한 하행이다

| 후보 | 문제 |
|---|---|
| `R`/`C` (예약/취소) | **주차 상태가 바뀐다.** `slots[]`·`reserved` 마스크가 움직이고, 장치가 **즉시 추가 S 프레임**을 보낸다 → 측정 도구가 측정 대상을 흔든다 |
| `W` | **지금 칩이 버린다**(원장 §3.2). 경로가 아니라 파서를 재게 된다 |
| **`T,S` (무장 안 한 상태)** | ✅ 장치가 `result=4` 로 **거절하고 아무 상태도 안 바꾼다** |

**이 성질은 이미 실측으로 확립돼 있다** — 원장 §7.6 의 `DEV_ACK` 격리 검증이
정확히 이 조건을 썼다. 그때 확인한 것을 여기서 재사용한다.

### 실측 확인 (2026-08-16 23:56, 시험 인스턴스 +100)

```
23:56:41  ←WS {"type":"test_set","slot":"A1","occupied":"1","rid":"inj-1"}
23:56:41  →ARD T,1,S,A1,1,5B          ← ①
23:56:41  ←ARD A,1,A1,4,34            ← ③  result=4
23:56:42  ←ARD S,6,0000000000,0000000000,6,P1,-,33   ← 다음 S 는 **평시 1Hz 박자 그대로**
```

🔑 **확인된 것 셋:**
1. `occupied`·`reserved` 마스크가 **`0000000000` 그대로** — 상태 변화 없음
2. `tmask` 가 **`-`**(무장 없음) 그대로
3. ACK 뒤에 **추가 S 프레임이 안 생겼다** — 다음 S 는 평시 주기(+1초)에 왔다
   (예약을 쏘면 여기서 즉시 S 가 하나 더 붙는다. 그게 §7.6 의 가림막이었다)

⚠ **무장(`T,A`)을 절대 보내면 안 된다.** 무장하면 그 뒤 `T,S` 가 **실제로 상태를 바꾼다.**
→ 주입기(`net/downlink_inject.py`)에는 **무장 명령이 옵션으로도 없다.**

## 1.5 🔴 갈래가 **둘**이다 — 창을 여느냐에 따라 설계가 달라진다 (루트 2026-08-17 00:0x)

무인 7~8시간 λ 창을 접을 수 있다. **그래도 하행 확인은 값이 남는다** —
λ 는 "하나 더 재도 3배는 못 잡는다"지만, 하행은 **지표가 아니라 기능이 되는지 모르는 것**이다.
서버→장치 명령이 실제로 닿는지 우리는 **한 번도 검증한 적이 없다.**

| | **단발 확인** | **장기** |
|---|---|---|
| 언제 | 창을 **안** 열 때 | 창을 열 때 |
| 설계 | **30초 간격 · 6건 · 약 10분** | 5분 간격 · 약 96건 · 8시간 |
| 묻는 것 | **D0 냐 D2 냐 — 닿기는 하는가** | 실패율 상한 |
| 명령 | `--interval 30 --count 6` | `--interval 300` |

🔑 **단발은 교란 논리가 다르다.** λ 를 안 재면 "TX 를 하나 더 시킨다"의 비용이 사실상 없다 —
**지킬 창이 없기 때문이다.** 그래서 간격을 좁혀도 된다.
→ ⚠ **보고에 반드시 적는다: "이 구간은 λ 측정용이 아니다."**
안 적으면 다음 사람이 이 10분을 기준선 자료로 읽는다.

🔴 **단발이어도 "하행이 건강하다"로 쓰지 마라.** n=6 으로 말할 수 있는 것은
**"닿는 경로가 존재한다"** 까지다. 그것만으로도 A 의 **D3(미실행) 칸이 채워진다** — 그게 목적이다.

⚠ 코드 변경은 필요 없다. 주입기가 이미 `--interval`·`--count`·`--start-delay` 로 둘 다 받는다.

## 2. 장기 갈래 — 주기와 건수 **5분 · 8시간 기준 약 96건**

| 항목 | 값 | 근거 |
|---|---|---|
| 주기 | **300초 (5분)** | 아래 |
| 첫 주입 | **t0 + 150초** | 서버 기동 유예 `SERVER_START_GRACE_S=90` 을 넘긴다. 그 안의 하행은 **집계에서 제외되므로 넣어도 안 세어진다** — A 의 유일한 1건이 정확히 그렇게 버려졌다 |
| 예상 건수 | 8h → **약 96건** · 7h → 약 84건 | |
| ACK 마감 | **30초** | monitor 짝짓기 시한(§8.3)과 **같은 값**으로 맞췄다. 다르면 내 기록과 판정이 어긋난다 |

### 왜 5분인가 — 위와 아래에서 눌린 값이다

**아래로(더 자주 못 하는 이유) — 🔴 주입이 λ 를 부풀릴 수 있다.**
관측 대상인 링크 끊김의 유력 기전이 **장치 TX 순간**(CIPSEND 프롬프트 대기)이다.
그런데 **주입은 장치에게 ACK 를 하나 더 보내게 만든다 = TX 를 하나 더 시킨다.**
즉 **측정 행위가 측정 대상을 늘릴 수 있다.**

- 실물 장치의 자연 송신은 약 1Hz다(A 실측: 3.20h 에 10,176 프레임 ≈ 0.88/s).
- 5분이면 자연 송신 **약 265회**에 주입 ACK **1회** → **약 0.4% 증가.**
- 2분으로 줄이면 약 1%. 아직 작지만 **이득이 없다** — 아래 참조.

**위로(더 드물게 하지 않는 이유) — 표본이 결론을 못 받친다.**
96건이면 전건 도달 시 실패율 상한을 **약 3%(95%)** 로 조일 수 있다.
48건(10분)이면 약 6% 로 두 배 헐거워진다. **96건에서 이미 충분하고, 더 늘려도
상한이 크게 안 좁아지는 대신 TX 교란만 커진다.**

⚠ **이 상한은 "하행이 안 깨진다"는 뜻이 아니다.** D0 이 96/96 이어도 말할 수 있는 것은
**"3% 보다 나쁜 고장률은 배제했다"** 까지다. 판정문에 그렇게 적어야 한다.

## 3. 무엇으로 넣나 — `net/downlink_inject.py` (신규)

`ws_probe.py` 는 일회성 대화형 탐침이라 8시간 주기 주입에 안 맞는다. 전용 도구를 만들었다.

- **핸드셰이크·프레이밍을 다시 구현하지 않는다** — `ws_probe` 에서 import 한다.
  같은 것을 두 곳에 두면 갈라진다(원장 §5.5).
- **주입할 때마다 날짜 있는 한 줄을 남긴다**(원장 §1.1). 이것이 monitor 의 ①에 대한
  **독립 기록**이 된다 — 서버 로그가 잘려도 "무엇을 언제 넣었는지"가 남는다.
- **`result` 가 4 가 아니면 크게 찍는다.** 4 가 아니라는 것은 **무장 상태일 수 있다**는
  뜻이고, 그러면 상태가 바뀌었을 수 있다. 조용히 넘어가면 안 되는 자리다.
- 연결이 끊기면 **재접속한다**(8시간 동안 링크가 끊길 것이 확실하다).
  즉시 반복하지 않고 최소 10초를 둔다 — 서버가 죽어 있을 때 초당 수십 번 두드리지 않게.
- **위상 드리프트를 막는다**: 다음 주입 시각을 `next_at += interval` 로 절대 기준에서 잡는다.
  `sleep(interval)` 만 쓰면 왕복 시간이 누적돼 8시간 뒤에는 주기가 밀린다.

### 기동 — 갈래별 명령 (복사해서 치는 것)

**(가) 단발 확인 — 창을 안 열 때. 약 10분.**

```bash
python3 net/downlink_inject.py \
  --port 9900 --allow-production \
  --interval 30 --count 6 --start-delay 150 --slot A1 \
  --log /Users/idong-u/parking-logs/downlink-inject.log
```

포그라운드로 둔다 — 10분이고 **끝나는 것을 보고 판정할 것**이라 떼어 낼 이유가 없다.

**(나) 장기 — 창을 열 때. `PPID=1` 로 뗀다.**

```bash
nohup python3 net/downlink_inject.py \
  --port 9900 --allow-production \
  --interval 300 --start-delay 150 --slot A1 \
  --log /Users/idong-u/parking-logs/downlink-inject.log \
  >/dev/null 2>&1 &
```

⚠ **(나)는 `PPID=1` 로 떠야 한다.** 세션에 매달리면 세션이 죽을 때 주입이 멈추고,
**창 후반이 조용히 D3(미실행)가 된다** — 그런데 그 사실이 로그에 안 남는다.
`ps -o ppid=` 로 확인해라.

⚠ `--allow-production` 이 필요하다 — **이 도구는 운영에 넣는 것이 목적**이지만
사고로 도는 것을 막으려고 명시하게 했다.
⚠ **`PPID=1` 로 떠야 한다.** 세션에 매달리면 세션이 죽을 때 주입이 멈추고,
그러면 창 후반이 조용히 D3 가 된다.

## 4. monitor 의 4칸에 어떻게 대응하나

| 칸 | 내 주입기가 보는 것 | monitor 가 가르는 것 |
|---|---|---|
| **D0 도달** | ACK `result=4` 수신 | ①②③ seq 일치 |
| **D1 받았는데 응답 없음** | ACK 없음(30초) | ②는 있고 ③ 없음 |
| **D2 못 받음** | ACK 없음(30초) | ②③ 둘 다 없음 |
| **D3 미실행** | 주입 0건 | ①이 0건 |

🔴 **내 기록만으로는 D1 과 D2 를 못 가른다.** 내가 보는 것은 서버 왕복(①③)뿐이고,
**②는 시리얼 로그에만 있다.** 그래서 주입기 요약에 그 한계를 명시해 뒀다.
**"ACK 없음 N건"을 "장치가 못 받았다"로 읽지 마라** — 그것이 D1/D2 를 합친 수다.

⚠ **seq 로 짝지을 때 인스턴스 경계를 넘지 마라.** seq 는 **인스턴스마다 1 부터 다시 시작한다**
(monitor 확인). 내 `rid`(`inj-N`)는 주입기 수명 동안 단조 증가하므로 **서버 재기동이
있으면 `rid` 와 seq 의 대응이 어긋난다** — 짝짓기는 **seq + 인스턴스**로 한다.

## 5. 이 계획이 창에 넣는 변수 — 숨기지 않고 적는다

1. **장치 TX 가 5분마다 1회 늘어난다**(자연 송신 대비 약 0.4%).
2. **WS 연결이 하나 상주한다**(주입기). 브라우저 한 대가 붙어 있는 것과 같다.
3. **A 창에는 이 둘이 없었다.** → **A 와 합산 금지**의 또 다른 이유다.
4. 🔴 **이 창이 나중에 펌웨어 A/B 의 A 팔이 되면, B 팔도 같은 주입을 받아야 한다.**
   한쪽만 주입하면 두 팔이 다른 부하를 받는다.

**배포 통보에 주기와 건수를 적는다**(루트 지시).
