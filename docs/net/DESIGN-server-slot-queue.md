# 서버 하행 큐 — 슬롯 구조의 ③ (설계)

> 사용자 설계: **1.2초 주기 · 0.6 장치 송신 / 0.6 서버 송신.**
> ①슬롯 ②장치 큐(arduino) **③서버 큐 ← 이 문서**
>
> 작성 2026-08-17 · socket-engineer · **설계만. 배포는 신호 받고.**

## 0. 🔑 이 구조가 내 막힌 문제를 푼다

나는 `W`(송신 허용 창)를 정하려다 **서버 로그가 1초 해상도라 113ms 특징을 못 잰다**는 데서
막혔다(`DESIGN-downlink-window.md` §3.5). **그래서 "위상을 추정"하려 했다.**

> ### **이 설계는 추정하지 않는다. `S` 도착이 트리거다 — 장치가 알려준다.**

```
S 도착   →  그 직후가 **내 슬롯**
슬롯 밖  →  큐에 담는다. 버리지 않는다
```

🔑 **그리고 트리거라서 자기교정된다.** 장치가 느려져 `S` 가 늦게 오면 **내 슬롯도 같이 밀린다.**
**병리 구간에서 `SEND OK` 가 2~5초로 벌어져도 구조가 안 깨진다** —
스케줄이 아니라 **이벤트**이기 때문이다. **내가 "가장 크게 어긋나는 때가 가장 위험한 때"라고
적었던 그 문제가 사라진다.**

⚠ **그래서 "겨냥할 창이 없다"고 폐기 후보로 넣었던 하행 창이 되살아난다** —
**겨냥하지 않기 때문이다.**

## 1. 창 판정 — `now - ard_last_ms < W_srv`

### 🔴 네트워크 지연을 빼야 한다. 그리고 **양쪽 다** 빠진다

```
장치가 S 를 다 보낸 시각      t_send
내가 S 를 받은 시각           t_recv = t_send + d_up
내 하행이 장치에 닿는 시각     t_recv + x + d_down
장치 슬롯이 다시 열리는 시각   t_send + 0.6
```

**안전 조건**: `t_recv + x + d_down < t_send + 0.6`
→ **`x < 0.6 − (d_up + d_down)` = `0.6 − RTT`**

→ **`W_srv = 600ms − RTT − 여유`**

⚠ **`RTT` 를 추측하지 마라.** 서버가 이미 잴 수 있다:
`pend` 에 `sent_ms` 가 있고 ACK 도착 시각을 안다 → **왕복 실측**이 쌓인다.
(그 값은 `RTT + 장치 처리시간` 이라 **RTT 의 상한**이다 — 보수적이라 안전한 방향이다.)

🔑 **LAN 이면 RTT 가 수 ms 라 거의 안 깎이지만, 값이 아니라 방법을 박아 둔다** —
**Wi-Fi 가 붐비면 RTT 가 커지고 창이 줄어야 한다.** 고정 상수로 두면 그때 조용히 깨진다.

⚠ **`ard_last_ms` 는 "체크섬을 통과한 `S`" 시각이다**(§720). **이 용도에 맞다** —
깨진 프레임으로 창을 열면 안 된다.

## 2. 큐

| 항목 | 설계 |
|---|---|
| 순서 | **FIFO.** 예약/취소가 뒤집히면 안 된다 |
| 창당 건수 | 🔴 **arduino 실측값**(0.6초에 몇 건 처리되나). **지금 값을 옮겨 쓰지 마라** |
| 깊이 | **유한.** 아래 |
| 소켓 끊김 | **큐를 비운다.** 세션이 바뀌면 `wire_rid` 도 새로 시작하고, 옛 큐를 그대로 쏘면 **장치가 모르는 rid** 를 받는다 |

### 🔴 넘칠 때 — **"버리지 않는다"와 "무한히 쌓는다"는 다르다**

루트 지시는 *"버리지 말고 미루고 미룬 수를 로그에"* 다. **그대로 하되 깊이는 유한하다:**

- **깊이 안**: 미룬다. **미룬 수를 로그에 남긴다**(조용히 미루면 지연이 안 보인다 · 원장 §5.2)
- **깊이 초과**: 🔴 **조용히 버리지 않고 브라우저에 즉시 거절을 돌려준다.**
  → **`너무 빠릅니다` 류의 명시적 실패.** 사용자가 **"안 눌린 것"을 알게 된다**

⚠ **이게 "버리는 것"이 아닌 이유**: 버리는 것은 **아무도 모르게 사라지는 것**이다.
**거절은 사용자에게 말한다.** 원장 §0 — **측정한 것을 이름으로 삼고 해석은 옆 칸에서 한다.**

~~🔑 그리고 같은 자리 중복 클릭은 `has_pending_for(slot)` 가 이미 걸러서 52회를 눌러도
그 자리는 1건만 진행 중이다.~~

> ### 🔴 **틀렸다 — `has_pending_for` 는 "pending 이 살아 있는 동안"만 막는다** (web 반박)
>
> **화면이 롤백하면 사용자가 다시 누르고, 그때는 새 `rid` 이고 서버 `pending` 도 이미 풀려 있다.**
>
> ```
> 큐 대기 중 → 화면 타임아웃이 먼저 터짐 → 롤백 → 사용자가 다시 누름
> → 새 rid (has_pending_for 가 안 막는다) → **큐에 한 건 더**
> ```
>
> 🔴 **타임아웃이 짧을수록 큐가 더 쌓인다.**
> **내가 막으려던 그 증폭을 화면이 만들어 낸다.**
>
> → **그래서 화면 타임아웃은 "적당히 늘리는" 문제가 아니라 서버 값에 묶여야 한다**(§4-B).

## 3. `S` 가 안 오면 — **상한이 없으면 하행이 영영 안 나간다**

장치가 조용하면(busy·리셋·링크 끊김) **창이 안 열린다.**

```
now - ard_last_ms > D_max  →  창을 포기하고 그냥 쏜다
```

⚠ **`D_max` 를 3.5초(오프라인 판정)보다 작게 둔다.** 그 뒤에 쏘면 **서버가 이미
"장치 없음"으로 판단한 상태**에 쏘는 것이다.
→ **후보: 2주기(약 2.4초).** ⚠ **주기를 상수로 박지 말고 실측 간격을 쓴다**(원장 §8.11).

🔑 **"그냥 쏜다"가 옳은 이유**: 안 쏘면 **하행이 조용히 사라진다.**
**지금은 최소한 나가서 실패라도 한다** — 조용한 소실이 더 나쁘다.

## 4. 몰아치기 흡수 — **화면이 같이 바뀌어야 한다** (web 맞춤)

사용자가 **52회**를 눌러도 전선에는 규율대로 나간다. **그러면 지연이 사용자에게 보인다.**

🔴 **화면에 "대기 중"이 없으면 사용자가 다시 누르고 그게 또 쌓인다.**
**사용자가 재현한 것이 정확히 그 모양이다.**

**web 에 필요한 것:**
- **큐에 들어간 상태**를 화면이 표시할 수 있어야 한다 → **서버가 그 상태를 알려줘야 한다**
- 🔴 **그러려면 WS 응답에 "접수됨(큐 대기)"이 필요하다.** 지금은 `ack` 아니면 `error` 뿐이라
  **"받았고 아직 안 보냈다"를 말할 수단이 없다.** ← **이 설계가 요구하는 새 응답이다**

⚠ **이건 web 과 합의해야 하는 계약 변경**이다. 원장 §6: **구/신 동시 수용 → 통보 → 변경.**

### ✅ 4-B. 합의된 계약 (REQ-0155 · web 회신)

```json
{"type":"queued", "rid":"…", "slot":"A1", "ahead":2, "expires_ms":4800}
```

| 항목 | 결정 | 🔴 이유 |
|---|---|---|
| **별도 타입** | **필수** | web 의 dispatcher 는 **모르는 타입을 조용히 무시**한다. `ack` 에 필드를 넣으면 **옛 화면이 `type==='ack'` 만 보고 pending 을 지우며 "예약되었습니다"를 띄운다** — **전선에 나가지도 않은 요청을 성공으로 선언**한다 |
| `ahead` | **넣는다** | "대기 중"만으로는 **멈춘 것과 밀린 것**을 못 가른다. `3→2→1` 이 **진행 중이라는 사실**을 보인다 |
| **`expires_ms`** | 🔴 **서버가 준다 · (가) 방식 — 이 프레임을 받은 시점 기준 남은 상한(지속시간)** | 화면이 추측하면 안 된다. 그리고 **절대 시각(epoch)으로 주면 시계 어긋난 만큼 그대로 틀린다** |

### 🔴 `expires_ms` 의 기준점 — **지속시간이다. 절대 시각이 아니다**

```
enqueue 시점에 **마감시각을 고정**한다:   deadline = enqueue_ms + cap
queued 를 낼 때마다:                      expires_ms = deadline − now_ms()
```

**이 구현이 web 이 요구한 두 성질을 자동으로 만족한다:**
- ✅ **받은 시점 기준 남은 시간** — `now` 로 빼므로 프레임마다 그 순간 기준이다
- ✅ **같은 `rid` 로 여러 번 오면 단조 비증가** — `deadline` 이 고정이라 **`now` 가 커지면 줄기만 한다**

🔑 **`ahead` 로 다시 계산하지 않는 이유**: 그러면 앞이 밀릴 때 값이 **늘 수 있어** 단조성이 깨진다.
**항목마다 마감을 한 번 박고 그것만 빼면 단조성이 공짜로 나온다.**

⚠ **두 시계를 안 섞는다** — 서버는 `now_ms()`(자기 시계)로 **차이만** 계산해 보내고,
화면은 받은 **지속시간**을 자기 시계로 잰다. **어느 쪽도 상대의 시계를 안 읽는다.**
🔑 **web 이 자기 산식(`expires_ms + ACK_TIMEOUT`)에서 두 시계를 섞을 뻔한 것을 스스로 잡았다** —
*"화면은 브라우저 시계, 로그는 서버 시계"* 라고 자기가 적어 두고 그 안에서 밟은 자리다.

⚠ **`cap` 의 값은 `rxmax` 에 종속이다**(창당 처리 건수 → 대기 상한). **의미는 지금 확정,
값은 실측 뒤.** 값이 없다고 계약을 못 정하는 것은 아니다.
| 거절 `code` | **`queue_full` · `already_pending`** | 화면 문구가 **완전히 다르다**(시스템 사정 대 사용자 잘못 아님). 지금은 둘 다 `error` 라 못 가른다 |

🔴 **서버가 지켜야 하는 보장 한 줄:**
> **`queued` 를 보냈으면 그 뒤에 반드시 `ack` 또는 `error` 가 간다.**
> **그 보장이 없으면 화면의 중간 상태가 영구가 된다.**

🔑 **내 §5 마이그레이션 순서(서버 먼저 배포)가 성립하는 것도 별도 타입일 때뿐이다** —
`queued` 를 모르는 화면은 **무시하고 지금처럼 `ack` 만 기다리므로 현재 동작과 같다.**
**필드 방식이었으면 서버 배포가 그 순간 옛 화면을 깨뜨린다.**

⚠ **`ahead` 로 시간을 환산하지 않는다** — 그러려면 `rxmax` 가 필요한데
**그 상수를 화면에 박으면 §4 가 경고한 그것**이 된다. **화면은 "앞에 N건"까지만 말한다.**

## 5. 🔑 `@<rid>` 를 `S` 에 얹는 것이 **이 구조에서 필수가 된다**

**장치 슬롯에 나가는 것이 `S` 하나뿐이라면 ACK 는 거기 실려야 한다.**
별도 `A` 프레임을 보내면 **그것이 장치 슬롯을 또 쓰거나 서버 슬롯을 침범한다.**

→ **`DESIGN-ack-on-status.md` 는 폐기가 아니라 이 설계의 전제다.**
⚠ 다만 **동기가 바뀌었다**: 전에는 *"추가 송신이 수신을 막으니까"*(반이중), 이제는
*"장치 슬롯에 두 개를 넣을 수 없으니까"*(슬롯 구조). **같은 결론, 다른 이유다.**

## 6. 값이 정해져야 시작할 수 있는 것

| 값 | 어디서 | 상태 |
|---|---|---|
| **창당 하행 건수** | 🔴 **arduino 샘플 — 0.6초에 몇 건 처리되나** | **대기** |
| `W_srv` | `600ms − RTT − 여유` · RTT 는 서버 실측 | 방법 확정 · 값 대기 |
| `D_max` | 2주기 후보 · 오프라인 판정(3.5초)보다 작게 | 초안 |
| 큐 깊이 | 창당 건수 × 감당할 지연 | **위 값에 종속** |

🔴 **지금 값을 옮겨 쓰지 마라 — 전부 반이중 전제에서 나온 숫자다**(`ANALYSIS-halfduplex-vs-needed` §0-A).

## 7. 안 정한 것

- **`M`·`T` 도 같은 큐를 타는가** — 그럴 것으로 보지만 **`T` 는 시험용이라 규율을 우회할
  이유가 있을 수 있다.** 정하지 않았다
- **재전송이 큐를 타는가** — 재전송도 하행이다. **타야 할 것으로 보지만**, 그러면
  재전송 간격이 창 주기에 종속된다. **arduino 값이 나온 뒤에 정한다**
