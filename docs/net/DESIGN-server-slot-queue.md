# 서버 하행 큐 — 슬롯 구조의 ③ (설계)

> 사용자 설계: **1.2초 주기 · 0.6 장치 송신 / 0.6 서버 송신.**
> ①슬롯 ②장치 큐(arduino) **③서버 큐 ← 이 문서**
>
> 작성 2026-08-17 · socket-engineer · **설계만. 배포는 신호 받고.**

## 0. 🔑 이 구조가 내 막힌 문제를 푼다

나는 `W`(송신 허용 창)를 정하려다 **서버 로그가 1초 해상도라 113ms 특징을 못 잰다**는 데서
막혔다(`DESIGN-downlink-window.md` §3.5). **그래서 "위상을 추정"하려 했다.**

> ### **이 설계는 추정하지 않는다. `S` 도착이 트리거다 — 장치가 알려준다.**

```
S 도착   →  그 직후가 **내 슬롯**
슬롯 밖  →  큐에 담는다. 버리지 않는다
```

🔑 **그리고 트리거라서 자기교정된다.** 장치가 느려져 `S` 가 늦게 오면 **내 슬롯도 같이 밀린다.**
**병리 구간에서 `SEND OK` 가 2~5초로 벌어져도 구조가 안 깨진다** —
스케줄이 아니라 **이벤트**이기 때문이다. **내가 "가장 크게 어긋나는 때가 가장 위험한 때"라고
적었던 그 문제가 사라진다.**

⚠ **그래서 "겨냥할 창이 없다"고 폐기 후보로 넣었던 하행 창이 되살아난다** —
**겨냥하지 않기 때문이다.**

## 1. 창 판정 — `now - ard_last_ms < W_srv`

### 🔴 네트워크 지연을 빼야 한다. 그리고 **양쪽 다** 빠진다

```
장치가 S 를 다 보낸 시각      t_send
내가 S 를 받은 시각           t_recv = t_send + d_up
내 하행이 장치에 닿는 시각     t_recv + x + d_down
장치 슬롯이 다시 열리는 시각   t_send + 0.6
```

**안전 조건**: `t_recv + x + d_down < t_send + 0.6`
→ **`x < 0.6 − (d_up + d_down)` = `0.6 − RTT`**

→ **`W_srv = 600ms − RTT − 여유`**

⚠ **`RTT` 를 추측하지 마라.** 서버가 이미 잴 수 있다:
`pend` 에 `sent_ms` 가 있고 ACK 도착 시각을 안다 → **왕복 실측**이 쌓인다.
(그 값은 `RTT + 장치 처리시간` 이라 **RTT 의 상한**이다 — 보수적이라 안전한 방향이다.)

🔑 **LAN 이면 RTT 가 수 ms 라 거의 안 깎이지만, 값이 아니라 방법을 박아 둔다** —
**Wi-Fi 가 붐비면 RTT 가 커지고 창이 줄어야 한다.** 고정 상수로 두면 그때 조용히 깨진다.

⚠ **`ard_last_ms` 는 "체크섬을 통과한 `S`" 시각이다**(§720). **이 용도에 맞다** —
깨진 프레임으로 창을 열면 안 된다.

## 1.5 🔴 하행은 **창당 정확히 1거래** — 건수가 아니라 배치다 (사용자 확정)

> **이벤트가 전송을 만들지 않는다. 전송은 항상 돈다. 이벤트는 거기에 실린다.**

```
서버는 자기 창(600~1200ms)에 **큐에 있는 명령 전부를 묶어 한 번에** 보낸다
이벤트 시점에 보내지 않는다 · 보낼 게 없으면 안 보내도 된다
```

⚠ **그래서 "창당 몇 건"이 상한이 아니다.** 상한은 **한 거래에 실을 수 있는 바이트**다:

| 상한 | 값 |
|---|---|
| RAM(아두이노 여유 `free=1036`) | 배치 **200~300B** |
| **창당 회선 용량** | 🔴 **576B** = `600ms × 960 B/s` ← **이것이 불변량이다** |

### 🔴 `cap` 은 **건수가 아니라 바이트다**

`rxmax=16`(3판 실측)을 **그대로 쓰면 안 된다** — **40바이트 프레임**을 **하드웨어 UART** 로 잰 값이고
**실기는 둘 다 다르다.**

```
프레임 비용 = 페이로드 + LF + "+IPD,<n>:" 접두(8~9B)

19B 명령(R,1,A1,00000000,13) → 28B → 창당 **약 20건**
40B 명령(fdtest)             → 49B → 창당 **약 12건**
```
🔑 **건수는 12도 되고 20도 된다. 고정값이 아니다. `576B` 를 쓴다.**

⚠ **회선이 병목이지 장치가 아니다** — 회선 상한 계산 14.4 대 실측 16.

### 🔑 배치가 **하행에서도** 접두를 없앤다

ESP 는 **받은 TCP 조각마다** `+IPD` 를 붙인다 — **줄마다가 아니다.**
```
따로 10번 : "+IPD,19:" × 10 = 접두 80~90B   ← 창의 15%
묶어 1번  : "+IPD,199:" × 1 = 접두  9B
```
**상행에서 거래를 아끼는 것과 같은 이유로 하행에서는 접두를 아낀다.**

⚠ **한 줄 상한은 따로다**: `RX_CAP=96`(`client.ino:368`)이고 **접두가 그 안에 포함**된다
→ **한 줄 페이로드 87B 초과 금지.** **배치 전체가 아니라 줄 하나의 제약**이다.
(TCP 가 쪼개져 `+IPD` 가 여러 번 와도 파서는 LF 로 가른다.)

🔴 **`576B` 는 상한이지 보장이 아니다** — 실제 경로는 아직 `SoftwareSerial` 이고
슬롯이 겹침을 없애도 `cli()` 는 남는다. **실기 재측정 전까지는 상한으로만 쓴다.**

🔑 **배치가 이기는 이유는 대역폭이 아니라 거래 횟수다.** 고정비용 ≈**150ms/거래**
(`SEND_GAP` 80 + 명령 15 + 프롬프트·`SEND OK` 왕복):
```
1바이트 × 10회 ≈ 1000ms      60바이트 × 1회 ≈ 160ms
```

⚠ **`rxmax=30`(2판)은 쓰지 마라 — 슬롯(1.2초) 기준이라 우리가 원한 값이 아니다.**

## 1.6 🔴 `OFFLINE_MS` 재검토 — **내 판단: 지금은 안 바꾼다. 대신 판정 방식을 바꾼다**

**루트 물음**: 슬롯이 1.2초면 `3500ms` 는 **2.9 슬롯**이다. 반송파가 매 슬롯 반드시 오니
**판정이 예전보다 예리해질 수 있다** — 값이 그대로가 맞나?

### 값은 그대로 둔다 — **지금 줄이면 오탐이 난다**

`3500 / 1200 = 2.92` → **3슬롯 연속 놓쳐야 오프라인.** 지금과 비슷한 자리다(전에는 3.14주기).

🔴 **줄이려면 "정상적인 최악의 슬롯 길이"를 알아야 하는데 그 값이 없다.**
슬롯은 **사건 기반이라 장치가 느려지면 늘어난다** — 배치가 크거나 `SEND OK` 가 지연되면
한 슬롯이 1.2초를 넘는다. **병리 구간에서 `SEND OK` 가 2~5초였다.**
→ **문턱을 2슬롯(2.4초)으로 조이면 그때 멀쩡한 장치를 죽었다고 판정한다.**

⚠ **그리고 지금 값을 바꾸면 새 구조의 효과 측정에 변수가 하나 더 섞인다.**

### 🔑 그런데 **더 나은 판정 방식이 생겼다 — 시간이 아니라 슬롯 수**

**반송파 구조의 새 성질**: 장치가 **슬롯마다 반드시** 프레임을 보낸다.
→ **"N슬롯 연속 결손"으로 세는 것이 벽시계 문턱보다 낫다.**

| | 벽시계(`3500ms`) | **슬롯 수(`N슬롯 결손`)** |
|---|---|---|
| 장치가 느려지면 | 🔴 **오탐** — 슬롯이 늘어난 만큼 문턱을 넘는다 | ✅ **같이 늘어난다. 자기교정된다** |
| 근거 | 주기 추정에 의존 | **장치가 보낸 것을 센다** |

🔑 **§8.19 와 같은 원리다** — **추정하는 설계보다 상대가 알려주는 사건에 거는 설계가 낫다.**
슬롯 자체가 이미 그렇게 자기교정되는데 **오프라인 판정만 벽시계에 남겨 둘 이유가 없다.**

**→ 제안: `OFFLINE_MS` 를 유지한 채(안전망) `N슬롯 결손` 판정을 추가하고, 실측 후 주 판정을 옮긴다.**
⚠ **`N` 은 슬롯 길이 분포를 보고 정한다** — **지금 정하면 추측이다.**
**필요한 자료**: 새 펌웨어의 **슬롯 간격 분포(p99)**. 그게 있어야 "정상적인 최악"이 정해진다.

## 2. 큐

| 항목 | 설계 |
|---|---|
| 순서 | **FIFO.** 예약/취소가 뒤집히면 안 된다 |
| 창당 건수 | 🔴 **arduino 실측값**(0.6초에 몇 건 처리되나). **지금 값을 옮겨 쓰지 마라** |
| 깊이 | **유한.** 아래 |
| 소켓 끊김 | **큐를 비운다.** 세션이 바뀌면 `wire_rid` 도 새로 시작하고, 옛 큐를 그대로 쏘면 **장치가 모르는 rid** 를 받는다 |

### 🔴 넘칠 때 — **"버리지 않는다"와 "무한히 쌓는다"는 다르다**

루트 지시는 *"버리지 말고 미루고 미룬 수를 로그에"* 다. **그대로 하되 깊이는 유한하다:**

- **깊이 안**: 미룬다. **미룬 수를 로그에 남긴다**(조용히 미루면 지연이 안 보인다 · 원장 §5.2)
- **깊이 초과**: 🔴 **조용히 버리지 않고 브라우저에 즉시 거절을 돌려준다.**
  → **`너무 빠릅니다` 류의 명시적 실패.** 사용자가 **"안 눌린 것"을 알게 된다**

⚠ **이게 "버리는 것"이 아닌 이유**: 버리는 것은 **아무도 모르게 사라지는 것**이다.
**거절은 사용자에게 말한다.** 원장 §0 — **측정한 것을 이름으로 삼고 해석은 옆 칸에서 한다.**

~~🔑 그리고 같은 자리 중복 클릭은 `has_pending_for(slot)` 가 이미 걸러서 52회를 눌러도
그 자리는 1건만 진행 중이다.~~

> ### 🔴 **틀렸다 — `has_pending_for` 는 "pending 이 살아 있는 동안"만 막는다** (web 반박)
>
> **화면이 롤백하면 사용자가 다시 누르고, 그때는 새 `rid` 이고 서버 `pending` 도 이미 풀려 있다.**
>
> ```
> 큐 대기 중 → 화면 타임아웃이 먼저 터짐 → 롤백 → 사용자가 다시 누름
> → 새 rid (has_pending_for 가 안 막는다) → **큐에 한 건 더**
> ```
>
> 🔴 **타임아웃이 짧을수록 큐가 더 쌓인다.**
> **내가 막으려던 그 증폭을 화면이 만들어 낸다.**
>
> → **그래서 화면 타임아웃은 "적당히 늘리는" 문제가 아니라 서버 값에 묶여야 한다**(§4-B).

## 3. `S` 가 안 오면 — **상한이 없으면 하행이 영영 안 나간다**

장치가 조용하면(busy·리셋·링크 끊김) **창이 안 열린다.**

```
now - ard_last_ms > D_max  →  창을 포기하고 그냥 쏜다
```

⚠ **`D_max` 를 3.5초(오프라인 판정)보다 작게 둔다.** 그 뒤에 쏘면 **서버가 이미
"장치 없음"으로 판단한 상태**에 쏘는 것이다.
→ **후보: 2주기(약 2.4초).** ⚠ **주기를 상수로 박지 말고 실측 간격을 쓴다**(원장 §8.11).

🔑 **"그냥 쏜다"가 옳은 이유**: 안 쏘면 **하행이 조용히 사라진다.**
**지금은 최소한 나가서 실패라도 한다** — 조용한 소실이 더 나쁘다.

---

## 4. 몰아치기 흡수 — **화면이 같이 바뀌어야 한다** (web 맞춤)

사용자가 **52회**를 눌러도 전선에는 규율대로 나간다. **그러면 지연이 사용자에게 보인다.**

🔴 **화면에 "대기 중"이 없으면 사용자가 다시 누르고 그게 또 쌓인다.**
**사용자가 재현한 것이 정확히 그 모양이다.**

**web 에 필요한 것:**
- **큐에 들어간 상태**를 화면이 표시할 수 있어야 한다 → **서버가 그 상태를 알려줘야 한다**
- 🔴 **그러려면 WS 응답에 "접수됨(큐 대기)"이 필요하다.** 지금은 `ack` 아니면 `error` 뿐이라
  **"받았고 아직 안 보냈다"를 말할 수단이 없다.** ← **이 설계가 요구하는 새 응답이다**

⚠ **이건 web 과 합의해야 하는 계약 변경**이다. 원장 §6: **구/신 동시 수용 → 통보 → 변경.**

### 🔴 4-A. **배포 순서 — 큐와 `queued` 를 갈라 올리면 그 사이가 위험 구간이다** (web 지적)

| 서버 상태 | 화면이 하는 일 |
|---|---|
| 큐 없음(지금) | 5.08초에 서버 실패 응답 → 정상 |
| 🔴 **큐 있음 + `queued` 안 보냄** | 대기가 6초를 넘으면 **화면 자체 타임아웃이 먼저 터져 거짓 롤백** → 재클릭 → **큐에 한 건 더** |
| 큐 있음 + `queued` 보냄 | 타이머가 `expires_ms + 6초` 로 다시 걸림 → 정상 |

**가운데 줄이 §8.20 의 증폭 고리다.** 그리고 🔴 **그 구간은 "옛 화면 호환" 문제가 아니다 —
새 화면도 못 막는다.** 화면이 아무리 준비돼 있어도 **서버가 `queued` 를 안 보내면 알 방법이 없다.**

> ### **규칙: 큐와 `queued` 는 같은 배포에 넣는다. 갈라야 하면 `queued` 를 먼저 올린다.**
> **`queued` 만 먼저 올라오는 것은 안전하다** — 큐가 없으면 그냥 안 보내질 뿐이다.
> **반대 순서만 위험하다.**

🔑 **이것이 원장 §6 의 "구/신 동시 수용" 과 다른 종류의 순서 문제다.**
§6 은 **상대가 모르는 것을 보내지 마라**이고, 이건 **내가 늦추면서 상대에게 안 알리지 마라**다.
**전자는 형식 문제, 후자는 타이밍 문제**다.

### ✅ 4-B. 합의된 계약 (REQ-0155 · web 회신)

```json
{"type":"queued", "rid":"…", "slot":"A1", "ahead":2, "expires_ms":4800, "ack_budget_ms":9900}
```

> ### 🔴 `ack_budget_ms` 는 나중에 붙었다 — **web 이 산술로 구멍을 찾아서다** (REQ-0166)
>
> `expires_ms` 가 **큐 대기까지만** 덮으므로 **이탈 후를 덮는 값이 화면 쪽에만** 남았고,
> 그 값(6000)이 서버 최악(9900)보다 **작았다.** 그러면 화면이 서버보다 먼저 롤백하고
> 사용자가 다시 눌러 **새 rid 로 큐에 한 건 더** — 이 설계가 닫으려던 고리가 그 틈에서 열린다.
>
> **화면이 기다려야 하는 전부 = `expires_ms + ack_budget_ms`.** 두 구간을 서버가 각각 준다.
> 🔑 **서버는 이 값을 리터럴로 쓰지 않고 상수에서 계산한다** — `ACK_TIMEOUT_MS`·`ACK_MAX_TRIES`·
> `D_max` 중 무엇을 바꿔도 따라오므로 **"값이 바뀌면 조용히 틀린다"가 구조적으로 불가능하다.**

| 항목 | 결정 | 🔴 이유 |
|---|---|---|
| **별도 타입** | **필수** | web 의 dispatcher 는 **모르는 타입을 조용히 무시**한다. `ack` 에 필드를 넣으면 **옛 화면이 `type==='ack'` 만 보고 pending 을 지우며 "예약되었습니다"를 띄운다** — **전선에 나가지도 않은 요청을 성공으로 선언**한다 |
| `ahead` | **넣는다** | "대기 중"만으로는 **멈춘 것과 밀린 것**을 못 가른다. `3→2→1` 이 **진행 중이라는 사실**을 보인다 |
| **`expires_ms`** | 🔴 **서버가 준다 · (가) 방식 — 이 프레임을 받은 시점 기준 남은 상한(지속시간)** | 화면이 추측하면 안 된다. 그리고 **절대 시각(epoch)으로 주면 시계 어긋난 만큼 그대로 틀린다** |

### 🔴 `expires_ms` 의 기준점 — **지속시간이다. 절대 시각이 아니다**

```
enqueue 시점에 **마감시각을 고정**한다:   deadline = enqueue_ms + WAIT_CAP_MS   (= 4800ms)
queued 를 낼 때마다:                      expires_ms = deadline − now_ms()
```

> ### 🔴 이 문서가 `cap` 을 **두 가지로** 쓰고 있었다 (web 이 잡았다 · 2026-08-17)
>
> | 이름 | 단위 | 무엇 |
> |---|---|---|
> | **`WAIT_CAP_MS`** (코드: `DOWNQ_WAIT_CAP_MS`) | **ms** · 4800 | 큐 **대기 마감** — `expires_ms` 의 출처 |
> | **`BATCH_CAP_B`** (코드: `DOWN_BATCH_CAP_B`) | **바이트** · 320 | 한 창에 실을 **배치 상한** |
>
> 위 식에 `cap` 이라고만 써 놓고 §1.5·§8 에서는 *"`cap` 은 바이트다 · 채택 320B"* 라고 적었다.
> 🔴 **그래서 `deadline = enqueue + 320` 으로 읽으면 마감이 320ms 가 되는데 그게 그럴싸해서 안 걸린다.**
> **코드는 처음부터 두 이름이 달라 안 섞였다 — 섞인 것은 이 문서다.**
> 🔑 **CLAUDE.md "이름이 아니라 정의를 맞춰라" 가 값이 아니라 문서의 낱말에도 걸린다.**
> (web 은 자기 원장에 이걸 "큐 깊이"로 옮겨 적었다가 정정했다 — **내 문서의 모호함이 남의 원장에
> 틀린 항목을 만들었다.** 그게 이 종류 실수의 실제 비용이다.)

**이 구현이 web 이 요구한 두 성질을 자동으로 만족한다:**
- ✅ **받은 시점 기준 남은 시간** — `now` 로 빼므로 프레임마다 그 순간 기준이다
- ✅ **같은 `rid` 로 여러 번 오면 단조 비증가** — `deadline` 이 고정이라 **`now` 가 커지면 줄기만 한다**

🔑 **`ahead` 로 다시 계산하지 않는 이유**: 그러면 앞이 밀릴 때 값이 **늘 수 있어** 단조성이 깨진다.
**항목마다 마감을 한 번 박고 그것만 빼면 단조성이 공짜로 나온다.**

⚠ **두 시계를 안 섞는다** — 서버는 `now_ms()`(자기 시계)로 **차이만** 계산해 보내고,
화면은 받은 **지속시간**을 자기 시계로 잰다. **어느 쪽도 상대의 시계를 안 읽는다.**
🔑 **web 이 자기 산식(`expires_ms + ACK_TIMEOUT`)에서 두 시계를 섞을 뻔한 것을 스스로 잡았다** —
*"화면은 브라우저 시계, 로그는 서버 시계"* 라고 자기가 적어 두고 그 안에서 밟은 자리다.

⚠ **`cap` 의 값은 `rxmax` 에 종속이다**(창당 처리 건수 → 대기 상한). **의미는 지금 확정,
값은 실측 뒤.** 값이 없다고 계약을 못 정하는 것은 아니다.
| 거절 `code` | **`queue_full` · `already_pending`** | 화면 문구가 **완전히 다르다**(시스템 사정 대 사용자 잘못 아님). 지금은 둘 다 `error` 라 못 가른다 |

🔴 **서버가 지켜야 하는 보장 한 줄:**
> **`queued` 를 보냈으면 그 뒤에 반드시 `ack` 또는 `error` 가 간다.**
> **그 보장이 없으면 화면의 중간 상태가 영구가 된다.**

🔑 **내 §5 마이그레이션 순서(서버 먼저 배포)가 성립하는 것도 별도 타입일 때뿐이다** —
`queued` 를 모르는 화면은 **무시하고 지금처럼 `ack` 만 기다리므로 현재 동작과 같다.**
**필드 방식이었으면 서버 배포가 그 순간 옛 화면을 깨뜨린다.**

⚠ **`ahead` 로 시간을 환산하지 않는다** — 그러려면 `rxmax` 가 필요한데
**그 상수를 화면에 박으면 §4 가 경고한 그것**이 된다. **화면은 "앞에 N건"까지만 말한다.**

## 5. 🔑 `@<rid>` 를 `S` 에 얹는 것이 **이 구조에서 필수가 된다**

**장치 슬롯에 나가는 것이 `S` 하나뿐이라면 ACK 는 거기 실려야 한다.**
별도 `A` 프레임을 보내면 **그것이 장치 슬롯을 또 쓰거나 서버 슬롯을 침범한다.**

→ **`DESIGN-ack-on-status.md` 는 폐기가 아니라 이 설계의 전제다.**
⚠ 다만 **동기가 바뀌었다**: 전에는 *"추가 송신이 수신을 막으니까"*(반이중), 이제는
*"장치 슬롯에 두 개를 넣을 수 없으니까"*(슬롯 구조). **같은 결론, 다른 이유다.**

## 8. 값이 채워졌다 — `cap` (2026-08-17)

```
arduino 4판 실측 : 창당 540B   ← 하드웨어 UART. **상한이지 보장이 아니다**
채택            : 320B
```

**540 을 안 쓴 이유**: `SoftwareSerial` 페널티가 **아직 안 쟀고**, 그보다 먼저
**도메인이 상한을 준다 — 자리가 10개뿐이라 최악 버스트가 `10 × 28B` = 280B 다.**
`320` = 280 + 여유 · 실측의 59%. **넘치면 버리는 게 아니라 미루므로 보수적으로 잡는 비용이 낮다.**
🔑 실측의 진짜 값은 540 이 아니라 **"프레임 크기를 3.4배 바꿨을 때 건수는 9~32 로 갈렸고
바이트는 ±1% 였다"** — §1.5 의 "바이트가 불변량"이 **주장에서 관측으로 바뀌었다.**
→ 실기 재측정이 오면 **`--down-cap=<B>`** 로 갈아끼운다(재빌드가 필요하면 "나중에"가 된다).
