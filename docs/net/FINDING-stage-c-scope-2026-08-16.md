## 4. 빠진 것 (D) — 🔴 배포 위험의 성격이 바뀌었다

handoff (G)는 **"소스가 dirty 라 앞서 있다"** 로 적혀 있다. **지금은 아니다:**

```
워킹트리 = HEAD(68abc6e) 와 동일 (조별과제샘플/ 변경 0건)
도는 것  = pid 75781 · build=337c926-dirty · 17:53:07 기동
```

즉 **동결 대상 변경이 전부 깨끗하게 커밋된 상태**다. 이제 누가 `git pull` 후 평범하게

"이거 뭔가 이상한데"가 보였는데 지금은 **안 보인다.** LEDGER §6.1 의 파생 위험 그대로다.

→ A 창(~21:53) 종료 전까지 **재빌드·배포를 담당(나)을 거치게** 해 달라.

## 5. 루트 질문 3개에 대한 답

### Q1. 하행(DeviceCommand)을 이번 범위에 넣기로 했었나, 단계 D 로 미뤘나

**둘 다 아니다. REQ-0096 에 `단계 D` 는 정의된 적이 없다.**

⚠ **질문이 두 단계 체계를 섞고 있다.** 이름이 같고 정의가 다른 전형적인 자리다:

| 체계 | A · B · C · D 의 뜻 |
|---|---|
| **REQ-0096 리팩터링** | A=`server_device.h` 추출 · B=`server_seam.h` 계약 · C=이음매 넘는 호출 이벤트화. **D 없음** |
| **`plan-windows-and-mapping.md` §5.7** | 매핑 이행 단계(A=매핑 로더 … D=와이어에서 `reserved` 제거). **리팩터링과 무관** |

하행이 단계 C 밖이라는 것은 **계약서 본문이 뒷받침한다**(추정이 아니다):
`server_seam.h:82` — *"REQ-0096 은 경계만 만들고 매핑은 안 건드린다"*, 그리고
`CMD_RESERVE`/`CMD_CANCEL` 의 과도기가 끝나는 시점을 **매핑 §5.7 의 B 단계**로 못 박아 뒀다.

→ **권고**: 하행 이관은 별도 단계로 **새로 정의**해야 한다(암묵적 "D" 로 부르지 말 것 —
매핑 D 와 충돌한다). 지금 하지 말자는 이유는 §2 와 같다: 하행을 이관하면
`dispatch()`·재전송·ACK 대기가 전부 딸려 온다.

### Q2. `server_wire.h` 미include 는 의도인가, 미완인가

**"의도"라고 적힌 문서는 없다**(추정하지 않는다). 다만 **지금 include 하면 죽은 코드가 된다**는
것은 확정이다:

- `server_wire.h` 는 **§2.4-W 하행 프레임 전용** 정의다(파일 머리말).
- 서버는 **W 를 한 번도 보내지 않는다** — `CMD_WRITE` 사용 0건(검증함).
- 지금 칩(`조별과제샘플/client.ino`)은 **`R`·`C`·`T`·`M` 만 받고 `W` 는 버린다**
  (LEDGER §3.2, `client.ino:1514`). include 해도 **동작이 생기지 않는다.**

→ **미완이 아니라 "쓸 곳이 아직 없다"** 가 정확하다. 하행 이관 단계가 정의될 때 같이 들어온다.
⚠ 다만 이 파일은 **장치와 공유될 것을 전제로 쓰였다**(`wire=N` 배너 대조 규약). 그 규약은
지금 **아무도 안 지키고 있다** — 서버가 자기 `WIRE_VERSION` 을 기동 로그에 안 찍는다. 확인함.

### Q3. 단계 C 를 "끝났다"고 말하려면 남은 것이 정확히 무엇인가

**이벤트 6종 중 3종이 남았다** — 루트 목록과 일치한다. 구체적으로:

1. **`DEV_CONNECT`** — 932행 `adopt_as_parking()` (작다. `reason` 에 `"새 연결"` 실으면 끝)
2. **`DEV_SENSORS`** — `on_ard_line()` S 분기 (1598 · 1637-1642 · 1644-1645). **가장 크다**
3. **`DEV_ACK`** — `on_ard_line()` A 분기 (1678-1679)

**+ 루트가 정해야 할 것 하나**: `on_plate()` 1992 를 단계 C 에 넣나 빼나(§2 끝).

✅ **자료구조는 막힌 것이 없다.** `DeviceEvent` 는 `sensors`·`tmask`·`uptime_s`·`seq`·`reboot`·
`rid`·`result`·`reason[40]` 을 이미 갖고 있어 **세 종류 전부 필드 추가 없이 실린다**(계약 확인함).
`emit_dev()` 도 `reason` 잘림 처리까지 돼 있다.

### 🔴 그러나 `DEV_CONNECT` 는 "작은 것"이 아니다 — **순서 위험이 있다**(새로 찾음)

복구 표는 932행을 항목 1(가장 단순)로 적어 뒀고 나도 처음에 그렇게 읽었다. **틀렸다.**
앞서 끝낸 3종과 달리 이 자리는 **전선으로 프레임을 내보낸다:**

```
resync_reservations()  →  dispatch('R', …)  ×  살아 있는 예약 수   (server.cpp:1512-1513)
```

**같은 틱 안의 실행 순서가 이렇다**(직접 따라가 확인함):

```
2315  promote_unknown() → adopt_as_parking() → resync_reservations("새 연결")   ← R 송신
2316  drain_ard_buf()   → on_ard_line(첫 S 프레임)  ← 은퇴 기준선 · 불일치 검사 · C 재하달
 …
2481  drain_dev_events()                                                        ← 여기로 옮기면?
```

→ 이벤트로 옮기면 **R 재하달이 첫 S 프레임 처리 뒤로 밀린다.** 순서가 뒤집힌다.

관련 상호작용 둘을 확인했다:
- 1638행 불일치 검사의 `!has_pending_for(SLOT_ID[i])` 가드는 **resync 가 만든 pending 을 본다.**
  순서가 바뀌면 이 가드가 보는 상태가 달라진다.
- 931행 `base_valid = false`(§7.5-1) 직후 첫 프레임이 은퇴 기준선을 세운다 — 그 사이에
  R 이 나가느냐 마느냐가 바뀐다.

⚠ **"그래서 깨진다"고 말하지 않는다** — 코드만 읽고 단정하지 않는다(LEDGER §6).
확인한 것은 **순서가 바뀐다는 사실**이고, 단계 C 의 계약은 `server.cpp:1235` · `2480` 에
**"구조만 바꾸고 동작은 안 바꾼다"** 라고 두 번 못 박혀 있다. 순서 변경은 그 계약에 걸린다.

**선택지 셋** — 루트가 정할 일이다:
1. `drain_dev_events()` 를 **승격 직후에도 한 번** 부른다(같은 자리 유지). 계약을 지키지만
   소비 지점이 둘이 된다.
2. `DEV_CONNECT` 만 **동기 소비**로 둔다(이벤트는 내되 그 자리에서 drain).
3. **단계 C 에서 빼고** 하행 이관 단계로 넘긴다 — 어차피 `dispatch()` 가 하행이다.

→ 나는 **3번을 권한다.** `resync_reservations` 는 이름과 달리 **하행 송신기**이고,
`DEV_SENSORS`(1598행)도 같은 함수를 부른다. 둘을 따로 옮기면 같은 문제를 두 번 푼다.

**검증 방법(아직 안 했다)**: `net/fake_arduino.py` 로 시험 인스턴스에 붙여
"예약 살아 있는 상태에서 재접속" 을 재현하고 R/C 송신 순서를 옮기기 전후로 대조한다.
운영 포트가 아니라 `--port-offset` 시험 인스턴스로 한다.
