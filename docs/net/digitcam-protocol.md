> **계약 개정 2 반영 (2026-08-13)** — 인식 대상이 **한국 자동차 번호판**으로 확정됐다.
> `value` 가 ASCII 숫자에서 **한글이 섞인 UTF-8 문자열**(`123가4568`)로 바뀌었고,

계약에 영향을 주지 않는다.

- 계약 원본: `docs/digitcam-contract.md` §7 (전송), §6 (설정 키), §5.1 (`fresh` 트리거)

## 1. 한눈에

| 항목 | 값 |
|---|---|
| 트랜스포트 | TCP (IPv4), 평문 |
| 역할 | **앱이 클라이언트, 노트북/서버가 리스너.** 서버는 접속하지 않는다 |
| 방향 | **단방향** 앱 → 서버 |
| 인코딩 | UTF-8, **BOM 없음** |
| 프레이밍 | **줄 단위. 종단자는 LF(`0x0A`) 하나** |
| 응답 | **없음(fire-and-forget).** 서버는 아무것도 보내지 않아도 된다 |
| 포맷 | `server.format=json` \| `plain` (설정 키는 계약 §6) |
| 포트 | `server.port`, 기본 `5500`. 고정값 아님 (계약 §6) |
| 주소 | `server.host`. **미정** — 이 문서는 어떤 IP 도 가정하지 않는다 |

## 2. 연결 모델

### 2.1 수립

1. 서버가 `server.port` 에서 `listen` 한다.
2. 앱이 `server.host:server.port` 로 `connect` 한다.
   - 연결 타임아웃: `socket.connect_timeout_ms` (기본 3000)
   - `socket.keepalive=true` 면 `SO_KEEPALIVE` 를 켠다
3. **핸드셰이크가 없다.** 연결이 서면 즉시 데이터 줄을 보낼 수 있다.
   서버는 헬로·버전·인증 어느 것도 기대하지 않는다.
4. `server.host` 가 비어 있으면 앱은 접속을 시도하지 않고 화면에 "서버 미설정"을 표시한다(계약 §6).

접속만 하고 한 줄도 보내지 않는 연결은 **정상이다.** 번호판을 못 읽으면 보낼 것이 없다.
서버는 조용한 연결을 오류로 취급하지 말아야 한다.

### 2.2 해제

- 어느 쪽이든 언제든 닫을 수 있다. 종료 메시지(`BYE` 같은 것)는 없다.
- 앱이 `close` 하면 서버는 `recv() == 0`(EOF)을 본다.
- 앱이 half-close(`shutdown(SHUT_WR)`)를 하더라도 서버가 할 일은 같다 — EOF 로 보고 정리한다.
  서버는 되돌려 보낼 데이터가 없으므로 half-close 를 특별 취급할 이유가 없다.
- **EOF 시점에 버퍼에 LF 로 끝나지 않은 잔여 바이트가 있으면 그것은 완성된 줄이 아니다.**
  서버는 그것을 온전한 값으로 처리해서는 안 되고, 조용히 버려서도 안 된다(§8.4).

### 2.3 재접속

- 연결이 끊기거나 접속에 실패하면 앱은 `reconnect.interval_ms`(기본 3000) 간격으로 재시도한다.
- 재시도 중에도 카메라·인식은 계속 돈다.
- **끊긴 동안 발생한 값은 버린다. 재전송 큐는 없다.**
  이유: 최신값만 의미가 있는 용도이고, 큐가 있으면 재접속 순간에 낡은 값이 한꺼번에 쏟아져
  서버가 "지금 보이는 번호판"을 잘못 알게 된다. 값 손실은 버그가 아니라 **설계된 동작**이다.
- 서버를 껐다 켜도 앱이 다시 붙는다. 서버는 재기동이 빈번하다고 가정하고 만들어야 한다
  → `SO_REUSEADDR` 필수(§9).

### 2.4 서버가 응답하지 않아도 되는 이유

REQ-0004 가 명시적으로 요구한 항목이므로 근거를 남긴다.

1. **응답할 내용이 없다.** 서버는 값을 받아 보여 주는 싱크다. 앱이 서버의 판단을 기다려
   행동을 바꾸는 지점이 하나도 없다.
2. **ACK 는 안전을 주지 못한다.** 애플리케이션 ACK 가 보장하는 것은 "서버가 받았다"인데,
   이 프로토콜은 못 받은 값을 **재전송하지 않기로** 이미 정했다(§2.3). 재전송하지 않을 정보를
   위해 왕복을 도입하면 지연만 늘고 얻는 것이 없다.
3. **ACK 는 앱을 느리게 만든다.** 응답을 기다리면 전송 스레드가 블로킹되고, 그 지연이 프리뷰
   프레임률로 새어 나온다(계약 §7: 전송은 카메라 스레드에서 하지 않는다).
4. **테스트 서버를 누구나 만들 수 있다.** 응답 규약이 없으면 `nc -l 5500` 한 줄로도 수신이 된다.
   실제 서버를 만드는 쪽의 진입 비용이 사실상 0 이다.
5. TCP 자체가 재전송·순서보장·흐름제어를 이미 한다. 애플리케이션 ACK 가 추가로 잡아 주는 것은
   "서버 프로세스가 살아서 읽었다"뿐인데, 그건 연결이 끊기면 어차피 드러난다.

**그래도 서버가 무언가 보낸다면?** 앱은 **읽더라도 무시한다**(계약 §7).
서버는 보내지 않는 것을 권한다 — 보낸 바이트는 앱의 수신 버퍼에 쌓이기만 한다.

## 3. 프레이밍 — 바이트 수준

> **TCP 는 스트림이지 메시지가 아니다.** 앱이 `write()` 를 한 번 했다고 서버가 `recv()` 한 번에
> 같은 덩어리를 받는다는 보장은 없다. 그래서 메시지 경계를 프로토콜이 직접 정의한다.

### 3.1 규칙

1. 한 메시지 = **한 줄**. 줄의 끝은 **LF 한 바이트(`0x0A`)** 다.
2. 줄의 본문은 **UTF-8** 로 인코딩한다. **BOM(`EF BB BF`)을 붙이지 않는다.**
3. 본문 안에 **LF(`0x0A`)가 나타나서는 안 된다.** 이것이 프레이밍의 유일한 불변식이다.
   - `json` 포맷: JSON 문자열 안의 개행은 RFC 8259 에 따라 `\n`(역슬래시 + n, 2바이트 `5C 6E`)로
     이스케이프된다. 자유 텍스트가 들어가는 필드는 `device` 하나뿐이므로 위험 지점은 거기다.
   - `plain` 포맷: 본문이 번호판 문자열이라 개행이 들어갈 여지가 없다.
   - **한글이 들어가도 LF 프레이밍은 안전하다.** UTF-8 멀티바이트 문자를 이루는 바이트는
     선두 바이트가 `C0`–`F4`, 이어지는 바이트가 `80`–`BF` 라 **어느 것도 `0x0A` 가 될 수 없다.**
     즉 한글 한복판에서 LF 로 오인될 바이트가 나오지 않는다. 이것이 UTF-8 의 자기동기화
     성질이고, 줄 단위 프레이밍을 한글 페이로드에 그대로 쓸 수 있는 이유다.
4. **CR(`0x0D`)은 보내지 않는다.** 종단은 CRLF 가 아니라 LF 다.
   (서버는 관용적으로 끝의 CR 하나를 벗겨도 된다 — §8.5. 그건 수신 측 관용이지 송신 규약이 아니다.)
5. 마지막 줄에도 LF 를 붙인다. **LF 없이 끝나는 조각은 메시지가 아니다.**
6. 줄 하나의 길이 상한은 프로토콜이 정하지 않는다. 실제 프레임은 100바이트 안쪽이다.
   서버는 방어적으로 상한을 두는 것을 권한다(§9).
7. 여러 줄을 한 번의 `write` 로 이어 보내도 되고, 한 줄이 여러 `write` 로 쪼개져도 된다.
   **어느 쪽이든 수신 결과는 같아야 한다.** 이것이 §8 의 요구사항이다.

### 3.2 이 프레이밍을 고른 이유 (길이 프리픽스가 아니라)

계약 §7 이 확정한 사항이다. 근거만 기록한다: 페이로드가 사람이 읽을 수 있는 텍스트고,
`nc`·`telnet`·`socat` 같은 범용 도구로 곧바로 눈으로 확인할 수 있다는 점이 이 단계에서 가장 크다.
길이 프리픽스는 바이너리/대용량 프레임에서 유리하지만 그런 요구가 없다.
**바꾸려면 루트에게 요청한다.**

## 4. 페이로드 — `server.format=json`

### 4.1 형태

한 줄에 **JSON 오브젝트 하나**. 배열도, 여러 오브젝트도, 줄바꿈 들여쓰기(pretty print)도 아니다.

```json
{"ts":1755080000000,"value":"123가4568","conf":0.82,"format":"new","seq":12,"device":"SM-S911N"}
```

### 4.2 필드

| 키 | JSON 형 | 범위·형식 | 의미 |
|---|---|---|---|
| `ts` | number (정수) | 부호 있는 64비트에 들어가는 양의 정수 | **ms 단위 epoch**. 앱을 실행 중인 기기의 시계 |
| `value` | string | **번호판 문자열. 한글을 포함한 UTF-8** (예: `123가4568`) | 왼→오로 읽은 번호판 전체 |
| `conf` | number | `0.0` ~ `1.0` | 문자별 신뢰도의 **최소값**(가장 약한 고리) |
| `format` | string | `new` (숫자3+한글1+숫자4 · 8자) \| `old` (숫자2+한글1+숫자4 · 7자) | 번호판 규격 |
| `seq` | number (정수) | `1` 부터 1씩 증가 | **앱 실행 후** 전송 일련번호 |
| `device` | string | 자유 텍스트(UTF-8) | 기기 식별 문자열(예: `SM-S911N`) |

- **여섯 키는 항상 존재한다.** 값이 없다고 키를 빼지 않는다. (개정 1 은 5개였다 — `format` 이 늘었다.)
- 키 순서는 위 표의 순서를 권장하지만 **JSON 에서 순서는 의미가 없다.**
  서버는 순서에 의존해 파싱하면 안 된다(문자열 자르기 금지, JSON 파서를 써라).
  `value` 에 한글이 들어간 뒤로 이건 더 중요해졌다 — **바이트 오프셋으로 자르는 파서는 반드시 깨진다.**
- **서버는 모르는 키를 만나면 무시하고 나머지를 처리한다.** 나중에 키가 늘어도 서버가 죽지 않게 한다.
  (실제로 개정 2 에서 늘었다. 개정 1 기준으로 만든 서버가 살아남는 이유가 이 규칙이다.)
- `format` 의 **와이어 값은 `new` \| `old` 뿐이다**(계약 §7). 네이티브 내부 JSON 에는 `unknown` 도
  있지만, 구조가 안 맞으면 애초에 값이 비고 빈 값은 전송되지 않으므로 와이어에 오지 않는다.
  그래도 **수신 측은 그 밖의 값이 와도 죽지 않아야 한다** — 방어일 뿐 계약 변경이 아니다.

### 4.3 한글 인코딩 — 두 가지 표기가 다 온다 (개정 2 핵심)

계약 §7 이 못 박은 사항이다. **송신 측은 둘 중 무엇을 써도 되고, 수신 측은 둘 다 복원해야 한다.**

| 표기 | `value` 부분 바이트 | 비고 |
|---|---|---|
| 원문 UTF-8 | `31 32 33 EA B0 80 34 35 36 38` | 안드로이드 `org.json` 의 기본 동작 |
| `\uXXXX` 이스케이프 | `31 32 33 5C 75 61 63 30 30 34 35 36 38` | `가` → `가` (ASCII 6바이트) |

- **JSON 파서를 쓰면 둘 다 저절로 해결된다.** `\uXXXX` 는 JSON 문자열 문법의 일부라
  어느 언어의 표준 파서든 알아서 되돌린다. **직접 자르고 이어붙이는 파서만 이 문제를 만난다.**
- 로그에 원문 줄을 그대로 찍는 도구(참조 서버 포함)는 이스케이프된 줄을 `123가4568` 로
  보여 준다. 이건 **깨진 게 아니다.** 사람이 오해하지 않도록 참조 서버는 복원값을 덧붙여 준다(§10.7).
- **이 자유는 `json` 모드에만 있다.** `plain` 은 JSON 문자열 문맥이 아니므로 언제나 원문 UTF-8 이다(§5).

### 4.4 값 해석에서 서버가 조심할 것

- **`ts` 는 폰의 시계다.** NTP 로 맞춰져 있다는 보장이 없고 노트북 시계와 다를 수 있다.
  이벤트 순서를 정할 때는 `ts` 보다 **도착 순서**와 `seq` 를 믿어라. `ts` 는 표시·기록용이다.
- **`seq` 는 앱을 재시작하면 1 로 돌아간다.** 연결을 가로질러 단조증가한다고 가정하지 마라.
  같은 연결 안에서만 단조증가다. `seq` 가 뒤로 갔다 = 앱이 재시작했다는 신호로 읽는 게 맞다.
- **`seq` 에 구멍이 있는 것은 정상이다.** 끊긴 동안 값이 버려지기 때문이다(§2.3).
  구멍을 손실 오류로 처리하지 마라.
- `conf` 는 최소값이므로 문자 수가 늘수록 낮아지는 경향이 있다. 절대 임계로 비교할 때 감안한다.
- `value` 는 **문자열이다.** 앞자리 0 이 의미를 갖고(`012가3456`), 무엇보다 **한글이 들어 있어
  정수 변환이 애초에 불가능하다.** 문자열로 받아 문자열로 보관한다.
- **바이트 수 ≠ 문자 수.** 한글 한 글자가 UTF-8 로 3바이트다.

  | 규격 | 예 | 문자 수 | **바이트 수** |
  |---|---|---|---|
  | `new` | `123가4568` | 8 | **10** |
  | `old` | `12가3456` | 7 | **9** |

  고정폭 필드에 넣거나 `char[8]` 로 받는 코드는 여기서 깨진다. 위 값은 **참고**이지
  서버가 강제해야 하는 검증 규칙이 아니다 — 길이로 거르면 규격이 늘 때 되돌리기 어렵다.

### 4.5 정확한 바이트 — 같은 메시지, 두 표기

**(가) 원문 UTF-8 · 98바이트**

```
{"ts":1755080000000,"value":"123가4568","conf":0.82,"format":"new","seq":12,"device":"SM-S911N"}\n
```

```
0000  7B 22 74 73 22 3A 31 37 35 35 30 38 30 30 30 30  |{"ts":1755080000|
0010  30 30 30 2C 22 76 61 6C 75 65 22 3A 22 31 32 33  |000,"value":"123|
0020  EA B0 80 34 35 36 38 22 2C 22 63 6F 6E 66 22 3A  |...4568","conf":|
0030  30 2E 38 32 2C 22 66 6F 72 6D 61 74 22 3A 22 6E  |0.82,"format":"n|
0040  65 77 22 2C 22 73 65 71 22 3A 31 32 2C 22 64 65  |ew","seq":12,"de|
0050  76 69 63 65 22 3A 22 53 4D 2D 53 39 31 31 4E 22  |vice":"SM-S911N"|
0060  7D 0A                                            |}.|
```

`0020` 행의 `EA B0 80` 이 `가` 한 글자다. ASCII 로는 안 보이므로 `...` 로 찍힌다 — 정상이다.

**(나) `\uXXXX` 이스케이프 · 101바이트 — 논리적으로 (가)와 같은 메시지다**

```
{"ts":1755080000000,"value":"123가4568","conf":0.82,"format":"new","seq":12,"device":"SM-S911N"}\n
```

```
0000  7B 22 74 73 22 3A 31 37 35 35 30 38 30 30 30 30  |{"ts":1755080000|
0010  30 30 30 2C 22 76 61 6C 75 65 22 3A 22 31 32 33  |000,"value":"123|
0020  5C 75 61 63 30 30 34 35 36 38 22 2C 22 63 6F 6E  |가4568","con|
0030  66 22 3A 30 2E 38 32 2C 22 66 6F 72 6D 61 74 22  |f":0.82,"format"|
0040  3A 22 6E 65 77 22 2C 22 73 65 71 22 3A 31 32 2C  |:"new","seq":12,|
0050  22 64 65 76 69 63 65 22 3A 22 53 4D 2D 53 39 31  |"device":"SM-S91|
0060  31 4E 22 7D 0A                                   |1N"}.|
```

3바이트(`EA B0 80`)가 ASCII 6바이트(`5C 75 61 63 30 30`)로 바뀌어 프레임이 3바이트 길어졌다.
**두 프레임 모두 유효하고 수신 결과는 같아야 한다.** 어느 쪽이 올지 가정하지 마라.

두 경우 다 마지막 바이트가 `0A` 이고 그 앞이 `7D`(`}`)다. `0D`(CR)는 없다.

## 5. 페이로드 — `server.format=plain`

### 5.1 형태

`value` 문자열 **그대로** + LF. 따옴표도, 접두어도, 단위도 없다.

```
123가4568\n          (신형 new · 11바이트)
12가3456\n           (구형 old · 10바이트)
```

```
0000  31 32 33 EA B0 80 34 35 36 38 0A                 |123...4568.|
0000  31 32 EA B0 80 33 34 35 36 0A                    |12...3456.|
```

- 메타데이터(`ts`/`conf`/`format`/`seq`/`device`)는 **전부 빠진다.** `plain` 은 `nc -l` 로 눈으로
  보거나 기존 장비에 그대로 물릴 때 쓰는 최소 포맷이다.
  신뢰도·순서·규격을 알아야 한다면 `json` 을 쓴다.
- **`plain` 에는 `\uXXXX` 이스케이프가 없다.** JSON 문자열 문맥이 아니기 때문이다.
  언제나 원문 UTF-8 그대로다. plain 줄에 대고 이스케이프 해제기를 돌리지 마라 —
  번호판에 `\u` 가 나올 일은 없지만, 그런 처리를 넣는 순간 규격만 복잡해진다.
- `new` 인지 `old` 인지는 **문자 수로 구분할 수밖에 없다**(8자 vs 7자). 그게 곤란하면 `json` 을 쓴다.

### 5.2 빈 줄 — 송신은 안 보내고, 수신은 그래도 견딘다

**송신 측**: 빈 줄은 나오지 않는다. 계약 §5.1 이 닫았다 —
`value==""` 인 프레임은 `stable=false, fresh=false` 라 안정화 자체가 되지 않고,
전송 조건이 `fresh == true && value.isNotEmpty()` 다.
**즉 `plain` 모드에서 LF 하나뿐인 줄은 프로토콜상 나올 수 없다.**

**수신 측**: 그래도 견딘다. 규약이 그렇다고 서버가 죽어도 되는 것은 아니다.
빈 줄을 받으면 무시하거나 "빈 값"으로 기록하되, 예외를 던지고 연결을 끊지는 않는다.
빈 줄이 실제로 보인다면 그건 **송신 측 버그의 신호**이므로 로그에는 남기는 편이 낫다.

### 5.3 수신 측 주의

- **정수 파싱을 강제하지 마라.** 한글이 들어 있어 애초에 정수로 바뀌지 않는다. 문자열로 다룬다.
- 문자 수(7/8)로 규격을 판정하되, 어긋난다고 버리지는 마라 — 로그에 남기고 값은 보존한다.
  규격은 나중에 늘어날 수 있다(계약 §1: 지역명 2단·영업용판은 이번 범위 밖이라고만 되어 있다).

## 6. 언제 보내는가 (참조)

이 문서는 전송 **타이밍**을 새로 정하지 않는다. 계약이 이미 정했다:

- 트리거는 C++ 가 만드는 **상승 엣지** `fresh` 다 — 계약 §5.1.
  전송 조건은 `fresh == true && value.isNotEmpty()` 이므로 **빈 값은 나가지 않는다**(§5.2).
- `send.mode` = `on_fresh`(기본) | `every_stable_frame` — 계약 §6.
- `send.min_interval_ms`(기본 1000)는 `on_fresh` 에서도 지키는 하한 — 계약 §6.

**서버 입장에서 알아야 할 것은 하나뿐이다: 줄은 불규칙한 간격으로 온다.**
한동안 아무것도 안 오다가 갑자기 올 수 있고, 최소 간격 이상은 벌어져 있다.
타임아웃으로 연결을 끊는 서버는 만들지 마라 — 조용한 연결이 정상이다.
개정 2 에서 움직임·선명도 게이트가 들어가 **조용한 구간이 더 길어졌다**(차가 움직이는 동안은
인식 자체를 건너뛴다). 몇 분씩 아무것도 안 와도 이상이 아니다.

## 7. 오류·엣지 케이스 — 누가 무엇을 하는가

| 상황 | 앱(송신) | 서버(수신) |
|---|---|---|
| 서버가 안 떠 있음 | `reconnect.interval_ms` 로 재시도, 화면에 "끊김(재시도 n)" | — |
| 전송 중 연결 끊김 | 그 값은 버리고 재접속 | EOF 또는 RST 로 감지, 버퍼 잔여 처리(§8.4) |
| 서버 재기동 | 재접속 | `SO_REUSEADDR` 로 즉시 재바인드(§9) |
| 서버가 읽지 않고 방치 | TCP 흐름제어로 send 버퍼가 참 → 전송 스레드가 막힘. **카메라 스레드가 아니어야 하는 이유**(계약 §7) | 읽어라. 안 읽으면 앱을 막는다 |
| 서버가 데이터를 보냄 | 읽더라도 무시 | 보내지 않는 것을 권함 |
| 이미 닫힌 소켓에 write | 예외(Java `IOException`) 또는 `SIGPIPE`/`EPIPE`(네이티브). 재접속 경로로 | — |
| LF 없는 조각으로 끝남 | 정상 종료면 발생하지 않아야 함 | 완성 줄로 처리 금지, 조용히 버리지도 말 것(§8.4) |
| 깨진 UTF-8 | 발생하지 않아야 함 | 줄 단위로 자른 **뒤** 디코딩, 실패 시 대체문자 + 로그 |
| 줄이 비정상적으로 김 | — | 상한 초과 시 연결을 끊는다(§9) |

`SIGPIPE` 주의: JVM 은 `SIGPIPE` 를 자체 처리해 `IOException` 으로 바꾸므로 Kotlin 쪽은 문제되지
않는다. 나중에 이 프로토콜을 **C/C++ 로 구현**하는 쪽(임베디드 이식)은 `SIGPIPE` 를 무시하도록
설정하거나 `MSG_NOSIGNAL` 을 써야 프로세스가 죽지 않는다.

## 8. 수신 구현 — 부분 수신 처리 (여기가 서버의 본체다)

> 이 절만 제대로 하면 나머지는 거저다. **틀리면 앱이 억울하게 의심받는다.**

### 8.1 실제로 일어나는 일

```
앱이 보낸 것                     서버 recv 가 보는 것 (전부 정상)
─────────────────────────────    ─────────────────────────────────────────────────
"123가4568\n" "12가3456\n"  →    b'123\xea\xb0\x804568\n12\xea\xb0\x803456\n'
                                                            (붙어서 한 번에)
"123가4568\n"               →    b'123\xea'  그리고  b'\xb0\x804568\n'
                                                            (한글 한복판에서 쪼개짐 ⚠)
"123가4568\n" "12가3456\n"  →    b'123\xea\xb0\x804568\n12'  그리고  b'\xea\xb0\x803456\n'
                                                            (경계가 줄 중간)
```

두 번째 경우가 개정 2 에서 새로 위험해진 지점이다. `가` 는 `EA B0 80` 세 바이트인데
그 **한복판에서 recv 가 갈릴 수 있다.** 아래 알고리즘은 이 경우를 자동으로 처리한다 —
바이트로 모으고, LF 로 자르고, **그 다음에** 디코딩하기 때문이다(§8.3).

`recv()` 한 번 = 메시지 한 개가 **아니다.** `recv().split('\n')` 으로 끝내면 위 세 경우 모두 틀린다.

### 8.2 올바른 알고리즘

```
연결마다(!) 빈 바이트 버퍼 buf 를 하나 둔다      ← 전역 버퍼를 쓰면 클라이언트끼리 섞인다
반복:
    chunk = recv(4096)
    if chunk 가 비었으면:        # EOF
        잔여 처리(§8.4) 후 종료
    buf += chunk
    반복:                        # 한 chunk 에 줄이 여러 개일 수 있으므로 while, if 가 아니다
        i = buf 에서 첫 0x0A 의 위치
        if 없으면: break         # 아직 줄이 완성되지 않았다 — 더 기다린다
        line_bytes = buf[:i]     # LF 는 제외
        buf = buf[i+1:]          # LF 까지 잘라낸다
        끝에 0x0D 가 있으면 하나 벗긴다        # CRLF 관용 (§8.5)
        text = UTF-8 디코딩(line_bytes)        # ← 반드시 자른 뒤에 디코딩
        한 줄 처리(text)
    if len(buf) > 상한: 비정상 → 연결 종료 (§9)
```

참조 구현은 `net/test_server.py` 의 `handle()` 이다.

### 8.3 디코딩은 자른 뒤에 (개정 2 에서 가장 중요해진 항목)

한글은 UTF-8 에서 3바이트다. 그 바이트열이 `recv` 경계에서 갈릴 수 있다.
**`recv()` 결과를 바로 `decode()` 하면 그 순간 예외가 나거나 문자가 깨진다.**
바이트 버퍼에 모아 LF 로 자른 **뒤에** 디코딩해야 한다.

개정 1 에서는 페이로드가 거의 ASCII 라 이 실수가 잘 드러나지 않았다.
**개정 2 에서는 모든 번호판 값에 한글이 들어가므로 반드시 드러난다.**
그리고 증상이 "서버가 이상하다"가 아니라 **"앱이 한글을 깨서 보낸다"**로 보인다 —
엉뚱한 쪽을 뜯어보게 만드는 종류의 버그다.

바이트 대신 문자열로 버퍼링하는 구현(`buf += recv().decode()`)이 정확히 이 함정이다.
**버퍼는 바이트여야 한다.**

참조 서버는 `가`(`EA B0 80`)를 `EA` / `B0 80` 으로 갈라 보낸 입력을 정확히 복원하는 것을
확인했다(§10.6). 새 서버를 만들면 같은 시험을 해라 — 이 시험을 통과하지 못하는 수신기는
실기기에서 반드시 실패한다.

### 8.4 EOF 시점의 잔여 바이트

버퍼에 LF 로 끝나지 않은 바이트가 남은 채 EOF 가 오면:

- **완성된 줄로 처리하면 안 된다.** 잘린 JSON 이나 잘린 번호판을 유효한 값으로 받아들이는 셈이다.
  (`123가45` 는 그럴듯해 보이지만 잘린 값이다. 그럴듯해서 더 위험하다.)
- **조용히 버려도 안 된다.** "앱이 보냈는데 서버에 안 찍혔다" 의 가장 흔한 원인이 바로 이것이고,
  그때 의심받는 건 서버가 아니라 앱이다. 잔여가 있었다는 사실을 **반드시 출력한다.**

참조 서버는 이렇게 찍는다:

```
21:11:24.637  ! 127.0.0.1:54110  미종단 잔여 15 바이트(LF 없음): MISSING-LF-TAIL
```

### 8.5 관용 규칙 (수신 측 재량 — 송신 계약이 아니다)

- 줄 끝의 CR 하나는 벗긴다. `telnet`·`printf '...\r\n'` 로 손시험할 때 값이 더러워지지 않는다.
- 빈 줄(LF 단독)은 버리거나 빈 값으로 기록한다. 죽지 않는다.
- 모르는 JSON 키는 무시한다.
- 파싱 실패한 줄은 버리되 원문을 로그에 남긴다.

## 9. 서버 구현 체크리스트

이 명세만 보고 새 서버를 만드는 사람을 위한 목록이다.

- [ ] `SO_REUSEADDR` 를 `bind` **전에** 설정한다. 없으면 `TIME_WAIT` 때문에 재기동이
      `EADDRINUSE` 로 막힌다. 껐다 켜는 시험이 이 프로젝트의 완료 기준에 들어 있다.
- [ ] `0.0.0.0` 에 바인드한다. `127.0.0.1` 은 **같은 기기에서만** 닿는다 — 폰에서 못 붙는다.
- [ ] 연결마다 스레드(또는 select/asyncio) — 동시 접속을 허용한다. 앱이 재접속하는 동안
      옛 연결이 아직 정리되지 않아 잠깐 둘이 겹칠 수 있다.
- [ ] 버퍼는 **연결마다** 따로. 전역 버퍼 금지.
- [ ] **버퍼는 바이트다.** LF 로 자른 **뒤에** UTF-8 디코딩(§8.3). 한글이 recv 경계에서 갈린다.
- [ ] **JSON 파서를 써라.** 문자열 자르기·바이트 오프셋으로 필드를 뽑지 마라 —
      `\uXXXX` 이스케이프(§4.3)와 한글 다중바이트에서 반드시 깨진다.
- [ ] **바이트 수 ≠ 문자 수**(§4.4). 고정폭 버퍼·`char[8]` 가정 금지.
- [ ] `plain` 은 언제나 원문 UTF-8 — 이스케이프 해제기를 돌리지 마라(§5.1).
- [ ] `format` 은 `new`/`old` 지만 그 밖의 값이 와도 죽지 않게(§4.2).
- [ ] 빈 줄은 오지 않지만 와도 견딘다(§5.2).
- [ ] EOF 잔여를 표시(§8.4).
- [ ] 줄 길이 상한(참조 구현 기본 64 KiB). 초과 시 연결 종료 — LF 를 안 보내는 클라이언트가
      메모리를 무한히 먹는 것을 막는다.
- [ ] 출력을 매 줄 **flush**. 안 하면 파이프·리다이렉션에서 "아무것도 안 온다"로 보인다.
- [ ] 여러 스레드가 찍으므로 출력에 락을 건다. 안 하면 줄이 섞인다.
- [ ] 아무것도 되돌려 보내지 않는다.
- [ ] 조용한 연결을 끊지 않는다(§6).
- [ ] `Ctrl-C` 로 깨끗이 종료.

## 10. 상호운용 예제 — 실제로 왕복시킨 기록

아래는 **실행해서 얻은 출력**이다(참조 서버 `net/test_server.py`).
새 서버를 만든 뒤 같은 입력으로 같은 결과가 나오면 이 명세를 만족한다.
**10.1·10.3·10.6·10.7 은 개정 2 의 실제 번호판 페이로드로 다시 돌린 것이다**(포트 5063).

### 10.1 붙인 두 줄(new+old) + 한글 한복판 쪼갬 + 미종단 번호판 꼬리

보낸 순서:
1. `sendall(new프레임 + old프레임)` — 두 줄을 한 번의 `sendall` 로
2. 한 줄을 `가`(`EA B0 80`)의 **`EA` 와 `B0` 사이**에서 갈라 두 번에 나눠 보냄
   (실측 분할점: `...ea | b080...`)
3. `sendall('123가45')` 후 close — **LF 없이** 종료. 잘린 번호판이다

받은 결과:

```
21:30:37.131  ← 127.0.0.1:55135  #1  {"ts":1755080001000,"value":"123가4568","conf":0.82,"format":"new","seq":1,"device":"SM-S911N"}
21:30:37.131  ← 127.0.0.1:55135  #2  {"ts":1755080002000,"value":"12가3456","conf":0.82,"format":"old","seq":2,"device":"SM-S911N"}
21:30:37.737  ← 127.0.0.1:55135  #3  {"ts":1755080003000,"value":"123가4568","conf":0.82,"format":"new","seq":3,"device":"SM-S911N"}
21:30:38.346  ! 127.0.0.1:55135  미종단 잔여 8 바이트(LF 없음): 123가45
21:30:38.347  - 127.0.0.1:55135  해제 — 클라이언트가 닫음 · 줄 3 · 298 바이트 · 동시접속 0
```

- `#1`/`#2` — 붙어 온 두 줄이 정확히 둘로 분리됐고 `format` 이 각각 `new`/`old` 로 보존됐다.
- `#3` — **한글 한복판에서 갈린 줄이 깨짐 없이 복원됐다.** 이게 개정 2 의 핵심 검증이다.
- 마지막 — 잘린 `123가45` 가 유효한 값으로 둔갑하지 않고 경고로 표시됐다.
  8바이트인 이유는 `123`(3) + `가`(3) + `45`(2)라서다 — **7문자가 아니라 8바이트**(§4.4).

### 10.2 `nc` 손시험 (CRLF 관용 포함)

```
$ printf 'nc-line-1\r\nnc-line-2\n' | nc -w 1 127.0.0.1 5057

21:11:43.552  ← 127.0.0.1:54128  #1  nc-line-1
21:11:43.552  ← 127.0.0.1:54128  #2  nc-line-2
```

CR 이 벗겨져 값이 깨끗하다. (프레이밍 시험이라 ASCII 로 두었다.)

### 10.3 동시 접속 3 + 각자 한글 한복판 쪼갬 + half-close

서로 다른 번호판 셋(`123가4568` / `456나7890` / `12다3456`)을 동시에 보내고,
각 연결에서 `plain` 줄을 자기 한글의 한복판에서 갈라 보냈다.

```
21:30:38.852  + 127.0.0.1:55137  접속 #2 · 동시접속 1
21:30:38.852  + 127.0.0.1:55138  접속 #3 · 동시접속 2
21:30:38.852  ← 127.0.0.1:55137  #1  {"ts":1755080001000,"value":"123가4568",...,"seq":1,"device":"SM-S911N"}
21:30:38.852  ← 127.0.0.1:55138  #1  {"ts":1755080001000,"value":"12다3456",...,"seq":1,"device":"SM-S911N"}
21:30:38.853  + 127.0.0.1:55139  접속 #4 · 동시접속 3
21:30:38.853  ← 127.0.0.1:55139  #1  {"ts":1755080001000,"value":"456나7890",...,"seq":1,"device":"SM-S911N"}
21:30:39.308  ← 127.0.0.1:55139  #2  456나7890
21:30:39.309  ← 127.0.0.1:55138  #2  12다3456
21:30:39.309  ← 127.0.0.1:55137  #2  123가4568
21:30:39.513  - 127.0.0.1:55138  해제 — 클라이언트가 닫음 · 줄 2 · 106 바이트 · 동시접속 2
21:30:39.514  - 127.0.0.1:55137  해제 — 클라이언트가 닫음 · 줄 2 · 108 바이트 · 동시접속 0
```

세 연결의 버퍼가 섞이지 않았고(각자 `#1 #2`), **서로 다른 한글이 각자 정확히 복원**됐다.
`가`·`나`·`다` 는 UTF-8 선두 바이트가 각각 `EA`·`EB`·`EB` 로 다르다 —
특정 바이트값에 맞춘 처리가 아니라 일반적인 조립이라는 뜻이다.

### 10.4 줄 길이 상한

`--max-line 64` 로 띄우고 LF 없이 200바이트를 보냈을 때:

```
21:12:27.279  + 127.0.0.1:54163       접속 #1 · 동시접속 1
21:12:27.280  ! 127.0.0.1:54163       줄 하나가 64 바이트를 넘었다 — LF 종단이 없다. 끊는다.
21:12:27.280  - 127.0.0.1:54163       해제 — 줄 길이 초과 · 줄 0 · 200 바이트 · 동시접속 0
```

### 10.5 재기동

서버를 죽이고 **곧바로** 같은 포트로 다시 띄운 뒤 접속:

```
21:12:12.671  + 127.0.0.1:54153       접속 #1 · 동시접속 1
21:12:12.672  ← 127.0.0.1:54153       #1  4242
```

`SO_REUSEADDR` 덕분에 `TIME_WAIT` 대기 없이 재바인드되었다.
(같은 포트에 두 번째 인스턴스를 띄우면 `바인드 실패 0.0.0.0:5057 — [Errno 48] Address already in use`
로 깨끗이 실패한다. 조용히 죽지 않는다.)

### 10.6 한글 왕복 3종 요약 (개정 2 필수 검증)

새 수신기를 만들면 **이 세 가지를 반드시 통과해야 한다.** 위 10.1·10.3 의 부분집합이다.

| 경우 | 보낸 방식 | 기대 결과 | 실측 |
|---|---|---|---|
| (a) 통째 | `123가4568` 한 줄을 한 번에 | 그대로 | ✅ 10.1 `#1` |
| (b) 쪼갬 | `가`(`EA B0 80`)의 `EA` 뒤에서 갈라 두 번에 | 한 줄로 복원 | ✅ 10.1 `#3` |
| (c) 붙임 | new+old 두 줄을 한 번의 `sendall` 로 | 두 줄로 분리 | ✅ 10.1 `#1`·`#2` |

(b) 를 통과하지 못하는 수신기는 **실기기에서 반드시 한글을 깬다.**
루프백에서는 운 좋게 한 번에 도착해 통과한 것처럼 보일 수 있으니, 위처럼 **일부러 갈라서** 시험한다.

### 10.7 `\uXXXX` 이스케이프 복원

송신 측이 한글을 `가` 형태로 보냈을 때:

```
21:30:39.921  ← 127.0.0.1:55140  #1  {"ts":1755080009000,"value":"123가4568","conf":0.82,"format":"new","seq":9,"device":"SM-S911N"}   → value=123가4568 format=new
```

원문 줄은 **받은 그대로** 남기고(수신의 본체는 바이트 재현이다),
그 뒤에 `→` 로 복원값을 덧붙였다. 로그만 보고 "한글이 깨졌다"고 오해하지 않게 하려는 것이다.
이 덧붙임은 **참조 서버의 편의 기능**이지 프로토콜 요구사항이 아니다 —
요구사항은 §4.3 의 "수신 측이 두 표기를 모두 복원한다"이고, JSON 파서를 쓰면 저절로 충족된다.

## 11. 아직 정해지지 않은 것 (앱·서버 모두 가정하지 말 것)

- **서버 IP·포트.** 이 문서는 어떤 주소도 가정하지 않는다. 앱은 `server.properties` 로 받고
  (계약 §6), 서버는 인자로 받는다. 문서·코드 어디에도 IP 를 하드코딩하지 않는다.
- IPv6, TLS, 인증, 압축: v1 범위 밖이다. 필요해지면 루트에게 요청해 새로 정한다.
- **번호판 규격 확장.** 지금 와이어에 오는 `format` 은 `new`/`old` 뿐이다.
  지역명 2단 번호판·노란 영업용판은 계약 §1 에서 이번 범위 밖이다.
  늘어난다면 `format` 에 값이 추가되는 형태가 자연스럽다 — 그래서 **수신 측이 모르는
  `format` 값에 죽지 않게** 해 두는 것이다(§4.2). 그때 이 명세는 갱신되지만
  기존 수신기가 깨지지는 않는다.
