> **전이중 토대가 서면 무엇이 사라지고 무엇이 남는가.**
> 작성 2026-08-17 · socket-engineer · **문서만. 구현·배포 없음.**
>
> 🔴 근본 원인: **`SoftwareSerial` 은 송신 중 `cli()` 로 인터럽트를 끄고, 수신은 인터럽트로만
> 일어난다**(`SoftwareSerial.cpp:436·464·219`). → **송신 중 수신이 원리적으로 불가능하다.**
> 하드웨어 UART 는 **전이중**이고 송수신 버퍼가 독립이다.

## 0-A. 🔴 **새 설계를 시작할 때 이것부터 읽어라 — 가져갈 것 / 버릴 것**

> **첫 작업은 "무엇을 버리고 무엇을 가져가나"를 가르는 것이다.**
> 안 가르면 **반이중 전제로 나온 값과 구조가 새 토대에 그대로 실려 온다.**

### ✅ 토대가 바뀌어도 **가져갈 것**

1. 🔴 **`pend` 를 "수신 대기"와 "확정 대기"로 분리한다** ← **첫 항목이다**
   지금은 하나가 둘을 겸해서, 진실원을 마스크로 옮기면 **자가 치유가 예약을 취소한다.**
   **설계 문제이지 이중성 문제가 아니다** — 새 토대에서도 그대로 터진다.
   **처음부터 분리해서 시작해라.**
2. **`@<rid>` 태그 형식 · 태그 기반 식별** — 위치가 아니라 태그로 찾으면 선택 필드가 늘어도
   안 깨지고 **옛 프레임이 자동으로 구 형식으로 읽힌다.** `a` 가 아니라 `@` 인 이유:
   **`devid` 가 ALPHA 로 시작할 수 있다**(`server.cpp:890`).
3. **구/신 동시 수용 절차**(원장 §6) — 수용 → 시각 통보 → 변경. **되돌릴 필요가 없어진다.**
4. **멱등 캐시** — 재전송이 남는 한 필요하다. 이중성과 무관.
5. **`result` 는 성공의 증거가 아니다** — 성공은 **마스크 변화**로 확정한다.
   **사용자가 짚은 그 문제이고, 이중성과 무관하게 옳다.**
6. **하행 흐름 제어**(속도 상한 · 큐 · 미룬 수 로깅) — §4.
   ⚠ **"반이중 회피"가 아니라 "장치 용량 존중"이다.**
7. **`0` 이 무엇인지 갈리게 하기 · 측정한 것을 이름으로 삼기**(원장 §0·§5.2) — 토대 무관.

### 🔴 **버릴 것 / 값을 다시 뽑을 것**

| 버린다 | 이유 |
|---|---|
| **하행 송신 창**(조용한 구간에만 송신) | 전이중이면 **겨냥할 창이 없다** |
| **"추가 송신을 줄인다"는 동기** | 송신이 수신을 안 막는다 |

| 값을 다시 뽑는다 | 왜 |
|---|---|
| 재전송 횟수·간격 | **유실 원인이 바뀐다**(§3.1) |
| `ACK_TIMEOUT` · 오프라인 임계값 | **주기가 바뀐다** — 새 토대에서 재실측 |
| 하행 속도 상한 | 🔴 **장치 처리 용량에서 뽑는다. 송신 창이 아니라.** |

⚠ **지금 값을 옮겨 쓰지 마라. 전부 반이중 전제에서 나온 숫자다.**

### 🤝 web 과 맞출 것

- **화면에 "대기 중"이 보여야 한다** — 하행이 큐에서 기다리는 동안.
  **안 보이면 사용자가 다시 누르고 그게 또 쌓인다.**
  🔑 **사용자가 재현한 것이 정확히 그 모양이었다**(연속 예약 6건/10초).

## 2. 동기가 사라진 것들 — **그래도 다시 볼 값이 있는 것**

### 2.1 `@<rid>` 태그 형식 — **토대와 무관하게 좋다**

`a<rid>` 가 아니라 `@<rid>` 인 이유(devid 가 ALPHA 로 시작 가능)와
**위치가 아니라 태그로 식별하는 것**은 **이중성과 아무 상관이 없다.**
→ **새 프로토콜에서도 선택 필드를 늘릴 때 그대로 쓴다.**

### 2.2 ACK 를 `S` 에 얹기 — **동기는 사라지지만 부수 이득은 남는다**

**사라지는 동기**: *"추가 송신이 수신을 막는다"* → 전이중이면 안 막는다.
**남을 수 있는 이유**:
- 프레임 수가 준다(대역·파싱·로그량)
- **`result` 를 성공의 증거로 쓰지 않는다**는 원칙은 **이중성과 무관하게 옳다**

🔴 **다만 그 원칙을 코드로 옮기는 것은 여전히 자가 치유 로직과 얽힌다**(내가 찾은 그 문제).
**토대가 바뀌어도 그 얽힘은 안 풀린다** — `pend` 하나가 "수신 대기"와 "확정 대기"를 겸하는 것은
**설계 문제이지 이중성 문제가 아니다.**

---

## 3. 남지만 **값을 다시 뽑아야** 하는 것

### 3.1 재전송 — **이유가 바뀐다**

| | 반이중 | 전이중 |
|---|---|---|
| 유실 원인 | **장치가 송신 중이라 못 들음** | 버퍼 넘침 · 파싱 실패 · 장치 바쁨 |
| 대응 | 다시 쏘면 다른 위상에 착지 | **다시 쏴도 같은 이유면 또 실패한다** |

⚠ **그래서 "3회"의 근거가 사라진다.** 반이중에서는 위상이 바뀌니 재시도에 의미가 있었지만,
전이중에서 같은 이유로 실패하면 **재시도가 같은 결과를 반복**한다.
→ **재전송 횟수·간격을 새 실패 모드에서 다시 정해야 한다.**

⚠ **그리고 TCP 가 이미 전달을 보장한다.** 그러므로 재전송이 지키는 것은
**"전달"이 아니라 "장치가 처리했다"** 이다.

> ### 🔑 **새 명세에 이 문장을 박아라**
>
> **재전송은 전달을 보장하지 않는다 — TCP 가 한다.**
> **재전송이 보장하려는 것은 "장치가 그 명령을 처리했다"이다.**
>
> ⚠ **같은 코드가 남더라도 그것이 무엇을 보장하는지가 바뀐다.**
> 오늘 우리가 계속 만난 형태(**이름은 그대로인데 세는 것이 달라진다** · 원장 §0)의
> **설계판**이다. 안 적으면 다음 사람이 **"재전송이 있으니 전달은 보장된다"** 로 읽는다.

### 3.2 `ACK_TIMEOUT` · 오프라인 임계값

**둘 다 장치 주기의 함수**다. 🔴 **그리고 주기는 상수가 아니다**(원장 §8.11 — 빌드·페이로드·
ESP 응답의 함수). **전이중으로 바뀌면 주기 자체가 달라진다** — 송신이 인터럽트를 안 막으므로
`SEND OK` 대기 구조가 바뀔 수 있다.
→ **새 토대에서 주기를 다시 실측한 뒤에 값을 정한다. 지금 값을 옮겨 쓰지 마라.**

## 4. 🔴 사용자 질문에 대한 답 — **"상행은 1초 제어가 있는데 하행은 없는가"**

### 맞다. 그리고 **그 비대칭은 전이중이 돼도 남는다.**

```
상행 : 장치가 스스로 약 1.113초마다 하나씩 보낸다        ← 속도가 정해져 있다
하행 : 사용자가 누를 때마다 나간다 · 상한 없음 · 몰릴 수 있다  ← 규율이 없다
```

**사용자 재현(연속 예약 6건/10초)이 그 비대칭의 실물이다.**

### 왜 전이중이 돼도 남는가

**이중성은 "동시에 되는가"의 문제이고, 이건 "얼마나 빨리 보내도 되는가"의 문제다.**
전이중이어도 장치는:
- **입력 버퍼가 유한하다** — 실제로 `[DROP-OVF] 96바이트 초과` 가 관측됐다
- **처리 시간이 있다** — 파싱·적용·응답
- **RAM 2KB** 다

→ **몰아 보내면 전이중이어도 넘친다.** 막는 것은 이중성이 아니라 **흐름 제어**다.

### 그래서 서버가 가져야 할 규율 (내 도메인 · 토대와 무관)

1. **하행에 속도 상한을 둔다.** 값은 **장치 처리 용량에서 뽑는다** — 송신 창이 아니라.
   ⚠ **지금 값을 옮겨 쓰지 마라.** 새 토대에서 "장치가 초당 몇 건을 처리하나"를 재야 한다
2. **큐를 만든다.** 상한을 넘으면 버리지 말고 **미루고, 미룬 수를 로그에 남긴다**
   (조용히 미루면 지연이 안 보인다 — 원장 §5.2)
3. **몰림을 서버가 흡수한다.** 사용자가 6건을 10초에 눌러도 **전선에는 규율대로 나간다**
4. ⚠ **화면에는 "대기 중"이 보여야 한다.** 안 그러면 사용자가 다시 누르고 그게 또 쌓인다

🔑 **이것은 "반이중 회피"가 아니라 "장치 용량 존중"이다.**
**전제가 바뀌어도 필요하고, 값만 새로 재면 된다.**
