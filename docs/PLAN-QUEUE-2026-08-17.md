> 1. **ESP 클래스는 `init`·`read`·`write` 3개 함수로 동작**하도록 작성.
>    `init` 은 `setup` 내에서 초기화 완료. `read`·`write` 는 루프 내에서 이용되어
>    패킷을 읽어 들여 **아두이노와 연결될 모듈들의 동작을 담당**한다.
> 2. **서버측에는 파킹 클래스와 아두이노모듈 클래스를 연결하는 브릿지 명세**가 확립되어야 한다.
> 3. **주차구역을 5개로 줄인다.** 해당 주차구역은 **유동적으로 변경 가능**해야 한다(크기·갯수 등).
> 4. **입구와 출구 영역이 추가로 필요하다.** 기본 구조는 동일하고 **이름만 다르다.**
> 5. **전체 맵**이 있다. 진짜 지도면 좋겠지만 지금은 **배열 같은 격자 구조**로 한다.
>    맵은 그리드로 나뉘고 해당 위치에 **주차구역 또는 입구·출구가 들어갈 수 있다.**
> 6. **각 주차구역·입출구는 모듈을 가질 수 있다.**
>    - 입차/출차 → **차단봉 · 입출차 센서**
>    - 주차구역 → **주차확인 센서 · 안내등 · 유도등**
> 7. 🔴 **이 센서들은 랜덤한 아두이노에 있을 수 있다.**
>    **1대의 아두이노가 1개의 주차구역, 이런 식이 아니다.**
>    아두이노는 **여러 모듈**을 가질 수 있고 이 모듈들은 **주차구역과 연결된다.**

### 🔴 장치는 완전히 독립이다 — 고장이 번지지 않는다 (사용자 확정 2026-08-17 21:1x)

> *"모든 아두이노는 독립이다. 하나의 아두이노에 설치된 esp01이 와이파이를 잡지 못한다고
> 다른 아두이노 esp01에 영향을 주는 일은 없다."*

**이것이 설계 원칙으로 승격된다. 세 가지가 여기서 따라 나온다:**

1. **`init` 이 사다리만 시작하는 이유가 확정된다**(위 (A) 결정). 한 대가 링크를 못 잡아도
   나머지는 물론이고 **그 한 대의 로컬 센서도 계속 돌아야 한다.**
2. 🔴 **서버가 "장치 하나 죽음"을 "시스템 죽음"으로 번지게 하면 안 된다.**
   지금 `OFFLINE_MS`·`ARD_IDLE_CLOSE_MS`·`first-S-wins` 는 **주차 노드가 하나**라는 전제 위에 있어서
   그 하나가 죽으면 전체가 오프라인이다. **노드별로 갈라야 한다** —
   한 노드의 오프라인은 **그 노드가 담당하는 모듈만** 미상으로 만든다.
3. **화면도 마찬가지다.** 구역 상태를 여러 장치에서 조립하므로(미결 ②) 한 장치가 죽으면
   **그 구역의 일부 칸만 미상**이다. **전체를 회색으로 덮으면 안 되고, 미상인 칸만 미상으로 그린다.**

⚠ **그리고 ③(WiFi 공유 매체)과 이 원칙은 충돌하지 않는다.** 독립인 것은 **고장·상태**이고,
공유하는 것은 **대역폭·지연**이다. 한 대가 죽어도 남은 대가 계속 도는 것은 참이고, N 대가 동시에
보내면 각자의 왕복이 늘어나는 것도 참이다. **다른 축이다** — 섞어서 "독립이니 N 은 상관없다"로
읽으면 창 계산이 틀린다.

#### ✅ ① 은 미결이 아니었다 — **루트가 슬롯 규칙을 잘못 확장했다** (사용자 정정 2026-08-17 21:2x)

> *"1.2초는 esp01 단위로 발생하는 것이다. **10개의 esp01에게는 동시에 보내도 된다.**"*

**슬롯이 제약하는 것은 "한 ESP 에게 얼마나 자주 보내는가" 하나다.**
그 이유는 물리적이다 — **그 ESP 와 그 아두이노 사이의 반이중 UART.**

```
슬롯이 막는 것 : 같은 ESP 에게 1.2초 안에 두 번 보내는 것    ← UART 겹침
슬롯이 막지 않는 것 : 다른 ESP 들에게 같은 순간에 보내는 것   ← 서로 다른 UART · 서로 다른 TCP 소켓
```

🔴 **내가 "서버가 슬롯당 한 번 보낸다"를 "서버가 한 번에 한 장치에게만 보낸다"로 넓혔다.**
그런 제약은 없다. 서버는 **10개 소켓에 동시에 write 한다** — 각 소켓이 자기 창에 있으면 된다.

**따라서:**
- **같은 아두이노의 모듈들** → 한 `CIPSEND` 에 여러 줄로 실린다. **편차 0**(이미 구현됨).
- **다른 아두이노의 모듈들** → **각 소켓에 동시에 나간다. 편차는 네트워크 지연 수준**(실측 왕복 최대 1ms).
  ⚠ 각 장치의 창이 지금 열려 있어야 하고, 창은 그 장치의 `S` 도착으로 열린다.
  **닫혀 있으면 최대 한 슬롯 기다린다** — 그것이 1.2초의 유일한 발생 조건이고,
  **동시 전송이 아니라 창 위상의 문제**다.

**→ 시계 동기가 필요 없다. `②`·`③` 만 남는다.**

##### 🔴🔴 그리고 **지금 메커니즘은 그대로 살린다. 없애는 것이 아니다** (사용자 강조)

> *"1.2초내에 발생한 이벤트는 모아서 보내고, 모은 것보다 많은 데이터는 1.2초 뒤에 보내거나
> 1.2초 인터벌을 넘는 이벤트들을 0번 슬롯 보내는 것이다. 0번 슬롯에 대한 이벤트만 처리되는 것이다.
> 지금 구현된 제어가 1개의 슬롯을 대상으로만 작동하는 방식이다. **작동은 해야 한다!! 없애는 것이 아니다**"*

**소스 대조 결과 — 사용자 서술이 구현과 정확히 일치한다**(`server.cpp` `flush_downq`):

```c
for (…) {
    if (payload.size() + q.line.size() > DOWN_BATCH_CAP_B) break;   // ← 넘치면 멈춘다
    payload += q.line;                                              // ← 모아서 한 거래로
    downq.erase(downq.begin());
}
// break 로 남은 것은 downq 에 그대로 → 다음 창에서 나간다
q_deferred++;                                                       // ← 남긴 창의 수를 센다
```

| 사용자 서술 | 구현 |
|---|---|
| 1.2초 안에 생긴 이벤트를 **모아서** 보낸다 | `payload += q.line` — 한 `CIPSEND` 에 여러 줄 |
| **모은 것보다 많으면** 1.2초 뒤에 보낸다 | `break` 후 `downq` 에 잔류 → 다음 창 (`q_deferred`) |
| 인터벌을 넘는 이벤트는 다음 차례에 | 같은 경로 |

> ### **그러므로 개정에서 할 일은 이 메커니즘을 노드마다 복제하는 것이다. 고치거나 약화시키는 것이 아니다.**

```
지금 : 이 상태 한 벌이 Server 에 전역으로 있다  →  1개 노드만 대상이 된다
개정 : 노드마다 한 벌 (downq · downq_bytes · ard_last_ms · rtt_max_ms · win_skips · dmax_flushes)
       각 노드가 자기 1.2초 주기로 자기 창에 자기 큐를 비운다 — 규칙은 한 글자도 안 바뀐다
```

⚠ **약화 금지 항목**(개정 중 이것들이 사라지면 창4 기전이 돌아온다):
`DOWN_BATCH_CAP_B` 상한 · `q_deferred` 계수 · `D_max` 창 포기 박자 · `queued` 응답 ·
`SLOT_TX_RESERVE_MS` 가드 · 배포 순서(큐를 `queued` 보다 먼저 올리지 않는다).

##### ⚠ 용어 충돌 — **"슬롯"이 두 가지를 뜻한다**

이 프로젝트에서 `슬롯` 이 이미 **주차 자리**(`Slot slots[10]` · `A1`~`B5`)를 뜻한다.
사용자가 말한 `0번 슬롯` 은 **자기 1.2초 주기를 갖는 단위 = 한 ESP·한 노드**다.

**CLAUDE.md §"이름이 아니라 정의를 맞춰라" 에 정면으로 걸리는 자리다.** 개정에서 이름을 갈라야 한다:

| 뜻 | 제안 이름 |
|---|---|
| 자기 1.2초 주기를 갖는 통신 단위 (ESP 하나 · 소켓 하나) | **노드**(`node`) |
| 격자 위의 주차 자리 | **자리**(`space`) 또는 `zone` |
| 1.2초 주기 자체 | **주기**(`cycle`) 또는 `carrier` |

**이름을 안 갈라 두면 "슬롯 10개"가 자리 10개인지 노드 10개인지 문서마다 달라진다.**

##### 남는 실제 물음 — 위상 정렬(급하지 않다)

장치들의 `S` 위상이 흩어져 있으면 명령이 각자 다음 창을 기다려 **최대 1.2초까지 벌어질 수 있다.**
**동시 전송이 안 되기 때문이 아니라 창이 안 열려 있어서다.** 완화가 필요하면 방법은 있다
(하행 대기 중일 때 창 개방을 앞당기기 등) — **실측으로 문제가 보인 뒤에 다룬다.**
⚠ 지금 위상을 정렬하려 들면 **`t0` 를 시계로 만드는 것**이고, 그건 이 설계가 일부러 버린 것이다.

#### 주소 체계 — **모든 객체가 고유 ID 를 갖는다** (사용자 확정 2026-08-17 21:3x)

> *"주차자리등의 객체와 아두이노는 고유값 ID 를 갖는다."*

```
아두이노    devid      전역 고유. 이미 있다 — 전선에 실린다 ("P1" · BNF 1*8자)
자리·입출구  zone id    전역 고유. 있지만 성질이 다르다 ↓
모듈        name       🔴 고유값이 아니다 — 명칭이다. devid 와 결합해서 고유해진다 ↓
```

##### 🔴 모듈 이름은 **장치 안에서만 유효하다** (사용자 정정 2026-08-17 21:3x)

> *"모듈ID는 고유값은 아니다. 아두이노ID와 결합되어 고유값이 될수 있다. 예를 들어 esp01은 모든
> 아두이노에 실장될 예정이다. 전체에 1개만 유지되는 고유값 개념은 아니다.
> **모듈의 id 는 명칭이라고 보는 것이 맞을 것이다.**"*

```
전역 키  =  (devid, name)          ← 복합 키다. 단일 값이 아니다
예시     :  (P1, esp01) · (P2, esp01) · (P1, barrier) · (P3, barrier)
                  ↑ 같은 이름이 여러 장치에 있다. 정상이다
```

**즉 `name` 은 신원이 아니라 역할·종류다.** `esp01`·`barrier`·`led` 처럼 **무엇인지**를 말한다.
그래서 **장치는 자기 안에서만 이름이 겹치지 않게 하면 되고, 전역 조율이 필요 없다** —
새 아두이노를 만들 때 남이 어떤 이름을 썼는지 알 필요가 없다. **이게 이 결정의 실질적 이득이다.**

⚠ **그러므로 설계·코드·로그에서 이렇게 다뤄라:**

| 하지 말 것 | 할 것 |
|---|---|
| `module_id` 라고 부르기 | **`name`** — 고유값처럼 읽히는 이름을 붙이지 않는다 |
| `name` 만으로 조회·라우팅 | **항상 `(devid, name)` 쌍으로** 조회한다 |
| `map<name, Module>` | **`map<devid, map<name, Module>>`** 또는 `map<pair<devid,name>, …>` |
| 로그에 `barrier 응답 없음` | **`P3.barrier 응답 없음`** — 어느 장치인지 없으면 추적 불가 |

🔴 **`zone → [module]` 관계도 복합 키로 적어야 한다:**
```
zone "A1" → [ (P1, sensor), (P3, led) ]      ← 한 자리의 모듈이 두 장치에 흩어질 수 있다
```
**`zone "A1" → [sensor, led]` 로 적으면 어느 장치인지 사라지고 하행을 보낼 곳을 모른다.**
그리고 web 의 "거짓 허용이 더 나쁘다"(닿지 않는 장치로 하행) 판정이 정확히 이 지점에 걸린다.

##### 🔴 지금 자리 ID 는 **고유값이 아니라 위치다**

```c
static const char* SLOT_ID[10] = {"A1","A2",…,"B5"};   // 표의 인덱스가 곧 신원
```

**`A1` 은 "그 장치가 보고하는 비트열의 0번째"** 라는 뜻이다. 그래서 지금 `S` 프레임은 **ID 를
안 싣는다** — 비트 위치가 ID 를 대신한다:

```
S,912,0110000010,0000000000,1080,P1,01
       ^^^^^^^^^^ 이 10비트의 순서가 곧 A1..B5
```

> ### **즉 자리의 신원이 "전선에서의 순서"에 묶여 있다.** 자리를 5개로 줄이거나 순서를 바꾸면
> **같은 비트가 다른 자리를 뜻하게 되고, 서버와 펌웨어가 조용히 어긋난다.**
> 고유 ID 를 도입하는 것은 이름을 붙이는 일이 아니라 **이 결합을 끊는 일**이다.

##### 그래서 확정 — **전선은 ID 로 말하고, 관계는 서버가 안다**

```
(devid, name) → pin              장치가 아는 것: 자기 모듈들. name 은 장치 안에서만 유효
zone id → [(devid, name), …]     서버가 아는 것: 자리↔모듈 관계. 여러 장치에 흩어질 수 있다
map cell → zone id               서버가 아는 것: 격자 배치
```

**`devid` 와 `zone id` 는 전역 고유이고, `name` 은 그 장치 안에서만 고유하다.**
**전역 신원은 항상 `(devid, name)` 쌍이다.**

- **장치는 자기 모듈 ID 만 안다. `zone` 을 모른다.**
  **장치가 구역을 알게 만들면 배선이 바뀔 때마다 펌웨어를 다시 굽는다** —
  `SERVER_IP` 를 펌웨어에 박아 데인 것과 같은 형태다(arduino 선행 의견, 채택).
- **`zone` 조립은 서버가 한다.** 그래야 배선 변경이 서버 설정 변경으로 끝난다.
- **ID 는 위치와 독립이어야 한다** — `A1` 이 격자 어디로 옮겨가도 같은 자리다.
  **격자 좌표를 ID 로 쓰면 자리를 옮길 때 신원이 바뀐다.**

##### ⚠ 전선 예산이 이 결정의 제약이다 — 계획 단계에서 먼저 계산할 것

**한 줄 64B 상한**(LF 포함)이고 현재 `S` 프레임이 **55B** 를 쓴다. **여유가 9B 다.**

```
지금 : 비트열 10칸 = 10B 로 10개 자리의 상태를 전부 나른다   ← 극도로 압축적
ID   : "A1:1" 하나가 5B  →  5개만 실어도 25B. 여유를 넘는다
```

🔴 **ID 를 상태 프레임에 그대로 실으면 예산이 터진다.** 선택지가 셋이고 **계획 단계에서 정한다:**

| 방식 | 비용 |
|---|---|
| **비트열 유지 + 순서를 서버가 등록**(접속 시 한 번 `M` 프레임으로 모듈 목록 신고) | 전선 비용 0. 등록 프레임 하나 추가 |
| ID 를 짧게(1~2자) + 상태를 여러 줄로 | 줄 수 증가 → 배치 크기 증가 |
| 변한 것만 보낸다(델타) | 상태 프레임이 멱등성을 잃는다 — **재접속 시 전체 재동기 경로가 필요** |

**첫 번째가 유력하다** — 비트열의 압축성을 지키면서 "순서가 곧 신원"을 끊는다.
접속 시 `M` 프레임으로 **"내 0번 비트는 `sensor`"** 를 신고하면 그 뒤 비트열은 그대로 쓸 수 있다.
⚠ **다만 그 등록이 유실되면 이후 모든 상태가 잘못 귀속된다** — 등록 확인·재시도 규약이 필요하다.

🔑 **그리고 `name` 이 장치 안에서만 유효한 것이 이 방식을 더 싸게 만든다.** 등록 프레임이
**자기 장치 문맥 안에서 보내지므로 `devid` 를 매 항목에 반복할 필요가 없다** —
그 프레임이 어느 소켓으로 왔는지가 곧 `devid` 다. 이름을 짧게 유지하면 등록도 몇 줄로 끝난다.

#### ✅ ESP 클래스 — **`init`·`read`·`write`·`reset` 넷으로 확정** (사용자 결정)

arduino 가 "셋으로는 접속 사다리(`netTick`)가 갈 곳이 없다"고 사실 보고했고, **사용자가 `reset` 을
추가하기로 정했다**(arduino 가 제안한 이름은 `tick` 이었다).

```
init()    setup 에서 한 번  — 모듈 기동 + 사다리 시작
read()    loop            — 수신
write()   loop            — 송신 (3단 게이트 · busy 대응 포함)
reset()   loop            — 링크 상태를 유지한다 ↓ 정의는 아래
```

**`reset()` 의 정의** — *"링크가 죽었을 때 세운다"* 로 좁히면 안 된다(arduino 정정):

> ### **링크 상태를 유지한다 — 안 서 있으면 세우고, 오래 서 있었으면 방어를 낮춘다.**

**`reset` 이 `tick` 보다 나은 이유**: 그 함수의 중심이 *"링크가 안 서 있다 → 세워라"* 이고
`AT+RST`·`CWQAP` 리셋 계단이 거기 있다. **`tick` 은 무엇이든 할 수 있는 이름이라 나중에
관계없는 코드가 들어오는 자리가 된다.**

- **호출부는 조건을 몰라도 된다.** `reset()` 을 매 루프 불러도 되고 함수가 스스로 판단한다.

#### 🔴 루트가 소스를 잘못 요약했다 — 정정 (arduino 가 실물을 봤다)

내가 *"`netTick()` 은 `if (netOnline) return;` 으로 시작하니 온라인일 때 아무것도 안 한다"* 고 적었다.
**실제 코드는 조기 반환 앞에 일이 있다**(`client.ino:2602`):

```c
if (netOnline) {
    // ★ REQ-0071 — 연속 30초 온라인이라야 사다리를 0단으로 내린다
    if (rung != RUNG_MEASURE && (now - onlineSince) >= LADDER_RESET_MS) {
        rung = RUNG_MEASURE;  rungFails = 0;      // ← 방어 수준 하강
    }
    return;
}
```

**온라인 경로에도 상태 변경이 있다: "30초 건강했으니 방어 수준을 낮춘다."**
그리고 **그 일은 좁은 의미의 `reset` 이 아니다** — 링크를 세우는 게 아니라 **안 세워도 된다는 판정**이다.
그래서 위 정의를 넓혔다. **이것이 원래 이름이 `netTick` 이었던 이유다** — 양쪽에 할 일이 있다.

⚠ **정의를 안 넓히면 그 로직이 조용히 사라지거나 `read()` 로 흘러든다.** 사라지면
**사다리가 영원히 높은 단에 머물러 다음 사고 때 4단(하드웨어 리셋)부터 시작한다** —
증상은 *"왜 갑자기 ESP 를 리셋하지?"* 이고 **원인은 안 보인다.**

> ### ★ 일반화 — 함수를 쪼갤 때
> **"그 함수가 오프라인일 때 하는 일"만 보지 말고 "온라인일 때 하는 일"도 세어라.**
> **조기 반환 앞의 코드는 눈에 안 띈다.** 이 팀은 오늘 같은 형태로 여러 번 걸렸다.
- **`read()` 에 넣지 않는 이유**: "읽는다"는 함수가 소켓을 다시 세우면 이름이 거짓이 되고,
  **읽을 것이 없을 때도 사다리는 돌아야 한다.**
- 3단 게이트·`busy` 대응은 `write` 안에 그대로 둔다 — 밖으로 꺼내면 실패 모드별 제어 경로가 생긴다.

##### ✅ `init` 은 **사다리만 시작하고 끝난다** — 안 (A) 로 확정 (사용자 결정)

지금 코드가 이미 그렇다(`setup` 에서 `netAdvance(NET_CWMODE, 1500)` 로 첫 단만 밀고 진행은 루프가 한다).
**대안 (B) `init` 이 온라인까지 대기**는 채택하지 않았다.

**근거**: 사다리가 약 12초 걸리고 **실패할 수 있다.** `init` 에서 막으면 그 12초 동안 센서도 못 읽고,
WiFi 가 안 되는 자리에서는 **영원히 `setup` 을 못 나온다.**

🔴 **그리고 지시 7번(모듈 분산)이 이 선택을 필수로 만든다:**
- 한 대가 WiFi 를 못 잡아도 **나머지 장치가 돌아야 한다**
- 그 한 대도 **로컬 센서는 계속 읽어야 한다** — 링크가 없다고 물리 세계가 멈추지 않는다

> **즉 링크 없이도 장치가 산다.** 통신은 장치 기능의 일부이고 전제가 아니다.

⚠ **구현 시 주의**: `init()` 이 "성공"을 돌려주면 안 된다 — 그 시점에 링크는 아직 없다.
반환값을 둔다면 **"모듈 기동에 실패했다"(하드웨어 문제)와 "아직 링크가 없다"(정상)를 갈라야** 한다.
합치면 호출부가 정상 상태를 오류로 읽는다.

🔴 **그런데 더 좁다**(arduino): **`init()` 은 "ESP 가 대답하는가"조차 확신할 수 없다.**
부팅 사다리 1단(`AT+RST`)의 응답은 **비동기로 오고 `setup` 에서는 아직 안 왔다.**

> ### **`init()` 이 진짜로 알 수 있는 것은 "UART 를 열었다"뿐이다. 그 이상을 반환값에 담으면 거짓이 된다.**

→ 모듈이 실제로 살아 있는지는 **`reset()` 이 사다리를 진행하면서 알아낸다.** 그것이 그 함수의 일이다.
2. **하위호환을 어디서 끊는가** — 지금 도는 실물은 `P1` 하나이고 그것이 유일한 실기 자료원이다.
3. **모듈 주소 체계** — `<device>.<module>` 인가 `<map좌표>.<module>` 인가.
   전선 프레임 형식(64B 한 줄)에 무엇이 실리는가.
4. **격자와 논리의 분리** — 맵 좌표(그리드)와 자리 ID 는 같은 것인가 다른 것인가.
5. **web 화면** — 지금 화면은 10칸 고정이다. 격자 렌더링으로 바뀐다.
