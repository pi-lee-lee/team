# 최소 샘플 설계 — **동시 송수신이 되는가** (굽기 전 · 설계만)

> **목표**: 초당 960자를 **송신하면서 동시에 수신**해서 **양쪽 다 손실 0** 인 최소 스케치.
> **기존 프로토콜·게이트·큐를 옮기지 않는다.** 가장 단순한 것부터.

---

## 0. ✅ 근본 원인 — **내 눈으로 확인했다**

`~/Library/Arduino15/…/avr/1.8.8/libraries/SoftwareSerial/SoftwareSerial.cpp`

```c
123: void SoftwareSerial::recv()          // 수신 본체
219: inline void SoftwareSerial::handle_interrupt()   // → recv()
230:   SoftwareSerial::handle_interrupt();            // PCINT 핸들러에서만 불린다
436:   cli();            // turn off interrupts for a clean txmit
464:   SREG = oldSREG;   // turn interrupts back on
```

> ### **송신하는 동안 인터럽트를 끄는데, 수신은 그 인터럽트로만 받는다.**
> ### **→ 송신 중 수신이 *원리적으로* 불가능하다.** 우연도 타이밍도 아니다.

**9600bps 에서 한 바이트 = 10비트 / 9600 = 약 1.042ms.** 그동안 우리는 **완전히 귀머거리**다.
한 주기에 우리가 쓰는 바이트: `AT+CIPSEND=42\r\n`(15) + 페이로드(43) ≈ **58바이트 ≈ 60ms.**

### 🔑 0.1 이것이 우리가 센 **12,920건을 정확히 설명한다**

원장 §8.2-9 의 ②(첫 바이트만 손상, **12,920건**)는 이렇게 난다:

```
우리가 페이로드를 쓴다 → ESP 는 받는 즉시 되돌려 보내기 시작한다
                       → 그런데 우리는 아직 쓰는 중이라 cli() 로 귀가 닫혀 있다
                       → 쓰기가 끝나 귀가 열리는 순간, 이미 진행 중인 바이트의 **중간**부터 샘플링한다
                       → 시작 비트를 한 비트 늦게 잡는다 → 값이 1비트 왼쪽으로 밀린다
```
**실측이 정확히 그 모양이다: `S`(0x53) → `\xA6`(0xA6) = `0x53 << 1`.**

> ### **`S`→`\xA6` 이 "정확히 1비트 시프트"인 것이 이 기전의 지문이다.**
> **12,920건이 전부 첫 바이트에서 멈춘 것**도 설명된다 — 그 뒤로는 귀가 열려 있어 정상 수신된다.

★ **오늘 쫓은 것들이 이 하나의 증상이었다**: `+IPD` 깨짐 · `busy` 폭풍 · "ESP 리셋"의 상당수 ·
하행 착지 타이밍 · ②③ 비트 손상. **그 위에 게이트·큐·상한·창 맞추기를 쌓고 있었다.**

## 1. 🔑 설계 판단 — **샘플에 ESP 를 넣지 않는다**

물어야 할 것은 **"이 MCU 가 동시 송수신을 손실 없이 하는가"** 다.
**ESP 를 끼우면 변수가 넷 는다**(ESP 펌웨어 · WiFi · 전원 · AT 프로토콜).

> **최소 재현은 변수를 하나로 줄이는 것이다.** ESP 는 그 다음이다.

### 시험 상대는 **맥이다. USB 로 이미 연결돼 있다**

```
Uno 하드웨어 UART(핀 0/1) ──USB── 맥
   양쪽이 동시에 번호 붙은 줄을 흘려보내고, 양쪽이 각자 유실을 센다
```

✅ **배선 변경 0. 사용자 개입 0.** ESP 는 핀 8/7 에 그대로 있고 이 시험에 안 쓰인다.

## 2. 🔑 실패 팔은 **이미 측정돼 있다 — 다시 만들 필요가 없다**

루트 요구 4번(*"실패도 보여야 한다"*)에 대한 답:

> ### **SoftwareSerial 팔의 자료가 이미 있다: A 창의 12,920건이다.**
> **같은 장비 · 같은 배선 · 실기 · 대규모.** 새로 만들면 오히려 표본이 작아진다.

| 팔 | 자료 | 결과 |
|---|---|---|
| **SoftwareSerial**(반이중) | A 창 실측 12,920건 | **자기 송신 직후 첫 바이트가 100% 가까이 깨진다** |
| **하드웨어 UART**(전이중) | **이 샘플이 만든다** | ? |

⚠ **두 팔은 조건이 다르다**(상대·보율·부하). **그러므로 "손실률 비교"가 아니라
"구조적으로 되는가/안 되는가"만 본다.** 숫자를 나란히 놓지 마라 — §5.5.

## 3. 샘플이 증명해야 하는 것

| # | 무엇 | 어떻게 |
|---|---|---|
| 1 | **송신하면서 동시에 수신** | 양방향을 **쉬지 않고** 흘린다. 한쪽씩이 아니다 |
| 2 | **초당 960자 지속** | 순간이 아니라 **분 단위 유지**. 초당 실적을 찍는다 |
| 3 | **스스로 검증** | 줄마다 **일련번호 + 체크섬**. 번호 건너뜀 = 유실, 체크섬 불일치 = 손상 |
| 4 | **실패를 구별** | **유실**과 **손상**을 따로 센다 — 같은 칸에 넣으면 기전을 못 가른다 |

**출력(양쪽 동일 형식):**
```
[FD] tx=<보낸 줄> rx=<받은 줄> gap=<번호 건너뜀> bad=<체크섬 불일치> rate=<초당 문자>
```

⚠ **`gap` 과 `bad` 를 합치지 마라.** 유실은 "인터럽트가 꺼져 못 받은 것", 손상은 "받았는데 깨진 것"이다.
**오늘 ②③ 을 가르는 데 쓴 그 구분이 여기서도 필요하다.**

## 4. ⚠ 미리 적어 두는 제약과 위험

### 4.1 하드웨어 UART 의 수신 버퍼는 **64바이트**다

ATmega328P 의 `HardwareSerial` 기본 RX 버퍼가 64바이트다. **960자/초면 1자당 약 1ms** 이므로
**루프가 64ms 안에 한 바퀴 돌지 못하면 버퍼가 넘친다.**
→ **샘플의 루프는 아무것도 블록하면 안 된다.** 넘침도 세어라(`Serial.available()` 이 63 이상인 순간).

### 4.2 🔴 운영으로 옮길 때 — **핀 0/1 은 USB 업로드와 공유다**

**샘플에는 해당 없다**(ESP 를 안 쓴다). 그러나 **나중에 ESP 를 하드웨어 UART 로 옮기면:**

> **업로드 중 핀 0/1 이 USB 와 충돌한다. 굽는 동안 ESP 를 분리해야 할 수 있다.**
> **그것은 실물 개입이고 사용자 손이 필요하다** — `BURN-CHECKLIST` 에 절차를 미리 넣어야 한다.

⚠ **그리고 더 큰 문제**: ESP 가 0/1 을 쓰면 **진단 출력이 갈 곳이 없다.**
USB 탭이 보는 것은 ESP 트래픽이 되고, **monitor 의 관측 체계가 통째로 바뀐다.**
→ **이건 샘플 다음 단계의 결정이다. 지금 정하지 않는다.** 다만 **공짜가 아니라는 것**을 적어 둔다.

### 4.3 굽는 비용

**샘플을 구우면 창4 가 끝나고 주차 펌웨어가 칩에서 사라진다.** 되돌리려면 다시 구워야 한다.
**시연 일정과 겹치는지는 루트가 안다.** 나는 굽지 않는다.

## 5. 사용자 질문 — **"상행은 1초 제어가 있는데 하행은 없는가"**

**맞다. 실재하는 비대칭이다.**

```
상행: 1Hz 로 페이싱된다 (HEARTBEAT_MS)
하행: 서버가 아무 때나 쏜다 — 장치 쪽에 흐름 제어가 없다
```

⚠ **전이중이 되면 성격이 달라지지만 사라지지는 않는다:**
- 반이중에서는 **"우리가 말할 때 들리지 않는다"** → 충돌이 곧 유실
- 전이중에서는 **"들리기는 한다"** → 남는 문제는 **버퍼 넘침과 처리 속도**(§4.1)

> **그러므로 새 설계에서도 하행 페이싱은 답해야 할 항목으로 남는다.** 다만 **급이 내려간다** —
> 유실을 막는 필수 장치에서 **혼잡을 다루는 선택지**로 바뀐다.
