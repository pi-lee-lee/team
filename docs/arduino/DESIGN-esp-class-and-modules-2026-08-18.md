## 1. ESP 클래스 — `init` · `read` · `write` · `reset`

**사용자 지시는 셋(`init`/`read`/`write`)이었고, 내가 넷을 제안해 채택됐다**(이름 `reset` 은 사용자 결정).

### 1.1 왜 셋으로는 안 되나 — ✅ 확정 (소스)

`netTick()` 이 하는 일은 **시간이 지나며 혼자 진행하는 상태기계**다:
`CIFSR → CIPMUX → CIPSTART → 실패 → CWJAP 부터 다시`, 그리고 리셋 계단(`ladderFail`).

> **읽는 것도 쓰는 것도 아니다. `read()` 안에 넣으면 이름이 거짓이 되고,
> 읽을 것이 없을 때 `return` 하면 사다리가 멈춘다.**

### 1.2 경계 표

| 함수 | 하는 일 | 지금 코드의 어디 |
|---|---|---|
| **`init()`** | UART 를 열고 **부팅 사다리를 시작만** 한다 | `wifi.begin()` + `netStep` 초기화 |
| **`read()`** | ESP 가 보낸 것을 꺼내 줄로 조립하고 처리 | `pumpSerialRaw` → `feedRxChar` → `handleLine` |
| **`write()`** | 한 거래를 내보낸다. **3단 게이트·`busy` 대응·프롬프트 대기가 여기 산다** | `sendPayload` |
| **`reset()`** | **링크 상태를 유지한다** — 안 서 있으면 세우고, 오래 서 있었으면 방어를 낮춘다 | `netTick` |

### 1.3 ⚠ `reset()` 의 정의를 좁게 쓰지 마라 — ✅ 확정 (소스)

*"링크가 죽었을 때 세운다"* 로만 적으면 **온라인 경로의 일이 갈 곳을 잃는다:**

```c
// client.ino:2602  netTick()
if (netOnline) {
  if (30초 연속 온라인) { rung = RUNG_MEASURE; rungFails = 0; }   // ← 방어 수준을 낮춘다
  return;
}
```
> ### **이 일은 "세우는 것"이 아니라 "안 세워도 된다는 판정"이다.**
> **그래서 `netTick` 이 `tick` 이었다 — 온라인/오프라인 양쪽에 할 일이 있다.**

⚠ **사라지면 사다리가 영원히 높은 단에 머물러 다음 사고 때 4단(하드리셋)부터 시작한다.**
증상은 *"왜 갑자기 ESP 를 리셋하지?"* 이고 원인은 안 보인다.

★ **일반화**: 함수를 쪼갤 때 **"오프라인일 때 하는 일"만 보지 말고 "온라인일 때 하는 일"도 세어라.**
**조기 반환 앞의 코드는 눈에 안 띈다.**

### 1.4 `init()` 이 돌려줄 수 있는 것 — ⚠ 거의 없다

- 사다리는 약 12초 걸리고 **실패할 수 있다.** `init` 에서 막으면 **WiFi 없는 자리에서 영영 `setup` 을 못 나온다.**
- 🔴 **모듈이 여러 장치에 흩어지므로**(사용자 지시 7) **한 대가 WiFi 를 못 잡아도 나머지가 돌아야 하고,
  그 한 대도 로컬 센서는 계속 읽어야 한다.** **링크가 없다고 물리 세계가 멈추지 않는다.**
- ⚠ **`init` 이 진짜로 아는 것은 "UART 를 열었다"뿐이다.** 부팅 사다리 1단(`AT+RST`)의 응답은
  비동기라 `setup` 에서는 아직 안 왔다. **그 이상을 반환값에 담으면 거짓이 된다.**
- ✅ 반환값을 둔다면 **"모듈 기동 실패(하드웨어)"와 "아직 링크 없음(정상)"을 갈라라.**
  합치면 호출부가 정상 상태를 오류로 읽는다.

## 2. 🔴 슬롯 규율은 **ESP 클래스와 다른 축이다** (측정이 추가한 항목)

**`cntTick`(`[CNT]` 진단 출력)이 넷 중 어디 사는가** — 루트가 명세에 넣으라고 한 항목이다.

### 2.1 답: **ESP 클래스 밖이다. 그런데 슬롯 규율 안이다** — ✅ 확정 (실측)

```
[CNT] 는 하드웨어 Serial(USB)로 나간다. ESP 와 한 바이트도 주고받지 않는다
  → ESP 클래스의 일이 아니다
그런데 그것이 60초마다 하행 프레임 하나를 깼다 (창 B 5 · C 4 · D 3, 전부 시각 정합)
  → 슬롯 규율의 대상이다
```

**기전**: `[CNT]` 약 142B, 하드웨어 UART TX 링버퍼 64B → 넘치는 78B 가 **블로킹**하고,
그동안 `pumpSerialRaw()` 가 안 돌아 **도착 중인 하행이 SoftwareSerial 링버퍼에서 사라진다.**
✅ **슬롯에 묶어 고쳤다**(`slot6`): 하행 256건 도착에 **파괴 0**.

### 2.2 ★ 그래서 규율의 정의가 넓어진다

> ### ❌ ~~"ESP UART 를 쓰는 것"~~ → ✅ **"loop 를 막는 모든 것"**
>
> **프레임 송신만이 아니라 진단 출력·계수기 출력·긴 계산이 전부 대상이다.**
> **지금까지 "송신"을 프로토콜 프레임으로만 좁게 봤다.**

### 2.3 두 축은 직교한다 — 명세에 이렇게 둔다

| | ESP 클래스 (축 1) | 슬롯 규율 (축 2) |
|---|---|---|
| 묻는 것 | **ESP 와 어떻게 말하는가** | **언제 loop 를 막아도 되는가** |
| `write()` | ✅ 산다 | ✅ 송신 창에서만 |
| `read()` | ✅ 산다 | 제약 없음(읽기는 안 막는다) |
| `reset()` | ✅ 산다 | ⚠ **미검토** — 사다리가 AT 를 쏘므로 대상일 가능성이 높다(🔮) |
| **`[CNT]` 등 진단 출력** | ❌ **밖이다** | 🔴 **안이다** — 이번에 그것으로 데였다 |

⚠ **`reset()` 의 사다리 명령(`AT+CWJAP` 등)이 슬롯 규율 대상인지 안 쟀다.**
🔮 **추론**: 대상일 것이다 — 그것도 UART 를 점유한다. **다만 오프라인 구간이라 하행이 없어
겹칠 대상이 없을 가능성이 높다.** ⚠ **재 봐야 안다.**

## 3. 자리·모듈 유동화

### 3.1 지금 구조 — ✅ 확정 (소스)

```c
SLOT_N = 10                     // 컴파일 상수
SLOT_PIN[SLOT_N] PROGMEM        // 자리 → 핀 고정 표
srcReal (uint16_t 비트마스크)    // 자리마다 "실물인가 시뮬인가" 1비트
```
**자리가 전부 같은 종류(주차 센서)이고 개수가 고정이다.**

### 3.2 바꿀 것 — **장치는 `name → pin` 과 `kind` 만 안다**

```
모듈 = { name(노드 안에서만 유효) , kind , pin }
장치는 "구역"을 모른다.  zone ← [module…] 조립은 서버가 한다
```

> ### 🔴 **장치가 구역을 알게 만들면 배선이 바뀔 때마다 펌웨어를 다시 굽는다.**
> **`SERVER_IP` 를 펌웨어에 박아 두고 IP 가 바뀌어 링크가 조용히 죽은 것(원장 §5.7)과 같은 형태다.**

- **개수 가변**: `SLOT_N` 고정을 버리고 **등록한 `n`** 이 폭이다.
- **`kind` 를 장치가 안다** — 차단봉·안내등은 **출력**, 센서는 **입력**이라 `pinMode` 가 갈린다.
  ✅ 그래서 **전선에 실을 수 있다**(socket 과 합의).
- 🔴 **출력 모듈도 상태 비트열에 넣는다** — **ACK 은 "받았다"이지 "됐다"가 아니다.**
  **명령이 실제로 반영됐는지 확인하는 유일한 경로가 상태 비트다.**
  _(web 이 `거짓 완료`로 이름 붙인 것과 같은 문제를 독립적으로 만났다.)_
- ⚠ **출력 핀은 되읽기가 없으면 장치도 조작 실패를 모른다** — 상태 비트는 **"우리가 그렇게 썼다"**
  까지이고 **"물리적으로 그렇게 됐다"가 아니다.** 그 한계를 계약에 적어야 한다.

### 3.3 RAM 제약 — ✅ 확정 (실측)

**실측 최저 여유 782B**(정적값 아님). `n` 이 커지면 모듈 표가 그만큼 는다.
⚠ **`n` 상한을 지금 정하지 마라** — socket 이 전선에서 `n ≤ 15` 를 냈고(프레임 고정부 33B 기준),
**RAM 쪽 상한은 모듈 구조체 크기가 정해진 뒤에 계산할 수 있다.** 🔮 15 개면 여유가 충분할 것이다
(구조체가 4~6B 면 90B 미만) — ⚠ **미측정.**

## 4. 전선 예산 · 등록 규약 — **socket 명세를 따른다**

📄 `docs/net/DESIGN-bridge-node-module-zone.md` §5 (**여기 복사하지 않는다**)

내가 합의에 낸 것만 요약하면: `D`(등록)/`Q`(질의) 문자 · **`n` 이 종료 조건**(마지막 줄 표시 불필요) ·
`REG_TIMEOUT = 3 × 슬롯주기`(값이 아니라 식으로) · `Q` 3회 상한 · **비트열 순서 = 등록 순서**.

### 4.1 ⚠ 장치는 등록 성공을 모른다 — 계약에 명시할 것

**등록에 ACK 이 없다.** 서버가 `Q` 3회 뒤 포기해도 장치는 모른다.
**그래도 (b)로 간다**: 장치가 알아도 **할 수 있는 일이 없다**(이미 보냈고, `Q` 에 반응하는 것이 유일한 행동).
🔑 **그리고 사람은 안다** — 서버가 `node_unregistered` 로 굳히고 화면이 `⏱` 로 그린다.
**`거짓 완료`와 다른 형태다: 거기선 사람이 잘못 알고, 여기선 사람이 정확히 안다.**

## 5. 🔴 미결 — **실측이 필요하고 지금 못 잰다**

### 5.1 노드 수 상한 — ⚠ 계산으로 못 닫는다

**WiFi 는 공유 매체다.** 슬롯은 **장치 내부 UART 반이중**만 없앤다(✅ 확정).
N 이 늘면 무선 경합이 각 노드의 `S` 주기를 흔들고, **그러면 서버의 창 계산도 같이 흔들린다.**

**재려면**: 노드를 늘려 가며 **`[SLOT] due=` 분포**와 **서버의 `왕복 최대`** 를 본다.
🔴 **지금 못 잰다 — 보드가 한 대뿐이다.**

### 5.2 `cap` 이 노드마다 다를 수 있는가 — ⚠ 미측정

🔮 **추론**: 다를 것이다. `cap` 은 **창 폭 − 왕복** 에서 나오는데 **왕복이 노드마다 다르다**
(거리·간섭·그 노드의 `due`). ⚠ **다만 한 대로는 분산을 볼 수 없다.**
**재려면**: 두 대 이상에서 같은 주입을 돌리고 노드별 `왕복 최대` 를 비교한다.

### 5.3 `reset()` 이 슬롯 규율 대상인가 — ⚠ 미측정 (§2.3)

### 5.4 하행 동시성 — **사용자 결정이 먼저다**

두 모듈이 다른 장치면 **명령이 최대 1.2초 어긋난다**(✅ 슬롯 규칙에서 바로 따라 나온다).
**1.2초를 허용하면 아무것도 안 해도 된다.** 안 되면 **명령에 실행 시각을 실어야 하고
장치 간 시계 동기가 필요해진다**(지금 없다 — `millis()` 원점이 장치마다 다르다).
🔑 **그 답을 먼저 받는 것이 싸다** — 동기를 먼저 설계했다가 "그 정도는 괜찮다"가 오면 전부 버려진다.

## 6. 🔴 배출률은 **장치가 선언한다** — 파생 값은 원본을 가진 쪽이 계산한다 (2026-08-18 추가)

**서버의 하행 건수 상한 `N` 은 장치의 ACK 배출률 `D` 에서 유도된다:**
```
k = N ÷ (D − N)        (한 슬롯 놓쳤을 때 회복에 걸리는 슬롯 수 · socket 유도)
N=4, D=6 → k=2 (2400ms)   ✅ 마감 4800ms 의 절반
N=4, D=5 → k=4 (4800ms)   🔴 **마감과 정확히 같다** — 놓친 순간 큐의 건이 그대로 만료된다
```

### 6.1 `D` 는 상수가 아니라 함수다 — ✅ 확정 (형식에서 유도)

```
D = (BATCH_CAP − S_worst − 1) ÷ (ACK_worst + 1)
```
**세 입력이 전부 arduino 도메인 값이다.** → 🔴 **서버가 이것을 계산하면 내 값의 사본이 생기고,
내가 하나 고칠 때 두 곳이 갈린다.**

> ### ✅ **채택: 등록(`D` 프레임)에 `drain` 을 실어 장치가 선언한다.**
> **서버는 그 값을 유도식에만 넣는다.** `BATCH_CAP` 을 바꾸든 `n` 이 늘든 **arduino 한 곳만 고친다.**

⚠ socket 이 **감시만** 넣었다: `S` 실제 길이가 60B 를 넘으면 *"배출 6 의 전제가 깨졌다"* 고 경고하되
**새 배출률은 계산하지 않는다.** **사본을 안 만들면서 전제 붕괴를 잡는 형태다.**

### 🔴 6.2 `BATCH_CAP` 을 올려서 `D` 를 유지하는 것은 **안 된다**

`n=15` 에서 `D=6` 을 유지하려면 `BATCH_CAP ≥ 172B` 가 필요하다. **RAM 은 12B 뿐이라 싸 보인다.**
**그런데 방향이 반대다:**
```
창 F 실측 : tx 150B 에서 stuck=3 (SEND OK 가 T2 8초 초과)
            150B 전송 자체는 156ms 이므로 **전송 시간이 원인이 아니다**
```
> ### **이미 150B 에서 `SEND OK` 가 병리 구간(§8.6-1: 2~3초)으로 밀렸다.**
> ### **`BATCH_CAP` 을 올리는 것은 §12.5 의 되먹임 고리를 키우는 방향이다.**

### 🔑 6.3 대신 — **비트열 인코딩이 이 문제를 통째로 없앤다** (🔮 추론 · 개정 범위)

지금 자리 비트열은 **10진 문자 1칸당 1비트**다(`0110001011` = 10자). **hex 면 4비트당 1자:**

| | 10진 | **hex** |
|---|---|---|
| `n=10` | S 60B → D **6** | S 39B → D **7** |
| `n=15` | S 75B → D **5** | S 42B → D **7** |

> ### **hex 로 실으면 `n=15` 에서도 `D=7` 이다** — `BATCH_CAP` 을 안 건드리고,
> **배치가 오히려 작아져 되먹임 고리도 같이 준다.**

⚠ **프로토콜 변경이라 socket·web·monitor 가 다 걸린다.** **개정 범위이고 지금 하는 것이 아니다.**
다만 *"`D=5` 를 받아들이고 유입을 3 으로 내린다"* 보다 싸다 — **사용자 큐 깊이를 안 깎는다.**
⚠ ✅확정은 위 표의 **산술**까지이고, **실기에서 `D=7` 이 나오는지는 미측정**이다.
