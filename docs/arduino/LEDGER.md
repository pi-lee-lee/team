# arduino 도메인 원장 (LEDGER)

> **기동하면 이 파일부터 읽어라.** 세션은 죽지만 원장은 남는다.
>
> **여기 적는 것**: 이 도메인에서 **시간이 지나도 참인 것** — 실측으로 확정된 상수·형식·임계값과
> 그 근거, 틀린 것으로 밝혀진 통념과 왜 틀렸는지, 다음 사람이 넘어질 함정.
>
> **여기 안 적는 것**: 그날의 상태·진행·인수인계. 그건 날짜 붙은 별도 파일이다.
> - 지금 칩에 무엇이 올라가 있나 · 개입 이력 → **`arduino/INTERVENTIONS.md`**
> - 그날의 인수인계 → `docs/arduino/handoff-<날짜>.md`
>
> **규칙**: ① 근거 없이 적지 마라(실측인지 추정인지 드러내라) ② 조건부 사실은 **조건을 같이** 적어라
> ③ 틀린 항목은 **지우지 말고 취소선 + 사유** ④ append 가 기본.

## 🔴 0.0 이 도메인의 제1 규칙 — **칩에 새기는 것은 문서에 적는 것과 값이 다르다**

> ### **숫자를 펌웨어에 새기는 것은 문서에 적는 것보다 되돌리기 어렵다 — 굽기가 그 자체로 관측 경계다.**

문서 오류는 고치면 끝이다. **칩에 박힌 것은 다시 구워야 지워지고, 그 굽기가 관측 창을 하나 더 깬다.**
같은 오류라도 **어디에 있느냐에 따라 비용이 다르다.**

**2026-08-17 실제 사례 (하마터면):**
루트가 준 `drop=15` 를 **확인 없이** `linkDrops` 선언 주석에 적었고 **그대로 구울 참**이었다.
monitor 가 *"굽기 전에 닫자 — 구우면 이 칩 상태는 사라진다"* 고 막아서 잡혔다.
전수 확인 결과 **그 수는 어느 로그에도 없었다**(창3 `[CNT]` 442줄에서 `drop` 은 0 또는 1 뿐).
출처는 요약 표의 **`[TX-DROP]` 줄 수**였고 펌웨어의 `[CNT] drop=`(=`linkDrops`)이 아니었다.

> ### ⚠ **루트가 준 숫자라고 확인이 면제되지 않는다.**
> 이 오류의 출처는 루트였고, 나는 **출처를 신뢰해서 검산을 건너뛰었다.**
> **위에서 내려온 값일수록 여러 문서로 빠르게 퍼지므로 검산 가치가 더 크다.**

**그래서 굽기 전 마지막 관문을 하나 더 둔다** (`BURN-CHECKLIST` 0단계와 함께):

> **이번 굽기에 들어가는 *숫자와 사실 주장*을 내가 직접 확인했는가?**
> 주석·로그 문구·기본값 전부다. **남에게 들은 값이 하나라도 있으면 그 자리에서 원문을 열어라.**

## 1. 링크 계층 — 오늘 뒤집힌 것이 가장 많은 영역

### 1.1 `send_fail_x3` 이 세는 것은 **링크 상태가 아니다** ★ 코드로 확정

세는 것은 **`AT+CIPSEND` 뒤 `>` 프롬프트를 제한시간 안에 봤는가, 그것 하나뿐**이다.
ESP 가 보내는 `SEND FAIL`·`busy`·`ERROR` 는 **로그만 남기고 세지 않는다**
(`link is not valid` 만 예외). 이중 계수를 피하려는 의도적 설계다.

> **그러므로 "3회 연속 실패"는 "링크가 죽었다"가 아니라 "우리가 세 번 제때 못 봤다"이다.**
> 소스도 이 판정을 **추정**이라고 명시한다 — 링크가 살아 있었다면 재시도에
> `ALREADY CONNECTED` 가 와서 그대로 복귀한다.

**연속이다. 누적이 아니다.** 송신이 한 번 성공하면 카운터가 0 으로 리셋된다.

### 1.2 `busy` 는 **ESP 의 명시적 신호**다 — 침묵과 다르다 ★ 실측

- `busy p...` = 앞 **명령**을 처리 중 · `busy s...` = 앞 **전송**을 아직 보내는 중
- 뜻은 **"지금 말고 나중에"** 이지 "고장"이 아니다. **기다렸다 재시도할 것**이다.
- ⚠ 기존 `busy` 처리 코드는 `if (!netOnline && ...)` 안에 있어 **오프라인 접속 사다리에서만**
  돈다. **온라인으로 프레임을 보내는 동안에는 그 경로가 아예 실행되지 않았다.**

**2026-08-16 실측 로그**:
```
[AT] "AT+CIPSEND=38"
[AT] "busy s..."        ← 명령 자체가 거부됐다. '>' 는 오지 않는다
```

### 1.3 `SEND OK` 를 **아무도 안 본다** ★ 코드로 확정 (두 계열 모두)

`SEND OK` 는 ESP 가 **"앞 전송이 끝났다"** 고 알려주는 신호인데 처리 코드가 없다.
대신 `SEND_GAP_MS = 80` 이라는 **고정 추측값**을 쓴다.

> **그 80ms 는 "우리가 쓰기를 끝낸 시점"부터 재는 것이지 "ESP 가 WiFi 전송을 마친 시점"이
> 아니다.** 망이 느리면 ESP 는 80ms 뒤에도 여전히 보내는 중이고 → `busy s...` 가 난다.
> **`busy s...` 는 이 추측이 틀린 순간에 나는 것이다.**

`SEND_GAP_MS` 자체는 원래 **`busy p...` 회피용**이므로 없애면 안 된다(하한으로 유지).

### 1.4 프롬프트 놓침에는 **두 갈래**가 있고 대응이 다르다 ★ 실측

| 갈래 | ESP 상태 | 더미 `#`×N 을 쓰면 | 서버 |
|---|---|---|---|
| **(a) `>` 는 왔는데 우리가 못 봄** | **데이터 모드**(N바이트 대기) | 소켓으로 나간다 — **채워야 한다** | 한 줄 받고 버림 |
| **(b) `>` 가 애초에 안 옴**(busy/ERROR 거부) | **명령 모드** | **AT 해석기가 먹는다 — 넣으면 안 된다** | 아무것도 안 옴 |

**가르는 법**: 프롬프트 놓침 직후의 `[AT] "..."` 를 봐라 — `SEND OK` 면 (a), `Error`/`busy` 면 (b).

> ## ❌ 1.4-1 **정정 (2026-08-16 밤) — ~~"에코로 돌아온 것이 명령 모드의 증거"~~ 는 틀렸다**
>
> 이 자리에 *"`[AT] "#####…"` 가 **에코로 되돌아왔다**"* 를 (b) 의 증거로 적어 뒀었다.
> **에코는 (a)/(b) 를 가르지 못한다. 정보가 없다.**
>
> **반증**: **정상 전송에서도 페이로드가 그대로 에코된다.** 로그가 매 초 그렇게 찍는다 —
> ```
> [AT] "AT+CIPSEND=42"                        ← 명령 에코
> [AT] "\xA6,12382,...,P1,39" (41)            ← 페이로드 에코 · 데이터 모드인데도 에코된다
> [AT] "SEND OK"
> ```
> 즉 ESP 는 **데이터 모드에서도 우리가 쓴 바이트를 되돌려 준다.** `#####` 가 돌아온 것은
> **"우리가 뭔가 썼다"는 뜻일 뿐** 모드에 대해 아무 말도 하지 않는다.
>
> ### **가르는 것은 `SEND OK` 가 오느냐 하나뿐이다.**
>
> ⚠ 그리고 **`SEND OK` 는 늦게 올 수 있다** — 20:54:02 의 CIPSEND 에 대한 `SEND OK` 가
> **:08 에** 왔다(약 6초). **직후 두세 줄만 보고 "없다"고 판정하면 (a) 를 (b) 로 오독한다.**
> 판정하려면 **그 CIPSEND 가 해소될 때까지** 따라가야 한다.
>
> **결론이 아니라 근거가 틀렸다.** 앞서 (b) 로 분류한 건들 중 일부는 실제로 (a) 일 수 있다 —
> 특히 **뒤늦은 `SEND OK` 를 못 보고 넘긴 경우**. 재판정하려면 위 규칙으로 다시 세라.

> ⚠ **판정 근거로 "서버 카운터가 0" 을 쓰지 마라.** 서버에는 **승격 전 소켓의 줄을 어느 카운터도
> 올리지 않고 버리는 경로**가 있다(`server.cpp:2156-2176`). 0 은 세 원인 모두와 양립한다.
> **가른 것은 장치측 AT 에코다.**

### 1.5 서버가 없으면 **백오프 없이 0.90초 주기로 재시도**한다 ★ 실측 (설계된 거동)

`CIFSR → CIPMUX → CIPSTART → ERROR/Unlink` 를 약 0.90초 주기로 쉬지 않고 반복하고
**재시도 간격이 늘지 않는다.**

> **이것은 결함이 아니다. 집계에서 "재연결 폭주 = 장치 이상"으로 세면 안 된다.**
> 부수 효과: 서버를 다시 띄우면 **1초 안에 연결 시도가 들어온다.**

### 1.6 프레임 형식과 `uptime` 의 의미 ★ 두 계열 동일 (코드 확인)

```
S,<seq>,<occupied>,<reserved>,<uptime>,<DEVICE_ID>[,<tmask>]
```

**`uptime` 은 `millis()/1000`, 즉 Uno 자신의 가동시간이다. ESP 것이 아니다.**

> **그러므로 uptime 붕괴 = Uno(호스트 MCU) 재부팅**이다.
> **ESP 만 재접속한 경우에는 uptime 이 끊기지 않고 계속 증가한다.**
> 이 둘은 원인 계층이 전혀 다르므로 집계에서 반드시 구분해야 한다.

### 1.7 `+IPD` 는 **연결 id 없는 단일 인자 형식**이다 ★ 실측 — ⚠ **조건부**

```
[AT] "+IPD,19:R,1,A1,00000000,13"     →  +IPD,<n>:
```

**⚠ 조건: `CIPMUX=0`(단일 연결)로 운용하는 지금 구성에서만 참이다.**
부팅 사다리가 `AT+CIPMUX=0` 을 넣기 때문이다.

> **`CIPMUX=1`(멀티 연결)로 바꾸면 `+IPD,<id>,<n>:` 이 되어 10자가 되고,
> 프레임 63자와 합쳐 73바이트가 된다.** `RX_CAP=96` 은 그 경우까지 덮는 여유이므로 **줄이지 마라.**

## 2. 리셋·전원

### 2.1 **포트를 여는 것 자체가 리셋이다** ★ 회로 사실

Uno 는 USB 시리얼의 **DTR 이 100nF 커패시터를 거쳐 RESET 에 직결**돼 있다(자동 리셋 회로).
`screen`·시리얼 모니터·`pyserial`·`avrdude` 등 **포트를 여는 모든 행위가 재부팅을 일으킨다.**

> **"읽기만 했다"도 개입이다.** 보드를 만지기 전에 `arduino/INTERVENTIONS.md` 에 먼저 적어라.

### 2.2 리셋 **원인**은 소프트웨어로 알 수 없다 ★ 확정 (디스어셈블 + 부팅 로그)

**부트로더가 `MCUSR` 을 앱보다 먼저 지운다.** 장치 부팅 로그가 스스로 그렇게 찍는다:
```
[BOOT] 리셋 원인: 불명 (부트로더가 MCUSR 을 지우고 넘어왔다)
```
> **펌웨어를 고쳐서 리셋 원인을 찍게 만드는 방향은 막다른 길이다.** 외부 관측으로만 좁힌다.

### 2.3 부팅 **횟수**는 EEPROM 에 있다 ★ 코드 확인

주소 2 = `bootCount`, 주소 0 = 매직 `0xB007`. **전원이 빠져도 남는다** —
로그 공백 구간의 재부팅을 소급 검증할 유일한 수단이다.
⚠ **avrdude 로 읽는 행위 자체가 리셋이고 포트를 점유한다.** 관측자와 시각을 맞춰라.

### 2.4 워치독은 **동작하지 않는다** — 단, "코드가 없다"는 뜻은 아니다 ✏️ **2026-08-16 정정**

| 계열 | 워치독 코드 | 실제 동작 |
|---|---|---|
| `arduino/client/EspLink.h` | **없다**(검색 0건) | 해당 없음 |
| `조별과제샘플/client.ino` (**지금 칩**) | **있다** — `#include <avr/wdt.h>`, `wdt_enable(WDTO_8S)` | **꺼져 있다**: `ENABLE_WDT 0` 로 컴파일에서 빠지고, 부팅 시 `wdt_disable()` 을 **항상** 호출 |

> ✏️ **정정 사유**: 처음에 *"두 파일 다 검색해 0건"* 이라고 적었는데, 실제로 검색한 것은
> **EspLink 계열**이었다. 옛 계열에는 워치독 코드가 있다. **결론(동작하지 않는다)은 유지되지만
> 근거가 부정확했다.** — 호스트 테스트를 붙이다 `avr/wdt.h` 가 없어 빌드가 깨지면서 드러났다.
> **교훈: "검색해서 0건"이라고 쓸 때는 어느 파일을 검색했는지 같이 적어라.**

**부팅 로그가 실제 상태를 말해 준다**: `6단(워치독) 끔`.
`wdt_disable()` 이 조건부가 아닌 이유도 의도적이다 — 워치독 리셋으로 들어왔다면 WDT 가 켜진 채일
수 있어 **켜기 전부터 방어**하는 것이다.

> **그러므로 남는 리셋 원인은 브라운아웃(전원 강하) · 외부 리셋(DTR/리셋핀) · 전원 순단뿐이다.**

### 2.6 리셋 원인 **캡처 코드는 있다** — 다만 0 을 읽는다

`.init3` 섹션의 naked 함수(`earlyInitCapture`)가 `MCUSR` 을 `mcusrMirror`(`.noinit`)로 옮기고
부팅 로그에서 `PORF`·`EXTRF`·`BORF`·`WDRF` 로 해독한다.
**그런데 부트로더가 이미 지운 뒤라 실기에서는 항상 0 → `리셋 원인: 불명` 이 찍힌다**(§2.2).
> **코드가 있다고 값이 있는 게 아니다.** 이 경로를 "구현하면 된다"고 다시 제안하지 마라 — 이미 있다.

### 2.5 SoftwareSerial 은 **64바이트 버퍼 · 반이중**이다 ★ 라이브러리 사실

`_SS_MAX_RX_BUFF = 64`(`SoftwareSerial.h`). 그리고 **송신 중에는 수신을 못 한다.**

> 결과: **우리가 쓰는 동안 도착한 응답은 받을 수 없고**, 버퍼가 넘치면 바이트가 **조용히 사라져
> 두 줄이 한 줄로 붙는다.** 진단 출력이 많을수록 루프가 늦어져 이 위험이 커진다.

## 3. 타이밍

### 3.1 기동 창 ≈ **12초** (부팅 → 서버 등록) ★ 실측 2026-08-16, 3자 교차 확인

t0 = 리셋 해제 기준. 시리얼(서브초)·탭·서버 로그 세 관측이 같은 부팅에서 일치했다.

| 사건 | t0 기준 |
|---|---|
| 부트로더 → 스케치 시작 | 1.0s |
| 배너 `[PARKING NODE]` | 1.51s |
| `CWJAP OK` (WiFi 결합 완료) | 10.42s (결합 자체 5.0s) |
| IP 확보 | 10.77s |
| 첫 `CIPSTART` | 11.29s |
| **서버 수락** | **≈12s** |

- ⚠ **가장 크게 흔들리는 구간은 `CWJAP`(WiFi 결합)** 이다. 펌웨어는 최대 30초까지 기다린다.
- ~~옛 기준 36초~~ 는 **EspLink(nextgen) 판 특성**이라 옛 계열에는 **적용되지 않는다.**

### 3.4 🔴 송신 주기는 **1.000초가 아니라 약 1.113초다** ★ 2026-08-17 · 소스 확정 + 2도메인 실측

**`HEARTBEAT_MS = 1000` 인데 실제 주기가 11% 길다.** monitor 가 시리얼에서 잡고 루트가 서버
로그로 독립 재현했다(창3 국면1, 797프레임/886초 → **평균 1.1131s**).

#### 기전 — `delay()` 가 아니라 **타이머를 언제 다시 장전하는가**

```c
// client.ino:2432
bool heartbeatDue = (now - lastStatusAt >= HEARTBEAT_MS);
...
bool ok = sendStatus();        // :2478  ← 여기서 막힌다(블로킹)
lastStatusAt = millis();       // :2480  ← 🔴 보낸 **뒤에** 찍는다
```

> ### **주기 = `HEARTBEAT_MS` + 송신에 걸린 시간.** 오차가 매 주기 쌓이고 **스스로 교정되지 않는다.**
> `delay(1000)` 은 없지만 **구조가 같다.** 재장전이 `lastStatusAt += HEARTBEAT_MS` 였다면
> 평균이 정확히 1000ms 로 유지된다(위상 고정). 지금은 **"1초 쉬고 일한다"** 이지
> **"1초마다 일한다"** 가 아니다.

**113ms 는 어디서 오나** — 대부분 9600bps SoftwareSerial 의 물리 시간이다(계산값):

| 항목 | 시간 |
|---|---|
| `AT+CIPSEND=42\r\n` 16바이트 @9600 | **16.7ms** |
| 페이로드 43바이트 @9600 | **44.8ms** |
| `>` 프롬프트 대기 · `[AT]`·`[TX]` 진단 출력 · 루프 지연 | 나머지 |

#### ⚠ 3.4-1 **주기는 상수가 아니다** — 그래서 더 조심해야 한다

`1.113s` 를 새 상수로 박지 마라. **일한 시간이 더해지는 구조이므로 조건에 따라 변한다:**

- **`DEBUG` 값에 따라 다르다** — 진단 출력이 그 시간에 포함된다.
  🔴 **그러므로 `DEBUG=0` 빌드는 주기가 다르다.** 두 빌드의 프레임 간격을 같은 척도로 비교하지 마라(§5.5).
- **페이로드 길이에 따라 다르다**(`tmask` 유무 등) · **ESP 응답 속도에 따라 다르다**
- 재전송·`busy`·프롬프트 놓침이 끼면 그 주기는 더 길다

> ### **주기는 상수가 아니라 `빌드 · 페이로드 · ESP 응답 속도`의 함수다.**
> **`1.113` 을 새 상수로 박지 마라.** 그건 **`DEBUG=1` · 정상 전송 · 창3 국면1** 조건의 값이다.

**여기에 걸리는 것 셋 — 전부 CLAUDE.md "비교 전 확인" 3번(누가 만들었는가)의 사례다:**

1. 🔴 **두 빌드의 프레임 간격 통계를 같은 척도로 비교하면 안 된다.** 이름이 같아도 다른 지표다.
2. 🔴 **`8b63846` 의 `DEBUG=0` 시연 빌드는 맥놀이 무늬가 다르다.** 주기가 더 짧으므로
   `2s` 로 읽히는 간격이 **더 드물게, 다른 주기로** 나타난다.
   **시연 중에 프레임 간격을 보고 "장치가 멈췄다"를 판단하면 틀린다.**
3. 🔴 **서버 무프레임 판정 3500ms 의 "몇 프레임 분량인가"가 빌드마다 다르다.**

| 주기 | `3500ms` 안에 들어가는 프레임 |
|---|---|
| 1.000s (의도) | 3.5개 |
| **1.113s (`DEBUG=1` 실측)** | **3.14개** |

> ⚠ **이 여유는 생각보다 얇다.** `DEBUG=1` 에서는 **연속 3프레임을 놓치면 이미 마감에 닿는다.**
> "3.5초니까 3~4번은 견딘다"고 읽으면 안 된다 — **실제로는 3번이 상한이고 그마저 빠듯하다.**
> ★ 이 값을 손대라는 뜻이 아니다(§3.2 대로 마감 자체는 유지가 맞다).
> **"여유가 몇 프레임인가"를 인용할 때 빌드를 같이 적으라는 뜻이다.**

#### 🔑 3.4-2 이 사실이 **없던 고장을 만들어 보이게 했다** — 계측기 해상도의 함정

1초 해상도 로그로 1.113s 주기를 표본화하면 **약 9프레임마다 한 번 `2s` 간격으로 읽힌다**
(`1/(1.113−1) = 8.9`). 실측 분포가 정확히 그랬다: `1s` 702 · `2s` 92 · **`>=3s` 0**,
그리고 `2s` 사이 프레임 수가 **9개인 경우가 82%**.

> ### **우리가 보던 `>=2s` 11.45% 는 "장치가 멈춘 것"이 아니라 맥놀이(aliasing)였다.**
> 장치는 내내 안 멈췄다.

⚠ **이 부류는 지금까지 밟은 것들과 성격이 다르다.** 오늘 밤 다른 다섯 건은 **누군가 잘못
계산하거나 확인을 건너뛴 것**이었다. **이번엔 아무도 틀리지 않았다** — 계측기의 해상도가
자료를 그렇게 보이게 만들었다. **읽는 사람이 정직해도 속는다.**

> **그래서 규칙**: 간격 자료에서 이상을 보면 **먼저 "표본화 주기와 신호 주기가 가까운가"를 물어라.**
> 둘이 가까우면 맥놀이가 나고, **그 무늬는 고장과 구별되지 않는다.**
> 가르는 법은 **간격 사이의 개수를 세는 것**이다 — 맥놀이면 그 개수가 `1/(T−1)` 근처에 몰린다.

⚠ **A 창 자료에도 같은 맥놀이가 있었다. 새로 생긴 것이 아니라 줄곧 있었고 아무도 못 봤다.**
→ **"프레임 공백"을 근거로 쓴 과거 판정이 있으면 다시 봐라.**

#### 3.4-3 영향 점검 — 무엇이 틀렸고 무엇은 안 틀렸나

| | |
|---|---|
| **ms 단위 임계값 자체** | **안 틀렸다.** `TX_STALL_MS`·`SEND_OK_TIMEOUT_MS` 등은 `millis()` 로 재므로 주기와 무관하다 |
| **"N초 = N주기" 환산** | 🔴 **11% 틀렸다.** §6.2 의 `10초 ≈ 10회` → 실제 **9.0회** (정정 완료) |
| **`SEND_GAP_MS = 80`** | **영향 없다 — 애초에 이 경로에서 안 돈다.** 대기는 `millis() - lastSendEndAt < 80` 인데(L1427) 1Hz 정상 동작에서는 그 차가 약 1000ms 라 **한 번도 대기하지 않는다.** 연속 송신(하트비트 직후 디바운스 전송 등)에서만 작동한다 |

⚠ **고치지 않았다**(루트 지시: 확인만). 고치려면 재장전을 `lastStatusAt += HEARTBEAT_MS` 로 바꾸는
것인데 **거동 변경이라 굽기가 필요하고, 그러면 프레임 간격 통계의 기준선이 바뀐다.**
**더미 전략 수정과 같은 굽기에 묶어야 한다**(§6.3 변경은 하나씩).

### 3.2 서버 마감(`UNKNOWN_TIMEOUT_MS`)은 **기동 창과 무관하다** ★ 중요

**마감 시계는 부팅이 아니라 `accept` 에서 시작한다.** 장치는 WiFi·IP 를 **끝낸 뒤에야** TCP 를 열고,
`CONNECT` 직후 곧바로 첫 프레임을 보낸다. **그 앞 12초는 소켓이 존재하지도 않는 구간**이다.

실측(서버측 accept 131건): `accept → device_id 확정` **최대 1.0초, 7초 초과 0건.**

> **⚠ 그래도 마감을 1~2초까지 줄이지는 마라.** 정상 세션을 끊기 시작하고, 끊긴 장치는
> **0.90초 무백오프로 즉시 재접속**하므로 **서버가 "붙었다 끊기는 주기적 사이클"을 스스로 만든다.**
> 7초는 실측 최악(1.0초)의 7배이고 **그 여유가 이 함정과의 거리다.**

### 3.3 두 계열의 프롬프트 제한이 **7.5배 다르다** ★ 코드 확인

| 계열 | 프롬프트 대기 상한 |
|---|---|
| `조별과제샘플/client.ino` (옛 계열) | **300ms** (`PROMPT_TIMEOUT_MS`) |
| `arduino/client/EspLink.h` | **40ms** (`ESPLINK_PROMPT_MS`) |

## 4. 빌드·저장소

### 4.1 아두이노 스케치 폴더는 **그 안의 모든 `.c/.cpp/.h` 를 함께 컴파일한다** ★ 함정

**다른 도메인의 소스가 같은 폴더에 놓이면 빌드가 깨진다.** 그래서 스케치는
**전용 폴더**에 두어야 하고, 서버 파일 등이 예약된 폴더와 공유하면 안 된다.

### 4.2 **폴더명 == 스케치명** 규칙

`arduino-cli` 는 이를 요구한다. 어기면 `main file missing from sketch` 로 빌드 자체가 안 된다.
`조별과제샘플/client.ino` 가 이 규칙을 어기므로 **저장소 경로 그대로는 빌드되지 않는다** —
`/tmp` 등에 `client/client.ino` 로 복사해서 빌드해야 한다.

### 4.3 헤더는 **스케치 폴더 안에** 둔다

정식 아두이노 라이브러리로 만들면 `--libraries` 플래그나 설치가 필요해져
**"받아서 그대로 빌드"가 깨진다.** 소비자가 하나뿐이면 스케치 폴더 안이 정답이다.
⚠ **두 번째 스케치가 생기면 그때 라이브러리로 승격**해야 한다(사본이 둘이 되면 반드시 갈라진다).

### 4.4 실장 펌웨어는 **hex 바이트 대조로 증명할 수 있다** ★ 방법

`avrdude -U flash:r:` 로 덤프 → 소스를 같은 FQBN 으로 빌드 → **32768바이트 raw 로 파싱해 비교.**
Intel HEX 텍스트를 눈으로 비교하지 마라(레코드 배치가 달라도 내용은 같을 수 있다).
2026-08-16 에 이 방법으로 **차이 0바이트**를 확인해 칩과 커밋본의 동일성을 증명했다.

## 5. 함정 (다음 사람이 같은 곳에서 넘어질 자리)

### 5.1 `[LINK] closed reason` 은 **EspLink 전용 문자열**이다 ★ 실제로 당할 뻔했다

옛 계열 칩에서 이걸 세면 **0 이 나오고, 0 은 "끊김 없음"으로 읽힌다.**
옛 계열은 같은 사건에서 이렇게 찍는다:
```
[NET] 전송 3회 연속 실패 → 오프라인 전환. 낡은 소켓부터 닫는다(CIPCLOSE)
```
> **일반화: 계수하기 전에 "지금 칩의 펌웨어가 그 문자열을 찍는가"를 확인하라.**
> 없는 신호를 세면 0 이 나오고, **0 은 "없음"과 "못 셈"이 구별되지 않는다.**

### 5.7 🔴 **서버 주소가 펌웨어에 박혀 있다** — 호스트 IP 가 바뀌면 링크가 **조용히** 죽는다 ★ 2026-08-17 00:0x 실측

```c
#define SERVER_IP    "192.168.35.21"   // client.ino:90
#define SERVER_PORT  "9991"            //            :91
```

**컴파일 타임 상수다.** 서버 호스트(이 맥)의 IP 가 바뀌면 **펌웨어를 다시 굽기 전에는 못 따라간다.**

**실제로 났다**(2026-08-17 00:02~00:07): 21:05 재부팅에서 맥의 DHCP 임대가
**`.21` → `.81`** 로 바뀌었다. 보드는 `.21` 로 계속 SYN 을 쏘고 서버는 `.81` 에서 듣고 있었다.

> ### ⚠ 이 고장의 지문 — **서버 로그가 완전히 비어 있다**
> `+? 연결 수락` **0건**. 붙었다 끊기는 것이 아니라 **아예 안 온다.**
> **서버측에서는 "보드가 죽었다"와 구별이 안 된다.** 실제로 socket 이 그 상태에서 4분을 썼다.
>
> **가르는 법은 서버 로그가 아니라 주소 대조다** — 한 줄이면 끝난다:
> ```bash
> strings <빌드>/client.ino.elf | grep CIPSTART    # 펌웨어가 거는 곳
> ifconfig | grep "inet " | grep -v 127.0.0.1      # 호스트가 실제로 가진 것
> ```

**같은 모양의 다른 고장이 이미 있었다**(8/15 `DNS Fail` — `SERVER_IP` 앞 공백).
**기전은 다른데 지문이 같다**: 둘 다 서버 로그가 빈다. → **로그가 비면 주소부터 대조하라.**

#### 5.7-1 진단할 때 **묶어서 읽지 마라**

**IP 불일치 하나만으로 "연결 0건"이 전부 설명된다.** 즉 **보드가 완전히 멀쩡해도 이 그림이 나온다.**

> **"연결이 0건이다" → "보드가 죽었다"로 가지 마라.** 주소를 맞춘 뒤에야 그 질문을 물을 수 있다.

★ 그리고 주소를 맞추는 것이 **보드 생사 확인을 겸한다**: 이 펌웨어는 서버가 없으면
**백오프 없이 0.90초 주기로 재시도**하므로(§1.5) **주소가 맞는 순간 1초 안에 붙는다.**
안 붙으면 그때 비로소 보드가 후보다. **포트를 안 열고 얻는 생사 판정이라 리셋을 아낀다.**

#### 5.7-2 고치는 방향 — **다시 굽는 것이 답이 아니다**

| 선택지 | 대가 |
|---|---|
| **호스트 IP 를 되돌린다(고정 IP·DHCP 예약)** | 보드 미접촉 · 리셋 0 · 즉시 확인 |
| 펌웨어에 새 IP 를 박아 다시 굽는다 | 리셋 1회 + 관측 경계 1개 + **다음 재부팅에 또 깨진다** |

> **DHCP 예약이 근본 수정이다.** 펌웨어를 고치는 것은 **같은 사고를 다음 재부팅으로 미루는 것**뿐이다.
> ⚠ 호스트 네트워크 설정은 **arduino 도메인이 아니다.** 발견은 우리가 하고 조치는 넘긴다.

**실제로 택한 것**(2026-08-17, 루트 결정): `sudo ifconfig en0 alias 192.168.35.21 255.255.255.0`.
✅ **서버 재기동조차 필요 없다** — 서버가 **와일드카드로 리슨**하므로(`TCP *:9991`, socket 확인)
**이미 열린 소켓이 새 주소를 자동으로 포함한다.** pid·`build=`·`t0` 가 전부 유지된다.

#### ⚠ 5.7-3 개입에는 **두 종류**가 있다 — "창 안"이라고 다 같지 않다 ★ 내가 여기서 틀렸다

나는 이 조치를 **"`t0` 앞이라 지금이 공짜"** 라고 권고했다. **전제가 이미 죽어 있었다** —
monitor 가 `00:04:34` 에 탭을 열었고 그것이 `t0` 였다. 내가 모르는 사이에 창이 열려 있었다.

> **그런데 결론은 안 바뀐다.** 왜인지가 중요하다:
>
> | | 관측 경계를 만드나 |
> |---|---|
> | 플래싱·탭 재개·리셋·전원 | **만든다** — 창을 쪼갠다 |
> | **호스트 IP 별칭** | **안 만든다** — 보드를 안 건드리고 리셋이 없다 |
>
> **내 권고가 옳았던 이유는 "창 앞이라서"가 아니라 "리셋을 안 만들어서"였다.**
> 근거를 타이밍에 걸었던 것이 실수다. 타이밍은 내가 확인할 수 없는 남의 상태였고, 실제로 틀렸다.

★ **교훈**: 개입의 값을 **"언제 하는가"로 따지기 전에 "관측 경계를 만드는가"로 따져라.**
후자는 내 도메인 지식으로 판정할 수 있고, 전자는 남에게 물어야 한다.
⚠ 그리고 **창이 열렸는지를 내가 안다고 가정하지 마라.** 탭·서버는 남의 손에 있다.

### 5.2 끊김만 세지 말고 **미수(near-miss)를 세라**

옛 계열은 실패할 때마다 `[NET] 전송 실패 n/3` 을 찍는다.
**실패 1회의 빈도 대비 3연속 도달 빈도**를 보면 실패가 **산발인지 뭉치는지**가 갈린다.
끊김만 세면 **분모가 안 보인다.**

### 5.3 로그 문구를 사실로 믿지 마라 — `[TX-RESYNC]` 사례

`(서버는 이 줄을 버린다)` 는 **조건부인데 단정형으로** 적혀 있었다. (b) 갈래에서는
더미가 서버에 도달조차 하지 않으므로 **일어나지 않은 일을 단언한다.**

### 5.4 ~~`#` 채움 문자는 "체크섬 이전에 타입에서 걸린다"~~ ❌ **틀렸다**

~~타입 문자가 아니라서 타입 검사에서 걸러진다~~ →
**서버의 실제 검사 순서는 길이(64B) → 체크섬 → 타입**이다(`server.cpp:906/1429/1541`).
`###…` 은 쉼표가 없어 **체크섬 단계에서 즉시 걸린다. 타입 검사까지 가지도 못한다.**

> 결론(반드시 버려진다)은 유지되지만 **근거가 틀렸다.** 그리고 그 말은
> **채움 문자를 무엇으로 고르든 들어가는 칸이 같다**는 뜻이다.
> **교훈: 남의 도메인 동작을 근거로 쓸 때는 그쪽에 확인하고 출처를 적어라.**

### 5.6 **재연결 ≠ 재부팅** — 새 연결을 재부팅으로 세지 마라 ★ 실측

기준선 13.92시간에서 **새 연결 36건 중 실제 재부팅은 1건뿐**이었다(나머지는 링크만 다시 붙었다).
서버의 옛 `재부팅감지` 칸은 **새 연결을 전부 재부팅으로 세어 30배 이상 과대계상**하고 있었다.

> **가르는 법은 `uptime` 이다**(§1.6) — 붕괴하면 Uno 재부팅, 계속 증가하면 링크만 재접속.
> **"장치가 자꾸 재부팅한다"를 전제로 가설을 세우기 전에 이 구분부터 하라.**
> 실제로는 재부팅이 거의 없고 **링크만 다시 붙고 있었다.**

### 5.5 숫자 둘을 비교하기 전에 **정의를 맞춰라** ★ 2026-08-16 하루에 네 번 밟았다

같은 단위(초·건수)라는 것은 비교 가능하다는 뜻이 **아니다.** 셋을 확인한다:

1. **무엇을 세는가** — 이름이 아니라 정의 (`새 연결` vs `링크 단절`은 둘 다 '건수'다)
2. **어디서 시작하는가** — 구간의 출발점 (`부팅→등록 12초` vs `accept→첫 프레임`)
3. **누가 만들었는가** — 같은 펌웨어·판본·계측기인가 (`send_fail_x3` 은 한쪽 계열에만 있다)

> **이 실수는 지식으로 못 막는다.** 네 번 다 당사자가 **반증을 자기 손으로 적어 놓고**
> 연결하지 못했다. 몰라서가 아니라 **확인을 안 해서**다. 비교 직전에 위 셋을 답하는 **절차**여야 한다.

## 6. 설계 원칙 (오늘 값을 치르고 얻은 것)

### 6.1 **실패 모드를 세지 말고 결과를 봐라** — 살아있음(liveness) 불변식

오늘 하루에 원인이 세 번 옮겨 다녔다(프롬프트 제한시간 → `busy` → ?).
**실패 종류마다 카운터를 다는 방식은 "아는 실패"만 막는다.**

그래서 이유를 묻지 않는 불변식을 둔다:
> **"온라인이라면서 T초 동안 한 줄도 못 내보냈으면 링크를 다시 세운다."**
> `busy` 든 `ERROR` 든 침묵이든 **아직 이름 없는 무엇이든** 여기에 걸린다.

**원인은 진단으로만 남긴다.** 원인별 제어 경로를 만들면 그게 다시 "아는 실패만 막는" 구조가 된다.

⚠ **예외 처리를 완화할 때는 회복 경로가 같이 사라지지 않는지 봐라.**
`busy` 를 실패로 안 세게 고쳤더니 **연속 카운터가 영원히 3에 도달하지 않아** 회복 경로가
사라질 뻔했다. **자해 하나를 없애면서 조용한 영구 정지를 만드는 교환**이었다.

### 6.2 상수는 **관측이 아니라 규약에서** 끌어오면 표본이 없어도 정당화된다

`TX_STALL_MS = 10초`의 근거는 관측 분포가 아니라 **서버 무프레임 판정(3.5초)** 과
**기존 3연속 실패 경로(약 3초)** 다 — 평범한 문제는 그쪽이 먼저 잡고, 무한 정지보다는 짧다.
관측 분포는 **다듬는 데** 쓰지 정하는 데 쓰지 않았다.

**사후 확인**(monitor, 1.13h): `busy` 런 3건 · 길이 1/2/3 · **최대 3** · 시도의 0.2%.
→ ~~10(≈10회)~~ **✏️ 2026-08-17 정정: 10초 = 약 9.0주기다**(주기가 1.000s 가 아니라 **1.113s** — §3.4).
  **결론은 살아남는다**(9.0 도 관측 최대 3 의 3배다) **그러나 "10초=10회" 환산은 틀렸다.**
  ★ 이렇게 아슬아슬하게 살아남는 것이 위험 신호다 — 최대가 3.3 이었으면 **결론이 뒤집혔다.**
⚠ **"충분히 크다"로 확정하지 마라 — 런이 3건뿐이라 꼬리는 여전히 미지다.**
관측이 쌓이면 다시 본다.

### 6.4 어느 쪽으로 틀릴지 고를 수 있으면 **드러나는 쪽으로 틀려라** ★ 2026-08-16

임계값·기본값을 정할 때 **두 방향의 실수는 값이 같지 않다.** 값이 같지 않으면 가운데를
고르는 것이 아니라 **덜 나쁜 쪽으로 치우쳐 고르는 것**이 맞다.

실례(`SEND_OK_TIMEOUT_MS`):

| 틀리는 방향 | 결과 | 드러나나 |
|---|---|---|
| 너무 **일찍** 자른다 | 2단계 이전 동작으로 되돌아갈 뿐 | **`okto` 에 계상되어 드러난다** |
| 너무 **늦게** 푼다 | ESP 가 죽었는데 그만큼 눈이 먼다 | **조용히 손해가 난다** |

> **그래서 통계가 아니라 이 비대칭이 값을 정했다.**

**이 규칙은 임계값에만 쓰는 것이 아니다.** 2026-08-16 에 이 팀이 데인 것이 거의 전부
**"조용한 손해"** 쪽이었다 — 커밋에서 CR 이 벗겨진 원시 로그, `DEBUG=0` 이 관측을 통째로 끄는 것,
서버에서 승격 전 소켓의 줄이 카운터 없이 버려지는 경로, 기록되지 않은 실물 개입.
**전부 "틀렸다는 사실 자체가 안 보이는" 형태였다.**

### 6.5 추측으로 넉넉히 잡지 말고 **재고 고칠 수 있게** 잡아라 ★ 짝 규칙

값을 크게 잡아 안전을 사는 것은 **그 값이 맞는지 영영 모르게 만드는 대가**를 치른다.
대신 **그 값이 틀렸을 때 드러나는 계수기를 같이 둔다.**

`SEND_OK_TIMEOUT_MS=2000` 에는 `okto` 가 붙어 있다 — 구운 뒤 `okto` 가 미도달 기대치를
넘으면 **빡빡하다는 증거**가 된다. **추측으로 3000 을 잡는 것과 근본적으로 다르다.**

#### ⚠ 6.5-1 그러나 — **경로가 있는 것과 그 경로의 눈금이 맞는 것은 다르다**

이 규칙에는 함정이 딸려 온다. **자기교정 장치를 달아 놓으면 그 뒤로는 안심하게 된다.**
*"값이 이상하면 `okto` 가 알려 줄 것"* 이라고 믿는 순간, **`okto` 를 무엇과 견주는지는
아무도 안 따진다.**

실제로 그럴 뻔했다: `okto` 의 비교 기준으로 잡은 미도달률 **0.33% 는 2단계가 없는 칩**에서
잰 값이다. **2단계는 송신 타이밍 자체를 바꾸므로 기대치가 달라질 수 있다.**
즉 장치는 있는데 **눈금이 다른 자로 잰 것**이었다.

> ### **안전장치가 검사를 대신하는 것처럼 보이는 자리가 제일 위험하다.**
> 자기교정 경로를 두었다면, **그 경로의 기준값이 어느 조건에서 나왔는지**를 같이 적어라.
> 기준값에도 §5.5(무엇을·어디서·누가)가 그대로 적용된다 — **장치를 달았다고 면제되지 않는다.**

→ **2단계를 구운 뒤 첫 일은 `okto` 를 보는 것이 아니라, 2단계 칩에서 미도달 기대치를
새로 잡는 것이다.**

### 6.3 변경은 **하나씩** 넣는다

효과를 재려면 변수를 하나로 줄여야 한다. 오늘 하루 종일 그러지 못해 치른 값이 크다
(캐패시터·펌웨어 계열·DEBUG·프롬프트 제한이 동시에 달라 어느 것도 귀속하지 못했다).

>

> 다음엔 *"`0.0.0.0` 단독이면 된다"*. **둘 다 전수 검증에서 반례가 나왔다.**
> **교훈: 판별자를 채택하기 전에 두 가지를 전수로 확인하라 —**
> **① 정상 동작에서도 뜨는가(오탐) ② 진짜 사건에서 안 뜰 수 있는가(누락).**

**C 가 발동하려면 `+IPD` → `[TX] A,`(ACK 송신) → `drainPending()` 이 시간을 쓰는 사슬이 필요하다.**
`drainPending()` 은 **보낼 것이 없으면 첫 줄에서 `return` 한다**(`client.ino:2255`) — 갱신도 송신도 없다.
**창4 는 ACK 를 한 번도 안 보냈으므로 그 코드가 아예 안 돌았다.**

> ### **`0` 은 "안 났다"와 "잴 기회가 없었다"를 구별하지 못한다** — §5.1 과 같은 뿌리다.
> ✅ **올바른 조건: `[TX] A,` ≥ 1 **그리고** `★ 정지 감지` = 0.**
> **분모를 먼저 확인하고 분자를 읽는다.**

⚠ **C-2(`CONNECT` 경로)는 창4 에서 두 번 돌았지만 검증력이 없다** — **수정 전 창3 에서도 안 떴다.**
**수정 전후 모두 0 이면 아무것도 못 가른다.** *"경로가 돌았다"는 "판별력이 있다"가 아니다.*

★ **내가 유보를 걸어 놓고 스스로 어겼다.** *"실기 증명은 하행 6건"* 이라고 써 두고
**6건이 도달했는지 확인하지 않고 분자만 읽었다.** **유보는 적어 두는 것으로 지켜지지 않는다 —
결과를 읽는 순간에 그 조건을 다시 꺼내 봐야 한다.**

### 8.2-6 ✅ **전원(공급 용량·벌크) 갈래는 접었다** ★ 2026-08-17 · 사용자 실물 확인

**보드 구성이 확인됐다**(`docs/arduino/BOARD-CHECK-2026-08-16.md` 의 답 · 사진):

| 항목 | 실제 |
|---|---|
| ESP-01 전원 | **외부 `XL4015` 벅 컨버터 → 3.3V** (아두이노 3.3V 핀 아님) |
| 디커플링 | **0.1µF + 100µF ×2 병렬** |
| 배치 | 벌크 전해가 **ESP 와 같은 만능기판** · 약 2~3cm |
| Uno 전원 | USB (맥) |
| Uno ↔ 기판 | **듀폰 점퍼** (납땜 아님) |

> ### **5A급 공급 + 200µF 벌크 + 0.1µF 세라믹이면 "용량이 모자라서" 나는 고장이 아니다.**
> **답 받기 전에 적어 둔 판정표대로 접는다.** 표를 답에 맞춰 고치지 않았다.

⚠ **접은 것은 *용량* 갈래다.** **"용량이 크다 ≠ 과도 응답이 좋다"** — `XL4015` 는 스위칭 벅이라
과도 응답이 느린 계열이다. **남은 한 조각은 `0.1µF` 이 ESP `VCC` 핀 바로 옆인가**이고,
그것만 확인되면 완전히 닫힌다. ⚠ **이름을 바꿔 되살리지 마라** — 남은 것은 그 한 조각뿐이다.

⚠ **사용자의 "전원 문제는 아닐 거다"는 판단이지 관측이 아니다.** 자료로 쓰지 마라.
**관측은 `XL4015 · 0.1µ+100µ×2 · 같은 기판`까지다.**

#### 🔴 8.2-7 그래서 **다음 후보는 ESP AT 펌웨어의 크래시**다

전원이 아니면서 **송신 순간과 결부되는 것**으로 지문이 가장 잘 맞는다:

> **부트 ROM 메시지 → `[System Ready]`** 라는 우리가 보는 지문은
> **"전원이 끊겼다 들어왔다"와 "펌웨어가 죽어 워치독이 리부팅했다"에서 똑같이 나온다.**
> 그리고 **TCP 송신은 AT 펌웨어가 가장 일을 많이 하는 구간**이다 — §8.2-4 의 6/6 과 맞는다.

→ **이건 우리가 고칠 수 있는 것이 아니다**(모듈 펌웨어). **확인하고 우회하는 문제**가 된다.

### 🔑 8.2-8 **리셋 원인을 이름으로 알아낼 수단이 이미 있다 — 74880bps**

**ESP8266 부트 ROM 은 `rst cause:N` 을 찍는다.** 브라운아웃과 워치독이 **다른 숫자**다.
**우리는 그 메시지를 이미 매번 받고 있고, 9600 으로 잘못 읽어 쓰레기로 보고 있을 뿐이다**(§8.2-2).

> ### **ESP 의 TX 선을 74880bps 로 읽으면 전원이냐 펌웨어냐가 그 자리에서 갈린다.**
> **보드를 바꾸지 않고 관측만 추가하는 것**이라 개입이 가볍다. USB-시리얼 어댑터 하나면 된다.

#### ❌ 8.2-8-1 ~~"가비지 바이트로 원인을 가를 수 있다"~~ — **단서지 결과가 아니다** ⚠ 내가 틀릴 뻔했다

가비지를 정렬하니 **자발 리셋 6건이 두 위치(idx6·idx9)에서 완전히 일치**하고 명령 리셋과 달랐다.
**"자발 리셋은 모두 한 가지 원인"이라고 쓸 뻔했다.**

**표본을 늘리니 무너졌다** — 명령 리셋(`AT+RST`) 기준선이 **n=1** 이었다:
```
명령 리셋 3건 : (0x50,0xFE) (0x52,0xFE) (0x50,0xFC)   ← 제각각
자발 리셋 6건 : (0x52,0xFC) × 6                        ← 균일
```
**자발 쪽이 균일한 것은 사실**이고 9건 중 그 6건이 자발과 정확히 일치할 확률은 약 **1/84** 이지만,
**27개 위치 중 가장 잘 갈리는 둘을 사후에 골랐다** — 다중 비교로 더 약해진다.

> ★ **교훈 둘**
> ① **기준선이 n=1 이면 "완벽히 일치"는 아무 뜻이 없다.** 비교군을 먼저 늘려라.
> ② **사후에 고른 특징으로 p 를 말하지 마라.** 27개 중 2개를 고른 것은 검정이 아니라 탐색이다.
> → **제대로 닫는 길은 §8.2-8 이다.** 추측을 정교하게 만들지 말고 **원문을 읽을 방법**을 찾아라.

### 8.2-1 세는 단위는 **사건이지 증상이 아니다** ★ 구현 함정

한 번의 리셋에서 `0.0.0.0` 이 여러 번 오고 그 뒤 3회 소진까지 가면 **한 사건이 네 번 세진다.**
그러면 카운터는 "사건 수"가 아니라 "증상 수"가 되어 **다른 도메인의 사건 계수와 정의가 어긋난다.**

> **IP 를 잃은 순간 한 번만 세고, 실제로 IP 를 되찾을 때 걸쇠를 푼다.**
> 이름이 같아도 세는 단위가 다르면 비교할 수 없다(§5.5).

### 8.3 기존 사다리가 기전 B 를 **이미 잘 처리한다** — 전용 탐지기가 필요 없는 이유 ★ 실측

```
18:24:50 마지막 SEND OK → (ESP 사망) → 18:24:55 오프라인 전환
18:24:56 CIFSR → 0.0.0.0   ← 사다리가 전진을 거부한다
18:24:58 CIFSR → 192.168.35.79  ← ESP 가 스스로 AP 에 재결합
18:24:59 CIPSTART → Linked → online     총 정전 ≈ 9초 (오프라인 전환 뒤 4초)
```

**사다리가 원인이 아니라 결과(IP 가 있는가)를 보기 때문에** 이름 모를 고장에도 그대로 동작했다.
→ §6.1 의 설계 원칙이 실제로 값을 한 사례다. **원인별 제어 경로를 새로 만들 이유가 없다.**

### 8.4 함정 — **`DEBUG=0` 으로 구우면 A/B 를 가를 수 없다** ★ 코드 확인

A/B 판별자가 **전부 `#if DEBUG` 안**에 있다: `[AT] "…"` 원문 로깅 · `busy s...` ·
`CIFSR → 0.0.0.0` · `[TX-BUSY]` · `[TX-RESYNC]`.
**그리고 `espResets` 를 찍는 두 곳도 `#if DEBUG` 안이다**(monitor 확인) —
즉 리셋을 사건 단위로 정확히 세게 만들어 놓아도 **그 빌드에서는 출력이 없다.**

> `DEBUG=0` 은 플래시를 25%p 아끼지만 **관측 능력을 통째로 가져간다.**
> 2단계 효과 측정이 끝나기 전에 `DEBUG=0` 으로 굽지 마라 — 효과를 잴 수단 자체가 사라진다.

#### 8.4-1 ★ 더 센 이유 — **`DEBUG` 는 편의가 아니라 "비교 가능성"의 조건이다**

위 논거(못 잰다)보다 이쪽이 더 강하고, **A/B 시험을 설계하는 사람이 반드시 알아야 한다:**

> **A 팔을 도는 칩이 `DEBUG=1` 이면 B 팔도 `DEBUG=1` 이어야 한다.**
> B 를 `DEBUG=0` 으로 구우면 두 팔이 **"펌웨어 수정"과 "로깅 유무" 두 군데**에서 달라진다.
> 그러면 링크가 좋아져도 나빠져도 **어느 쪽 때문인지 귀속할 수 없다**(§6.3).

즉 `DEBUG` 는 **관측 설정이 아니라 실험 변수**다. 팔마다 다르게 두면 그 순간 시험이 깨진다.
플래시 절약용 `DEBUG=0` 빌드는 **A/B 가 끝난 뒤 시연·배포용으로** 쓴다.

#### 8.4-2 ✅ 해결 — 운영 계수기 `[CNT]` 는 **`DEBUG` 밖으로 뺐다** (2026-08-16 · 루트 지시)

**계수기 *변수* 는 원래도 `DEBUG` 밖이었다. 없던 것은 *읽는 경로* 였다.**
`DEBUG=0` 이면 찍는 줄이 전부 사라져 **관측이 3칸→1칸이 아니라 0칸**이 됐다.
그 빌드로 시연하면 장치가 **자기 ESP 리셋에 대해 눈이 먼 채로** 현장에 선다.

```
[CNT] up=<초> drop=<n> esprst=<n> resync=<n> sendfail=<n> okto=<n> skip=<n> online=<0|1>
```

- **60초 주기 · `#if DEBUG` 밖 · 전부 부팅 이후 누적**(구간값이 아니다 — 창을 잡으려면 두 줄을 뺀다)
- **바이너리로 확인했다**: `DEBUG=0` ELF 안에 `[CNT] up=`·`drop=`·`esprst=` 문자열이 실재한다
  (호스트 시험 통과는 증거가 아니라서 `strings` 로 직접 봤다)
- 비용: `DEBUG=0` 플래시 12732B → **13382B(+650B, +2%p)**. 시리얼은 60초에 약 60바이트.

✅ **2026-08-17 재확인 — 이 항목은 닫혔다. 다시 하지 마라.**
지금 칩에 올라간 소스(`539ac53`)에서 **정의(`cntTick`, L1264)와 호출(L2599) 둘 다 `DEBUG` 밖**이다
(호출은 `#if DEBUG` 블록 **바로 위** 줄이다 — 눈으로 놓치기 쉬운 자리라 적어 둔다).
**바이너리로 닫았다**: 현재 소스를 `DEBUG=0` 으로 빌드하니 **13382B**(위 표와 일치)이고
`[CNT] up=`·`esprst=`·`okto=`·`skip=` 문자열이 **실재한다.**

> ⚠ **`RESUME §4` 항목 4 와 `REQ-0144` 의 *"정수 카운터를 DEBUG 밖으로 빼라(별건으로 여전히 유효)"*
> 는 낡은 지시다.** 이 수정이 들어가기 **전에** 쓰인 문장이 그대로 옮겨 다닌 것이다.
> **읽고 다시 착수하지 마라 — 이미 돼 있다.**
> ★ 일반화: **"아직 안 됐다"는 지시도 사실 주장이다.** 착수 전에 지금 소스로 확인해라.

> ### 경계 원칙 — **정수 카운터는 밖 · 장문 진단은 안**
> `[AT]` 원문 로깅은 **시리얼 대역과 플래시를 실제로 먹으므로** 안에 남긴다.
> 정수 카운터는 비용이 사실상 0 인데 **없으면 운영에서 못 센다.** 이 경계를 흐리지 마라.

⚠ **형식을 바꾸면 monitor 파서가 깨진다.** 칸을 **추가**하되 기존 칸 이름·순서는 유지하라.

**남은 더 나은 선택지**: 계수기를 **전선(S 프레임)에 실으면** 서버 로그에 영구 보관된다
(날짜·인스턴스 경계까지 있다). ⚠ **프로토콜 변경이라 socket·web 이 걸리고**, 펌웨어 수정과
같은 굽기에 섞으면 변수가 둘이 된다 — **별건으로 다뤄야 한다.**

### 8.4-3 `SEND OK` 지연 실측 — **`SEND_OK_TIMEOUT_MS` 의 근거** ★ monitor REQ-0131

> ### ⚠ 말할 수 있는 것과 없는 것
> · **말할 수 있다**: 2000ms 는 관측된 정상 분포를 자르지 않는다 → **"실측과 모순 없음"**

★ **이 선택은 자기교정된다**: `okto` 가 `[CNT]` 줄로 항상 나가므로, 구운 뒤 그 값이 미도달
기대치(≈0.33%)보다 크게 나오면 **2000 이 빡빡하다는 증거**다. 그때 근거를 갖고 올린다.

### 8.7 🔴 **기전 C · 계측기 자해** — 정지 감시기가 하행 ACK 뒤에 스스로 링크를 끊는다 ★ 2026-08-17 · 소스 확정

**기전이 둘이 아니라 셋이다.** A(자해)는 송신 타이밍 추측이 틀려서, B(리셋)는 모듈이 죽어서,
**C 는 우리가 넣은 감시기가 틀려서** 끊는다.

#### 기전 — `now` 가 낡았다

```c
void loop() {
  unsigned long now = millis();   // :2593  ← 루프당 한 번만 뜬다
  ...
  drainPending();                 // :2596  ← 하행 ACK 를 여기서 보낸다 (약 64ms 소요)
                                  //           그 안에서  lastTxOkAt = millis()   (:1534)
  statusTick(now);                // :2598  ← 🔴 낡은 now 를 넘긴다
}
// :2442   if (netOnline && (uint32_t)(now - lastTxOkAt) >= TX_STALL_MS)
```

**ACK 송신에 걸린 시간만큼 `lastTxOkAt` 이 `now` 보다 미래가 된다.**
→ `now - lastTxOkAt` = **−64** → unsigned → **`2^32−64` = 4294967232ms(49.7일)**
→ **어떤 임계값도 즉시 넘어 살아있음 불변식이 오발동한다.**

#### 지문 — 이 조합이면 C 다 (A·B 와 겹치지 않는다)

| 표지 | 값 |
|---|---|
| `★ 정지 감지` 의 경과값 | **`4294967232` 같은 20억 이상의 수** (= 2^32 − 실제 지연ms) |
| 실패 계수기 | **`busy 0 / 무응답 0 / 거부 0 / sendfail=0`** — 전부 0 |
| 부트 배너 · `0.0.0.0` | **없다** (B 가 아니다) |
| `[TX-RESYNC]` | **없다** (A 가 아니다) |
| `uptime` | **연속** (Uno 재부팅 아님) |
| 🔑 **직전에 `+IPD`** | **있다 — 이것이 방아쇠다** |

#### ⚠⚠ 8.7-3 **몰라서 낸 결함이 아니다 — 같은 파일 7줄 위는 제대로 돼 있다**

```c
// :2433  changeAt 은 전송 실패 시 **미래 시각**으로 밀린다. unsigned 뺄셈으로 비교하면
// :2434  언더플로로 곧장 참이 되어 백오프가 통째로 무력화된다 → 부호 있는 비교로 본다.
// :2435  bool debounced = changePending && ((long)(now - changeAt) >= (long)DEBOUNCE_MS);
```

**주석이 이 함정을 정확히 설명하고, 그 줄은 옳게 돼 있다. 7줄 아래에서 같은 실수를 했다.**

> ### **함정을 아는 것과 그 함정의 *모든* 사례를 찾는 것은 다르다.**
> **교훈: 어떤 위험을 한 곳에서 방어했으면, 같은 타입의 다른 시각 변수를 전수로 훑어라.**
> `now` 와 비교되는 시각 변수는 `lastStatusAt`·`changeAt`·`lastTxOkAt` 셋이었고
> **방어된 것은 하나뿐이었다.**
> ⚠ `lastStatusAt`(:2432)은 unsigned 인데 **안전하다** — `statusTick` 안에서만 갱신되어
> `now` 보다 미래가 될 수 없다. **위험한 것은 "다른 함수가 갱신하는" 변수다.**

#### 🔴 8.7-4 **안전장치가 스스로 새 실패 모드를 만들었다**

§6.1 에 *"실패 모드를 세지 말고 결과를 봐라"* 며 이유를 묻지 않는 불변식을 두었다.
**그 불변식 자신이 결함을 냈고, 그것도 A·B 어디에도 안 들어가는 새 기전으로 냈다.**

> **안전장치를 넣을 때 "무엇을 막나"만 보고 "이 장치가 어떤 새 실패를 만드나"를 안 보면
> 순증이 아니다.** §6.4 로 말하면 이 결함은 **드러나는 쪽**이었다(감시기가 로그를 남긴다) —
> 그래서 잡혔다. **조용히 끊는 형태였으면 몇 주를 쫓았을 것이다.**

#### 🔴 8.7-5 **방아쇠가 둘이다 — 하나는 하행이 필요 없다**

`lastTxOkAt` 을 갱신하는 곳이 셋인데 **그중 둘이 `statusTick` 보다 앞에서 돈다:**

```
loop(): netTick(:2594) → pumpSerialRaw(:2595) → drainPending(:2596) → statusTick(:2598)
```

| 갱신 위치 | 언제 | 하행 필요? |
|---|---|---|
| `:1534` `sendLine` ← `drainPending` → `sendAck` | 하행 ACK 송신 후(약 64ms) | **필요** ✅ 실측됨 |
| **`:2160` `pumpSerialRaw` — `CONNECT` 처리** | **소켓이 붙는 순간** | **불필요** ⚠ **미관측** |
| **`:2148` 〃 — `ALREADY CONNECTED`** | 초기 접속 경합 | **불필요** ⚠ **미관측** |
| `:1534` ← `statusTick` → `sendStatus` | 검사보다 **뒤**라 안전 | — |

> ### **그러므로 "하행이 없으면 안전"은 정확하지 않다.**
> **링크가 붙어 있는 동안은 안전하고, 끊겼다 다시 붙는 순간은 아니다.**
> 조건은 `now` 를 뜬 뒤 `CONNECT` 처리까지 **1ms 이상 경과**뿐이다 — **경합이지 보장이 아니다.**

⚠ **발동하면 "접속 직후 즉시 재차단"이 되어 한 번의 끊김이 연쇄로 보인다.**
**λ 를 부풀린다.** 창3 의 유일한 CONNECT(00:23)에서는 나지 않았다 — **안 났다는 것이지
안 난다는 것이 아니다.**
**지문**: `CONNECT` 직후 수 초 안의 `★ 정지 감지` + 실패 계수기 전부 0.

#### ⚠⚠ 8.7-6 **고칠 때 `(long)` 만 쓰면 호스트에서 틀린다** ★ 실제로 밟았다

처음에 §8.7-3 의 교훈대로 **7줄 위와 같은 관용구**(`(long)`)를 그대로 썼더니
**호스트 회귀가 3개 깨졌다(58 PASS / 3 FAIL).**

> **AVR 은 `long` 이 32비트라 자연히 감싸이지만 호스트는 64비트라 안 감싸인다.**
> 그래서 **정상적인 `millis()` 되감김이 음수로 읽혀** 10초 초과를 못 잡았다.

**옳은 형태 — 폭을 먼저 맞춘 뒤 부호를 준다:**
```c
if (netOnline && (int32_t)((uint32_t)now - lastTxOkAt) >= (int32_t)TX_STALL_MS)
```

> ### 🔴 **그리고 이것은 `:2435`(`changeAt`) 자신도 같은 취약성을 갖는다는 뜻이다.**
> 실기에서는 맞고 **호스트에서는 폭이 다르다.** 지금은 그 경로가 시험에 안 걸릴 뿐이다.
> ★ **"모범 사례를 복사한다"가 위험을 같이 복사할 수 있다.**
> §8.7-3 이 *"관용구를 전파하라"* 였다면, 이 항목은 그 **반대 방향의 함정**이다 —
> **전파하기 전에 그 관용구 자신이 두 환경에서 같은지 확인해라.**

#### ✅ 8.7-7 전수 훑기 결론 — **위험한 것은 "앞 함수가 갱신하는" 시각 변수뿐이다**

`now` 와 비교하는 시각 변수를 전부 봤다. `lastTxOkAt` 외에는 안전하고, **이유가 구조적이다:**

| 변수 | 판정 |
|---|---|
| `netStepAt`(:2290 unsigned) · `lastLadderFailAt`(:996) | **안전** — `pumpSerialRaw` 가 갱신하지만 읽는 `netTick` 이 **그보다 앞**이라 다음 반복의 새 `now` 로 읽는다 |
| `lastStatusAt`(:2432 unsigned) | **안전** — `statusTick` 안에서만 갱신 |
| `changeAt`(:2435) · `onlineSince`(:2273) | 부호 있는 비교 — 실기 안전(§8.7-6 의 폭 주의는 별개) |
| **`lastTxOkAt`(:2442)** | 🔴 **유일하게 "앞 함수가 갱신 + unsigned 비교"** 였다 |

> ### **규칙: 위험한 것은 같은 반복에서 *더 앞에 있는 함수*가 갱신하는 시각 변수다.**
> 자기 함수 안에서만 갱신되면 안전하다. **호출 순서가 곧 안전 조건이다** —
> 그래서 `loop()` 의 순서를 바꾸면 **지금 안전한 것들이 위험해진다.** 순서를 바꿀 때 이 표를 다시 봐라.

**수정 완료**: 커밋 `9a0c823`. 회귀 시험 `[8b]` 신설 —
**수정 전 2 FAIL · 수정 후 0 FAIL 로 차이를 잡는 것까지 확인했다**(61/2 → 63/0).
**항상 통과하는 시험이 아니라는 것을 실제로 확인한 것이다**(`BURN-CHECKLIST` §5 와 같은 규율).
⚠ **아직 굽지 않았다** — 루트 지시로 아침 하행 작업 전에 굽는다. **칩은 여전히 결함을 갖고 있다.**

### 8.5 `busy` 가 났다고 반드시 끊기는 것이 아니다 ★ monitor 실측

`busy` 전수 20건 중 3연속 실패까지 간 것은 일부이고, **2건짜리 런은 살아남았다.**
그리고 **리셋 사건에는 `busy` 가 0건**이다 — **두 기전은 섞이지 않는다.**
> **끊는 것은 `busy` 자체가 아니라 3진아웃 규칙이다.**
