# arduino 도메인 원장 (LEDGER)

> **기동하면 이 파일부터 읽어라.** 세션은 죽지만 원장은 남는다.
>
> **여기 적는 것**: 이 도메인에서 **시간이 지나도 참인 것** — 실측으로 확정된 상수·형식·임계값과
> 그 근거, 틀린 것으로 밝혀진 통념과 왜 틀렸는지, 다음 사람이 넘어질 함정.
>
> **여기 안 적는 것**: 그날의 상태·진행·인수인계. 그건 날짜 붙은 별도 파일이다.
> - 지금 칩에 무엇이 올라가 있나 · 개입 이력 → **`arduino/INTERVENTIONS.md`**
> - 그날의 인수인계 → `docs/arduino/handoff-<날짜>.md`
>
> **규칙**: ① 근거 없이 적지 마라(실측인지 추정인지 드러내라) ② 조건부 사실은 **조건을 같이** 적어라
> ③ 틀린 항목은 **지우지 말고 취소선 + 사유** ④ append 가 기본.

## 1. 링크 계층 — 오늘 뒤집힌 것이 가장 많은 영역

### 1.1 `send_fail_x3` 이 세는 것은 **링크 상태가 아니다** ★ 코드로 확정

세는 것은 **`AT+CIPSEND` 뒤 `>` 프롬프트를 제한시간 안에 봤는가, 그것 하나뿐**이다.
ESP 가 보내는 `SEND FAIL`·`busy`·`ERROR` 는 **로그만 남기고 세지 않는다**
(`link is not valid` 만 예외). 이중 계수를 피하려는 의도적 설계다.

> **그러므로 "3회 연속 실패"는 "링크가 죽었다"가 아니라 "우리가 세 번 제때 못 봤다"이다.**
> 소스도 이 판정을 **추정**이라고 명시한다 — 링크가 살아 있었다면 재시도에
> `ALREADY CONNECTED` 가 와서 그대로 복귀한다.

**연속이다. 누적이 아니다.** 송신이 한 번 성공하면 카운터가 0 으로 리셋된다.

### 1.2 `busy` 는 **ESP 의 명시적 신호**다 — 침묵과 다르다 ★ 실측

- `busy p...` = 앞 **명령**을 처리 중 · `busy s...` = 앞 **전송**을 아직 보내는 중
- 뜻은 **"지금 말고 나중에"** 이지 "고장"이 아니다. **기다렸다 재시도할 것**이다.
- ⚠ 기존 `busy` 처리 코드는 `if (!netOnline && ...)` 안에 있어 **오프라인 접속 사다리에서만**
  돈다. **온라인으로 프레임을 보내는 동안에는 그 경로가 아예 실행되지 않았다.**

**2026-08-16 실측 로그**:
```
[AT] "AT+CIPSEND=38"
[AT] "busy s..."        ← 명령 자체가 거부됐다. '>' 는 오지 않는다
```

### 1.3 `SEND OK` 를 **아무도 안 본다** ★ 코드로 확정 (두 계열 모두)

`SEND OK` 는 ESP 가 **"앞 전송이 끝났다"** 고 알려주는 신호인데 처리 코드가 없다.
대신 `SEND_GAP_MS = 80` 이라는 **고정 추측값**을 쓴다.

> **그 80ms 는 "우리가 쓰기를 끝낸 시점"부터 재는 것이지 "ESP 가 WiFi 전송을 마친 시점"이
> 아니다.** 망이 느리면 ESP 는 80ms 뒤에도 여전히 보내는 중이고 → `busy s...` 가 난다.
> **`busy s...` 는 이 추측이 틀린 순간에 나는 것이다.**

`SEND_GAP_MS` 자체는 원래 **`busy p...` 회피용**이므로 없애면 안 된다(하한으로 유지).

### 1.4 프롬프트 놓침에는 **두 갈래**가 있고 대응이 다르다 ★ 실측

| 갈래 | ESP 상태 | 더미 `#`×N 을 쓰면 | 서버 |
|---|---|---|---|
| **(a) `>` 는 왔는데 우리가 못 봄** | **데이터 모드**(N바이트 대기) | 소켓으로 나간다 — **채워야 한다** | 한 줄 받고 버림 |
| **(b) `>` 가 애초에 안 옴**(busy/ERROR 거부) | **명령 모드** | **AT 해석기가 먹는다 — 넣으면 안 된다** | 아무것도 안 옴 |

**가르는 법**: 프롬프트 놓침 직후의 `[AT] "..."` 를 봐라 — `SEND OK` 면 (a), `Error`/`busy` 면 (b).
**2026-08-16 실측은 (b) 였다**: `[AT] "#####…"` 가 **에코로 되돌아왔고 `SEND OK` 는 한 번도 없었다.**

> ⚠ **판정 근거로 "서버 카운터가 0" 을 쓰지 마라.** 서버에는 **승격 전 소켓의 줄을 어느 카운터도
> 올리지 않고 버리는 경로**가 있다(`server.cpp:2156-2176`). 0 은 세 원인 모두와 양립한다.
> **가른 것은 장치측 AT 에코다.**

### 1.5 서버가 없으면 **백오프 없이 0.90초 주기로 재시도**한다 ★ 실측 (설계된 거동)

`CIFSR → CIPMUX → CIPSTART → ERROR/Unlink` 를 약 0.90초 주기로 쉬지 않고 반복하고
**재시도 간격이 늘지 않는다.**

> **이것은 결함이 아니다. 집계에서 "재연결 폭주 = 장치 이상"으로 세면 안 된다.**
> 부수 효과: 서버를 다시 띄우면 **1초 안에 연결 시도가 들어온다.**

### 1.6 프레임 형식과 `uptime` 의 의미 ★ 두 계열 동일 (코드 확인)

```
S,<seq>,<occupied>,<reserved>,<uptime>,<DEVICE_ID>[,<tmask>]
```

**`uptime` 은 `millis()/1000`, 즉 Uno 자신의 가동시간이다. ESP 것이 아니다.**

> **그러므로 uptime 붕괴 = Uno(호스트 MCU) 재부팅**이다.
> **ESP 만 재접속한 경우에는 uptime 이 끊기지 않고 계속 증가한다.**
> 이 둘은 원인 계층이 전혀 다르므로 집계에서 반드시 구분해야 한다.

### 1.7 `+IPD` 는 **연결 id 없는 단일 인자 형식**이다 ★ 실측 — ⚠ **조건부**

```
[AT] "+IPD,19:R,1,A1,00000000,13"     →  +IPD,<n>:
```

**⚠ 조건: `CIPMUX=0`(단일 연결)로 운용하는 지금 구성에서만 참이다.**
부팅 사다리가 `AT+CIPMUX=0` 을 넣기 때문이다.

> **`CIPMUX=1`(멀티 연결)로 바꾸면 `+IPD,<id>,<n>:` 이 되어 10자가 되고,
> 프레임 63자와 합쳐 73바이트가 된다.** `RX_CAP=96` 은 그 경우까지 덮는 여유이므로 **줄이지 마라.**

## 2. 리셋·전원

### 2.1 **포트를 여는 것 자체가 리셋이다** ★ 회로 사실

Uno 는 USB 시리얼의 **DTR 이 100nF 커패시터를 거쳐 RESET 에 직결**돼 있다(자동 리셋 회로).
`screen`·시리얼 모니터·`pyserial`·`avrdude` 등 **포트를 여는 모든 행위가 재부팅을 일으킨다.**

> **"읽기만 했다"도 개입이다.** 보드를 만지기 전에 `arduino/INTERVENTIONS.md` 에 먼저 적어라.

### 2.2 리셋 **원인**은 소프트웨어로 알 수 없다 ★ 확정 (디스어셈블 + 부팅 로그)

**부트로더가 `MCUSR` 을 앱보다 먼저 지운다.** 장치 부팅 로그가 스스로 그렇게 찍는다:
```
[BOOT] 리셋 원인: 불명 (부트로더가 MCUSR 을 지우고 넘어왔다)
```
> **펌웨어를 고쳐서 리셋 원인을 찍게 만드는 방향은 막다른 길이다.** 외부 관측으로만 좁힌다.

### 2.3 부팅 **횟수**는 EEPROM 에 있다 ★ 코드 확인

주소 2 = `bootCount`, 주소 0 = 매직 `0xB007`. **전원이 빠져도 남는다** —
로그 공백 구간의 재부팅을 소급 검증할 유일한 수단이다.
⚠ **avrdude 로 읽는 행위 자체가 리셋이고 포트를 점유한다.** 관측자와 시각을 맞춰라.

### 2.4 워치독은 **동작하지 않는다** — 단, "코드가 없다"는 뜻은 아니다 ✏️ **2026-08-16 정정**

| 계열 | 워치독 코드 | 실제 동작 |
|---|---|---|
| `arduino/client/EspLink.h` | **없다**(검색 0건) | 해당 없음 |
| `조별과제샘플/client.ino` (**지금 칩**) | **있다** — `#include <avr/wdt.h>`, `wdt_enable(WDTO_8S)` | **꺼져 있다**: `ENABLE_WDT 0` 로 컴파일에서 빠지고, 부팅 시 `wdt_disable()` 을 **항상** 호출 |

> ✏️ **정정 사유**: 처음에 *"두 파일 다 검색해 0건"* 이라고 적었는데, 실제로 검색한 것은
> **EspLink 계열**이었다. 옛 계열에는 워치독 코드가 있다. **결론(동작하지 않는다)은 유지되지만
> 근거가 부정확했다.** — 호스트 테스트를 붙이다 `avr/wdt.h` 가 없어 빌드가 깨지면서 드러났다.
> **교훈: "검색해서 0건"이라고 쓸 때는 어느 파일을 검색했는지 같이 적어라.**

**부팅 로그가 실제 상태를 말해 준다**: `6단(워치독) 끔`.
`wdt_disable()` 이 조건부가 아닌 이유도 의도적이다 — 워치독 리셋으로 들어왔다면 WDT 가 켜진 채일
수 있어 **켜기 전부터 방어**하는 것이다.

> **그러므로 남는 리셋 원인은 브라운아웃(전원 강하) · 외부 리셋(DTR/리셋핀) · 전원 순단뿐이다.**

### 2.6 리셋 원인 **캡처 코드는 있다** — 다만 0 을 읽는다

`.init3` 섹션의 naked 함수(`earlyInitCapture`)가 `MCUSR` 을 `mcusrMirror`(`.noinit`)로 옮기고
부팅 로그에서 `PORF`·`EXTRF`·`BORF`·`WDRF` 로 해독한다.
**그런데 부트로더가 이미 지운 뒤라 실기에서는 항상 0 → `리셋 원인: 불명` 이 찍힌다**(§2.2).
> **코드가 있다고 값이 있는 게 아니다.** 이 경로를 "구현하면 된다"고 다시 제안하지 마라 — 이미 있다.

### 2.5 SoftwareSerial 은 **64바이트 버퍼 · 반이중**이다 ★ 라이브러리 사실

`_SS_MAX_RX_BUFF = 64`(`SoftwareSerial.h`). 그리고 **송신 중에는 수신을 못 한다.**

> 결과: **우리가 쓰는 동안 도착한 응답은 받을 수 없고**, 버퍼가 넘치면 바이트가 **조용히 사라져
> 두 줄이 한 줄로 붙는다.** 진단 출력이 많을수록 루프가 늦어져 이 위험이 커진다.

## 3. 타이밍

### 3.1 기동 창 ≈ **12초** (부팅 → 서버 등록) ★ 실측 2026-08-16, 3자 교차 확인

t0 = 리셋 해제 기준. 시리얼(서브초)·탭·서버 로그 세 관측이 같은 부팅에서 일치했다.

| 사건 | t0 기준 |
|---|---|
| 부트로더 → 스케치 시작 | 1.0s |
| 배너 `[PARKING NODE]` | 1.51s |
| `CWJAP OK` (WiFi 결합 완료) | 10.42s (결합 자체 5.0s) |
| IP 확보 | 10.77s |
| 첫 `CIPSTART` | 11.29s |
| **서버 수락** | **≈12s** |

- ⚠ **가장 크게 흔들리는 구간은 `CWJAP`(WiFi 결합)** 이다. 펌웨어는 최대 30초까지 기다린다.
- ~~옛 기준 36초~~ 는 **EspLink(nextgen) 판 특성**이라 옛 계열에는 **적용되지 않는다.**

### 3.2 서버 마감(`UNKNOWN_TIMEOUT_MS`)은 **기동 창과 무관하다** ★ 중요

**마감 시계는 부팅이 아니라 `accept` 에서 시작한다.** 장치는 WiFi·IP 를 **끝낸 뒤에야** TCP 를 열고,
`CONNECT` 직후 곧바로 첫 프레임을 보낸다. **그 앞 12초는 소켓이 존재하지도 않는 구간**이다.

실측(서버측 accept 131건): `accept → device_id 확정` **최대 1.0초, 7초 초과 0건.**

> **⚠ 그래도 마감을 1~2초까지 줄이지는 마라.** 정상 세션을 끊기 시작하고, 끊긴 장치는
> **0.90초 무백오프로 즉시 재접속**하므로 **서버가 "붙었다 끊기는 주기적 사이클"을 스스로 만든다.**
> 7초는 실측 최악(1.0초)의 7배이고 **그 여유가 이 함정과의 거리다.**

### 3.3 두 계열의 프롬프트 제한이 **7.5배 다르다** ★ 코드 확인

| 계열 | 프롬프트 대기 상한 |
|---|---|
| `조별과제샘플/client.ino` (옛 계열) | **300ms** (`PROMPT_TIMEOUT_MS`) |
| `arduino/client/EspLink.h` | **40ms** (`ESPLINK_PROMPT_MS`) |

> **두 계열의 끊김률을 같은 척도로 비교하지 마라.** 실패 판정의 민감도가 애초에 다르다.

## 4. 빌드·저장소

### 4.1 아두이노 스케치 폴더는 **그 안의 모든 `.c/.cpp/.h` 를 함께 컴파일한다** ★ 함정

**다른 도메인의 소스가 같은 폴더에 놓이면 빌드가 깨진다.** 그래서 스케치는
**전용 폴더**에 두어야 하고, 서버 파일 등이 예약된 폴더와 공유하면 안 된다.

### 4.2 **폴더명 == 스케치명** 규칙

`arduino-cli` 는 이를 요구한다. 어기면 `main file missing from sketch` 로 빌드 자체가 안 된다.
`조별과제샘플/client.ino` 가 이 규칙을 어기므로 **저장소 경로 그대로는 빌드되지 않는다** —
`/tmp` 등에 `client/client.ino` 로 복사해서 빌드해야 한다.

### 4.3 헤더는 **스케치 폴더 안에** 둔다

정식 아두이노 라이브러리로 만들면 `--libraries` 플래그나 설치가 필요해져
**"받아서 그대로 빌드"가 깨진다.** 소비자가 하나뿐이면 스케치 폴더 안이 정답이다.
⚠ **두 번째 스케치가 생기면 그때 라이브러리로 승격**해야 한다(사본이 둘이 되면 반드시 갈라진다).

### 4.4 실장 펌웨어는 **hex 바이트 대조로 증명할 수 있다** ★ 방법

`avrdude -U flash:r:` 로 덤프 → 소스를 같은 FQBN 으로 빌드 → **32768바이트 raw 로 파싱해 비교.**
Intel HEX 텍스트를 눈으로 비교하지 마라(레코드 배치가 달라도 내용은 같을 수 있다).
2026-08-16 에 이 방법으로 **차이 0바이트**를 확인해 칩과 커밋본의 동일성을 증명했다.

## 5. 함정 (다음 사람이 같은 곳에서 넘어질 자리)

### 5.1 `[LINK] closed reason` 은 **EspLink 전용 문자열**이다 ★ 실제로 당할 뻔했다

옛 계열 칩에서 이걸 세면 **0 이 나오고, 0 은 "끊김 없음"으로 읽힌다.**
옛 계열은 같은 사건에서 이렇게 찍는다:
```
[NET] 전송 3회 연속 실패 → 오프라인 전환. 낡은 소켓부터 닫는다(CIPCLOSE)
```
> **일반화: 계수하기 전에 "지금 칩의 펌웨어가 그 문자열을 찍는가"를 확인하라.**
> 없는 신호를 세면 0 이 나오고, **0 은 "없음"과 "못 셈"이 구별되지 않는다.**

### 5.2 끊김만 세지 말고 **미수(near-miss)를 세라**

옛 계열은 실패할 때마다 `[NET] 전송 실패 n/3` 을 찍는다.
**실패 1회의 빈도 대비 3연속 도달 빈도**를 보면 실패가 **산발인지 뭉치는지**가 갈린다.
끊김만 세면 **분모가 안 보인다.**

### 5.3 로그 문구를 사실로 믿지 마라 — `[TX-RESYNC]` 사례

`(서버는 이 줄을 버린다)` 는 **조건부인데 단정형으로** 적혀 있었다. (b) 갈래에서는
더미가 서버에 도달조차 하지 않으므로 **일어나지 않은 일을 단언한다.**

### 5.4 ~~`#` 채움 문자는 "체크섬 이전에 타입에서 걸린다"~~ ❌ **틀렸다**

~~타입 문자가 아니라서 타입 검사에서 걸러진다~~ →
**서버의 실제 검사 순서는 길이(64B) → 체크섬 → 타입**이다(`server.cpp:906/1429/1541`).
`###…` 은 쉼표가 없어 **체크섬 단계에서 즉시 걸린다. 타입 검사까지 가지도 못한다.**

> 결론(반드시 버려진다)은 유지되지만 **근거가 틀렸다.** 그리고 그 말은
> **채움 문자를 무엇으로 고르든 들어가는 칸이 같다**는 뜻이다.
> **교훈: 남의 도메인 동작을 근거로 쓸 때는 그쪽에 확인하고 출처를 적어라.**

### 5.6 **재연결 ≠ 재부팅** — 새 연결을 재부팅으로 세지 마라 ★ 실측

기준선 13.92시간에서 **새 연결 36건 중 실제 재부팅은 1건뿐**이었다(나머지는 링크만 다시 붙었다).
서버의 옛 `재부팅감지` 칸은 **새 연결을 전부 재부팅으로 세어 30배 이상 과대계상**하고 있었다.

> **가르는 법은 `uptime` 이다**(§1.6) — 붕괴하면 Uno 재부팅, 계속 증가하면 링크만 재접속.
> **"장치가 자꾸 재부팅한다"를 전제로 가설을 세우기 전에 이 구분부터 하라.**
> 실제로는 재부팅이 거의 없고 **링크만 다시 붙고 있었다.**

### 5.5 숫자 둘을 비교하기 전에 **정의를 맞춰라** ★ 2026-08-16 하루에 네 번 밟았다

같은 단위(초·건수)라는 것은 비교 가능하다는 뜻이 **아니다.** 셋을 확인한다:

1. **무엇을 세는가** — 이름이 아니라 정의 (`새 연결` vs `링크 단절`은 둘 다 '건수'다)
2. **어디서 시작하는가** — 구간의 출발점 (`부팅→등록 12초` vs `accept→첫 프레임`)
3. **누가 만들었는가** — 같은 펌웨어·판본·계측기인가 (`send_fail_x3` 은 한쪽 계열에만 있다)

> **이 실수는 지식으로 못 막는다.** 네 번 다 당사자가 **반증을 자기 손으로 적어 놓고**
> 연결하지 못했다. 몰라서가 아니라 **확인을 안 해서**다. 비교 직전에 위 셋을 답하는 **절차**여야 한다.

## 6. 설계 원칙 (오늘 값을 치르고 얻은 것)

### 6.1 **실패 모드를 세지 말고 결과를 봐라** — 살아있음(liveness) 불변식

오늘 하루에 원인이 세 번 옮겨 다녔다(프롬프트 제한시간 → `busy` → ?).
**실패 종류마다 카운터를 다는 방식은 "아는 실패"만 막는다.**

그래서 이유를 묻지 않는 불변식을 둔다:
> **"온라인이라면서 T초 동안 한 줄도 못 내보냈으면 링크를 다시 세운다."**
> `busy` 든 `ERROR` 든 침묵이든 **아직 이름 없는 무엇이든** 여기에 걸린다.

**원인은 진단으로만 남긴다.** 원인별 제어 경로를 만들면 그게 다시 "아는 실패만 막는" 구조가 된다.

⚠ **예외 처리를 완화할 때는 회복 경로가 같이 사라지지 않는지 봐라.**
`busy` 를 실패로 안 세게 고쳤더니 **연속 카운터가 영원히 3에 도달하지 않아** 회복 경로가
사라질 뻔했다. **자해 하나를 없애면서 조용한 영구 정지를 만드는 교환**이었다.

### 6.2 상수는 **관측이 아니라 규약에서** 끌어오면 표본이 없어도 정당화된다

`TX_STALL_MS = 10초`의 근거는 관측 분포가 아니라 **서버 무프레임 판정(3.5초)** 과
**기존 3연속 실패 경로(약 3초)** 다 — 평범한 문제는 그쪽이 먼저 잡고, 무한 정지보다는 짧다.
관측 분포는 **다듬는 데** 쓰지 정하는 데 쓰지 않았다.

**사후 확인**(monitor, 1.13h): `busy` 런 3건 · 길이 1/2/3 · **최대 3** · 시도의 0.2%.
→ 10(≈10회)은 관측 최대의 3배 이상이라 **현재 자료와 모순이 없다.**
⚠ **"충분히 크다"로 확정하지 마라 — 런이 3건뿐이라 꼬리는 여전히 미지다.**
관측이 쌓이면 다시 본다.

### 6.4 어느 쪽으로 틀릴지 고를 수 있으면 **드러나는 쪽으로 틀려라** ★ 2026-08-16

임계값·기본값을 정할 때 **두 방향의 실수는 값이 같지 않다.** 값이 같지 않으면 가운데를
고르는 것이 아니라 **덜 나쁜 쪽으로 치우쳐 고르는 것**이 맞다.

실례(`SEND_OK_TIMEOUT_MS`):

| 틀리는 방향 | 결과 | 드러나나 |
|---|---|---|
| 너무 **일찍** 자른다 | 2단계 이전 동작으로 되돌아갈 뿐 | **`okto` 에 계상되어 드러난다** |
| 너무 **늦게** 푼다 | ESP 가 죽었는데 그만큼 눈이 먼다 | **조용히 손해가 난다** |

> **그래서 통계가 아니라 이 비대칭이 값을 정했다.**

**이 규칙은 임계값에만 쓰는 것이 아니다.** 2026-08-16 에 이 팀이 데인 것이 거의 전부
**"조용한 손해"** 쪽이었다 — 커밋에서 CR 이 벗겨진 원시 로그, `DEBUG=0` 이 관측을 통째로 끄는 것,
서버에서 승격 전 소켓의 줄이 카운터 없이 버려지는 경로, 기록되지 않은 실물 개입.
**전부 "틀렸다는 사실 자체가 안 보이는" 형태였다.**

### 6.5 추측으로 넉넉히 잡지 말고 **재고 고칠 수 있게** 잡아라 ★ 짝 규칙

값을 크게 잡아 안전을 사는 것은 **그 값이 맞는지 영영 모르게 만드는 대가**를 치른다.
대신 **그 값이 틀렸을 때 드러나는 계수기를 같이 둔다.**

`SEND_OK_TIMEOUT_MS=2000` 에는 `okto` 가 붙어 있다 — 구운 뒤 `okto` 가 미도달 기대치를
넘으면 **빡빡하다는 증거**가 된다. **추측으로 3000 을 잡는 것과 근본적으로 다르다.**

### 6.3 변경은 **하나씩** 넣는다

효과를 재려면 변수를 하나로 줄여야 한다. 오늘 하루 종일 그러지 못해 치른 값이 크다
(캐패시터·펌웨어 계열·DEBUG·프롬프트 제한이 동시에 달라 어느 것도 귀속하지 못했다).

### 8.2 판별자는 **하나로는 안 된다. 둘을 OR 로 쓴다** ★ 전수 검증 · 두 번 정정됨

| 판별자 | 실측 약점 | 단독 사용 |
|---|---|---|
| 부트 배너 `[System Ready, Vendor:...]` | **정상 부팅(16:59:57)에도 뜬다** | ❌ **오탐** |
| `CIFSR` 응답 `0.0.0.0` | 18:48:12 리셋에서 **CIFSR 응답 자체가 가비지**라 문자열이 안 나왔다 | ❌ **누락** |
| `CIFSR 3회 소진`(우리 쪽 상태) | 문자열이 아니라 **내부 카운터**라 응답이 깨져도 성립 | — |

> ### **IP 소실 = (`0.0.0.0` 을 봤다) OR (CIFSR 을 3회 물어도 쓸 IP 가 없었다)**
>
> ⚠ **`0.0.0.0` 은 리셋이 심할수록 놓치는 방향**이다 — 응답이 깨지기 때문이다.
> **즉 가장 중요한 사건을 골라서 놓친다.** 그래서 OR 이 필요하다.

`0.0.0.0` 이 뜨는 기전: ESP 가 제멋대로 죽으면 우리는 아직 자신을 online 이라 믿다가
사다리 **CIFSR 단부터 재진입**하는데 그때는 아직 AP 재결합 전이다.
**정상 부팅은 `CWJAP` 를 끝낸 뒤 CIFSR 로 오므로 절대 0 이 아니다.**

> ⚠⚠ **이 항목은 하루에 두 번 틀렸다.** 처음엔 *"배너와 CIFSR 둘 다 오탐 여지가 좁다"*,
> 다음엔 *"`0.0.0.0` 단독이면 된다"*. **둘 다 전수 검증에서 반례가 나왔다.**
> **교훈: 판별자를 채택하기 전에 두 가지를 전수로 확인하라 —**
> **① 정상 동작에서도 뜨는가(오탐) ② 진짜 사건에서 안 뜰 수 있는가(누락).**
> 하나만 확인하면 반드시 다른 쪽에서 틀린다.

### 8.2-1 세는 단위는 **사건이지 증상이 아니다** ★ 구현 함정

한 번의 리셋에서 `0.0.0.0` 이 여러 번 오고 그 뒤 3회 소진까지 가면 **한 사건이 네 번 세진다.**
그러면 카운터는 "사건 수"가 아니라 "증상 수"가 되어 **다른 도메인의 사건 계수와 정의가 어긋난다.**

> **IP 를 잃은 순간 한 번만 세고, 실제로 IP 를 되찾을 때 걸쇠를 푼다.**
> 이름이 같아도 세는 단위가 다르면 비교할 수 없다(§5.5).

### 8.3 기존 사다리가 기전 B 를 **이미 잘 처리한다** — 전용 탐지기가 필요 없는 이유 ★ 실측

18:24:56 CIFSR → 0.0.0.0   ← 사다리가 전진을 거부한다
18:24:58 CIFSR → 192.168.35.79  ← ESP 가 스스로 AP 에 재결합

### 8.4 함정 — **`DEBUG=0` 으로 구우면 A/B 를 가를 수 없다** ★ 코드 확인

A/B 판별자가 **전부 `#if DEBUG` 안**에 있다: `[AT] "…"` 원문 로깅 · `busy s...` ·
`CIFSR → 0.0.0.0` · `[TX-BUSY]` · `[TX-RESYNC]`.
**그리고 `espResets` 를 찍는 두 곳도 `#if DEBUG` 안이다**(monitor 확인) —
즉 리셋을 사건 단위로 정확히 세게 만들어 놓아도 **그 빌드에서는 출력이 없다.**

> `DEBUG=0` 은 플래시를 25%p 아끼지만 **관측 능력을 통째로 가져간다.**
> 2단계 효과 측정이 끝나기 전에 `DEBUG=0` 으로 굽지 마라 — 효과를 잴 수단 자체가 사라진다.

#### 8.4-1 ★ 더 센 이유 — **`DEBUG` 는 편의가 아니라 "비교 가능성"의 조건이다**

위 논거(못 잰다)보다 이쪽이 더 강하고, **A/B 시험을 설계하는 사람이 반드시 알아야 한다:**

> **A 팔을 도는 칩이 `DEBUG=1` 이면 B 팔도 `DEBUG=1` 이어야 한다.**
> B 를 `DEBUG=0` 으로 구우면 두 팔이 **"펌웨어 수정"과 "로깅 유무" 두 군데**에서 달라진다.
> 그러면 링크가 좋아져도 나빠져도 **어느 쪽 때문인지 귀속할 수 없다**(§6.3).

즉 `DEBUG` 는 **관측 설정이 아니라 실험 변수**다. 팔마다 다르게 두면 그 순간 시험이 깨진다.
플래시 절약용 `DEBUG=0` 빌드는 **A/B 가 끝난 뒤 시연·배포용으로** 쓴다.

#### 8.4-2 ✅ 해결 — 운영 계수기 `[CNT]` 는 **`DEBUG` 밖으로 뺐다** (2026-08-16 · 루트 지시)

**계수기 *변수* 는 원래도 `DEBUG` 밖이었다. 없던 것은 *읽는 경로* 였다.**
`DEBUG=0` 이면 찍는 줄이 전부 사라져 **관측이 3칸→1칸이 아니라 0칸**이 됐다.
그 빌드로 시연하면 장치가 **자기 ESP 리셋에 대해 눈이 먼 채로** 현장에 선다.

```
[CNT] up=<초> drop=<n> esprst=<n> resync=<n> sendfail=<n> okto=<n> skip=<n> online=<0|1>
```

- **60초 주기 · `#if DEBUG` 밖 · 전부 부팅 이후 누적**(구간값이 아니다 — 창을 잡으려면 두 줄을 뺀다)
- **바이너리로 확인했다**: `DEBUG=0` ELF 안에 `[CNT] up=`·`drop=`·`esprst=` 문자열이 실재한다
  (호스트 시험 통과는 증거가 아니라서 `strings` 로 직접 봤다)
- 비용: `DEBUG=0` 플래시 12732B → **13382B(+650B, +2%p)**. 시리얼은 60초에 약 60바이트.

> ### 경계 원칙 — **정수 카운터는 밖 · 장문 진단은 안**
> `[AT]` 원문 로깅은 **시리얼 대역과 플래시를 실제로 먹으므로** 안에 남긴다.
> 정수 카운터는 비용이 사실상 0 인데 **없으면 운영에서 못 센다.** 이 경계를 흐리지 마라.

⚠ **형식을 바꾸면 monitor 파서가 깨진다.** 칸을 **추가**하되 기존 칸 이름·순서는 유지하라.

**남은 더 나은 선택지**: 계수기를 **전선(S 프레임)에 실으면** 서버 로그에 영구 보관된다
(날짜·인스턴스 경계까지 있다). ⚠ **프로토콜 변경이라 socket·web 이 걸리고**, 펌웨어 수정과
같은 굽기에 섞으면 변수가 둘이 된다 — **별건으로 다뤄야 한다.**
