# 장치가 N 대가 되면 슬롯 구조는 어떻게 되나 (2026-08-17 · 계획 단계 선행 답변)

> **루트가 "먼저 답하지 않으면 나머지 설계가 헛돈다"로 지정한 질문**
> (`PLAN-QUEUE-2026-08-17.md` §계획에 들어갈 것 1번):
> *"슬롯 `t0` 는 장치 사건인데 장치가 N 대면 `t0` 가 N 개다."*
>
> ⚠ **코드는 고치지 않았다.** 창 A 판정 전이고 PLAN-QUEUE 가 착수를 금지했다.
> 이 문서는 **판단만** 낸다. 계획 REQ 가 오면 이 위에서 시작한다.

---

## 답 — **`t0` 가 N 개인 것은 문제가 아니다. 문제는 다른 데 있다.**

### 왜 문제가 아닌가 — 슬롯이 해결하는 것은 **장치 내부** 제약이다

슬롯 구조가 없애는 겹침은 **`SoftwareSerial` 반이중**이다(원장 §2.5·§10.1):
송신 중 `cli()` 로 수신 인터럽트가 꺼져 **그 장치가 자기 귀를 닫는 것**.

> ### **장치 A 의 UART 와 장치 B 의 UART 는 물리적으로 별개다.**
> **A 가 송신 중일 때 B 가 송신해도 아무 일도 일어나지 않는다.**

따라서 **각 장치가 자기 격자를 갖고, 서버가 `device_id` 별로 `t0` 를 따로 추적**하면 그대로 성립한다.
오히려 **자기교정(장치가 느려지면 그 장치의 서버 슬롯도 같이 밀림)이 장치별로 독립**이라 더 강건하다.

**서버가 져야 할 부담은 "슬롯 상태를 장치 수만큼 갖는 것"뿐이다.**
⚠ socket 의 `tick()` 이 200ms 해상도이므로 **N 개 위상을 그 해상도로 추적할 수 있는지**는 socket 판단이다.

## 🔴 진짜 문제 셋 — 전부 사용자 지시 7번("모듈이 랜덤한 아두이노에 있다")에서 나온다

### ① 하행 명령의 **동시성이 깨진다** ★ 가장 깊다

```
"차 들어옴 → 차단봉 열고 안내등 켜라"
   차단봉 = 장치1 의 모듈       안내등 = 장치3 의 모듈
   → 두 하행이 **서로 다른 슬롯**에 나간다
   → 두 장치의 슬롯 위상은 독립이므로 **최대 1.2초 어긋난다**
```

> ### **물리 동작이 어긋나면 사용자가 눈으로 본다.** 차단봉은 열렸는데 안내등은 아직 꺼져 있다.
> **이것은 통신 지연이 아니라 설계가 만드는 구조적 편차다.**

**슬롯 구조가 이 편차의 원인이다** — 슬롯당 1거래라는 규칙이 곧 "다음 기회는 1.2초 뒤"이기 때문이다.
⚠ **그렇다고 슬롯을 버리면 안 된다.** 그 규칙이 폭주를 막는 것이고, 편차는 **묶는 방법**으로 다뤄야 한다.

**생각해 둔 방향(계획에서 확정)**: 명령에 **실행 시각**을 실어 보낸다.
"지금 열어라"가 아니라 "`t` 에 열어라". 그러면 도착이 어긋나도 **동작은 같이 난다.**
⚠ 다만 **장치 간 시계 동기가 필요**해지고, 지금 우리에겐 없다(`millis()` 는 장치마다 원점이 다르다).
→ **동기 비용 대 편차 허용치**의 문제로 바뀐다. 사용자가 1.2초를 허용하면 아무것도 안 해도 된다.

### ② 한 구역의 **상태가 여러 장치에서 조립된다**

구역 A1 의 주차확인 센서는 장치1, 안내등 상태는 장치3 에 있다.
각 장치는 자기 슬롯에 **자기 부분만** 보고하므로 서버는 **부분 갱신 상태**를 본다.

> **최대 한 슬롯(1.2초) 동안 "센서는 새 값, 등은 옛 값"인 구역이 존재한다.**

⚠ **지금 `S` 프레임은 "한 장치가 10칸 전부를 안다"를 전제로 만들어져 있다**
(`S,<seq>,<occupied 10비트>,<reserved 10비트>,…`). **그 전제가 무너진다.**
→ **프레임 형식이 구역 단위가 아니라 모듈 단위가 되어야 한다.**

### ③ WiFi 는 **공유 매체다** — 슬롯이 이것까지 없애지는 않는다

슬롯은 UART 겹침만 없앤다. **N 대가 같은 AP 를 쓰면 무선은 공유된다.**
802.11 CSMA/CA 가 충돌 자체는 처리하지만 **지연이 늘어난다.**

> ### **그러면 `d1`·`d2`(전파 지연)가 N 에 따라 커지고, socket 의 창 계산이 N 의 함수가 된다.**
> 지금 socket 의 `cap` 은 **장치 1대 기준**이다(원장 §10.10).

⚠ **이건 계산으로 못 닫는다. 실측해야 한다.** 장치를 늘려 가며 `왕복 최대` 를 보는 것이 유일한 길이다.

## 그래서 주소 체계가 바뀌어야 한다 (계획 3번에 대한 선행 의견)

```
지금 :  device → slots[10]              한 장치가 자리 10칸을 통째로 안다
필요 :  module → (device, pin)          모듈이 어느 장치에 물렸는가
        zone   → [module, module, …]    구역이 어떤 모듈로 이루어지는가
```

> ### **전선 프레임의 주소는 `module` 이어야 한다. `zone` 은 서버가 조립한다.**

**근거**: 장치는 자기에게 물린 모듈만 안다. **구역이라는 개념 자체를 장치가 알 필요가 없다** —
알게 만들면 배선이 바뀔 때마다 펌웨어를 다시 구워야 한다(원장 §5.7 이 `SERVER_IP` 로 데인 그것과 같은 형태).

⚠ **한 줄 64B 상한은 그대로다**(§2.1). 모듈 주소가 길어지면 그 안에서 압박이 생긴다 —
`<device>.<module>` 을 문자열로 실으면 금방 찬다. **계획에서 자릿수를 계산해야 한다.**

## ESP 클래스를 `init`/`read`/`write` 셋으로 — ⚠ **셋으로는 접속 사다리가 갈 곳이 없다**

사용자 지시 1번에 대한 **사실 보고**다(지시를 뒤집는 것이 아니다).

지금 통신층이 하는 일은 셋이 아니라 **넷**이다:

| 지금 함수 | 하는 일 | `init`/`read`/`write` 중 어디? |
|---|---|---|
| `wifi.begin` + 부팅 사다리 | 초기화 | **`init`** ✅ |
| `pumpSerialRaw`→`handleLine` | 수신 | **`read`** ✅ |
| `sendPayload`(게이트·프롬프트·`busy`) | 송신 | **`write`** ✅ |
| **`netTick()` — 접속 사다리** | **시간이 지나며 진행하는 상태기계** | 🔴 **갈 곳이 없다** |

`netTick()` 은 `CIFSR → CIPMUX → CIPSTART → 실패 → CWJAP 부터 다시` 를 **시간 기준으로** 돈다.
읽는 것도 쓰는 것도 아니고 **혼자 진행한다.** 재접속·리셋 계단(`ladderFail`)이 전부 여기 있다.

> ### **`read()` 안에 넣으면 이름이 거짓이 된다** — "읽는다"고 적힌 함수가 소켓을 다시 세운다.
> 그리고 **읽을 것이 없을 때도 사다리는 돌아야 한다.** `read` 가 빈손일 때 return 하면 사다리가 멈춘다.

**제안(계획에서 확정): 넷으로 한다 — `init` · `read` · `write` · `tick`.**
`tick` 은 "시간을 준다"는 뜻이고 루프에서 부른다. 사용자 지시의 정신(**`setup` 에서 한 번, 루프에서 나머지**)은
그대로 지켜진다 — **루프에서 부르는 것이 둘에서 셋이 될 뿐이다.**

⚠ **3단 게이트·`busy` 대응은 `write` 안에 들어간다**(이미 `sendPayload` 안에 있다).
**그것들을 밖으로 꺼내면 안 된다** — 원장 §6.1(실패 모드별 제어 경로를 만들지 마라)에 걸린다.
