# 설계 — **게이트가 일찍 풀려 `busy` 폭풍을 만든다** (창4 실측 2/2)

> **소스 작업만. 굽지 않는다.** 창4 가 돌고 있고 그 자료가 값을 내고 있다.
> **상태: 설계안. 채택 전이다.** 값을 정하려면 §5 의 측정이 먼저 필요하다.

---

## 0. 🔴 먼저 — **루트가 지목한 경로가 아니다**

루트의 서술: *"게이트가 건너뛴 뒤 10초가 비고, 그동안 장치는 아무것도 안 보낸다."*

**원문은 다르다. 장치는 매 초 계속 보내고 있었다.** 그리고 **더미는 이 경로에 없다**(`[TX-RESYNC]` 0건).

> ### **그러므로 "더미 전략 수정"은 지금 관측된 고장을 안 고친다.**
> 더미 문제는 **A 창의 `[TX-RESYNC]` 경로**이고, 창4 의 고장은 **게이트/`busy` 경로**다.
> **둘 다 실재하지만 다른 것이다.** 섞으면 또 "고칠 것을 안 고치는" 굽기가 된다.

## 1. 관측된 사슬 — **두 건이 완전히 같다**

```
09:02:05  [TX] S,3747               ← 성공 전송. 게이트 무장(awaitingSendOk)
09:02:05  [AT] "AT+CIPSEND=40"      ← 명령 에코까지는 정상
              ⋯ 페이로드 에코도 SEND OK 도 안 온다 ⋯
09:02:06  [TX-WAIT] 이번 주기는 건너뛴다        ← 게이트가 1주기 양보 (설계대로)
09:02:07  [TX-WAIT] ★ 상한 초과 → 대기를 푼다   ← 🔴 okto++ · 2000ms 만료
09:02:07  [TX-BUSY] busy s...                   ← 즉시 CIPSEND → ESP 가 거부
09:02:07  [AT] " S,3747,…,33AT+CIPSEND=40" (53) ← 🔑 3747 의 페이로드 에코가 **이제서야** 왔다
              ⋯ busy 가 8초 더 ⋯ seq 3748 이 8번 반복, 한 프레임도 못 나감 ⋯
09:02:15  ★ 정지 감지: 10000ms (busy 8 / 무응답 0 / 거부 0) → CIPCLOSE
```

**두 번째(09:13:45~55)도 줄 단위로 같다.** `[TX] → 건너뜀 → 상한 초과 → busy 폭풍 → 정지 감지`.

### 🔑 결정적 한 줄

`09:02:07` 의 **53바이트 병합 줄**이 이 사건을 설명한다.
**우리가 포기한 바로 그 순간에 3747 의 페이로드 에코가 도착했다.**

> ### **ESP 는 죽지 않았다. 느렸을 뿐이다. 그리고 우리가 먼저 포기했다.**

## 2. ❌ 원장 §6.4 의 비대칭 표를 정정한다 — **내가 값을 잘못 매겼다**

원래 이렇게 적었다:

| 틀리는 방향 | ~~원래 적은 결과~~ | **실측된 결과** |
|---|---|---|
| 너무 **일찍** 자른다 | ~~2단계 이전 동작으로 되돌아갈 뿐~~ | 🔴 **`busy` 폭풍을 만든다.** 그리고 REQ-0116 이 `busy` 를 실패로 안 세므로 **3진아웃(약 3초)이 안 걸리고 살아있음 불변식(10초)까지 간다** |

**즉 일찍 자르는 비용이 내가 적은 것보다 크다.** 옛 칩이면 약 3초에 끝났을 것이 **10초가 된다.**

> ★ **그러나 이 정정을 가능하게 한 것이 `okto` 다**(§6.5). 값이 틀렸을 때 드러나는 계수기를
> 같이 둔 설계가 실제로 값을 냈다 — **추측으로 3000 을 잡았으면 이 사슬을 못 봤다.**

## 3. 무엇이 문제인가 — **두 층으로 갈린다**

| 층 | 문제 | 성격 |
|---|---|---|
| **원인** | 게이트가 **ESP 가 아직 보내는 중인데** 풀린다 | 상한 값이 모집단과 안 맞는다 |
| **증폭** | 풀린 뒤 **1초마다 `busy` 인 ESP 에 CIPSEND 를 계속 쏜다** | 물러설 줄 모른다 |

증폭만 고치면 회복이 여전히 느리다.

## 4. 설계안 — **둘 다 이유를 묻지 않는 형태로** (§6.1 준수)

### 안 A — 상한을 실측에 맞춘다 (원인 층)

`SEND_OK_TIMEOUT_MS` 를 **관측된 "느린 전송" 분포를 덮도록** 올린다.
⚠ **값은 §5 의 측정 전에는 정하지 않는다.** 추측으로 올리면 §8.4-3 의 가짜 정밀도다.

**죽음 탐지가 늦어진다는 반론은 성립하지 않는다** — **살아있음 불변식(이유 불문)이 그대로 뒤를 받친다.**
게이트는 *첫 반응*을 늦출 뿐이고 **탐지 자체를 없애지 않는다.**

### 안 B — **실패한 뒤에는 물러선다** (증폭 층)

**이유를 묻지 않는다.** `busy` 든 거부든 무응답이든 **직전 송신 시도가 실패했으면 다음 시도를 늦춘다.**

```
성공     → 다음 주기 = HEARTBEAT_MS (지금 그대로)
실패     → 다음 시도까지 최소 SEND_FAIL_BACKOFF_MS 를 둔다   ← 이미 있는 상수를 하트비트 경로에도 적용
```

> ⚠ **`busy` 전용 카운터를 만들지 않는다.** §6.1 이 금지한 "원인별 제어 경로"다.
> **"실패했다"만 보고 물러선다.** `busy` 는 로그로만 남는다(지금과 같다).

⚠ **이미 있는 것과의 관계**: `SEND_FAIL_BACKOFF_MS=500` 이 `changeAt` 에만 걸려 있어
**하트비트 경로에는 사실상 적용되지 않는다**(`client.ino:2488`). **그 구멍을 막는 것**이지 새 개념이 아니다.

### 안 C — `TX_STALL_MS` 를 낮춘다 ⚠ **지금은 반대한다**

10초가 길게 느껴지지만, **A·B 를 하면 폭풍 자체가 줄어든다.** 원인을 안 고치고 마감만 당기면
**정상 지연까지 끊는다.** **A·B 를 구워 보고 그때도 10초까지 가면 그때 다시 본다.**

## 5. 🔴 값을 정하려면 이 측정이 먼저다 (monitor 요청안)

**질문 하나뿐이다:**

> **게이트가 상한 초과로 풀린 시점부터, 그 전송의 `SEND OK`(또는 페이로드 에코 완결)까지 얼마였나?**
> = **"얼마나 더 기다렸으면 됐나"**

- 모집단: `[TX-WAIT] ★ 상한 초과` 가 찍힌 **전 건**(창4 기준 `okto` 누적 6건)
- 1초 해상도 그대로. **평균·백분위수 금지**(§8.4-3)
- **끝내 안 온 건수도 따로** — 그건 상한을 올려도 소용없는 부류다

**판정 규칙(측정 전에 고정한다):**

| 결과 | 결론 |
|---|---|
| 대부분 **+1~2초** 안에 왔다 | **안 A 채택.** 상한을 그 꼬리 위로 올린다 |
| 대부분 **끝내 안 왔다** | **안 A 기각.** 올려도 손해만 본다 → **안 B 만** |
| 갈린다 | **안 B 를 먼저** 굽고 A 는 자료를 더 본다 |

## 5-R. 🔴 측정 결과와 판정 — **안 A 를 기각한다** (2026-08-17 · REQ-0154)

출처: `monitor/out-win4-okto.txt` · 도구 `monitor/okto_wait.py`

### 5-R.1 등록한 규칙이 **퇴화했다** — 규칙은 안 고쳤다

```
1차 측정:  a.곧왔다 1 · b.끝내안옴 0 · c.짝못지음 24   (전부 Δ=0)
```
**결함이 아니라 설계된 거동이다** — 상한이 만료되면 **즉시** `CIPSEND` 를 쏘므로
**조용한 창이 아예 안 생기고** (c) 가 Δ=0 에서 항상 먼저 참이 된다.

> ### **즉 "얼마나 더 기다렸으면 됐나"는 이 로그로 관측할 수 없다.**
> **우리 행동이 계를 바꾸기 때문이다.** 가만히 기다렸으면 어땠을지는 **반사실**이고 자료에 없다.

### 5-R.2 보조 측정 (`CIPSEND` 를 지나쳐 다음 `SEND OK` 까지)

```
a.왔다 23건   Δ: 0s×9 · 1s×5 · 2s×1 · 3s×4 · 4s×2 · 5s×2   최대 5s
b.끝내안옴 2건  →  09:02:07 · 09:13:47
```

> ### 🔑 **끝내 안 온 2건이 정확히 링크를 죽인 그 두 사건이다.**
> **나머지 23건은 5초 안에 `SEND OK` 가 왔고 아무 일도 없었다.**

### 5-R.3 ❌ **안 A(상한 올리기) 기각** — 근거는 규칙이 아니라 물리다

1. **해를 낸 2건은 `SEND OK` 가 *끝내* 안 왔다.** **더 기다려도 안 온다.** 상한을 올리면
   **같은 폭풍에 더 늦게 들어갈 뿐**이다.
2. **우리 `CIPSEND` 가 `SEND OK` 를 막는 것도 아니다** — **23건에서는 똑같이 쏘고도 왔다.**
   (이 23건이 대조군 역할을 한다. 그래서 2건은 **진짜로 다른 사건**이다.)
3. **올리는 비용은 확실하다**: 무해한 23건 전부를 최대 6초씩 막는다. 그리고 `TX_STALL_MS`(10초)에 근접한다.

### ⚠ 5-R.4 **내가 등록한 규칙이 잘못 지정돼 있었다 — 글자대로 하면 해롭다**

등록 규칙: *"(a)가 대부분이고 +1~2초 안이면 상한을 올린다."*
**글자대로 읽으면 (a)=23 이 대부분이고 꼬리가 5초이므로 → "6초로 올려라"** 가 된다.
**그 답은 위 세 근거로 해롭다.**

> ### **원인: 규칙을 *다수*에 걸었는데 해는 전부 *꼬리 2건*에 있었다.**
> **"대부분이 어땠나"가 아니라 "해를 낸 것이 어땠나"로 걸었어야 했다.**
>
> ★ **교훈**: 사전 등록은 **모집단과 결과 지표를 같이** 고정해야 한다.
> **판정 규칙만 고정하고 "무엇이 해인가"를 안 고정하면, 규칙이 엉뚱한 부분집합을 가리킨다.**
> **그리고 이 오류는 자료를 본 뒤에야 보인다** — 그래서 규칙을 고치는 것과 구별이 어렵다.
> **구별법: 새 근거가 자료의 *어느 값*이 아니라 *구조*(반사실 불가·대조군 존재)에서 오는가.**

⚠ **이 정정은 루트에 보고하고 승인을 받는다. 내가 조용히 바꾸지 않는다.**

### 5-R.5 ✅ **안 B(실패 후 물러섬) 채택 근거가 강해졌다**

해를 낸 2건에서 실제로 나쁜 것은 **`SEND OK` 가 안 온 것**이 아니라
**그 뒤 8초 동안 매 초 `busy` 인 ESP 를 두드린 것**이다. **안 B 가 정확히 그것을 막는다.**

⚠ **Δ=0 인 9건을 "0초만 더 기다리면 됐다"로 읽지 마라**(monitor 경고).
**같은 초 안**이라는 뜻이고 **직후 `CIPSEND` 의 응답일 수도 있다.**

### 5-R.6 같은 두 사건이 **두 가지 증거로 동시에 쓰인다** — 섞지 마라

| 무엇의 증거인가 | 근거 |
|---|---|
| **기전 C 수정이 작동한다** | 인쇄값이 `10000ms` 다(언더플로 없음) |
| **그 위에서 상한이 짧다** | 그 10초가 `busy` 폭풍으로 채워졌다 |

**둘 다 참이다.** 하나를 다른 하나의 반박으로 쓰지 마라(monitor 지적).

## 5-S. 🔴 **안 B 를 철회한다 — 기전을 안 건드린다** (2026-08-17 설계 중 발견)

안 B 는 *"실패한 뒤에는 물러선다"* 였다. **설계하려고 소스를 다시 보니 성립하지 않는다.**

**폭풍의 실체**: ESP 가 **앞 전송을 끝내지 못한 상태**다(`busy s...` = "아직 보내는 중").
그리고 그 두 건은 monitor 측정에서 **`SEND OK` 가 끝내 안 온 `b` 갈래**다.

> ### **우리가 재시도를 늦춰도 ESP 의 전송이 빨리 끝나지 않는다.**
> 재시도는 **무용하지만 유해하지도 않다.** `busy s`(전송 중)는 `busy p`(명령 처리 중)와 달리
> **우리 재시도가 만드는 것이 아니다.** → **물러서기는 원인에 안 닿는다.**

⚠ 그리고 `SEND_GAP_MS` 가 이미 연속 송신을 막고 있다(§3.4-3 · ACK→S 에서 실제로 작동).
**"너무 촘촘히 쏜다"는 문제는 이미 다뤄져 있었다.**

## 5-T. ✅ **진짜 결함은 "상한이 만료됐을 때 무엇을 하는가"다**

지금 코드는 상한이 만료되면 **"옛 동작으로 복귀"** 한다 — 즉 **막힌 ESP 에 다시 쏘기 시작한다.**

```
0 ~ 2초   게이트가 조용히 기다린다        ← 옳다
2초       상한 만료 → 옛 동작 복귀        ← 🔴 여기서 두들기기 시작한다
2 ~ 10초  매 초 CIPSEND → busy 8회        ← 무용한 8초
10초      살아있음 불변식 → 복구           ← 결국 이것이 고친다
```

> ### **안 A(상한 올리기)와 안 B(물러서기)가 둘 다 부분적이었던 이유가 이것이다.**
> **상한만 올리면 두들기기가 늦게 시작될 뿐이고, 물러서기만 하면 여전히 10초를 기다린다.**
> **고칠 자리는 값도 재시도 간격도 아니라 *만료 시의 행동*이다.**

### 안 C — **3단 게이트** (이것을 제안한다)

| 단계 | 구간 | 행동 | 근거 |
|---|---|---|---|
| 1 | `0 ~ T1` | **조용히 기다린다**(지금 게이트 그대로) | 정상 지연을 안 자른다 |
| 2 | `T1 ~ T2` | **계속 조용히 기다린다** ← **신설** | 관측된 느린 전송 23/25 가 **5초 안에 회복**했다 |
| 3 | `> T2` | **복구로 간다**(`startSocketRecovery`) | 끝내 안 오는 건은 기다려도 소용없다 |

**핵심은 2단계다. 지금은 그 구간에서 두들긴다.**

**효과(실측 25건에 대입):**
- **무해했던 23건** → 두들기지 않고 조용히 회복. **`busy` 폭풍이 애초에 안 생긴다**
- **해를 낸 2건** → **`T2` 에 복구**. 10초가 아니라 `T2`

**이유를 묻지 않는다** — `busy` 든 침묵이든 **"`SEND OK` 가 왔는가" 하나만 본다**(§6.1 준수).
**`busy` 전용 카운터를 만들지 않는다.**

#### 값 — **`T2` 는 실측에서 나온다. `T1` 은 그대로 둔다**

```
T1 = SEND_OK_TIMEOUT_MS = 2000    (그대로. 이 값이 문제가 아니었다)
T2 = ?  ← 관측된 (a) 꼬리가 5초다(최대 Δ=5s). 그 위여야 23건을 안 자른다
```
⚠ **`T2` 를 정하기 전에 알아야 할 것**: 위 25건은 **1초 해상도**다. `Δ=5s` 는 실제 (4,6)초다.
**따라서 `T2` 는 최소 6초 이상**이어야 관측된 정상 회복을 안 자른다.

#### 🔴 그런데 여기서 구조적 충돌이 하나 드러난다 — 미리 적는다

```
서버 무프레임 판정 : 3.5초
관측된 정상 느린 전송 : 최대 (4,6)초
```
> ### **두 값이 겹친다. `T2` 를 어떻게 잡아도 그 사이를 만족시킬 수 없다.**
> `T2 ≥ 6초` 면 **정상 느린 전송을 살리지만 서버는 그 동안 "무프레임"으로 본다.**
> `T2 ≤ 3.5초` 면 **서버에는 안 보이지만 정상 회복 23건 중 일부를 자른다.**

**→ 이건 우리 도메인 안에서 못 푸는 교환이다.** 선택지는 둘:
1. **`T2 ≥ 6초` 로 두고, 서버의 "무프레임" 표시가 몇 초 뜨는 것을 받아들인다** (프레임은 안 잃는다 — `seq` 연속)
2. **서버 무프레임 판정을 늘린다** — socket 도메인이고 시연 화면에 영향

**내 권고는 1 이다.** `seq` 가 연속이라 **자료 손실이 없고**, 표시가 몇 초 뜨는 것은 되돌릴 수 있다.
⚠ **그러나 이건 socket·화면 쪽 결정이다. 내가 정하지 않는다.**

## 5-U. 🔴 **게이트가 닫혀 있으면 ACK 가 버려진다** — 안 C 의 전제조건 (2026-08-17)

**소스 확인:**
```c
handleLine():  cachePut(rid, s0, s1, result);   // ← 상태는 커밋되고 캐시에도 들어간다
               sendAck(rid, s0, s1, result);    // ← 🔴 반환값을 안 쓴다
               return;
sendLine():    if (awaitingSendOk && 경과 < 상한) { sendSkips++; return false; }   // ← ACK 도 여기 걸린다
```

> ### **장치는 하행을 받고 적용까지 하는데, ACK 만 조용히 사라진다.**
> **`T2` 를 늘리면 그 창이 그만큼 길어진다** — 그래서 **큐 없이 `T2` 를 늘리면 악화된다.**

### 🔑 5-U.1 그런데 **재시도 장치는 이미 있다** — 큐가 생각보다 훨씬 작다

```c
int8_t hit = cacheFind(rid);
if (hit >= 0) { sendAck(cache[hit]...); return; }   // §4.2 멱등 캐시
```
**서버가 재전송하면 캐시가 같은 ACK 를 다시 만든다.** **즉 "무엇을 보낼지"는 이미 보존돼 있다.**
**잃는 것은 "보내야 한다는 사실" 하나뿐이다.**

> ### **그러므로 일반 송신 큐가 아니라 *보류된 ACK 의 rid 목록*이면 된다.**
> 내용은 캐시에서 다시 만든다. **엔트리는 `uint16_t rid` 하나.**

⚠ **RAM 이 빠듯하다** — 실측 `[RAM] 최저 여유 782 B`. **깊이 4면 8바이트**로 끝난다.
일반 큐(프레임 통째)로 만들면 **한 칸이 64바이트**라 같은 깊이에 32배다. **캐시 재사용이 그것을 없앤다.**

### 5-U.2 설계

| 항목 | 값 | 근거 |
|---|---|---|
| 자료구조 | `uint16_t pendingAckRid[4]` + 머리/꼬리 | 캐시가 내용을 갖고 있다 |
| **깊이** | **4** | 60초 간격 주입에서는 1이면 충분. **사람이 연달아 누르는 경우**를 위해 4 |
| 넣는 때 | `sendAck()` 가 **실패**를 돌려줬을 때 | ⚠ **반환값을 쓰기 시작한다 — 지금은 버린다** |
| 빼는 때 | **게이트가 열렸을 때, `statusTick` 보다 먼저** | 하행이 상행보다 앞이라는 기존 순서와 같다 |
| **가득 차면** | **가장 오래된 것을 버리고 `ackdrop` 을 센다** | ⚠ **조용히 버리면 지금과 같아진다** |
| **소켓이 끊기면** | **비운다** | 새 소켓에서 옛 `rid` 에 답하면 안 된다 (`awaitingSendOk=false` 와 같은 자리) |
| 계수기 | `[CNT]` 에 **`ackq`**(보류 중) · **`ackdrop`**(폐기) 추가 | 틀리면 드러난다(§6.5) |

#### ⚠ 5-U.3 멱등 캐시와 **겹치지 않는다** — 확인했다

| | 무엇을 하나 |
|---|---|
| **멱등 캐시** | *"같은 `rid` 가 또 오면 **상태를 다시 바꾸지 말고** 같은 답을 만든다"* |
| **ACK 큐** | *"만든 답을 **못 보냈으면 나중에 보낸다**"* |

**하나는 중복 수신, 하나는 송신 지연.** 직교한다. **큐가 캐시를 읽어 쓰므로 정합도 자동이다.**

#### ⚠ 5-U.4 게이트에서 ACK 를 **면제하는 방법은 안 된다**

*"ACK 는 작으니 게이트를 건너뛰게 하자"* 가 자연스러워 보이지만 **소용없다.**
게이트가 닫힌 이유는 **ESP 가 아직 전송 중**이라서다. 면제해도 **`busy` 로 거부된다.**
→ **미루는 것 말고 답이 없다. 큐가 맞다.**

#### 5-U.5 이 결함이 만든 관측 — 사용자 재현(13:20:22)

```
13:20:22  →ARD R,31,B5     장치가 받고 적용 · ACK 는 게이트에 막혀 버려짐
13:20:23  →ARD R,31 재전송  캐시 적중 → ACK 재생성 → 또 막힘
13:20:25  →ARD R,31 재전송  또
13:20:24  ! 무프레임 3500ms → 오프라인 판정
13:20:31  세션 종료
```
> **서버는 세 번 다 "못 받았다"로 읽었고, 장치는 세 번 다 받고 세 번 다 답을 못 했다.**
> ⚠ **재전송이 있어도 소용없다** — 재전송분도 **같은 닫힌 게이트**를 만난다.
> **그래서 서버측 재전송은 이 결함의 해법이 아니다.**
