# 2단계 설계 — `SEND OK` 를 실제로 기다린다 (미구현)

> 상태: **설계만. 코드 없음. 플래싱 없음.** (REQ-0116 2단계 · 2026-08-16)
> 대상: `조별과제샘플/client.ino` 송신 경로
> 1단계(REQ-0116, 커밋 d805f43)와 **섞지 않는다** — 섞으면 어느 쪽이 효과를 냈는지 못 가른다.

---

## 🔴 먼저 — **1단계가 만든 정지 위험 하나. 이건 설계가 아니라 결정이 필요하다**

1단계에서 `busy` 를 실패로 세지 않게 했다. 의도는 옳지만 **부작용이 하나 생겼다.**

**변경 전**: `busy` 가 계속 오면 → 3회 연속 실패 → `goOffline()` → 소켓 재수립.
즉 **엉뚱한 이유였지만 어쨌든 빠져나오는 길**이 있었다.

**변경 후**: `busy` 는 세지 않는다 → **연속 카운터가 영원히 3에 도달하지 않는다.**

> ### 즉 ESP 가 계속 `busy` 로만 답하는 상태에 빠지면 **회복 경로가 없다.**
> 장치는 자신을 `online` 이라 믿고, 프레임은 한 줄도 못 나가고, 서버는 무프레임으로 본다.
> **1단계 이전에는 3초 만에 끊고 다시 붙었을 상황이, 이제는 무한정 지속될 수 있다.**

### 얼마나 현실적인가 — 정직하게

- **낮다고 본다.** 실제 죽은 링크는 보통 `Unlink`·`CLOSED`·`link is not valid` 로 드러나고
  그 경로들은 그대로 살아 있다(`startSocketRecovery()`).
- 그러나 **배제할 수는 없다.** ESP 가 TCP 재전송에 물려 "전송 중"에서 안 빠져나오면
  `busy s...` 만 반복될 수 있다. 그리고 그것이 정확히 우리가 관측한 상태다.
- **위험의 성질이 나쁘다**: 확률은 낮지만 걸리면 **조용히 영구 정지**다. 로그에는
  `[TX-BUSY]` 만 쌓이므로 보고 있으면 보이지만, 아무도 안 보면 그냥 멈춰 있다.

### 제안 — **`busy` 에도 상한을 둔다** (1단계에 넣을지 2단계로 갈지는 루트 판단)

```
연속 busy 가 N회(또는 T초) 이상이면 → 그때는 링크 이상으로 보고 goOffline()
```

- **연속 실패 카운터와 별도 카운터**로 센다. 둘의 의미가 다르기 때문이다 —
  하나는 "링크가 죽었을 것", 다른 하나는 "ESP 가 계속 바쁘다".
- 성공하면 **둘 다** 0 으로 되돌린다.
- 값은 넉넉하게 잡는다. `busy` 는 정상적으로도 나므로 짧게 잡으면 1단계를 무효화한다.
  **1Hz 하트비트 기준 10초(=10회) 정도**가 출발점으로 적당해 보인다 —
  서버의 무프레임 판정(수 초)보다는 확실히 길고, 영구 정지보다는 확실히 짧다.
- ⚠ 이 값은 **추측이다.** A 구간에서 `[TX-BUSY]` 의 실제 연속 길이 분포가 나오면
  그걸 보고 정하는 것이 맞다. **monitor 가 그 분포를 뽑아 주면 근거 있는 값이 된다.**

---

## 1. 고칠 것 — 고정 80ms 는 **앎을 추측으로 대체한 것**이다

```c
static const uint8_t SEND_GAP_MS = 80;   // 연속 CIPSEND 사이 최소 간격 (busy p... 회피)
...
while (millis() - lastSendEndAt < SEND_GAP_MS) pumpSerialRaw();
```

`lastSendEndAt` 은 **우리가 쓰기를 끝낸 시각**이다. 그런데 우리가 알아야 하는 것은
**ESP 가 WiFi 로 전송을 마친 시각**이다. 이 둘은 같지 않고, 망이 느릴수록 더 벌어진다.

**ESP 는 그 시각을 이미 알려준다 — `SEND OK`.** 지금 두 계열 어느 쪽도 그걸 읽지 않는다.

```
지금 : CIPSEND → '>' → 페이로드 → (80ms 세고) → 다음 CIPSEND      ← 추측
목표 : CIPSEND → '>' → 페이로드 → SEND OK 확인 → 다음 CIPSEND     ← 사실
```

**`busy s...` 는 이 추측이 틀린 순간에 나는 것이므로, 이걸 고치면 원인이 사라진다.**

## 2. 반드시 **비블로킹**이어야 한다

`SEND OK` 를 그 자리에서 기다리면 안 된다. 하트비트가 1Hz 인데 전송 완료가 수백 ms 걸리면
**루프가 통째로 밀린다.** 하행(`+IPD`) 처리도 같이 밀려 ACK 가 늦어진다.

```
sendLine() 성공 → awaitingSendOk = true, sendStartedAt = millis()  → 즉시 반환
다음 송신 시도 시점:
    awaitingSendOk 가 여전히 true 면  → 이번 주기는 보내지 않는다(건너뛴다)
    SEND OK 수신                     → awaitingSendOk = false  (다음 송신 허용)
    SEND FAIL 수신                   → awaitingSendOk = false + **실패로 센다**(아래 3)
    상한 시간 초과                    → awaitingSendOk = false + 안전망(아래 4)
```

`SEND OK`/`SEND FAIL` 은 `handleLine()` 에서 잡는다. 다만 **송신 직후의 줄은 `pendLine` 으로
미뤄지므로**(`inSend`), 그 경로에서도 확인되게 해야 한다. **1단계에서 `pendLine` 이
첫 줄만 담는다는 것을 확인했으니 여기서도 같은 함정에 빠지지 않게 주의한다.**

## 3. `SEND FAIL` 을 세야 한다 — **지금 아무도 안 보고 있다**

`SEND FAIL` 은 **프롬프트까지 정상으로 받고 페이로드도 썼는데 전송이 실패한 것**이다.
`busy`(거부)나 무응답(프롬프트 못 봄)과 **완전히 다른 사건**이고, **진짜 전송 실패**다.

지금은 이 신호가 오면 로그만 남는다. 즉 **성공으로 세어 연속 카운터를 0 으로 되돌린 뒤**
실제로는 프레임이 안 나간 상태가 된다. 2단계에서 `noteSendResult(false)` 로 세야 한다.

> 이건 1단계가 만든 것이 아니라 **원래 있던 구멍**이다. 다만 1단계로 `busy` 가 빠지면서
> **실패를 감지하는 경로가 줄었으므로 상대적으로 더 중요해졌다.**

## 4. 안전망 — `SEND OK` 가 안 올 수도 있다

ESP AT 펌웨어 판본에 따라 `SEND OK` 를 항상 주지 않거나, 응답이 유실될 수 있다
(반이중 + SoftwareSerial RX 64바이트 버퍼 — 송신 중에는 못 받는다).
**`awaitingSendOk` 에 상한 시간을 두고, 넘으면 풀어 준다.** 상한을 두지 않으면
2단계가 1단계보다 더 나쁜 정지를 만든다.

- 상한을 넘긴 경우는 **`SEND_GAP_MS` 시절과 같은 상태**이므로 그때의 동작으로 되돌아간다.
- 이 경우를 **로그로 남긴다** — 상한 초과가 잦다면 `SEND OK` 를 못 받고 있다는 뜻이고,
  그건 그 자체로 발견이다.
- `SEND_GAP_MS` 는 **없애지 말고 하한으로 남긴다.** `SEND OK` 가 즉시 와도 연속 CIPSEND 를
  너무 촘촘히 쏘면 `busy p...` 가 난다 — 원래 그걸 막으려고 있던 값이다.

## 5. 검증 방법 (플래싱 뒤)

1. **`[TX-BUSY]` 가 사라지거나 크게 줄어야 한다.** 이게 2단계의 직접 목표다.
2. `[NET] 전송 실패 n/3` 의 빈도 — 1단계 후 값과 비교한다.
3. **새 연결(ACCEPT) 발생률** — monitor 의 동일 계수 규칙으로. 최종 지표다.
4. **하행 도달 시험을 다시 한다**(socket, REQ-0115 와 같은 방식). 송신 타이밍을 바꾸므로
   **수신 경로가 영향을 받을 수 있다.** 5/5 가 유지되는지 확인해야 한다.

⚠ **1단계 효과를 먼저 측정하고 나서 2단계를 넣는다.** 같이 넣으면 못 가른다.

## 6. 이 설계가 건드리지 않는 것

- **수신 경로** — 하행은 5/5 로 동작이 확인됐다(REQ-0115). 건드릴 이유가 없다.
- **`PROMPT_TIMEOUT` 의 더미 채움** — 그 갈래는 여전히 필요하다(ESP 가 데이터 모드일 수 있다).
- **`RX_CAP=96`** — `CIPMUX=1` 로 바뀔 때를 덮는 여유이므로 줄이지 않는다.
