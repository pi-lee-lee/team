# web 설계 — 상태 모형을 모듈 단위로 · 격자 렌더링 (REQ-0181 · 2026-08-18)

**명세다. 코드는 한 줄도 고치지 않았다.** 시험 인스턴스도 띄우지 않았다(창 B 가 돌고 있다).

> **이름은 내가 만들지 않았다.** `Zone` · `zone id` · `kind: parking|entrance|exit` ·
> `modules: [(devid, name)]` · `cell → zone id` 는 **socket 의 브릿지 명세(REQ-0179)** 가 세운 것을
> 그대로 쓴다. 값이 갈리면 **원본(socket)이 이긴다.**
> 🔑 **왜 이 문단이 맨 위인가**: 어제 `cap` 이 한 문서 안에서 두 뜻, 팀 전체로 세 뜻이었고
> 그 모호함이 **내 원장에 틀린 항목을 만들었다**(원장 §5.27). 같은 개념에 두 이름이 붙는 것을
> 먼저 막는다.

**전제로 받는 것**(내가 정한 것이 아니다):

- REQ-0179 §① — 모듈의 **전역 신원은 `(devid, name)` 복합 키**다. **`name` 만으로 조회 금지.**
- REQ-0179 §① — 모듈 종류: 주차확인센서 · 안내등 · 유도등 · 차단봉 · 입출차센서
- REQ-0179 §① — **격자는 `cell → zone id` 이고 좌표와 신원은 독립**이다(자리를 옮겨도 같은 자리).
  → 이것이 내 원장 §5.32.1 의 열린 물음("ID 와 좌표를 가르는가")을 **가른다 쪽으로 닫는다.**
  **내가 닫은 것이 아니라 REQ-0179 가 닫았다.**
- REQ-0179 §④ · 사용자 확정 — **노드는 완전 독립**. 한 노드의 오프라인은 **그 노드가 담당하는
  모듈만** 미상으로 만든다.

**확정된 계약 다섯**은 원장 `docs/web/LEDGER.md` **§5.32** 에 있다. **여기 복사하지 않는다** —
같은 내용이 두 곳에 있으면 하나가 낡고, 그게 오늘 REQ-0159 의 원인이었다.

## 1. 상태 모형 — `known` 을 모듈 단위로 내린다

### 1.1 지금 무엇이 자리 단위인가 (코드 근거)

```
normalizeSnapshot()   known: bySlot.has(id)          ← **자리 하나 = 불리언 하나**
                      (없는 자리는 known:false 로 합성한다)
tileView(slot)        if (!state.snapshot || !slot.known) → view:'unknown' / '상태 미상'
                      const deviceDown = device.online === false   ← **하나가 전 칸을 정한다**
buildGrid()           for (const id of SLOT_IDS)      ← DOM 을 미리 만든다
```

**이 셋이 개정에서 손대는 자리 전부다.** (행 번호로 안 적는다 — 판본마다 썩는다. 식별자로 찾아라.)

### 1.2 개정 뒤 모형

**자리의 상태는 단일 값이 아니다. 모듈별 `(값, 아는지)` 의 모음이다.**

```
Zone
  zone id · kind
  modules: [ { devid, name, type, value, known } , … ]
  actionable      ← 🔴 서버가 계산한다 (§1.3)
  blocked_reason  ← 서버가 준다. 화면은 문구만 고른다
```

🔴 **`known` 이 모듈마다 따로 있어야 하는 이유**: 노드가 독립이므로 **한 자리 안에서
"주차확인센서는 알고 안내등은 모른다"가 정상**이다. 자리 단위 불리언은 이 상태를 **표현할 수
없어서** 둘 중 하나로 거짓말한다 — 전체를 미상으로 덮거나, 모르는 것을 아는 것처럼 그린다.

### 1.3 🔴 조작 가능성은 **서버가 계산한다** — 화면이 조합하지 않는다

REQ-0179 §③ 이 규칙을 정했다: *"조작 가능성은 모듈 단위로 판정한다(그 모듈의 노드가 살아
있는가)."* **그 규칙은 받는다. 다만 "누가 계산하나"는 따로 정해야 한다.**

**web 의 요구: 서버가 `actionable` + `blocked_reason` 을 계산해서 준다.**

| | 대가 |
|---|---|
| 화면이 모듈 목록을 조합해 판정 | 🔴 **조합 규칙이 두 곳에 생긴다**(서버 하행 라우팅 + 화면). 갈리면 화면이 **거짓 허용**을 낸다 — 닿지 않는 노드로 하행이 나가고, 그 하행은 큐에 쌓여 재전송까지 돈다 |
| **서버가 판정** | 규칙이 한 곳. 화면은 받은 값을 쓴다 |

**근거는 이미 팀 규율이다**: 원장 §5.14 — *"화면의 타임아웃은 서버가 준 상한에 묶는다.
화면이 짐작하지 않는다."* `ack_budget_ms`(§5.26)가 그 규율을 적용해 실제로 구멍 하나를
막았다. **같은 형태의 문제이므로 같은 해법을 쓴다.**

⚠ **이 항목이 socket 합의가 필요한 단 하나다.** 나머지는 표시 문제라 내 도메인에서 닫힌다.

⚠ **그렇다고 모듈 목록이 필요 없는 것은 아니다** — **판단은 서버, 표시는 모듈 목록**이다.
차단봉·안내등·유도등을 **보여 주려면** 목록이 있어야 한다. **둘을 섞으면 안 된다.**

## 2. 🔴 `⏱` / `⚠` 를 모듈 층으로 — **두 축으로 가른다**

### 2.1 먼저, 왜 단순 확장이 안 되는가

원장 §5.31 에서 `⏱`(모른다) 대 `⚠`(고장)을 갈랐다. 그때는 **폴백일 때만** 나오는 상태였다.
개정 뒤에는 **미상이 상시로 존재하는 정상 상태**가 된다(노드 독립).

그러면 요구가 **서로 민다**:

- 미상을 경보로 그리면 → **상시 켜진 경고**가 되고 아무도 안 읽는다(원장 §3.1 이 배너를
  "정상에서 침묵"하게 만든 이유가 그것이다).
- 미상을 너무 조용하게 만들면 → **REQ-0067 이 막으려던 것**(모르는 것을 아는 것처럼)으로 돌아간다.

### 2.2 해법 — **기호는 원인을, 강조는 영향을 나타낸다**

**한 축으로 풀려던 것이 모순의 원인이었다. 두 축으로 가른다.**

| | 축 | 값 |
|---|---|---|
| **기호축** | 원인 | `⏱` 모른다 · `⚠` 고장/차단 확정 · (없음) 정상 |
| **강조축** | 영향 | **조작을 막는가** — 막으면 눈에 띄게, 안 막으면 조용한 배경 |

이러면 네 조합이 나오고 **각각이 다른 것을 말한다**:

```
⏱ + 눈에 띔   미상이 조작을 막는다      예: 주차확인센서 미상 → 예약 판정 불가
⏱ + 조용      미상이지만 조작과 무관    예: 안내등 미상 (상시 정상 상태 · 배경)
⚠ + 눈에 띔   고장이 조작을 막는다      예: 차단봉 고장 보고
⚠ + 조용      고장이지만 조작과 무관    예: 유도등 하나 고장
```

🔑 **강조축의 값을 화면이 계산하지 않는다** — §1.3 의 `actionable`/`blocked_reason` 에서
**그대로 나온다.** 즉 **§1.3 을 정하면 이 규칙이 파생으로 따라온다.** 미학 문제가 아니다.

### 2.3 미상 집계 한 줄 — **정상에서 침묵한다**

원장 §3.1 의 선례: 칸 안 문구만으로는 부족해서(10칸 중 3칸만 미상이면 전체가 멀쩡해 보인다)
집계 배너를 넣었다. 모듈 단위가 되면 **같은 문제가 더 크게** 생긴다.

**세는 규칙 — `blocked_reason` 이 미상 계열인 zone 의 수만 센다.**

```
정상(안내등만 미상)        → 배너 침묵          ← 상시 상태가 경고를 만들지 않는다
주차확인센서 미상 2자리    → "⏱ 2자리는 지금 예약 판정을 할 수 없습니다"
```

- **조작을 막지 않는 미상은 집계에 넣지 않는다.** 넣으면 상시 켜진 경고가 된다.
- 🔴 **그렇다고 감추지 않는다** — 그것은 **칸 안의 조용한 표시**로 남는다(§2.2 의 `⏱`+조용).
  **집계에서 빠지는 것과 화면에서 사라지는 것은 다르다.**
- 집계는 **집계만 한다.** 칸의 문구를 대신하지 않는다(§3.1 이 정한 규율 그대로).

⚠ **아직 형태가 아니라 규칙까지만 정했다.** 문구·배치는 §5(표시량 확인 대기)에 걸린다.

## 3. 격자 렌더링 — 구조만

### 3.1 `cell → zone`, 1:1 가정

기본값 **`5×5`** · **자리 하나 = 칸 하나**(REQ-0181 지시). 초기 배치는 **예시일 뿐**이고
구조가 그것에 묶이지 않는다 — 크기·배치는 **맵 정의에서 온다**(설정으로 바뀐다).

### 3.2 🔴 대부분의 칸은 **비어 있다** — 빈 칸과 미상 자리를 갈라야 한다

`5×5 = 25칸` 인데 자리 5 + 입구·출구 → **18칸 안팎이 빈 칸**이다.

**이것이 원장 §2.4 의 함정이 격자 형태로 다시 나오는 자리다.** 지금 코드는 `slots` 에 없는 ID 를
`known:false` → `view:'unknown'`(점선 · "상태 미상")로 그린다. **격자에서 그러면 빈 칸 18개가
"상태 미상"으로 보인다** — 존재하지 않는 것을 "모른다"고 말하는 것이고, §2.3 의 집계를
쓸모없게 만든다.

→ **셋을 다른 것으로 그린다:**

| | 뜻 | 근거 |
|---|---|---|
| **빈 칸** | 그 좌표에 zone 이 없다 | **맵 정의**에 없다 |
| **미상 자리** | zone 은 있는데 상태를 모른다 | 맵 정의에 있고 `known:false` |
| **정상 자리** | zone 이 있고 상태를 안다 | — |

🔑 **이 구분은 "맵 정의를 상태와 별개로 준다"(§5.32 ①)가 있어야만 가능하다.** 상태만 오면
*"안 온 것"* 과 *"없는 것"* 이 같아 보인다. **계약 항목이 왜 필요한지가 여기서 구체화된다.**

### 3.3 `kind` 별 상태 어휘 — 입구에 "예약됨"이 없다

지금 `tileView` 의 7개 view(`free|reserved|occupied|done|pending|settled|unknown`)는 **전부
예약 가능한 주차 자리 기준**이다. 입출구를 `unknown` 으로 떨어뜨리면 **존재하는 것을 없다고
말한다**(§3.2 와 같은 오류).

→ **`kind` 로 먼저 갈라 상태 어휘를 따로 둔다.** 사용자 지시(*"기본 구조는 동일, 이름만 다르다"*)는
**구조에는 참이고 상태 어휘에는 거짓**이다(루트 정정).

| kind | 상태 어휘(초안) | 조작 |
|---|---|---|
| `parking` | 지금 7개 그대로 | 예약 / 취소 |
| `entrance` · `exit` | 차단봉 열림·닫힘 · 통과 중 · 미상 | **예약이 아니다.** 조작이 있다면 **다른 확인 문구**가 필요하다 |

⚠ **입출구에 `action:'reserve'` 가 절대 생기지 않아야 한다.** 지금 격자 클릭 위임은
`btn.dataset.action` 으로 갈라지므로(`reserve`/`cancel`) **`kind` 를 보지 않으면 조용히
예약 경로로 들어간다.**

🔑 **누를 수 없음은 계속 `aria-disabled` 로 말한다** — `disabled` 로 만들면 키보드·스크린리더
사용자가 그 칸에 도달조차 못 해 이유를 들을 수 없다(원장 §3.2, 의도된 설계).

### 3.4 1:1 이 깨지면 무엇이 바뀌는가 — **미리 지목한다**

사용자 확인 대기 항목이다(*"자리 크기도 유동"* 이면 칸→자리가 **N:1**). 그때 바뀌는 것:

| 깨지는 것 | 왜 |
|---|---|
| `cell → zone` 이 **다대일** | 한 zone 이 여러 칸을 차지한다 |
| **맵 정의가 기하를 실어야 한다** | 지금 구상은 좌표 하나면 되지만, N:1 이면 **원점 + 폭·높이**(또는 칸 목록)가 필요하다 → **계약이 바뀐다** |
| 타일 배치가 **span 기반** | CSS grid 에 `grid-area`/span 을 zone 마다 지정해야 한다 |
| "빈 칸" 계산(§3.2) | zone 이 덮는 칸 전체를 빼야 한다 |

**주소 방식(`data-zone`)은 안 깨진다** — DOM 노드는 zone 마다 하나이고 칸 수와 무관하다.
→ **N:1 로 바뀌어도 상태 모형(§1)·표시 규칙(§2)은 그대로다. 바뀌는 것은 맵 정의와 배치뿐이다.**
🔑 **그래서 1:1 로 먼저 가도 재작업이 격자 층에 갇힌다.** 이것이 1:1 가정을 감수하는 근거다.

## 4. 안 깨지는 것 — **다시 만들지 마라**

목록과 근거는 원장 **§5.32.2** 에 있다(복사하지 않는다). 요점만:

**아이들 1초 · `queued`/`expires_ms`/`ack_budget_ms` 계약 · 포트 해석 · 폴백 상한 문구**가 그대로다.
🔑 **값이 "안 바뀐다"가 아니라 "왜 안 바뀌는지"다** — 아이들 1초가 살아남는 이유는 그것이
**자리가 아니라 전선(`canAct()` · `transport.send()`)에 걸려** 있어서다. 근거가 없으면 다시 본다.

⚠ **하나는 열려 있다**: 폴백 상한 문구(§5.31)는 **장치 하나**를 전제한다. 노드가 N 개면
`last_frame_ts` 도 N 개다 → **모듈마다 "언제 확인된 값인가"** 가 필요해질 수 있다. **미정.**

## 5. 표시량 의존부 — **여기는 결정된 것이 아니다** (확인 대기)

`docs/DECISIONS-pending-user-2026-08-18.md` §① — 모듈 표시량(A 칸 안에 다 / B 눌러 펼치기 /
C 집계만). **답이 오기 전에는 아래를 설계하지 않는다.** 결정된 것처럼 적어 두면 답이 왔을 때
재작업이고, 그게 이 문서에서 가장 되돌리기 비싼 부분이다.

- 모듈을 칸 안에 몇 개까지 보이나 · 펼침 UI 가 있나 · 집계 배너의 문구와 위치
- 미상 표시의 **시각 형태**(점선? 흐림? 칩?) — **규칙은 §2.2 에서 정해졌고 형태만 남았다**

⚠ **§1(상태 모형)·§2.2~2.3(규칙)·§3(격자 구조)은 이 답과 무관하다.** 그래서 지금 썼다.
(루트가 `DECISIONS` §①에 *"데이터 계약은 그 답과 무관하므로 먼저 만들 수 있다"* 로 적은 것과 같다.)

## 6. 이 문서의 한계

- **전부 설계다. 실측 0.** 개정 코드가 없으므로 잴 것이 없다. **여기 숫자는 하나도 측정값이 아니다.**
- 현재 코드에 대한 주장(§1.1)은 **파일을 읽고 확인**했다(`normalizeSnapshot` 의 `known: bySlot.has(id)` ·
  `tileView` 의 `!slot.known` 분기와 `deviceDown` · `buildGrid` 의 `SLOT_IDS` 순회).
  **행 번호는 적지 않았다** — 판본마다 썩으므로 식별자로 찾아라(원장 §4.4 의 pid 교훈과 같은 이유).
- **§1.3(서버가 `actionable` 을 계산한다)은 web 의 요구이고 합의가 아니다.** socket 과 합의해야 한다.
- 서버·전선 쪽 형태(키 이름·프레임 형식)는 **내 판단이 아니다.** 원본은 REQ-0179 와 `docs/net/` 이다.
