## 1. 화면이 붙는 곳

### 1.1 서버는 HTTP 와 WS 가 **같은 포트 하나**다 — 오프셋은 둘을 같이 옮긴다 (실측)

`server.cpp` 의 리스너 하나가 `index.html` 정적 서빙과 `GET /ws` 업그레이드를 겸한다
(`lsn_http = listen_on(PORT_HTTP + g_port_offset)`, 2102행 / `path == "/"` → `/index.html`, 1855행).

- 운영: **9900** · 시험 인스턴스(`--port-offset=100`): **10000**
- 실측 근거: `http://127.0.0.1:10000/` 이 페이지를 주고, 같은 포트로 `ws://127.0.0.1:10000/ws`
  업그레이드가 성사됐다(CDP `Network.webSocketCreated` 로 확인, 2026-08-16 19:07).

**따라서 "페이지를 준 포트 = WS 포트"가 이 시스템의 불변식이다.** 화면이 WS 포트를 따로
정하려 들면 그 순간 두 서버를 섞을 수 있다 — 실제로 그랬다(§1.2).

### 1.2 🔴 함정 — 화면이 `location.port` 를 무시하고 상수 9900 을 쓰면 **운영으로 샌다**

2026-08-16 이전의 `index.html` 이 그랬다. 호스트만 `window.location` 에서 가져오고
포트는 `const WS_PORT = 9900` 이었다.

결과(코드 판독 + 그 뒤 실측으로 확인):

> 시험 서버(:10000)가 준 페이지를 열면 **WebSocket 은 운영(:9900)** 으로 붙는다.
> 폴백 폴링만 상대경로라 :10000 으로 간다 → **한 화면이 두 서버를 섞는다.**
> 그 화면에서 예약을 누르면 **운영 장치로 하행 명령이 내려간다.**

**이 함정의 지독한 점**: 시험 인스턴스 로그에는 아무것도 안 남는다. 흔적은 운영 로그에만
생기므로 **깨진 줄도 모른다.** 포트·`flock`·로그 분리를 아무리 겹쳐도 화면에 박힌 상수
하나가 전부 통과했다.

지금은 `resolveWsPort()` 가 `?ws=` → `location.port` → 9900 순으로 정한다.
회귀 검사: `node web/tools/check-index.mjs` §5.

### 1.3 함정 — 리버스 프록시·80/443 뒤에서는 `location.port` 가 **빈 문자열**이다 (추정, 미실측)

그 경우 §1.2 의 규칙이 문서화된 기본값 9900 으로 떨어진다. 프록시가 WS 를 다른 데로
넘긴다면 `?ws=` 로 명시해야 한다. **이 구성은 이 프로젝트에 아직 없어서 실측하지 않았다.**

### 1.4 폴백은 상대경로 `data_log.json` 이다 → 기본 경로에서는 WS 와 항상 같은 오리진 (실측)

둘이 다른 서버를 가리킬 수 있는 유일한 경우는 `?ws=` 를 명시했을 때이고, 그때 화면이
빨간 경고를 띄운다(실측: `web/artifacts/4-fallback.png`).

## 2. 서버가 화면에 주는 것

### 2.1 WS 스냅샷의 `device` 에는 `last_frame_ts` 가 **없다** (실측)

> ⚠ **이 항목은 빌드에 딸린 사실이다. `build=22f788d` 부터는 아니다 — §5.1 을 먼저 읽어라.**
> (아래 내용은 그 빌드 **이전**에 대해 여전히 참이고, 운영에 무엇이 올라가 있는지는 별개다.)

2026-08-16 19:07, 시험 인스턴스에서 받은 실제 프레임(`web/artifacts/ws-snapshot.json`):

```
WS   device = { online, device_id, uptime, seq }
파일 device = { online, last_frame_ts }
```

→ **신선도 표시는 폴백 경로에서만 동작한다.** 정상 운영 중에는 화면이 계속
`"알 수 없음 (이 경로에는 이 정보가 없습니다)"` 를 띄운다(실측한 DOM 문자열).

REQ-0132 로 socket 에 요청했다. 오면 화면은 그날로 동작한다(이미 그 키를 읽고 있다).

### 2.2 🔴 함정 — `GET /?쿼리` 는 **404** 다. `GET /index.html?쿼리` 는 200 (실측)

> ⚠ **이 항목도 빌드에 딸린다. `build=22f788d` 부터는 200 이다 — §5.1.**
> 그리고 **이 응답 코드 자체가 빌드 판별자다**: 붙은 서버가 REQ-0132 이전인지 이후인지
> `GET /?demo=1` 한 줄로 갈린다(404 = 이전 · 200 = 이후).

```
GET /                  → 200
GET /index.html?demo=1 → 200
GET /?demo=1           → 404
```

원인(판독): `serve_file()` 이 `path == "/"` → `/index.html` 매핑을 **쿼리 제거보다 먼저**
한다. `/?demo=1` 은 `"/"` 와 다르므로 매핑을 놓치고, 쿼리를 자르면 파일명이 빈 문자열이 된다.

**시연에서 `호스트:9900/?demo=1` 을 치면 빈 페이지가 뜬다.** 주소에 `/index.html` 을 반드시
넣어라. REQ-0132 로 요청했고, 고쳐지면 `web/tools/e2e.mjs` §9 가 저절로 초록이 된다.

### 2.3 화면은 서버 **로그**를 읽지 않는다 (REQ-0122 에서 확인, 여전히 참)

입력 경로는 WS JSON 과 `data_log.json` 둘뿐이다. 그래서 로그 줄의 지표 이름이 바뀌는
`오프라인` → `무프레임` 개명에 화면은 걸리지 않는다.

### 2.4 화면은 최상위 `occupied`/`reserved` **비트열을 읽지 않는다.** `slots[]` 만 본다 (실측)

비트열이 멀쩡히 있어도 `slots` 가 비면 10칸 전부 "상태 미상"이 된다
(측정: `web/artifacts/probe-slots.json` 의 `bits` 사례). 서버가 지금 둘 다 보내므로 문제는
없지만, **`slots[]` 를 빼는 변경은 화면을 조용히 눈멀게 한다.**

## 3. 화면이 상태를 말하는 방식

### 3.1 `slots[]` 결손은 "빈 자리"로 보이지 **않는다** — 통념 정정 (실측)

> ~~"slots 가 없으면 10칸이 조용히 빈자리로 보인다"~~ — **틀렸다.**
> 2026-08-16 실측: 결손 칸은 `상태 미상 / 데이터 없음`(점선 테두리)으로 그려진다.
> 근거는 `normalizeSnapshot()` 이 칸마다 다는 `known: bySlot.has(id)` 이고,
> `tileView()` 가 `!slot.known` 이면 `view:'unknown'` 을 돌려준다.
> 측정 원문: `web/artifacts/probe-slots.json` (5개 사례 · `web/artifacts/slots-*.png`).

**다만 진짜 빈틈은 다른 데 있었다**: 그 말이 **칸 안에만** 있었다. 10칸 중 3칸만 미상이면
나머지 7칸이 정상이라 화면 전체는 멀쩡해 보인다. 그래서 같은 날 격자 위에 **집계 배너**를
추가했다(`#slots-banner`). 배너는 집계만 하고 칸의 문구를 대신하지 않는다.

### 3.2 함정 — 이 화면의 "누를 수 없음"은 `disabled` 가 아니라 `aria-disabled` 다 (실측)

`t.button.setAttribute('aria-disabled', …)` 만 쓰고 `button.disabled` 는 건드리지 않는다.
**의도된 설계다**: 진짜 `disabled` 로 만들면 키보드·스크린리더 사용자가 그 칸에 도달조차
못 해서 "왜 못 누르는지"를 들을 수 없다. 클릭 핸들러가 `aria-disabled` 를 보고 이유를 띄운다.

→ **자동 검사에서 `el.disabled` 를 읽으면 항상 `false` 라 "막힘이 안 먹는다"고 오판한다.**
실제로 이날 그 오판을 한 번 했다. 반드시 `getAttribute('aria-disabled')` 를 읽어라.

### 3.3 소켓이 끊겨도 화면은 비지 않는다 — 폴백이 이어받는다 (실측)

살아 있는 WS 를 끊으면 **2ms 안에** 연결 표시가 "연결 끊김 — N초 후 재연결 시도"로 바뀌고,
칸 10개는 **직전 상태를 유지**한다("상태 미상"으로 떨어지지 않는다). 그 뒤 자동 재연결된다.
즉 이 화면의 실패 모드는 "빈 화면"이 아니라 "오래된 값 + 그렇다는 표시"다.
(측정 절차: `e2e.mjs` §6 — 브라우저에서 `transport.ws.close()` 로 소켓만 끊는다)

### 3.4 예약 왕복은 브라우저 클릭에서 화면 반영까지 **약 205ms** (실측 2회)

시험 인스턴스 + `fake_arduino`(로컬) 기준이다. 실물 ESP·무선이 들어가면 달라진다 —
**이 숫자를 실물 경로의 기대값으로 옮겨 쓰지 마라.**
구간 정의: `#confirm-dialog` 의 확인 버튼 클릭 → 그 칸의 상태 문구가 "내 예약"으로 바뀜.

## 4. 시험 방법에 대해 참인 것

### 4.1 브라우저 검증은 의존성 없이 된다 — CDP 직접 (실측)

node 22 의 전역 `WebSocket`·`fetch` 로 크롬 DevTools 프로토콜을 직접 말한다
(`web/tools/cdp.mjs`). puppeteer 같은 것을 들이지 않았다.
`--headless=new` + **매번 새 임시 `--user-data-dir`**(사용자 프로필을 재사용하면 잠금 충돌).

### 4.2 함정 — 상태 문구를 `waitFor` 로 기다리면 **바뀌기 전 값에 즉시 걸린다** (실측)

빈 문자열이 아닌 모든 문자열은 참이다. `waitFor("…textContent")` 는 "빈 자리"에 즉시
성공하고, 그러면 4ms 만에 "화면이 안 바뀌었다"는 **거짓 실패**가 난다.
반드시 **불리언**을 기다려라: `/예약/.test(…)`.
이날 이 한 줄 때문에 종단 시험이 두 번 잘못된 결론을 냈다.

### 4.3 시험 인스턴스의 `data_log.json` 은 오프셋으로 갈리지 않는다 (실측)

`atomic_write_log()` 가 **cwd 상대경로**로 쓴다. `--port-offset` 이 갈라 주는 것은
**로그 파일 경로뿐**이다(`.test+100`).

- 운영 인스턴스의 cwd 는 `/Users/idong-u/parking-bin` 이라 **운영 파일과는 안 부딪친다**
  (`lsof -p <pid> -a -d cwd` 로 확인).
- cwd 를 `조별과제샘플` 로 잡는 시험 인스턴스는 `조별과제샘플/data_log.json` 을 덮어쓴다.
  ~~그 파일은 git 추적 대상이라 커밋에 딸려갈 수 있다~~ — **틀렸다.** `.gitignore:53` 에
  있어 추적되지 않는다(socket-engineer 정정, `git ls-files` 로 확인). **되돌릴 것이 없다.**
  내가 `git ls-files` 를 돌려 보지 않고 "추적 파일"이라 단정한 것이 원인이다.

### 4.4 🔴 화면이 서빙되는지는 **서버를 어디서 띄웠느냐**로 결정된다 (실측 — 단, 근거는 GET 이 아니다)

`serve_file()` 은 `index.html` 을 **cwd 상대경로**로 연다. 즉 **바이너리 위치가 아니라
작업 디렉터리에 `index.html` 이 있어야 화면이 나온다.** 없으면 그 포트는 404 만 준다.

2026-08-16 시점의 실제 상태:

```
/Users/idong-u/parking-bin/     ← 운영(pid 75781)의 cwd
  srv_parking · data_log.json · stderr.log      ← index.html 이 **없다**
```

> ⚠ **`pid 75781` 은 낡았다** (2026-08-16 23:5x 정정). 21:05:10 머신 재부팅으로 종료됐다 —
> 비정상 종료가 아니라 SIGTERM 정상 종료다(root 확인 · 운영 로그 13608행
> `INSTANCE-END reason=normal frames=10176 sessions=11`). 나는 23:47 에 프로세스·LISTEN 이
> 비어 있는 것만 봤고, 경위는 root 가 로그로 채웠다.
>
> **이 항목의 결론은 그대로 참이다** — 낡은 것은 pid 하나뿐이고, "그 디렉터리에 `index.html`
> 이 없어서 운영은 화면을 못 준다"는 결론은 pid 와 무관하다.
>
> 교훈: **원장에 pid 를 적으면 반드시 썩는다.** 재부팅 한 번이면 끝이다. 경로·cwd·포트는
> 안 썩는다. 다음부터는 프로세스를 가리킬 때 pid 대신 **cwd 와 포트**로 적는다.

→ **운영 인스턴스는 관측용이고 화면을 서빙하지 못한다.**

**이 결론의 근거가 무엇인지가 결론만큼 중요하다** — 세 가지이고, **셋 다 운영 포트를 건드리지
않는다**(관측 창 규칙):

1. `server.cpp:1892` `std::ifstream f(fn.c_str(), std::ios::binary)` — 상대경로다(소스)
2. `~/parking-bin/` 의 파일 목록에 `index.html` 이 없다 (`ls`, web·root 가 각각 독립 확인)
3. 같은 방식으로 쓰는 `data_log.json` 이 **그 디렉터리에 실제로 생겨 있다** — cwd 상대라는 방증

즉 근거는 **소스와 파일 목록**이지 *GET 응답*이 아니다. GET 은 일부러 안 보냈다 —
얻을 것이 없고 운영 로그에 accept 한 줄이 남아 monitor 의 계수에 섞인다.
(**"필요 없으면 안 건드린다"** 가 이날 지킨 규율이다. 확인하고 싶은 충동이 관측을 오염시킨다.)

시연에서 화면을 띄우려면 **`index.html` 이 있는 디렉터리에서 서버를 띄워야 한다** —
지금 그런 곳은 `조별과제샘플/` 이다. 루트 판단으로 **사본을 두지 않고**
`--webroot` 로 경로 해석을 고치는 방향이 socket 에 넘어가 있다(사본이 둘이면 갈라진다).

**이 함정이 지독한 이유**: 서버는 정상 기동하고 로그도 정상이며 WS 도 열린다.
화면만 안 나온다. "서버는 떴는데 왜 페이지가 없지"를 시연장에서 만나게 된다.

### 4.5 `?demo=1` 은 서버에 트래픽을 만들지 않는다 (코드 판독 + 실측)

`transport.start()` 가 `connect()`·`startPolling()` **앞에서** 반환한다.
관측 창이 걸려 있을 때 화면 검증에 쓸 수 있는 유일한 경로다.
단, 주소는 `/index.html?demo=1` 이어야 한다(§2.2).

### 4.6 브라우저 검증을 다시 돌리는 절차

```bash

#    선례: REQ-0128

# ② 브라우저 없이 도는 회귀 — 시험 인스턴스가 없어도 된다
```

| 아는 것 | 값 |
|---|---|

| 기록 자체의 나이 | `now - ts` |

### 5.13 `handleServerMessage()` 에는 **캐치올이 없다** — 모르는 타입은 조용히 무시된다 (실측)

`조별과제샘플/index.html` 1885-1968행. `if (msg.type === 'snapshot'/'ack'/'error') { … return; }`
사슬이고 마지막 `error` 블록이 1966행에서 닫힌 뒤 **1967행이 `// 모르는 type 은 조용히
무시한다.`** 이며 곧바로 함수가 끝난다.

**왜 이것이 원장에 남을 값인가**: 이 성질 하나가 **프로토콜을 앞으로 늘릴 때 안전한 방향을
결정한다.**

- **새 타입을 추가하는 변경** → 옛 화면은 무시 → **깨지지 않는다.** 서버를 먼저 배포해도 된다
- **기존 타입에 필드를 추가해 뜻을 바꾸는 변경** → 옛 화면은 **그 타입의 옛 뜻대로 동작한다**
  → 서버 배포가 **그 순간 옛 화면을 깨뜨린다**

REQ-0155(하행 큐의 "접수됨") 때 이 판정이 실제로 방향을 정했다. `ack` 에 상태 필드를 넣는
안이었으면 옛 화면이 `type==='ack'` 만 보고 **전선에 나가지도 않은 요청을 "예약되었습니다"로
선언**했을 것이다.

⚠ **근거 정정 이력**: 처음에는 `msg.type` 세 곳만 grep 하고 이 결론을 적었다. **그건 "세 타입을
검사한다"만 증명하지 "끝에 else 가 없다"를 증명하지 않는다.** 함수 끝까지 읽어 확인한 뒤
근거를 바꿨다 — **결론은 같았지만 근거가 부실했다.** 캐치올이 있었다면 위험의 크기가 달랐다
("조용히 무시" 가 아니라 "시끄럽게 오작동").

### 5.14 🔴 화면의 자체 타임아웃이 **짧으면 서버 큐를 키운다** (설계 함정)

REQ-0155 에서 나온 것. 서버가 하행을 큐에 담게 되면 이 연쇄가 생긴다:

```
큐 대기 → 화면 자체 타임아웃(ACK_TIMEOUT)이 먼저 터짐 → 롤백
→ 사용자가 다시 누름 → 새 rid (서버 pending 은 이미 풀려 has_pending_for 도 안 막는다)
→ 큐에 한 건 더
```

**즉 화면이 "안전하게" 되돌리는 동작이 시스템 부하를 키운다. 타임아웃이 짧을수록 더 쌓인다.**
socket 이 "같은 자리 중복은 서버가 막는다"고 적어 뒀던 항목이 이것 때문에 취소선으로 정정됐다 —
**그 방어는 pending 이 살아 있는 동안만 유효하다.**

→ **규칙**: 화면의 타임아웃은 **서버가 준 상한에 묶는다. 화면이 짐작하지 않는다.**

### 5.15 확정된 계약 — `queued` (REQ-0155 · 구현은 아직 안 했다)

**원본은 socket 의 `docs/net/DESIGN-server-slot-queue.md` §4-B**(커밋 `3cf6ed9`·`8ba70cb`)다.
여기에는 **화면 쪽이 지켜야 할 것만** 적는다. 값이 갈리면 원본이 이긴다.

```json
{"type":"queued", "rid":"…", "slot":"A1", "ahead":2, "expires_ms":<남은 지속시간 ms>}
```

- **`expires_ms` 는 "이 프레임을 받은 시점 기준 남은 상한"**(지속시간). 절대 시각이 아니다.
  서버는 `deadline = enqueue + cap` 을 항목마다 한 번 박고 낼 때마다 `deadline − now` 를 보낸다
  → **단조 비증가가 구조상 보장된다.** 🔑 **두 시계를 안 섞는 방식이다** — 서버는 자기 시계로
  차이만 내고, 화면은 받은 지속시간을 자기 시계로 잰다. **어느 쪽도 상대 시계를 안 읽는다.**
- **화면 규칙**: `queued` 를 받을 때마다 **타이머를 다시 건다**(`expires_ms + ACK_TIMEOUT`).
- **`queued` 뒤에는 반드시 `ack` 또는 `error` 가 온다** — 서버가 지키기로 한 보장이다.
  **이게 없으면 중간 상태가 영구가 된다**(타일이 영원히 맥동한다).
- **거절 코드 둘을 다른 문구로 그린다**: `queue_full`(시스템 사정 — "지금 붐빕니다") ·
  `already_pending`(**사용자 잘못이 아니다** — "이미 처리 중입니다").
- **`ahead` 로 시간을 환산하지 않는다.** 그러려면 창당 처리 건수(`rxmax`)를 화면이 들고 있어야
  하는데 그건 실측 중이고 내 도메인도 아니다 — **화면에 그 상수를 박는 순간 전제가 바뀌면
  조용히 틀린다.** 화면은 **"앞에 N건"까지만** 말한다.

⚠ **`cap` 의 값은 `rxmax` 실측에 종속이다. 의미는 확정, 값은 미정.**
