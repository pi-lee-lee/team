# web 화면이 설계 개정에서 어디가 깨지는가 — 조사 (2026-08-17 · web-engineer)

**착수 금지 상태에서 쓴 조사서다. 코드는 한 줄도 고치지 않았다.**
`docs/PLAN-QUEUE-2026-08-17.md` 가 *"읽고 조사하는 것은 자유 · 코드는 고치지 마라"* 라고
했으므로, 계획 REQ 가 내려올 때 바로 쓸 수 있게 **내 도메인의 파열면만** 먼저 적어 둔다.

> 대상 판본: `조별과제샘플/index.html` (커밋 `a3a2493` 시점) · 행 번호는 그 판본 기준이다.
> ⚠ **행 번호는 썩는다.** 판단이 걸리는 곳은 행 번호가 아니라 **식별자**로 같이 적었다.

## 0. 한 줄 답

**10칸 고정은 생각보다 싸게 풀린다(`SLOT_IDS` 한 곳).
비싼 것은 `device.online` **단일 불리언**이다 — 그것 하나가 **10칸 전부의 조작 가능성**을
결정하고 있어서, 모듈이 여러 아두이노에 흩어지는 순간 **틀린 칸을 잠그거나 틀린 칸을 열어 준다.**

**그리고 더 깊은 것이 하나 있다(루트가 사용자 확정 원칙을 전해 줬다)**:
장치가 **완전히 독립**이면 **"일부만 아는 상태"가 예외가 아니라 상시 정상 상태**가 된다.
지금 화면은 **자리 하나 = 상태 하나**라 그것을 표현할 자리가 없다 — §2.2 가 이 문서의 핵심이다.

⚠ **"자리가 10 → 5 로 줄어드니 단순해진다"로 읽지 마라**(루트 지적). 격자에 **입구·출구**가
추가되고 각 칸이 **모듈을 여러 개** 갖는다 → **화면 요소 수는 줄지 않는다.**
바뀌는 것은 수가 아니라 **구조**다: **1차원 목록 → 2차원 격자 + 모듈 트리.**

## 1. 값싼 쪽 — 10칸 고정 (`SLOT_IDS`)

```
468 : const SLOT_IDS = ['A1','A2','A3','A4','A5','B1','B2','B3','B4','B5'];
```

**쓰이는 곳이 좁다**: `buildGrid()`(1053) · `renderSlotsBanner()`(1302-1303) ·
`tileView` 없는 경우의 기본 격자(1325) · 데모 생성기(691·719·853) · 주입(1053) .

→ **자리 수·이름이 유동이 되는 것 자체는 `SLOT_IDS` 를 서버 스냅샷에서 받는 것으로 대체된다.**
이미 화면은 `slots[]` 만 보고 그린다(원장 §2.4) — 즉 **데이터 경로는 이미 가변이다.**
고정된 것은 **DOM 을 미리 만드는 것**과 **없는 칸을 "상태 미상"으로 채우는 것**뿐이다.

⚠ **다만 §2.4 의 성질이 뒤집힌다.** 지금은 *"`slots` 에 없는 ID = 데이터 없음(점선)"* 인데,
자리가 유동이면 **"없는 ID = 그 자리가 존재하지 않음"** 이다. **둘은 화면에서 반대로 말해야
한다** — 지금 코드는 전자만 안다(`known: bySlot.has(id)` · `normalizeSnapshot`).
→ **서버가 "정의된 자리 목록"을 주지 않으면 화면은 이 둘을 구분할 수 없다.** 계약 항목이다.

### 1.1 레이아웃은 코드가 아니라 CSS 에 박혀 있다

```
149-150 : 전선 순서(A1..A5,B1..B5)를 DOM 순서로 유지한 채 **열 우선**으로 배치한다
357     : "2열 5행 · 10칸 · 빈자리를 눌러 예약합니다"   ← 사람이 읽는 문구
```

격자 맵으로 가면 **열 우선 트릭이 필요 없어진다**(좌표가 오므로). 오히려 지금 구조는
**좌표가 없어서** DOM 순서로 위치를 흉내내고 있다. → 개정이 이 부분을 **단순하게** 만든다.

## 2. 🔴 비싼 쪽 — `device.online` 이 단일 불리언이다

```
1249 : const deviceDown = state.snapshot.device.online === false;      ← tileView
1261 : if (mine && canAct() && !deviceDown) { …조작 허용… }
1270 : if (deviceDown) { …그 칸을 "센서 끊김 — 예약 불가"로… }
1376 · 1468 · 1499 : 시뮬 패널 · 배너 · 연결 표시도 같은 값을 본다
```

**지금 전제**: 주차 노드는 **하나**이고 그것이 10칸 전부를 안다(서버 `park_dev` 와 짝).
그래서 `online=false` 면 **10칸이 동시에** 잠기는 것이 옳다.

**개정 뒤**: 사용자 지시 7번 — *"센서들은 랜덤한 아두이노에 있을 수 있다. 1대가 1구역이 아니다."*
→ **자리 A 의 센서가 장치 X 에, 자리 B 의 차단봉이 장치 Y 에 있을 수 있다.**

| 지금 코드가 하는 일 | 개정 뒤 결과 |
|---|---|
| 아무 장치나 끊기면 **전부 잠근다** | 멀쩡한 장치에 붙은 자리까지 **예약 불가**(거짓 차단) |
| 모든 장치가 살아 있으면 **전부 연다** | 어떤 자리의 센서 장치가 죽었어도 **눌린다**(거짓 허용) |

🔴 **후자가 더 나쁘다.** 거짓 차단은 사용자가 못 누르는 것으로 끝나지만, **거짓 허용은 하행이
닿지 않는 장치로 명령을 보낸다.** 원장 §5.10 이 고친 문구(*"장치 연결이 끊겨 예약을 보내지
않았습니다"*)도 **어느 장치인지 말할 수 없게 된다.**

### 2.2 🔴 이 문서의 핵심 — **부분 미상이 "정상 상태"가 된다**

사용자 확정 원칙(루트 전달 · `PLAN-QUEUE` §"장치는 완전히 독립이다"):

> **모든 아두이노는 독립이다.** 한 아두이노의 ESP01 이 와이파이를 못 잡아도
> 다른 아두이노에 영향을 주지 않는다.

구역 상태를 **여러 장치에서 조립**하므로 한 장치가 죽으면 **그 구역의 일부만** 미상이다.
→ 🔴 **전체를 회색으로 덮으면 안 된다. 미상인 것만 미상으로 그린다.**

**지금 화면에 없는 것**: 한 구역 안에서 *"주차확인 센서는 살아 있고 안내등은 미상"* 이
**정상**인 상태. 지금 구조는 자리 하나에 상태 하나다:

```
1207 tileView(slot) → view 하나 · state 문구 하나 · meta 하나 · aria-disabled 하나
     normalizeSnapshot: known = bySlot.has(id)      ← **자리 단위 불리언**
```

→ **`known` 이 모듈 단위로 내려가야 한다.** 자리의 "상태"는 단일 값이 아니라
**모듈별 (값 · 아는지) 쌍의 모음**이 된다.

#### 2.2.1 🔑 여기서 §5.31 의 구분이 다시 쓰인다 — 다만 **더 세게** 필요하다

`⏱`(모른다) 대 `⚠`(고장)을 §5.31 에서 한 번 갈랐다. 그때는 **폴백일 때만** 나오는 상태였다.
개정 뒤에는 **미상이 상시로 존재하는 정상 상태**가 된다.

→ **미상이 경보로 보이면 화면을 쓸 수 없게 된다.** 상시 켜진 경고는 아무도 안 읽는다
(원장 §3.1 에서 배너를 "정상에서 침묵"하게 만든 것과 같은 이유).

**설계 요구로 올린다**: 미상은 **조용한 표시**여야 하고(점선·`⏱`·흐림),
**고장·차단은 눈에 띄는 표시**여야 한다(`⚠`). **둘을 같은 기호로 그리면 안 된다.**

⚠ **반대 함정도 같이 적는다**: 미상을 너무 조용하게 만들면 **REQ-0067 이 막으려던 것**
(모르는 것을 아는 것처럼 보이기)으로 돌아간다. **조용하되 반드시 보여야 한다** —
§3.1 이 칸 안의 문구만으로는 부족해서 집계 배너를 추가한 그 교훈이 여기서도 유효하다.
→ **미상 모듈 수를 집계로 한 줄 내는 것**이 후보다(배너는 집계만 하고 칸 문구를 대신하지 않는다).

### 2.3 그래서 화면이 서버에 요구해야 하는 것

**자리마다 "이 자리가 의존하는 장치들의 상태"** 가 필요하다. 자리 하나가 모듈 여러 개를
가지므로 **불리언 하나로는 부족하다.**

- 예약을 걸려면 **어느 모듈이 살아 있어야 하나**(주차확인 센서? 차단봉?)를 서버가 정해 줘야 한다.
  **화면이 판단하면 안 된다** — 원장 §5.14 의 규칙과 같은 형태(*화면이 짐작하지 않는다*).
- 그래서 계약 후보: 자리마다 **`actionable: bool` + `blocked_reason: code`** 를 서버가 계산해 준다.
  🔑 **모듈 목록을 화면에 주고 화면이 조합하게 하면, 조합 규칙이 두 곳에 생긴다.**

⚠ 반대로 **모듈 상태 자체는 표시용으로 필요하다**(안내등·유도등·차단봉을 보여 줘야 한다).
→ **"보여 줄 것"과 "판단에 쓸 것"을 갈라야 한다.** 판단은 서버가, 표시는 모듈 목록으로.

## 3. 입구·출구 — 자리와 **종류가 다르다**

사용자 지시 4번: *"기본 구조는 동일하고 이름만 다르다."* **화면에서는 그렇지 않다.**

```
1207 : function tileView(slot)      view: free|reserved|occupied|done|pending|settled|unknown
```

이 7개 view 는 **전부 "예약 가능한 주차 자리"의 상태**다. 입구·출구는:

- **예약 대상이 아니다** → `action: 'reserve'` 가 있어서는 안 된다
- 상태가 다르다 → 차단봉 열림/닫힘 · 차량 통과 중 같은 것
- **누를 수 있는가**: 조작(차단봉 열기)이 있다면 예약과 **다른 확인 문구**가 필요하다

🔴 **`aria-disabled` 로 "누를 수 없음"을 말하는 지금 방식(§3.2)은 그대로 쓸 수 있지만, 이유
문구 표가 전부 주차 전용이다.** 입출구를 `view:'unknown'` 으로 떨어뜨리면 **"데이터 없음"으로
보인다** — 존재하는 것을 없다고 말하는 §2.4 계열 오류다.

→ 계약 항목: 자리마다 **`kind: 'parking'|'entrance'|'exit'`**. 화면은 `kind` 로 먼저 갈라야 한다.

## 4. 안 깨지는 것 — 그대로 가는 것

**개정이 큰 것에 비해 살아남는 것이 많다.** 계획 단계에서 이걸 다시 만들지 않게 적어 둔다.

| 그대로 | 근거 |
|---|---|
| WS/폴백 이중 경로 · 포트 해석(`resolveWsPort`) | 자리 구조와 무관 (원장 §1.1·§1.2) |
| `queued`/`ack_budget_ms` 타이머 계약 | rid 단위다. 자리 수와 무관 (§5.26·§5.28) |
| 하행 아이들 1초 · `canAct()`·`transport.send()` 두 지점 | **전선 하나**에 걸린 것이라 자리가 늘어도 그대로 (§5.16) |
| 폴백 신선도 상한 문구 | 장치 축이다 (§5.31) — 다만 **장치가 N 대면 "어느 장치의 프레임인가"가 생긴다** |
| `handleServerMessage` 캐치올 없음 → **새 타입 추가는 안 깨진다** | §5.13 — 개정을 **새 타입으로** 하면 옛 화면이 조용히 무시한다 |

🔑 **§5.13 이 개정의 배포 순서를 결정한다**: **기존 `snapshot` 의 `slots[]` 항목에 필드를 추가**하는
방식이면 옛 화면이 **옛 뜻대로 동작**하므로 서버 배포가 그 순간 화면을 깨뜨린다.
**새 타입/새 키로 주고 옛 키를 한동안 같이 싣는 쪽**이 안전하다.

## 5. 계획 REQ 가 오면 web 이 답해야 할 물음 (미리 적어 둔다)

1. **자리 ID 와 격자 좌표는 같은 것인가 다른 것인가** — 계획서 4번과 같은 물음이다.
   화면은 `data-slot` 하나로 DOM 을 찾고 예약 payload 에도 그 값을 쓴다(`{type:'reserve',slot}`).
   **좌표를 ID 로 쓰면 자리를 옮길 때 예약이 따라 움직인다.** 갈라야 한다고 본다.
2. **예약 가능 판정을 누가 하나** — §2.3. **서버라고 본다.**
   그리고 **판단(서버)과 표시(모듈 목록)를 갈라야 한다** — §2.2 때문에 표시는 모듈 단위가 된다.
3. **`kind` 를 어떻게 주나** — §3.
4. **정의된 자리 목록을 어떻게 주나** — §1 의 "없음 대 존재하지 않음".
5. **모듈을 화면에 얼마나 보여 주나** — 시연 화면이라 **10칸 격자보다 복잡해지면 읽히지 않는다.**
   ⚠ 이건 기술 문제가 아니라 표시 문제다 — **사용자에게 물어야 할 것**이라고 본다.
   구체적으로 갈릴 지점: **모듈을 칸 안에 다 보이나(요소 수 폭발), 칸을 누르면 펼치나(한 번에
   하나만 보인다), 집계만 내나(어느 모듈인지 안 보인다).** 셋의 대가가 다르다.
6. **미상을 어떻게 그리나** — §2.2.1. 상시 상태이므로 **조용하되 보여야 한다.**
   미상 모듈 **집계 한 줄**을 낼지가 갈림길이다(§3.1 의 배너가 선례다).
7. **모듈 상태의 나이** — 장치가 N 대면 `last_frame_ts` 도 N 개다.
   §5.31 이 방금 만든 상한 문구는 **장치 하나**를 전제한다 → **모듈마다 "언제 확인된 값인가"**
   가 필요해질 수 있다. **그러면 §5.31 을 모듈 단위로 다시 풀어야 한다.**

## 6. 이 문서의 한계

- **전부 코드 판독이다. 아무것도 실측하지 않았다** — 개정 코드가 없으므로 잴 것이 없다.
- 서버·전선 쪽 파열면은 **내 판단이 아니다**(`docs/net/`·`docs/arduino/` 가 원본).
  여기 적힌 서버 요구사항은 **요구이지 합의가 아니다.**
- 행 번호는 판본에 딸린다. 식별자(`SLOT_IDS`·`deviceDown`·`tileView`)로 찾는 것이 안전하다.
