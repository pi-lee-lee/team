**web-engineer · 2026-08-17 08:1x 시작** *(초판에 `00:0x` 로 적었던 것을 정정했다 — 날짜가
바뀐 것만 보고 시각을 확인하지 않았다. monitor 가 잡아 줬다. 개입 기록은 시각이 전부이고,
`00:1x` 로 갔으면 이미 판정문이 나간 창3 구간 안에 없는 개입이 하나 생길 뻔했다.)*

> **읽는 순서**: 결론만 필요하면 §0 만 읽으면 된다. §1~§2 는 관측 **전에** 확정한 예측이고

## 0. 한 줄 답

> **화면은 안 깨진다. 스스로 복구한다.**
> **딱 하나 깨지는 것이 있다 — 하필 그 순간에 예약을 확정하려던 사람이고,
> 화면은 그 사람에게 틀린 이유를 말한다.**

| 물음 | 답 | 근거 |
|---|---|---|
| 화면이 빈다? | **아니다.** 10칸 값이 그대로 유지된다 | §3.2 |
| 예약이 롤백된다? | **아니다** | §3.2 |
| 복구 후 자동 정상화? | **된다.** 사람이 아무것도 안 해도 돌아온다 | §3.2 |
| 조작 중이었다면? | 🔴 **사라진다. 3/3.** 그리고 **이유를 잘못 말한다** | §3.3 |

**시연을 깨뜨리나 — 내 판단**: 화면 붕괴는 아니므로 **시연 자체는 진행된다.** 다만
시연에서 예약을 누르는 그 순간이 정확히 끊김을 유발하는 순간이라(**하행 명령이 원인**),
발표자가 확인을 눌렀는데 아무 일도 안 일어나고 **"그 사이 자리 상태가 바뀌어 예약하지
않았습니다"** 라는 **사실과 다른 문구**를 보게 될 수 있다. 다시 누르면 된다.

**고칠 것은 동작이 아니라 문구 한 줄이다.** 장치가 끊긴 동안 예약을 안 보내는 것은
**옳은 동작**이다(보내 봐야 못 간다). 잘못된 것은 **이유를 자리 상태 탓으로 돌리는 것**이다.
→ §5 에 제안을 적었다. **아직 안 고쳤다** — 고치면 그 화면을 다시 재야 한다.

### 0.1 🔴 **같은 고장이 화면에서 두 가지로 보인다** — 길이가 3.5초를 걸치기 때문

초판은 루트에게 "끊김은 2초"라고 받아 적었다. **그 전제가 틀렸다**(루트가 서버 로그로 정정):

| 실물 사건 | 길이 | `OFFLINE_MS=3500` 기준 | 화면 |
|---|---|---|---|
| 창3 00:21:22 | 약 2초 | **아래** | **아무 일도 안 일어남** |
| 창3 01:25:04 | 약 2초 | **아래** | **아무 일도 안 일어남** |
| 창4 07:54:36 | 약 8초 | **위** | 3.5초 뒤부터 10칸 잠김 |

→ **끊김의 길이에 따라 화면의 실패 모드가 갈린다. 그리고 갈리는 방향이 반대다:**

- **3.5초 미만**: 화면이 눈치를 못 챈다 → 예약 확인이 **그대로 나간다** → 그 명령은 끊긴
  링크로 가므로 **ack 이 안 올 수 있다**(§4 의 경우 C — **아직 못 쟀다**)
- **3.5초 이상**: 화면이 잠근다 → 예약이 **안 나간다** → 대신 **틀린 이유를 말한다**(§3.3)

**즉 "짧으면 안전"이 아니다.** 짧으면 화면이 막지 못해 명령이 허공으로 나가고,
길면 막긴 하는데 이유를 잘못 말한다. **위험이 사라지는 구간이 없다.**

⚠ **전제**: 위는 끊김이 **모양 ①**(소켓이 닫히거나 대체되는 쪽)일 때다. 루트가 서버 로그로
확인했다 — 실물 3건 모두 `상대가 닫음`/`재접속으로 대체` 였다. **모양 ②(소켓 유지 · 프레임만
멈춤)는 실물에서 관측된 적이 없다**(§3.1 은 그 모양을 인공적으로 만들어 잰 것이다).

## 1. 🔴 먼저 갈라야 하는 것 — "끊김"이 두 가지다

**이 구분을 안 하면 답이 정반대로 나온다.** 서버 소스(`조별과제샘플/server.cpp`)를 읽어
확인했다(읽기만 했다. 내 파일이 아니다):

```cpp
static const int OFFLINE_MS = 3500;                                    // 102행
bool device_online() const {                                           // 885-886행
    return ard != BAD_SOCK && ard_seen && (now_ms() - ard_last_ms) < OFFLINE_MS;
}
```

조건이 **두 개의 OR 가 아니라 AND** 라서, 끊기는 모양에 따라 결과가 갈린다:

| 모양 | 무슨 일인가 | `ard != BAD_SOCK` | `now - last_ms < 3500` | **`device.online`** |
|---|---|---|---|---|
| **① 정상 종료** | 소켓이 FIN/RST 로 닫힌다 (프로세스 죽음·명시적 close) | **거짓 즉시** | (무관) | **즉시 false** |
| **② 조용한 정지** | 소켓은 살아 있고 S 프레임만 멈춘다 | 참 | 2초는 3.5초 미만 → 참 | **계속 true** |

→ **2초는 3.5초 임계값 아래다.** 그래서 ② 에서는 **서버가 끊김을 아예 인지하지 못하고**,
화면도 아무 일이 없다. ① 에서만 화면이 반응한다.

🔴 **실물 ESP 리셋이 ① 인지 ② 인지 나는 모른다.** 그건 arduino/socket 도메인이다.
**이 문서의 결과를 실물 예측으로 쓰려면 그것부터 확정해야 한다.** 여기서 답하는 것은
"이 모양이면 화면이 이렇게 된다"까지다.

본 뒤에 항목을 고르면 무엇을 봐도 "예상대로"가 된다. 그래서 먼저 적고 시작한다.

### 2.2 경우 (n 을 미리 정한다)

**타이밍에 따라 다를 것이므로 한 번 보고 결론짓지 않는다.** 각 3회:

| 경우 | 무엇을 하나 | n |
|---|---|---|
| **A. 조작 없이 끊김** | 화면을 띄워 두고 2초 끊었다 붙임 | 3 |
| **B. 대화상자가 열려 있는 동안 끊김** | 칸 클릭 → 대화상자 열림 → 끊김 → **끊긴 상태에서 확인 누름** | 3 |
| **C. 예약을 보낸 직후 끊김** | 확인 → `reserve` 송신 → 즉시 끊김 (ack 가 그 구간에 걸림) | 3 |

**B 와 C 가 시연에서 실제로 일어날 모양이다** — 하행 명령이 끊김의 *원인*이므로,
끊김은 항상 "누군가 예약을 누른 직후"에 온다. 조작 없는 A 는 오히려 인공적인 경우다.

### 2.3 예측 — 소스에서 미리 세운다 (틀리면 그대로 적는다)

**모양 ② 라면**: M1~M7 **전부 변화 없음.** 서버가 인지를 못 하므로 화면에 도달할 신호가 없다.
유일한 흔적은 `#dev-frame` 의 나이가 2초까지 자랐다가 돌아오는 것.

**모양 ① 이라면** — `index.html` 판독 기준:

- M3: 🔴 **빈 자리 10칸이 전부 잠긴다.** `tileView()` 1182-1183행 —
  `if (deviceDown) return { view:'free', disabled:true, meta:'센서 끊김 — 예약 불가' }`
- M4: **내 예약은 롤백되지 않는다.** 다만 **취소 동작이 사라진다**(1173행 `mine && canAct() && !deviceDown`)
- M2: 칸은 **안 빈다.** 값은 유지되고 잠기기만 한다
- M6: 🔴 **조작이 사라진다.** `requestReserve()` 1711-1716행 —
  확인을 누른 **뒤에** `tileView(slot).action !== 'reserve'` 를 재검사하는데, `deviceDown` 이면
  그 분기에 `action` 이 없어 **예약이 취소되고** 이렇게 뜬다:
  `"그 사이 자리 상태가 바뀌어 예약하지 않았습니다"`
  → **문구가 사실과 다르다.** 자리 상태는 안 바뀌었고 **장치 링크가 깜빡한 것**이다.
- C 의 ack: `ACK_TIMEOUT = 6000`(564행)이고 서버 재시도가 1500×3 = 4500ms(§7.3) 이므로
  **2초 끊김은 두 예산 안에 들어간다.** → 늦게라도 ack 이 와서 정상 확정될 것으로 예측한다.
  ⚠ 만약 ack 이 영영 안 오면 6초 뒤 `"응답이 없어 요청을 되돌렸습니다"` 로 롤백되는데,
  **그때 장치는 이미 예약을 적용했을 수 있다** — 화면과 장치가 갈린다. 이것이 최악의 경우이고
  C 에서 확인할 것이 정확히 이것이다.
- M5: 복구되면 다음 스냅샷에 `online:true` 가 실려 **자동 정상화**될 것으로 예측
- `UNCONFIRMED_MS = 12000`(563행) ≫ 2초 → **"그 뒤로 확인된 바 없음" 표시는 안 뜬다**

## 3. 실측

측정 환경: socket 이 띄운 **시험 인스턴스 10500**(아두이노 10591 · pid 1419 · `build=22f788d`),
`fake_arduino --start-empty`. **운영 포트 미접촉.** 하니스 `web/tools/blink.mjs`.

빌드 판별(§0단계)을 먼저 했다 — `GET /?demo=1 → 200`, `GET / → 200`.
**이 빌드는 REQ-0132 수정이 들어 있다**(옛 빌드면 404). 겸사겸사 REQ-0132 (2) 가
**web 쪽 실측으로도 확인**됐다.

### 3.1 모양 ② (3.5초 아래 침묵) — **화면에 아무 일도 일어나지 않는다** (실측)

`--mute-every 8 --mute-for 2`(소켓은 유지하고 S 프레임만 2초 멈춤) · **08:19:49~08:20:13** ·
250ms 간격 **95표본** · 원자료 `web/artifacts/blink-A.json`

| 항목 | 결과 |
|---|---|
| `device.online` | **95표본 전부 `true`** (false 0개) |
| M1 연결 표시·배너 | 변화 없음 |
| M2 10칸이 비는가 | **안 빈다** (상태 미상 0개) |

**침묵이 실제로 있었다는 증거**(안 그러면 "아무 일 없음"은 아무 의미가 없다):

2초 침묵 창이 자료에 그대로 찍혀 있다.

→ **§2.3 의 ② 예측이 그대로 맞았다.** `OFFLINE_MS=3500` 아래 침묵은 서버가 인지하지 못하므로
화면에 도달할 신호 자체가 없다.

### 3.1.1 🔴 이 측정에서 하마터면 잃을 뻔한 것 — "장치 없음"과 "침묵"은 화면에서 안 갈린다

측정 직전 3분간(08:16:33~08:19:19) **장치가 아예 안 붙어 있었다.** socket 이 `--mute-every` 를
검증하고 fake 를 껐는데 포트만 알려 주고 그 사실을 안 적었다(socket 이 스스로 잡아 알려 왔다).
그 구간에 쟀다면 **영구 오프라인을 "2초 침묵"으로 읽을 뻔했다.**

내 표본은 그 구간이 **아니다.** 08:19:49 시작이라 fake 재기동(08:19:19) 이후다. 그리고
**자료 자체가 그것을 증명한다**:

> 24초 동안 서로 다른 `last_frame_ts` 값이 **19개**였고 나이가 **진동**했다.
> 장치가 없으면 `last_frame_ts` 는 하나로 얼어붙고 나이는 **단조증가**한다(§5.2).

**→ 화면은 "침묵"과 "장치 부재"를 구별 못 하지만, `last_frame_ts` 의 시계열은 구별한다.
얼어 있으면 부재, 진동하면 연결.** 앞으로 측정 시작 전에 이것부터 본다.

멀쩡해 보이고, **칸을 눌러 봐야** 이유를 안다. 장치 패널은 접혀 있어 `센서: 끊김` 도 안 보인다.

### 3.3 🔴 모양 ① · **대화상자를 연 채 끊기면 — 조작이 사라진다. 3/3** (실측)

절차: 빈 자리 클릭 → 대화상자 열림 → `online=false` 가 될 때까지 대기 →
**끊긴 상태에서 "확인"** → 결과 관찰. **3회 전부 같은 결과.**

```
결과 칸   = A1: 빈 자리 / aria-disabled=true      ← 예약 안 됨
결과 문구 = "A1 · 그 사이 자리 상태가 바뀌어 예약하지 않았습니다"
그때 online = false (3회 모두)
```

**§2.3 에서 소스로 예측한 그대로다** — `requestReserve()` 1711-1716행이 확인을 누른 **뒤에**
`tileView(slot).action !== 'reserve'` 를 재검사하고, `deviceDown` 이면 그 분기에 `action` 이
없어 걸러진다.

🔴 **동작은 옳고 문구가 틀렸다.**
장치가 끊긴 동안 예약을 안 보내는 것은 맞다(보내도 못 간다). 그런데 화면은 그 이유를
**"자리 상태가 바뀌었다"** 고 말한다 — **자리 상태는 안 바뀌었다.** 바뀐 것은 장치 연결이다.
발표자·사용자는 "누가 먼저 채갔나?" 로 읽고 엉뚱한 곳을 본다.

**그리고 이 타이밍은 우연이 아니다.** 하행 명령 1건이 끊김의 *원인*이므로 끊김은 항상
**누군가 예약을 누른 직후**에 온다. 즉 **이 경우가 시연에서 가장 자주 만날 모양**이다.

### 4.1 🔴 경우 C (예약을 보낸 직후 끊김) — **못 쟀다. 이게 제일 위험한 자리다**

`ACK_TIMEOUT = 6000` 이므로 ack 이 6초 안에 안 오면 화면은
`"응답이 없어 요청을 되돌렸습니다"` 로 **롤백한다.** 그런데 **장치는 그 명령을 이미 받아
적용했을 수 있다** — 실제로 그 명령이 리셋을 유발했다면 **받긴 받은 것**이다.
→ **화면은 "예약 안 됨", 장치는 "예약됨". 둘이 갈린다.** 화면이 조용히 틀리는 유일한 경로다.

**재려면 필요한 것**: 하행을 받고 **ack 없이 소켓을 닫는** fake 모드(예: `--die-on-downlink`).
socket 에게 요청했다.

### 4.2 임계값을 걸치는 지점 — **2초와 6초만 쟀다.** 3초·4초·8초는 안 쟀다

`3500ms` 근처에서 거동이 뒤집히는 것을 2초(§3.1)와 6초(§3.2) **양끝으로만** 보였다.
경계 바로 앞뒤(3초·4초)는 재지 않았다. **"때에 따라 다르다"를 자료로 만들려면 그 둘이 필요하다.**

### 4.3 그 밖에

- **실물 ESP 가 ①/② 중 무엇인지** — **내가** 안 쟀다. 실물 보드 미접촉 조건이었다.
  루트가 **서버 로그로** 확인해 준 것을 §0.1 에 인용했다(내 측정이 아니다).
- ⚠ **§3.1.1 의 판별자에는 한계가 있다**(socket 지적): 침묵이 길면(6초) 그 동안
  `last_frame_ts` 는 **얼어 있으므로**, 그 구간에서 "얼었다 → 장치 없음"으로 읽으면 틀린다.
  판별자는 **침묵보다 긴 시간을 볼 때만** 유효하다.
- 실물 무선 구간의 지연·재전송 — `fake_arduino` 는 로컬 프로세스라 그 구간이 없다.
- 이 문서의 어떤 숫자도 **실물 왕복 시간의 기대값이 아니다**(LEDGER 3.4 와 같은 이유).
