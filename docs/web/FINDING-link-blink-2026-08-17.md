## 1. 🔴 먼저 갈라야 하는 것 — "끊김"이 두 가지다

**이 구분을 안 하면 답이 정반대로 나온다.** 서버 소스(`조별과제샘플/server.cpp`)를 읽어
확인했다(읽기만 했다. 내 파일이 아니다):

```cpp
static const int OFFLINE_MS = 3500;                                    // 102행
bool device_online() const {                                           // 885-886행
    return ard != BAD_SOCK && ard_seen && (now_ms() - ard_last_ms) < OFFLINE_MS;
}
```

조건이 **두 개의 OR 가 아니라 AND** 라서, 끊기는 모양에 따라 결과가 갈린다:

| 모양 | 무슨 일인가 | `ard != BAD_SOCK` | `now - last_ms < 3500` | **`device.online`** |
|---|---|---|---|---|
| **① 정상 종료** | 소켓이 FIN/RST 로 닫힌다 (프로세스 죽음·명시적 close) | **거짓 즉시** | (무관) | **즉시 false** |
| **② 조용한 정지** | 소켓은 살아 있고 S 프레임만 멈춘다 | 참 | 2초는 3.5초 미만 → 참 | **계속 true** |

→ **2초는 3.5초 임계값 아래다.** 그래서 ② 에서는 **서버가 끊김을 아예 인지하지 못하고**,
화면도 아무 일이 없다. ① 에서만 화면이 반응한다.

🔴 **실물 ESP 리셋이 ① 인지 ② 인지 나는 모른다.** 그건 arduino/socket 도메인이다.
**이 문서의 결과를 실물 예측으로 쓰려면 그것부터 확정해야 한다.** 여기서 답하는 것은
"이 모양이면 화면이 이렇게 된다"까지다.

본 뒤에 항목을 고르면 무엇을 봐도 "예상대로"가 된다. 그래서 먼저 적고 시작한다.

### 2.2 경우 (n 을 미리 정한다)

**타이밍에 따라 다를 것이므로 한 번 보고 결론짓지 않는다.** 각 3회:

| 경우 | 무엇을 하나 | n |
|---|---|---|
| **A. 조작 없이 끊김** | 화면을 띄워 두고 2초 끊었다 붙임 | 3 |
| **B. 대화상자가 열려 있는 동안 끊김** | 칸 클릭 → 대화상자 열림 → 끊김 → **끊긴 상태에서 확인 누름** | 3 |
| **C. 예약을 보낸 직후 끊김** | 확인 → `reserve` 송신 → 즉시 끊김 (ack 가 그 구간에 걸림) | 3 |

**B 와 C 가 시연에서 실제로 일어날 모양이다** — 하행 명령이 끊김의 *원인*이므로,
끊김은 항상 "누군가 예약을 누른 직후"에 온다. 조작 없는 A 는 오히려 인공적인 경우다.

### 2.3 예측 — 소스에서 미리 세운다 (틀리면 그대로 적는다)

**모양 ② 라면**: M1~M7 **전부 변화 없음.** 서버가 인지를 못 하므로 화면에 도달할 신호가 없다.
유일한 흔적은 `#dev-frame` 의 나이가 2초까지 자랐다가 돌아오는 것.

**모양 ① 이라면** — `index.html` 판독 기준:

- M3: 🔴 **빈 자리 10칸이 전부 잠긴다.** `tileView()` 1182-1183행 —
  `if (deviceDown) return { view:'free', disabled:true, meta:'센서 끊김 — 예약 불가' }`
- M4: **내 예약은 롤백되지 않는다.** 다만 **취소 동작이 사라진다**(1173행 `mine && canAct() && !deviceDown`)
- M2: 칸은 **안 빈다.** 값은 유지되고 잠기기만 한다
- M6: 🔴 **조작이 사라진다.** `requestReserve()` 1711-1716행 —
  확인을 누른 **뒤에** `tileView(slot).action !== 'reserve'` 를 재검사하는데, `deviceDown` 이면
  그 분기에 `action` 이 없어 **예약이 취소되고** 이렇게 뜬다:
  `"그 사이 자리 상태가 바뀌어 예약하지 않았습니다"`
  → **문구가 사실과 다르다.** 자리 상태는 안 바뀌었고 **장치 링크가 깜빡한 것**이다.
- C 의 ack: `ACK_TIMEOUT = 6000`(564행)이고 서버 재시도가 1500×3 = 4500ms(§7.3) 이므로
  **2초 끊김은 두 예산 안에 들어간다.** → 늦게라도 ack 이 와서 정상 확정될 것으로 예측한다.
  ⚠ 만약 ack 이 영영 안 오면 6초 뒤 `"응답이 없어 요청을 되돌렸습니다"` 로 롤백되는데,
  **그때 장치는 이미 예약을 적용했을 수 있다** — 화면과 장치가 갈린다. 이것이 최악의 경우이고
  C 에서 확인할 것이 정확히 이것이다.
- M5: 복구되면 다음 스냅샷에 `online:true` 가 실려 **자동 정상화**될 것으로 예측
- `UNCONFIRMED_MS = 12000`(563행) ≫ 2초 → **"그 뒤로 확인된 바 없음" 표시는 안 뜬다**

## 3. 실측

측정 환경: socket 이 띄운 **시험 인스턴스 10500**(아두이노 10591 · pid 1419 · `build=22f788d`),
`fake_arduino --start-empty`. **운영 포트 미접촉.** 하니스 `web/tools/blink.mjs`.

빌드 판별(§0단계)을 먼저 했다 — `GET /?demo=1 → 200`, `GET / → 200`.

### 3.1 모양 ② (3.5초 아래 침묵) — **화면에 아무 일도 일어나지 않는다** (실측)

`--mute-every 8 --mute-for 2`(소켓은 유지하고 S 프레임만 2초 멈춤) · **08:19:49~08:20:13** ·

|---|---|

| M1 연결 표시·배너 | 변화 없음 |

**침묵이 실제로 있었다는 증거**(안 그러면 "아무 일 없음"은 아무 의미가 없다):

2초 침묵 창이 자료에 그대로 찍혀 있다.

→ **§2.3 의 ② 예측이 그대로 맞았다.** `OFFLINE_MS=3500` 아래 침묵은 서버가 인지하지 못하므로
화면에 도달할 신호 자체가 없다.

### 3.1.1 🔴 이 측정에서 하마터면 잃을 뻔한 것 — "장치 없음"과 "침묵"은 화면에서 안 갈린다

측정 직전 3분간(08:16:33~08:19:19) **장치가 아예 안 붙어 있었다.** socket 이 `--mute-every` 를
검증하고 fake 를 껐는데 포트만 알려 주고 그 사실을 안 적었다(socket 이 스스로 잡아 알려 왔다).
그 구간에 쟀다면 **영구 오프라인을 "2초 침묵"으로 읽을 뻔했다.**

내 표본은 그 구간이 **아니다.** 08:19:49 시작이라 fake 재기동(08:19:19) 이후다. 그리고
**자료 자체가 그것을 증명한다**:

> 24초 동안 서로 다른 `last_frame_ts` 값이 **19개**였고 나이가 **진동**했다.
> 장치가 없으면 `last_frame_ts` 는 하나로 얼어붙고 나이는 **단조증가**한다(§5.2).

**→ 화면은 "침묵"과 "장치 부재"를 구별 못 하지만, `last_frame_ts` 의 시계열은 구별한다.
얼어 있으면 부재, 진동하면 연결.** 앞으로 측정 시작 전에 이것부터 본다.

- 이 문서의 어떤 숫자도 **실물 왕복 시간의 기대값이 아니다**(LEDGER 3.4 와 같은 이유).
