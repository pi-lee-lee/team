# 장치 온보딩 흐름 — 정밀 검토와 가이드 (2026-08-19 · 사용자 요청)

> 사용자 원문 요지: 개발자가 만든 아두이노가 ESP01 로 접속 → 보유 모듈을 서버에 올림 →
> 서버가 **신규/기존/구성변경**을 판정해 노드를 등록·활성화 → **관리자 페이지에서 주차구역에 할당** →
> **모듈의 동작 방식을 결정**(← 여기가 안 떠오른다) → 완료하면 `index.html` 에 노출.
> **동기**: *"서버에 모듈과 동작을 코딩으로 해야 하면 다인원이 서버 로직을 직접 컨트롤하는 게 쉽지 않다."*

**결론부터**: 방향이 맞다. 다만 **지금 구조가 정확히 그 반대로 되어 있고**, 선결 과제가 셋이다.
그리고 막힌 부분("동작 방식 결정")에는 **함정이 하나 있고 답은 그 반대편에 있다.**

## 1. 🔴 지금 구조가 왜 그 문제를 만드는가 — 값으로

```
① 결속이 **이름 일치**다
   Modules.h:25  "D,<name>,<kind> 의 name 이 **자리 id 와 같으면** 그 자리에 붙는다"
   → 🔴 **배치가 펌웨어에 박혀 있다.** 자리를 바꾸려면 **다시 구워야** 한다
   → 사용자가 말한 "코딩으로 컨트롤" 이 바로 이것이다(코드가 아니라 *이름* 이라는 형태일 뿐)

② `devid` 가 컴파일 상수다
   Config.h:39  #define DEVICE_ID "P1"
   → 🔴 **모든 보드가 P1 이다.** "신규인가 기존인가"를 **물을 수가 없다**
   ⚠ 2026-08-18 에 조원들의 동일 카피 보드 때문에 관측이 반나절 오염될 뻔한 그 축이다

③ 서버가 등록을 **영속하지 않는다**
   persist.h 에 노드·모듈 관련 저장이 없다
   → 🔴 재기동하면 **누가 있었는지 다 잊는다.** 대장(臺帳)이 없다

④ `D,*,<drain>,<n>,<ck>` 의 `<ck>` 는 **프레임 체크섬**이지 구성 지문이 아니다
   → "모듈이 바뀌었나"를 **한 필드로 못 묻는다**
```

> ### **넷을 한 줄로: 지금은 *펌웨어가 배치를 알고, 서버는 아무것도 기억하지 않는다.* 사용자 안은 그 반대다.**

```
                    ┌─────────── 장치 접속 (S 프레임 첫 도착)
```

**없는 모듈을 가리키는 자리**가 생긴다. **사람이 한 번 봐야 한다.**

## 3. 🔴 선결 과제 셋 — 이게 없으면 위 흐름이 성립하지 않는다

### (1) `devid` 전역 고유 — **1번이고, 다른 모든 것의 전제**

```
지금 : #define DEVICE_ID "P1"      (컴파일 상수 · 모든 보드가 같다)
안   : **EEPROM 에 최초 부팅 시 1회 생성해 저장**
       비어 있으면 만들고, 있으면 읽는다 → **같은 펌웨어를 여러 장에 구워도 서로 다르다**
```
🔑 **굽기와 신원을 분리하는 것이 요점이다.** 지금은 굽는 순간 신원이 정해져서 복제된다.
⚠ 난수 원천: `analogRead(미배선 핀) ^ micros()` 는 이미 `randomSeed` 에 쓰고 있다. 그것으로 충분하다.
⚠ **사람이 읽을 이름은 따로다** — `devid` 는 기계용(고유), 표시 이름은 관리자가 붙인다.

### (2) 모듈 구성 지문 — 전선에 한 필드

```
지금 : D,*,<drain>,<n>,<ck>          <ck> 는 프레임 체크섬
안   : D,*,<drain>,<n>,<fp>,<ck>     <fp> = (name,kind) 목록을 **순서대로** 접은 값
```
🔑 **서버가 한 번의 비교로 "그대로/바뀜"을 안다.** 모듈 줄을 다 모아 대조할 필요가 없다.
⚠ **순서를 포함해야 한다** — `idx` 가 순서로 정해지므로 순서가 바뀌면 다른 구성이다.

### (3) 서버 대장 영속

```
data_log.json 에 추가:
  nodes       : devid → { 표시이름, 최초등록, 최종접속, 모듈목록, 지문, 상태 }
  assignments : (devid, 모듈idx) → { 자리id, 역할, 정책 }
```
⚠ **할당은 `devid` + `모듈 idx` 로 건다.** 이름으로 걸면 ①의 문제가 그대로 남는다.

## 4. 🔴 막힌 부분의 답 — "모듈의 동작 방식을 결정한다"

### 함정부터: **자유로운 규칙을 만들게 하면 안 된다**

```
❌ "조건이 A 이면 B 한다" 를 관리자가 조립하게 한다
   → 그건 **코딩을 화면으로 옮긴 것**이지 없앤 것이 아니다
   → 규칙이 서로 간섭하면 **코드보다 디버깅이 어렵다**(순서·우선순위·순환)
   → 🔴 **사용자가 피하려던 복잡도가 다른 옷을 입고 돌아온다**
```

### ✅ 답: **유한한 정책 목록에서 *고르게* 한다**

**서버가 정책을 구현하고, 관리자는 조합만 한다.**

```
■ 역할(role) — 이 모듈이 이 자리에서 무엇인가
   주점유센서 · 보조점유센서 · 차단봉 · 표시등 · 미사용

■ 자리 판정 정책 — 그 자리의 점유를 어떻게 정하나
   아무거나(OR)   ← 🔑 지금 하드코딩된 것이 바로 이것이다
   모두(AND)
   다수결
   주센서만 (보조는 **불일치 감지용**으로만 쓴다 — 지금 `센서갈림` 계기가 그 자리다)

■ 차단봉 정책 — 언제 여는가
   수동만 · 예약확인시 자동 · 입구전용 · 출구전용
```

> ### **관리자가 만드는 것은 *조합* 이지 *로직* 이 아니다.**

```
조합은 유한하다        → 전부 시험할 수 있다. 자가검증에 넣을 수 있다
새 동작이 필요하면      → **정책을 하나 추가한다.** 그건 코딩이지만 **한 번**이고 개발자 몫이다
다인원이 하는 것은      → **배치와 선택뿐.** 서버 로직을 안 만진다  ← 사용자가 원한 것
```

⚠ **정책 이름이 곧 계약이다.** 오늘 `n` 이 *"자리 수"* 와 *"모듈 수"* 두 뜻을 겸해서
값이 갈릴 때까지 아무도 몰랐다. **정책 이름은 "무엇을 하는가"로 짓고 "어디에 쓰는가"로 짓지 마라.**

⚠ **그리고 정책마다 "이 정책이 답하지 않는 것"을 적어라.** 예: `아무거나(OR)` 는
*"두 센서가 갈렸다"* 를 **감추지 않는다** — 계기는 계속 센다. 그걸 안 적으면 다음 사람이 정책이
불일치를 해결한 줄 안다.

---

## 5. 무엇을 어디에 두나 — 경계

```
펌웨어  devid(EEPROM) · 모듈 목록 · 지문        🔴 **배치를 모른다**
전선    등록(D)에 지문 한 필드 추가. 나머지 그대로
서버    노드 대장 · 할당 · 정책 선택 · 판정      → data_log.json 에 영속
화면    관리자 페이지(할당·정책) + index.html(운영)
```

> ### **핵심은 "펌웨어가 배치를 모르게 하는 것"이다. 지금은 이름으로 알고 있다.**

---

## 6. 순서 — 한 번에 하나. 각 단계가 **혼자서 값이 있어야** 한다

```
1. devid 고유화(EEPROM)        굽기 필요 · **다른 모든 것의 전제**
                               단독 값: 보드가 여럿이어도 서버가 구분한다
2. 서버 대장 영속               할당 없이 먼저 · 단독 값: **재기동해도 누가 있었는지 기억한다**
3. 모듈 지문 한 필드            굽기 필요 · 단독 값: "구성이 바뀌었다"를 서버가 안다
4. 관리자 화면 — **할당만**     정책 없이 · 단독 값: **굽지 않고 자리를 바꿀 수 있다** ← 사용자 목표의 절반
5. 정책 — **자리 판정 하나만**  단독 값: OR 말고 다른 판정을 코딩 없이 고른다
6. index.html 이 할당을 읽는다  단독 값: 화면이 대장을 따라간다
```

### ⚠ 이름 일치 결속을 언제 버리나 — **버리지 말고 강등한다**

```
4단계 이후 : 할당이 **있으면** 할당으로, **없으면** 지금처럼 이름 일치로
→ 옛 장치가 계속 동작한다. 마이그레이션이 필요 없다
→ 🔑 그리고 "할당이 없는 노드"가 관리자 화면에 자연히 뜬다 — 그게 [미할당] 상태다
```

---

## 7. ⚠ 이 설계가 답하지 *않는* 것 — 미리 적어 둔다

```
· **권한** — 누가 할당할 수 있나. 지금 관리자 페이지에 인증이 없다
· **충돌** — 두 관리자가 같은 자리에 다른 모듈을 동시에 할당하면
· **모듈 제거** — 장치에서 모듈이 빠졌을 때 옛 할당·옛 예약을 어떻게 하나
· **정책 변경 시점** — 운영 중에 정책을 바꾸면 진행 중인 예약은 어떻게 되나
```
🔑 **넷 다 "나중에"로 둬도 되지만, *적어 두지 않으면* 구현하다 만나서 즉흥으로 정하게 된다.**

# 🔴 개정 1 (2026-08-19 저녁) — socket 의 반박 넷을 전부 받는다

**루트가 쓴 §3(3)·§6 순서가 틀렸다. socket 이 코드로 반박했고 값이 맞다.**

## ① 저장 위치 — `data_log.json` 은 **안 된다**

```
config.h:245  LOG_KEEP = 2 · persist.h:67 초과분 pop_back()  → 🔴 **최신 2건만 남기고 버린다**
persist.h:83  dst = "data_log.json"                          → 🔴 **cwd 상대.** 오늘 §5.85 가 그 함정이었다
http.h:296    이 파일은 **브라우저에 그대로 서빙된다**        → 🔴 devid·지문이 인증 없이 공개
persist.h:29  쓰기 조건이 **자리 비트열**                     → 🔴 대장만 바뀌면 **조용히 안 쓴다**
```
> ### **`data_log.json` 은 *회전하는 로그* 이고 대장은 *신원* 이다. 수명이 다른 것을 한 파일에 못 둔다.**

✅ **간다**: `~/parking-logs/parking-nodes.json` — **절대경로** · offset 이면 `.test+300` 분리.
**rid 커서가 이미 그 형태이고 재기동을 건너 사는 것이 실측됐다**(오늘 "이어받음 4420").
⚠ HOME 없으면 **영속 불가를 크게 로그에 남기고 메모리로만** · `no_disk`(자가검증)면 안 건드린다.

## ② 🔴 `devid` 가 전부 `P1` 인 동안 대장은 **조용히 거짓을 쌓는다**

루트가 *"한 줄만 생긴다, 구조는 맞다"* 고 했는데 **한 줄이 문제가 아니다:**
```
두 보드가 번갈아 붙으면 → 같은 `P1` 행에 **서로 다른 보드의 모듈 목록이 번갈아 덮인다**
→ 지문이 매번 바뀌어 대장이 **"구성이 바뀌었다"를 계속 보고한다**
→ ⚠ 원인은 구성 변경이 아니라 **다른 보드**인데 대장에 그 구분이 없다
```
✅ **대장에 `last_peer_ip` 를 같이 적는다.** *"`devid` 가 고유하지 않을 때 남는 유일한 구분자는
커널이 주는 주소다"* — 2026-08-18 에 그 부재로 반나절을 썼다. **이건 기능이 아니라 관측 요건이다.**

## ③ 🔴 **(3) 모듈 지문은 전제가 아니라 *최적화* 다 — 순서가 바뀐다**

```
루트 안 : 장치가 지문을 계산해 `D,*` 에 싣는다 → **굽기 필요** → (4) 보다 앞
🔴 사실  : 서버가 **이미 모듈 목록 전부를 갖고 있다**(`park.mods`)
          → **서버가 순서대로 접으면 지문이 나온다. 전선 필드가 없어도 된다**
```
> ### **(2) 만으로 신규/기존/구성변경 판정이 성립한다. (3) 은 "모듈 줄을 다 모으기 전에 안다"는 이득뿐이다.**

✅ **그래서 순서를 바꾼다: (2) → **(4) 관리자 화면** → (5) 정책 → (1)(3) 은 굽기 묶어서 나중에.**
🔑 **(4) 가 사용자 목표의 절반("굽지 않고 자리를 바꾼다")인데, 굽기 없이 갈 수 있게 됐다.**
⚠ **다만 등록이 중간에 끊기면 목록이 부분이다** → **`reg_done` 뒤에만 접는다.**
안 그러면 거짓 "구성 변경"이 된다.

## ④ 빈 자리 하나 — **"최종접속"을 언제 쓰나**

루트가 필드만 적고 **갱신 시점을 안 적었다**(§"계약의 빈 자리는 받는 쪽이 메운다").
✅ **socket 이 정하고 문서에 박는다:**
```
쓰는 시점 : ① 등록 완료 ② 세션 종료 ③ 지문 변경 ④ 할당 변경   ← **사건이 있을 때만**
안 쓰는 것 : 매 프레임 · 매 슬롯 → 정상 운영에서 **세션당 두 번**
⚠ 대가 : SIGKILL 로 죽으면 마지막 "최종접속"이 안 남는다. **받아들인다** —
        대장의 목적은 *누가 있었나* 이지 *언제까지 있었나* 가 아니다
```

## 🔑 이 개정에서 배운 것

> ### **"전제"라고 쓴 것이 정말 전제인지 받는 쪽에 확인해라.**
> **루트는 (3)을 (4)의 전제로 뒀는데, 받는 쪽은 그 자료를 *이미 갖고 있었다.***
> **그래서 굽기 하나가 계획에서 통째로 빠졌다.**

⚠ **설계자는 "장치가 보내야 한다"로 생각하고, 구현자는 "이미 있다"를 안다.**
**순서를 정하기 전에 각 단계의 전제를 그 도메인에 물어라.**

# 🔴 개정 2 — **"장치가 명세와 반대로 코딩하면?"** (사용자 물음, 2026-08-19)

> 사용자 원문: *"서버의 명세와 다른 동작을 하도록 아두이노 코딩을 하면 어떻게 되나?
> 즉 1이면 차 없음 0이면 차 있음인데 아두이노에서 반대로 센서 설정을 했다면?"*

## 짧은 답: **막을 수 없다. 그리고 그것이 정상이다.**

```
zone.h:25   int occupied;   // **아두이노가 진실값을 준다**   ← 🔴 계약이 이미 여기 적혀 있다
```
**`1` 은 `1` 이다. 값 하나로는 의미를 검증할 수 없다.**
> ### **의미는 *값* 이 아니라 **값과 실제 세계의 대응** 에서만 검증된다.**

### 반전된 장치를 붙이면 실제로 일어나는 일
```
화면에 **정확히 반대로** 표시된다
서버는 이상을 못 느낀다 — **모든 검사를 통과한다**(체크섬·계약·자가검증 전부 정상)
🔴 예약이 **점유된 자리에** 걸리고, 빈 자리는 "차 있음"으로 막힌다
```

---

## ✅ 그런데 우리 구조에 답의 절반이 이미 있다 — **자리당 센서 둘**

```
자리 A1 = 센서 A1 + B1
🔴 극성이 반대인 센서 하나가 붙으면 → **두 센서가 *항상* 반대다**
✅ `센서갈림` 계기가 이미 그것을 센다 (metrics.h:353 · `sensor_split_now`)
```
> ### **가끔 갈리면 *고장* 이고, **항상** 갈리면 *극성* 이다. 서명이 다르다.**
⚠ **센서가 하나인 자리는 못 잡는다.** 그래서 아래 세 겹이 필요하다.

---

## 세 겹으로 답한다

### 1겹 — **극성을 서버 설정으로** (정책 목록의 하나)
```
모듈별 : 정상 / 반전
```
🔑 **펌웨어를 안 고치고 바로잡을 수 있다.** 사용자가 원한 "코딩 없이"의 연장이다.
⚠ **설정을 잘못하면 여전히 틀린다** → 2겹이 필요하다.

### 2겹 — 🔴 **교정(calibration)으로 확정한다. 이게 진짜 답이다**
```
관리자 화면 : "이 자리를 **비워** 주세요"  → 값 읽음
              "이제 **차를 대** 주세요"    → 값 읽음
→ 두 값이 다르면 **극성이 관측으로 결정된다.** 문서가 아니라 사실로
```
> ### **의미는 선언으로 정해지지 않는다. *상태 변화와 실제 세계의 대응* 으로 정해진다.**
⚠ **두 값이 *같으면* 그것도 결과다** — 센서가 안 붙었거나 고장이다. **교정이 그것도 잡는다.**
🔑 그리고 교정 결과는 **대장에 저장한다** — 그러면 재기동해도 유지되고, 장치를 바꾸면 다시 한다.

### 3겹 — 자동 의심 신호 (사람이 안 봐도 뜬다)
```
· 두 센서가 **항상** 반대            → 극성 의심 (`센서갈림` 이 이미 센다)
· 한 자리가 오래 **변화 없이 점유**   → 의심
· 차단봉이 열렸는데 **어떤 자리도 0→1 이 아님** → 의심
```

---

## 🔴 그리고 근본 — 경계를 어디에 긋나

> ### **서버는 *의미* 를 정의하고, 장치는 *그 의미대로 값을 만들* 책임을 진다.**
> ### **서버가 그것을 강제할 수는 없다. 강제할 수 있는 것은 *어긋남이 드러나고 고쳐지는 것* 이다.**

```
❌ 목표를 "틀린 장치를 막는다"로 두면   → **불가능하다.** 무엇을 해도 장치가 거짓말하면 모른다
✅ "틀린 장치를 **빨리 드러내고 코딩 없이 고친다**" → 가능하고, **사용자 목표와 같은 방향이다**
```

## ⚠ 장치가 극성을 *선언* 하게 하는 안은 답이 아니다

`D,<name>,<kind>,<flags>` 에 극성 비트를 넣을 수 있다.
🔴 **그런데 선언도 코딩이다. 반대로 코딩한 사람은 선언도 반대로 한다.**
**문제를 한 칸 옮길 뿐이다.**
🔑 **일반화**: **"장치가 스스로 신고하게 한다"는 장치가 틀렸을 때의 대책이 될 수 없다.**
**대책은 *다른 곳에서 관측* 하는 것뿐이다** — 교정도, 두 센서 대조도, 전부 그 형태다.

# 🔴 개정 3 — **모듈 종류 카탈로그를 서버가 가져야 하나** (사용자 물음)

> *"모듈 목록을 서버에서 관리해야 되는 것인가? 아두이노에 있는 목록이 아닌
> **아두이노가 가질 수 있는 모듈 전체 목록**이다."*

## 답: **네. 다만 이유가 *극성* 이 아니다 — 그 오해를 먼저 끊는다**

```
🔴 카탈로그가 "IP: 1 = 차 있음" 이라고 정의해도,
   아두이노가 반대로 코딩하면 **서버는 여전히 모른다**
→ 카탈로그는 **의미를 한 곳에 모으는 것**이지 **강제하는 것이 아니다**
```
✅ **다만 카탈로그가 있으면 *교정* 이 체계화된다** — 카탈로그가 *"이 종류는 이진값이고 교정이 필요하다"* 를
알면 관리자 화면이 **자동으로 교정 단계를 띄운다.** **해결책이 아니라 해결책을 적용할 기반이다.**

---

## 🔴 진짜 이유 — 지금 종류 하나를 추가하려면 **세 도메인을 다 고쳐야 한다**

**실측으로 흩어진 자리:**
```
펌웨어  Modules.h:40   char kind[4]  ·  MODULE_TABLE 에 KIND_PARK_SENSOR 하드코딩
서버    downlink.h:110 kind_commandable(...)     ← 조작 가능 여부가 코드에
        downlink.h:211 p.kind == 'G' / 'M' / 'T' ← 하행 갈래가 **코드 분기**
화면    index.html:2072 '차단봉 열기' / '차단봉 닫기'  ← 한글 라벨이 코드에
```
> ### **새 모듈 종류 하나 = 세 도메인의 코드 수정. 이것이 "다인원이 못 한다"의 정확한 원인이다.**

## 🔴 그리고 더 나쁜 것 — **모르는 종류가 조용히 버려진다**

```
uplink.h:282  "이 분기가 없으면 `D` 는 **`drop_unknown`("AT 잡음 유입 의심")** 으로 떨어진다"
```
**새 종류를 만든 개발자의 장치가 붙으면 → 서버가 그것을 *AT 잡음* 으로 버린다.**
🔴 **그 개발자는 왜 안 되는지 모른다. 로그에는 "잡음 의심"이라고 적혀 있다.**
> ### **카탈로그의 첫째 값은 통제가 아니라 — **모르는 것을 "모른다"고 말하게 하는 것** 이다.**

---

## 카탈로그에 무엇을 담나

```
kind 코드     "IP"
표시 이름     "주차확인센서"          ← 지금 화면에 하드코딩된 것
값 의미       1 = 차 있음 / 0 = 없음   ⚠ **선언이지 보증이 아니다**(개정 2)
값 domain     이진 / 범위
방향          센서(읽기) / 액추에이터(조작)   ← 지금 `kind_commandable()` 이 코드로 아는 것
고를 수 있는 정책  [아무거나(OR), 모두(AND), 다수결, 주센서만]
교정 필요 여부    예 / 아니오 · 교정 절차 종류
```

🔑 **그러면 이렇게 바뀐다:**
```
종류 추가 = **카탈로그에 한 줄**  (그 종류의 동작이 기존 정책으로 표현되는 한)
❌ 지금 = 펌웨어 상수 + 서버 분기 + 화면 라벨, **세 곳**
```

---

## ⚠ 카탈로그가 **못 하는 것** — 미리 못 박는다

```
① 극성 강제      → 못 한다. **교정으로만 확정된다**(개정 2)
② 완전히 새로운 동작 → 기존 정책으로 표현이 안 되면 **여전히 코딩이다**
   🔑 다만 그 코딩은 **정책 하나 추가**이고, 그 뒤로는 데이터다
③ 펌웨어와의 동기 → 장치가 카탈로그에 없는 kind 를 보내는 것을 막을 수 없다
   ✅ 대신 **"미등록 종류"로 명확히 보고**하고 관리자가 카탈로그에 추가하게 한다
```

> ### **카탈로그는 *강제* 가 아니라 *합의의 저장소* 다. 어긋남을 없애지 못하고, 어긋남을 *보이게* 한다.**

## 어디에 두나

```
`~/parking-logs/parking-catalog.json`  — 대장과 같은 규율(절대경로 · offset 분리 · HOME 없으면 경보)
⚠ 기본 카탈로그는 **코드에 내장**하고 파일이 없으면 그것으로 시작한다
   → 파일이 사라져도 지금 종류들은 계속 돈다. §"시험이 준비를 대신해 주면 실기만 빈다" 의 반대 대비
```

