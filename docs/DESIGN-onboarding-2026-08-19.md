# 장치 온보딩 흐름 — 정밀 검토와 가이드 (2026-08-19 · 사용자 요청)

> 사용자 원문 요지: 개발자가 만든 아두이노가 ESP01 로 접속 → 보유 모듈을 서버에 올림 →
> 서버가 **신규/기존/구성변경**을 판정해 노드를 등록·활성화 → **관리자 페이지에서 주차구역에 할당** →
> **모듈의 동작 방식을 결정**(← 여기가 안 떠오른다) → 완료하면 `index.html` 에 노출.
> **동기**: *"서버에 모듈과 동작을 코딩으로 해야 하면 다인원이 서버 로직을 직접 컨트롤하는 게 쉽지 않다."*

**결론부터**: 방향이 맞다. 다만 **지금 구조가 정확히 그 반대로 되어 있고**, 선결 과제가 셋이다.
그리고 막힌 부분("동작 방식 결정")에는 **함정이 하나 있고 답은 그 반대편에 있다.**

---

## 1. 🔴 지금 구조가 왜 그 문제를 만드는가 — 값으로

```
① 결속이 **이름 일치**다
   Modules.h:25  "D,<name>,<kind> 의 name 이 **자리 id 와 같으면** 그 자리에 붙는다"
   → 🔴 **배치가 펌웨어에 박혀 있다.** 자리를 바꾸려면 **다시 구워야** 한다
   → 사용자가 말한 "코딩으로 컨트롤" 이 바로 이것이다(코드가 아니라 *이름* 이라는 형태일 뿐)

② `devid` 가 컴파일 상수다
   Config.h:39  #define DEVICE_ID "P1"
   → 🔴 **모든 보드가 P1 이다.** "신규인가 기존인가"를 **물을 수가 없다**
   ⚠ 2026-08-18 에 조원들의 동일 카피 보드 때문에 관측이 반나절 오염될 뻔한 그 축이다

③ 서버가 등록을 **영속하지 않는다**
   persist.h 에 노드·모듈 관련 저장이 없다
   → 🔴 재기동하면 **누가 있었는지 다 잊는다.** 대장(臺帳)이 없다

④ `D,*,<drain>,<n>,<ck>` 의 `<ck>` 는 **프레임 체크섬**이지 구성 지문이 아니다
   → "모듈이 바뀌었나"를 **한 필드로 못 묻는다**
```

> ### **넷을 한 줄로: 지금은 *펌웨어가 배치를 알고, 서버는 아무것도 기억하지 않는다.* 사용자 안은 그 반대다.**

## 2. 흐름을 상태로 — 사용자 안을 그대로 옮긴 것

```
                    ┌─────────── 장치 접속 (S 프레임 첫 도착)
                    ▼
              [미식별]  devid 로 대장 조회
                    │
    ┌───────────────┼────────────────┐
    ▼               ▼                ▼
 [신규]        [기존·지문 동일]   [기존·지문 변경]
    │               │                │
    ▼               ▼                ▼
 [미할당]        [운영] ←──────  [재확인 필요]
    │                                │
    │  관리자: 모듈 → 자리 할당        │ 관리자: 변경 확인·재할당
    ▼                                │
 [할당됨] ── 정책 선택 ──▶ [운영] ◀───┘
                            │
                            ▼
                     index.html 에 노출
```

⚠ **`[기존·지문 변경]` 을 `[운영]` 으로 바로 보내지 마라.** 모듈이 빠졌는데 옛 할당이 남으면
**없는 모듈을 가리키는 자리**가 생긴다. **사람이 한 번 봐야 한다.**

## 3. 🔴 선결 과제 셋 — 이게 없으면 위 흐름이 성립하지 않는다

### (1) `devid` 전역 고유 — **1번이고, 다른 모든 것의 전제**

```
지금 : #define DEVICE_ID "P1"      (컴파일 상수 · 모든 보드가 같다)
안   : **EEPROM 에 최초 부팅 시 1회 생성해 저장**
       비어 있으면 만들고, 있으면 읽는다 → **같은 펌웨어를 여러 장에 구워도 서로 다르다**
```
🔑 **굽기와 신원을 분리하는 것이 요점이다.** 지금은 굽는 순간 신원이 정해져서 복제된다.
⚠ 난수 원천: `analogRead(미배선 핀) ^ micros()` 는 이미 `randomSeed` 에 쓰고 있다. 그것으로 충분하다.
⚠ **사람이 읽을 이름은 따로다** — `devid` 는 기계용(고유), 표시 이름은 관리자가 붙인다.

### (2) 모듈 구성 지문 — 전선에 한 필드

```
지금 : D,*,<drain>,<n>,<ck>          <ck> 는 프레임 체크섬
안   : D,*,<drain>,<n>,<fp>,<ck>     <fp> = (name,kind) 목록을 **순서대로** 접은 값
```
🔑 **서버가 한 번의 비교로 "그대로/바뀜"을 안다.** 모듈 줄을 다 모아 대조할 필요가 없다.
⚠ **순서를 포함해야 한다** — `idx` 가 순서로 정해지므로 순서가 바뀌면 다른 구성이다.

### (3) 서버 대장 영속

```
data_log.json 에 추가:
  nodes       : devid → { 표시이름, 최초등록, 최종접속, 모듈목록, 지문, 상태 }
  assignments : (devid, 모듈idx) → { 자리id, 역할, 정책 }
```
⚠ **할당은 `devid` + `모듈 idx` 로 건다.** 이름으로 걸면 ①의 문제가 그대로 남는다.

## 4. 🔴 막힌 부분의 답 — "모듈의 동작 방식을 결정한다"

### 함정부터: **자유로운 규칙을 만들게 하면 안 된다**

```
❌ "조건이 A 이면 B 한다" 를 관리자가 조립하게 한다
   → 그건 **코딩을 화면으로 옮긴 것**이지 없앤 것이 아니다
   → 규칙이 서로 간섭하면 **코드보다 디버깅이 어렵다**(순서·우선순위·순환)
   → 🔴 **사용자가 피하려던 복잡도가 다른 옷을 입고 돌아온다**
```

### ✅ 답: **유한한 정책 목록에서 *고르게* 한다**

**서버가 정책을 구현하고, 관리자는 조합만 한다.**

```
■ 역할(role) — 이 모듈이 이 자리에서 무엇인가
   주점유센서 · 보조점유센서 · 차단봉 · 표시등 · 미사용

■ 자리 판정 정책 — 그 자리의 점유를 어떻게 정하나
   아무거나(OR)   ← 🔑 지금 하드코딩된 것이 바로 이것이다
   모두(AND)
   다수결
   주센서만 (보조는 **불일치 감지용**으로만 쓴다 — 지금 `센서갈림` 계기가 그 자리다)

■ 차단봉 정책 — 언제 여는가
   수동만 · 예약확인시 자동 · 입구전용 · 출구전용
```

> ### **관리자가 만드는 것은 *조합* 이지 *로직* 이 아니다.**

```
조합은 유한하다        → 전부 시험할 수 있다. 자가검증에 넣을 수 있다
새 동작이 필요하면      → **정책을 하나 추가한다.** 그건 코딩이지만 **한 번**이고 개발자 몫이다
다인원이 하는 것은      → **배치와 선택뿐.** 서버 로직을 안 만진다  ← 사용자가 원한 것
```

⚠ **정책 이름이 곧 계약이다.** 오늘 `n` 이 *"자리 수"* 와 *"모듈 수"* 두 뜻을 겸해서
값이 갈릴 때까지 아무도 몰랐다. **정책 이름은 "무엇을 하는가"로 짓고 "어디에 쓰는가"로 짓지 마라.**

⚠ **그리고 정책마다 "이 정책이 답하지 않는 것"을 적어라.** 예: `아무거나(OR)` 는
*"두 센서가 갈렸다"* 를 **감추지 않는다** — 계기는 계속 센다. 그걸 안 적으면 다음 사람이 정책이
불일치를 해결한 줄 안다.

## 5. 무엇을 어디에 두나 — 경계

```
펌웨어  devid(EEPROM) · 모듈 목록 · 지문        🔴 **배치를 모른다**
전선    등록(D)에 지문 한 필드 추가. 나머지 그대로
서버    노드 대장 · 할당 · 정책 선택 · 판정      → data_log.json 에 영속
화면    관리자 페이지(할당·정책) + index.html(운영)
```

> ### **핵심은 "펌웨어가 배치를 모르게 하는 것"이다. 지금은 이름으로 알고 있다.**

---

## 6. 순서 — 한 번에 하나. 각 단계가 **혼자서 값이 있어야** 한다

```
1. devid 고유화(EEPROM)        굽기 필요 · **다른 모든 것의 전제**
                               단독 값: 보드가 여럿이어도 서버가 구분한다
2. 서버 대장 영속               할당 없이 먼저 · 단독 값: **재기동해도 누가 있었는지 기억한다**
3. 모듈 지문 한 필드            굽기 필요 · 단독 값: "구성이 바뀌었다"를 서버가 안다
4. 관리자 화면 — **할당만**     정책 없이 · 단독 값: **굽지 않고 자리를 바꿀 수 있다** ← 사용자 목표의 절반
5. 정책 — **자리 판정 하나만**  단독 값: OR 말고 다른 판정을 코딩 없이 고른다
6. index.html 이 할당을 읽는다  단독 값: 화면이 대장을 따라간다
```

### ⚠ 이름 일치 결속을 언제 버리나 — **버리지 말고 강등한다**

```
4단계 이후 : 할당이 **있으면** 할당으로, **없으면** 지금처럼 이름 일치로
→ 옛 장치가 계속 동작한다. 마이그레이션이 필요 없다
→ 🔑 그리고 "할당이 없는 노드"가 관리자 화면에 자연히 뜬다 — 그게 [미할당] 상태다
```

---

## 7. ⚠ 이 설계가 답하지 *않는* 것 — 미리 적어 둔다

```
· **권한** — 누가 할당할 수 있나. 지금 관리자 페이지에 인증이 없다
· **충돌** — 두 관리자가 같은 자리에 다른 모듈을 동시에 할당하면
· **모듈 제거** — 장치에서 모듈이 빠졌을 때 옛 할당·옛 예약을 어떻게 하나
· **정책 변경 시점** — 운영 중에 정책을 바꾸면 진행 중인 예약은 어떻게 되나
```
🔑 **넷 다 "나중에"로 둬도 되지만, *적어 두지 않으면* 구현하다 만나서 즉흥으로 정하게 된다.**
