# REQ-0159 · 재개 3 — queued 수신 처리 + expires_ms 연동(지금 착수) · 시험 인스턴스는 3번째다

**요청자** `root` → **담당** `web-engineer`

## 요청 내용

세션이 리셋됐다. 팀 전원 새 세션이고 문맥은 파일에서 복원했다.
**원본은 `docs/DESIGN-slot-carrier-2026-08-17.md`(사용자 결정) 이고, 그 문서 §web 상세 를 이어서 한다.**

## 지금 착수 — `queued` 수신 처리 + `expires_ms` 연동

문서가 이 항목을 **🔴 미구현 · `rxmax` 를 안 기다린다** 로 적어 뒀다. 그대로 간다.

- 계약은 REQ-0155 에서 이미 합의됐다(네가 닫은 요청이다). **계약을 다시 열지 말고 구현해라.**
- 큐가 흡수한 사용자 입력이 **조용히 사라지지 않고 `queued` 로 보이게** 하는 것이 목적이다.
  아이들 1.0초 < 슬롯 1.2초 불일치는 **알고 둔 것**이고, 그 간극을 이 표시가 덮는다(문서 §276).
  **아이들 값을 1.2초로 맞추려 하지 마라** — 재작업 가치 없다고 문서가 판정했다.

## 실측은 순서를 기다려라 — 시험 인스턴스는 배타적 자원이다

`1초 아이들 실제 WS 미확인` · `거짓 문구 브라우저 재측정 미완` · `경우 C` 셋은
전부 시험 인스턴스에 걸려 있다. **네 원장이 검증 없는 변경을 금하는 것은 맞고, 순서는 루트가 정한다:**

```
① socket 이 pid 46224(9900+5500 동시 LISTEN)의 정체를 밝힌다
② arduino 의 rxmax 측정용 인스턴스를 확정한다
③ 그 다음 네 시험 인스턴스
```

**임의로 띄우지 마라.** 지난 창4 에서 `server_test`·`fake_arduino` 가 9시간 19분 방치돼
CPU 경합이 판정의 교락 후보로 남았다(monitor/HANDOFF-win4.md). **띄운 것은 내려라**까지가 한 벌이다.

③ 차례가 오면 루트가 신호한다. 그때까지는 코드와 문서 작업만.

## 참고 — 지금 확정된 것

- `AT+CIPSEND` 조용한 잘림 없음(300B·상행·그 보드/AT 빌드 한정, 커밋 `1299286`).
- 계열은 `조별과제샘플/client.ino` 로 확정.

## 왜 필요한가

queued 는 rxmax 와 무관한데 미구현으로 남아 있고, 큐가 흡수한 입력이 화면에서 조용히 사라지는 것을 막는 유일한 장치다. 시험 인스턴스는 배타적 자원이라 순서가 필요하다

### 1. 실제로 고친 것 — 거절 코드 둘 (계약의 유일한 빈틈)

`ERROR_TEXT`(index.html 592행)에 `queue_full` · `already_pending` 이 **없었다.**
없으면 `msg.message` → 없으면 `'오류가 발생했습니다'` 로 떨어진다(2073-2075행).

**왜 문구 누락으로 끝나지 않나**: 둘 다 **사용자 잘못이 아닌데** 그 일반 문구는 고장이나
자기 실수로 읽힌다 → **다시 누른다** → 이 REQ 가 닫으려는 증폭 고리 그 자체다.

- **코드 문자열은 원본에서 확인했다** — `docs/net/DESIGN-server-slot-queue.md` §4-B 를 grep 해
  `queue_full`·`already_pending` 스펠링을 맞췄다. 내 원장(§5.15)에 옮겨 적힌 이름을 근거로
  쓰지 않았다 — 틀리면 **영원히 안 걸리는 죽은 코드**가 되고 화면은 그대로 일반 문구를 낸다.
- 문구는 **재클릭을 유도하지 않는 쪽으로** 갈랐다:
  `queue_full` = 접수 안 됨 · 시스템 사정 → "잠시 뒤 다시" (재시도가 의미 있다)
  `already_pending` = 앞선 요청이 살아 있음 → **"그 결과가 나온 뒤에"** (다시 누르면 또 거절된다)
- `already_pending` 에 "내 예약이 곧 확정된다"고 쓰지 않았다 — 서버는 **자리 단위**로 막으므로
  그 앞선 요청이 내 것인지 남의 것인지 화면은 모른다. 단정하면 남의 요청일 때 거짓말이 된다.

### 3. 검증 — 두 하니스를 **실제로 돌린 출력**

`[6]` 은 §5.3 교훈대로 **고쳐지면 저절로 초록이고 그 뒤로는 회귀 감시**가 되는 형태다.
검사에 힘이 있는지도 확인했다 — 직전 판본(`HEAD`)에는 두 코드가 **0건**이므로 변경 전이면 빨간불이다.

```
$ node web/tools/check-index.mjs

  ✅ queue_full 에 문구가 있다        ✅ already_pending 에 문구가 있다
  ✅ 두 문구가 서로 다르다             ✅ 모든 error code 가 서로 다른 문구를 쓴다 (6개)
통과 — 22 pass / 0 fail
```

```
$ node web/tools/queue-contract.mjs        (file:// · 데모 · 포트 인자 없음 · 트래픽 0)
[A] · queue_full      → "A1 · 지금 전송 대기가 가득 차 접수하지 못했습니다 — 잠시 뒤 다시 눌러 주세요"
    · already_pending → "A2 · 이 자리의 앞선 요청이 아직 처리 중입니다 — 그 결과가 나온 뒤에 다시 시도해 주세요"
    · zzz_unknown(대조군) → "A3 · 오류가 발생했습니다"
[B] · B1 → ["접수됨 · 전송 대기…","서버가 받았습니다 — 앞에 2건"]  · 타이머 id 갈림 확인
    · B2 → "서버가 받았습니다 — 다음 차례입니다"
    · B3 → "…(언제까지인지는 서버가 알려 주지 않았습니다)"  · expiresAt=null · timer=0
    · B4 자체 타임아웃(6000ms)을 넘겨 6500ms 기다린다… → **여전히 queued** (롤백 안 됨)
    · B5 → "예약 확정됨"
통과 — 25 pass / 0 fail
```

**대조군(`zzz_unknown`)이 A 의 근거다** — 표에 없는 코드가 일반 문구로 떨어지는 것을 같이 재서,
내가 넣은 두 키가 **실제로 걸린다**는 것을 증명했다.

**B4 가 이 계약의 존재 이유를 확인한 항목이다.** `expires_ms=4800` 주입 후 **자체 6초를 넘겨
6500ms** 기다렸는데 pending 이 `queued` 로 살아 있었다 → 큐에서 정상 대기 중인 요청을 화면이
되돌려 사용자가 다시 누르는 고리가 **닫혀 있다.** 지난 기록(§5.15.1)은 "주입으로 확인"이었지만
**시간을 흘려 본 것은 이번이 처음**이다 — 타이머 재설정은 시계 없이는 판독일 뿐이다.

### 4. 🔴 이 측정에서 하마터면 잃을 뻔한 것 — 하니스가 **거짓 초록**을 냈다

첫 판본이 `#messages .msg` **첫 줄**(가장 새 메시지)을 읽었다. 데모 전송 계층의 시작 메시지가
**비동기로** 내 주입 뒤에 도착해서, 첫 사례가 `"§5.3 예제 스냅샷을 적용했습니다…"` 를 읽었다.
**그런데도 `14 pass / 0 fail`** 이었고 `두 문구가 서로 다르다` 까지 통과했다 — 한쪽이 남의
메시지였기 때문이다. §5.18 과 같은 뿌리(아무것도 못 쟀는데 초록)이고 **다른 것은 예외가 아니라
순서**다. → 순서에 기대지 않고 `rollback()` 이 붙이는 `"<자리> · "` 접두로 내 것만 고르게 고쳤다.
**이것을 잡은 것은 대조군이다** — 대조군을 같이 안 쟀으면 초록만 보고 넘어갔다.
