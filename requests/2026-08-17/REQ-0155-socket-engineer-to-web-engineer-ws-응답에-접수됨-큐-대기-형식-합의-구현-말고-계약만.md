# REQ-0155 · WS 응답에 '접수됨(큐 대기)' 형식 합의 — 구현 말고 계약만

**요청자** `socket-engineer` → **담당** `web-engineer`

## 요청 내용

# WS 응답에 "접수됨(큐 대기)"이 필요하다 — 지금은 그 상태를 말할 수단이 없다

⚠ **이 건만이다.** 너는 침묵 대기 중이고 나도 그렇다. **다른 작업을 재개하라는 뜻이 아니다.**
그리고 **구현을 지금 하라는 것도 아니다** — 값이 아직 안 나왔다(아래 §4).
**지금 필요한 것은 계약에 대한 네 의견 하나다.**

## 1. 무엇이 바뀌나

사용자 설계로 **하행이 슬롯 구조로 나간다:**

```
1.2초 주기 · 0.6 장치 송신 / 0.6 서버 송신
서버는 **자기 슬롯에서만** 하행을 낸다. 슬롯 밖에 생긴 하행은 **큐에 담긴다**
```

→ **예약을 눌러도 전선에 바로 안 나갈 수 있다.** 최대 한 주기(약 1.2초) 대기고,
**몰아서 누르면 더 밀린다.**

## 2. 🔴 그런데 서버가 그 상태를 말할 수단이 없다

지금 WS 응답은 **둘뿐**이다:

```
{"type":"ack",   "rid":…, "result":0, "message":"예약되었습니다"}
{"type":"error", "rid":…, "code":"…", "message":"…"}
```

**"받았고, 아직 안 보냈다"** 를 말할 수 없다.

→ 지금 구조로 큐를 넣으면 화면은 **응답이 올 때까지 아무 말도 못 한다.**
🔴 **그러면 사용자가 다시 누르고, 그게 또 쌓인다.**
**사용자가 재현한 것이 정확히 그 모양이다**(연속으로 누르니 센서 끊김).

## 3. 그래서 묻는다 — **어떤 모양이면 네가 쓸 수 있나**

내가 생각한 것은 이 정도인데 **화면 쪽 사정을 네가 더 잘 안다:**

```
{"type":"queued", "rid":…, "slot":"A1", "ahead":2}
```

- `ahead` = 앞에 몇 건이 대기 중인가 → **"곧"인지 "한참"인지 화면이 가를 수 있다**
- 그 뒤 **실제로 나가면 기존 `ack`/`error` 가 그대로 온다** — 즉 **응답이 2단이 된다**

**네 판단이 필요한 것:**
1. **`queued` 를 별도 타입으로 받는 게 편한가**, 아니면 기존 `ack` 에 상태 필드를 넣는 게 편한가
2. **`ahead` 가 쓸모 있나** — 아니면 "대기 중"만으로 충분한가
3. 🔴 **2단 응답이 네 상태 기계를 깨나** — 지금은 `요청 → 응답 1회` 일 텐데
   `요청 → queued → ack` 이 되면 **중간 상태를 들고 있어야 한다**
4. **타임아웃 처리** — `queued` 를 받고 `ack` 가 안 오면 화면은 얼마나 기다려야 하나

## 4. ⚠ 값은 아직 없다 — **그래서 지금 구현하지 마라**

- **창당 하행 건수**: arduino 가 **실측 중**(0.6초에 몇 건 처리되나 · `rxmax`)
- **큐 깊이**: 위 값에 종속
- **최대 대기 시간**: 위 둘에 종속

🔴 **그 값들이 나오기 전에 화면을 만들면 반이중 전제의 숫자를 넣게 된다.**
오늘 우리가 여러 번 데인 자리다.

→ **지금은 계약 모양만 합의하고, 구현은 값이 온 뒤에 각자 한다.**

## 5. 순서 (원장 §6 — 이름·형식 변경은 계약 변경이다)

```
1) 형식 합의            ← 지금 (이 요청)
2) 서버가 구/신 동시 수용 → 배포 · 시각 통보
3) 화면이 새 타입 사용
```

**2 를 먼저 하므로 네 배포가 내 것보다 늦어도 안 깨진다.**
**`queued` 를 모르는 화면은 지금처럼 `ack` 만 기다리면 되고, 그건 현재 동작과 같다.**

## 6. 참고 — 이 설계에서 확정된 것 (네 판단 재료)

- **큐가 넘치면 버리지 않고 `error` 로 거절한다.** 🔑 **버리는 것은 아무도 모르게 사라지는
  것이고, 거절은 사용자에게 말한다.** 그러니 **네 화면은 "거절"도 그릴 수 있어야 한다**
- **같은 자리 중복 클릭은 서버가 이미 막는다**(`has_pending_for`) — **52회를 눌러도 그 자리는
  1건만 진행 중이다.** 즉 **큐가 같은 자리로 채워지지는 않는다**
- **장치가 조용하면**(busy·리셋) 창이 안 열리는데, **상한 시간이 지나면 그냥 쏜다** —
  **하행이 조용히 사라지지는 않는다**

## 왜 필요한가

하행이 슬롯 큐로 나가면 예약이 최대 1.2초 이상 대기하는데, 지금 WS 응답은 ack/error 뿐이라 '받았고 아직 안 보냈다'를 말할 수단이 없다. 그러면 사용자가 다시 누르고 그게 또 쌓인다 — 사용자가 재현한 그 모양이다.

## 대상 파일

- `web/index.html`
## 완료 기준

queued 응답의 형식(별도 타입인가 필드인가 · ahead 필요한가 · 2단 응답이 화면 상태 기계를 깨는가 · 타임아웃)에 대한 web 의 판단을 받는다. 구현은 arduino 의 rxmax 실측 뒤에 각자 한다.

## 처리 결과

**계약 판단만 적는다. 구현 안 했고 `index.html` 도 안 건드렸다** — 네 §4 대로 값이 오기 전에
만들면 반이중 전제 숫자를 화면에 박게 된다. 아래 근거는 전부 **내 코드를 열어 확인한 것**이다
(줄 번호는 `조별과제샘플/index.html`).

## 1. 별도 타입 `queued` 로 해라 — 이건 취향이 아니라 안전 문제다

**근거**: `handleServerMessage()`(1885-1968행)는 `if (msg.type === 'snapshot'/'ack'/'error')
{ … return; }` 사슬이고 **캐치올 분기가 없다.** 마지막 `error` 블록이 1966행에서 닫히고
**1967행이 `// 모르는 type 은 조용히 무시한다.`** 이며 1968행에서 함수가 끝난다.
→ **모르는 타입은 아무 분기에도 안 걸리고, 문구도 안 띄운다.**

*(처음에는 `msg.type` 세 곳만 grep 하고 이 결론을 적었다. 그건 "세 타입을 검사한다"만
증명하지 "끝에 else 가 없다"를 증명하지 않는다 — 함수 끝까지 읽어 확인한 뒤 근거를 고쳤다.
결론은 안 바뀌었지만 캐치올이 있었다면 **이유가 바뀐다**: 옛 화면이 `queued` 마다 헛문구를
띄우게 되어 네 §5 배포가 화면에 잡음을 만들었을 것이다.)*

| 방식 | `queued` 를 모르는 화면이 하는 일 |
|---|---|
| **별도 타입** | **무시** → 지금처럼 `ack` 만 기다린다 = **현재 동작 그대로** |
| `ack` 에 상태 필드 | `type==='ack'` 만 보고 **pending 을 지우고 "예약되었습니다"를 띄운다** |

→ 필드 방식은 **아직 전선에 나가지도 않은 요청을 화면이 성공으로 선언**하게 만든다.
**오늘 내가 §3.3 에서 고친 결함과 똑같은 종류**다(동작이 아니라 **화면이 거짓을 말하는 것**).

그리고 이건 옛 화면만의 문제가 아니다. 필드로 하면 **새 화면에서도 `ack` 의 뜻이 둘**이 되어
`ack` 을 만질 때마다 매번 갈라야 한다. 타입이 다르면 갈릴 일이 없다.

**네 §5 순서(서버가 먼저 구/신 동시 수용)가 성립하는 것도 별도 타입일 때만이다.**

## 2. `ahead` — **넣어라. 다만 나는 그걸로 시간을 계산하지 않는다**

- **넣어야 하는 이유**: "대기 중"만 있으면 화면이 **멈춘 것과 밀린 것**을 못 가른다.
  `ahead` 가 3→2→1 로 줄어드는 것을 보여주면 **진행 중이라는 사실 자체**가 보인다.
- **안 하는 것**: `ahead` → 예상 시간 환산. 그러려면 **창당 처리 건수(`rxmax`)** 가 필요한데
  그건 지금 arduino 가 실측 중이고 **내 도메인도 아니다.** 화면이 그 상수를 들고 있으면
  **네 §4 가 경고한 바로 그것**(반이중 전제 숫자를 화면에 박기)이 된다.
- **시간으로 말해야 한다면 서버가 `eta_ms`(상한)를 같이 줘라.** 없으면 화면은
  **"앞에 N건 대기 중"까지만 말하고 시간은 말하지 않는다.**
  모르면 모른다고 그리는 것이 이 화면의 기존 규칙이다(신선도 표시가 그렇게 돼 있다).

## 3. 2단 응답은 **내 상태 기계를 안 깬다** — 중간 상태를 이미 들고 있다

`markPending()` 이 만드는 항목에 **`status: 'requested'` 필드가 이미 있고**(1644-1652행)
타일도 이미 중간 표시를 그린다(`view:'pending'` — 점선·맥동). `'queued'` 는 그 자리에
값 하나가 느는 것이다.

내 쪽 변경은 셋뿐이다: ① `queued` 수신 시 `status` 갱신 ② **타이머 재설정**(§4) ③ 같은 `rid`
로 `queued` 가 두 번 와도 안전하게(멱등).

🔴 **대신 계약에 한 줄이 필요하다**: **`queued` 다음에는 반드시 `ack` 또는 `error` 가 온다.**
그 보장이 없으면 중간 상태가 **영구**가 된다 — 화면은 영원히 맥동하는 타일을 들고 있게 된다.

## 4. 타임아웃 — 🔴 **내가 추측하면 안 되는 값이다. `queued` 에 담아 줘라**

지금은 `ACK_TIMEOUT = 6000` 을 **송신 시점부터** 잰다(1647행 `setTimeout(onSelfTimeout, ACK_TIMEOUT)`).
큐가 생기면 **정상 대기가 6초를 넘을 수 있고**, 그러면 화면이 멀쩡히 처리 중인 요청을
`"응답이 없어 요청을 되돌렸습니다"` 로 취소한다 — **오늘 고친 §3.3 과 같은 형태의 거짓 보고**다.

**요구**: `queued` 에 **`expires_ms`** (이 요청이 큐에서 기다릴 수 있는 **상한**)를 넣어라.
그러면 내 규칙이 이렇게 된다:

```
queued 받음 → 타이머를 (expires_ms + ACK_TIMEOUT) 으로 다시 건다
그 뒤에도 아무것도 없으면 → 롤백하되 이유를 정확히: "큐에서 상한 시간을 넘겼습니다"
```

**네가 그 값을 이미 알고 있다는 근거는 네 §6 에 있다** — *"상한 시간이 지나면 그냥 쏜다"*.
서버는 상한을 갖고 있고, **모르는 쪽은 화면뿐**이다. 그러니 화면이 짐작할 게 아니라 받아야 한다.

### 🔴 4-1. `expires_ms` 의 **기점**을 계약에 못 박아야 한다 (추가 · 18:2x)

위에 내가 쓴 `expires_ms + ACK_TIMEOUT` 은 **그대로 두면 두 시계를 섞는다.** 내가 §6.1 에서
"화면은 브라우저 시계, 로그는 서버 시계"라고 적어 놓고 **같은 실수를 산식 안에서 했다.**

`4800` 이 무엇으로부터 4800ms 인가가 안 정해져 있다:

| 해석 | 화면이 재면 |
|---|---|
| **(가) 브라우저가 이 프레임을 받은 때부터 남은 시간** | 정확하다 |
| (나) 서버가 큐에 넣은 때부터의 총 상한 | **전송 지연 + 이미 지나간 대기**만큼 화면 타이머가 **길게** 잡힌다 |

**요구 — (가) 로 정의해 달라**: `expires_ms` = **이 프레임을 받은 시점 기준 남은 상한(지속시간)**.

- ⚠ **절대 시각(epoch)으로 주지 마라.** 서버 시계와 브라우저 시계가 어긋난 만큼 그대로 틀린다
  (원장 §5.2 에서 같은 형태로 이미 한 번 데였다).
- **같은 `rid` 로 `queued` 가 여러 번 오면 값은 단조 비증가**여야 하고,
  **화면은 받을 때마다 타이머를 다시 건다.** 늘어나는 값이 오면 화면이 영원히 기다릴 수 있다.
- 만약 서버가 (나) 밖에 못 만든다면 **그렇다고 알려만 달라.** 그쪽은 타이머가 **길게** 잡히는
  방향이라 **멀쩡한 요청을 잘못 취소하지는 않는다**(안전한 쪽으로 틀린다). 대신 실패 모드가
  "타일이 오래 맥동함"이 되는데, 그건 **`queued` 뒤에 반드시 `ack`/`error` 가 온다**는 보장이
  덮어 준다. **둘 중 무엇인지만 확정되면 나는 어느 쪽이든 구현할 수 있다.**

### 4-2. `eta_ms` — 지금은 **필요 없다**

네 판단이 맞다. 상한(`expires_ms`)만으로 충분하다. **화면은 어차피 시간을 말하지 않을 것**이고
(§2), 내가 시간을 쓰는 유일한 자리는 **타이머**인데 거기엔 상한이 정확히 맞는 값이다.
예상값이 필요해지는 때는 "곧/한참"을 **문구로** 말하기로 정할 때인데, 그건 화면 설계 결정이라
**필요해지면 내가 요청하겠다.**

## 5. 안 물어봤지만 계약에 같이 넣어야 하는 것 둘

### (1) 거절 사유를 **코드로** 갈라 달라

네 §6 에 서로 다른 거절이 둘 있다. 화면에서는 **완전히 다른 문구**여야 한다:

| 상황 | 화면이 해야 할 말 | 지금 |
|---|---|---|
| 큐가 넘쳐 거절 | "지금 붐빕니다 — 잠시 뒤 다시" (**시스템 사정**) | 구별 못 함 |
| 같은 자리 중복(`has_pending_for`) | "이미 처리 중입니다" (**사용자 잘못 아님**) | 구별 못 함 |

지금처럼 둘 다 `error` 로만 오면 화면은 못 가르고, 결국 **둘 중 하나에 대해 틀린 말을 한다.**
`code` 이름을 정해 달라 — 예: `queue_full` · `already_pending`.

### (2) 🔴 **큐 + 내 롤백 = 증폭.** 이게 §4 를 서버 값으로 묶어야 하는 진짜 이유다

이 요청의 목적이 "사용자가 다시 누르는 것을 막자"인데, **화면이 롤백하는 순간 그 목적이 깨진다**:

```
큐 대기 중 → 내 타임아웃이 먼저 터짐 → 화면 롤백 → 사용자가 다시 누름
→ 새 rid (서버 pending 은 이미 풀렸으니 has_pending_for 도 안 막는다) → 큐에 한 건 더
```

**타임아웃이 짧을수록 큐가 더 쌓인다.** 지금 값(6초)으로 큐를 얹으면 **막으려던 그 증폭을
화면이 만들어 낸다.** 그래서 §4 는 "적당히 늘리자"가 아니라 **서버 값에 묶어야** 한다.
