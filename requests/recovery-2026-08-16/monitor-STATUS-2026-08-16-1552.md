# 재기동 직후 시스템 상태 관측 — 2026-08-16 15:52 KST

작성 `monitor-engineer` · 재기동 후 첫 관측 · 근거는 전부 이 문서 하단 §5 에 명령과 함께 적었다.

> 이 문서의 목적은 **인수인계 문서(`docs/monitor-engineer/handoff-2026-08-16.md`)의
> 시스템 상태 표를 정정하는 것**이다. 그 표에 따라 행동하면 실제로 손해가 난다.
> `docs/` 는 루트 소유라 내가 못 고친다 → 정정본을 여기에 둔다.

## 1. 🔴 가장 급한 것 — **서버는 죽지 않았다. 21시간짜리 소크가 지금도 돌고 있다**

인수인계 표는 `서버 pid 36998 · 🔴 죽음` 이라고 적었다. **틀렸다.**

```
pid 36998  /tmp/srv_parking   etime 21:06:45 → 지금도 실행 중
/tmp/parking-soak.log         1분마다 ⏱ 하트비트 계속 기록 중 (마지막 15:52:34)
```

⚠ **인수인계대로 "서버를 되살리는" 조치를 하면 21시간 연속 소크가 그 자리에서 끊긴다.**
재기동 순서를 잡기 전에 이 항목을 먼저 반영해야 한다.

**단, "살아 있다 ≠ 정상이다"** — 아래 2번이 그 이유다. 나는 프로세스 생존과 로그 증가만
관측했다. **새 연결을 정상 처리하는지는 확인하지 않았다.** 이 서버는 블로킹 `send()` 에서
행에 걸린 전력이 있다(커밋 6e3f63c).

## 2. 🔴 지금 이 순간 장애가 진행 중이다 — 22분째 미복구

소크 로그 마지막 구간(15:47~15:52)에서 **프레임 카운터가 62551 에 멈춰 있다.** 5분 내내 안 늘었다.

```
15:52:34  ⏱ 소크 21:09:55 · 세션 66회(현재 끊김) · 프레임 62551
          · 🔴미복구 1회(진행 1327.4초)   ← 계속 증가 중
```

그리고 **장치가 붙었다가 끊기는 것이 반복**되고 있다:

```
15:47:19  +? 연결 수락 — device_id 대기 중(7초 안에 유효 프레임 없으면 끊는다)
15:47:26  ✂ id 미상 소켓 마감 — 7000ms 안에 유효 프레임이 없었다
15:48:03  +? 연결 수락 …
15:48:10  ✂ id 미상 소켓 마감 …
15:48:46  +? / 15:48:53 ✂
15:52:25  +? / 15:52:33 ✂
```

**증상**: TCP 연결은 성립하는데 **`device_id` 프레임이 7초 안에 안 온다.** 서버가 규정대로 끊는다.
연결 자체가 안 되는 것이 아니라 **붙은 뒤 말을 못 하는** 상태다.

**미복구 구간 시작 시각** = 15:52:34 − 1327.4초 ≈ **15:30:27**.

⚠ **인과는 단정하지 않는다.** 파일 삭제 사고(≈15:26~15:30)와 시각이 겹치지만,
파일 삭제가 실행 중인 장치·서버를 끊을 경로를 나는 아직 못 찾았다. **시각 근접은 상관이지 인과가 아니다.**
표본도 이 구간 하나뿐이다(n=1).

## 3. 시리얼 캡처 — **아직 살아서 쓰고 있다. 그런데 아무도 못 읽는다**

인수인계는 이 로그를 "재현 불가·소실"로 적었다. **절반만 맞다.**

```
pid 91345  python3 monitor/serial_tap.py --port /dev/cu.usbmodem21201
  fd 3w → monitor/serial-esplink.log       46587 B → 47575 B  (증가 중)
  fd 4w → monitor/serial-esplink.log.raw   34609 B → 35417 B  (증가 중)
```

`monitor/` 디렉터리는 삭제됐다. 즉 **파일은 unlink 됐지만 fd 가 열려 있어 내용이 디스크에 남아 있다.**
프로세스가 살아 있는 동안에만 그렇다. **`kill 91345` 하는 순간 약 83 KB 가 영구 소실된다.**

지금 진행 중인 2번 장애의 장치측 원문이 바로 이 파일에 들어가고 있다. **접근 경로만 없다.**

### 🔴 루트가 정해야 할 것 — 양쪽 다 대가가 있다

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| **91345 유지** | 캡처 데이터 보존 · 계속 축적 | `/dev/cu.usbmodem21201` 을 계속 점유 → **캡처 재시작 불가** |
| **91345 종료** | 포트 해방 → 캡처 재개 가능 | 83 KB 영구 소실 + **재시작 시 DTR 리셋이 MCU 를 리셋** → 21시간 소크가 끊긴다 |

**내 권고: 둘 다 건드리지 마라.** 순서는 루트가 정한다.
unlink 된 fd 에서 내용을 뽑는 시도(lldb attach 등)는 **지시받지 않았으므로 하지 않았다.**

## 4. `monitor/` 는 `.gitignore` 대상이 아니다 — `git add` 로 보호된다

```
git check-ignore -v monitor/   → exit 1 (무시 규칙에 안 걸림)
```

인수인계가 남긴 교훈(`docs/` 가 안전한 이유는 경로가 아니라 **추적되고 있음**)이 여기도 적용된다.
이 문서는 `git add` 로 인덱스에 올려 뒀다. 사고 원인으로 지목된 `.gitignore` 44행
`조별과제샘플/server_*` 문제와는 별개다.

## 5. 근거 — 실행한 명령 그대로

```bash
ps -eo pid,etime,command | grep -a -E "parking|serial_tap"   # 36998 / 91345 생존 확인
wc -c < /tmp/parking-soak.log                                # 4944125 → 4944580 (증가)
tail -c 4000 /tmp/parking-soak.log | grep -a . | tail -25    # 15:47~15:52 구간
lsof -p 91345 | grep -a serial-esplink                       # fd 3w/4w 바이트수 2회 비교
git check-ignore -v monitor/                                 # exit 1
```

⚠ **표본과 한계를 분명히 한다:**
- 소크 로그를 **전체 재집계하지 않았다.** 위 숫자는 서버가 스스로 찍은 누적 카운터를
  마지막 4 KB 에서 읽은 것이다. 집계 도구는 아직 없다(9종 전부 소실, §6).
- 20초 간격 두 번 읽기에서 `parking-soak.log` 가 안 늘어난 구간이 있었으나,
  이 로그는 **이벤트 기반**이라 **무증가가 정지 신호가 아니다. 그것으로는 판별 못 한다.**
  생존 판정 근거는 그것이 아니라 1분 주기 ⏱ 하트비트다.
- 2번의 미복구 장애는 **표본 1건**이다. "펌웨어 회귀"라고 부를 근거가 아직 없다.
