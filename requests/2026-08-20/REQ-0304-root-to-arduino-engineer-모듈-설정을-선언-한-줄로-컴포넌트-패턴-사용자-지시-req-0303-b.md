# REQ-0304 · 🔴 모듈 설정을 선언 한 줄로 — 컴포넌트 패턴 (사용자 지시 · REQ-0303 B단계를 대체한다)

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

> ### 🔴 **이 REQ 가 `REQ-0303` 의 B단계를 *대체한다*.**
> REQ-0303 의 B단계 절들(런타임 등록 → 표에 핸들러 → kind 감추기)은 **이력이다. 정본은 이 파일이다.**
> A단계(setup/loop 경계)와 B 1/2 커밋(`setup()` 두 줄 · 표에 핸들러)은 **그대로 살린다.**

사용자 지시:
> *"**팩토리 패턴이라든가 고정적으로 컴포넌트 패턴등의 확장으로 설정방법을 쉽게** 해달라.
> **하나의 라인에서 설정이 완성되는것이 중요하다.**
> 지금처럼 **배열 따로 그 배열에서 설정한 값을 또 설정하고 그걸 또 등록하는 방식**은
> 기여자들에게는 **이해난이도가 너무 높다.**"*

그리고 그 전제:
> *"기여자들의 수준이 **아두이노 기본 설정과 센서연동이 가능한 수준**이다."*
> *"**Ram문제가 있다면** 코드 작성을 더 직관적이고 쉽게 만들어달라."*  ← 🔑 RAM 을 써도 된다는 허가다

## 무엇이 문제인가 — 사용자가 센 단계 그대로

```
① 배열을 만든다        static constexpr ModuleDef MODULE_TABLE[] PROGMEM = { … }
② 그 안에 값을 넣는다   SENSOR("A1", 2)
③ 핸들러를 따로 쓴다    static bool cmdLed(uint32_t arg) { … }
④ 그걸 또 등록한다      (지금은 표가 하지만 개념이 남아 있다)
```
> ### **한 모듈을 붙이는 데 개념이 넷이다. "한 줄"이 아니다.**

## 목표 — **선언 한 줄로 끝난다**

아두이노 관용이 이미 이 모양이다. 기여자가 아는 형태다:
```c
Servo myservo;                    // 선언
myservo.attach(9);                // 붙임
```
우리 목표:
```c
ParkingSensor  a1("A1", 2);       // 🔓 한 줄. 핀 2를 읽는다
ParkingSensor  b1("B1", 9);
ParkingLed     ld("LD", 13);      // 🔓 한 줄. **핸들러도 필요 없다** — LED 동작은 컴포넌트가 안다
ParkingDisplay l2("L2");          // 🔓 한 줄. 숫자를 받는다

void setup() { Serial.begin(115200); node.begin(); }
void loop()  { node.tick(); }
```
```
✅ 배열 없다 · 등록 호출 없다 · `IP`/`OG` 없다 · 핸들러 없다(기본 컴포넌트)
✅ 기여자가 배우는 것 : **컴포넌트 타입 이름 + 이름 + 핀.** 그것이 전부다
```

### 확장은 콜백으로 — **고정 컴포넌트가 못 덮는 것만**
```c
ParkingActuator dr("DR", 7, myGate);   // 🔓 내 동작을 넣는다
ParkingSensor   us("A2", 5, readUltrasonic);  // 🔓 내 읽기를 넣는다
```
🔑 **기본 컴포넌트가 먼저고 콜백은 탈출구다.** 반대로 두면 사용자 요구가 안 풀린다.

## 🔴🔴 형태 확정 — **`setup()` 에서 초기화, `loop()` 에서 사용** (사용자 지시 · 이것이 정본 형태다)

> 사용자 원문: *"**셋업에서 초기화 하여 루프에서 사용 이부분은 모두 익숙한 패턴이다.
> 이패턴을 활용할수 있는 구조도 필요하다.**"*

**위의 `ParkingSensor a1("A1", 2);`(전역 선언에 핀까지)를 이것으로 바꾼다:**

```c
ParkingSensor a1, b1;          // 🔓 선언 — 생성자는 아무것도 안 한다
ParkingLed    ld;
ParkingNumber l2;

void setup() {
  Serial.begin(115200);
  node.begin();
  a1.attach("A1", 2);          // 🔓 **여기서 초기화.** 이름 + 핀 한 줄
  b1.attach("B1", 9);
  ld.attach("LD", 13);
  l2.attach("L2");             // 핀이 없는 모듈
}

void loop() {
  node.tick();
  // 🔓 필요하면 여기서 직접 쓴다 — `if (a1.read()) …` · `ld.on()`
}
```

### 🔑 이 형태가 `Servo` 와 **글자 그대로 같다** — 기여자가 이미 아는 것이다
```c
Servo myservo;                  void setup(){ myservo.attach(9); }   void loop(){ myservo.write(90); }
ParkingSensor a1;               void setup(){ a1.attach("A1", 2); }  void loop(){ a1.read(); }
```

### 🔴 그리고 이것이 **설계 제약 ①을 없앤다**
```
전역 생성자에서 `pinMode` 를 못 부르는 문제 → 🔑 **`attach()` 가 setup 에서 불리므로 사라진다**
self-registration 링크드 리스트도 **필요 없다** — `attach()` 가 등록한다
→ 아래 제약 ① 은 이제 성립하지 않는다. **생성자 순서 조사도 불필요하다**
🔴 `occMask` 비트 = **`attach()` 호출 순서**가 된다. 기여자가 적은 순서 그대로다 — 값으로 확인해라
```

### ⚠ 앞 요구("한 줄에서 완성")와 어긋나지 않는다
선언과 `attach` 로 두 줄이지만 **각 줄이 완결**이다. 배열·핸들러·별도 등록이 없다.
🔑 **사용자가 `Servo` 를 두 줄이라고 불평하지 않는 이유가 그것이다.**

### `loop()` 에서 쓰는 API — 판단해서 값으로 답해라
```
· `a1.read()` · `ld.on()/off()` · `l2.show(1234567)` 를 공개할지
🔴 판별자 : **서버 명령과 로컬 조작이 충돌하나.** 충돌하면 그 자리에서 멈추고 알려라
  (에코 규약이 서버 명령을 전제한다 — 로컬 조작이 에코를 어긋나게 만들 수 있다)
⚠ 충돌하면 **읽기(`read`)만 공개하고 쓰기는 안 공개**하는 절충이 있다. 값으로 판단해라
```

## 🔴🔴🔴 **최종 형태 — 서버 `lot.cpp` 와 같은 체이닝이다** (사용자가 코드로 지정했다)

사용자가 `lot.cpp` 원문을 그대로 붙이고 **"이런 구조가 적합하다"** 고 했다:
```cpp
lot.spot("A1").at(0,0).parking().label("1번 자리").module("P1","A1").module("P1","B1");
lot.label("P1","LD","안내등");
lot.control("P1","LD").toggle();
```
🔑 **말로 된 목적이 아니라 코드 모양을 줬다.** 그러면 그것이 정본이다.

### 장치도 같은 모양으로

```c
void setup() {
  Serial.begin(115200);
  node.begin();

  node.sensor  ("A1").pin(2);                 // 🔓 한 표현식에서 완성
  node.sensor  ("B1").pin(9);
  node.actuator("LD").pin(13).on(cmdLed);     // 🔓 이름 · 핀 · 동작
  node.actuator("L2").on(cmdL2);              // 🔓 핀 없는 모듈 — .pin() 을 안 쓴다
}
void loop() { node.tick(); }
```
```
✅ 배열 없다 · 등록 호출 없다 · `IP`/`OG` 없다 · **전역 객체 선언도 없다**
✅ 안 쓰는 항은 **안 적는다** — 서버의 `parking()`·`label()` 이 그러하다
🔑 그리고 **기여자가 서버·장치 양쪽에서 같은 패턴을 배운다.** 이게 가장 큰 이득이다
```

### ⚠ 앞 지시(`attach()` · Servo 패턴)와의 관계 — **이것이 이긴다**

```
Servo 패턴  : ParkingSensor a1;  a1.attach("A1", 2);   ← 🔴 **전역 객체 이름을 지어야 한다**
체이닝      : node.sensor("A1").pin(2);                ← 이름이 하나뿐이다
```
사용자의 *"셋업에서 초기화"* 요구는 **체이닝도 만족한다** — `setup()` 안에서 부른다.
🔑 **우리 프로젝트 안의 일관성(서버와 같은 모양)이 외부 관용(Servo)보다 강한 근거다.**
⚠ `attach` 안은 이제 **이력이다.** 정본은 체이닝이다.

### `loop()` 에서 쓰려면 — 이름으로 찾거나 참조를 잡는다
```c
if (node.sensor("A1").read()) { … }     // 이름으로 (문자열 비교 비용 있다)
auto& a1 = node.sensor("A1").pin(2);    // setup 에서 잡아 둔다 (비용 0)
```
**둘 중 무엇을 공개할지 값으로 판단해라.** 🔴 판별자는 그대로 — **서버 명령과 로컬 조작이 충돌하나.**

## 🔴 설계 제약 — 값으로 답해라. 추측하지 마라

### ① 전역 생성자에서 `pinMode` 를 못 부른다 — 지금 코드가 그 경고를 달고 있다
`client.ino` 주석: *"생성자가 아니라 여기다: **전역 생성자는 `main()` 전에 돌아 `pinMode` 를 부를 수 없다**"*
```
✅ 해법(표준 self-registration) : 생성자는 **연결만** 한다(정적 링크드 리스트에 자기를 넣는다)
                                 `begin()` 이 그 목록을 순회하며 `pinMode` 를 잡는다
🔴 실측해라 : 전역 객체의 생성자 순서가 이 툴체인에서 보장되나 · 링크 순서에 딸리나
```

### ② 🔴 RAM 이 이 설계의 유일한 진짜 제약이다
```
지금 : PROGMEM 표 → RAM 0
후   : 객체마다 RAM (`name[3]` + pin + next 포인터 + vtable? ≈ 6~10B/모듈)
```
```
🔑 1단계는 **이것을 재는 것이다.** 모듈 4개 · 8개 · 16개로 각각 재라
⚠ 그리고 `ramLow`(D6)를 같이 얻어라 — 정적 여유(837B)는 **예산이 아니다.** 네가 그것을 밝혔다
🔴 문턱은 네가 사전 등록하고 나에게 알려라. 재기 **전**에
```
⚠ **`virtual` 을 쓰면 vtable 이 붙는다.** 콜백 포인터로 되면 그쪽이 싸다 — **재서 정해라.**

### ③ 고정 컴포넌트를 몇 개 만드나
```
🔑 판별자 : **지금 샘플과 실기에 실제로 있는 것만.** 없는 하드웨어를 흉내 내지 마라
지금 있는 것 : 디지털 센서 · LED(토글) · 숫자 표시기 · 차단봉(옵션)
⚠ 넷을 넘기지 마라. 늘리면 사용자가 거부한 "다섯 외우기" 로 돌아간다
🔴 그리고 이름에 `KIND_` 를 쓰지 마라 — 오전에 없앤 그것과 겹친다
```

## 판별자

```
❌ hex 0 — 구조 변경이므로 반드시 바뀐다
✅ 전선 바이트 불변 : 등록 `D,*,7,4,` · `D,A1,IP` · `D,LD,OG` · S 프레임 · 54B
                    🔑 **`kind` 문자열은 컴포넌트가 채운다. 계약은 안 바꾼다**
✅ stage1_test 통과 유지 (시험이 표 내부를 만지면 **계약으로 다시 써라** — 그게 강해지는 신호다)
✅ 부팅 표지 불변 · flash·RAM 증분을 값으로
🔴 선후 교체 목록 — `begin()` 이 순회를 추가하므로 초기화 순서가 는다. **따로 적어라**
```

## ⚠ 지키라

```
· 전선·서버·화면 계약 **불변**. 바뀌어야 한다고 판단되면 **착수 전에 알려라**
· `occMask` 비트 위치 = 등록 순서. 🔴 **전역 객체 순서가 그것을 정하게 되면 위험하다** — 값으로 확인해라
· 굽기 필요. 굽기 직전 한 줄을 monitor 와 루트에게
· `GUIDE.md` 를 같이 고쳐라 — 기여자가 배우는 것이 통째로 바뀐다
🔴 · **1단계(RAM 실측 + 설계안)를 값으로 내고 멈춰라.** 내 확인을 받고 2단계로 가라
     세 번 형태를 바꿨다. 이번엔 재고 나서 만든다
```

## 1단계 결과 — **재고 나서 멈춘다** (arduino-engineer · 2026-08-20 17:0x)

### ① RAM 실측 — 체이닝(빌더)

빌더는 **임시 객체라 정적 RAM 에 안 든다.** 드는 것은 **표 하나**다.
```
Mod{name[2], pin, flags, cmd, sense}  : 4모듈 34B · 8모듈 90B · 16모듈 178B → **모듈당 11B**
🔑 `cmd`/`sense` 를 **union** 으로 (모듈은 둘 중 하나만 쓴다)
                                      : 4모듈 **26B** · 8모듈 74B · 16모듈 **146B** → **모듈당 9B**
```
⚠ **기울기는 8→16 구간으로 읽어라** — 4모듈 값에는 `#if` 로 빠진 코드가 섞여 있다.
🔑 **지금 판은 PROGMEM 표라 RAM 0 이다. 그래서 위 값이 그대로 증분이다.**

**전역 객체(`Servo` 안)와의 비교는 성립하지 않는다** — 그쪽 프로브는 `cmd`/`sense` 를 객체가 아니라
별도 표에 뒀다(객체당 6B). **필드 구성이 다르면 같은 축이 아니다.** 통합해서 재야 비교가 된다.

### 🔴 `virtual` 축이 **사라졌다**
```
전역 객체 안에서는 : virtual 이 클래스당 vtable **8B(.data)** 를 더했다(4모듈 25B → 41B)
🔴 체이닝에서는    : 빌더가 인덱스 하나만 갖고 핸들러는 **함수 포인터**다 → **virtual 을 쓸 자리가 없다**
```
**재라고 한 축인데 형태가 그 축을 없앴다.** 값으로 비교할 것이 남지 않았다.

### ② 🔴 `loop()` 공개 API — **쓰기는 못 연다. 에코 규약이 깨진다**
```
Modules.h:204  dispatch() 안에서만  echo_ |= bit    ← 서버 명령만이 에코를 세운다
Modules.h:390  occOut |= router.echoMask()          ← 🔴 에코가 `occ` 비트열에 OR 로 실린다
```
```
❌ 쓰기(`ld.on()`) : 핀은 바뀌고 `echo_` 는 안 바뀐다 → 서버가 보는 `occ` 가 실제와 갈리고
   RESUME §2 의 교차 불변식 `(occ&0x10)!=0 == (occ&0x08)!=0` 이 깨진다
   🔴 반대로 `echo_` 를 같이 세우면 **서버가 안 보낸 명령의 에코**가 나가 "내 명령이 먹었다"로 오독된다
   → **어느 쪽으로 해도 계약이 깨진다. 안 연다**
✅ 읽기 : 안전하다(상태를 안 바꾼다). **다만 지금 요구가 없다** — `tick()` 이 이미 훑어 보낸다
   🔑 되살릴 조건 : *"기여자가 로컬 판단(자기 자리 상태로 자기 액추에이터 제어)을 요구할 때."*
     그때 `Ref` 를 값으로 보관하는 형태를 같이 정한다(매 호출 문자열 비교를 피하려면 필요하다)
```

### ③ 제약 셋 중 둘이 사라졌다 — 그리고 **하나가 새로 생겼다**
```
✅ 전역 생성자 `pinMode` 문제 : 없다 — 체이닝이 `setup()` 에서 돈다
✅ 생성자 순서 조사          : 불필요
```
