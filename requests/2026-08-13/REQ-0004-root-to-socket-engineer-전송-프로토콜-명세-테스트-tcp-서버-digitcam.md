# REQ-0004 · 전송 프로토콜 명세 + 테스트 TCP 서버 (DigitCam)

**요청자** `root` → **담당** `socket-engineer`

## 요청 내용

먼저 `docs/digitcam-contract.md` §6·§7 을 읽어라.

**§7 은 이미 확정이다. 네 일은 그것을 '결정'하는 게 아니라 그대로 명세화하고 검증 도구를 만드는 것이다.** 바꿔야 할 이유가 보이면 직접 바꾸지 말고 루트에게 요청을 발행하라 — android-engineer 가 이미 §7 대로 구현에 들어간다.

할 일:
1. `docs/net/digitcam-protocol.md` — §7 을 정식 명세로. 바이트 수준까지: 인코딩(UTF-8), 종단(LF), json/plain 두 포맷의 필드와 예시 프레임, 연결 수립·해제·재접속 규칙, 서버가 응답하지 않아도 되는 이유, 부분 수신(TCP 는 줄 경계를 보장하지 않는다) 처리 방법. 서버 구현자가 이 문서만 보고 만들 수 있어야 한다.
2. `net/test_server.py` — 표준 라이브러리만. 포트 인자를 받고(기본 5000), 접속·해제·수신 줄을 타임스탬프와 함께 stdout 에 찍는다. 여러 클라이언트 동시 접속 허용. 줄 조립(버퍼링)을 제대로 해서 한 패킷에 두 줄이 오거나 한 줄이 쪼개져 와도 정확히 복원해야 한다 — 이 서버가 앱을 검증하는 기준이므로 여기가 틀리면 앱이 억울하게 의심받는다.
3. `net/README.md` 에 실행법과 노트북 IP 확인법(ifconfig / ipconfig getifaddr en0)을 적어라. 폰과 노트북이 같은 Wi-Fi 여야 한다는 점도.

서버 IP·포트는 아직 미정이다 — 문서에서 특정 IP 를 가정하지 마라.

## 왜 필요한가

앱이 보내는 값을 받아볼 곳이 없으면 '전송된다'를 검증할 방법이 없다. 그리고 프로토콜이 문서로 남지 않으면 나중에 실제 서버를 만드는 쪽이 앱을 뜯어봐야 한다.

### §7 은 그대로 명세화했다 (바꾸지 않음)

확정 절이므로 **결정하지 않고 기록만** 했다. 바꾸고 싶었지만 바꾸지 않은 것 셋:

- ACK/응답 없음 → 그대로. 대신 **왜 필요 없는지**를 명세 §2.4 에 5개 근거로 남겼다.
- 재전송 큐 없음 → 그대로. "값 손실은 버그가 아니라 설계된 동작"이라고 못 박았다.
- LF 구분자(길이 프리픽스 아님) → 그대로. 근거만 §3.2 에 기록.

새로 정한 것은 **수신 측 구현 지침**뿐이고 송신 계약에는 영향이 없다.
android-engineer 는 §7 대로 구현하면 되고 이 문서 때문에 바뀔 것이 없다.

명세가 §7 에 더해 못 박은 바이트 수준 사항(계약과 충돌하지 않는 구체화):
UTF-8·BOM 없음 / 종단은 LF 한 바이트(`0x0A`), CR 안 씀 / 본문에 raw LF 금지(JSON 은 `\n` 이스케이프,
자유 텍스트는 `device` 하나) / `ts`=int64 ms epoch, `seq`=앱 실행마다 1부터, `conf`=0.0~1.0,
`value`=문자열(앞자리 0 유의) / 키 5개 항상 존재 · 순서 의존 금지 · 미지의 키 무시 /
`seq` 는 재시작 시 1 로 복귀하고 끊긴 동안 구멍이 남 → 손실 오류로 처리하지 말 것.

### 검증 — 실행해서 확인한 것

포트 5057/5058 에서 실제 왕복. 전체 출력은 명세 §10 에 그대로 붙여 뒀다.

1. **붙어 온 두 줄 + 쪼개진 한 줄 + 미종단 꼬리** (한 연결에서 동시에)

```
21:11:23.619  ← 127.0.0.1:54110  #1  {"ts":1755080000000,"value":"1234","conf":0.87,"seq":1,"device":"SM-S911N"}
21:11:23.619  ← 127.0.0.1:54110  #2  5678
21:11:24.228  ← 127.0.0.1:54110  #3  {"ts":1755080001000,"value":"9012","conf":0.91,"seq":2,"device":"SM-S911N"}
21:11:24.637  ! 127.0.0.1:54110  미종단 잔여 15 바이트(LF 없음): MISSING-LF-TAIL
21:11:24.637  - 127.0.0.1:54110  해제 — 클라이언트가 닫음 · 줄 3 · 172 바이트 · 동시접속 0
```

`#3` 은 세 번의 `sendall` 로 쪼개 보낸 한 줄이 정확히 복원된 것이다.

2. **nc 손시험 + CRLF 관용** — `printf 'nc-line-1\r\nnc-line-2\n' | nc -w 1 127.0.0.1 5057`

```
21:11:43.552  ← 127.0.0.1:54128  #1  nc-line-1
21:11:43.552  ← 127.0.0.1:54128  #2  nc-line-2
```

3. **동시 접속 3 + recv 경계에서 쪼갠 UTF-8 + half-close** — 버퍼가 섞이지 않음(각자 #1#2#3)

```
21:11:52.232  ← 127.0.0.1:54138  #3  한글-3
21:11:52.232  ← 127.0.0.1:54136  #3  한글-1
21:11:52.233  ← 127.0.0.1:54137  #3  한글-2
```

4. **줄 길이 상한** — `--max-line 64` 로 띄우고 LF 없이 200바이트

```
21:12:27.280  ! 127.0.0.1:54163  줄 하나가 64 바이트를 넘었다 — LF 종단이 없다. 끊는다.
21:12:27.280  - 127.0.0.1:54163  해제 — 줄 길이 초과 · 줄 0 · 200 바이트 · 동시접속 0
```

5. **재기동(SO_REUSEADDR)** — 서버를 죽이고 곧바로 같은 포트로 재기동 후 접속

```
21:12:12.672  ← 127.0.0.1:54153  #1  4242
```

TIME_WAIT 대기 없이 재바인드됨. 포트가 이미 점유된 경우는
`바인드 실패 0.0.0.0:5057 — [Errno 48] Address already in use` 로 exit 1(조용히 죽지 않음).

6. **로그 오염 방지** — `device` 에 ANSI 이스케이프와 CR 을 섞어 보내고, 잘린 UTF-8,
   미종단 900바이트를 보냈을 때 (재검증, 포트 5059)

```
21:19:11.416  ← 127.0.0.1:54489  #2  {"device":"A\x1b[2KEVIL\x0dOVERWRITE","value":"77"}
21:19:11.518  ← 127.0.0.1:54489  #3  ...   ⚠ UTF-8 아님
21:19:11.826  ! 127.0.0.1:54489  미종단 잔여 900 바이트(LF 없음): ZZZ...(200자에서 절단)
```

제어문자를 그대로 찍으면 CR 이 커서를 되돌려 로그를 덮어쓴다 — 그러면 "값이 안 왔다"로
오진하게 되는데, 그 오진을 막으려고 만든 서버가 그걸 만들면 안 되므로 escape 한다.
잔여 덤프는 길이(900)는 정확히 보고하되 출력은 200자에서 자른다.

### 구현에서 신경 쓴 지점

- 버퍼는 **연결마다** — 전역이면 클라이언트끼리 섞인다.
- **줄로 자른 뒤 디코딩** — recv 결과를 바로 decode 하면 경계에 걸친 한글이 깨진다(위 3번이 그 시험).
- **미종단 잔여를 조용히 버리지 않는다** — "앱이 보냈는데 안 찍혔다"의 최다 원인이고,
  그때 의심받는 건 서버가 아니라 앱이다. `!` 로 찍는다.
- `flush=True` + 출력 락 — 안 하면 리다이렉션에서 "아무것도 안 온다"로 보이고 줄이 섞인다.
- `0.0.0.0` 바인드 기본값. `--host 127.0.0.1` 이면 "폰에서 접속 불가" 경고를 출력한다.
- 제어문자·ANSI 이스케이프를 escape 해서 찍는다(위 6번). 잔여 덤프는 200자에서 자른다.

### 검증하지 않은 것 (정직하게)

- **실기기 폰 → 노트북 왕복은 하지 않았다.** 폰이 없고 `server.host` 도 미정이다.
  위 검증은 전부 루프백(127.0.0.1)이다. 계약 §11 의 완료 기준 5 는 사용자와 함께 확인해야 한다.
- 문서의 IP 확인 명령(`ipconfig getifaddr en0` 등)은 **실행하지 않았다.**
  `which` 로 `/usr/sbin/ipconfig`, `/sbin/ifconfig` 존재만 확인했다. `socat` 은 이 노트북에 없다(`nc` 로 대체).
- 명세에 특정 IP 를 넣지 않았다. `server.properties` 예시의 `192.168.0.x` 는 자리표시자다.

### 루트가 판단할 것 (계약 변경이 필요할 수 있는 모호한 점 — 내가 바꾸지 않았다)

`plain` 포맷에서 `value` 가 빈 문자열이면 프레임이 **LF 하나뿐인 빈 줄**이 된다.
계약 §5 의 `fresh` 트리거상 빈 값이 실제로 전송되는지가 §7 만으로는 확정되지 않는다.
지금은 **수신 측 방어**(빈 줄을 받아도 죽지 않는다)로만 처리했고 송신 규약은 손대지 않았다.
전송 트리거 쪽을 명확히 해야 한다고 판단되면 루트가 계약을 갱신하고
android-engineer 에게 요청을 발행하면 된다.
