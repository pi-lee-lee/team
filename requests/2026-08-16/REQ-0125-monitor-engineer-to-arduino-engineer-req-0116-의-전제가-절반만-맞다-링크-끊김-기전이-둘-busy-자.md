그리고 **프롬프트 놓침이 배너보다 2~4초 앞선다** — ESP 는 리셋되기 전에 이미 응답을 멈췄다.

## 3. 그래서 부탁하는 것 — 판단은 네 것이다

1. **`busy` 와 침묵을 갈라서 세라.**
   `busy` 를 실패로 안 세는 건 옳다(기전 A). 그런데 기전 B 에서 오는 것은 `busy` 가 아니라
   **침묵**이고, 지금 **ESP 리셋을 탐지하는 유일한 경로가 그 3진아웃**이다.
   둘 다 안 세면 ESP 가 죽어도 장치가 모른 채 허공에 쏘게 된다.
   → 침묵 카운터는 남기고 `busy` 만 빼는 형태를 검토해 달라.

2. **리셋 탐지기를 따로 붙일 수 있다(제안).**
   부트 배너 문자열 또는 `CIFSR` 응답이 `0.0.0.0` — 둘 다 이 로그에서 실제로 관측됐고
   오탐 여지가 좁다. 카운터로 간접 추정하는 것보다 확실하다.

3. **기대 효과를 미리 낮춰 잡아라.** REQ-0116 을 구워도 기전 B 는 안 고쳐진다.
   끊김이 절반만 줄어도 그건 실패가 아니라 예상대로다. 그걸 모르고 재면
   "고쳤는데 왜 그대로냐"가 된다.

## 4. 원인 후보 — 내가 지목하지 않는 것

기전 B 의 리셋이 **둘 다 TX 시도 중**(소비 전류 최대 순간)에 일어났다.
LEDGER 4.2 의 변수 중 하나가 캐패시터(2200µF vs 100µF)였고, 사용자가 15:26~17:0x 에
실물을 만졌으며 내용은 아직 미상이다.
→ **전원이 유력한 후보지만 이 로그만으로는 확정할 수 없다.** 확정하려면 지금 보드의
전원·캐패시터 구성 확인이 필요하다.

⚠ **그건 실물 접촉이라 지금 하면 안 된다.** 관측 창 A 가 ~21:53 까지 돌고 있고,
루트가 실물 동결(보드·포트 접촉 금지)을 걸어 뒀다. **A 가 닫힌 뒤 루트 순서를 받고 해라.**

## 1. `busy` 와 침묵은 **이미 갈려 있다** — 네 걱정은 일어나지 않는다

`조별과제샘플/client.ino` 의 계수 지점은 **한 줄**이다:

```c
if (pr != PROMPT_BUSY) noteSendResult(ok);
```

**제외되는 것은 `busy` 하나뿐이다.** 침묵(`PROMPT_TIMEOUT`)과 `ERROR`(`PROMPT_REJECT`)는
그대로 센다 → **3진아웃 경로가 살아 있다.**

> 네가 지적한 위험(*"둘 다 안 세면 ESP 가 죽어도 모른 채 허공에 쏜다"*)은 **정확한 지적이지만,
> 1단계가 이미 그렇게 만들지 않았다.** 실측 로그가 그 증거이기도 하다 — 18:24 사건은
> `busy` 가 아니라 침묵이었는데 **실패 1/3·2/3·3/3 이 정상적으로 올라갔다.**

⚠ **다만 네 요청 덕분에 진짜 문제를 하나 찾았다 — 아래 3번.**

## 2. 리셋 탐지기 — **제어 경로는 넣지 않는다. 세기만 한다**

### 판별자는 네 정정본대로 `CIFSR → 0.0.0.0` 이다

배너를 쓰지 않은 이유는 네가 전수로 잡아 준 그대로다 — **정상 부팅에도 뜬다.**
내가 처음 짠 코드는 **배너 기반이었고**, 네 정정이 도착해서 갈아엎었다.
그것 없이 그대로 갔으면 **매 기동을 리셋으로 세는 카운터**를 심을 뻔했다.

```c
else if (strncmp(s, "AT+", 3) != 0 && strcmp(s, "0.0.0.0") == 0) {
  if (espResets < 65535) espResets++;      // 진단 전용
}
```

### 왜 제어 경로는 안 만드나 — **사다리가 이미 잘 처리한다**(실측)

```
18:24:55 오프라인 전환 → 18:24:56 CIFSR 0.0.0.0 (사다리가 전진 거부)
                       → 18:24:58 CIFSR 192.168.35.79 (ESP 스스로 재결합)
                       → 18:24:59 CIPSTART → Linked → online
```

**오프라인 전환 뒤 4초에 복귀했다.** 사다리가 *원인* 이 아니라 *결과(IP 가 있는가)* 를 보기
때문에 이름 없는 고장에도 그대로 동작한 것이다(원장 §6.1).
배너를 보고 즉시 복구를 걸면 2~3초를 아끼지만, **한 번에 하나씩** 넣어야 효과를 귀속할 수 있다(§6.3).
→ **다음 변경 후보로 남긴다.**

## 3. 🔴 네 요청 덕분에 찾은 것 — **2단계가 침묵 탐지를 늦춘다**(없애지는 않는다)

2단계는 `SEND OK` 를 볼 때까지 다음 송신을 **건너뛴다.** 그런데 ESP 가 죽으면 `SEND OK` 가
영영 안 오므로, **상한이 풀릴 때까지 3진아웃이 시작되지도 못한다.**

**그래서 설계 초안의 상한 3000ms 를 2000ms 로 줄였다.** 네 요청(과 루트 지시)이 아니었으면
이 비용을 못 보고 넘어갔다.

**주장으로 두지 않고 시험으로 쟀다** — 완전 침묵을 흉내 내어 오프라인까지 가는지 확인:

```
[16] ESP 죽음 시나리오 — 침묵 3연속이 여전히 오프라인으로 간다
  PASS  ★★ ESP 가 완전히 침묵해도 결국 오프라인으로 간다 (탐지 유지)
  PASS  ★ 복구 사다리로 들어간다
      (참고: 오프라인까지 4 주기 — 2단계 이전은 3주기였다)
```

> ### 결론: **탐지는 유지된다. 비용은 1주기(약 1초)다.**
> 무한 정지가 아니고, 살아있음 불변식(10초)이 이중 안전망으로 남는다.

## 6. 🔴 너에게 되돌려 주는 경고 — `DEBUG=0` 이면 **네 A/B 판별이 통째로 사라진다**

A/B 를 가르는 판별자가 **전부 `#if DEBUG` 안**에 있다:
`[AT] "…"` 원문 로깅 · `busy s...` · `CIFSR → 0.0.0.0` · `[TX-BUSY]` · `[TX-RESYNC]`.

팀이 플래시 절약용으로 `DEBUG=0` 빌드를 준비해 뒀다(25%p 절약). **그걸 구우면 네가 만든
분류 방법이 그날로 못 쓰게 된다.** 2단계 효과 측정이 끝나기 전에는 `DEBUG=1` 로 구워야 한다.

## ⚠ 발행 후 정정 (2026-08-16 18:50, monitor-engineer) — **읽기 전에 이것부터**

### 1. 4건(2:2) → **5건(자해 2 : ESP 리셋 3)**

18:44:56 에 5번째 사건이 났고 **리셋 형**이다(배너 18:44:55 · CIFSR 0.0.0.0 18:44:57).

### 2. 판별자를 전수로 검증했다 — 처음 보낼 때 이건 확인 전이었다

| 판별자 | 전수 | 리셋 사건과의 일치 | 정상 부팅(16:59:57)에서 |
|---|---|---|---|
| 부트 배너 | 4건 | 리셋 3건 + 정상부팅 1건 | **뜬다** |
| `CIFSR -> 0.0.0.0` | 3건 | **리셋 3건과 3/3** | **안 뜬다** |

→ **`0.0.0.0` 이 배너보다 나은 판별자다.** 배너는 매 기동에 뜨므로 그것만 쓰면
   정상 부팅을 리셋으로 오탐한다. 처음 요청에서 "둘 다 오탐 여지가 좁다"고 쓴 것은
   **검증 전 추정이었다. 정정한다** — 배너는 단독으로 쓰면 오탐한다.

### 3. `busy` 는 났다고 반드시 끊기는 게 아니다
