# REQ-0116 · 자해를 멈춰라 1단계 — busy 를 실패로 세지 않는다 · 더미 주입 중단 (구현만, 플래싱 금지)

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

**고칠 것을 승인한다 — 다만 단계를 나누고, 플래싱 시점은 내가 정한다.**

네 진단이 오늘의 결론을 바꿨다. `링크 끊김 2.5회/h` 는 고장이 아니라 **자해**다.
링크는 멀쩡한데 우리가 끊는다. 그리고 무손실인 이유도 그것으로 설명된다.

## 1단계 — 지금 구현해라 (지혈)

**후보 1·2 만.** 가장 작은 변경으로 자해를 멈추는 것이다.

1. **`busy` 는 실패가 아니라 재시도다.** 대기 중 `busy` 가 오면 즉시 중단하고
   **카운터를 올리지 않는다.** ESP 가 "지금 바쁘니 나중에"라고 **명시적으로 답한 것**을
   침묵과 같이 취급하지 않는다.
2. **`busy`/`ERROR` 를 받았으면 더미를 채우지 마라.** 더미는 (a) 갈래에서만 옳고,
   (b) 에서는 명령 스트림에 쓰레기를 주입해 상황을 악화시킨다 —
   monitor 가 본 "두 줄이 붙은" 흔적이 그 결과다.

이 둘은 **동작을 늘리는 게 아니라 잘못된 판정을 없애는 것**이라 위험이 낮다.

## 2단계 — 1단계와 **같이 넣지 마라**

3. **`SEND OK` 를 기다렸다 다음 `CIPSEND`.** 네 말대로 고정 80ms 를 없앨 유일한 정답이지만,
   **송신 경로의 타이밍 구조를 바꾸는 변경**이다. 1·2 와 섞으면 어느 쪽이 효과를 냈는지
   못 가른다 — 오늘 하루 종일 변수를 하나로 못 줄여서 치른 값을 또 치르는 것이다.

   1단계 효과를 측정한 뒤 별도로 간다. **설계는 지금 해 둬도 좋다.**

4. **`#` 채움 근거 주석**(서버 검사 순서가 길이→체크섬→타입인데 반대로 적힌 것) —
   1단계에 같이 고쳐라. 결론이 아니라 근거만 틀린 것이지만, **틀린 근거는 다음 사람이
   그 위에 쌓는다.**

## 🔴 플래싱은 하지 마라 — 순서가 있다

지금 A 구간이 쌓이는 중이고, **그게 이제 "고치기 전" 팔이 됐다.** 목적이 바뀌었다 —
DEBUG 실험 설계용이 아니라 **네 수정의 효과를 증명할 기준선**이다. 지금 구우면 그걸 버린다.

그리고 socket 이 **하행 도달 시험**(REQ-0115)을 지금 칩에서 한다. 그 시험이 끝나기 전에
펌웨어가 바뀌면 무엇을 잰 것인지 모르게 된다.

**순서**: ① 네가 1단계 구현(코드만) → ② socket 하행 시험 완료 → ③ A 표본 확보 →
④ 내가 플래싱 창을 준다 → ⑤ 고친 뒤 같은 규칙으로 재계수.

## ④(DEBUG) 판단 — 네 말이 맞다

**"고치기 전에 DEBUG 실험을 하는 것은 순서가 나쁘다"** 채택한다. 1·2·3 이 영향을 줄일
것이므로 고친 뒤에도 남으면 그때 잰다. SoftwareSerial RX 버퍼 64바이트·반이중이라
DEBUG 출력이 버퍼를 넘치게 한다는 기전도 기록해 둬라 — **"붙은 줄"의 자연스러운 설명**이
둘 있다는 뜻이고, 나중에 그 둘을 갈라야 한다.

## 정정 둘 — 접수

**(1) 근거 교체 접수.** 서버측 0 은 세 원인 모두와 양립하므로 증명이 못 된다는 것,
실제로 가른 것은 **AT 에코가 돌아왔고 `SEND OK` 가 없었다**는 장치측 증거라는 것.
결론이 같아도 근거가 틀리면 다음 사람이 그 근거로 다른 결론을 만든다. monitor 에게도 전한다.

**(2) 주석 오류를 수정 금지 지시를 지켜 안 고치고 목록에 넣은 것** — 맞다.

## 왜 필요한가

링크는 멀쩡한데 우리가 끊고 있다. ESP 가 명시적으로 busy 라고 답한 것을 침묵과 같이 실패로 세고 3번이면 소켓을 파기한다. 시연에서 하행 명령이 그 순간에 걸리면 그대로 실패다.

## 무엇을 바꿨나 — `조별과제샘플/client.ino` 한 파일

### 1. 프롬프트 대기가 **bool → 4상태**가 됐다

이게 결함의 뿌리였다. 예전에는 `>` 를 봤는가 아닌가(bool)뿐이라
**"ESP 가 바쁘다고 명시적으로 답한 것"과 "아무 답도 없는 것"이 같은 값으로 뭉개졌다.**

```c
PROMPT_OK      // '>' 수신 — 데이터 모드
PROMPT_BUSY    // "busy"  — 거부. 명령 모드
PROMPT_REJECT  // "ERROR" — 거부. 명령 모드
PROMPT_TIMEOUT // 무응답  — 데이터 모드일 수 있다
```

**거부가 확인되면 남은 시간을 안 기다리고 즉시 반환한다.** 그 CIPSEND 에 `>` 는 오지 않는다.

### 2. `busy` 는 세지 않는다

```c
if (pr != PROMPT_BUSY) noteSendResult(ok);
```

**`noteSendResult(true)` 로 성공 처리하지 않고 호출 자체를 건너뛴다.** 이유를 코드 주석에도 적었다 —
`busy` 는 성공이 아니므로 **카운터를 0 으로 되돌려서도 안 된다.** 앞선 진짜 실패가 있었다면 그대로 남는다.
`ERROR`(PROMPT_REJECT)는 **그대로 센다** — 명령이 실제로 거부된 것이고 링크 이상일 수 있다.

### 3. 거부일 때 더미를 넣지 않는다

`busy`/`ERROR` 는 ESP 가 **명령 모드에 그대로 있다는 확답**이라 **채울 약속 자체가 없다.**
넣으면 AT 해석기가 먹어서 스트림을 더 어지럽힌다(monitor 가 본 "붙은 줄").
**무응답(PROMPT_TIMEOUT) 갈래에서는 기존 더미 채움을 그대로 유지**했다 — 거기서는 ESP 가
데이터 모드일 수 있으므로 채우는 쪽이 여전히 안전하다.

### 4. `#` 채움 근거 주석 정정

*"체크섬 이전에 **타입**에서 걸린다"* → **사실과 반대**였다. 서버는 **길이 → 체크섬 → 타입** 순이고
(`server.cpp:906/1429/1541`, socket 확인) `###…` 은 쉼표가 없어 체크섬 단계에서 걸린다.
결론(반드시 버려짐)은 유지되나 **근거가 틀렸었고, 채움 문자를 무엇으로 고르든 같은 칸에 들어간다.**
교훈도 같이 적었다 — **남의 도메인 동작을 근거로 쓸 때는 확인하고 출처를 적어라.**
덤으로 옛 주석의 *"무해하다"* 단정도 낙관이었음을 표시했다(실측에서 스트림이 더 엉켰다).

## 구현에서 판단한 것 하나 — **`pendLine` 을 쓰지 않았다**

`busy` 를 잡는 자연스러운 자리는 `pendLine` 이지만, 송신 중에는 **첫 줄 하나만** 담기고 나머지는
버려진다(`feedRxChar`). 앞선 줄이 자리를 차지하면 **정작 이 CIPSEND 의 `busy` 응답을 못 본다.**
그래서 **바이트 흐름에서 직접 훑는 방식**으로 갔다 — 기존 버퍼 의미를 전혀 건드리지 않는다.
대소문자를 가리지 않게 한 이유도 적어 뒀다: 실측에서 **`ERROR` 와 `Error` 가 둘 다** 나왔다.

## 2단계 설계 — `SEND OK` 대기 (구현하지 않았다)

네 지시대로 **섞지 않았다.** 설계만 남긴다.

**핵심**: 지금은 `SEND_GAP_MS=80` 이라는 고정 추측으로 "앞 전송이 끝났을 것"을 가정한다.
정답은 ESP 가 주는 **`SEND OK` 를 실제로 기다리는 것**이다. 그러면 `busy s...` 자체가 사라진다.

- `sendLine()` 성공 직후 `SEND OK`/`SEND FAIL` 을 기다리는 상태를 둔다. 다만 **블로킹으로 기다리면
  1Hz 하트비트가 밀린다** — `awaitingSendOk` 플래그로 두고 다음 송신 전에 확인하는 **비블로킹**이 맞다.
- `SEND FAIL` 은 **진짜 전송 실패**이므로 이때는 `noteSendResult(false)` 로 센다.
  지금은 이 신호를 아무도 안 보고 있다.
- `SEND_GAP_MS` 는 `SEND OK` 가 오면 **불필요해진다.** 다만 안전망으로 상한 타임아웃은 남긴다
  (ESP 가 `SEND OK` 를 안 주는 경우가 있다).
- ⚠ **위험**: 송신이 완료 확인에 묶이므로 하행 처리·하트비트 주기와의 상호작용을 봐야 한다.
  1단계와 섞으면 못 가른다는 네 판단이 맞다.
