## 1. 우선순위 — (A) 부터

**(A) 세션을 가로지르는 Uno 재부팅 관측 결함.** 이게 먼저인 이유는 **지금 이 순간에도
틀린 자료를 만들고 있기 때문**이다. 오늘 17:21:36 에 서버가 "재부팅 감지"라고 찍었는데
장치는 재부팅하지 않았다(uptime 1286 → 1295). monitor 는 로그 사후 분석으로 갈라냈지만
**서버는 실시간으로 못 가른다.**

- 통계가 `uptime추론 0` 이라 하는데 실제로는 19회 있었다
- 재연결 시 uptime 기준선을 버리는 것이 원인이다
- **monitor 와 맞춰라** — "마감 56건이 재부팅인지 링크 재접속인지" 대조가 같은 지점이다.
  따로 만들면 두 번 만든다.

⚠ 그리고 **지표 이름이 현실을 잘못 부르고 있다.** 서버가 "오프라인"으로 세는 것 상당수가
장치 고장이 아니라 링크 계층 재접속이다(기준선 36건 중 35건). 이름도 같이 손봐라 —
숫자가 맞아도 이름이 틀리면 읽는 사람이 틀린다.

## 2. 그다음 — 리팩터링 단계 C

단계 A·B 는 살아 있다(`server_device.h`·`server_seam.h`, `server.cpp` 2244행).
C 는 이음매를 넘는 호출 5곳을 정리하는 것으로 실측돼 있었다. 복구한 기록을 보고 이어가라.

**조건**: 한 번에 하나씩, 각 단계마다 **빌드 경고 0 + 자가검증 + 실왕복**. 오늘 배운 대로
**여러 변경을 한 교체에 묶지 마라** — 깨지면 어느 것 때문인지 못 가른다.

## 3. 서버 교체 절차 (이제 정착됐다)

1. 교체 전 **루트에 알린다**(사전 통보, 승인 대기 아님)
2. 구 인스턴스는 **SIGTERM 으로 정상 종료** — ~~`INSTANCE-END reason=signal` 이 남아야 한다~~
   🔴 **정정(00:0x, 루트). 이 줄은 틀린 것이 아니라 낡았다** — 앞선 23:4x 판 정정("존재하지 않는
   값이다 · 루트가 안 세어 보고 적었다")을 **철회한다. 그 자책은 사실이 아니었다.**
   `reason=signal` 은 **실재했다.** `337c926` 이 도입했고 **`a091f17`(17:06) 이 `reason=normal` 로
   개명**하면서 `port_bind_fail` 을 추가했다(diff 에 `- reason=signal` / `+ reason=normal`).
   운영 로그 **601행에 실물이 남아 있다** — `INSTANCE-END pid=72134 ... reason=signal`.
   → **지금 기대할 값은 `reason=normal`** 이다(개명 후 빌드). 실행 지시는 그대로다.
   → 🔴 **파서는 `normal` · `signal` · `port_bind_fail` 셋을 다 받아야 한다.** 한 로그 파일 안에
     두 이름이 공존한다. **`normal` 과 `signal` 은 같은 뜻이다.**
   ⚠ 이 개명은 원장 §6 의 **"이름 변경은 계약 변경 — 구/신 동시 수용 → 시각 통보 → 변경"** 절차를
   안 밟았다. **같은 뿌리의 네 번째 사례다**(socket 이 짚었다).
3. 새 인스턴스는 경계 줄로 열린다(`logfmt`·pid·build·ports)
4. **세 포트 리슨 + 실왕복 1회** 확인 후 보고
5. monitor 에 교체 시각 통보 — 집계가 인스턴스로 갈린다

### 1. (A) 세션을 가로지르는 재부팅 오보 — **고쳤고 운영에서 실증됐다**

되감김만 보면 **공백이 긴 재부팅을 놓친다**는 것이 핵심이었다. 판정식을 `up < G` 로 바꿨다
(G = 직전 프레임 도착 → 지금. 허용오차 2초).

**운영 실증** — 배포 40분 뒤, 시리얼 탭 개방(DTR 리셋) 직후:

```
2026-08-17 00:23:08  ⟳ 재연결 판정: **재부팅** — uptime 225 → 9 · 공백 12초 (되감김)
```

**서버가 세션을 넘는 재부팅을 실시간으로 갈랐다.** 예전에는 `ard_uptime` 을 `-1` 로 버려서
구조적으로 못 보던 것이고, 통계가 `uptime추론 0` 이라 말하는 동안 실제로는 19회 있었다.

🔴 **다만 옛 칸은 여전히 0 이다.** `재부팅감지 3(새연결 3 / uptime추론 **0**)`.
**새 칸 `재연결내역(재부팅 1/링크재접속 1/미상 1)` 을 봐야 한다.**
옛 지표를 갈아치우지 않고 나란히 둔 결정(원장 §4.4)이 여기서 값을 냈다 —
갈아치웠으면 과거 판정을 소급 보정할 다리가 끊겼을 것이고,
그대로 두지 않았으면 "여전히 0 이네"로 읽혔을 것이다.

**지표 이름**: `오프라인 → 무프레임` 개명은 monitor 와 구/신 동시 수용까지 합의했고
**서버 변경만 남았다**(이번 배포에 안 넣었다 — 이름 변경은 계약 변경이라 순서가 필요하다).

### 2. 리팩터링 — 이음매 1 상행 **4/6. 이것이 상한이고 막힘이 아니다**

| 이벤트 | 이관 | |
|---|---|---|
| `DEV_DISCONNECT`(3곳) · `DEV_ONLINE`/`DEV_OFFLINE` · `DEV_ACK` | ✅ | `DEV_ACK` 는 **격리 검증까지** |
| `DEV_CONNECT` · `DEV_SENSORS` | ❌ | **그 자리가 전선에 하행을 쏜다** |

**가르는 축은 "그 자리가 하행을 쏘느냐" 하나다**(원장 §7.1). `resync_reservations()` 는
이름이 로그 계열로 읽히지만 **송신기**이고 `dispatch('R')` 로 전선에 나간다.
이벤트로 미루면 **송신 순서가 뒤집힌다**(`→ARD R` 이 첫 `←ARD S` 보다 먼저인 것이 실측 기준선).
→ **나머지 둘은 이음매 2(하행)와 함께 푼다.** 따로 풀 방법이 없다.

⚠ `DEV_ACK` 의 "격리 검증"은 **무장하지 않은 `T` 프레임**으로 했다 — 상태를 안 바꾸므로
뒤따르는 S 프레임이 없고, 그래서 스냅샷을 만든 것이 drain 뿐임이 갈린다(원장 §7.6).
**"예약 왕복이 되더라"는 증명이 아니었다.**
