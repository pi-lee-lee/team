# REQ-0114 · 링크 끊김의 촉발 조건을 좁혀라 — send_fail_x3 은 왜 도달하는가 (보드 미접촉·읽기만)

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

10:51:02 을 보겠다는 제안 — 승인한다. **단, 물음을 다시 정의하고 시작해라.**

## 그건 이미 미제가 아니다

monitor 가 표본부터 세서 풀었다(`monitor/FINDING-2026-08-16-link-vs-mcu.md`):
**기준선 13.92시간의 새 연결 36건 중 35건**이 같은 것이었다. 시간당 2.5회다.
10:51:02 은 그중 하나가 사이클 분석에 걸린 것뿐이다.

- MCU 는 안 죽었다 — 첫 프레임 uptime 이 126 → 1,248 → 8,189 → 34,541 로 계속 커진다
- 서버 회수도 아니다 — 유휴 마감 회수 0건
- 형태는 `오프라인 판정 → 상대가 닫음 → 재접속` 이고, 옛 시리얼 관측의
  `errno=54` / `[LINK] closed reason=send_fail_x3` 와 맞는다

## 그래서 진짜 물음은 이것이다

**ESP 링크 계층은 왜 `send_fail_x3` 에 도달하는가.**

"장치가 스스로 끊고 다시 붙는 정상 복구"까지는 밝혀졌지만, **무엇이 그 복구를 촉발하는지**는
모른다. 시간당 2.5회면 드물지 않다. 이건 네 도메인이고 **보드 없이 코드 경로만으로 상당 부분
좁힐 수 있다.**

좁혀 볼 것:

1. **`send_fail_x3` 의 3회는 무엇을 세는가** — 연속 실패인가 누적인가, 리셋 조건은 무엇인가.
   경계가 헐거우면 산발적 실패가 시간이 지나며 쌓여 끊는다.
2. **직전 송신이 무엇이었나** — 주기 S 프레임인가, 하행 응답인가, keepalive 인가.
   특정 종류에서만 난다면 그게 단서다.
3. **AT 응답 대기 타임아웃** — ESP 가 느리게 답할 때 실패로 세는가. 그렇다면
   "링크가 끊긴 것"이 아니라 **"우리가 못 기다린 것"**이다. 성격이 완전히 달라진다.
4. **끊은 뒤 재접속이 0.90초 무백오프**라는 것을 이미 실측했다 — 복구 쪽 설계도 같이 봐라.

## 하지 말 것

- **보드 미접촉 유지.** monitor 의 새 기준선 창이 돌고 있다.
- **고치지 마라. 이번엔 읽고 좁히는 것까지다.** 원인 후보가 서면 그때 순서를 준다.
  monitor 의 시리얼이 곧 `[LINK] closed reason` 을 **직접** 세기 시작한다 —
  네 코드 경로 분석과 그 실측이 만나는 지점에서 고치는 게 맞다.

## 네가 원장에 박은 규칙에 대해

> 다른 도메인의 임계값을 권고하기 전에, 그 임계값이 재는 구간이 어디서 시작하는지 먼저 확인한다.

채택한다. 그리고 **오늘 세 번 틀린 것을 셋 다 남긴 것**이 이 팀에서 제일 값나가는 자산이다.
특히 두 번 다 **반증을 자기 손으로 적어 놓고 연결하지 못했다**는 진단 — 그건 지식의 문제가
아니라 확인 절차의 문제라 규칙으로 막을 수 있다. 그래서 규칙이 맞는 대응이다.

단서 ②를 **"늘려라"가 아니라 "줄이지 마라"로 방향을 바꿔 남긴 것**도 정확하다.
7초의 여유가 곧 그 함정과의 거리다.

## 왜 필요한가

시간당 2.5회 끊기는데 왜 끊기는지 모른다. 정상 복구로 가려져 있었을 뿐이고, 복구가 실패하는 날 그대로 장애가 된다.

## 0. 🔴 먼저 — **monitor 의 계수 계획이 그대로면 0건이 나온다**

> `monitor 의 시리얼이 곧 [LINK] closed reason 을 직접 세기 시작한다`

**지금 칩에서는 그 문자열이 나오지 않는다.** `[LINK] closed reason=send_fail_x3` 은
**`arduino/client/EspLink.h` 에만 있다.** 지금 칩에 도는 것은 `조별과제샘플/client.ino`(옛 계열)이고,
같은 사건에서 이 문자열을 찍는다:

```
[NET] 전송 3회 연속 실패 → 오프라인 전환. 낡은 소켓부터 닫는다(CIPCLOSE)
```

**이걸 모르고 `closed reason` 만 세면 "끊김 0건"이라는 잘못된 결론이 나온다.** 계수 대상을 바꿔야 한다.

### ★ 그리고 훨씬 좋은 지표가 이미 찍히고 있다 — **미수(near-miss)를 셀 수 있다**

끊김(3회 연속)만 세지 말고 **개별 실패 1회**를 세라. 옛 계열은 실패할 때마다 이걸 찍는다:

```
[TX-RESYNC] 프롬프트 놓침 → 더미 N바이트로 스트림 복구(서버는 이 줄을 버린다)
[NET] 전송 실패 1/3     ← 2/3, 3/3 도 그대로 찍힌다
```

**`전송 실패 1/3` 의 빈도 대비 `3회 연속` 의 빈도**를 보면 실패가 **산발인지 뭉치는지**가 바로 갈린다.
끊김만 세면 3회 연속이 된 것만 보이고 **직전까지 얼마나 아슬아슬했는지가 안 보인다.**
→ 시간당 2.5회 끊김의 분모를 알 수 있는 유일한 값이다. **이걸 같이 세 달라.**

덤: `promptResyncs` 는 **서버의 "버린 줄(모름)" 카운터와 1:1로 짝**이 되게 설계돼 있다
(`client.ino:1070-1072`). socket 의 그 카운터와 수가 어긋나면 **프롬프트 놓침 외의 원인이 더 있다는 뜻**이다.
교차검증이 이미 준비돼 있으니 쓰면 된다.

## 1. 3회는 **연속**이다 — 누적 아님. 네 우려는 배제된다

```c
// 조별과제샘플/client.ino:1108
static void noteSendResult(bool ok) {
  if (ok) { sendFailStreak = 0; return; }     // ★ 성공 한 번이면 0 으로 리셋
  if (sendFailStreak < 255) sendFailStreak++;
  if (sendFailStreak >= SEND_FAIL_LIMIT) goOffline();   // LIMIT = 3
}
```
EspLink 도 동일하다: `if (ok) { _fail = 0; } else if (++_fail >= 3) goOffline(...)` (`EspLink.h:325`).

리셋 지점은 둘: **① 송신 성공 시 즉시 0**, **② 복구 진입 시 0**(`startSocketRecovery`, `client.ino:1080`).

> **"경계가 헐거워 산발적 실패가 시간이 지나며 쌓여 끊는다"는 배제된다.**
> 중간에 한 번이라도 성공하면 카운터가 0 이 된다. 1Hz 하트비트에서 **3초 안에 3연속**이어야 끊긴다.

## 2. 직전 송신 — **거의 전부 주기 S 프레임이다**

`sendLine()` 호출부는 **딱 두 곳**이다(`client.ino:1236`, `1248`): **S 프레임**과 **A(응답) 프레임**.
keepalive 같은 별도 경로는 없다. S 가 1Hz 로 계속 나가므로 **물량으로는 S 가 압도적**이다.
→ **특정 프레임 종류에서만 나는 것이 아니다.** 이 축에서는 단서가 안 나온다.

## 3. ✅ 핵심 — **네 가설 3번이 맞다. 세는 것은 "링크 끊김"이 아니라 "우리가 못 기다린 것"이다**

```c
bool ok = waitForPrompt();   // '>' 를 PROMPT_TIMEOUT_MS 안에 봤는가 — 그것뿐이다
...
noteSendResult(ok);          // client.ino:1196 — 실패를 세는 유일한 지점
```

`waitForPrompt()` 는 **오직 `>` 프롬프트가 제한시간 안에 왔는지**만 본다(`client.ino:1123`).
그리고 소스 주석이 **세는 곳이 여기 하나뿐**임을 명시한다(`client.ino:1105-1107`):
ESP 가 보내는 `SEND FAIL`·`busy`·`ERROR` 같은 오류 문구는 **로그만 남기고 세지 않는다**
(`link is not valid` 만 예외). 이중 계수를 피하려는 의도적 설계다.

> ### 그러므로 `send_fail_x3` = **"연속 3번 `>` 를 제때 못 봤다"** 이다.
> 링크가 죽었다는 **증거가 아니라 추정**이다. 소스도 그렇게 적혀 있다 —
> `client.ino:1081`: *"이 판정은 **추정**이고, 링크가 실은 살아 있었다면 재시도에
> ALREADY CONNECTED 가 와서 그대로 복귀한다"*. **설계자도 오탐 가능성을 알고 있었다.**

### 🔑 그리고 두 계열의 제한시간이 **7.5배 다르다** — 이게 제일 큰 발견이다

| 계열 | 프롬프트 제한 | 비고 |
|---|---|---|
| `조별과제샘플/client.ino` (옛 계열, **지금 칩**) | **300ms** | `PROMPT_TIMEOUT_MS` |
| `arduino/client/EspLink.h` (11:26~15:26 구간) | **40ms** | `ESPLINK_PROMPT_MS` |

**`send_fail_x3` 관측은 EspLink 구간에서 나온 것**인데, 그쪽은 ESP 에게 **40ms** 밖에 안 준다.
ESP-01 이 `AT+CIPSEND` 에 보통 수 ms 로 답하는 건 맞지만, **재전송·내부 처리로 수십 ms 로 늘어지는
순간이 3번 연속이면 끊는다.** 40ms 는 그 여유가 거의 없다.

→ **같은 이름의 사건이지만 두 계열의 민감도가 전혀 다르다. 두 구간의 끊김률을 같은 것으로 비교하지 마라.**

## 4. 복구 설계 — 이미 실측과 일치한다

`startSocketRecovery()`(`client.ino:1078`)는 **CIPSTART 가 아니라 CIPCLOSE 부터** 간다.
이유가 주석에 있다 — CIPSTART 는 ESP 의 낡은 소켓을 못 지우고 `ALREADY CONNECTED` 만 돌려주므로
그대로 무한 루프가 된다(REQ-0051 에서 실제로 겪은 것). 그래서 닫고 → `CLOSED` 를 받아
정상 생명주기 신호에 다시 올라탄다. **내가 실측한 0.90초 무백오프 재시도가 이 사다리다.**

멱등 캐시를 복구 진입 때 **비우지 않는** 것도 의도적이다(`client.ino:1081-1084`) — 판정이 추정이라,
링크가 살아 있었을 때 캐시를 비우면 멱등성이 깨진다.

## 5. 원인 후보 (고치지 않았다 · 근거 강한 순)

**① 제한시간이 실패 판정을 지배한다 — 특히 EspLink 40ms** ★ 코드로 확증
세는 것이 프롬프트 대기 하나뿐이므로, **끊김률은 링크 품질보다 이 상수에 더 민감하다.**
EspLink 구간의 `send_fail_x3` 은 이것만으로 설명될 수 있다.

**② 반이중(half-duplex) 구조상 놓치는 프롬프트** ⚠ 기전은 확실, 기여도는 미측정
`EspLink.h:315` 가 명시한다 — *"송신 중에는 수신을 못 한다(반이중)"*. SoftwareSerial 9600 이라
**우리가 보내는 동안 도착한 `>` 는 받을 수 없다.** ESP 는 제때 답했는데 우리가 못 받은 경우가 된다.
이 경우 "링크 문제"가 아니라 **직렬 계층 문제**다.

**③ 진짜 ESP 지연(busy)** — `SEND_GAP_MS=80` 이 `busy p...` 회피용으로 이미 들어가 있다.
즉 **연속 송신 시 ESP 가 바빠지는 현상은 이미 알려져 있었다.** 그 여유가 부족하면 프롬프트가 늦는다.

**④ 관측이 원인일 가능성(observer effect)** ⚠ 확인 필요 — **지금 칩은 `#define DEBUG 1` 이다**
(`client.ino:29`). 그래서 AT 대화가 전부 115200 으로 나간다(내 부팅 캡처에서 초당 수십 줄 확인).
EspLink 쪽 주석은 정확히 이걸 경고한다 — *"DEBUG 는 AT 대화를 전부 찍어서 소크에 못 쓴다"*(`EspLink.h:117`).
**진단 출력 자체가 프롬프트 수신 타이밍을 밀어 미수를 늘리고 있을 가능성**이 있다.
지금 기준선이 DEBUG=1 로 돌고 있으므로 **이 값을 아는 것이 판정에 중요하다.**

## 6. 다음에 무엇을 재면 갈리는가 (실측 제안 · 고치는 것 아님)

1. **`전송 실패 1/3` 과 `3회 연속` 의 비율** — 산발이면 ①③, 뭉치면 ②④ 쪽이다.
2. **`promptResyncs` vs 서버의 "버린 줄" 카운터** — 어긋나면 프롬프트 놓침 외의 원인이 있다.
3. **DEBUG=1 과 DEBUG=0 의 끊김률 비교** — ④를 가르는 유일한 방법. 다만 **플래싱이 필요**하므로
   지금은 하지 않는다. 순서를 받으면 하겠다.

> **가장 값싼 것은 1번이다.** monitor 가 계수 대상만 바꾸면 **보드를 안 건드리고** 오늘 안에 나온다.
