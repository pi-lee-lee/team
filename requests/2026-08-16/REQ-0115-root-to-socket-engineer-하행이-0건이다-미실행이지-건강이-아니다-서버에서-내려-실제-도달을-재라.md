# REQ-0115 · 🔴 하행이 0건이다 — 미실행이지 건강이 아니다. 서버에서 내려 실제 도달을 재라 (지금 칩은 EspLink 아님)

**요청자** `root` → **담당** `socket-engineer`

## 요청 내용

monitor 가 지금 기준선의 구멍을 찾았다. **하행이 0건인데, 그건 "괜찮다"가 아니라 "한 번도 안 돌았다"이다.**

```
서버 → 장치 (→ARD)              0건
시리얼 수신측 [RX]/예약/ACK/R,   0건
```

그리고 **가만히 쌓아서는 안 풀린다.** 상행은 장치가 1초마다 알아서 보내지만
**하행은 사람이 트리거해야 생긴다.** A 를 24시간 쌓아도 아무도 예약을 걸지 않으면
이 칸은 영원히 0 이다.

**시연에서 예약 명령이 내려가는 경로가 하행이다.** 지금 우리는 가장 위험한 경로를
전혀 관측하지 못한 채 "무손실"이라고 말하고 있다 — 오늘 반복해서 밟은
**"0 이 건강인가 미실행인가"** 의 바로 그 자리다.

## 할 일

**서버에서 하행을 몇 번 내려라.** 상행 관측은 그대로 도니 A 구간을 깨지 않는다.

1. **내리기 전에 monitor 에게 시각을 알려라**(초 단위). 개입이므로 집계에 표시된다.
   이번엔 기록용이 아니라 **그 시각이 관측 대상**이다.
2. 몇 번 내리고 **끝까지 도달했는지 확인해라** — 서버가 보냈다가 아니라
   **장치가 받았고 그에 맞게 동작했는가**. monitor 의 시리얼이 수신측을 직접 본다.
3. 실패하면 실패한 대로 보고해라. **지금 알아내는 게 시연장에서 알아내는 것보다 싸다.**

## 🔴 함정 — 지금 칩은 EspLink 가 아니다

**사용자가 `조별과제샘플/client.ino`(옛 계열)로 재플래싱했다.** 그러니:

- **`W` 프레임과 `server_wire.h` 디코더는 EspLink 쪽 산물이다.** 지금 칩이 그걸
  이해한다고 가정하지 마라. W 를 내려 놓고 "하행이 깨졌다"고 결론 내면 틀린다.
- **지금 칩이 실제로 해석하는 하행 형식**이 무엇인지 먼저 확인해라. 필요하면
  arduino 에게 물어라 — 그쪽 소스를 읽으면 바로 나온다.
- 형식이 옛 계열의 예약 `R` 이라면 그걸로 시험해라. **칩이 아는 말로 걸어야
  경로를 재는 것이지, 모르는 말로 걸면 파서를 재는 것이다.**

## 이 시험이 답해야 할 것

- 서버→장치 하행이 **지금 구성에서 실제로 도달하는가**
- 도달률과 지연 — 상행에서 본 무손실이 하행에도 성립하는가
- 실패한다면 어느 계층인가(서버 송신·AT·장치 수신·해석)

## 그다음 (지금은 하지 마라)

여기까지 되면 **웹→서버→장치 종단 경로**를 web-engineer 가 시험하는 것이 다음이다.
시연은 브라우저에서 시작하므로 서버 주입만으로는 절반만 잰 것이다. 순서는 내가 준다.

## 왜 필요한가

시연에서 예약 명령이 내려가는 경로가 하행인데 지금 기준선이 그 경로를 전혀 관측하지 못한다. 상행 무손실 결론을 하행까지 읽으면 한 번도 안 쓰인 경로를 건강하다고 부르는 것이 된다.

## 1. 함정부터 — `W` 를 안 썼다

내리기 전에 **지금 칩이 무엇을 해석하는지 소스에서 확인**했다.
`조별과제샘플/client.ino:1514` — `cand[0]` 가 **`R`·`C`·`T`·`M`** 이 아니면 버린다.
**`W` 는 없다.** 그래서 `W` 를 쓰지 않고 **`R`/`C`** 로 걸었다.
(`W` 로 걸었으면 "하행이 깨졌다"는 틀린 결론이 나왔을 것이다 — 경로가 아니라 파서를 재는 것이므로)

서버가 내리는 형식(`server.cpp:1301`)도 확인했다:
`R,<rid>,<slot>,<user_id>,<cksum>` / `C,<rid>,<slot>,<cksum>` — **칩이 아는 말과 일치한다.**

## 2. 결과 — 5/5 도달, ACK 5/5, 예약 마스크 5/5 반영

| rid | 명령 | 서버 송신 | 장치 ACK | result |
|---|---|---|---|---|
| 1 | `R A1` | 17:23:08 | 17:23:08 | 0 |
| 2 | `C A1` | 17:23:41 | 17:23:41 | 0 |
| 3 | `R B2` | 17:23:49 | 17:23:50 | 0 |
| 4 | `R A4` | 17:23:52 | 17:23:52 | 0 |
| 5 | `C B2` | 17:24:00 | 17:24:00 | 0 |

**도달률 100% (5/5) · 지연 4건은 같은 초, 1건만 1초.** (로그가 초 단위라 그 이하는 못 가른다)

### 🔑 "보냈다"가 아니라 "장치가 그에 맞게 동작했다" — 예약 마스크로 확인했다

ACK 는 장치가 **받았다**까지만 말한다. 그다음 S 프레임의 `reserved` 필드가 실제로 바뀌었는지를 봤다:

```
17:23:08  res 0000000000 → 1000000000   R A1   (A1 = 0번 비트)
17:23:42  res 1000000000 → 0000000000   C A1
17:23:50  res 0000000000 → 0000001000   R B2   (B2 = 6번 비트)
17:23:52  res 0000001000 → 0001001000   R A4   (A4 = 3번 비트, B2 유지)
17:24:01  res 0001001000 → 0001000000   C B2   (B2만 내려가고 A4 유지)
```

**다섯 번 다 명령과 정확히 일치한다.** 특히 4·5번은 **다른 예약을 건드리지 않고** 목표 칸만 바꿨다.
장치가 명령을 삼킨 것도, 전체를 덮어쓴 것도 아니다.

## 3. 🔑 부수 소득 — `+IPD` 형식이 처음으로 실측됐다

펌웨어가 **"실측 못 했다"고 주석에 남겨 둔 값**(`client.ino:347-351`)이 이번에 확정됐다.
monitor 의 시리얼 탭이 잡은 것:

```
17:23:08  [AT] "+IPD,19:R,1,A1,00000000,13" (26)
17:23:08  [TX] A,1,A1,0,30
17:23:08  [TX] S,1224,0110000010,1000000000,1386,P1,3B
```

**답: `+IPD,<n>:` — 연결 id 없는 단일 인자 형식이다.** 근거도 부팅 로그에 있다(`CIPMUX=0`).
→ 펌웨어가 걱정하던 `+IPD,<id>,<n>:` 로 인한 **버퍼 넘침 시나리오는 지금 구성에서 발생하지 않는다.**
(그 주석은 arduino 파일이라 내가 안 고친다 — 실측값이 나왔으니 갱신하면 좋겠다)

## 4. 실패 계층 — 없음. 다만 관측 중 다른 것이 보였다

하행 자체는 어느 계층에서도 실패하지 않았다. 대신 **17:21:36 에 이런 줄이 있었다**:

```
17:21:36  -ARD 세션#1 종료(같은 device_id(P1) 재접속으로 대체)
17:21:36  ⟳ 재부팅 감지(새 연결) — 살아 있는 예약 0건 재하달
17:21:36  ←ARD S,1141,…,1295,P1   ← uptime 1286 → 1295. **재부팅이 아니다**
```

**서버가 "재부팅 감지"라고 찍었지만 장치는 재부팅하지 않았다.** 재연결이라 uptime 기준선을
버려서 못 가른 것 — 내 숙제 **(A)** 가 만들어 내는 오보의 **오늘 실물 사례**다.
arduino 가 규명한 `send_fail_x3 → 소켓 닫음` 사슬의 결과이기도 하다.

## 5. 덤 — TX-RESYNC 7건 대조 완료 (arduino/monitor 요청)

monitor 가 준 7건 전부 대조했다. **7건 모두 내 드롭 카운터가 하나도 안 움직였다**(체크섬·과길이·잡음 0).

그리고 **내가 제기한 (d)(승격 전이라 못 셌을 가능성)를 배제할 수 있다** — 7건 모두 소켓이
**이미 승격된 뒤**였다(세션#1·#3 진행 중). 승격 후에는 모든 줄이 `on_ard_line` 을 타므로
도착했다면 카운터가 반드시 움직인다. **안 움직였다 = 안 왔다.**
→ arduino 의 **(b) 가 표본 7로 확정**된다. 다만 판정의 무게는 arduino 의 장치측 증거
(`#####` 에코 + `SEND OK` 부재)에 있고, 내 것은 **반증 실패**로서 보태는 것이다.

보강: `17:03:27→17:03:28` 에 uptime 이 **208 → 211** 로 뛴다(벽시계 1초에 장치 시계 3초).
그 사이 루프가 막힌 것이고 더미 처리 비용과 맞물린다.

## 6. 남는 한계 — 이번 시험이 재지 않은 것

- **표본 5건이다.** 100% 는 "5건에서 실패가 없었다"이지 실패율이 0 이라는 뜻이 아니다.
  장시간·부하 조건은 안 쟀다.
- **모두 링크가 건강한 순간이었다.** `send_fail` 이 쌓이는 중이거나 재접속 직후에 내리면
  결과가 다를 수 있다. 특히 **재연결 직후 멱등 캐시**(`client.ino:420`, 옛 rid 충돌) 는 안 건드렸다.
- **브라우저에서 시작하지 않았다.** `net/ws_probe.py` 로 WS 를 직접 물었다. 시연 경로의
  마지막 한 칸(실제 브라우저 → 서버)은 **web-engineer 몫**이라 루트 순서대로 남겨 뒀다.
