# REQ-0109 · 🔴 칩 위 펌웨어가 바뀌었다 — 사용자가 조별과제샘플/client.ino 로 재플래싱 · 15:30 미스터리 종결

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

사용자가 답했다. **네 질문 셋 다 답이 나왔고, 그보다 중요한 사실이 하나 더 있다 — 칩 위 펌웨어가 바뀌었다.**

## 사용자가 확인해 준 것 (그대로 옮긴다)

> 아두이노 범인 나 맞다. 복구 작업은 코드 작업만인 줄 알고 **테스트를 위해 아두이노를 제거했고 끼웠고**,
> **시리얼 포트를 자꾸 뺏겨서 재기동 작업이 여러 번** 된 것이다. 해당 데이터는 나로 인해 오염된 것이다.
> 복구 작업 시작 후 모든 모니터링은 검토 대상에서 제외하라.
> 그리고 **시리얼 문제였는데 아두이노 문제인 줄 알고 `조별과제샘플` 폴더의 아두이노 스케치로
> 재플래싱도 진행한 상태**이다.

## 1. 15:30 미스터리 — 닫힌다

네가 옳았다. 시각이 안 맞는다고 지적해서 "사용자가 만졌으니 다 설명됐다"로 닫히는 걸 막은 덕에,
**정확히 무엇을 언제 만졌는지**까지 나왔다. 답은 네 후보 ②였다 — 보드를 물리적으로 뽑았다 끼웠다.
전원 설계도 열화도 아니다. **캐패시터 증설은 하지 마라.** 고칠 것이 없다.

## 2. 🔴 칩 위 펌웨어가 EspLink 가 아니다

사용자가 **`조별과제샘플/client.ino` 로 재플래싱했다.** 즉 지금 보드에 도는 것은
EspLink 판이 아니라 **08-15 계열 스케치**다. 여기서 따라오는 것들:

- REQ-0100 의 "복원본 hex = 실장 hex 바이트 동일" 증명은 **16:03 시점에는 참이었지만 지금은 아니다.**
  그 문서를 지우지 말고 **"이 대조는 16:0x 기준이며 이후 사용자가 재플래싱해 무효"** 라고 명시해라.
  증명 자체는 유효했다 — 대상이 바뀐 것이다.
- 지금 칩에 무엇이 있는지 **네가 직접 확인해라.** 사용자가 쓴 `조별과제샘플/client.ino` 는
  uncommitted 상태로 +1001줄이 얹혀 있던 그 파일이다. **SERVER_IP 앞 공백(DNS Fail) 수정이
  그 판본에 들어 있는지** 확인해라 — 안 들어 있으면 지금 보드는 그 결함을 안고 도는 것이다.
- 그 파일은 커밋돼 있다(fa52a51). 실장본과 대조할 기준이 저장소에 있다는 뜻이다.

## 3. `arduino/INTERVENTIONS.md` 에 남길 것

- 15:26~ 사용자 직접 개입: **보드 물리적 탈착 반복**, 포트 경합으로 재기동 다수
- 사용자 재플래싱: `조별과제샘플/client.ino` 판본 (시각 미상, 16:2x 이전)
- **오염 경계 15:26 — 이후 관측 데이터는 판정에 쓰지 않는다**
- 그리고 네가 이미 박아 둔 "이것으로 15:30 미스터리가 풀린 것은 아니다" 경고는 **이제 해제해라.**
  풀렸다. 열어 둔 채로 두면 다음 사람이 없는 원인을 쫓는다.

## 4. 보드 접촉

여전히 **보류**다. 사용자 작업이 아직 끝나지 않았다. 끝났다는 신호는 내가 준다.
그때 첫 순서는 재플래싱이 아니라 **지금 칩에 무엇이 있는지 확인**이다 — 모르는 상태로 덮어쓰면
이번 구간이 왜 이랬는지 영영 못 밝힌다.

## 왜 필요한가

지금 보드에 도는 것이 EspLink 판이 아니다. 이걸 모른 채 다음 관측을 하면 어느 펌웨어의 거동인지 알 수 없고, hex 대조 증명도 대상이 바뀐 채로 인용된다.

## 1. ✅ 판정: 지금 칩의 펌웨어에 **SERVER_IP 공백 결함은 없다**

소스만 읽고 답하지 않았다. 그 결함을 처음 찾을 때 쓴 것과 **같은 방법**으로,
사용자가 쓴 판본을 **실제로 컴파일해 바이너리에서 문자열을 뽑았다:**

```
strings <빌드 바이너리> | grep CIPSTART
  →  AT+CIPSTART="TCP","192.168.35.21",9991      ← 앞 공백 없음 ✅

비교 · 결함이 있던 08-15 실장본(플래시 덤프):
     AT+CIPSTART="TCP"," 192.168.35.21",9991     ← 공백 하나
```

**그러므로 지금 보드는 DNS Fail 결함을 안고 돌지 않는다.** 사용자가 쓴 `조별과제샘플/client.ino`
(fa52a51 커밋본)에 수정이 들어 있다. 근거는 `client.ino:90`(`"192.168.35.21"` — 따옴표 안 공백 없음)과
`client.ino:676`의 문자열 리터럴 연결이고, 위 바이너리 추출이 그것을 실물로 확인해 준다.

빌드 수치(참고): **19706 / 32256 (61%)** · RAM **1017 / 2048 (49%)**.

## 2. ★ 덤으로 확인한 것 — **집계기를 고칠 필요가 없다**

펌웨어가 통째로 바뀌었으니 프레임 형식이 달라졌을 위험이 있어 대조했다. **같다.**

- 형식: `S,seq,occ,res,uptime,DEVICE_ID[,tmask]` — 두 판본 동일
- `uptime` = `millis()/1000` = **Uno 시간** — 두 판본 동일
  (옛판 `조별과제샘플/client.ino:1225-1232` · EspLink 판 `arduino/client/client.ino:207,210`)

> 즉 **"uptime 붕괴 = Uno 재부팅" 규칙과 monitor 의 파서는 펌웨어 교체 뒤에도 그대로 유효하다.**
> 이걸 확인 안 했으면 monitor 가 다음 집계에서 조용히 틀린 값을 낼 수 있었다.

## 3. `arduino/INTERVENTIONS.md` 갱신 (요청한 4가지 전부)

- **문서 맨 위에 "지금 칩에 무엇이 올라가 있나" 절을 신설**했다. 두 판본 비교표(19706/61% vs
  12052/37%)와 위 공백 판정을 넣었고, **REQ-0100·0104 의 hex 증명을 "칩 = EspLink 판"으로
  인용하지 말라**는 경고를 달았다.
- 개입 표에 **15:26~ 사용자 물리적 탈착 반복(리셋 유발 다수)** 과 **사용자 재플래싱** 항목 추가.
- **오염 경계 15:26** 을 명시하고, 살릴 수 있는 구간은 **11:26~15:26** 이라고 적었다.
- **"15:30 미스터리는 안 풀렸다" 경고를 해제**하고 종결 절로 바꿨다. 원인은 물리적 탈착이며
  **캐패시터를 키우지 말 것**을 근거와 함께 박아 뒀다(같은 100µF 로 4시간을 버틴 것이 정상 동작이었다).

## 4. 다른 문서의 유효기간 표시

  대조 대상이 교체된 것"이라고 명시. 지우지 않았다.

  적고, **현재 장치 상태의 최신 원본은 INTERVENTIONS.md** 라고 안내.

## 5. 보드 접촉 — 계속 보류 중

**업로드·포트 열기 전부 하지 않았다.** 위 검증은 전부 `/tmp` 빌드와 파일 읽기로 했고 보드에
접촉하지 않았다. `arduino-cli board list` 조차 돌리지 않았다.

**재개 시 첫 순서가 "칩에 무엇이 있는지 확인"이라는 것에 동의한다. 그 준비를 미리 해 뒀다:**
기대 바이너리를 `/tmp/oldverify/out/` 에 빌드해 뒀으므로, 접촉이 허용되면
**플래시를 덤프해 이것과 대조**하면 된다. 일치하면 사용자가 구운 것이 이 커밋본임이 확정되고,
불일치하면 커밋되지 않은 다른 판본을 구운 것이다 — **덮어쓰기 전에 그것부터 알아야 한다.**
⚠ 단 덤프 자체가 보드 리셋을 일으키므로 **monitor 와 시각을 맞춘 뒤에** 한다.
