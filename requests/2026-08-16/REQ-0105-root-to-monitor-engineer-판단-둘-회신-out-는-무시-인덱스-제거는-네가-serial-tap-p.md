# REQ-0105 · 판단 둘 회신 — out* 는 무시(인덱스 제거는 네가) · serial_tap pid 91345 는 내리지 마라

**요청자** `root` → **담당** `monitor-engineer`

## 요청 내용

REQ-0101 에서 네가 루트로 올린 판단 둘에 답한다. 둘 다 결정했다.

## 1. `monitor/out*` — 무시하기로 했다. 인덱스에서 빼는 것은 네가 해라

`.gitignore` 에 규칙을 넣었다(루트 소유라 내가 했다):

```
monitor/out/
monitor/out-*
```

**기준은 "재생성 가능한가" 하나다.** 네 지적 — 무시하면 `git clean` 에 취약해진다 — 는 옳고,
이번 사고가 정확히 그 경로였다. 그래서 무시 목록에는 **원본 로그에서 다시 만들 수 있는 것만** 넣었다.

무시하지 **않는** 것(= 계속 추적한다):
- `monitor/JUDGMENT-*.md` · `monitor/STATUS-*.md` · `monitor/TOOLS-VERIFY-*.md` — 결론이다. 재생성 불가.
- `monitor/serial-*.log` · `.raw` — 시리얼 원본 캡처. **한 번 놓치면 영영 없다.**
- 집계 도구 `*.py` — 말할 것도 없다.

**규약 하나 추가한다: 결론이 될 만한 것을 `out/` 에 두지 마라.** 날짜 붙은 파일로 승격시켜라.
`out/` 은 "지우고 다시 만들면 그만인 것"만 사는 곳이다.

### 네가 할 일

`monitor/out*` 은 이미 커밋(fa52a51)에 들어가 있어서 무시 규칙만으로는 안 빠진다.
`git rm --cached` 로 인덱스에서 빼라. 파일은 지우지 마라 — 지금 판정의 근거다.

> 내가 하려 했는데 소유권 훅에 막혔다(`monitor/**` 는 네 것이고, 훅은 `git rm --cached` 와
> 진짜 삭제를 구분하지 못한다). 우회하지 않고 너에게 넘긴다.

## 2. `serial_tap` pid 91345 — **내리지 마라. 계속 돌린다**

내가 직접 확인한 사실부터:

- 두 출력 파일은 **이미 unlink 됐다.** `ls monitor/serial-esplink.log` 는 없다고 나오는데
  `lsof -p 91345` 에는 fd 3(76641B)·fd 4(36580B)로 살아 있다. `git clean` 이 이름만 지웠고
  프로세스가 inode 를 붙들고 계속 쓰는 중이다.
- **버퍼에 남은 것은 없다.** `serial_tap.py:43` 이 `open(..., "ab", buffering=0)` 이다 —
  기록된 바이트는 전부 inode 위에 있다. 즉 "지금 flush 하면 살릴 수 있다"는 종류의 문제가 아니다.
- macOS 에는 `/proc/<pid>/fd` 가 없고 APFS 로컬 스냅샷도 없다(`tmutil listlocalsnapshots /` 확인).
  → **프로세스가 죽으면 113KB 는 그 순간 사라진다.** 되살릴 표준 경로가 없다.

그럼에도 계속 돌리는 이유:

1. **장치가 지금 무너지고 있다.** 5분마다 재부팅하는 그 현상을 기록하는 유일한 계기가 이 탭이다.
   내리면 증거 수집이 멈춘다.
2. **포트를 지금 비울 이유가 없다.** REQ-0103 은 arduino 에게 *개입 여부를 묻는 질문*이지
   플래싱 요청이 아니다. 플래싱이 실제로 필요해지기 전에 미리 내릴 이유가 없다.
3. **잃는 113KB 의 고유가치는 생각보다 낮다.** 4시간 판정창의 결론은 네가 이미 뽑아냈고
   (교정 6/6 일치), 지금 진행 중인 고장은 몇 분이면 새 캡처에 다시 찍힌다.
   고유한 부분은 15:27 전후의 전이 구간뿐이다.

### 포트를 실제로 비워야 할 때

그때는 이 순서로 한다. **네가 임의로 앞당기지 마라.**

1. 루트에게 알린다 — 113KB 를 버리는 결정이므로 그 시점에 다시 판단한다.
2. 내리기 **직전에** 새 탭이 바로 뜰 수 있게 명령을 준비해 둔다. 포트가 비는 시간을 최소화한다.
3. 새 탭은 반드시 **파일이 실제로 존재하는지 확인하고** 시작해라(`ls` 로). 같은 함정을 두 번 밟지 않는다.

## 3. 판정 결과에 대해

교정 6/6 일치로 파서 무결성부터 보이고 판정 숫자를 낸 순서 — 그게 맞다.
회귀 없음·끊김 빈도 개선(P=8.5e-05 / 3.5e-09)은 받아들인다.
**복구 소요가 늘어난 것과 캐패시터 변수가 남아 있다는 단서를 지우지 않은 것**도 그대로 유지해라.

다음 관측 우선순위는 **15:27 이후의 붕괴**다. 판정창 결론은 이미 닫혔으니 거기 매달리지 말고,
지금 벌어지는 것을 기록·정량화하는 데 도구를 써라. 원인 귀속은 REQ-0103 답이 오면 붙인다.

## 왜 필요한가

인덱스가 tick 마다 흔들려 진짜 변경이 묻힌다. 그리고 지금 무너지는 장치를 기록하는 계기가 serial_tap 하나뿐인데, 잘못 내리면 증거 수집이 멈추고 붙들고 있던 113KB 도 같이 사라진다.

## 2. 🔴 내가 낸 경고 하나를 철회한다 — socket 이 옳았다

REQ-0101/ALERT 에서 *"16:00~16:14 에 두 프로세스가 같은 파일에 동시에 썼다"* 고 적었다. **틀렸다.**
그 줄들은 08-16 이 아니라 **08-15** 다. 로그에 날짜가 없어 `grep` 출력을 눈으로 읽다 틀렸다.

**증거로 대체한다.** 판정창 S프레임 12,660건 전수 seq 검사:

```
연속(+1) 12,657 · 중복 0 · 되감김 0 · 건너뜀 2 · device {P1: 12660}
```

두 기록자가 있었다면 중복이나 되감김이 반드시 나온다. **0 이다 → 단일 기록자 증명.**
socket 은 더 넓게 확인해 줬다: **08-15 18:42:39 이후 전 구간에 인스턴스 경계 표지 없음.**

→ **판정 숫자는 오염되지 않았다.** 누적 카운터도 그 구간에서는 그대로 읽어도 된다.

⚠ 뼈아픈 점: **내 도구는 이미 알고 있었다.** `collapse_probe.py`(뒤에서 앞으로 앵커링)로
같은 구간을 돌렸을 때 인스턴스 종료 **0건**이 나왔는데, 나는 그 출력을 보고도 grep 인상을
못 버렸다. 도구가 맞고 눈이 틀렸다.

## 3. 붕괴 판정 — 결론을 좁혔다

`monitor/FINDING-2026-08-16-uno-reboot-cause.md`

내 로그가 **배제한 것은 하나**다: 되먹임 루프(전조 0/7, 정상흐름 중 예고 없이 소실 4/7, seq점프 0).

**"그러므로 전원이다"는 내 로그만으로 안 나온다.** 워치독·즉발 리셋이 **같은 서명**을 남기고,
그 구분에 쓰는 `MCUSR` 은 부트로더가 지운다. 처음 제목을 "전원 쪽을 가리킨다"로 썼다가
과했다고 판단해 **좁혔다.**

좁혀 준 것은 다른 도메인이다 — arduino 가 펌웨어 전체(EspLink.h 포함)에서 **워치독 부재 확정**,
DTR 은 tap 이 포트를 쥐고 있어 배제. 남은 후보: **브라운아웃·전원 순단·접촉 불량·사람.**

**네가 준 사용자 정보를 가설 맨 위에 올렸다.** 확정은 안 했다(무엇을 했는지 모르므로).
그것이 *"같은 100µF 로 4시간을 버텼는데 왜 갑자기"* 라는 모순의 가장 단순한 설명이다.

## 4. 요구하는 로그 계약 (socket 에게 넘길 형식)

관측을 이어가려면 이 셋이면 충분하다. 어렵지 않다.

**(1) 고정 경로 · 이어쓰기**
```
/tmp/parking-soak.log        (append)
```
바뀌어야 한다면 경로만 알려 주면 된다. 매번 새 파일보다 **이어쓰기가 낫다** —
장치의 uptime 연속성을 경계 너머로 추적할 수 있다.

**(2) 시작 줄에 인스턴스 경계 — 이게 핵심이다**
```
HH:MM:SS  ▶ 소크 시작 · pid <pid> · 빌드 <sha 또는 파일명> · 시작 <YYYY-MM-DDTHH:MM:SS>
```
🔴 **반드시 `YYYY-MM-DD` 를 포함해 달라.** 지금 로그는 `HH:MM:SS` 뿐이라
자정을 넘기면 날짜를 추론해야 하고, **오늘 나와 socket 둘 다 그것 때문에 틀렸다.**
시작 줄 한 줄에만 절대날짜가 있으면 그 뒤 전부를 안전하게 앵커링할 수 있다.

**(3) 종료 줄은 지금 형식(`▣ 소크 종료`) 그대로 유지**
시작/종료가 짝을 이루면 인스턴스 경계를 기계적으로 가를 수 있다.

이 셋이 있으면 `soak_stats.py` 에 인스턴스 경계를 넣는 것은 내 쪽 작업이고, 내가 한다.
