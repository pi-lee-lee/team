# 🔴 즉시 작업 정리 — 사고가 났다. 사용자가 곧 재기동한다

## 무슨 일이 있었나

`git clean` 계열 작업으로 **추적되지 않는 파일이 전부 삭제됐다.** 확인된 피해:

```
requests/2026-08-15/          통째로 삭제 (REQ-0055~0092 전부)
requests/2026-08-16/          1개만 남음
monitor/                      비어 있음 (산출물·도구 전부)
조별과제샘플/server_*.h        삭제 (server_wire.h·server_seam.h·server_device.h)
.claude/hooks/req_protocol_guard.py   삭제됨 (루트가 복구)
서버 프로세스                  죽음
시리얼 캡처                    죽음
```

원인 후보: `.gitignore` 44행 `조별과제샘플/server_*` 가 리팩터링 산출물을 통째로 무시한다.
그래서 그 파일들이 **추적되지 않는 상태**였고, clean 에 함께 쓸려 나갔다.
(REQ-0054 로 socket-engineer 가 이 문제를 이미 지적해 뒀다.)

## ⚠ 살아 있는 것 — 여기에 기대라

```

```

## 지금 할 일 — 딱 이것만. 다른 작업 시작하지 마라

**1) 네 문맥에만 있는 것을 파일로 내려라.**

재기동하면 네 머릿속은 0 이 된다. 그리고 방금 파일이 대량으로 사라졌으니
**너만 알고 있는 것이 진짜로 유일본**일 수 있다. 다음을 적어라:

- 지금까지 한 일과 **결론**(수치·판정·근거)
- **다시 만들어야 할 산출물 목록** — 무엇이 사라졌고 어떻게 복원하는가
- 재기동 뒤의 네가 이어받을 **다음 한 걸음**
- 빌드/시스템이 **동작하는 상태인가, 깨진 상태인가**

**2) 어디에 적는가 — 이번엔 안전한 곳에 적어라.**

`requests/` 아래 REQ 파일에 적되, **그 파일도 untracked 라 또 지워질 수 있다.**
그래서 **`docs/` 아래에도 사본을 남겨라**(`docs/` 는 커밋돼 있고 clean 대상이 아니다):

```
docs/handoff-<네이름>-2026-08-16.md
```

⚠ `docs/*` 는 루트 소유다. 네가 못 쓰면 **REQ 본문에 전문을 적고 나에게 알려라. 내가 옮긴다.**
`docs/net/**` 는 socket-engineer 소유이므로 socket 은 거기 써도 된다.

**3) 파괴적 명령을 절대 쓰지 마라.**

`git clean`·`git checkout -- .`·`rm -rf` 를 이 저장소에서 실행하지 마라.
지금 상태에서 한 번 더 나면 복구 불가다. `.gitignore` 문제는 **루트가 사용자와 정리한다.**

**4) 끝나면 알려라.**

```
team/bin/req.sh progress <ID> --by <너> --note "정리 완료 · 인수인계 <경로>"
```

사용자가 그것을 보고 재기동한다. **네 회신 전에는 재기동하지 않는다.**

## 하지 말 것

- 새 작업 착수 금지. 지금은 **건지는 시간**이다.
- 서버·시리얼 캡처를 되살리지 마라 — 재기동 후 루트가 순서를 정해서 한다.
- 사라진 파일을 급하게 재작성하지 마라. **무엇이 사라졌는지 목록만** 남겨라.
  복원은 재기동 후 순서를 잡아서 한다.

### ⚠ 먼저 알아야 할 전제 — 요청의 핵심은 수행 불가였다

**"재기동 전 문맥을 내려라"는 이미 늦었다.** 이 응답을 쓰는 세션은 **이미 재기동된 새 세션**이고,
사고 이전 socket-engineer 의 문맥은 **회수 불가로 소실**됐다. 기억에서 건질 것은 0 이다.

그래서 요청을 **적응시켜** 수행했다 — 완료 기준 4개 중 문맥 덤프를 뺀 나머지 3개
(사라진 산출물 목록 / 다음 한 걸음 / 동작 여부)는 **생존 증거에서 재구성 가능**했고, 그렇게 했다.
문서의 모든 줄은 지금 실행한 읽기 전용 관측의 출력이다. **기억을 재구성한 문장은 한 줄도 없다.**

### 핵심 4가지

**1) 🔴 빌드가 깨져 있다 — 가장 중요**
`server.cpp:191` 이 `#include "server_device.h"` 하는데 그 헤더가 삭제됐고
**체크포인트 ref 에도 없다**(`git ls-tree` 로 확인). **git 어디에서도 파일 자체를 못 되찾는다.**
→ 지금 `server.cpp` 는 **컴파일되지 않는다.** (없는 include 로부터의 추론이다 — 빌드는 안 돌렸다.
다만 `SHA1`·`base64` 정의가 파일에 없는 것까지 확인했으니 헤더 없이 될 여지는 없다)
_왜 체크포인트에 없는지는 아래 "추가 검증 2건" 에서 추정으로 낮췄다._

**2) 서버는 죽지 않았다 — 피해 목록 정정**
`pid 36998` `/tmp/srv_parking` 이 **8/15 18:42 기동 이후 21시간째 생존 중**이다.
9991·9900·5500 전부 LISTEN, IP 는 새 대역 192.168.35.21, 웹 9900 은 `HTTP 200` (111,798 bytes).
소크 로그도 계속 갱신된다. REQ 본문의 "서버 프로세스 죽음"은 **사실과 다르다.**

**3) 🔴 그 살아있는 바이너리는 재현 불가능한 유일본이다**
바이너리 mtime 8/15 18:42 · 워킹트리 `server.cpp` mtime 8/16 12:01(HEAD 대비 수정 상태).
**바이너리는 현재 소스의 산출물이 아니고, 현재 소스는 빌드도 안 된다.**
→ **pid 36998 을 죽이면 되살릴 수단이 없다.** 헤더 복구 전까지 재기동 금지.
백업(`cp /tmp/srv_parking /tmp/srv_parking.bak-0816`)을 권하지만, "되살리지 마라" 지시 범위로 보고
**실행하지 않고 루트 판단을 기다린다.**

**4) 아두이노 링크가 44초 주기로 헛돌고 있다**
TCP 연결은 매번 성립하는데 7초 안에 유효 프레임이 0줄이라 서버가 끊는 패턴이 무한 반복.
프레임 62551 에서 정지, 🔴미복구 1건이 사고 직후(15:30경)부터 20분 넘게 진행 중.
**서버 수신 경로는 규약대로 정상 동작 중이고, 말단이 안 보내고 있다.**
말단은 arduino-engineer 소유라 손대지 않았다. 원인은 **미검증 추정**만 있다.

### 복원 경로 (조사만 함 — 복원은 실행하지 않았다)

- **체크포인트 `refs/claude/checkpoint-7fb8eb20`(8/15 16:06)에서 그대로 복구 가능** —
  `net/swap_server.sh` · `soak_probe.py` · `soak_report.py` · `reconnect_stats.py` ·
  `uptime_anchor.py` · `zombie_probe.py` **6종**. (현재 `net/` 에서 전부 사라진 상태)
- **`server_device.h` 는 파일은 못 살리지만 내용은 재추출 가능** —
  뜯기 전 모놀리식 판이 `HEAD`(6e3f63c)에 남아 있다. SHA1 122행 · base64 181행 ·
  `ws_accept` 196행 · 자가검증 벡터 1402행. 완료 판정은 `./server --selftest` 통과.
- **루트에게 참고**: 같은 체크포인트에 `requests/2026-08-15/` 도 남아 있을 가능성이 높다.
  **추정이다** — 확인은 안 했다. `git ls-tree -r --name-only refs/claude/checkpoint-7fb8eb20` 로 조회된다.

### ✅ `.gitignore` 는 이미 고쳐져 있었다 — 내 초안 권고를 철회한다

처음엔 "헤더 복구보다 `.gitignore` 정정이 먼저"라고 썼는데, **직접 읽어 보니 루트가 이미
고쳐 놨다.** 문제의 `조별과제샘플/server_*` 는 `server_test`·`server_*.exe`·`server_*.o`·
`server_*.out` 로 좁혀졌고 사고 경위 주석까지 붙어 있다(43~50행).
→ **지금 `server_device.h` 를 만들면 추적된다. 선행 조건 없음. 바로 복구해도 된다.**

내 초안이 틀린 이유가 곱씹을 만하다 — **REQ-0055 본문을 검증 없이 인용했기 때문이다.**
같은 본문의 "서버 프로세스 죽음"도 거짓이었다. 사고 직후 작성된 피해 목록은 그 자체가
검증 대상이다. 문서 §6 에 이 교훈을 남겼다.

남은 노출: 인수인계 문서와 복원 예정인 `net/` 도구 6종이 아직 untracked 다 — **커밋을 권한다.**

### 추가 검증 2건 (초안 이후)

- **복구 계획 확인됨**: 워킹트리 `server.cpp` 에 `SHA1`·`base64` **정의가 없고** `ws_accept`
  **호출부만 2곳**(1532·2106행)이다 → HEAD 에서 뽑아 헤더로 만들어도 **중복 정의가 안 난다.**
  또한 로컬 include 는 191행 하나뿐이라 **당장 필요한 헤더는 `server_device.h` 하나**다
  (`server_wire.h`·`server_seam.h` 는 지금 빌드에 불필요).
- **"체크포인트에 없는 이유"는 추정으로 낮춘다**: `.gitignore` 탓일 수도 있지만, 체크포인트
  ref 가 전부 8/15 인데 헤더 리팩터링은 8/16 12:01 이라 **애초에 그 이후 스냅샷이 없다**는
  설명도 똑같이 들어맞는다. **복구 불가라는 결론은 어느 쪽이든 동일**하다.

### 이 세션이 하지 않은 것

새 작업 착수 · 서버/시리얼 캡처 재기동 · 사라진 파일 복원 · 파괴적 명령 — **전부 하지 않았다.**
실행한 것은 읽기 전용 관측뿐이고, 만든 파일은 인수인계 문서 하나다.

### 상태를 `done` 이 아니라 `claimed` 로 두는 이유

REQ 본문의 완료 지침이 `done` 이 아니라 `progress` 다. 그리고 원래 요구된 산출물(소실된 문맥)은
**끝내 회수하지 못했다.** 그러니 내가 닫지 않고 **루트가 판단해서 닫는 것**이 맞다.
