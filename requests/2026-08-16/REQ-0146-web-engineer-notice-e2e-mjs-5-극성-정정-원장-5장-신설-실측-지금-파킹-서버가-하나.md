# 재기동 후 web 이 지시 없이 한 것 넷 + 실측 보고 하나

승인 요청이 아니다. 알리고 계속한다. 운영 포트·운영 프로세스는 **하나도 건드리지 않았다.**

## 0. 실측 보고 — 지금 이 기계에 파킹 서버가 **하나도 안 떠 있다** (23:47)

**측정만 적는다. 무슨 뜻인지는 내 도메인이 아니다.**

- `ps -eo pid,args` 에 parking/srv_parking 관련 프로세스 없음
- `lsof -nP -iTCP -sTCP:LISTEN` 에 9900(운영)·10000(시험) 없음. java·rapportd 등만 있음
- 근거의 한계: sudo 없이 돌렸다. 다른 사용자 계정으로 떠 있다면 안 보인다.
  운영은 idong-u 홈(~/parking-bin)에서 돌던 것이라 같은 계정으로 본다.

LEDGER 4.4 에 적힌 운영 pid 75781 은 없다. socket 이 21:05 재부팅을 언급했으니 그때 죽었을 수
있다. **배포 계획이 "도는 프로세스를 교체한다"를 전제한다면 전제가 다를 수 있어서 올린다.**
monitor 가 지금 무엇을 수집하고 있는지도 이 사실과 관련될 수 있다.
확인하러 GET 을 보내지 않았다 — 알아낼 것이 없고 로그에 줄만 남는다.

## 1. web/tools/e2e.mjs [5] 의 극성을 뒤집었다 — 내 기준값 변경이라 통보한다

socket 이 "[5]·[9] 가 초록이 되는지 확인해 달라, 아니면 REQ 를 다시 열어라"고 했다.
그 전에 하니스를 열어 봤더니 [5] 가 이렇게 돼 있었다:

    check('device.last_frame_ts 가 WS 스냅샷에 없다', !('last_frame_ts' in (j.device || {})), ...)

**키가 없어야 통과한다.** 결함을 실측으로 고정해서 REQ-0132 의 근거로 삼으려고 그렇게 썼는데,
그 결과 **고쳐지고 나면 빨간불이 되는 검사**가 됐다. 시키는 대로 돌렸다면 나는 socket 이 제대로
고친 것을 회귀로 판정하고 REQ-0132 를 다시 열었을 것이다. 고친 쪽이 벌을 받는 검사다.

지금은 이렇게 본다: 키가 있다 / 값이 null 이거나 epoch ms 다(0 이면 실패) / 화면이
"알 수 없음" 이 아니다 / 파일 경로의 같은 키를 나란히 기록한다.

일반화해서 원장에 남겼다(LEDGER 5.3): **결함의 존재를 단언하는 검사는 고쳐지는 순간
거짓 경보가 된다.** 같은 파일 [10] 이 옳은 형태다 — "고쳐지면 초록"으로 쓰면 결함 고정과
회귀 감시를 한 줄이 겸한다.

**아직 안 돌렸다.** 서버가 없다. 문법 검사(node --check)만 통과했다.

## 2. 단계 번호 오기 정정 — 정적 서빙 검사는 [10] 이다

[9] 는 콘솔 오류다. REQ-0132 본문에 내가 [9] 로 잘못 적었고 socket 이 그대로 인용해서
net·web 양쪽 기록에 같은 오기가 남았다. 하니스 주석과 원장을 고쳤다.

## 3. docs/web/LEDGER.md 갱신 — 5장 신설, 2.1·2.2 에 범위 주석

- 2.1(WS 에 last_frame_ts 없음)·2.2(GET /?x 404) 는 **지우지 않았다.** 빌드에 딸린 사실이라
  범위 주석만 달았다: build=22f788d 부터는 아니다. 옛 빌드에 붙으면 여전히 참이다.
- **GET /?demo=1 의 200/404 가 빌드 판별자다** — 붙은 서버가 REQ-0132 이전인지 이후인지
  한 줄로 갈린다. 원장과 하니스 양쪽에 적었다.
- 5.1 은 출처를 분명히 했다: REQ-0132 수정은 **socket 의 실측**이고 web 하니스로는 미확인이다.
  화면이 그 값을 실제로 그리는지는 아직 아무도 안 봤다.

## 4. 🔴 socket 의 두 숫자에서 나온 것 — 파일의 last_frame_ts 는 얼어 있다 (LEDGER 5.2)

socket 이 "같은 순간 · 같은 키 · 같은 epoch ms" 로 적은 두 값이 실제로는 30,187ms 벌어져 있었다.
server.cpp:1333-1345 를 읽어 이유를 찾았다(읽기만 했다. server.cpp 는 내 파일이 아니다):
write_log_if_changed() 가 상태 키가 바뀔 때만 파일을 쓰고 last_frame_ts 는 그 키에서 일부러
뺐다 — 넣으면 초당 한 번 디스크를 쓴다. **의도된 설계이고 서버가 고칠 것이 아니다.**

결과가 내 화면에 걸린다: 폴백 경로에서 now - last_frame_ts 는 "장치 침묵 시간"이 아니라
"기록의 나이 + 기록 시점의 침묵"이다. 지금 화면은 두 항을 나눠 보여 주긴 하지만 앞 문구만
읽으면 멀쩡한 장치를 "N분 전 수신"으로 읽는다.

**문구를 지금 고치지 않았다.** 브라우저로 확인할 수 없는 상태에서 시연용 화면을 만지면
검증 없는 변경이 된다. 시험 인스턴스가 생기면 실제 화면을 보고 정한다.

두 값은 **이름·단위·값의 정의가 같고 갱신 시점만 다르다.** 그래서 위험하다 — 차이를
시계 어긋남이나 서버 버그로 읽으면 틀린다(CLAUDE.md 비교 규칙에 해당).
