# REQ-0122 · 화면이 서버에서 무엇을 읽는지 목록화하라 — 곧 오프라인→무프레임 이름이 바뀐다 (트래픽 금지)

**요청자** `root` → **담당** `web-engineer`

## 요청 내용

**서버 출력 형식이 오늘 세 번 바뀌었고, 앞으로 한 번 더 바뀐다.** 화면이 그걸 읽고 있다면
지금 확인해야 한다 — 바뀐 뒤에 알면 시연에서 알게 된다.

## 배경 — 오늘 서버에 일어난 일

로그·상태 출력에 계약이 생겼고(`docs/net/server-log-contract.md` v1.0 → `logfmt=3`),
카운터가 추가됐다. 그리고 **아직 안 바뀐 것이 하나 남아 있다:**

- **`오프라인` → `무프레임` 으로 이름이 바뀐다.** 이유는 그 이름이 현실을 잘못 불러서다 —
  "오프라인"으로 세던 것의 상당수가 장치 고장이 아니라 **링크 계층 재접속**이었다
  (기준선 13.92시간의 새 연결 36건 중 35건). 측정한 것을 이름으로 삼고 해석은 옆 칸에서 한다.
- 전환 절차는 **읽는 쪽이 먼저 양쪽을 받고 → 쓰는 쪽이 바꾼다.** monitor 는 1단계를 끝냈다.
  **네가 읽고 있다면 너도 그 1단계가 필요하다.**

## 이 요청 — 확인만 해라. 고치는 것은 그다음이다

1. **화면이 서버에서 무엇을 받는가**를 목록으로 만들어라. 필드명·프레임 종류·엔드포인트.
   폴백 경로(`device_online`·`last_frame_ts` 등)도 포함한다.
2. 그중 **이름이나 형식이 바뀔 예정인 것**이 있는지 대조해라. 기준은
   `docs/net/server-log-contract.md` 와 `docs/net/LEDGER.md`(socket 이 작성 중).
3. **깨질 것이 있으면 구/신 양쪽을 받도록 고쳐라.** 없으면 "없음"이라고 보고하면 된다 —
   그것도 값어치 있는 답이다.

## 🔴 지금 하지 말 것 — 트래픽을 만들지 마라

**monitor 가 관측 창(A)을 돌리고 있다.** 약 4시간짜리이고 지금 0.2h 다.
브라우저에서 예약을 걸거나 장치에 닿는 요청을 보내면 **그 창을 오염시킨다.**

- 서버에 연결해 화면을 띄우는 것까지는 괜찮다(수동적 구독).
- **하행 명령(예약·취소)을 걸지 마라.** 그건 장치까지 내려가고 ESP 를 바쁘게 만든다.
- 종단 시험(브라우저→서버→장치)은 **A 창이 끝난 뒤 별도 요청으로 준다.** 그때가 네 차례다.

판단이 서지 않으면 트래픽을 만들기 전에 물어라.

## 참고 — 이미 확인된 것

- **하행 경로 자체는 동작한다.** socket 이 서버에서 직접 5건 내려 **5/5 도달, ACK 5/5**,
  그리고 예약 마스크가 명령대로 정확히 바뀌는 것까지 확인했다. 남은 것은 **브라우저 구간**이다.
- **지금 칩은 `R·C·T·M` 만 받는다. `W` 프레임은 없다.** 옛 계열 펌웨어가 올라가 있다.
  화면이 `W` 를 전제로 만들어졌다면 그것부터 보고해라.

## 왜 필요한가

서버 출력 형식이 오늘 세 번 바뀌었고 지표 이름이 한 번 더 바뀐다. 화면이 그걸 읽고 있다면 바뀐 뒤에 알게 되고, 그때는 시연장이다.

## 대상 파일

- `조별과제샘플/index.html`
## 완료 기준

화면이 읽는 서버 필드·프레임·엔드포인트 목록 · 계약과 대조해 깨질 항목 판정 · 깨질 것이 있으면 구/신 양쪽 수용하도록 수정 · 없으면 '없음' 보고 · A 창 동안 하행 트래픽 미발생

## 1. 화면이 서버에서 받는 것 — 전수 목록

입력 경로는 **둘뿐**이다. 서버 로그 파일은 어느 경로로도 읽지 않는다.

### A. WebSocket `ws://<host>:9900/ws` — JSON push

| 프레임 | 화면이 읽는 필드 |
|---|---|
| `type:"snapshot"` | `ts` · `device.online` · `device.device_id` · `device.uptime` · `device.seq` · `device.last_frame_ts`\* · `test_mode.armed` · `test_mode.override_count` · `slots[].id/occupied/reserved/user_id/reserved_at/overridden` |
| `type:"ack"` | `rid` · `slot` · `result`(0–5) · `message` |
| `type:"error"` | `rid` · `code` · `message` |
| 그 밖의 `type` | **조용히 무시**한다 (새 프레임이 생겨도 안 깨진다) |

\* `last_frame_ts` 는 코드가 읽지만 **WS 스냅샷에는 그 키가 없다**(`server.cpp:1174-1178` 확인).
항상 "모름"으로 떨어진다 — 파일 경로 전용 필드다.

화면이 표를 들고 있는 문자열 상수:
`error.code` = `device_offline` · `ack_timeout` · `bad_request` · `rate_limited`
(모르는 code 가 오면 서버가 준 `message` 를 그대로 띄운다 — 표에 없어도 안 깨진다)

### B. HTTP GET `data_log.json` — 3초 폴링 폴백 (5초 상한)

최상위 JSON 배열, `[0]` 이 최신. 읽는 필드:
`ts` · `device_id` · `uptime` · `seq` · `device.online` · `device.last_frame_ts` ·
`test_mode.armed` · `test_mode.override_count`(← 이번에 고친 것) · `slots[].id/occupied/reserved/overridden`

> ⚠ **최상위 `occupied`/`reserved` 비트열 문자열은 읽지 않는다.** 화면은 `slots[]` 만 본다.
> 서버가 지금 둘 다 쓰므로 문제는 없다(`server.cpp:1259, 1269-1276`). 다만 **`slots[]` 를 빼는
> 변경이 오면 화면은 10칸 전부 '상태 미상'이 된다** — 오류 없이. 계약 변경 후보로 기록해 둔다.

### C. 브라우저 → 서버 (참고)

JSON 동사만 보낸다: `reserve` · `cancel` · `test_arm` · `test_disarm` · `test_set` · `test_clear` · `sim_step`.

## 2. `오프라인` → `무프레임` 대조 결과 — **없음**

근거:

- 바뀌는 이름의 실제 위치는 `server.cpp:808` 의 소크 요약 줄 `" · 오프라인 " + offline_episodes + "회"` 다.
  그 줄은 stdout/로그 파일로 가고, 소비자는 monitor 의 로그 파서다.
- 화면의 입력은 위 §1 의 두 경로뿐이고, **어느 쪽도 그 문자열을 담지 않는다.**

→ **화면에는 1단계(구/신 동시 수용)를 넣을 대상이 없다.** monitor 와 달리 화면은 이 전환에서 할 일이 없다.

### 다만 인접한 결합 둘을 보고한다 — 같은 개념, 다른 이름

| 화면이 잡고 있는 이름 | 어디 | 이름이 바뀌면 |
|---|---|---|
| `device_offline` (`error.code`) | WS §5.3 | **안전하게 열화.** 모르는 code 는 서버가 준 `message` 로 대체된다. 조치 불필요 |
| `device.online` (bool 필드) | WS + 파일 | 🔴 **조용히 열화.** boolean 이 아니면 모름으로 접혀 **센서 끊김 배너가 영영 안 뜬다.** 오류도 안 난다 |

위험한 쪽은 오류 코드가 아니라 **필드 이름**이다. → **REQ-0123** 으로 socket-engineer 에게
"개명이 전선 JSON 키까지 오는가, 온다면 확정된 새 문자열" 하나만 물었다.
새 이름을 **추측해서 넣지 않았다** — 지어낸 이름을 넣는 것은 CLAUDE.md 가 경고하는 함정 그대로다.
REQ-0122 는 그 답을 기다리지 않고 닫는다.

## 3. `W` 프레임 전제 — **없다**

화면은 전선 프레임을 **만들지 않는다.** JSON 동사를 보내고 문자 선택은 서버가 한다.
`server.cpp` 의 `send_ack(kind)` 는 `R`/`C`/`T`/`M` 뿐이고, `'W'` 는 `server.cpp` 전체 grep 0건이다.
지금 칩이 아는 말(`R·C·T·M`)과 정확히 일치한다. 펌웨어 계열이 바뀌어도 화면은 영향받지 않는다.

## 4. 고친 것 — 폴백이 주입값을 실측값처럼 그리고 있었다 (구/신 동시 수용)

이번 개명과 별개로, **계약과 화면이 이미 어긋나 있었다.**

**증상**: WS 가 끊겨 파일 폴백으로 넘어가면, 테스트 모드가 무장 중이어도 화면이
"알 수 없음"으로 표시하고 **주입된 칸에 빗금이 안 붙었다.** §12A.6("무장 중에는 놓칠 수 없는
표시가 있어야 한다")이 **폴백 경로에서만 안 지켜지고 있었다** — §9.1 개정 4(2026-08-14)가
파일에 `test_mode` 를 넣어 막으려던 바로 그 구멍이다. `device.online` 이 개정 9 에서 겪은 것과 같은 형태.

**원인은 두 군데였다** (한 쪽만 고치면 아무 효과가 없다):

1. `snapshotFromLog()` 가 `latest.test_mode` 를 **애초에 옮기지 않았다**
2. `normalizeSnapshot()` 이 `source === 'file'` 이면 **무조건 null** 로 접었다

**고침**: 판정 기준을 **경로(source)가 아니라 `test_mode` 키의 유무**로 바꿨다.

| 입력 | 전 | 후 |
|---|---|---|
| 개정 4 이후 파일 · `armed:true` | 알 수 없음 · 빗금 없음 | **무장 배너 + 주입칸 빗금** |
| 개정 4 이후 파일 · `armed:false` | 알 수 없음 | 해제됨 |
| 개정 4 **이전** 파일 (키 없음) | 알 수 없음 | 알 수 없음 *(그대로)* |
| WS (키 있음/없음) | *(그대로)* | *(그대로)* |
| 키는 있는데 값이 boolean 이 아님 | — | **모름** (해제로 단정하지 않는다) |

> WS 의미는 일부러 건드리지 않았다. 키가 없을 때 WS 는 종전대로 `false`, 파일만 `null` 이다 —
> 여기서 규칙을 통일하면 이 요청과 무관한 WS 동작이 조용히 바뀐다.

문구도 같이 고쳤다(이제 사실이 아니므로):
`"파일 폴백에는 무장 여부가 없습니다"` → `"이 기록에 test_mode 가 없습니다 (§9.1 개정 4 이전 형식)"`.
개정 9 때 `device.online` 문구를 고친 것과 같은 이유 — **모름의 원인은 경로가 아니라 그 기록의 형식이다.**

**바뀐 파일**: `조별과제샘플/index.html` (이 한 개)

## 5. 검증 — 무엇을 실제로 했고 무엇을 안 했나

🔴 **브라우저로 열어 보지 않았다.** 이 세션에 브라우저 조작 도구가 없다(ToolSearch 로 확인).
아래는 전부 **코드 수준 검증**이며, 화면에 실제로 어떻게 그려지는지는 확인하지 않았다.

- ✅ 인라인 스크립트 전체 구문 파싱 통과 (69,126자, `new Function` 컴파일)
- ✅ 바뀐 함수들을 **실제 파일에서 뽑아** node 에서 단언 11건 — 전부 통과
  (위 표의 모든 행 + 깨진 입력 2건: `test_mode:null`, `armed:"true"` 문자열)
- ✅ 생산자 쪽 대조: `server.cpp:1250-1276`(파일에 `test_mode` 를 실제로 쓴다) ·
  `1172-1197`(WS 스냅샷) · `808`(개명 대상 로그 줄) · `1200-1225`(ack/error)

**사람 눈으로 볼 검증은 데모 버튼으로 남겨 뒀다.**
`index.html?demo=1` → 「**§9.1 개정 4 폴백 + 무장(test_mode.armed) → A3 빗금**」 버튼.
무장 배너와 A3 의 `⚑ 주입값` 빗금이 뜨면 통과다. 안 뜨면 파일의 `test_mode` 를 다시 버리고 있는 것이다.
(옆의 「device 없는 옛 형식」 버튼과 번갈아 눌러 '무장됨' ↔ '알 수 없음' 이 갈리는지 본다)

## 6. 트래픽 — 만들지 않았다 ✅

A 창(monitor, 4시간) 동안 **서버·장치에 아무것도 보내지 않았다.** 브라우저조차 띄우지 않았다.
확인은 전부 파일 읽기와 node 로 했다.

참고로 `?demo=1` 은 검증에 써도 안전하다 — `transport.start()` 가 `connect()` 와 `startPolling()`
**앞에서 반환**하므로 WS 도 폴링도 열지 않는다. 종단 시험(브라우저→서버→장치)은 지시대로
**A 창이 끝난 뒤 별도 요청을 기다린다.**

## 7. 손대지 않고 기록만 남기는 것

- `ERROR_TEXT[code]` 가 `hasOwnProperty` 없이 조회한다. 서버가 낼 수 없는 code(`constructor` 등)
  에서만 이상 표시가 나므로 **이번 변경에 묶지 않았다** — 섞으면 무엇 때문에 깨졌는지 못 가른다.
- 화면이 파일의 최상위 `occupied`/`reserved` 비트열을 쓰지 않는다는 사실(§1.B 의 ⚠).
