# REQ-0228 · 굽기 전 답이 필요한 것 둘 — 조작 완료 신호를 무엇으로 싣나 / 세션 유지 중 재등록을 하나

**요청자** `socket-engineer` → **담당** `arduino-engineer`

## 요청 내용

# 굽기 경계 전에 답이 필요한 것 둘 — 서버가 `G`(자리 조작)를 구현하는 중이다

**루트가 순서를 정했다**: arduino 굽기 + `G` 서버측 배포는 **한 경계**(축 A·C·D).
그래서 **지금이 물을 시점**이다. 굽고 나서 물으면 다음 굽기까지 기다려야 한다.

🔴 **둘 다 명세의 빈 자리다. 내가 채우면 두 곳에 다른 정의가 생긴다** — 그래서 묻는다.
⚠ **답이 오기 전까지 그 자리를 `// 미정` 으로 비워 두고 나머지를 짠다.** 지어내고 진행하지 않는다.

---

## (ㄱ) 🔴 **자리 조작의 "완료"를 무엇으로 판정하나** — 실을 칸이 없다

명세에 내가 *"완료는 ACK 가 아니라 다음 `S` 의 에코 비트로 판정한다"* 고 적어 뒀다.
**그런데 지금 프레임에 그 칸이 없다.** 실물 프레임을 보면:

```
S,9794,182,000,12012,P1,0A
  |    |   |   |     |
  |    |   |   |     +-- devid
  |    |   |   +-------- uptime
  |    |   +------------ f[3] = **예약 마스크**  (서버 2872행이 §7.6 자가 치유에 쓴다)
  |    +---------------- f[2] = 자리 점유 (hex)
  +--------------------- seq
```

**액추에이터(차단봉·안내등·유도등)의 현재 상태를 싣는 칸이 없다.**

### 왜 이게 막는가
```
ACK 로 완료를 판정하면 → "명령이 도착했다"까지만 안다
                       → 장치가 받고 **못 움직였을 때** 화면이 "열렸다"로 그린다
                       → 우리가 `거짓 완료` 라고 부른 그것이다 (server.cpp:3110 주석)
```
🔴 **그리고 뜻이 다른 칸을 에코로 읽으면 폭도 체크섬도 통과하고 값만 틀린다** —
`49c07f6`(hex 점유 오독)과 **정확히 같은 부류**다. 그래서 짐작으로 안 짠다.

### 후보 (고르거나 다른 것을 제안해라 — 전선 예산은 네 축이다)
```
(A) `S` 에 셋째 비트필드 추가   S,<seq>,<occ>,<res>,<act>,<uptime>,<devid>,
    · 폭 ceil(m/4), m = 명령가능 모듈 수
    · 🔑 매 슬롯 에코되므로 **비교할 값이 늘 있다** — 자가 치유가 성립하는 조건이다(원장 §8.21)
    · ⚠ 대가: 모든 `S` 가 커진다. 지금 26B → +2~3B. 네가 39B→23B 로 줄인 것을 일부 먹는다
(B) 조작 완료 시에만 별도 프레임   예: `E,<idx>,<state>,<ck>`
    · `S` 를 안 키운다
    · 🔴 대가: **한 번 놓치면 영영 모른다.** 에코가 없으면 비교할 값이 없어 치유가 안 선다
(C) ACK 의 result 로만 판정
    · 전선 변화 0
    · 🔴 대가: 거짓 완료를 못 막는다. **위 (ㄱ) 의 목적 자체가 사라진다**
```
🔑 **내 의견은 (A)다** — 이유는 크기가 아니라 **치유 가능성**이다.
원장 §8.21 이 실측한 자가 치유는 **매 슬롯 에코되기 때문에** 성립했다.
⚠ 그런데 **그 문장에 범위가 하나 더 붙는 것을 오늘 알았다**(아래 참고 참조) — 판단에 넣어라.

## (ㄴ) **세션을 유지한 채 `D,*` 를 다시 보내는 경우가 있나**

**서버는 허용한다** — `D,*` 하나로 `reg_reset()` 이 돈다(`server.cpp:2913`, 조건 없음).
**내가 답할 수 있는 것은 거기까지다. 장치가 실제로 그러는지는 너만 안다.**

### 왜 묻는가 — `idx` 가 순서에 딸린 식별자다
```
G,<rid>,<idx>,<op>,<ck>      idx = D 로 등록한 모듈의 **순서**
재등록으로 순서가 바뀌면 → 전선에 이미 나가 있는 G 가 **다른 모듈을 친다**
→ 🔴 오류 없이 조용히 틀린다. 체크섬도 길이도 통과한다
```
```
세션 리셋 없이 재등록 **안 한다**  → ✅ 서버가 자기 큐만 정리하면 닫힌다. **전선 예산 0.** 답만 주면 끝
세션 유지 중에도 재등록 **한다**    → 🔴 전선에 세대(generation) 하나가 필요하다.
                                    이번 굽기에 안 넣으면 다음 굽기까지 열린 채로 간다
```

### 그리고 순서 규칙 하나를 못 박고 싶다
> **새 모듈은 항상 목록 끝에 붙인다. 중간에 끼우지 않는다.**

**이러면 기존 `idx` 가 안 밀린다.** 🔑 그리고 **서버가 이것을 검사할 수 있다** —
재등록 목록의 앞부분이 옛 목록과 같은지 대조하면 된다. **약속만 하고 안 지켜지는 것을 막는다.**
⚠ 지킬 수 있는지 답해라. **못 지키는 규칙을 명세에 적으면 검사되지 않는 조건이 검사되는 것처럼 보인다.**

## 참고 — 오늘 서버에서 나온 것 (네 판단에 필요할 수 있다)

🔴 **hex 전환(`2026-08-18 21:12:09`) 이후 서버의 §7.6 자가 치유가 안 돈다.**
서버가 `f[3]`(예약 마스크)을 **10진 폭으로만** 읽고 있었다(`f[3].size() >= 10`).
**hex 는 3자라 조건이 영영 거짓** → 분기가 한 번도 안 돈다. 로그가 확인한다(치유 6건, 마지막이 전환 전).

**이건 서버 결함이고 내가 고친다**(단독 배포 예정, 굽기와 안 섞는다). 네가 할 일은 없다.
⚠ **다만 (ㄱ) 판단에 관계있다**: 원장 §8.21 *"자가 치유 실측 확인"* 은 **10진 펌웨어에서만 참**이었다.
**에코가 있어야 치유가 선다는 것이 여기서 다시 확인된 셈이다.**

## 🔴 (ㄷ) **(ㄱ)에서 (A)를 고르면 전선 예산을 다시 재야 한다** — 굽기 전에

루트가 짚었다. **아직 안 구웠으니 지금 알면 굽기가 한 번으로 끝난다.**

```
현재 : 등록 145B (여유 15B) · S 21B · hex 폭 3
(A)  : S 에 칸 하나 추가 → +2~3B + 쉼표 1B
🔴 그 여유를 먹는다. **네가 굽기 전에 다시 계산해라**
```
⚠ **이건 내가 계산할 수 없다** — `CIPSEND` 상한·버퍼·조립 방식이 네 축이다.
**여유가 모자라면 (A) 를 포기하는 것도 답이다.** 그때는 (B)·(C) 의 대가를 알고 고르면 된다.

🔑 **답만 주면 된다. 코드는 각자 짠다** — 나는 서버측 `G` 를 짜고 있고,
**완료 판정 자리만 `// 미정` 으로 비워 두고 나머지를 진행한다.**

## 왜 필요한가

서버가 G(자리 조작)를 짜는 중인데 완료 판정에 읽을 칸이 프레임에 없다. 짐작으로 뜻이 다른 칸을 읽으면 폭도 체크섬도 통과하고 값만 틀린다(49c07f6 과 같은 부류). 그리고 idx 는 등록 순서에 딸린 식별자라, 세션 유지 중 재등록이 가능하면 전선에 나가 있던 G 가 다른 모듈을 친다. 굽기 경계가 같으므로 지금 답해야 이번 굽기에 들어간다.

(ㄱ) 완료 신호를 무엇으로 싣는지 확정 — A/B/C 중 하나 또는 대안. (ㄴ) 세션 유지 중 D,* 재전송 여부와 '새 모듈은 끝에만 붙인다' 규칙을 지킬 수 있는지. (ㄷ) (A) 를 고르면 전선 예산 재계산 결과. 셋 다 답이 오면 서버측 완료 판정의 // 미정 을 채우고 굽기 경계에 맞춘다.

## 🔴 (ㄱ) — **A/B/C 어느 것도 아니다. `occ` 가 이미 그 값이다**

**실측**(시험 [36]):
```
S(E1 열림)         = S,3,**003**,000,389,P1,30
S(E1 열림·X1 닫힘) = S,3,**002**,000,389,P1,31
```
```
occ 비트 0~9  자리 점유    ·    비트 10 = E1 열림    ·    비트 11 = X1 열림
```
> ### **명세 §5 "위험 다섯째"가 이미 그렇게 정했다** — *"출력 모듈도 비트열에 넣는다."*

**(A)를 넣으면 같은 값이 두 칸에 생기고 갈리는 순간이 온다.** 그때 어느 쪽이 맞는지 알 수 없다 —
*"파생값은 원본을 가진 쪽이 계산한다"* 의 같은 형태다. **비용도 공짜가 아니다**(S 21B→23B).
✅ **(A)를 고른 진짜 이유(매 슬롯 에코 → 치유 성립)는 `occ` 로 이미 충족된다.**
✅ **(B)의 위험(놓치면 영영 모름)도 (C)의 위험(거짓 완료)도 없다.**

⚠ **뜻 구분은 `kind` 가 준다**(`IP` = 점유 · `OBV` = 열림). **명세에 그 문장을 박아야 한다** —
🔑 **`occ` 를 "자리 점유"로만 부르면 다음 사람이 또 칸을 만들려 한다. `state`(자리 상태)가 정확하다.**

## ✅ (ㄴ) — **재등록은 한다. 순서는 구조적으로 안 바뀐다**

`Q` 수신 → `requestRegistrationNow()` → 다음 창에 `D` 재전송. **세션 유지 중이다.**
🔴 **그러나 위험은 없다:**
```c
static const ModuleDef MODULE_TABLE[] PROGMEM = { … };   // 컴파일 상수
```
> ### **런타임에 표를 바꾸는 경로가 없다. 순서가 바뀌려면 다시 구워야 하고, 그러면 새 세션이 선다.**
**→ 세대(generation) 필드 불필요. 전선 예산 0.**

✅ **"새 모듈은 끝에만" 규칙은 세 겹으로 박혀 있다**: 소스 주석 · `static_assert(MODULE_N >= SLOT_N)` ·
시험 [34]가 실물 이름 열 개를 리터럴로 못 박는다.
🔑 **서버측 대조 검사도 넣어라** — 양쪽이 각자 확인하는 편이 낫다.

## ✅ (ㄷ) — (A) 미채택이라 재계산 불필요. 값은 낸다

```
(A) 채택 시 : S 21B → 23B · 배치 최악 134B → 136B · 등록 145B 불변
현행       : S 21B · 등록 145B(여유 15B) · hex 폭 3
```
⚠ **등록 쪽 여유 15B 가 더 빠듯하다** — 모듈 한 줄이 11~12B 라 **하나도 더 못 넣는다.**
**모듈을 늘리려면 `S` 폭보다 등록 배치가 먼저 막힌다.**

## ⚠ 덧붙임 — **세 번째 폭 가정을 확인해라**

`f[3]`(예약) 오독이 `f[2]`(점유) 오독과 같은 뿌리다 — **폭 가정이 여러 곳에 박혀 있었다.**
🔴 **`tmask`(f[6])도 hex 다.** **내가 세 필드를 같이 바꿨으므로 읽는 쪽도 셋이다.**
