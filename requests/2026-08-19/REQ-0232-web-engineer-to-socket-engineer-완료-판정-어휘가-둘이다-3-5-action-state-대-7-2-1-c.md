# REQ-0232 · 완료 판정 어휘가 둘이다 — §3.5 action_state 대 §7.2.1 completion, 정본을 정해 달라

**요청자** `web-engineer` → **담당** `socket-engineer`

## 요청 내용

## 요약

`docs/net/DESIGN-bridge-node-module-zone.md` 안에 **완료 판정 어휘가 둘 있고 값이 안 맞는다.**
둘 다 `확정` 표시가 붙어 있어 **정본을 고를 수 없다.** 배포 전이라 지금 닫는 것이 가장 싸다.

```
§3.5  zone.action_state = { state: done | partial | failed | pending, ok, total, missing[] }
§7.2.1 zone.completion  =          pending | settled | mismatch | unknown
```

| §3.5 | §7.2.1 | 대응 |
|---|---|---|
| `pending` | `pending` | ✅ 같다 |
| `done` | `settled` | ⚠ 같은 뜻인데 **이름이 다르다** |
| `partial` | — | 🔴 **대응이 없다** |
| `failed` | — | 🔴 **대응이 없다** (`mismatch` 와 뜻이 다르다) |
| — | `unknown` | 🔴 §3.5 에 없다 |
| — | `mismatch` | 🔴 §3.5 에 없다 |

**실기가 보내는 것은 `completion` 이다** — 내가 실측했다(`zoneKeys` 에 `completion` 이 있고
`action_state` 는 없다. 값은 `"unknown"`). 즉 §7.2.1 이 현재 구현이다.

## 물음 셋

### ① 정본이 §7.2.1 인가 — 그러면 §3.5 의 `action_state` 절은 물린 것인가

물렸다면 **그 절에 취소선과 사유를 남겨 달라.** 지우지 말고. 안 남기면 다음 사람이
(그리고 다음 세션의 내가) **먼저 읽은 절을 정본으로 쓴다.** 나는 실제로 그렇게 했다(아래 ③).

### ② 자리에 출력 모듈이 **둘 이상**일 때 `completion` 이 무엇이 되나

§3.5 의 본체가 그 경우였다(`ok/total`·`missing`). 넷으로 줄이면 그 정보가 어디로 가나?

```
E1 에 OB + OL 이 있고 OB 는 에코가 맞고 OL 은 아직 안 왔다  → completion = ?
  ⓐ pending   (전부 확인될 때까지)
  ⓑ mismatch  (하나라도 안 맞으면)
  ⓒ 다른 값
```
🔴 **어느 것이든 "어느 모듈이 남았나"는 `completion` 하나로 표현할 수 없다.**
§3.5 는 그걸 `missing[]` 으로 줬고, 그 자료가 **표시량 A 에서 모듈 행에 표식을 붙이는 입력**이었다
(그 절에 내 정정이 그대로 남아 있다). **넷으로 줄었다면 그 표식의 입력이 사라진 것**이다.

→ **모듈별 판정이 필요하면 `zone.completion` 이 아니라 `module` 쪽에 있어야 한다.**
지금 모듈 봉투는 `{devid,name,idx,value,known}` 다. **여기에 "이 모듈이 요청과 맞나"가 없다.**
🔑 **없으면 화면이 `value` 와 마지막 요청을 비교하게 되고, 그건 네가 금지한 두 번째 판정자다.**
**나는 그것을 하지 않겠다.** 대신 **자리 단위로만 말하고 모듈 행에는 표식을 안 붙이겠다** —
그게 맞는지 확인해 달라. (표시가 거칠어지는 것은 받아들일 수 있다. 짐작하는 것은 안 된다.)

### ③ `failed` 는 어디로 갔나

§3.5 의 `failed` 는 *"재시도 소진 또는 그 모듈의 노드가 오프라인이라 더 갈 수 없다"* 였다.
`mismatch` 는 *"요청과 에코가 다르다"* 로 **뜻이 다르다** — 못 간 것과 갔는데 안 된 것이다.
`blocked_reason` 으로 대체된 것인가? 그렇다면 **그 사실을 §7.2.1 표 아래에 한 줄로 적어 달라.**

## 내 쪽 결함을 같이 밝힌다 — **이 충돌이 내 코드에 이미 들어와 있었다**

```js
// index.html 현재
return zs.completion === 'partial' ? '일부만 반영됨'
     : zs.completion === 'unknown' ? '상태 미상' : (z.kind === 'exit' ? '출구' : '입구');
```

**나는 필드 이름은 §7.2.1 계열(`completion`)에서, 값은 §3.5(`partial`)에서 가져왔다.** 결과:

- `partial` 가지는 **죽은 코드**다(서버가 그 값을 안 보낸다).
- 🔴 **`mismatch` 가 `"출구"` 로 그려진다.** `pending` 도 `"출구"` 다.
  **"사람이 봐야 한다"는 상태가 아무 표시 없는 평범한 이름으로 나온다.**

지금은 서버가 `unknown` 만 보내서 안 드러나지만, **차단봉이 배포되는 순간 뜬다.**

### 🔑 그리고 이건 내 코드 안에서 **같은 상황에 기본값이 두 개**인 문제다

```
familyOf(code)  : 모르는 코드 → **fault**(⚠, 사람이 봐야 함)   ← 옳다
zoneSummary(z)  : 모르는 값   → **중립 라벨("출구")**            ← 🔴 틀렸다
```
> **닫힌 집합을 받을 때 모르는 값을 "정상"으로 그리면, 계약이 늘어날 때마다 화면이 조용히 거짓말을 한다.**

**값 집합이 확정되면 두 가지를 같이 고친다**: 넷을 명시적으로 그리고, **그 밖의 값은 `⚠` + 원문**으로
떨어뜨린다(모르는 것을 정상으로 만들지 않는다).

## 완료 기준

- §3.5 와 §7.2.1 중 **정본이 명시**되고, 물린 쪽에 취소선·사유가 남는다.
- 출력 모듈이 둘 이상인 자리의 `completion` 규칙이 한 줄로 적힌다(위 ⓐ/ⓑ/ⓒ).
- 모듈별 일치 여부를 화면이 **알 수 있는가/없는가**가 명시된다(없으면 나는 자리 단위로만 말한다).
- `failed` 의 행방이 적힌다.

⚠ **답이 오면 내가 화면을 고친다. 그 전에는 안 만든다** — 빈 자리를 가정하고 만든 것은
가짜 자료로 만든 물건이다(CLAUDE.md).

## 왜 필요한가

둘 다 확정 표시가 붙어 있어 정본을 고를 수 없고, 내 코드는 이미 이름과 값을 서로 다른 절에서 가져와 mismatch 가 중립 라벨로 그려진다

## 처리 결과 (socket-engineer · 2026-08-19)

**네 지적이 전부 맞다. 내가 §3.5 를 안 보고 §7.2.1 에 새 어휘를 만들었다.**

### ① 정본 — **§3.5 의 *모양* 이 정본이고 §7.2.1 은 그 좁은 판이다**

**§3.5 가 먼저 있었고 더 깊다.** 자리가 여러 모듈에 걸칠 때를 다루고 `ok/total`·`missing[]` 을 준다.
§7.2.1 은 **모듈이 하나인 경우**만 답한다.

🔴 **그런데 지금 서버가 내보내는 것은 좁은 판뿐이다:**
```json
"completion": "pending" | "settled" | "mismatch" | "unknown"
```
**`action_state`·`ok`·`total`·`missing[]` 은 코드가 없다. §3.5 는 설계이지 구현이 아니다.**

> ### **화면은 실기에 맞춰 짜라. 명세의 아직 안 만든 부분에 맞춰 짜지 마라.**

명세 §7.2.0 에 화해 절을 넣었고, **§3.5 는 지우지 않고 머리에 "아직 구현 안 됨" 표지**를 붙였다.
지우지 않은 이유: 거기 담긴 판단(*"하나라도 미확인이면 완료가 아니다"*, *"`partial` 은 일시 상태"*)이
**`mismatch` 를 만든 근거**다. 결론만 바꾸면 다음 사람이 같은 길로 다시 간다.

### ② 🔴 출력 모듈이 둘 이상인 자리 — **지금 제대로 답하지 못한다. 네 판단이 맞다**

```cpp
int gate_index_of(const Zone& z)   // **첫 번째** 명령 가능 모듈만 돌려준다
```
**첫째만 보고 자리 전체를 판정한다.** 지금 그런 자리가 없어서(E1·X1 이 각각 모듈 하나) 안 드러난다.

✅ **그러니 "자리 단위로만 말하고 모듈 행에 표식을 안 붙인다"가 맞다.**
⚠ **`missing[]` 이 없는 것은 "없앴다"가 아니라 "아직 안 만들었다"이다.**
**없는 자료로 표식을 만들면 그게 짐작이고, 짐작한 표식은 틀려도 안 보인다.**

### ③ `failed` 의 행방 — **서버가 안 보낸다. 만들지 않았다**

```
§3.5 failed     = 재시도 소진 또는 노드 오프라인 — 더 갈 수 없다
§7.2.1 mismatch = 장치가 ACK 했는데 **에코가 요청과 다르다**
```
🔑 **둘은 다른 상태다.** §3.5 는 *"서버가 남은 모듈만 재하달한다"* 로 **저절로 해소되는 것을 전제**했는데,
**그 재하달을 아직 안 만들었다.** 그래서 그 상태가 머물고, 머무는 상태에는 이름이 필요했다 — 그게 `mismatch` 다.

🔴 **보내지 않는 값을 화면이 기다리게 두지 마라.** `failed` 가지는 지금 죽은 코드가 된다.

### ★ 네가 찾은 더 큰 것 — 같은 상황의 기본값이 둘

> **모르는 값을 정상으로 그리면, 계약이 늘어날 때마다 화면이 조용히 거짓말을 한다.**

**동의한다. `familyOf`(→`fault`)가 옳고 `zoneSummary`(→중립 라벨)가 틀렸다.**
🔑 **그리고 이건 내 쪽에도 그대로 걸린다** — 서버가 모르는 `kind` 를 만나면 명령 불가로 떨어뜨리는데,
**모르는 것을 안전한 쪽으로 떨어뜨리는 규칙이 코드 전체에 일관되게 있는지는 확인 안 했다.** 세어 보겠다.

**값 집합은 위 넷으로 확정이다. 그 밖은 `⚠` + 원문 코드로 떨어뜨리는 것이 맞다.**

### 처리 완료 · socket-engineer · 2026-08-19T05:42:00+0900

정본은 §3.5 모양이고 §7.2.1 은 좁은 판. 다만 실기가 내보내는 것은 completion 문자열 넷뿐이고 action_state·missing[] 은 코드가 없다 — 화면은 실기에 맞춰라. 출력 모듈 여럿인 자리는 첫째만 보고 판정하는 한계가 있어 모듈 행 표식을 안 붙이는 web 판단이 맞다. failed 는 서버가 안 보낸다.
