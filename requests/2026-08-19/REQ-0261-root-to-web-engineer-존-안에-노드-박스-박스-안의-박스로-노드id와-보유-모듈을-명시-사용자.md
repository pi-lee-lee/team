# REQ-0261 · 존 안에 노드 박스 — 박스 안의 박스로 노드ID와 보유 모듈을 명시 (사용자 지시)

## 요청 내용

# 존 안에 **노드 박스**를 그린다 — 박스 안의 박스 (사용자 지시)

> 사용자 원문: *"존을 그릴 때 해당 존 안에 있는 **노드들은 묶어서 표시**되고
> **노드ID와 보유중인 모듈이 명시**되도록 **박스 안에 박스**로 표시되도록 개선해달라."*

## ✅ 계약은 이미 다 있다 — socket 에 물을 것이 없다

루트가 코드로 확인했다:
```cpp
server.cpp:2359   o << "{\"devid\":" << jstr(dv) << ",\"name\":" << jstr(nm)
                    << ",\"kind\":" << jstr(kind) << ",\"idx\":" << idx << "}";
```
```json
zones[].modules : [ {"devid":"P1","name":"A1","kind":"IP","idx":0}, … ]
```
**`devid` 가 모듈마다 실려 온다.** 네 코드도 이미 그것으로 대조한다(`index.html:2613` —
`x.devid === mod.devid && x.name === mod.name`).
🔑 **그러니 이건 화면 단독 작업이다. 서버 변경 0.**

## 그릴 모양

```
┌─ 영역1  (kind=parking · 요약/상태) ─────────┐
│  ┌─ P1 ────────────────────────────────┐  │
│  │  A1 (IP)   ·  B1 (IP)               │  │
│  └─────────────────────────────────────┘  │
│  ┌─ P2 ────────────────────────────────┐  │
│  │  C1 (IP)                            │  │
│  └─────────────────────────────────────┘  │
└───────────────────────────────────────────┘
```
- **묶는 키는 `devid`.** 한 영역에 여러 노드의 모듈이 들어올 수 있다(`Zone.modules` 가 `(devid,name)` 벡터인 이유).
- **노드 박스에 `devid` 를 명시**하고, 그 안에 **그 노드가 이 영역에서 보유한 모듈**을 나열한다.
- 모듈에는 **이름과 `kind`** 를 같이 보여라 — `IP`(센서)와 `OBV`(차단봉)가 섞인다.

## 🔴 사용자 추가 지시 — **모듈 리스트 + 녹색/적색 동작상태등**

> *"노드는 **각각 개별 박스**이고 내부에 **보유한 모듈이 리스트 형식**으로 표시되고
> **동작상태가 녹색/적색등**으로 표시되어야 한다."* / *"지금 **주차확인센서와 같은 구조**이다."*

```
┌─ 영역1  (parking) ────────────────────┐
│  ┌─ P1 ──────────────────────────┐   │   ← 노드마다 **개별 박스**
│  │  ● A1 (IP)                    │   │   ← 모듈 **리스트** · ● 녹색/적색
│  │  ● B1 (IP)                    │   │
│  └───────────────────────────────┘   │
└──────────────────────────────────────┘
```

### 🔴 상태등의 원천 — **주차확인센서와 같은 구조다** (사용자 확정)

**즉 모듈 상태 = `occupied` 비트열에서 그 모듈의 `idx` 비트다.**
`map` 의 `modules[].idx` 가 그 색인이고, 비트 `>= 실물 자리 수` 는 **자리 점유가 아니라 차단봉 상태**다(명세 §7.2).

### ⚠ 그런데 **지금 `state` 에 그 값이 없다** — 루트가 확인했다

```
state_json() 의 자리 본문 :  id · occupied · reserved · actions      ← **자리 단위뿐**
map_json()   의 모듈      :  devid · name · kind · idx              ← **값이 없다**
```
> ### **모듈별 값이 전선에서 화면까지 오지 않는다. 지금 그리면 지어내는 것이다.**

**socket 에 REQ 를 따로 냈다**(모듈별 값을 `state` 에 싣기). **계약 이름이 확정되면 루트가 넘긴다.**
```
✅ 지금 해도 되는 것 : 박스-인-박스 골격 · 노드 그룹핑 · 리스트 레이아웃 · 검사 작성
🔴 계약을 기다릴 것   : 상태등의 **값 바인딩**
⚠ 🔴 **필드 이름을 지어내지 마라.** 지어내면 그 순간부터 두 곳에 다른 정의가 생긴다
   (§"계약에 빈 자리가 있으면 받는 쪽이 메운다")
```

### 상태등이 답해야 하는 것 — **셋을 갈라라**
```
🟢 정상·값 있음    · 🔴 이상        ← 사용자가 말한 둘
⚪ 🔴 **값을 모름**  ← 노드 오프라인 · 미등록 · 결속 끊김
```
**"모름"을 녹색이나 적색으로 칠하지 마라.** `0` 이 건강인지 못 셈인지를 구별 못 하는 그 형태다 —
**우리 원장 1.1 이 그 얘기다.** 세 번째 표시를 반드시 둬라.

## 🔴 지금은 **퇴화형으로 보인다** — 그것을 알고 만들어라

```
지금 지형 : 영역 12개 · 영역 하나에 모듈 하나 → 박스 안에 박스가 **1:1:1** 로 보인다
곧 바뀐다 : 영역 7개(주차 5 + 입 + 출) · 🔴 **영역1 ← A1·B1** 처럼 **모듈 둘** (REQ-0260)
```
**"지금 하나뿐이니 굳이 묶지 말자"로 최적화하지 마라.** 곧 둘이 된다.
⚠ **모듈 0개인 영역**도 지금 실재한다(등록 전·결속 끊김). **그 경우를 먼저 정하고 그려라** —
빈 영역을 정상처럼 그리면 §"빈 지형은 답이 아니라 고장이다" 를 반복한다.

## 같이 봐야 할 것

```
· 노드가 오프라인이면? → 노드 박스에 표시. **모듈 값은 못 믿는다**
  (네 REASON_TEXT 계열에 `node_offline`·`node_unregistered`·`module_absent` 가 이미 있다)
· 같은 이름 모듈이 다른 노드에 있으면? → **복합 키(devid,name)로 구분**. name 만 쓰면 섞인다
  🔑 서버 주석이 그것을 명시한다 — *"`kind` 와 `idx` 는 그 모듈을 등록한 노드가 갖고 있다.
     이름만으로 찾으면 안 된다(복합 키)"*
· 정렬 — `orderedModules()` 가 이미 있다. **노드 정렬 규칙도 정해라**(devid 사전순 등).
  안 정하면 순서가 프레임마다 흔들려 눈이 못 따라간다
```

## 검사 — 🔴 **존재형으로 쓰지 마라**

우리가 오늘 이미 밟았다(§"존재형 검사는 유물을 통과시킨다").
```
❌ "노드 박스가 있다"           → 하나만 그려도 통과한다
✅ "영역1 의 노드 박스 집합 == 그 영역 modules 의 devid 집합"
✅ "P1 박스 안의 모듈 이름 집합 == modules 중 devid==P1 인 것들의 name 집합"
```
**긍정형·집합 대조로 써라.** 그래야 하나가 빠졌을 때 빨강이 된다.

**창 P 주입이 돌고 있다**(A[1] 판정 창). **브라우저 신규 접속은 그 창의 `화면` 축을 움직인다** —
지금 주입기 8개가 WS 클라이언트로 세어져 `화면` 이 이미 부풀어 있다.

## 🔴 먼저 — 이 요청의 전제 하나가 틀렸었다 (진행에 영향이 컸다)

> *"state 에 모듈별 값이 없다 → 상태등 값 바인딩은 지금 하면 지어내는 것이다"*

**소스에 있다.** `server.cpp:2502~2519`(`state_json()` 안, `completion` 바로 뒤):
`"modules":[{"devid","name","idx","value":true|false|null,"known":true|false}]`
주석까지 **"🔴 이제 값이 있다 … 모름과 거짓은 다르다"** 다. 내 원장 §5.44 에도 실측으로 적혀 있었다.
→ **루트가 값으로 확인하고 정정했다**(원인: `sed -n '2442,+55p'` 로 **5줄 모자라게** 봤다).
→ **상태등을 기다리지 않고 지금 붙였다. 필드 이름은 하나도 안 지어냈다.**

**그 과정에서 진짜 결함이 하나 나왔다** — `if (z.modules[m].first == park.devid)` 라
**주 노드가 아닌 모듈은 항상 `known:false`** 다. socket 에 넘어갔고(REQ-0262), socket 이
**고치는 순서가 반대**임을 알려 왔다: `mod_bits` 가 `Server` 에 한 벌뿐이라 `idx` 조회만 노드별로
고치면 **둘째 노드가 주 노드의 비트를 자기 값이라고 말한다**(거짓 확신).
🔑 **그러므로 지금 보이는 `known:false` 는 버그가 아니라 옳은 답이다.** 내 화면은 그것을 ⚪ 로 그린다.

### 🔴 상태등을 **두 축으로 갈랐다** — 사용자 지시를 그대로 두면 축이 섞인다

사용자는 *"동작상태가 녹색/적색등"* 이라고 했다. 그런데 `value` 는 **측정값**(차 있음/없음)이지
**동작 상태가 아니다.** 한 칸에 합치면 **"차가 없다"와 "모듈이 죽었다"가 같은 색**이 된다.

```
등 (녹/적/회) = 그 모듈이 지금 값을 내고 있는가   ← known (+ 고장 계열 사유)
값 기호 ●/○   = 측정값                          ← value
```
- 🟢 `known:true` · ⚪ `known:false`(모름) · 🔴 서버가 준 `reason` 이 **고장 계열**일 때만.
- 🔴 **`known:false` 를 적색으로 칠하지 않는다.** socket 확정: *"서버는 '모듈이 고장났다'는 신호를
  전선에 안 낸다. 적색으로 칠하면 없는 고장이 보인다."* → 제3의 표시(회색)로 그렸다.
- 색만으로 뜻을 안 나른다: 도형(● ▲ ○)이 다르고 `aria-label` 에 **문장**이 붙는다.

**실패할 수 없는 검사의 초록은 아무 말도 안 한다**(오늘 §5.85 에서 배운 것).

⚠ **전부 주입이다**(`file://` · 트래픽 0 · 하행 0 · 서버 미사용). **브라우저를 실기에 안 붙였다.**
🔴 **그러므로 "실기에서 이렇게 보인다"는 아직 못 쟀다** — 미측정 1건으로 따로 세어 뒀다.
배포 뒤에 실기로 한 번 돌리는 것이 남았다.

## 남은 것

- **배포**(root/socket) 뒤 실기 확인
- **둘째 노드 값**: socket 의 `mod_bits` 를 `Node` 로 내리는 작업(REQ-0260 과 같은 배포). **화면은 안 고쳐도 된다**
- **`modules[].reason` 여섯**(socket): `known:false` 의 사유. **아직 전선에 안 나간다.**
  내 코드는 그것에 의존하지 않는다 — 오면 ⚪ 를 사유별로 나눌지 그때 판단한다
- ⚠ **socket 경고 기록**: `completion` 이 **두 벌**이다(조작 결과 `pending|settled|mismatch|unknown`
  대 값 온전성 `complete|partial|unknown`). 아직 안 갈렸다 — **`kind` 별로 다르게 읽어야 한다**
