# REQ-0180 · 설계 — ESP 클래스 명세(init/read/write/reset) · 자리·모듈 유동화 · 전선 예산은 socket 과 합의

## 너의 몫 — 셋

### ① ESP 클래스 명세 — **`init` / `read` / `write` / `reset`** (사용자 확정)

**네 사실 보고가 지시를 고쳤다.** 넷으로 확정됐고 이름은 `reset` 이다(사용자가 `tick` 대신 정했다).

```
init()    setup 에서 한 번  — 모듈 기동 + 사다리 시작
read()    loop            — 수신
write()   loop            — 송신 (3단 게이트 · busy 대응 포함)
reset()   loop            — 링크 상태를 유지한다 ↓
```

**`reset()` 의 정의를 좁히지 마라**(네 정정 채택):
> **링크 상태를 유지한다 — 안 서 있으면 세우고, 오래 서 있었으면 방어를 낮춘다.**

🔴 **네가 잡은 것을 명세에 박아라**: `netTick` 의 조기 반환 **앞에 일이 있다**(`client.ino:2602`) —
*"30초 연속 온라인이면 사다리를 0단으로 내린다"*. **그건 링크를 세우는 게 아니라 안 세워도 된다는 판정**이다.
정의를 안 넓히면 **그 로직이 조용히 사라지거나 `read()` 로 흘러들고**, 사라지면
**사다리가 영원히 높은 단에 머물러 다음 사고 때 4단부터 시작한다.**

★ **일반화도 같이 적어라**: **함수를 쪼갤 때 "오프라인일 때 하는 일"만 보지 말고
"온라인일 때 하는 일"도 세어라. 조기 반환 앞의 코드는 눈에 안 띈다.**

**`init` 은 (A) — 사다리만 시작하고 끝난다**(사용자 확정). 지금 코드가 이미 그렇다.
그리고 **`init()` 이 진짜로 알 수 있는 것은 "UART 를 열었다"뿐이다**(네 지적) —
`AT+RST` 응답은 비동기라 `setup` 에서는 안 왔다. **그 이상을 반환값에 담으면 거짓이 된다.**

🔴 **명세에 반드시 답할 것**: **3단 게이트·`busy` 대응·리셋 계단이 넷 중 어디에 사는가.**
`write` 안에 두기로 했는데(밖으로 꺼내면 실패 모드별 제어 경로가 생긴다), **리셋 계단은 `reset` 이다.**
**그 경계를 표로 그려라** — 지금 `netTick` 과 `sendLine` 에 섞여 있는 것을 어디로 나눌지가 이 명세의 전부다.

### ② 자리 개수·모듈을 유동으로 — **지금 무엇이 막고 있나**

```
SLOT_N = 10                컴파일 상수 (client.ino:142)
SLOT_ID[10] = {"A1"…"B5"}  고정 표 (server.cpp:291)
srcReal 비트마스크 16칸     자리 = 1비트(occupied)
```

**개정 후**: 자리 5개(유동) · 각 자리가 모듈 여러 개 · **모듈이 여러 아두이노에 흩어진다.**

🔴 **핵심**: 지금 `S` 프레임은 **자리 ID 를 안 싣는다 — 비트 순서가 ID 를 대신한다.**
```
S,912,0110000010,0000000000,1080,P1,01
       ^^^^^^^^^^ 이 10비트의 순서가 곧 A1..B5
```
**즉 자리의 신원이 "전선에서의 순서"에 묶여 있다.** 개수를 바꾸면 **같은 비트가 다른 자리를 뜻하고
서버와 펌웨어가 조용히 어긋난다.** **고유 ID 도입은 이름 붙이기가 아니라 이 결합을 끊는 일이다.**

**네가 명세할 것**: 장치가 아는 것은 **`(자기 name) → pin`** 뿐이다. **`zone` 을 모른다** —
네 선행 의견 그대로다(*"장치가 구역을 알면 배선이 바뀔 때마다 펌웨어를 다시 굽는다"*).

### ③ 🔴 전선 예산 — socket 과 **합의**해라. 이게 가장 급하다

**한 줄 64B 상한**이고 `S` 가 **55B** 를 쓴다. **여유 9B.** ID 를 그대로 실으면 터진다.

| 방식 | 대가 |
|---|---|
| **비트열 유지 + 접속 시 `M` 프레임으로 순서 등록** | 전선 비용 0 ← **루트가 유력하다고 본다** |
| ID 1~2자 + 상태를 여러 줄 | 배치 크기 증가 |
| 델타 | **상태 프레임이 멱등성을 잃는다** — 재접속 시 전체 재동기 경로 필요 |

**첫 번째면 네가 명세할 것**: `M` 프레임 형식 · **등록 유실 시 재시도 규약**.
⚠ **등록이 유실되면 이후 모든 상태가 잘못 귀속된다** — 조용히 틀리는 형태라 가장 위험하다.
🔑 **`name` 이 장치 안에서만 유효한 것이 이걸 싸게 만든다** — 등록이 자기 소켓으로 오므로
**`devid` 를 항목마다 반복할 필요가 없다.**

socket 에게 같은 항목을 REQ-0179 로 냈다. **둘이 직접 합의해라** — 내가 중계하면 한 단계 늦는다.

## 하지 말 것

- 🔴 **보드를 건드리지 마라.** 창 B 가 돌고 있다(`build=aeb5283` · pid 4029).
- **`client.ino` 를 고치지 마라.** 명세만이다. 구현은 합의 뒤 별도 REQ.
- ⚠ **다음 굽기 대기 항목이 이미 둘 있다**: `왕복 최대`(socket 이 창 B 에서 넘긴다)로 `cap` 재계산 ·
  `ssovf` 를 창 B 값으로 재판정. **그것들과 개정 구현을 한 굽기에 묶을지는 내가 정한다.**

## 그리고 창 B 에서 네게 올 것

socket 이 **`왕복 최대 Nms(n=K)`** 를 넘긴다 — **d1+d2 의 실기 첫 값**이다.
**창 A 에서는 원리적으로 못 나왔다**(그 계측이 큐 커밋에 들어갔다).
**네 `cap` 이 두 항 모두 이론 최악이라 실측 대비 약 20배 보수적**이고, 그 값이 그것을 처음 대체한다.
받으면 **`cap` 재계산 근거를 원장에 적어 둬라** — 굽기는 나중이다.

## 왜 필요한가

지금 S 프레임은 자리 ID 를 안 싣고 비트 순서가 신원을 대신한다 — 개수를 바꾸면 같은 비트가 다른 자리를 뜻해 서버와 펌웨어가 조용히 어긋난다. 그리고 전선 여유가 9B 뿐이라 ID 를 그대로 실으면 예산이 터진다. 명세 없이 구현하면 그 결합을 짐작으로 끊게 된다
