# REQ-0212 · 🔴 점검 — 송신 주기가 1.2초가 아니라 1.1초다 · 구조를 무너뜨린 수정 찾기 (사용자 지시)

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

🔴 **사용자가 구조 위반을 지적했다. 실측으로 확인됐다.**

> *"지금 구조가 1.2초마다 송수신하는 구조인지 확인해라. 1.2초마다 송수신 스트림은 고정이고
> 해당 통신 시점에 데이터를 실어보내는 구조이다. **이는 esp01과 아두이노의 시리얼 통신 제약으로
> 인해 지켜야 하는 방식이다.** 그런데 지금 데이터를 많이 보낸다고 터지는 거면
> **뭔가 수정사항 중에 이 구조를 무너뜨리는 수정사항이 발생한 것 같다. 점검하라.**"*

## 🔴 실측 — **주기가 1.2초가 아니다**

```
[TX] S,… 시각 (연속 12개)
15:51:33 :34 :35 :37 :38 :39 :40 :41 :43 :44 :45 :46
         ↑1s ↑1s ↑2s ↑1s ↑1s ↑1s ↑1s ↑2s ↑1s ↑1s ↑1s

[SLOT] n=2329 → 2334 가 15:51:40 → 15:51:46 (6초에 6슬롯)
```

**약 1.1초 주기다. 설계값 1.2초가 아니다.**
⚠ **`SLOT_MS = 1200` 이고 `slotStart += SLOT_MS` 로 누적 오차도 안 나게 돼 있다.**
**그런데 실측이 안 맞는다 — 어딘가가 슬롯 경계와 다른 것을 보고 송신한다.**

## 🔴 내가 좁힌 지점 — **확인은 네 몫이다**

```c
client.ino:2907   const bool inTxWindow = (slotUsed + SLOT_TX_RESERVE_MS <= TX_WINDOW_MS);
client.ino:2908   bool heartbeatDue = inTxWindow && !slotSent;
client.ino:2970   if (!netOnline || !heartbeatDue) return;
```

**`heartbeatDue` 는 "지금이 창 안이고 이번 슬롯에 아직 안 보냈다"** 이고,
**`statusTick(now)` 는 `loop()` 마다 불린다**(`client.ino:3119`).

🔴 **그러면 송신 시각은 "슬롯 시작"이 아니라 "슬롯 시작 이후 `loop` 가 처음 도는 순간"이다.**
**`slotSent` 가 그 슬롯의 두 번째 송신은 막지만, 첫 송신이 언제인지는 `loop` 주기가 정한다.**

⚠ **이것만으로 1.2 → 1.1 이 설명되는지는 네가 확인해라.** 후보 셋:
```
① 위 구조 자체 — loop 가 슬롯 경계를 지나 처음 도는 순간에 보낸다
② while 루프가 여러 슬롯을 한 번에 소진하며 위상이 당겨진다(2888행)
③ 다른 경로가 슬롯 밖에서 보낸다 — sendAck 우회는 막았지만 또 있나
```

## 🔴 그리고 사용자 지적의 핵심 — **이게 왜 중대한가**

**1.2초 고정은 최적화가 아니라 `SoftwareSerial` 반이중 제약을 지키는 유일한 방법이다.**
**주기가 흔들리면 송신 창과 수신 창의 경계가 흔들리고, 그러면 겹침이 다시 난다.**

**그리고 실제로 그 증상이 있다:**
```
oow 8 → 47      하행이 송신 창에 떨어진 수가 크게 늘었다
esprst +4       분당 1회 · stuck 과 1:1 (T2 8초 초과)
🔴 그런데 cksumng +0 — 파괴는 안 났다
```

⚠ **`oow` 가 늘었다는 것이 창 경계가 흔들린다는 직접 증거일 수 있다.** 확인해라.

## 점검할 것 — **이 순서로**

```
1. 🔴 실제 송신 주기가 왜 1.1초인가 — 위 후보 셋 중 무엇인가
2. 언제부터 그랬나 — slot1~slot7 중 어느 굽기에서 들어왔나
   ⚠ 창 A~E 판정에 "프레임 간격 1.11~1.12s" 가 이미 기록돼 있다(설계 문서 §지표 경계)
   🔴 **그러면 이건 최근 수정이 아니라 처음부터였을 수 있다.** 그 경우도 답이다
3. 슬롯 경계와 실제 송신 시각의 관계 — [SLOT] due= 값이 그것을 말해 주나
4. 🔴 창 경계가 흔들리면 수신 창이 얼마나 침범되나 — oow +46 과 연결되나
```

### 결론 — **구조는 안 무너졌다. 주기는 1.2초가 맞다**

**400프레임 연속 구간(seq 1896~2295 · 513초) 실측:**
```
정상 간격만(394개) 평균 = **1.2056 초**   ← 설계 SLOT_MS 1.200 과 일치
전체 평균          1.2857 초             ← 이상치 5건이 끌어올린 값
```

### 🔑 "1.1초"의 정체 — **원장 §3.4-2 의 맥놀이. 우리가 이미 데인 함정이다**

REQ 본문의 자료 `1 1 2 1 1 1 1 2 1 1 1` 이 **그 자체로 1.2초의 증거**다:
```
2초 간격이 5프레임마다 → 1/(T−1) = 5 → **T = 1.2초**
```
전체 자료에서도 **2초 간격 사이 프레임 수 중앙값 = 5**.

⚠ **`[SLOT] n=2329 → 2334` 도 같다** — **5 증가**다(2334−2329). **6초에 5슬롯 = 1.2초.**
**"6슬롯"으로 세면 1초가 나온다 — 오프바이원.**

> ### 원장 §3.4-2 원문: *"1초 해상도로 표본화하면 맥놀이가 나고 그 무늬는 고장과 구별되지 않는다.
> 가르는 법은 간격 사이의 개수를 세는 것이다."*
> **오늘 그 함정을 다시 밟았고, 이번엔 자료가 아니라 판독이 밟았다.**

★ **그래서 "고치지 마라"가 옳았다.** 고쳤으면 **멀쩡한 격자를 건드리고 축이 하나 늘었을 것이다.**

### 🔴 진짜 문제는 이상치 5건 — **주기가 아니라 간헐 정지다**

```
15:47:45 seq 1990 뒤  4초    15:48:38 seq 2031 뒤  4초
15:48:55 seq 2042 뒤 **16초**  15:49:12 seq 2044 뒤 **10초**   15:51:06 seq 2132 뒤 4초
```
**15:47~15:51 에 몰려 있다**(연타 구간 15:23 과 다른 시각).
🔑 `4초 = 3슬롯 건너뜀` · `10초 = TX_STALL_MS` · `16초 = T2(8초)+복구` 로 읽힌다
→ **§12.5 의 되먹임 고리와 같은 모양.**
⚠ **확정하려면 그 시각의 `[SLOT] r=0`·`skip`·`stuck` 원문이 필요하다 — monitor 자료다.**

### ⚠ `oow 8 → 47` — 창 경계가 흔들린 증거가 **아닐 수 있다**

`oow` 는 **하행 도착이 송신 창 구간에 들어왔는가**를 센다.
**주기가 정상이면 창도 정상**이고, 증가는 **"하행이 그 구간에 더 많이 왔다"** 는 뜻일 수 있다.
🔑 **`oow / 하행 도착 수` 비율이 안 변했으면 창은 안 흔들린 것이다** — 분모를 같이 봐야 한다.

### 후보 셋에 대한 답

**"송신 시각이 `loop` 가 처음 도는 순간"** 이라는 지적은 **사실이다**(`due` 지터).
**그러나 격자(`slotStart`)는 `+= SLOT_MS` 로 고정이므로 평균 주기는 안 변한다** —
실측 1.2056 이 그것을 확인한다. **지터는 창 안의 위치를 흔들지 주기를 안 흔든다.**
