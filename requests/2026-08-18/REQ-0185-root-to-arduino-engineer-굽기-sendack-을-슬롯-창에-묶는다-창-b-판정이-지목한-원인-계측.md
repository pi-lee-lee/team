# REQ-0185 · 굽기 — sendAck 을 슬롯 창에 묶는다(창 B 판정이 지목한 원인) + 계측기 넷 · 축 개수는 네 판단

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

**창 B 판정이 나왔다**(`monitor/JUDGMENT-2026-08-18-winB.md`). 결론이 둘이고 하나가 네 몫이다.

```
✅ 큐는 링크 붕괴를 막았다        51건 만에 세션 사망 → 300 완주 ×2회 (서버·장치 양쪽 확정)
🔴 큐는 하행 파괴를 막지 못했다    inj6 에서 5건 — **그리고 원리적으로 못 막는다**
```

**못 막는 이유가 판정문에 지목돼 있다**: 충돌 상대가 서버 위상이 아니라
**장치 내부의 슬롯 우회 송신(`sendAck → sendLine`)** 이다.
**서버가 창을 지켜도 장치가 그 창에서 송신한다.**

> ### **즉 다음 굽기가 이 판정의 후속이고, ①이 그 답이다.**

---

## 굽기 하나에 다섯

### ① 🔴 `sendAck` 을 슬롯 창에 묶는다 — **최우선. 판정이 지목한 원인이다**

`client.ino:1853` 이 `sendLine(buf)` 를 직접 부른다. **`sendSlotBatch` 를 안 탄다.**
그래서 **ACK 이 수신 창 한복판에서도 나가고, `[SLOT-OOW]`·`[SLOT]`·`smiss`·`skip` 어디에도 안 잡힌다.**

⚠ **설계 문서가 손실 0 의 직접 원인으로 적은 문장이 "수신 창에는 한 바이트도 쓰지 않는다"** 인데
**ACK 은 그 문장 밖에 있었다.** 이걸 묶는 것이 그 문장을 처음으로 참으로 만든다.

🔴 **주의 — ACK 을 잃지 마라.** 지금 `sendAck` 은 실패 시 `ackqPush(rid)` 로 담아 둔다
(호출부 5곳을 안 고치려고 한 곳에 모아 둔 구조). **슬롯에 묶으면서 그 보장이 깨지면
ACK 이 조용히 사라진다** — `sendSlotBatch` 의 "성공했을 때만 큐에서 소비한다"와 같은 규율을 지켜라.

### ② `[ACK] lag=` — `d1+d2` 를 실측으로

`d1+d2 = rtt − lag`. 재료는 `rxLineOff`(REQ-0174)에 이미 있다.
🔑 **①을 한 뒤가 오히려 정확해진다**(즉시/큐 두 경로가 섞여도 `lag` 이 차이를 흡수한다) —
네가 socket 과 합의한 그대로다.

### ④ `ack=` 정의 변경을 확인해 답하라

①을 하면 ACK 이 `sendSlotBatch` 를 타므로 **`[SLOT] ack=` 에 세어질 것이다.**
**그러면 지금까지의 `ack=` 는 무엇을 세고 있었나** — 큐에 담긴 것만인가?
🔴 **정의가 바뀌면 monitor 가 창 B↔창 C 를 못 잇는다.** 바뀌면 **대조 불가 칸으로 선언해라.**

### ⑤ 🔑 `ssovf` 의 **문맥**을 기존 줄에 얹어라 — monitor 가 형태까지 줬다

monitor 결론: **`ssovf` A/B 판별이 자료가 아니라 계측 방식 때문에 막혔다.**
`[CNT]` 표본에서만 읽히니 **해상도가 60초**이고, 그 안에 주입 구간과 유휴 구간이 같이 들어가면
**어떤 대비도 성립하지 않는다.**

⚠ **내가 처음 낸 요구("넘친 그 자리에서 시각을 찍어라")에는 자기모순이 있었다** —
그 한 줄이 또 `Serial.print` 면 **`[CNT]` 블로킹과 같은 성질**이 되고
**후보 B 를 재려는 계측이 후보 B 를 만든다.**

🔑 **monitor 가 그것을 푸는 형태를 줬다 — UART 추가 트래픽 0:**

```
[CNT] … ssovf=5 ssovf_at=+<슬롯오프셋ms> ssovf_ctx=<cnt|tx|ack|idle> ssovf_n=<표본 구간 증가분>
```

| 칸 | 왜 |
|---|---|
| `ssovf_at` | 넘침을 **본 순간의 슬롯 오프셋**. 지금 이 값이 없어서 60초 해상도에 막혔다 |
| **`ssovf_ctx`** | 🔴 **이 한 칸이 A/B 를 직접 가른다.** `cnt`=B · `tx`/`ack`=송신 중 못 꺼냄 · **`idle`=제3 후보** |
| `ssovf_n` | 표본 구간 증가분. **누계 차분은 표본 경계에서 틀린다** — 오늘 그 함정을 둘이 밟았다 |

⚠ **`ssovf_at`·`ssovf_ctx` 는 "마지막 1건"만 담아도 충분하다**(RAM 4~5B). 표본당 증가가 보통 1 이고,
2 이상인 표본은 `ssovf_n` 으로 드러나 **"여러 건 중 마지막"으로 읽으면 된다.**

**형태 결정권은 너다.** 다만 monitor 의 원칙을 받아라:

> ### **계측을 위해 새 출력을 만들지 말고, 이미 나가는 줄에 문맥을 얹어라.**
> **`[CNT]` 블로킹이 파괴를 만든 것이 그 근거다 — 출력을 늘리는 것 자체가 위험 요인이다.**

🔴 **그리고 그 원칙이 ②(`[ACK] lag=`)에도 걸린다.** 슬롯당 1~2줄 추가다.
`DEBUG` 안에 두기로 했지만 **그러면 관측 빌드와 시연 빌드의 손실률이 다르다**(monitor 판정문 §6).
→ **②를 넣는 회차는 "계측기가 대상을 바꾼 창"으로 표시**해야 하고 `inj7` 판정에 그 조건이 들어간다.

## 🔴 순서 — 관측을 멈추고 굽는다

```
① 굽기 직전 한 줄 → monitor 가 탭·요약기를 내린다 (monitor 는 루트 순서를 안 기다린다)
② 굽기 → hex 대조
③ 🔴 완료 통보를 **monitor 와 루트 양쪽**에 보내라
④ monitor 가 새 t0 로 연다 → socket 이 inj7 을 돌린다 (같은 조건 1.15s·300건)
```

⚠ **③을 강조하는 이유**: **내가 창 B 배포에서 완료 통보를 monitor 에게 빠뜨려 `inj6` 를 추가로
돌려야 했다.** 같은 형태를 반복하지 않는다 — **기다리는 쪽이 둘이면 둘 다에 보낸다.**

## `inj7` 이 답할 질문 하나

> **`sendAck` 을 묶으면 하행 파괴가 실제로 0 이 되는가.**

**`cksumng` 이 그 답이다.** 창 B 는 5 였다.
⚠ **`oow` 도 오를 것으로 예상한다** — ACK 이 이제 창을 지키므로 **미룬 ACK 이 생기고**
그것이 `[SLOT] ack=` 에 나타난다. **`oow` 는 하행 도착만 보므로 직접 관련은 없지만**,
**`smiss` 가 처음 발동할 수 있다**(ACK 이 창 끝자락에 걸리면 가드가 문다).
**네 가드가 "아직 시험되지 않은 방어"에서 "시험된 방어"로 바뀌는 자리다.**

## 🔴 축을 몇 개로 할지 — **네가 정해라. monitor 가 문제를 제기했다**

monitor: *"`[CNT]` 블로킹(③)을 같은 굽기에 넣으면 축이 둘이 된다 —
**①만으로 파괴가 남는지 보는 것이 더 값지다.**"*

**맞는 지적이고 판단을 너에게 맡긴다.** 두 갈래:

| **A. ①만 굽는다** | `inj7` 이 *"`sendAck` 을 묶으면 파괴가 0 이 되는가"* 에 **깨끗하게** 답한다. 계측기는 다음 굽기 |
| **B. 다섯 다 굽는다** | 굽기 1회로 끝나지만 **`cksumng` 변화의 원인이 ①인지 계측기 변경인지 흐려진다** |

⚠ **②·⑤ 는 계측기이고 ①·③ 은 거동에 닿는다.** 특히 ③(`txdrop=`)이 무엇을 바꾸는지 네가 안다.
**"계측기만"과 "거동 변경"을 갈라서 두 굽기로 나눌 수 있으면 그게 가장 깨끗하다.**

**네 판단을 근거와 함께 보고해라.** 나는 어느 쪽이든 승인한다 —
**축을 세는 것은 네가 나보다 정확하다**(오늘 창4 대비 변수 여섯을 네가 찾았다).

## 하지 말 것

- **액추에이터 에코(`n` 폭 비트열)는 넣지 마라.** **설계 개정 항목**이고 이 굽기에 넣으면
  축이 늘어난다. 네가 이미 그렇게 판단했다 — 유지해라.
- **`cap` 을 바꾸지 마라.** `d1+d2` 실측이 ②로 처음 나오고, 그 값을 보고 정한다.
- 🔴 **설계 명세(REQ-0180)는 멈춰라. 사용자 지시다** — *"설계를 멈춰라. 진행한 것까지만 유지하고
  측정을 완전히 마무리해라."* **지금까지 쓴 것은 그대로 두고 커밋해라. 이어 쓰지 마라.**
  측정이 끝나면 재개한다.

## 왜 필요한가

창 B 판정이 '큐는 하행 파괴를 원리적으로 못 막는다'로 결론했고 원인을 sendAck 의 슬롯 우회로 지목했다 — 서버가 창을 지켜도 장치가 그 창에서 송신한다. 설계 문서가 손실 0 의 직접 원인으로 적은 '수신 창에는 한 바이트도 쓰지 않는다'가 ACK 경로에서 거짓이었다

### 축 판단 — 🔴 **①만 굽는다. 계측 넷은 전부 다음으로**

**계측 넷이 축이 아니라고 보기 쉽지만, 셋 다 UART 출력을 늘린다:**
```
창 B 의 [CNT] 줄       142B      (루트 실측)
SERIAL_TX_BUFFER_SIZE   64B      → 이미 2.2배. 78B 가 블로킹으로 나간다
```
> ### **`[CNT]` 자체가 손실원이다**(§11.2 — 60초마다 하행 1건 파괴).
> **칸을 더하면 블로킹이 정비례로 늘어 손실이 커진다.**
> **"이미 나가는 줄에 얹어라"는 그 줄이 손실원이 아닐 때만 성립한다.**

★ **§11.2 를 찾은 지 한 시간 만에 또 밟을 뻔했다** — 그리고 그 형태를 **루트가 REQ 로 시키고
monitor 가 형태까지 준** 상태였다. **셋 다 그 원칙을 아는 상태였다.**

**①을 고른 이유(가설 배제력)**: 창 B 파괴 5건이 **전부 `[CNT]` 주기와 정합**했고(`44:40` 결손까지).
두 기전이 한 사건일 수 있어 **하나만 끊어야 갈린다.**
①을 고친 뒤 파괴가 남으면 **`[CNT]` 가 독립 원인임이 확정되고 60초 주기라 깔끔하게 보인다.**
②만 고치면 `sendAck` 우회는 하행마다 기회가 있어 **관측이 흩어진다.**

### ① 구현

```c
// 전: sendAck() → sendLine() 직접   → 슬롯 창을 안 본다 → 수신 창에서도 송신
// 후: sendAck() → ackqPush() 만     → 실제 송신은 sendSlotBatch 가 자기 창에서
```
- 호출부 **5곳 모두 `cachePut` 을 먼저 부르고 반환값을 안 쓴다**(확인함) → **호출부 변경 0**
- 프레임 문자열 만들던 코드 제거(배치가 캐시에서 재생성) → **플래시 120B 감소**
- ✅ **ACK 유실 보장은 오히려 강해진다**: 전에는 "즉시 보내고 실패하면 push" 라 **경로가 둘**,
  이제 **하나**다. 송신은 배치가 하고 **성공했을 때만 큐에서 소비**한다.

### ④ `ack=` 정의 — **바뀐다. 대조 불가**

```
창 B 까지 : ack = ackq 를 거친 것만 (게이트가 닫혔을 때만 — 소수 경로)
창 C 부터 : ack = 그 슬롯의 전체 ACK (처음으로 진짜 분모)
```
`SEND OK` 가 99.7% 같은 초에 와 **게이트가 대부분 열려 있었다 → 지금까지 대부분을 놓쳤다.**
monitor 가 창 A 판정문에 정정 블록을 넣었고 **"묶음이 동작했다"는 결론은 `tx 53B×142` 로
근거를 갈아 끼웠다** — 결론을 지키며 근거를 바꾼 처리다.

★ **다른 회귀가 전부 통과해서 "거동이 안 바뀐 것처럼" 보였다** — 그래서 이 시험을 넣었다.
