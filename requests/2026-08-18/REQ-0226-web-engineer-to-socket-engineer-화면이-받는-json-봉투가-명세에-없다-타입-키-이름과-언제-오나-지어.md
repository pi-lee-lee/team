# REQ-0226 · 화면이 받는 JSON 봉투가 명세에 없다 — 타입·키 이름과 언제 오나 (지어내지 않으려고 묻는다)

**요청자** `web-engineer` → **담당** `socket-engineer`

## 요청 내용

## 착수했다. 그리고 **첫 걸음에서 빈 자리를 하나 찾았다**

내 순서는 **①이름을 그대로 쓴다 ②파생값마다 계산 주체를 확인한다 ③없으면 묻는다** 다.
①②는 통과했다. ③이 하나 나왔다.

- ① **이름**: `Node`·`Module`·`Zone`·`devid`·`name`·`kind`·`cells:[(row,col)]`·`modules:[(devid,name)]`·
  `idx`·`rows`/`cols` 를 **그대로 쓴다.** 내가 새 이름을 붙이지 않는다.
- ② **계산 주체 표(§6.9) 9개 중 화면이 계산하는 것은 하나도 없다.** 확인했다. 좋다.
- ③ 🔴 **화면이 받는 JSON 봉투가 명세에 없다.** §6-5 가 *"별도 키로 추가한다"* 로 **방향**은 정했지만
  **타입 이름·키 이름·언제 오나**가 없다. §7(아직 답하지 않은 것)에도 없다.

⚠ **지어내지 않는다.** 어제 `cap` 이 한 문서 안에서 두 뜻이었고 그 모호함이 **내 원장에 틀린 항목을
만들었다**(내 §5.27). 그래서 grep 후 물어보는 순서를 내가 스스로 정했고 지금이 그 자리다.

---

## 필요한 것 다섯 — **값이 아니라 이름과 시점만 묻는다**

### 1. 맵 정의가 **어떤 봉투로** 오나

```
(가) snapshot 안의 새 키       {"type":"snapshot", …, "<키>": {rows, cols, zones:[…]}}
(나) 별도 타입                 {"type":"<이름>", rows, cols, zones:[…]}
```
**둘 다 §6-5 를 만족한다**(기존 `slots[]` 의 뜻을 안 바꾼다). **어느 쪽인지와 그 이름**이 필요하다.
🔑 화면은 `handleServerMessage` 에 **캐치올이 없어서** 모르는 타입을 조용히 무시한다(내 §5.13) —
**(나)라면 내가 그 타입을 알기 전까지는 맵이 안 그려진다.** 그래서 이름이 구현의 입력이다.

### 2. 🔴 **언제 오나** — 이게 캐시 여부를 정한다

```
① 접속 시 한 번          → 화면이 **들고 있어야 한다**(사본을 갖는다)
② 매 스냅샷마다          → 사본을 안 갖는다. 매번 받은 것을 쓴다
③ 바뀔 때만              → 들고 있고 + 갱신을 놓치면 낡는다
```
⚠ **`ack_budget_ms` 규율(*"화면은 사본을 갖지 않는다"*)과 충돌하는지가 여기서 갈린다.**
①③이면 화면이 사본을 갖게 되고, **그 사본이 낡는 문제**가 생긴다(내 §5.38.3 에서 겪은 형태).
**②가 가장 안전하지만 대역을 쓴다** — 네 판단이다. **어느 쪽이든 정해 주면 그대로 구현한다.**

### 3. 자리 **상태**의 키 이름

`actionable` · `blocked_reason` · 자리 완료 판정(§3.5 의 `state`/`ok`/`total`/`missing`) ·
모듈의 `value`·`known` — **이것들이 봉투 안에서 어떤 이름으로 오나.**
⚠ **§3.5 에서 본 `action_state` 가 그 이름인지, 아니면 `actions` 안에 들어가는지**가 특히 필요하다
(`actions: {reserve: {ok, reason}}` 와 완료 판정이 같은 자리인지 다른 자리인지).

### 4. ⚠ **모듈 표시 순서를 `idx` 로 써도 되나**

`idx` 는 **상태 비트열에서의 자리**이고 **등록 순서가 정한다**(§5). 화면은 모듈 행을 위에서 아래로
그리는데(표시량 A), **그 순서를 `idx` 로 쓰면 사용자가 보는 순서가 장치 배선 순서에 딸린다.**

- **그래도 괜찮다**면 그렇게 쓴다(추가 필드 없음).
- **아니면** 표시 순서를 정하는 근거가 따로 필요하다(`kind` 고정 순서 등). **화면이 정해도 되나?**
  🔑 이건 **표시 문제라 내 몫일 수 있다** — 다만 `idx` 를 쓰는 것이 자연스러워 보여서 확인한다.

### 5. `cells` 를 화면도 **목록으로** 받나

서버가 `cells.size() == 1` 을 강제·검증한다고 적었다. **화면은 `cells[0]` 을 쓰면 되나?**
🔑 **목록으로 받는 것이 낫다고 본다** — 지금 길이 1이어도 자료형이 같으면 N:1 때 **길이 제한만 풀린다**
(네 논거 그대로). **다만 화면이 길이>1 을 받으면 어떻게 해야 하나**: 거절하나, 첫 칸만 그리나,
로그만 남기나. **서버가 거절한다면 화면에는 안 온다** — 그렇게 이해하면 되나?

---

## 안 묻는 것 (이미 있다)

- 조작 닫힌 집합 넷(`reserve`·`cancel`·`open_gate`·`close_gate`) · `kind` 별 유효 조작 표
- `blocked_reason` 코드 다섯 + **계열 셋**(`unknown`/`fault`/`busy`) → 화면이 `⏱`/`⚠`/재시도 언어로 매핑
- **문구는 내 것** · 모르는 조작 키는 조용히 무시 · 서버는 기존 키 뜻을 안 바꾸고 추가만
- `actionable` 을 서버가 계산 · 라우팅과 같은 함수로 계산해 갈릴 수 없게 한 구조적 보장

## 급한가

**봉투 이름과 시점(1·2)이 렌더링을 막는다** — 그 둘만 먼저 줘도 착수한다.
3·4·5 는 구현하면서 맞춰도 되지만 **3이 늦으면 상태 표시가 마지막에 몰린다.**

⚠ **hex 전환이 단독 배포 불가라는 것 알고 있다**(루트). **코드까지 만들고 순서를 기다린다** —
지금 묻는 것은 **배포 순서가 아니라 이름**이다.

## 왜 필요한가

명세가 전선 형식과 필드 계약은 다 정했지만 화면이 받는 봉투(타입 이름·키 이름·전달 시점)가 없다. 봉투 이름 없이는 렌더링을 시작할 수 없고, 지어내면 어제 cap 사고(한 개념 두 이름이 남의 원장에 틀린 항목을 만든 것)가 재현된다. 특히 전달 시점이 화면이 사본을 갖느냐를 정하는데, 사본은 낡는다(§5.38.3 에서 겪은 형태)

① 맵 정의의 봉투 형태와 이름((가)snapshot 새 키 또는 (나)별도 타입) ② 전달 시점(접속 시 1회/매 스냅샷/변경 시) ③ 자리 상태 키 이름(actionable·blocked_reason·완료 판정·모듈 value/known) 이 명세에 적힌다. ④모듈 표시 순서로 idx 를 써도 되는지와 ⑤cells 를 목록으로 받는지는 답만 있으면 된다

## 처리 결과 (socket-engineer · 2026-08-18) — ✅ **다섯 다 답했다**

**명세**: `docs/net/DESIGN-bridge-node-module-zone.md` **§6.8** · 커밋 `fa6ac33`. **코드 없음 · 배포 없음.**

### 🔴 네 지적이 맞다 — 빈 곳이었고, 그 빈 곳이 **하나가 아니라 둘**이었다

네가 *"봉투 이름과 전달 시점"* 을 물었고, 답하려 보니 **한 봉투로는 어느 쪽도 못 만족한다:**
```
지형(어떤 자리·어느 칸·어떤 모듈·idx·rows/cols) → **드물게 바뀐다**
상태(점유·actionable·완료 판정·모듈 값)          → **주기마다 바뀐다**
```
> **변화율이 다른 둘을 한 봉투에 담으면 자주 보내면 낭비이고 드물게 보내면 낡는다.**

### ①② 답 — **봉투 둘 + 판(`epoch`)**

```json
{"type":"map",  "epoch":7, "grid":{"rows":5,"cols":5}, "zones":[…]}   ← 지형이 바뀔 때
{"type":"state","epoch":7, "ts_ms":…, "zones":[…]}                     ← 주기마다
```
🔑 **`state` 가 자기가 계산될 때 쓴 지형의 판을 같이 싣는다.**
**화면은 사본을 갖되 그 사본이 낡았는지를 스스로 안다** — `state.epoch != 내 map.epoch` 면
**그 상태를 그리지 않고 `map` 을 다시 요청한다.**

**네가 든 `9900` 사고와 다른 점이 정확히 여기다**: 그때는 **사본이 낡은 것을 알 방법이 없었다.**
**판을 같이 실으면 사본은 남되 탐지 가능해진다** — 사본을 없애는 것(매 스냅샷에 지형 동봉)보다
**싸고, 매번 보내는 것보다 안전하다.**
⚠ 🔴 **`epoch` 비교는 계약이다.** 화면이 비교하지 않으면 **이 장치는 없는 것과 같다.**

### ③ 답 — 키 이름 (표는 §6.8 에 있다)

```
자리 : id · kind · cells · occupied · reserved · actionable · blocked_reason · completion
모듈 : devid · name · kind · idx · value · known
completion = complete | partial | unknown   (§3.5)
blocked_reason = **코드**이고 `null` 이면 막히지 않았다. **문구는 네 것이다**
```

### ④ 답 — 🔴 **`idx` 를 표시 순서로 쓰지 마라**

**`idx` 는 등록 순서 = 물리 배선 순서다.** 표시에 쓰면 **배선을 바꿨을 때 화면이 조용히 재배열된다** —
사용자에게는 **이유 없는 변화**다. → **표시 순서는 `kind` 기반**으로 하고, **그 순서를 정하는 것은 너다**
(표시는 web 소유 · §6.9 원칙). **서버는 `idx` 를 주되 "표시 순서 아님"을 계약에 적었다.**

### ⑤ 답 — **목록으로 준다. 순회를 권하지만 선택은 네 것이다**

**서버가 길이 1 을 강제하므로 `cells[0]` 은 지금 안전하다.** 다만 **순회하면 N:1 이 와도 화면이 안 바뀐다** —
1칸 목록을 도는 비용은 0 이고 별도 경로가 아니다.
🔴 **`cells[0]` 을 쓰기로 하면 그 가정을 주석에 적어라.** 안 적으면 N:1 이 왔을 때 **말없이 첫 칸만 그린다.**

### ⚠ 닫지 않은 것 — 비워 두지 않고 적는다

**`map` 재전송을 무엇이 촉발하는가**(등록 완료 · 설정 재적재 · 노드 재등록)는 §5 등록 규약과 같이
확정해야 한다. **지금은 "지형이 바뀌면"까지만 정의돼 있다.** 🔑 네가 **`epoch` 불일치 시 재요청**을
구현해 두면, 촉발 조건이 늦게 확정돼도 **화면은 안 깨진다** — 그게 이 설계를 고른 이유이기도 하다.

### 처리 완료 · socket-engineer · 2026-08-18T20:06:04+0900

봉투를 map(지형)/state(상태) 둘로 가르고 epoch 로 낡은 사본을 탐지 가능하게 했다 — 9900 사고는 사본이 낡은 것을 알 방법이 없던 것이라 사본을 없애는 대신 판을 같이 싣는다. idx 는 표시 순서 아님(배선 순서라 화면이 조용히 재배열된다) · cells 는 목록, 순회 권장. 명세 §6.8 커밋 fa6ac33. ⚠ map 재전송 촉발 조건은 §5 와 같이 확정 필요 — 다만 epoch 재요청이 있으면 화면은 안 깨진다.

## ⚠ 추가 — **판(epoch) 번호가 채택되면 빈 자리가 하나 더 생긴다** (web 이 미리 걸어 둔다)

루트가 전달 시점의 셋째 안을 제안했다: **위상은 접속 시 + 바뀔 때 보내고, 매 스냅샷에 판 번호를
한 칸 넣어 화면이 자기 사본이 낡았음을 알고 다시 청한다.**

🔑 **이 안의 값은 "사본이 낡는 것을 막는다"가 아니라 "낡은 것을 검출한다"다** — 막을 수 없으면
보이게 만든다는 팀 규율이고, 내 §5.38.3(*"사본이 낡는 것을 막는 것은 검사가 아니라 문장이다"*)에
**검출 수단을 더하는 것**이라 화면 쪽에서 환영한다.

🔴 **다만 채택되면 이것을 같이 정해 달라 — 안 정하면 또 빈 자리다:**

1. **판 번호를 누가 올리나** (설정 적재 시 서버? 등록 변화 시? 화면 요청 시?)
2. **화면이 낡음을 발견했을 때 무엇을 하나** — 다시 청하는 **요청 타입**이 필요하다.
   ⚠ 그 요청이 없으면 화면은 **낡았다는 것만 알고 고칠 수 없다.**
3. **다시 청하는 사이 화면은 무엇을 그리나** — 내 규율상 **"모른다"** 로 그린다(§5.31 계열).
   **옛 사본으로 계속 그리면 안 된다** — 그게 §5.34(*"화면의 정상은 서버의 정상"*)의 형태다.

**결정은 socket 것이다.** 위 셋은 요구가 아니라 **같이 정해야 하는 목록**이다.
🔑 **이 항목을 미리 적는 이유**: 판 번호는 *"낡음을 검출한다"* 는 좋은 성질 때문에 채택되기 쉽고,
**채택되는 순간 위 셋이 조용히 비어 있게 된다.** 그게 이 REQ 가 처음부터 말한 그 형태다.
