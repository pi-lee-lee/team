# REQ-0202 · 🔴 구현 1.5 — cmdPending 구멍 즉시 수정 (사용자가 실물 재현) · ack_budget_ms 를 써라

**요청자** `root` → **담당** `web-engineer`

## 요청 내용

🔴 **네가 찾아 놓고 미룬 구멍을 사용자가 실물로 재현했다. 즉시 수정이다.**

## 사용자 보고 — 그리고 우리가 처음에 잘못 쫓았다

```
사용자 1차 : "한걸음 진행을 20개 이상 보내면 esp01이 리셋된다"
우리 조사   : 재현 관측 · 탭 개방 · 후보 셋(큐 상한 / 아이들 간극 / cmdPending)
              🔴 그런데 시리얼 로그에 리셋 표지 0건
사용자 2차 : "'응답이 없습니다. 자체타임아웃' << 이게 리셋 아닌가?"
1초 만에 갈림 : index.html:1948 · sim_step 경로 · **장치는 정상이다**
```

**`sim_step` 이 "한걸음 진행"이고, 화면이 자기 타이머로 포기한 것이다.**

## 기전 — **네 판독 그대로다**

> `queued` 분기가 `state.pending` 만 보고 **`state.cmdPending` 은 안 본다.**
> `M`·`T` 도 같은 큐를 타므로 **큐에 담기고 `queued` 가 오는데 화면이 조용히 버리고
> 6초 고정으로 거짓 실패를 낸다.**

```
20개 연타 → 큐에 쌓인다 → 서버가 queued 를 보낸다
→ sim_step 경로가 그 프레임을 버린다 → 6초 고정 타이머 만료 → "응답이 없습니다"
```

**서버도 장치도 정상인데 화면만 실패라고 말한다.** 🔴 **그리고 그것이 재클릭을 부른다** —
**REQ-0166 에서 예약 경로에 닫은 증폭 고리가 이 경로엔 열려 있다.**

⚠ **네 판단(*"피해가 예약보다 작다"*)이 실물로 뒤집혔다.** **20개 규모에서는 거의 확실히 재현된다.**
🔑 **다만 그 판단이 틀린 게 아니라 근거가 소스 판독뿐이었고 실측이 없었다** —
너도 *"소스 판독이고 실측 아니다"* 라고 명시했다. **그 표시가 있어서 지금 바로 뒤집을 수 있었다.**

## 고칠 것

```
① queued 분기가 state.cmdPending 도 본다
② 🔴 6초 고정 대신 ack_budget_ms(12600)를 쓴다
   지금 서버 계약값: ACK_TIMEOUT 2400ms · 큐대기마감 4800ms · ack_budget_ms 12600
   → 6초는 큐 대기(최대 4800ms)를 못 견딘다. 구조적으로 모자란다
③ 예약 경로(REQ-0166)와 같은 처리 — 그쪽은 닫혀 있고 이쪽은 안 닫혔다
```

⚠ **한 교체에 변경 둘을 넣지 마라** — **이 구멍만 고쳐라.** 화면 개정(4단계)은 그대로 나중이다.

## 끝의 조건 — **사용자 조작으로 검증한다**

```
20개 이상 연타에서
  · "자체 타임아웃" 이 안 난다
  · queued 가 화면에 보인다 (받았고 아직 안 보냈다)
```

🔴 **이 결함을 드러낸 유일한 자극이 사용자 조작이다.** 하니스로는 안 나왔다 —
**하니스가 그 경로를 안 밟는다는 것 자체도 기록할 값이 있다.**
⚠ **가능하면 하니스에 그 경로를 추가해라** — 안 그러면 다음에 또 사람이 찾아야 한다.

## 배포

**서버는 이미 새 값으로 돌고 있다**(`build=c719d87` · pid 80947 · 12:28:40).
**화면만 바꾸면 된다.** 배포 방법은 네 도메인이니 네가 정해라 —
⚠ **운영 `9900` 에 사용자 브라우저가 붙어 있다.** 사용자가 바로 다시 눌러 볼 수 있어야 한다.

## 진행을 원장에 남겨라
