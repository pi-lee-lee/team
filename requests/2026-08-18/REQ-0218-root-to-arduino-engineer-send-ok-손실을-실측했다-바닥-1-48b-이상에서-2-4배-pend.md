# REQ-0218 · 🔴 SEND OK 손실을 실측했다 — 바닥 1%, 48B 이상에서 2~4배. pendLine/잘림 대비를 만들어라

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

🔴 **네 `pendLine` 가설을 원문으로 검증했다. 방향이 맞고, 숫자가 나왔다.**
**그리고 네가 예상한 것보다 나쁘다 — 상시로 잃고 있다.**

## ① 원문 — `winF` 의 T2 사건 직전 (n=214)

```
[TX] S,200,1110011010,0000000000,256,P1,31   ← tx=135 배치
[SLOT] n=214 tx=135 ack=7 due=0 r=1
[AT] " S,200,1110011010,0000000000,256,P1,31A,451,B2,0,31A,452,A5,0,3" (63)  ← 🔴 63자에서 잘림
[AT] "+IPD,72:M,458,74" (16)     ← 송신 중에 하행이 들어온다
[SLOT-OOW] +369ms
[AT] "M,459,75" … "M,465,7A"     ← 8줄 더
[AT] "OK" (2)
[AT] "AT+CIPSEND=136" (14)
🔴 SEND OK 가 **끝내 안 나온다**
[TX-WAIT] 앞 전송의 SEND OK 를 아직 못 봤다 — 이번 주기는 건너뛴다
[TX-WAIT] ★ T1 초과
```

⚠ **`[AT]` 줄 길이 분포를 봤다: 최대가 67이고 63이 20건으로 몰려 있다.**
**버퍼 상한이 64 근처다.** 🔑 **즉 네가 말한 "두 번째 줄을 버린다"보다 먼저,**
**긴 에코가 잘려서 뒤에 붙은 것이 아예 사라질 수 있다.** 어느 쪽인지는 **네가 소스로 갈라라.**

## ② 🔴 상시로 잃고 있다 — **`AT+CIPSEND=` 와 `SEND OK` 를 짝지어 셌다**

```
창      선언크기 48B 미만            48B 이상
winE    169/13192  = 1.28%       13/505  = 2.57%     ← 2.0배
winC    142/16035  = 0.89%       11/304  = 3.62%     ← 4.1배
winF     51/3798   = 1.34%       10/42   = 23.8%     ← ⚠ 분모 42, 참고만
```

> ### **분모가 크다(1.3만·1.6만). 방향이 세 창에서 같다.**
> ### 🔑 **① 상시 손실이 약 1% 있다 — 이건 크기와 무관한 바닥이다**
> ### 🔴 **② 페이로드가 커지면 손실률이 2~4배로 오른다**

**②가 사용자 질문의 답이다** — *"실어보내는 용량이 많아서 터지는건가?"*
**용량이 크면 `SEND OK` 를 잃을 확률이 오르고, 잃으면 게이트가 안 풀린다.**

## ③ 손실이 곧 T2 는 아니다 — **분모를 하나 더 찍었다**

```
winF:  SEND OK 손실 61건 · "이번 주기 건너뛴다" 102회 · T1 초과 19 · 🔴 T2 초과 14
       [SLOT] 총 3956
```
**대부분은 회복된다**(늦게 오거나 다음 주기에 잡힌다). **일부만 T2 8초까지 간다.**
⚠ **그러니 "손실 = 재접속"으로 쓰지 마라.** 두 숫자는 다른 것을 센다.
**T2 14건이 서버가 본 `8.4초 공백 + 재접속` 과 자릿수가 맞는지는 monitor 가 대조한다.**

# 고칠 것 — **네가 형태를 정해라. 나는 무엇을 지킬지만 준다**

```
1. 🔴 SEND OK 를 놓치지 마라 — inSend 구간의 **모든** 줄을 봐야 한다
   ⚠ 접두 비교(strncmp(s,"SEND OK",7))로는 앞에 뭐가 붙으면 못 잡는다 → **부분일치**로
2. 🔴 잘림 대비 — 상한 64 근처에서 잘리면 뒤에 붙은 SEND OK 가 사라진다
   → 줄 단위가 아니라 **바이트 흐름에서 찾는 방법**을 검토해라(작은 상태기계면 RAM 몇 B)
3. ⚠ 상행 배치 상한 — 지금 없다(tx=151 관측). ②가 크기 의존을 보였으므로 이제 후보다
```

## 🔴 축을 나눠라 — **1·2 를 먼저, 3 은 다음 굽기**

**1·2 는 "잃던 것을 안 잃는다"이고 3 은 "보내는 양을 바꾼다".**
**같이 넣으면 손실률이 내려간 이유가 갈리지 않는다.** 오늘 우리가 그것 때문에 반나절 썼다.

🔑 **검증 지표는 이미 있다: `AT+CIPSEND=` 대 `SEND OK` 짝짓기.** 위 표를 그대로 다시 낸다.
**1·2 가 먹으면 바닥 1% 가 내려가야 하고, 크기 의존(2~4배)도 같이 내려가야 한다.**
⚠ **크기 의존만 남으면 원인이 잘림이 아니라 다른 것이다** — 그때 3 으로 간다.

## 왜 필요한가

AT+CIPSEND= 와 SEND OK 를 짝지어 세니 세 창에서 같은 방향이 나왔다 — 손실 바닥 약 1%(분모 1.3만·1.6만), 페이로드 48B 이상에서 2~4배. SEND OK 를 잃으면 게이트가 안 풀리고 T2 8초 뒤 TCP 재접속이 되며 그것이 서버의 8.4초 공백 클러스터와 자릿수가 맞는다

```c
for (uint16_t i = 0; i < len; i++) {
  wifi.write((uint8_t)line[i]);

```
**왜 16B**: 최악에도 링버퍼에 16B 만 쌓인다 → **64B 대비 4배 여유.**
