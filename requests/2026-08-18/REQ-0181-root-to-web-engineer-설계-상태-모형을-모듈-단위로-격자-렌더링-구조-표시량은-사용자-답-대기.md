# REQ-0181 · 설계 — 상태 모형을 모듈 단위로 · 격자 렌더링 구조 · 표시량은 사용자 답 대기(막지 않는다)

**요청자** `root` → **담당** `web-engineer`

## 요청 내용

**사용자 지시**: *"관측작업이 완전히 완료되면 설계작업까지 이어간다. 확인이 필요한 사항들은
정리만 해두고 확인없이 진행할수 있는 일들을 처리한다."*

**너의 조사(`docs/web/ANALYSIS-redesign-impact-2026-08-17.md`)가 이 REQ 의 근거다.**
그 문서가 없었으면 내가 짐작으로 요구사항을 썼을 것이다.

## 🔴 먼저 — 네 질문은 사용자 확인 대기로 정리해 뒀다

`docs/DECISIONS-pending-user-2026-08-18.md` §① 에 **모듈 표시량**(칸 안에 다 / 눌러 펼치기 / 집계만)을
네 표현대로 셋의 대가까지 담아 올렸다. **답이 오면 전한다.**

**그런데 그 답이 너를 막지 않는다** — 내가 그 문서에 이렇게 적었다:

> **데이터 계약(`kind`·모듈 목록·`known` 모듈 단위)은 그 답과 무관하므로 먼저 만들 수 있다.**

**즉 화면 구조는 기다리고, 계약과 상태 모형은 지금 설계해라.**

## 할 것 — 설계 문서 하나 (`docs/web/`)

### ① 상태 모형을 모듈 단위로 내린다

네가 찾은 것이 그대로 요구사항이다:

```
지금 : known 이 자리 단위 불리언 · device.online 하나가 10칸 전부의 조작 가능성을 정한다
개정 : known 이 모듈 단위 · 조작 가능성은 그 모듈이 속한 노드의 생존으로 판정
```

🔴 **사용자가 확정한 원칙이 여기 착지한다**: *"모든 아두이노는 독립이다. 하나가 와이파이를 못
잡아도 다른 것에 영향이 없다."* → **구역 상태를 여러 노드에서 조립하므로
"일부만 아는 상태"가 예외가 아니라 상시 정상 상태다.**

**그러므로**: **전체를 회색으로 덮으면 안 된다. 미상인 모듈만 미상으로 그린다.**

### ② `⏱` / `⚠` 구분을 모듈 층으로 확장 — **네가 이미 한 번 푼 문제다**

§5.7 에서 폴백 문구를 고칠 때 만든 구분이다: **`⏱` 는 모른다, `⚠` 는 고장.**
**미상이 상시가 되면 경보로 그리면 화면을 못 쓴다.**

⚠ **그리고 네가 같이 적은 반대 함정을 유지해라**: 너무 조용하면 REQ-0067(모르는 것을 아는 것처럼)로
돌아간다. **"조용하되 반드시 보여야 한다."** §3.1 의 교훈(칸 문구만으로 부족해 집계 배너를 넣었다)이
유효하고, **미상 모듈 집계 한 줄**이 후보라고 네가 적었다. **그것을 명세에 넣어라.**

### ③ 격자 렌더링 — 구조만. 크기·배치는 기본값

`cell → zone` · `zone.kind: parking|entrance|exit`. **입구·출구는 구조가 같고 상태 어휘가 다르다** —
네 지적대로 `tileView` 의 7개 상태가 전부 **예약 가능한 주차 자리** 기준이고 **입구에 "예약됨"이 없다.**
`unknown` 으로 떨어뜨리면 **존재하는 것을 없다고 말한다.**

⚠ **격자 크기·초기 배치는 사용자 미상이다**(`DECISIONS` §③). **기본값 `5×5` · 자리 하나가 한 칸으로
가정하고, 설정으로 바뀔 수 있게 설계해라.** 사용자가 *"유동적으로 변경 가능"* 을 요구했으니
**초기 배치는 예시일 뿐 구조가 그것에 묶이지 않아야 한다.**

🔴 다만 하나는 확인 값이 있어서 올려 뒀다: **"자리 크기도 유동"이면 칸→자리가 N:1 이 된다**(큰 자리가
2칸 차지). 그러면 구조가 달라진다. **일단 1:1 로 설계하고 그 가정을 문서에 명시해라.**

### ④ 배포 순서 제약 — 네가 짚은 것을 계약으로 올렸다

> 새 타입은 옛 화면이 조용히 무시해 안전하지만, **기존 `slots[]` 항목에 필드를 넣어 뜻을 바꾸면
> 서버 배포가 그 순간 옛 화면을 깨뜨린다.**

→ **맵 정의를 `slots[]` 에 얹지 말고 별도 키로 추가**하는 근거다. socket 의 REQ-0179 에 넣었다.

### ⑤ 안 깨지는 목록을 문서에 옮겨라

네 §5.32.2 다. 🔑 **그 목록의 값은 "안 바뀐다"가 아니라 "왜 안 바뀌는지"** 라는 네 말이 맞다 —
**아이들 1초가 살아남는 이유는 자리가 아니라 전선에 걸려서다.** 근거가 없으면 다음 사람이 다시 본다.

### 0. 먼저 한 일 — **이름을 만들지 않았다**

명세를 쓰기 전에 `docs/net/` 과 REQ-0179 를 grep 했다. **socket 이 이미 이름을 세워 뒀다**:
`Zone` · `zone id` · `kind: parking|entrance|exit` · `modules: [(devid, name)]` · `cell → zone id` ·
**전역 신원은 `(devid, name)` 복합 키**(`name` 단독 조회 금지). **그것을 그대로 쓴다.**

**왜 이걸 먼저 했나**: 같은 개념에 두 문서가 각자 이름을 붙이면 어제 `cap` 사고(한 문서 안에서
두 뜻 · 팀 전체로 세 뜻 · 그 모호함이 **내 원장에 틀린 항목을 만들었다** · 원장 §5.27)가
**그대로 재현된다.** 두 REQ(0179·0181)가 병렬로 돌고 있어 위험이 실재했다.

🔑 **덤으로 내 열린 물음 하나가 닫혔다**: 원장 §5.32.1 의 *"자리 ID 와 격자 좌표를 가르는가"* —
REQ-0179 §① 이 **"좌표와 신원은 독립"** 으로 이미 갈라 뒀다. **내가 닫은 것이 아니라 REQ-0179 가
닫았다**는 것을 명세에 적었다(근거의 출처를 바꿔 적지 않는다).

### 2. 🔴 REQ 문구와 다르게 쓴 곳 하나 — **조작가능성을 누가 계산하나**

REQ ①의 *"조작 가능성은 그 모듈이 속한 노드의 생존으로 판정"* 은 **화면이 조합하는 것처럼**
읽힌다. **규칙은 그대로 받고, 계산 주체는 서버로 요구했다**(명세 §1.3):

- 화면이 조합하면 **조합 규칙이 두 곳**(서버 하행 라우팅 + 화면)에 생기고, 갈리는 순간 화면이
  **거짓 허용**을 낸다 — 닿지 않는 노드로 하행이 나가고 **큐에 쌓여 재전송까지 돈다.**
  (루트가 채택한 내 판정 *"거짓 허용이 더 나쁘다"* 가 바로 이 자리다.)
- 팀 규율이 이미 같은 형태를 풀었다 — 원장 §5.14 *"화면이 짐작하지 않는다"* ·
  그 규율을 적용한 `ack_budget_ms`(§5.26)가 실제로 구멍 하나를 막았다.

⚠ **이것이 socket 합의가 필요한 단 하나다.** 나머지는 표시 문제라 내 도메인에서 닫힌다.
⚠ 그리고 **모듈 목록은 여전히 필요하다** — **판단은 서버, 표시는 목록.** 섞으면 안 된다.

### 3. ③의 내부 모순을 규칙으로 풀었다 — **기호축 × 강조축**

REQ 가 요구한 두 가지가 서로 민다: 미상이 **상시 정상**인데 집계를 상시로 띄우면 **§3.1 이
피하려던 "상시 켜진 경고"** 가 되고, 너무 조용하면 **REQ-0067**(모르는 것을 아는 것처럼)로 돌아간다.

**한 축으로 풀려던 것이 모순의 원인이었다.** 두 축으로 갈랐다:

```
기호축 = 원인   ⏱ 모른다 / ⚠ 고장·차단 확정
강조축 = 영향   조작을 막는가 → 막으면 눈에 띄게, 안 막으면 조용한 배경
```

🔑 **강조축을 화면이 계산하지 않는다** — §2 의 `actionable`/`blocked_reason` 에서 **파생으로
나온다.** 즉 계산 주체를 정하면 이 규칙이 따라오고, **집계가 정상에서 저절로 침묵한다**
(주차확인센서 미상은 세고, 안내등 미상은 안 센다). **미학 문제가 규칙 문제로 내려왔다.**

⚠ **집계에서 빠지는 것과 화면에서 사라지는 것은 다르다** — 조작을 막지 않는 미상도 칸 안에는
조용히 남는다. 이것이 §2.3 에 명시돼 있다.

### 4. 명세에서 새로 나온 것 — **빈 칸과 미상 자리가 격자에서 충돌한다**

`5×5=25칸` 에 자리 5 + 입출구 → **18칸 안팎이 빈 칸**이다. 지금 코드는 `slots` 에 없는 ID 를
`view:'unknown'`("상태 미상" 점선)으로 그리므로, **격자에서 그대로 두면 빈 칸 18개가 "상태
미상"으로 보이고 §3 의 집계가 쓸모없어진다.**

→ **빈 칸 / 미상 자리 / 정상 자리 셋을 다르게 그린다.** 그리고 🔑 **이 구분은 "맵 정의를 상태와
별개로 준다"(§5.32 ①)가 있어야만 가능하다** — 상태만 오면 *"안 온 것"* 과 *"없는 것"* 이 같아
보인다. **계약 항목이 왜 필요한지가 여기서 구체화된다**(원장 §2.4 함정의 격자 판본).

### 5. 1:1 가정 — 명시에서 멈추지 않았다

N:1 이 되면 **무엇이 깨지는지 이름으로** 적었다(명세 §3.4): `cell → zone` 다대일 ·
**맵 정의가 기하(원점+span)를 실어야 한다 → 계약이 바뀐다** · 타일 배치가 span 기반 ·
빈 칸 계산.

🔑 **그리고 안 깨지는 것을 확인했다**: 주소 방식(`data-zone`)은 DOM 노드가 zone 마다 하나라
칸 수와 무관하다 → **상태 모형(§1)·표시 규칙(§2)은 N:1 에서도 그대로다.**
**즉 재작업이 격자 층에 갇힌다 — 그것이 1:1 로 먼저 가도 되는 근거다.**

### 6. 안 한 것 · 남은 것

- **표시량 의존부는 명시적 빈칸으로 격리했다**(명세 §5). 결정된 것처럼 적어 두면 답이 왔을 때
  재작업이고 그게 가장 되돌리기 비싼 부분이다. **규칙은 정해졌고 형태만 남았다.**
- **폴백 상한 문구(§5.31)는 장치 하나를 전제한다** — 노드가 N 개면 `last_frame_ts` 도 N 개다.
  **모듈마다 "언제 확인된 값인가"가 필요해질 수 있다. 미정으로 남겼다.**
- **임계값 스윕 3·4초** — 창 B 판정 뒤 인스턴스에서. 신호 대기.
- **실측 0.** 개정 코드가 없으므로 잴 것이 없다 — 명세의 숫자는 **하나도 측정값이 아니다.**
