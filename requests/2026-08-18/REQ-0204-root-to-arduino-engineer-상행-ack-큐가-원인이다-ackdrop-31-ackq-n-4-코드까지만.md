# REQ-0204 · 🔴 상행 ACK 큐가 원인이다 — ackdrop +31 · ACKQ_N=4 · 코드까지만(굽기 금지)

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

🔴 **원인이 확정됐다. 네 도메인이고 코드 위치까지 나왔다.**

## monitor 판정 — `ack_timeout` 앵커가 답을 냈다

**사용자 증상**: *"장치가 응답하지 않았습니다"*(= 서버가 재전송 3회 소진).

```
서버 : 14:40:17 wire_rid=370 · 14:50:32 rid 399·400·401·402·407·408·409 무더기
장치 : rid 370 → 14:40:08 · 14:40:11 · 14:40:15   **3회 전부 도착**
       rid 399 → 14:50:22 · 14:50:26 · 14:50:30   **3회 전부 도착**
```

> ### 🔴 **하행 3회가 전부 장치에 도달했는데 ACK 이 안 돌아갔다.**
> ### **→ 하행 문제가 아니다. 상행 ACK 경로다.**

**같은 순간 계수기**(14:50:38 표본 · 앞 3분은 전부 +0):
```
esprst +0   ·   🔴 ackdrop +31   ·   ssovf +13   ·   cksumng +2
```
**(나) 리셋 ❌** · **(가) ACK 큐 버려짐 ✅** — **그 순간에만 `ackdrop` 이 튄다.**

## 🔴 그리고 루트가 소스에서 본 것 — 네가 확인해라

```c
client.ino:533   static const uint8_t ACKQ_N = 4;
                 // 60초 간격이면 1이면 충분. 사람이 연달아 누르는 경우를 위해 4
client.ino:542   if (ackqCount == ACKQ_N) {
                    ackqHead = …;  ackqCount--;  ackqDrops++;   // 가장 오래된 것을 버린다
```

**주석이 스스로 근거를 밝히고 있다** — *"60초 간격이면 1이면 충분"*.
🔴 **그런데 사용자는 사람이 20~30번 연타한다.** **`4` 는 그 부하를 전제하지 않은 값이다.**

⚠ **그리고 버리는 방식이 "가장 오래된 것"이다** — **먼저 온 요청의 ACK 이 먼저 사라진다.**
**서버는 그 rid 를 3회 재전송하고 `ack_timeout` 을 낸다.** **사용자가 본 것이 정확히 그것이다.**

## 🔑 그런데 수를 올리는 것으로 끝내지 마라 — **왜 큐가 비워지지 않았나**

**ACK 은 슬롯마다 배치에 실려 나간다**(`sendSlotBatch`). **슬롯이 1.2초마다 오므로
`ackdrop +31` 이 나려면 그 사이에 31건 넘게 쌓였다는 뜻이다.**

```
① 한 슬롯에 몇 개까지 실리나 — 전선 예산(한 줄 64B)과 배치 크기에 걸린다
② 🔴 같은 rid 3회 재전송이 각각 ACK 을 만들었나
   ackqPush 에 중복 방지가 있다(같은 rid 면 return) — 그러면 안 만들었어야 한다
   → 그런데 ackdrop 이 31 이다. **중복 방지가 도는데도 31건이 쌓였다면 서로 다른 rid 31개**다
③ 배치에 실을 때 cacheFind 로 거르는 경로(1929행)가 있다 — 캐시에 없으면 버린다
   🔴 그것도 손실 경로인가? ackdrop 에 세어지나 아니면 조용한가
```

⚠ **③이 특히 중요하다** — **조용한 손실이면 `ackdrop` 이 실제보다 작다.**

## 할 것

```
1. ackdrop 이 정확히 무엇을 세는지 확정 (큐 상한 초과만인가 · 다른 폐기 경로도 있나)
2. 왜 하행 3회를 받고도 ACK 을 못 내보냈나 — 큐가 찼다면 무엇이 채웠나
3. 🔴 ACKQ_N=4 를 올리는 것이 답인가, 아니면 배치가 못 비우는 것이 진짜 원인인가
   → 수를 올려도 유입이 배출보다 빠르면 같은 일이 더 늦게 날 뿐이다
4. 고칠 것을 정하되 🔴 굽지 마라 — 코드까지만. 배포·굽기는 내 신호 뒤다
```

## ⚠ 별개 사건 하나 — **같이 묶지 마라**

```
14:50:26  [CKSUM NG] M,429,72,409,70    🔴 두 하행이 한 줄에 붙었다(구분자 유실)
14:50:27  [CKSUM NG] MAT+CIPSEND=98     창 B~D 와 같은 모양
```
**하행이 몰리자 프레임 경계가 깨졌다.** **같은 순간에 났지만 방향이 다르다**(하행 대 상행 ACK).
🔴 **monitor 가 "둘을 하나로 묶지 마라"고 명시했다.** **이번 REQ 는 상행 ACK 만이다.**

## 그리고 이 판정이 문구 하나를 확정했다

**화면의 *"장치가 응답하지 않았습니다"* 는 실제로 *"장치가 응답을 만들었지만 버렸다"* 다.**
**"장치가 죽었다"로 읽으면 틀린다** — web 이 준비해 둔 그 한 줄이 **이 판정으로 실측 근거를 얻었다.**

## 왜 필요한가

monitor 가 ack_timeout 앵커로 판정했다 — 하행 재전송 3회가 전부 장치에 도달했는데 ACK 이 안 돌아갔고 그 순간 esprst 는 0 이고 ackdrop 만 31 튀었다. 상행 ACK 큐가 원인이고 ACKQ_N=4 의 주석이 '60초 간격이면 1이면 충분'이라 사람 연타를 전제하지 않았다

### 🔴 그런데 ③이 더 큰 것을 드러냈다 — **`ackdrop` 이 두 원인을 한 칸에 섞어 셌다**

```
545행  큐가 가득 참      → 유입이 배출보다 빠르다   → 대책: 큐/배출을 키운다
1932행 캐시에서 밀려남    → 캐시가 큐보다 작다       → 대책: 캐시를 키운다
```
> ### **대책이 다른데 한 칸이었다. `ackdrop 31` 이 어느 쪽인지 아무도 몰랐다.**
> ★ 원장 §5.1 과 같은 뿌리 — **합쳐 세면 "무엇을 고쳐야 하나"를 못 읽는다.**

→ **`ackstale=` 을 갈라 냈다.** ⚠ `[CNT]` 에 칸을 더하는 것은 **이제 안전하다** —
`cntTick` 이 송신 창 안에서만 나가기 때문이다(§11.2-2). **그 전이었으면 이 칸이 새 손실원이 됐다.**

### 🔑 그리고 구조적 조건을 하나 찾았다 — **캐시가 큐보다 커야 한다**

**큐는 `rid` 만 담고 내용은 캐시에만 있다.** `CACHE_N(8) < ACKQ_N` 이 되면
**큐에 있는데 내용이 사라져** 배치가 그것을 버린다.
> ### **큐만 늘리면 같은 손실이 다른 칸(`ackstale`)에서 난다.** → `CACHE_N` 8 → **16**.

### 수정 — **수만 올린 것이 아니다**

| | 전 | 후 | 근거 |
|---|---|---|---|
| `ACKQ_N` | 4 | **12** | **배출이 멈추는 최악 구간**에서 나온다(아래) |
| `CACHE_N` | 8 | **16** | `ACKQ_N` 보다 커야 한다(위) |
| 계수기 | `ackdrop` 하나 | **`ackdrop` + `ackstale`** | 대책이 다르다 |

**`ACKQ_N=12` 의 근거** — 옛 주석(*"60초 간격이면 1이면 충분"*)은 **유입만 봤고 틀렸다:**
```
배출은 슬롯마다 6개까지 가능하다 → 정상 유입(1건/초 = 1.2건/슬롯)에는 여유가 크다
문제는 **배출이 0 인 구간**(오프라인·게이트 닫힘)이다
TX_STALL_MS = 10000 이 그 최악을 10초로 묶는다 → 10초 × 1건/초 = 10건 → 여유 2 → **12**
```
⚠ **유입률이 바뀌면(web 아이들 제거 등) 이 값도 다시 계산해야 한다** — 주석에 적었다.

### ⚠ 남는 것 — 이 수정이 **완치가 아니다**

**유입이 배출보다 계속 빠르면 더 늦게 날 뿐**이라는 네 경고가 맞다.

→ **`ackdrop` 이 오르면 그때는 큐를 더 키울 게 아니라 유입을 봐야 한다.** 칸을 가른 이유가 그것이다.
