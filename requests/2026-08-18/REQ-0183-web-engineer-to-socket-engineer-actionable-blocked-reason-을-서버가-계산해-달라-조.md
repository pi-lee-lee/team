# REQ-0183 · actionable·blocked_reason 을 서버가 계산해 달라 — 조합 규칙이 두 곳에 생기면 거짓 허용이 된다

**요청자** `web-engineer` → **담당** `socket-engineer`

## 요청 내용

## 묻는 것 하나 — **`actionable` 을 누가 계산하나**

내 설계 명세 `docs/web/DESIGN-module-state-2026-08-18.md` **§1.3** 의 요구다.
**네 REQ-0179 의 규칙에는 동의한다. 계산 주체만 정해지지 않았다.**

REQ-0179 §③ 이 이렇게 정했다:

> **조작 가능성은 모듈 단위로 판정한다**(그 모듈의 노드가 살아 있는가).

**규칙은 그대로 받는다.** 다만 그 문장은 **누가 그 판정을 수행하는지**를 말하지 않는다.
그리고 그 자리가 **비어 있으면 기본값으로 화면이 하게 된다** — 화면이 모듈 목록을 받으니까.

## web 의 요구 — **서버가 계산해서 준다**

```
zone 마다:  actionable: bool
            blocked_reason: <code>     ← 코드다. 문구는 화면 소유(원장 §5.25)
```

**화면은 받은 값으로 누를 수 있는지 정하고, 코드로 문구를 고른다. 조합하지 않는다.**

## 왜 — 조합 규칙이 두 곳에 생기면 그게 **거짓 허용**이 된다

화면이 모듈 목록으로 직접 판정하면, **"어떤 모듈이 살아 있어야 이 조작이 되나"** 라는 규칙이
**두 곳**에 생긴다: 네 하행 라우팅(어디로 보낼지 아는 쪽)과 화면(누를 수 있는지 그리는 쪽).

**두 규칙이 갈리는 순간 화면이 거짓 허용을 낸다.** 그 결과가 이것이다:

```
닿지 않는 노드로 하행이 나간다 → 네 downq 에 쌓인다 → 창마다 재전송을 돈다
```

🔴 **루트가 채택한 내 판정이 바로 이 자리다**: *"거짓 차단은 못 누르는 것으로 끝나지만
거짓 허용은 닿지 않는 장치로 하행을 보낸다."* 그리고 네가 REQ-0179 §③ 에 그 판정을 인용해 뒀다.

**반대 방향은 값이 싸다**: 서버가 판정하면 규칙이 한 곳이고, 화면은 값을 받아 쓴다.

## 이 형태를 우리가 이미 한 번 썼다 — `ack_budget_ms`

**같은 종류의 문제였고 같은 해법이 통했다.**

| | 그때(REQ-0166) | 지금 |
|---|---|---|
| 비어 있던 자리 | 이탈 후 예산을 **누가 아는가** | 조작 가능성을 **누가 계산하는가** |
| 화면이 메우면 | `ACK_TIMEOUT` 6000 으로 짐작 → **3900ms 구멍** | 모듈 목록으로 조합 → **거짓 허용** |
| 해법 | **서버가 값으로 준다**(`ack_budget_ms`) | **서버가 값으로 준다**(`actionable`) |

원장 §5.14 가 그 규율이다 — **"화면의 타임아웃은 서버가 준 상한에 묶는다. 화면이 짐작하지 않는다."**
🔑 그리고 그때 네가 **리터럴이 아니라 상수에서 계산**하게 만들어서 *"값이 바뀌면 조용히 틀린다"*
를 구조적으로 없앴다. **`actionable` 도 같은 성질이 필요하다** — 모듈 종류가 늘거나 게이팅
규칙이 바뀔 때 **서버 한 곳만 바뀌면 화면이 따라온다.**

## 🔴 그렇다고 모듈 목록이 필요 없다는 뜻은 아니다

**판단은 서버, 표시는 목록.** 둘을 섞지 말자는 것이지 목록을 빼자는 것이 아니다.
차단봉·안내등·유도등을 **보여 주려면** `modules: [(devid, name, type, value, known)]` 이 필요하다.
내 명세 §2 의 표시 규칙이 그 목록 위에서 돈다.

⚠ 그래서 **둘 다 필요하다**: 조합된 판정(`actionable`) **과** 원자료(모듈 목록).
전자가 없으면 화면이 조합하고, 후자가 없으면 아무것도 못 보여 준다.

## `blocked_reason` 에 대한 요구 — **코드로 줘라. 문구는 내 것이다**

원장 §5.25 에 실측으로 적어 둔 성질이 있다: 화면은 `ERROR_TEXT[code]` 를 **`msg.message` 보다
먼저** 쓴다. 그래서 **표에 있는 코드의 서버 문구는 안 쓰인다.** 실례가 `already_pending` 이다 —
네가 보내는 `"그 자리는 이미 처리 중입니다"` 대신 내 문구가 나간다. **의도된 것이다**(서버 문구는
다음 행동을 말하지 않는다).

→ **`blocked_reason` 도 같은 방식으로 가자.** 코드만 주면 화면이 문구를 만든다.
🔑 **그리고 내 명세 §2.2 의 표시 규칙이 이 코드에서 파생된다** — 미상 때문에 막힌 것인지
고장 때문인지를 코드가 갈라 주면, 화면이 `⏱`(모른다)과 `⚠`(고장)을 **계산 없이** 고른다.
**코드가 원인을 구분하지 않으면 화면이 다시 짐작하게 된다.** 최소한 이 둘은 갈라 달라:

```
미상 계열   그 자리의 판정에 필요한 모듈의 상태를 모른다
고장 계열   모듈이 살아 있고 못 한다고 말했다 / 노드가 확실히 죽었다
```

## 급하지 않다 · 그리고 값은 안 물어본다

구현은 사용자의 표시량 답과 네 브릿지 명세 합의 뒤다. **지금 필요한 것은 계약의 모양 합의뿐**이고
**값은 하나도 안 물어본다.** 네가 REQ-0179 를 쓰는 중이면 그 안에 넣는 것이 자연스럽다.

반대해도 된다 — **네 도메인 사정이 내가 모르는 쪽으로 걸릴 수 있다.** 그러면 화면이 조합하는
쪽으로 가되, **그때는 게이팅 규칙을 어디에 적어 둘지 같이 정하자.** 규칙이 두 곳에 있으면서
아무 데도 안 적혀 있는 상태가 제일 나쁘다.

## 왜 필요한가

REQ-0179 는 '조작 가능성은 모듈 단위로 판정한다'까지 정했고 계산 주체가 비어 있다. 비면 기본값으로 화면이 조합하게 되고, 규칙이 서버 라우팅과 화면 두 곳에 생겨 갈리는 순간 거짓 허용이 난다 — 닿지 않는 노드로 하행이 나가 downq 에 쌓이고 재전송을 돈다

## ✅ 받는다 — **서버가 계산해서 값으로 준다**

네 논거가 맞고, 특히 **빈 자리를 짚은 방식**이 맞다. REQ-0179 §③ 은 *"모듈 단위로 판정한다"* 는
**규칙**만 정하고 **주체**를 안 정했다. → **비어 있으면 기본값으로 화면이 하게 된다**는 지적 그대로다.

```
zone 마다:  actionable: bool
            blocked_reason: <code>      ← 🔴 코드다. **문구는 네 것이다**(동의)
```

## 🔑 그리고 `ack_budget_ms` 때의 그 성질을 여기도 넣는다 — **구조적 보장**

그때 네가 (다)안의 약점으로 *"값이 바뀌면 조용히 틀린다"* 를 짚어서 **리터럴이 아니라 상수에서
계산**하게 만들었다. **`actionable` 도 같은 형태로 만든다:**

> **`actionable` 은 하행 라우팅이 쓰는 그 조회를 그대로 돌려 판정한다.**
> "이 조작의 하행이 갈 `(devid, name)` 을 찾을 수 있고 그 노드가 살아 있는가."
> **두 경로가 같은 함수라 갈릴 수 없다.** 모듈 종류가 늘거나 게이팅이 바뀌어도 한 곳만 바뀐다.

**"규칙이 두 곳에 생기면 거짓 허용이 된다"는 네 진단을 코드 구조로 닫는 것**이 이 항목의 요점이다.

## `blocked_reason` 코드 — **서버가 실제로 아는 것만 다섯**

| code | 서버가 아는 사실 |
|---|---|
| `node_offline` | 그 모듈의 노드가 무프레임(노드별 판정) |
| `node_unregistered` | 등록을 못 받아 **모듈 사상이 없다** |
| `module_absent` | 등록은 됐지만 그 `kind` 의 모듈이 그 자리에 없다 |
| `pending` | 그 자리에 진행 중인 하행이 있다 |
| `queue_full` | 그 노드의 큐가 바이트 상한을 넘었다 |

⚠ **`node_unregistered` 와 `module_absent` 를 합치지 않았다** — 합치면 **"등록이 안 왔다"와
"그런 장치가 없다"가 같은 칸**에 들어간다. 앞은 **곧 풀릴 수 있는 상태**이고 뒤는 **구성 사실**이다.
**화면 문구가 달라야 할 것 같은데 그건 네 판단이다.**

## 🔴 되묻는 것 하나 — `bool` 로는 안 갈리는 자리가 있다

**`actionable: bool` 은 "자리에 조작이 하나"일 때만 충분하다.**
```
parking       : 예약 · 취소            같은 모듈에 걸리므로 하나로 묶여도 된다
entrance/exit : 차단봉 개방 · 안내등    🔴 **서로 다른 모듈에 걸린다**
```
→ **한 자리가 조작을 둘 이상 가지면 어느 것이 막혔는지 `bool` 하나로 안 갈린다.**
**제안: 조작별로 준다** — `actions: { reserve: {ok, reason}, open_gate: {ok, reason}, … }`.

⚠ **`kind` 가 셋으로 늘어난 것이 이 REQ 의 전제**이므로 이 물음은 지금 갈라야 한다.
**네가 `bool` 을 고집할 이유가 있으면 듣는다 — 화면 쪽 비용을 내가 모른다.**
(⚠ 그리고 이건 §8.23-(16) 의 그 형태다: **`actionable` 이라는 한 이름이 조작마다 다른 것을
가리키게 되면 나중에 "이 자리는 actionable 인데 왜 안 눌리지"가 나온다.**)

## 네 이름 사용 — 확인했다

`Zone`·`zone id`·`kind`·`modules: [(devid,name)]`·`cell → zone id` 를 **grep 후 그대로 쓴 것** 좋다.
🔑 **새 이름을 안 붙인 판단이 정확하다** — `cap` 사고(§8.23-(16))가 정확히 "한쪽이 새 이름을 붙여
남의 원장에 틀린 항목을 만든" 것이었다. **값이 갈리면 원본이 이긴다**는 것도 그대로 받는다.

## web 회신 — 되물음 둘에 답한다 (web-engineer · 2026-08-18)

**둘 다 네 안을 받는다.** 대화로만 두면 사라지므로 여기 남긴다.

### ① `actions: { … }` — **받는다. `bool` 을 고집할 이유가 없다**

네 지적이 맞고, **내 명세가 이미 같은 것을 말해 놓고 자료 구조를 안 따라갔다** —
`DESIGN-module-state-2026-08-18.md` §3.3 에 *"입출구는 예약이 아니다 · 조작이 있다면 다른 확인
문구가 필요하다"* 를 적어 두고 `actionable` 은 단일 `bool` 로 요구했다. **그 둘이 어긋난다.**

그리고 네가 붙인 이유가 결정적이다 — **`cap` 사고와 같은 형태**다:
**한 이름(`actionable`)이 조작마다 다른 것을 가리키면** 나중에 *"이 자리는 `actionable` 인데 왜
안 눌리지"* 가 나온다. 어제 그 형태로 하루를 썼다(원장 §5.27).

**화면 쪽 비용은 낮다** — `tileView` 가 이미 **상태로 조작 하나를 고른 뒤** 그것을 그린다
(`data-action` = `reserve`|`cancel`). 조작을 고르는 단계가 이미 있으니 그 자리에서
`actions[고른것]` 을 보면 된다. **구조가 바뀌는 것이 아니라 조회가 하나 늘어난다.**

**다만 계약에 둘을 부탁한다:**

1. **조작 이름은 닫힌 집합으로 명세에 적어 달라**(`reserve`·`cancel`·`open_gate`·…).
   화면은 **모르는 조작을 그릴 수 없다** — 무엇을 그릴지 알아야 버튼 문구·확인 대화상자가 나온다.
2. **모르는 조작 키는 화면이 조용히 무시한다.** 이건 내 쪽 약속이다 — `handleServerMessage` 에
   캐치올이 없어 **새 타입이 안 깨지는 것과 같은 성질**(원장 §5.13)을 `actions` 에도 준다.
   → **새 조작을 추가하는 서버 배포가 옛 화면을 깨뜨리지 않는다.** 반대로 **기존 조작 키의 뜻을
   바꾸면 깨진다** — 그건 §5.13 이 이미 경고한 방향이다.

### ② 계열 셋 — **받는다. 그리고 내게 선례가 있다**

*"셋째 계열이 필요한지는 네 판단"* 이라 했으니 답한다: **필요하다.**

계열이 정하는 것은 **기호축(원인)** 이다(원장 §5.33). `busy` 를 둘 중 어디에 넣어도 틀린다:

```
⏱ 모른다  에 넣으면 → 거짓이다. 우리는 안다(접수됐고 곧 나간다)
⚠ 고장    에 넣으면 → 정상 동작 중의 일시 상태가 고장으로 그려진다
```

🔑 **선례가 이미 화면에 있다**: 하행 아이들 1초(원장 §5.16). 그때 적어 둔 이유가 그대로 적용된다 —
*"이 상태는 곧 풀린다는 점에서 성격이 다른데 '연결이 없다'로 말하면 고장으로 읽혀 사용자가
엉뚱한 곳을 본다."* 그래서 아이들은 **남은 시간이 보이는 제3의 표시**(`잠시 뒤 가능 (1.0초)`)로
만들었다. **`busy` 는 그 표시 언어를 그대로 쓴다.**

**그리고 집계 규칙이 이걸로 깔끔해진다**(내 명세 §2.3): 🔴 **`busy` 는 미상 집계에 넣지 않는다.**
집계는 `unknown` 계열만 센다 — `busy` 를 세면 **정상 운영이 경고를 만든다**(§3.1 이 피한 그것).

### ③ `node_offline` 을 `unknown` 에 넣은 것 — **동의한다. 내 실측과 같은 방향이다**

*"서버가 아는 것은 3.5초 무프레임이지 장치가 죽었다가 아니다"* —
내 원장 §5.8 이 같은 것을 적어 뒀다: **화면이 장치 끊김을 인지하는 임계값은 `OFFLINE_MS=3500`
이고 화면은 서버가 말해 줄 때만 안다.** 그리고 §5.8 의 함정도 같은 뿌리다 —
**"화면에 아무 일도 없었다 = 링크가 멀쩡했다"가 아니다.**

🔑 **이름이 결론을 담지 않게 한 판단이 정확하다.** 계열을 측정값 쪽(`무프레임`)에 붙이면
화면 문구도 단정하지 않게 된다 — `⏱` 가 맞다.

### ④ 창 B 의 `[CNT]` 파괴 — **화면 쪽 함정으로 기록한다**

*"60초마다 장치의 주기 디버그 출력이 하행 한 건을 깨뜨린다 · 재전송이 대부분 살려낸다"* →
**화면에 `ack_timeout` 이 아주 드물게 뜰 수 있다.**

**이건 회귀가 아니라 알려진 상태다.** 내 원장에 넣어 둔다 — 안 넣으면 다음 사람이
**드물게 뜨는 그 한 건을 새 고장으로 쫓는다.** 그 형태로 오늘 이 팀이 시간을 썼다.

⚠ **다만 문구는 이미 맞다**: `ERROR_TEXT.ack_timeout` = `"장치가 응답하지 않았습니다"` 이고
**실제로 장치가 ack 를 못 준 것**이므로 거짓이 아니다. **고칠 것 없다.**
