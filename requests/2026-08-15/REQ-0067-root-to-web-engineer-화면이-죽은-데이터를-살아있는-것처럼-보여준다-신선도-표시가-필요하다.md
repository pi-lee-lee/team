## 왜 필요한가

socket-engineer 가 서버 §3.4 오프라인 판정이 사실상 동작한 적이 없음을 재현·확정했다(소켓 연 채 12초 침묵 → 판정 0회). 그 자리의 push_snapshot 이 브라우저에 '센서 끊김'을 알리는 유일한 경로라, 장치가 조용하면 push 자체가 없어 화면이 마지막 상태를 계속 진짜처럼 보여준다. 서버는 고쳤지만, 주차 관제에서 빈 자리를 점유로 점유를 빈 자리로 계속 보여주는 것은 최악의 실패다. 서버 한 겹에만 의존하면 같은 종류의 결함이 재발할 때 화면이 또 거짓말한다.

## 처리 결과

**담당** web-engineer · **대상** `조별과제샘플/index.html` (이 파일 하나만 바뀜) · 와이어 포맷 무변경

### 설계 판단 — 무엇을 근거로 삼았는가

**신선도의 유일한 입력은 `state.snapshot.receivedAt`(브라우저 시계)다.** `device.online` 도,
`link` 상태도, `source` 도 판정에 쓰지 않는다. 이유는 요청서에 적힌 그대로다 — 서버가 침묵하는
순간이 바로 사고 상황이라, 근거를 서버 메시지에 두면 **사고가 나는 그 순간 판단도 같이 멈춘다.**
화면을 미는 동력도 서버 이벤트가 아니라 **1초마다 도는 로컬 타이머**다.

`docs/dead-detector-pattern.md` 4번("끝나야만 세는 지표는 끝나지 않는 사고를 영원히 놓친다")을
직접 적용했다. 침묵의 길이를 *다음 스냅샷이 도착했을 때* 계산하지 않는다 — 매 초 `Date.now()` 로
**진행 중인 침묵**을 잰다. 다음 프레임이 영영 안 와도 숫자가 계속 자란다.

**임계 12초 (`UNCONFIRMED_MS`)** — 하트비트 1 Hz(§3.2), 서버의 오프라인 판정 3.5초(§3.4).
정상 서버라면 장치가 조용해진 뒤 3.5초 안에 무슨 말이든 온다. 12초는 그 3.4배로, 서버가 말할
기회를 충분히 주고도 아무 말이 없었다는 뜻이다. (기존 `STALE_MS`=10초와 혼동하지 않도록 주석에
**기준 시계가 다르다**고 명시했다 — 그쪽은 `ts`(서버 시계), 이쪽은 `receivedAt`(브라우저 시계).)

### ⚠ 일부러 하지 않은 것 — 진단하지 않는다

**"12초 침묵 = 고장"이 아니다.** §5.3 은 "변화가 있을 때" push 라고만 하므로 **조용한 주차장에서도
push 는 오지 않는다.** 화면은 "조용해서 정상"과 "알림 경로가 죽음"을 원리적으로 구분할 수 없다.
그래서 문구는 진단("끊겼다")이 아니라 사실("그 뒤로 확인된 바 없다")이고, 색도 빨강이 아닌 중립이다.
정상 상태를 빨간 오류로 그리면 §12A.6 의 진짜 경고까지 같이 흘려보내게 된다.

같은 이유로 **예약을 막지 않았다.** 최종 판정은 ACK 이고(§7.2), 조용한 주차장에서 예약을 막는 것이
더 큰 고장이다. 대신 확인 대화상자에 나이를 한 줄 덧붙인다(누르기 직전이 그 사실이 가장 필요한 순간).

`device.online` 은 **지우지 않고 보조 지표로 나란히** 뒀다 — 같은 문서 5번("단일 지표는 자기 고장을
증언하지 못한다"). 서버의 마지막 주장("연결됨")과 브라우저 실측("그 뒤로 아무것도 안 옴")이 동시에
보이면 그 **모순 자체가 사용자에게 정보**다.

| 구분 | 내용 |

| 상태 | `state.freshKey` — 배너 문구를 **등급이 바뀔 때만** 다시 쓰기 위한 열쇠 |

| 격자 | `body.is-stale #grid { filter: grayscale(.82) }` — 격자 전체 탈색 |
| 칸 | 칸마다 `⏱ N분 전 값` 칩(`.tile__stale`) |
| 배너 | `#stale-banner` **신설**(기존 `#offline-banner` 를 재사용하지 않음 — 한 노드에 두 주인이 붙으면 깜빡인다) |

**표시 축을 채도로 고른 이유**: 이 파일에서 투명도는 이미 "누를 수 없음"(`aria-disabled`), 파선은
"주입됨/요청 중", 점선은 "상태 미상"으로 **다 쓰고 있다.** 거기 얹으면 뜻이 겹친다. 남은 채도 축을
썼고, 4조합 구분은 문구가 이미 따로 지고 있다(색만으로 구분하지 않는다는 기존 원칙).
알고 받아들인 부작용 하나: 무장 중이면 빨간 빗금도 같이 탈색된다 — 다만 그때 `.test-frame` 테두리와
배너는 격자 **밖**이라 빨간 채로 남는다.

**aria-live 함정 회피**: 1초 타이머에서 `render()` 를 부르지 않는다. `renderTestMode()` 가 매번
`#test-banner`(aria-live) 자식을 새로 만들어서, 스크린리더가 1초마다 같은 경고를 다시 읽게 된다.
그래서 신선도만 미는 `renderFreshness()` 를 따로 뒀고, **흐르는 초 단위 숫자는 aria-live 밖**
(「마지막 갱신」dd·칸 칩)에만 두고 배너 문구는 임계를 넘나들 때만 바뀌게 했다.

### 검증 — 브라우저에서 **실제로 열어** 확인함

하드웨어가 죽어 있어 실기는 불가. `srv_parking`(PID 76096)은 교체 예정이라 **건드리지 않았다**
(연결도 하지 않음). 대신 **`?demo=1` 이 이 결함의 정확한 재현 조건**이다 — 데모 전송부는 조작이
있을 때만 push 하므로, 가만히 두면 "서버가 살아 있는데 아무것도 안 오는" 상황이 그대로 재현된다.

실행: Chrome 헤드리스(`--headless=new`) + `--virtual-time-budget` 으로 시간을 앞당겨 실제 렌더링을
캡처했다. 코드만 읽고 판단한 것이 아니라 **화면을 눈으로 확인한 결과**다.

| 조건 | 결과 | 증거 |
|---|---|---|
| 가상 3초 (신선) | 신선도 표시 없음, 4조합 색 정상 | `/tmp/parking-fresh.png` |
| 가상 95초 (침묵) | 격자 전체 탈색 · 10칸 전부 `⏱ 2분 전 값` · 배너 노출 · 「마지막 갱신」에 "그 뒤로 확인된 바 없음" | `/tmp/parking-stale.png` |
| 침묵 60초 후 스냅샷 1건 도착 | 배너 사라짐 · 색 복귀 · 칩 사라짐 · `seq` 1234→1235 · "3초 전 수신" | `/tmp/parking-recover.png` |

완료 기준 대조: ① 화면만 보고 '지금 값이 아님'을 안다 → **확인**(탈색+칩+배너, 세 겹).
② push 부재 자체로 드러난다 → **확인**(위 재현에서 서버 메시지는 단 한 건도 오지 않았다).
③ 복귀 시 정상 표시 → **확인**(스냅샷 1건으로 즉시 복귀).

`node --check` 로 인라인 스크립트 문법 통과. 회귀 없음(위 3장 모두 기존 격자·시뮬·테스트 패널이
정상 렌더링됨).

**코드만 보고 판단한 것(브라우저 미확인)**: WS 가 붙어 있는데 조용한 실제 상황에서
「WebSocket 연결됨」과 신선도 배너가 **동시에** 뜨는 모습. `renderConnection()` 과
`renderFreshness()` 가 서로 독립이고 각각 다른 노드를 쓰므로 그렇게 동작하지만, 실제 서버를 상대로는
확인하지 않았다(교체 예정이라 접속을 피함). 서버 교체가 끝난 뒤 한 번 눈으로 볼 것을 권한다.

### 🐞 후속 — 위 검증이 못 짚은 결함을 하나 찾아서 고쳤다 (같은 작업 안에서)

**위의 `?demo=1` 검증 3건만으로는 부족했다.** `transport.start()` 는 데모면 폴링 분기 **앞에서**
빠져나가므로, 데모 경로는 파일 폴백을 한 번도 타지 않는다. 즉 위 3장은 폴백 경로를 검증하지 못했다.

**결함**: 폴백은 3초마다 `data_log.json` 을 **다시 읽고**, 매번 `applySnapshot` → `receivedAt = Date.now()`
로 시각을 새로 찍었다. 그런데 서버는 상태가 바뀔 때만 그 파일을 쓴다(§9.4). 결과적으로
**똑같은 바이트를 반복해서 읽고는 그때마다 "방금 확인했다"고 기록**하는 셈이라, 나이가 3초를 넘지
못하고 **신선도 표시가 폴백에서 영원히 뜨지 않았다.** WS 가 끊긴 상태 — 즉 이 기능이 가장 필요한
상황 — 에서 기능이 통째로 죽어 있었다.

이것은 `docs/dead-detector-pattern.md` 의 그 유형 그대로다. 탐지기(신선도 시계)가 죽어 있었고,
우회 경로(`renderConnection()` 의 §9.4 note 배너)가 "그래도 뭔가 뜨니까" 결함을 가리고 있었다.

**수정**: `applySnapshot` 에서 **파일 경로에 한해**, 들어온 기록이 지금 것과 내용이 같으면
(`snapshotFingerprint` = `ts`+occupied 비트+reserved 비트) 이전 `receivedAt` 을 그대로 들고 간다.
**재확인이 아니라 재열람이기 때문**이다. WS·데모는 반대로 항상 새로 찍는다 — 서버는 스냅샷을 만들 때
`device_online()` 을 그 자리에서 계산하므로(server.cpp), 칸이 하나도 안 바뀐 스냅샷이라도
**도착했다는 사실 자체가** "장치가 3.5초 안에 프레임을 보냈다"는 새 증거다(§3.4).
그래서 억제는 파일 경로에만 건다.

**폴백 경로 재검증 (A/B, 브라우저 실측)** — `srv_parking` 은 건드리지 않았다. 임시 사본의 `WS_PORT`
를 죽은 포트(9911)로 바꿔 격리하고, `ts` 가 **41분 전**인 `data_log.json` 과 함께
`python3 -m http.server` 로 띄워 40초(가상시간) 동안 열어 뒀다(그동안 폴링 성공 약 13회).

| | 「마지막 갱신」 표시 | 격자 |
|---|---|---|
| 수정 전 (`nofix.html`) | **"1초 전 수신"** — 41분 된 파일을 방금 확인한 값처럼 그린다 | 색 그대로, 신선도 표시 **없음** |
| 수정 후 | **"⏱ 40초 전 수신 · 그 뒤로 확인된 바 없음"** | 탈색 + 10칸 전부 `⏱ 40초 전 값` + 배너 |

증거: `/tmp/parking-nofix.png` (수정 전) · `/tmp/parking-fallback.png` (수정 후).
같은 파일·같은 시간·같은 폴링 횟수에서 표시만 갈렸다.

즉 **완료 기준 ①②③ 은 WS/데모 경로뿐 아니라 파일 폴백 경로에서도 성립한다.** 위 3장만 있었을 때는
그렇게 말할 수 없었다 — 그 사실을 기록으로 남긴다.

### 🔭 남은 구멍 두 가지 (이 요청 범위 밖 · 후속 필요)

1. **폴백은 "서버는 살아 있고 *장치*가 죽은" 경우를 알 수 없다.** `data_log.json` 에 장치 생사 필드가
   없기 때문이다(§9.1). socket-engineer 가 같은 문제를 서버 쪽에서 독립적으로 찾아 제안을 보내왔고,
   레코드에 `online`/`last_frame_ts` 를 추가하는 방향으로 **별도 REQ 로 진행한다.**
   이번 변경은 그때까지도 "확인된 바 없음"으로는 정직하게 표시되므로 서로 충돌하지 않는다.
2. **`pollOnce()` 에 fetch 타임아웃이 없다.** 서버가 응답하지 않고 **매달리면**(02:19 의 블로킹 send 행
   같은 경우) 그 promise 는 성공도 실패도 하지 않는다 — 폴백 실패 보고 자체가 영영 안 온다.
   지금은 신선도 시계가 계속 자라므로 화면이 거짓말하지는 않지만, "읽지 못했다"는 말은 못 한다.
   `AbortController` 로 상한을 거는 후속 작업이 필요하다.
