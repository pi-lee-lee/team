# REQ-0062 · 365일 상시가동 결함: seq 랩(18.2h)이 재부팅 오탐을 만든다 — 판정 규칙을 정하라

**요청자** `root` → **담당** `socket-engineer`

## 요청 내용

server.cpp:753 이 재부팅을 이렇게 판정한다.

    bool reboot = (ard_uptime >= 0 && up < ard_uptime) || (ard_seq >= 0 && seq < ard_seq);

두 항 모두 **랩 허용이 없다**. 그래서 정상 연속가동 중에 참이 된다.

(1) seq — client.ino:361 `static uint16_t seqNo`. §2.4 가 uint16 순환으로 정한 값이다.
    하트비트 1Hz(client.ino:46 HEARTBEAT_MS=1000)로 증가하므로 65536초 ≈ **18.2시간마다**
    65535 → 0 으로 되돌아간다. 그 순간 `seq < ard_seq` 가 참 → 재부팅 오탐.
    → 1년에 약 480회. **하루도 못 버틴다.**

(2) uptime — client.ino:684,689 가 `millis()/1000UL` 을 보낸다. millis() 는 32비트라
    **49.7일마다** 0 으로 되돌아간다 → `up < ard_uptime` 참 → 재부팅 오탐. 1년에 약 7회.

오탐의 결과는 server.cpp:771 `if (reboot) resync_reservations("uptime/seq 역행")` —
멀쩡히 돌고 있는데 예약이 재동기화된다. 그리고 §7.5-1 경로상 occupied 기준선도 다시 세운다.

**이건 명세가 정할 문제이지 클라이언트가 임의로 정할 문제가 아니다.** 네가 정해 달라:

  (a) 랩 허용 비교로 바꾼다 — 예: `(uint16_t)(seq - ard_seq)` 가 임계값 미만이면 전진으로 본다
      (부호 없는 순환 비교). uptime 도 같은 방식.
  (b) 재부팅을 **추론하지 않고 명시**한다 — 부팅 때마다 바뀌는 boot-id 필드나
      재부팅 직후 1회 플래그. REQ-0059 에서 네가 하행에 택한 "단조증가 cseq"의 상행 대응.
  (c) 그 밖에 네가 더 낫다고 보는 방안.

(b) 는 와이어 포맷이 바뀌므로 §2.4 개정과 arduino 쪽 구현이 따라온다.
(a) 는 서버만 고치면 되지만 "18.2시간 안에 진짜 재부팅이 두 번" 같은 경계가 남는다.

**서버 구현은 네 파일이니 네가 하고**, client.ino 변경이 필요하면 arduino-engineer 에게
요청을 직접 발행하라(루트를 거칠 필요 없다). 지금 arduino-engineer 는 기동돼 있다(0b18fd8a).

## 왜 필요한가

사용자 요구가 "ESP8266 365일 상시가동"이다. 지금 코드는 재부팅 오탐이 18.2시간마다 나므로
목표를 하루도 만족하지 못한다. 그리고 이 결함은 짧은 벤치 테스트에서 절대 드러나지 않는다 —
장시간 돌려야만 나오는 종류라 지금 잡지 않으면 납품 후에 나온다.

### 판정 — (a) 계열이되, **seq 가 아니라 uptime 에** 적용한다. 전선은 그대로 둔다

`seq` 를 재부팅 판정에서 **완전히 뺐다.** 1Hz 에서 uint16 은 18.2시간마다 합법적으로 0 을
지나가므로, 어떤 랩 허용 비교를 얹어도 "18.2시간 안에 진짜 재부팅이 두 번" 같은 경계가 남는다.
**판정 근거로 쓸 수 없는 값이다.** 반면 `uptime` 은 49.7일 주기라 순환과 재부팅이 깨끗이 갈린다.

규칙은 한 줄이다. 되돌아감과 순환은 뺄셈으로 구별되지 않지만, **순환을 접으면**
정상 전진은 작고 재부팅은 거의 한 바퀴가 된다 — 경계 특례가 필요 없다.

```
WRAP = 4294968 ; MAX_FWD = 86400
fwd    = ((up - prev_up) % WRAP + WRAP) % WRAP
reboot = (fwd > MAX_FWD)
```

**`MAX_FWD` 를 86400 으로 정한 근거** — 이게 유일한 판별 상수라 값의 출처를 남긴다.
진짜 재부팅의 `fwd` 는 400만대이므로 선을 1시간에 두든 하루에 두든 판정은 같다(세 자릿수 차이).
다만 **아래로는 못 내린다**: `OFFLINE_MS`(3.5초)는 오프라인 **표시만** 하고 연결을 닫지 않으므로
한 연결 안 침묵에 코드상 상한이 없고(호스트 절전·ESP 멈춤·링크 복구 지연) 그동안에도 uptime 은
전진한다. 실제로 명세 §7.4 표의 "랩을 걸쳐 100분 침묵"은 `fwd=5968` 이라 **3600 에 두면 오탐**이다.
크게 잡을수록 아래 "놓치는 창"이 넓어지므로 실측 간격의 10배 남짓인 24시간에 세웠다.

**(b) 부팅 ID 를 기각한 이유** — 와이어 포맷이 바뀌어 재플래시가 필요하고(플래시는 사용자 몫),
AVR 에는 부팅마다 다른 값을 만들 엔트로피원이 없으며(EEPROM 카운터는 마모·새 실패모드),
64바이트 줄 예산(§2.1)도 깎인다. **서버만 고쳐 같은 결과가 나오면 그쪽이 옳다.**
그래서 **client.ino 변경 없음 → arduino-engineer 앞 요청도 발행하지 않았다**(완료기준 ④ 해당 없음).

### ① 명세 확정 — `docs/net/parking-protocol.md` **개정 8 · v1.7**

- **§2.4** — `seq` 를 진단용 카운터로 격하. "재부팅 증거로 쓰지 마라" 명시.
- **§7.4** — 판정식·상수·판정표·**놓치는 창**을 못 박음. 1차 신호는 여전히 "새 TCP 연결".
- **§13** — 개정 8 이력(피해 범위와 (b) 기각 근거 포함).

> 개정 번호는 7 이 아니라 8 이다 — §12C 가 이미 "개정 7" 을 쓰고 있는데 **§13 이력에는 개정 7
> 항목이 없다.** 내 변경과 무관한 기존 누락이라 손대지 않았다. 루트가 판단할 몫이다.

> `docs/digitcam-contract.md` 는 **고치지 않았다.** grep 결과 그 문서의 `seq`/`uptime` 은

> `docs/net/parking-protocol.md` 다. (애초에 그 파일은 루트 소유라 내가 쓸 수도 없다.)

### ② 서버 구현 — `조별과제샘플/server.cpp`

- `uptime_says_reboot(prev_up, up)` **순수 함수**로 분리(+ 상수 2개). 자가검증이 직접 부른다.
- 호출부: `bool reboot = uptime_says_reboot(ard_uptime, up);` — `seq` 항 제거.
- 로그 문구를 새 규칙에 맞게 정정(`uptime/seq 역행` → `uptime 전진량이 한 바퀴에 가깝다`).
- 테스트 이음매 2개: `resync_count`(계측), `no_disk`(자가검증이 `data_log.json` 을 안 건드리게).
  **둘 다 판정에는 관여하지 않는다.**
- `--selftest` 의 하드코딩 `i < 22` → `sizeof(L)/sizeof(L[0])` (줄 추가하고 개수 못 고치는 사고 방지).

### ③ 검증 — 실행했다. 두 층으로 본다

**(A) `./server --selftest`** — `g++ -O2 -Wall` 무경고 빌드 후 실제 실행, 전부 통과:

- 판정식 8케이스: 평시 / 침묵 10분 / **millis 49.7일 랩** / 랩 걸친 침묵 / 기준선 없음 → 정상,
  진짜 재부팅 / 부트 루프 / 11.6일 뒤 재부팅 → 재부팅.
- **호출 지점까지** 통과시킨 4케이스(판정식이 맞아도 호출부가 틀리면 소용없으므로):
  - `seq` 를 **65530 에서 시작**해 65535→0 을 넘김, uptime 정상 전진 → **resync=0** ✅ (요구사항 그대로)
  - uptime 4294966→1 → resync=0 ✅
  - uptime 3601→2 (진짜 재부팅) → **resync=1** ✅ (정탐 유지)
  - uptime 5000→3 인데 **seq 는 전진** → resync=1 ✅ — **옛 규칙이 놓치던 재부팅**이다

**(B) 실제 TCP 왕복** — 포트만 바꾼 사본(19991)을 띄우고 체크섬 정품 `S` 프레임을 소켓으로 주입:

```
←ARD S,65534,…,3600  → 기준선
←ARD S,65535,…,3601  ┐
←ARD S,0,…,3602      ├ 랩 통과 — 재부팅 감지 로그 없음 ✅
←ARD S,1,…,3603      ┘
←ARD S,2,…,4         → ⟳ 재부팅 감지(uptime 전진량이 한 바퀴에 가깝다) ✅
(연결 끊고 재접속)    → ⟳ 재부팅 감지(새 연결) ✅  1차 신호도 그대로
```

> **9991 의 실행 중인 서버(`srv_hw`)는 건드리지 않았다.** server.cpp 는 새 ARD 연결이 오면
> 기존 연결을 닫으므로, 거기에 주입했다면 **실제 아두이노가 끊겼다.** 그래서 포트를 옮겼다.
> 시험 서버가 만든 빈 `data_log.json` 은 지워 원상복구했다.

### 부수 발견 — 이 결함의 조용한 절반

오탐의 피해는 재하달만이 아니었다. 오탐 프레임은 `if (base_valid && !reboot)` 의 else 로 빠져
**§7.5-1 "재부팅이면 전이 판정을 건너뛴다" 경로를 같이 탄다.** 즉 그 프레임에 실제로 일어난
`occupied` 1→0 은 **은퇴되지 않고 삼켜지고** 기준선만 다시 깔렸다. 18.2시간마다 예약 하나가
조용히 영구화될 수 있었다 — 개정 2가 없앤 **"죽은 자리"의 재발 경로**다. 이번 수정으로 같이 닫혔다.

### 남은 한계 (숨기지 않는다)

`fwd <= 86400` 인 재부팅은 추론으로 못 잡는다: ⑴ 랩 직전 24시간 구간의 재부팅(49.7일마다 열림),
⑵ 부팅 1초 안에 첫 `S` 를 보내고 곧장 죽는 부트 루프. **둘 다 "새 TCP 연결" 신호가 받는다** —
재부팅하면 링크가 끊기고 다시 `CIPSTART` 하기 때문이다. 추론은 MCU 만 리셋되고 소켓이 살아남은
드문 경우를 위한 2차 방어선이다. §7.4 에 그대로 적어 두었다.
