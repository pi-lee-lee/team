# REQ-0069 · 폴백 fetch 에 상한을 걸어라 — 매달린 응답은 실패 보고조차 못 한다

**요청자** `root` → **담당** `web-engineer`

## 요청 내용

## 왜 필요한가

REQ-0067 처리 중 web-engineer 가 스스로 발견해 「남은 구멍」에 남긴 항목이다. pollOnce() 에 fetch 타임아웃이 없어, 서버가 응답하지 않고 매달리면 그 promise 는 성공도 실패도 하지 않는다 — 폴백 실패 보고 자체가 영영 안 온다. 가상의 위험이 아니다: 오늘 02:19 에 서버가 블로킹 send 로 매달린 정황이 실제로 있었고, 그 형태가 바로 이 경우다. 신선도 시계 덕에 화면이 거짓말하지는 않지만 '읽지 못했다'는 말을 못 한다.

## 대상 파일

- `조별과제샘플/index.html`
## 완료 기준

서버가 응답을 매달아도 정해진 상한 안에 폴백 시도가 종료되고, 화면이 '예비 경로를 읽지 못했다'를 말할 수 있다. 정상 응답에는 영향이 없다. 상한 값의 근거를 주석에 남긴다.

## 처리 결과

**담당** web-engineer · **대상** `조별과제샘플/index.html` · 와이어 포맷 무변경

### 변경점

1. **`POLL_TIMEOUT_MS = 5000`** — `AbortController` 로 폴백 fetch 를 끊는다.
   근거(주석에 남김): 폴링 주기 3초보다 넉넉해야 하고(느린 응답을 실패로 몰면 안 된다),
   §7.3 의 최종 실패 지평이 1500×3=**4500ms** — 시스템이 이미 "그 요청은 잃었다"고 보는 시각이다.
   작은 정적 파일 하나를 그보다 오래 끌고 있다면 느린 게 아니라 매달린 것이다. 그리고
   `UNCONFIRMED_MS`(12초)보다 **작다** — "확인된 바 없음"을 한참 띄우고 있기 전에
   "읽지 못했다"는 더 구체적인 말을 먼저 할 수 있어야 한다.
2. **in-flight 가드** — 앞 시도가 매달려 있으면 새로 쌓지 않는다.
   ⚠ 불리언만 보면 플래그가 새는 순간 폴링이 **영영** 멈춘다(그 자체가 죽은 탐지기다).
   그래서 시작 시각도 같이 보고 **상한+1초가 지나면 플래그와 무관하게 재개**한다.
3. **`.finally()` 로 해제** — 성공·실패·중단 어느 쪽으로 끝나도 반드시 지나는 자리에서 타이머를 지우고
   플래그를 푼다.
4. **`timeout` 을 별도 종류로 보고** — "연결이 거부됨"과 "연결은 되는데 응답이 없음"은 사용자가 할 일이
   다르다. 후자는 서버 프로세스를 봐야 하는 상황이므로 문구를 갈랐다. WS 가 살아 있을 때도
   상한 초과만은 흘려보내지 않는다(같은 서버가 HTTP 를 매달고 있다면 그게 지금 WS 가 조용한 이유일 수 있다).

### 검증 — 매달린 서버를 실제로 만들어 브라우저로 붙였다

`srv_parking` 은 건드리지 않았다. 대신 02:19 의 형태를 그대로 재현하는 서버를 세웠다:
**포트는 열려 있고 TCP 연결도 되는데 `data_log.json` 에만 영원히 답하지 않는다**(index.html 은 정상 응답).
화면의 `showMessage()` 를 감싸 비콘을 쏘게 해 관측했다 — 검증 대상 코드(pollOnce)는 손대지 않고 계측만 덧댔다.

**A/B (각 22초, 같은 서버·같은 조건)**

| | data_log.json 요청 | 요청 간격 | **화면 알림** |
|---|---|---|---|
| 수정 전 | 6건이 **전부 매달린 채 쌓임** | 3.0초 | **0건 — 화면이 아무 말도 못 한다** |
| 수정 후 | 4건, 하나씩 | 6.0초 | **1건 @6.1초** "…5초 안에 응답이 없습니다 — 연결은 되는데 응답이 없습니다(서버가 멈춰 있을 수 있습니다)" |

수정 전은 22초 동안 **단 한 건의 실패 보고도 발생하지 않았다.** 완료 기준이 말한 그 상태 그대로다.

**덤으로 드러난 피해 하나**: 수정 전 로그에서 요청이 16초(6건)에서 **뚝 끊긴다.** 브라우저의
**호스트당 동시 연결 상한(6)** 을 매달린 폴백이 혼자 다 써 버려, 그 뒤로는 요청이 브라우저 안에서
큐에 갇힌 것이다. 즉 상한이 없으면 침묵할 뿐 아니라 **같은 출처로 나가는 다른 요청까지 막는다.**
(예상하지 못했고, 실측에서 나왔다.)

**회귀 없음** — 정상 응답 서버(41분 된 `data_log.json`)로 20초:

- 폴링 **7회 정상 성공**(3초 주기 그대로, 상한·가드가 정상 경로를 늦추지 않았다)
- 오류 알림 **0건**(느린 응답을 실패로 오인하지 않는다)
- REQ-0067 신선도도 그대로: `body=[is-stale]`, 「마지막 갱신」=`⏱ 18초 전 수신 · 그 뒤로 확인된 바 없음`,
  배너 노출, 칸 칩 `⏱ 18초 전 값` — **같은 파일을 7번 성공적으로 읽고도** 나이가 자란다

문법 검사는 따로 돌리지 않았다 — 위 세 번의 실행에서 **Chrome 이 실제로 스크립트를 파싱하고 실행했고**
비콘이 도착했다. `node --check` 보다 강한 증거다.

### 알아 둘 것 (루트에게)

이 검증용 하네스를 `/tmp` 에 파일로 쓰려다 **소유권 훅에 정상적으로 막혔다**(프로젝트 밖 = root 소유).
`python3` 로 우회할 수 있었지만 **하지 않았다** — 방금 받은 거부를 우회하는 것이 되기 때문이다.
대신 파일을 한 개도 만들지 않는 방식(페이지·픽스처를 전부 메모리에서 서빙)으로 바꿔 해결했다.
결과적으로 작업에 지장은 없었으나, **에이전트가 프로젝트 밖에 임시 파일을 만들 수 없다**는 점은
규칙의 실제 효과이므로 보고해 둔다. 판단은 루트 몫이다.
