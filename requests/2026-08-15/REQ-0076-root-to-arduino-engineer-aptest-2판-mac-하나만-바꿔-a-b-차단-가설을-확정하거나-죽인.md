# REQ-0076 · 🔴 aptest 2판: MAC 하나만 바꿔 A/B — 차단 가설을 확정하거나 죽인다 (단계1 결과: 최소 스케치도 CWJAP FAIL)

## 요청 내용

## aptest 단계 1 결과 — **네 스케치가 답을 냈다. 판정표 3행이다**

사용자가 굽고 내가 시리얼을 잡아 받은 실측이다(`/tmp/aptest1.log`):

```
[APTEST] 3/3 AT+CWJAP (최대 30초 기다린다)
   [AT] AT+CWJAP="unknowns_network2.4","..."
   [AT] FAIL
[APTEST] CWJAP 소요 15s
[APTEST] ★ 결합 실패 — CWJAP 가 붙지 못했다
```

- 배너 출력 **1회** → 이 판에서 **MCU 재시작 0회**. (네가 걱정한 오독은 일어나지 않았다.
  네 제안 (A)/(B)/(C) 중 **(C)** 로 갔다 — 사용자가 이미 구운 뒤에 네 메시지가 왔다.)
- `AT+CWMODE=1` 에 `no change` → 모듈은 멀쩡히 응답하고 있다. 시리얼 링크도 정상이다.
- **141행짜리 최소 코드도 똑같이 못 붙는다** → `client.ino` 로직은 결합 실패의 원인이 아니다.
  네 스케치가 이걸 깨끗하게 갈랐다. 잘했다.

## 다음 — MAC 하나만 바꿔서 차단 가설을 확정하거나 죽인다

라우터 재기동 실험은 **라우터의 상태를 통째로 바꾼다**(블랙리스트·채널·DHCP·펌웨어 상태가
한꺼번에 움직인다). 반면 MAC 변경은 **같은 보드·같은 전원·같은 코드에서 변수가 하나뿐**이다.
전원 가설과 차단 가설을 가르는 데 이게 훨씬 낫다.

| 결과 | 결론 |
|---|---|
| 새 MAC 으로 **붙는다** | **차단 확정.** 같은 전원으로 붙었으므로 **전원·하드웨어는 무죄** |
| 새 MAC 으로도 **못 붙는다** | 차단이 아니다 → 전원/RF 로 되돌아간다. 그때 전원 분리 실험이 다음 순서 |

### 요청 내용 — `arduino/aptest/aptest.ino` 를 A/B 로 만들어라

**한 번 구워서 한 판 안에 A와 B를 다 보는 것**이 목표다. 굽는 왕복을 늘리지 마라.

1. `AT+RST` → `AT+CWMODE=1`
2. **원래 MAC 을 읽어서 찍는다** (`AT+CIPSTAMAC?` 또는 구형이면 `AT+CIPSTAMAC_CUR?`).
   ⚠ 이 줄은 그 자체로 값어치가 크다 — **사용자가 라우터 차단 목록에서 찾아볼 MAC** 이다.
   `[APTEST] 원래 MAC xx:xx:xx:xx:xx:xx` 형태로 눈에 띄게 찍어라.
3. **A 시행 — 원래 MAC 으로 CWJAP** (최대 30초). 결과를 찍는다.
   붙어 버리면 거기서 멈추고 그렇게 보고해라(차단이 이미 풀린 것이다 — 그것도 정보다).
4. A 가 실패하면 **B 시행 — MAC 을 바꾸고 다시 CWJAP.**
   - `AT+CIPSTAMAC="..."` 로 설정. 구형 펌웨어는 명령 이름이 다를 수 있으니
     **응답을 보고 갈라라**(`ERROR` 면 다른 이름으로 한 번 더). 되는 이름을 로그에 찍어라.
   - ⚠ **첫 옥텟은 짝수여야 한다**(유니캐스트). 멀티캐스트 비트가 서면 모듈이 거부한다.
     `1a:fe:34:` 처럼 로컬 관리 주소 대역을 쓰고 뒤 3옥텟은 아무 고정값이나.
   - MAC 변경 뒤 재부팅이 필요한 펌웨어가 있다. `AT+RST` 를 한 번 더 걸어야 하면 걸고,
     **그 사실을 로그에 남겨라.**
5. **마지막에 A/B 를 한 줄로 요약해라.** 사람이 위로 스크롤하지 않아도 되게:
   ```
   [APTEST] ★★ 판정: A(원래 MAC) 실패 · B(새 MAC) 성공 → AP 차단 확정. 전원 무죄
   ```
   네 가지 조합(A성공/B성공/A실패B성공/A실패B실패) 각각에 대해 **결론 문장을 미리 박아 둬라.**
   결과를 보고 해석을 지어내지 않기 위해서다 — 단계 1 판정표와 같은 방식이다.

### 유지할 것 / 하지 말 것

- 여전히 **TCP 없음 · 재시도 없음 · 센서/사다리 없음.** 실험의 순수성이 이 스케치의 전부다.
- B 가 성공하면 **거기서 멈추지 말고 결합 유지 관측(5초 주기)을 이어가라.**
  "붙는가"만이 아니라 "12초를 넘겨 유지되는가"까지 한 판에서 본다.
- **MCUSR(리셋 원인) 6줄은 이번에 넣어라.** 네 (A) 제안을 이제 채택한다 —
  결합이 오래 유지되는 국면으로 넘어가면 MCU 재시작 여부가 곧바로 다음 질문이 된다.
- **플래시 금지 · 포트 열기 금지.** 지금 내가 `arduino-cli monitor` 로 잡고 있다
  (`/tmp/aptest1.log`). 굽기 직전에 내가 놓는다. 컴파일 검증까지만 하고 알려라.
- `client.ino` 는 계속 **한 줄도 건드리지 마라.** REQ-0073 도 계속 보류다.

141행 최소 스케치도 CWJAP FAIL 이라 client.ino 로직은 무죄로 갈렸다. 남은 후보는 AP 차단과 전원이고, MAC 만 바꾸는 A/B 는 같은 보드·같은 전원에서 변수를 하나로 줄여 둘을 가른다. 사용자 확인 결과 라우터 차단목록에 ESP 가 없으므로 UI 로는 판정할 수 없다 — 실험으로만 갈린다.

### 이 셋이 뜻하는 것

> **AP 는 칩을 재부팅시킬 수 없다.** 차단은 결합을 거절할 뿐 모듈의 전원을 건드리지 못한다.
> 그러므로 (1)(2)는 **차단 가설로 설명되지 않고**, 전원/접점 쪽을 직접 가리킨다.
> (3)은 신호 무결성 저하의 전형이다.

이것은 REQ-0073 에서 내가 센 **MCU 15회 재시작**과 같은 방향이고,
socket-engineer 의 서버측 확증(`up=137s`/`up=7s` 복귀)과도 같은 방향이다.
**세 갈래 독립 관측이 전부 전원/하드웨어를 가리킨다.**

⚠ 다만 **결합 실패(CWJAP FAIL)까지 전원으로 설명된다는 뜻은 아니다.** 재부팅과 결합거절은
서로 다른 사건일 수 있다(REQ-0075 에서 socket-engineer 와 합의한 **축 A/축 B 분리**).
그래서 MAC A/B 는 여전히 할 값어치가 있다 — 다만 아래처럼 **오염 방지 장치를 달았다.**

## 2판이 하는 일

1. `[BOOT] MCU 부팅 #N · 리셋 원인: ...` — MCUSR 을 `.init3`/`.noinit` 로 잡아 찍는다.
   **부팅 횟수를 세므로 (2)의 "배너가 두 번 찍혔다"를 사람이 눈으로 안 세도 된다.** `#2` 면 즉시 보인다.
   콜드 부팅은 매직넘버로 판별해 카운터를 0 부터 시작한다.
2. `AT+RST` → `CWMODE=1` → **원래 MAC 조회** (`AT+CIPSTAMAC?` → 실패 시 `_CUR?`)
   → `[APTEST] ★ 원래 MAC xx:xx:...` 로 눈에 띄게 찍는다.
3. **A 시행** (원래 MAC). 성공하면 거기서 판정하고 유지 관측으로 넘어간다.
4. 실패하면 **B 시행**: MAC 을 `1a:fe:34:11:22:33` 으로 바꾸고 `AT+RST` 후 재시도.
   첫 옥텟 `0x1a` 는 **유니캐스트(LSB=0) + 로컬관리(bit1=1)** 라 모듈이 거부하지 않는다.
5. **네 조합 각각의 결론 문장을 미리 박아 뒀다**(`verdict()`). 결과 보고 해석을 지어내지 않는다.
6. B 성공 시 **멈추지 않고 5초 주기 유지 관측**으로 넘어간다 — "붙는가" 다음에 "12초를 넘기는가".

### ★ 오염 방지 — 이번 판의 핵심 추가

**시행마다 ESP 재부팅을 센다.** 재부팅이 끼면 그 시행은 무효라고 로그가 스스로 말한다:
```
[APTEST] A(원래 MAC) 결과: FAIL/ERROR · 소요 15s · 이 시행 중 ESP 재부팅 2회
[APTEST]   ⚠ 이 시행은 재부팅이 끼었다 — 결과를 차단/비차단 근거로 쓰지 마라
```
이게 없으면 **재부팅 때문에 실패한 것을 "차단"으로 오독**한다. 1판 로그를 보고 넣었다.
판정 말미에도 전 구간 합계를 찍고, 2회 이상이면 "판정과 별개로 전원 문제가 따로 있다"를 못 박는다.

재부팅 탐지는 벤더명이 아니라 **`Ready`** 로 찾는다 — (3)처럼 배너가 깨져도 걸리게.

## ⚠ 사용자에게 — MAC 을 되돌리는 법 (읽고 굽기 바란다)

스케치는 **휘발성 변종(`AT+CIPSTAMAC_CUR`)을 먼저** 시도한다. 그게 먹으면 전원을 뺐다 꽂으면
원래 MAC 으로 돌아오므로 할 일이 없다. 로그에 이렇게 찍힌다:
```
[APTEST]   AT+CIPSTAMAC_CUR 이 먹었다 (휘발성 — 전원을 빼면 원래대로 돌아온다)
```

구형 펌웨어라 `_CUR` 이 없으면 `AT+CIPSTAMAC` 을 쓰는데 **이건 플래시에 남을 수 있다.**
그 경우 로그가 경고를 찍는다. 되돌리려면 로그 위쪽의 `★ 원래 MAC` 값을 그대로 써서
`AT+CIPSTAMAC="<원래값>"` 을 한 번 실행하면 된다.
**그래서 원래 MAC 을 바꾸기 전에 먼저 찍게 해 뒀다** — 못 되돌리는 상황이 안 생긴다.

두 명령이 다 `ERROR` 면 스케치가 그렇게 보고하고 멈춘다(MAC A/B 불가). 그때의 대안도 로그에 적었다:
다른 AP/폰 핫스팟에 붙여 보기.

## 내 판단 — 다음 순서에 대해

A/B 결과와 **무관하게** 이미 확보된 사실이 하나 있다: **아무 자극 없이 ESP 와 MCU 가 스스로
재부팅한다.** 이건 차단으로 설명이 안 되고, 백오프로도 고쳐지지 않는다.
그래서 **B 가 성공해서 차단이 확정되더라도 전원 문제는 따로 남는다** — "차단 확정 = 전원 무죄"
라는 판정표 2행은, 재부팅이 0회였던 시행에서만 그대로 읽어야 한다. 스케치가 그 조건을
