# REQ-0066 · 실기 수신경로 검증: 서버에서 예약(R)을 한 번 내려 달라 — +IPD 가 0건이다

**요청자** `arduino-engineer` → **담당** `socket-engineer`

## 요청 내용

요청: 아두이노 하드웨어가 복구되어 내가 '접속됨'을 알리면, **진짜 서버에서 예약 프레임(R)을 1회 이상 내려 달라.** 가짜 아두이노(net/fake_arduino.py)가 아니라 실기 세션 대상이어야 한다. 가능하면 2시간 소크 중에도 최소 1회 더 걸어 달라(장시간 운용에서 수신 경로가 사는지 확인). 내가 확인할 것: (1) 장치가 +IPD 를 실제로 받는가 (2) reserved 비트에 반영되는가 (3) ACK(A 프레임)를 되쏘는가. 서버 쪽에서 확인해 줄 것: 그 ACK 가 실제로 도착했는가와 rid 가 일치하는가.

## 왜 필요한가

실기 로그 전체(약 10분, 프레임 125개 송신)에서 **+IPD 가 0건**이다. 즉 서버→아두이노 방향(예약 R / 취소 C / 테스트 T / 시뮬 M)이 실기에서 **한 번도 실행된 적이 없다.** 프레임 파싱·체크섬 검증·멱등 캐시·ACK 송신이 전부 미실행 코드다. 이 프로젝트의 핵심 흐름이 브라우저 예약 → 서버 → 아두이노 → 반영 → ACK 인데 그중 '→ 아두이노' 구간이 미검증이라, 이대로면 시연의 예약 버튼이 그 경로의 첫 실행이 된다. 게다가 이 보드의 구형 펌웨어는 어휘가 문서와 달랐다(CLOSED 가 아니라 Unlink, ALREADY 가 아니라 ALREAY). +IPD 형식도 다를 수 있는데 한 번도 안 걸려봐서 발견될 기회조차 없었다.

### ⚠ 교차검증 지표 — arduino 의 예상이 틀려서 정정했다 (03:1x, 주입으로 확인)

arduino-engineer 가 CIPSEND 프롬프트를 놓쳤을 때 **`#`×n + `\n`** 더미 줄을 보내 재동기한다.
그쪽은 그게 서버의 `버린줄(모름)` 로 잡힐 거라 예상했는데 **아니다. `체크섬` 으로 잡힌다.**

측정: `#×38` → 체크섬, `#×50` → 체크섬, `#×70` → **과길이**. 결과 `버린줄 3(체크섬 2/과길이 1/모름 0/잡음 0)`.

이유: `verify_line()` 이 **타입 검사보다 먼저** 돌고, `#` 만 있는 줄에는 쉼표가 없어
마지막 쉼표 탐색에서 탈락한다. "모르는 타입" 분기는 **체크섬을 통과한 줄만** 도달한다.
§2.1-7 을 읽고 추론하면 틀리는 자리다 — 규칙과 코드가 도는 순서는 다르다.

**짝짓기 해석** (`프롬프트 재동기 N회` ↔ `버린줄(체크섬)`, 약속 길이가 64 이상이면 `과길이`도 합산):

| 비교 | 해석 |
|---|---|
| 체크섬 == 재동기 | 더미가 전부 전선으로 나갔고 진짜 손상 없음 |
| 체크섬 > 재동기 | **초과분이 진짜 바이트 손상** — 링크를 의심할 조건은 이쪽뿐이다 |
| 체크섬 < 재동기 | **정상 기대치다.** 차이 = ESP 가 실은 명령 모드여서 더미를 로컬에서 삼킨 횟수 |

> ⚠ **세 번째 행은 내가 처음에 "링크가 끊겼다"로 단정했다가 실측으로 반증됐다**(arduino-engineer 관측).
> ESP 가 데이터 대기가 아니라 **명령 모드**였으면 더미를 에코하고 `Error` 로 먹는다 — **전선에 안 나간다.**
> 그래서 서버에는 아무것도 안 온다. **정상이고 링크 이상이 아니다.** 정상 기대치는 `재동기 ≥ 체크섬`이고,
> 그 차이 자체가 "프롬프트를 헛되이 기다린 비율"이라는 정보다.
>
> **둘을 가르는 방법 — 내 로그의 세 번째 지표를 본다.** 같은 시각에
> `! 아두이노 오프라인 판정` 또는 `-ARD 세션#N 종료` 가 **있으면** 진짜 링크 사고,
> **없으면** 명령 모드(무해)다. 두 지표로 모호하면 세 번째를 본다 — 오늘 밤의 교훈 그대로다.

셈법: `프레임 = 정상 + 체크섬 + 모름` (과길이·잡음은 파서 도달 전에 버려져 미포함).
**더미도 공백 타이머를 리셋한다**(깨진 줄도 링크 생존의 증거다) → 재동기 중에는 `최대공백`이 작게 유지된다.

### 소크 요약 작성 규칙 — **`0` 을 "무결"로 적지 마라**

`0` 은 두 가지 뜻이다. **"그 경로가 건강했다"(성과)** 와 **"그 경로가 한 번도 안 돌았다"(미관측)**.
오늘 밤 `+IPD 0건` 이 정확히 후자였고 우리는 그걸 "문제 없음"으로 오해할 뻔했다.
지표별로 미리 정해 둔다.

| 지표 | `0` 의 뜻 | 요약에 쓸 말 |
|---|---|---|
| 세션 / 프레임 | 장치가 안 붙었다 | **소크 자체가 무효** |
| 오프라인 N회 | 링크가 한 번도 안 끊겼다 | **성과** (엣지 판정이 실제로 도는 건 사본에서 검증했다) |
| 재부팅감지(uptime추론) | 2차 방어선이 안 걸렸다 | **미관측이 정상.** "검증됨"으로 쓰지 마라 |
| 버린줄(모름/과길이/잡음) | 그 오류가 안 일어났다 | **미관측** (분기 생존은 주입으로 따로 증명해 뒀다) |
| 버린줄(체크섬) | 손상도 더미도 없었다 | `재동기` 와 **짝지어** 판단 |
| **재전송 / ACK실패** | ⚠ **모호하다** — 아래 참조 | 하행 요청 수를 세어 판정 |

**🔴 `재전송 0 · ACK실패 0` 이 가장 위험하다.** 그건 "하행이 건강했다"일 수도,
**"하행 요청이 아예 없었다"**(= `+IPD` 0건과 같은 상태)일 수도 있다. 지금 요약에는
**하행 요청 수를 세는 칸이 없다** — 서버 동결 중이라 카운터를 못 넣는다.

**→ 로그에서 유도한다(코드 변경 불필요):**
```bash
grep -c "→ARD" /tmp/parking-soak.log      # 하행에 실제로 나간 줄 수(재전송 포함)
# 최초 요청 수 = (위 값) - (요약의 재전송 수)
```
최초 요청 수가 **0 이면** `재전송 0 · ACK실패 0` 은 **미관측**이다. **1 이상이어야 성과로 읽는다.**

**이 식도 계측기다 — 소크 전에 검증했다** (기존 실행 로그로. 추가 비용 0):

- **전제 ①: `→ARD` 가 전부 요청인가** → ✅ `send_ard()` 호출 지점이 **정확히 4곳**뿐이다
  (R/C 하달 · T · M · 재전송). **하행에는 하트비트·킵얼라이브·스냅샷이 없다.** 분자가 부풀 여지가 없다.
- **전제 ②: `재전송` 이 "줄" 단위인가** → ✅ `tick()` 의 재전송 루프에서 **줄마다 1 증가**한다.
- **실측 대조**: 예약 1건에 재전송 2회가 났던 실행에서 `grep -c "→ARD"` = **3**, 요약 `재전송 2`
  → `3 − 2 = 1`. **실제로 보낸 요청 1건과 정확히 일치.** 식이 맞는다.

> ⚠ **다만 "요청"에는 서버가 스스로 낸 것도 포함된다.** §7.4 재부팅 재하달(`R`)과
> §7.6 불일치 정정(`C`)도 같은 경로로 나간다. **하행이 돌았는가**를 재는 목적에는 그게 맞지만,
> 이 숫자를 **"사용자 예약 건수"로 읽으면 틀린다.** 요약에는 "하행 요청(서버 자발 포함)"으로 적는다.
>
> **부수 효과 — B3 를 먼저 하는 이유가 하나 더 있다.** B3 예약이 살아 있으면 이후
> **장치가 재접속할 때마다 §7.4 재하달이 `R` 을 자동으로 내린다.** 즉 B3 한 번이
> 소크 내내 하행 표본을 계속 만들어 준다. 예약이 하나도 없으면 재하달은 아무것도 안 보내므로
> 하행은 2시간 내내 0으로 남는다.

> **그래서 REQ-0066(B3 예약 왕복)이 소크의 전제조건이다.** 이 시험이 하행 요청을 최소 1건
> 만들어 주므로, 그 덕에 소크의 `재전송/ACK실패` 숫자가 **비로소 의미를 갖는다.**
> 소크 중에도 최소 1회 더 걸기로 한 이유가 이것이다 — 장시간 구간에도 하행 표본을 남기기 위해서다.

### 소크 중 하행 표본 일정 — **재접속에 기대지 않는다** ⚠

**성공이 계측을 굶긴다.** §7.4 재하달은 **재접속할 때만** 도므로, 소크가 잘 될수록(끊김 0)
하행 표본이 **최초 B3 한 건뿐**이 된다. 게다가 초반 표본 하나로는 **후반의 열화**
(5분째는 되는데 90분째는 안 되는 경우)를 원리적으로 못 잡는다.
규칙 4와 같은 형태다 — **초반에만 재는 지표는 후반의 사고를 못 잡는다.**

**→ 일정으로 박는다. 도구도 만들어 뒀다: `net/soak_probe.py`** (내 트리, 검증 완료)

```bash
# 소크 시작(T0)과 동시에 백그라운드로 띄운다
python3 net/soak_probe.py --at 5:A1 --at 60:A2 --at 110:A3
```

- **T0+5분 / T0+60분 / T0+110분** 세 지점에서 `예약 → 취소` 짝을 돌린다.
- **취소까지 짝으로 도는 이유**: 예약만 걸면 자리가 잠긴 채 남는다. 상태를 원위치시킨다.
- **B3(REQ-0066 본 시험) 예약은 그대로 둔다** — 재접속이 일어나면 §7.4 재하달 표본이 덤으로 생긴다.
- 이 스크립트는 **서버를 건드리지 않는다.** 브라우저와 똑같은 WS 요청(§5.4)일 뿐이라 동결선과 무관하다.
- **내 세션이 죽어도 돌아간다**(별도 프로세스). 세션이 살아 있어야만 되는 계획은 계획이 아니다.

**예행 검증 완료**(가짜 장치, 포트 옮긴 사본): 한 표본 = 하행 요청 **정확히 2건**.
```
→ARD R,1,A1,u17,60   ←ARD A,1,A1,0,30     (예약)
→ARD C,2,A1,2D       ←ARD A,2,A1,0,33     (취소)
```
둘 다 같은 초에 ACK, 재전송 0. 자리도 원위치됐다.

**읽는 법 — 열화 판정**: 세 지점의 **재전송 발생 여부**를 비교한다. 서버 로그 시각이 초 단위라
ACK 지연을 정밀히 못 재지만, **재전송(1.5초 임계) 발생이 곧 임계 초과 신호**다.
`P1 재전송 0 / P3 재전송 2` 같은 모양이 나오면 **시간에 따른 열화**다.

**⚠ arduino-engineer 와 시각을 맞춰야 한다** — 그쪽이 장치에서 `+IPD` 수신을 봐야 왕복이 성립한다.

> **처방**: 조각 검사와 **별도로** 이어붙인 전체를 한 번 더 검사한다. 조각 검사의 합은 전체 검사가 아니다.

### ✅ §4.2 멱등 — **검증됐다. 사고가 표본을 만들었다** (08:57, `[미검증]` 딱지 해제)

일정으로 못 박지 못한다던 그 시험이 **링크 사고로 저절로 발동했다.** 끊길 때마다 §7.4 재하달이

**세 건이 나왔고, 답이 셋 다 다르다:**

| rid | 서버 송신 | 장치 `[DUP rid]` | 판정 |
|---|---|---|---|
| 2 | 3회 | **없음** | **하행 유실** — 한 번도 도착 못 함(세션#6 은 `프레임 0` 으로 끝났다) |

rid 6 의 장치 로그가 결정적이다 — result·slot·**체크섬까지 동일**한 ACK 를 상태 재평가 없이 냈다.
**캐시를 그대로 낸 것이지 다시 계산한 것이 아니다.**

> ⚠ 단, 두 번째 DUP 의 ACK 는 `[TX-DROP]`(프롬프트 놓침)으로 **송신 자체가 실패**했다.
> **캐시는 옳았고 링크가 실패한 것**이라 §4.2 문제가 아니다. 둘을 섞어 적지 않는다.

> ⚠ **알 수 없는 채로 남기는 것**: 각 건에서 **몇 번째 송신이 ACK 된 것인지**는 못 가른다.
> 로그 시각이 초 단위라 재전송과 ACK 가 같은 초에 찍히기 때문이다. **추정으로 채우지 않는다.**

**내가 틀린 방식도 기록한다.** 나는 `A,3,B3,2` 의 해석을 **두 갈래**(캐시 재생 / 재평가)로 제시하고
"장치 로그가 이 둘을 가른다"고 했다. **실제 답은 셋째였다 — 중복이 애초에 도착하지 않았다.**
`체크섬 < 재동기` 때와 **같은 실수**다: 그럴듯한 두 갈래를 만들고 **"그 사건이 일어나지 않았다"를
목록에서 빠뜨렸다.** 앞으로 해석지를 만들 때 **"전제된 사건 자체가 없었다"를 항상 한 줄 넣는다.**

### 그 밖에 미검증으로 남는 것 — 정직하게 적는다

**§4.2 멱등(같은 `wire_rid` 재수신)은 이 시험으로 검증되지 않았다.**
`wire_rid` 는 서버가 단조증가로 부여하므로(§4.1) WS 로 예약을 한 번 더 보내면 **새 rid** 가 나간다.
같은 rid 가 두 번 나가는 경로는 **§7.3 재전송뿐**이고 그건 **ACK 가 1.5초 안에 안 올 때만** 발동한다.
**인위적 훅(ACK 한 번 버리기)은 넣지 않기로 했다** — 재플래시가 소크 관측을 무효화하는 비용이 크고,
무엇보다 **인위적 고장은 실기 조건이 아니다.**

→ 소크 중 자연 발생을 기다린다. 대조 규칙(요청자와 합의):

| 관측 | 해석 |
|---|---|
| 내 `↻ 재전송(wire_rid=N)` **와** 장치 `[DUP rid] N` 둘 다, rid·횟수 일치 | §4.2 설계대로 동작 |
| 내 재전송은 있는데 장치 `[DUP rid]` 없음 | **재전송이 장치까지 못 갔다**(하행 유실) |
| 장치 `[DUP rid]` 는 있는데 내 재전송 기록 없음 | **서버 계측 누락** — 내 쪽을 봐야 한다 |

**끝내 안 나오면 `[미검증 — 발동 조건이 오지 않음]` 으로 적는다.** "검증됨"으로 쓰지 않는다.
