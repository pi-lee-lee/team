## 왜 필요한가

실기에서 step=4 로 100초 넘게 정체하며 [AT] "no ip" 만 반복된다. 서버·IP·포트는 전부 정상임을 루트가 실측 확인했으므로 남은 원인은 클라이언트 코드 하나다. 이 건이 풀리기 전에는 어떤 상시가동 개선도 검증할 수 없다.

## 대상 파일

- `조별과제샘플/client.ino`
## 완료 기준

보드를 구운 뒤 시리얼에 (1) CWJAP 실패 사유가 사람이 읽는 문장으로 찍히고 (2) IP 를 못 받은 동안 CIPSTART 가 나가지 않으며 (3) WiFi 가 붙으면 자동으로 TCP 까지 올라가 서버에 +ARD 가 찍힌다. 그 뒤 2시간 연속 무재부팅·무끊김을 관측한다.

### 1. 플래시 성공 — 배선 수리가 먹었다

`arduino-cli upload -p /dev/cu.usbmodem21201 --fqbn arduino:avr:uno` **성공**(처음이다).
컴파일 12186 B(37%) / RAM 792 B(38%) — 파일을 한 글자도 안 고쳤으므로 종전과 동일하다.
포트는 업로드 직전 `lsof` 로 비어 있음을 확인했다.

**`rx` 가 0 을 벗어났다.** 3초 주기로 계속 증가한다(111 → 170 → 248 → 358 → 505 …).
즉 **ESP→Uno 방향이 살아났고 ESP 는 정상 응답 중이다.** REQ-0061 의 미지가 여기서 닫혔다.

### 2. 그런데 펌웨어가 REQ 본문의 가정과 다르다 ⚠

```
[AT] "[System Ready, Vendor:www.ai-thinker.com]" (41)
```

**ESP-AT v2.2 가 아니라 구형 ai-thinker AT 펌웨어다.** 그래서:

- `WIFI CONNECTED` / `WIFI GOT IP` 를 **아예 내지 않는다.** 로그 전체에 `WIFI` 로 시작하는 줄이 0건이다.
  → REQ 의 근본원인 (1)(`strncmp(s,"WIFI",4)==0` 이 상태줄을 버린다)은 **이 보드에서는 발동하지 않는다.**
    버릴 줄 자체가 안 온다. 그 수정은 신형 펌웨어 대비로는 옳지만 지금 증상의 원인이 아니다.
- `+CWJAP:n` **사유 코드도 없다.** 이 펌웨어는 그냥 `FAIL` 한 줄로 끝낸다.
  → REQ 의 산출물 ③("+CWJAP:n 을 사람이 읽는 문장으로")은 **이 펌웨어에서는 원리적으로 불가능**하다.
    사유를 알아내려면 `AT+CWLAP`(주변 AP 목록) 쪽으로 가야 한다.

### 3. 진짜 원인 — 근본원인 (2) 가 맞았고, 증상은 더 나쁘다

```
[NET] 2 CWJAP
[AT] "AT+CWJAP="unknowns_network2.4","Dmagbdgks_spxmdnjzm!01"" (55)
[DIAG] offline step=3 rx=170 lines=7 up=6s        ← 응답 없음
[DIAG] offline step=3 rx=170 lines=7 up=9s        ← 응답 없음 (rx 가 12초간 170 고정)
[DIAG] offline step=3 rx=170 lines=7 up=12s
[NET] 3 CIPMUX=0
[AT] "AT+CIPMUX=0" (11)
[AT] "busy p..." (9)                              ← ★ 거부됐다. CWJAP 가 아직 안 끝났다
[NET] 4 CIPSTART
[AT] "AT+CIPSTART="TCP","192.168.50.146",9991" (39)
[AT] "busy p..." (9)                              ← ★ 또 거부
[NET] 4 CIPSTART
[AT] "AT+CIPSTART="TCP","192.168.50.146",9991" (39)
[AT] "busy p..." (9)
[AT] "FAIL" (4)                                   ← ★★ up≈20s, CWJAP 의 최종 결과
[NET] 4 CIPSTART
[AT] "AT+CIPSTART="TCP","192.168.50.146",9991" (39)
[AT] "no ip" (5)                                  ← 이후 무한 반복
```

읽는 순서가 중요하다:

1. **CWJAP 는 9초 안에 안 끝난다.** 이 펌웨어에서 결과(`FAIL`)가 나오기까지 **약 16초** 걸렸다.
2. 그 사이 사다리는 타이머만 보고 전진해 CIPMUX·CIPSTART 를 쐈고, ESP 는 **`busy p...` 로 전부 거부**했다.
   → **`AT+CIPMUX=0` 은 실제로 적용된 적이 없다.** 로그에 `OK` 가 없다. 이것이 조용한 두 번째 고장이다.
3. `FAIL` 이 온 뒤의 `no ip` 는 원인이 아니라 **결과**다. IP 가 없으니 당연하다.

즉 `no ip` 무한반복의 상류는 **CWJAP 실패**이고, 그 실패가 `busy p...` 더미에 묻혀 안 보였던 것이다.

### 4. 사용자 확인이 필요한 것 (코드로 못 고친다)

CWJAP 가 `FAIL` 로 끝났다. 구형 펌웨어라 사유가 없으므로 남은 갈래는 둘이다:

- **(a) 비밀번호가 틀렸다** — `Dmagbdgks_spxmdnjzm!01`
- **(b) 그 AP 가 ESP 에게 안 보인다** — 2.4GHz 여야 하고, 전파가 닿아야 하고, 구형 펌웨어는
  WPA3/혼합모드·숨김 SSID·긴 SSID 에서 실패하는 사례가 흔하다

**이 둘을 가르는 것이 `AT+CWLAP` 이다.** 지금 코드에 없어서 내가 넣는 중이다(REQ 요구 ⑤).
목록에 `unknowns_network2.4` 가 보이면 (a), 안 보이면 (b) 로 확정된다.

⚠ ESP 는 Uno 의 SoftwareSerial 에만 물려 있어 **내가 USB 로 AT 를 직접 칠 수 없다.**
스케치에 넣어서 구워야만 물어볼 수 있다. 그래서 CWLAP 도 코드 작업에 포함된다.

### 5. 지금 하는 일

사다리를 **타이머 구동에서 응답 구동으로** 바꾼다. 구체적으로:

1. CWJAP 는 결과(`OK` / `FAIL` / `WIFI GOT IP` / `+CWJAP:n`)가 올 때까지 **기다린다.** 9초 타임아웃으로 전진하지 않는다.
2. `busy p...` 를 받으면 **전진하지 않고 같은 단계를 뒤로 미룬다.**
3. IP 확보를 `AT+CIFSR` 로 **확인한 뒤에만** CIPSTART 로 간다(펌웨어 세대와 무관하게 동작하는 유일한 방법).
4. `no ip` → CIPSTART 재시도가 아니라 **CWJAP 로 되돌아간다.**
5. CWJAP 2회 연속 실패 시 `AT+CWLAP` 한 번 → AP 목록을 찍는다.

끝나는 대로 다시 구워서 로그를 붙인다.

## ★ 결론 — 코드는 고쳤고, 남은 것은 **사용자만 고칠 수 있다**

수정본을 구워서 실측했다. **사다리는 이제 설계대로 동작한다. 그리고 그 덕분에 진짜 원인이 드러났다.**

### 진단 결과: AP 는 보인다. 결합만 거부된다

CWJAP 를 두 번 실패시킨 뒤 자동으로 `AT+CWLAP` 이 나갔고, 목록에 **우리 AP 가 있었다**:

```
[AT] "+CWLAP:(3,"unknowns_network2.4",-63,"fc:34:97:4e:6c:10",12)" (59)
[AT] "OK" (2)
[NET] ── AP 스캔 판정 ──────────────────────────
[NET] 설정한 SSID 가 목록에 **있다** → AP 는 보인다.
[NET]   그런데 CWJAP 가 실패한다 = **비밀번호를 의심하라.**
```

읽는 법:

| 필드 | 값 | 뜻 |
|---|---|---|
| SSID | `unknowns_network2.4` | 철자가 설정과 **정확히 일치**한다 |
| ecn | `3` | WPA2_PSK — 구형 ESP8266 이 지원하는 방식이다 |
| RSSI | `-63` | **신호는 충분히 강하다.** 거리·전파 문제가 아니다 |
| 채널 | `12` | 아래 참고 |

즉 **(b) "AP 가 안 보인다" 가설은 실측으로 배제됐다.** SSID 철자도, 대역(2.4GHz)도, 거리도 아니다.
AP 는 멀쩡히 보이는데 **결합(association)만 `FAIL`** 로 끝난다.

### 그래서 남은 것 — 사용자 조치가 필요하다 (코드로 우회하지 않는다)

**1순위: 비밀번호가 틀렸다.**
현재 스케치의 값은 `Dmagbdgks_spxmdnjzm!01` 이다(22자). 이 문자열이 공유기의 실제 비번과
한 글자라도 다르면 지금 증상이 정확히 재현된다. 대소문자·`_`·`!`·`0`과`O`·`1`과`l` 을 확인해 달라.
⚠ REQ 본문대로 `!` 와 `_` 는 AT 이스케이프 대상이 아니다 — 그쪽은 원인이 아니니 파고들 필요 없다.

**2순위(가능성 낮음): 공유기가 구형 클라이언트를 거부한다.**
WPA3 전환모드나 PMF(802.11w) 필수 설정이 켜져 있으면 구형 ESP8266 은 결합하지 못한다.
비번이 확실히 맞는데도 계속 FAIL 이면 이쪽을 본다.

**채널 12 에 대하여 — 의심했다가 접었다. ⚠ 이 판단은 아래 「정정」에서 뒤집혔다. 그쪽을 읽어라.**
(원래 근거: 스캔이 채널 12 의 AP 를 찾아냈으니 허용 채널 집합에 12가 있다고 봤다. **틀렸다.**)

### 검증된 코드 변경 (REQ 요구 1~5 전부)

| 요구 | 상태 | 실측 근거 |
|---|---|---|
| ① WIFI 상태줄을 읽되 `return` 유지 | 구현 | 이 펌웨어는 `WIFI *` 줄을 안 낸다. 신형 대비 경로로 넣었고 `return` 은 그대로 뒀다 |
| ② IP 확인 후에만 CIPSTART | **동작 확인** | IP 가 없는 내내 `step` 이 5(CIPSTART)에 **한 번도 가지 않았다.** `no ip` 가 로그에서 사라졌다 |
| ③ 실패 사유를 사람 말로 | **동작 확인** | `[NET] ★ CWJAP 실패 1회/2회` + 위 스캔 판정 3줄. 구형 펌웨어는 `+CWJAP:n` 을 안 주므로 CWLAP 판정이 그 자리를 대신한다 |
| ④ `no ip` → CWJAP 복귀 | 구현 | 애초에 `no ip` 가 나올 상황을 안 만들게 됐다. 코드 경로는 살아 있다 |
| ⑤ 2회 실패 시 CWLAP 1회 | **동작 확인** | 위 로그. 이 진단이 이번 답을 냈다 |

전후 비교가 가장 분명한 증거다:

```
[전] CWJAP 응답 전에 전진 → busy p... ×2 → FAIL → no ip 무한반복 (step=4 정체)
[후] CWJAP 응답을 기다림      → FAIL 을 정확히 계수 → 2회째에 CWLAP → 원인 판정 출력
```

부수 수정 하나가 더 있다: 부팅 때 ESP 가 이전 세션의 명령을 처리 중이면 `AT+RST` 조차
`busy p...` 로 거부되는데, 예전 코드는 그것도 무시하고 전진했다. 이제 `busy` 를 받으면
**전진하지 않고 같은 단계를 다시 시도**한다(실측: 12초간 재시도하다 정상 부팅으로 복귀).

### 추가 수정 2건 — 재접속 경로의 구멍 (2시간 관측 전에 막아야 한다)

위 로그로는 안 드러나는(=아직 한 번도 붙지 못해서 재접속 경로를 안 밟은) 결함 둘을 더 고쳤다.
**둘 다 2시간 연속 관측이 반드시 밟게 되는 경로다.**

**(1) 소켓이 죽은 뒤 재접속할 때 IP 를 다시 확인하지 않았다 — 요구 ② 위반이 재발한다.**

`netHasIp` 는 접속 성공에서 참이 되는데, `CLOSED` 분기와 CIPCLOSE 사다리는 이 값을 건드리지 않고
곧장 CIPSTART 로 갔다. **소켓이 죽은 이유가 공유기 재부팅이면 와이파이도 같이 끊긴 것**이고,
이 펌웨어는 `WIFI DISCONNECT` 를 내지 않으므로 `netHasIp` 는 참으로 남는다.
→ 문지기를 통과해 **IP 없이 CIPSTART** 가 나간다. 이번에 고치려던 바로 그 상황이 재현된다.
자기교정은 된다(`no ip` → CWJAP) 하지만 그건 "안 나가게 한다"는 요구를 어긴 뒤의 뒷수습이다.

→ 두 경로 모두 **CIPSTART 가 아니라 CIFSR 로** 되돌아가게 바꿨다. CIFSR 은 로컬 질의라 300ms 다.
  **재진입할 때마다 IP 를 다시 확인한다.** 검증 방법: 강제로 끊었을 때 로그에 `[NET] 3 CIFSR` 이
  CIPSTART 보다 먼저 나오고 `no ip` 가 한 줄도 안 나오면 맞다.

**(2) `busy` 재전송이 사다리를 가둘 수 있었다.**

`busy` 를 받으면 같은 단계를 1.5초 뒤 되쏘게 했는데, 되쏘면 안 되는 단계가 셋 있었다:
`CWLAP`(재스캔이 9초를 태우고 그동안 결합 불가 + "한 번만 스캔" 규칙이 깨진다),
`CIPCLOSE`(`closeAttempts` 계수를 우회해 사다리가 영원히 안 올라간다), `CWJAP`(이미 제외돼 있었다).
→ 되쏘는 단계를 `RST · CIFSR · CIPMUX · CIPSTART` 넷으로 **한정**했다.

컴파일 통과 — flash **14720 B (45%)** / RAM **879 B (42%)**. 이 최종본을 보드에 올려 뒀다.
즉 **비밀번호만 맞으면 그대로 붙는 상태**다.

### ⚠ 비밀번호 단정에 대한 유보 — 관측 하나가 그쪽을 약하게 만든다

위에서 "비밀번호를 의심하라"고 했지만, **오타로 단정하지는 말아 달라.** 근거:

**CWJAP 가 매번 정확히 약 16초를 다 태우고 `FAIL` 한다.** 구형 ai-thinker SDK 에서
비밀번호가 틀리면 보통 **2~4초** 만에 떨어진다(AP 가 인증을 즉시 거절하므로). 16초는
**결합·핸드셰이크가 시도되다 시간초과로 끝나는 모양**에 가깝다.

그래서 두 갈래를 **같은 무게로** 봐 달라:
- (a) 비밀번호 오타 — 확인 비용이 0 이니 먼저 확인
- (b) **공유기가 이 구형 클라이언트를 못 받아들인다** — WPA3 전환모드, PMF(802.11w) 필수,
  또는 "레거시 기기 허용" 류 설정. 이쪽이면 비번을 열 번 다시 쳐도 안 붙는다.
  공유기 설정에서 보안을 **WPA2-PSK(AES) 단독**으로, PMF 를 **비활성/선택**으로 두면 해결된다.

(b) 를 배제하지 못한 채 비번만 고치면 한 사이클을 버린다. 둘을 같이 확인해 달라.

## 🔁 정정 (루트 지적 반영) — **1순위는 채널 12 다. 내 판단이 틀렸다.**

루트가 출처를 들고 두 가지를 정정했고, **둘 다 받아들인다.** 근거가 내 추론보다 강하다.

### 정정 A — 채널 12 를 접은 것이 성급했다 (내 오류)

내 근거는 *"스캔이 12번 AP 를 찾았으니 허용 채널 집합에 12가 있다"* 였다. **이 추론이 틀렸다.**
ESP8266 은 **패시브 스캔으로는 12/13 을 보면서 결합만 막히는** 것이 알려진 실패 양상이다.
스캔 가능 채널과 결합 가능 채널이 같다고 가정한 것이 오류였다.

- [확정: https://github.com/espressif/ESP8266_NONOS_SDK/issues/300] ch13 결합 불가, `wifi_set_country()` 무효
- [확정: https://github.com/esp8266/Arduino/issues/7083] 동일 증상
- [확정: https://olimex.wordpress.com/2021/12/10/avoid-wifi-channel-12-13-14-when-working-with-esp-devices/] 12/13/14 회피 권고
- 기본 규제도메인이 US(1~11)다.

**그리고 내 16초 관측이 오히려 이 가설을 지지한다.** 비번 오류면 AP 가 즉시 거절해 2~4초에 떨어진다.
채널이 막히면 **결합 시도가 응답 없이 시간초과**로 끝난다 — 16초는 정확히 그 모양이다.
즉 내가 "비번 단정 금지"의 근거로 든 바로 그 데이터가 **채널 가설의 증거였다.**

### 정정 B — WPA3 전환모드 갈래는 내린다 (다만 단서 하나)

[확정: ESP-AT Wi-Fi AT Commands, ecn 표] `0=OPEN 1=WEP 2=WPA_PSK 3=WPA2_PSK 4=WPA_WPA2_PSK 5=WPA2_ENTERPRISE 6=WPA3_PSK 7=WPA2_WPA3_PSK`
받은 값은 `+CWLAP:(3,...)` = **WPA2_PSK 단독**. 전환모드였다면 7 이어야 한다. → 내린다.

⚠ 단서 하나만 기록해 둔다(순위를 올리자는 게 아니라 나중에 헛짚지 않기 위해서다):
**이 보드의 구형 ai-thinker 펌웨어는 WPA3 이전 물건이라 ecn 열거가 0~4 까지밖에 없을 수 있다.**
그렇다면 WPA2/WPA3 전환 AP 를 `3` 으로 보고했을 가능성이 남는다 — `6`/`7` 을 모르는 코드가
`7` 을 출력할 수는 없기 때문이다. 따라서 "ecn=3 이므로 WPA3 아님"은 **신형 펌웨어에서만 엄밀**하다.
이 단서는 아래 `AT+GMR` 로 펌웨어 판을 확인하면 바로 정리된다. 순위는 그대로 뒤에 둔다.

### 사용자에게 전할 순서 (확정)

| 순위 | 조치 | 비고 |
|---|---|---|
| **1** | **공유기 채널을 12 → 1 / 6 / 11 로 변경** | **확정 해법.** 코드로는 못 고친다 |
| 2 | 비밀번호 확인 | 비용 0 |
| 3 | PMF(802.11w) 비활성 / WPA2-PSK(AES) 단독 | 위 둘이 아니면 |

⚠ SSID 가 `unknowns_network2.4` 라 **사용자가 관리 권한을 가진 공유기가 아닐 수 있다.**
그렇다면 1순위 조치가 불가능하므로 아래 우회 실험의 값이 커진다.

### 부수 실험 — `AT+GMR` / `AT+CWCOUNTRY` (루트 승인, 실패하면 즉시 접는다)

ESP 는 Uno 의 SoftwareSerial 에만 물려 있어 **AT 를 손으로 칠 수 없다.** 스케치에 넣어야만 물어본다.
그래서 CWJAP 2회 실패 시의 진단 사슬에 두 단계를 끼워 넣었다(주 사다리는 건드리지 않았다):

```
CWJAP 2회 실패 → AT+GMR → AT+CWCOUNTRY_DEF=0,"KR",1,13 → AT+CWLAP → CWJAP 재시도
```

- `AT+GMR` — **펌웨어 판을 확정한다.** 이것이 위 ecn 단서와 CWCOUNTRY 지원 여부를 동시에 정리한다
- `AT+CWCOUNTRY_DEF` — 규제도메인을 1~13 으로 넓히는 우회 시도.
  구형 펌웨어면 `ERROR` 가 뜰 것이고, **그 `ERROR` 자체가 "코드로는 못 고친다"의 확증**이다.
  위 이슈들도 대부분 무효라고 보고하므로 기대는 낮다. 되면 로그에 바로 드러난다.

## ✅ 최종 — **붙었다. 사용자 조치는 필요 없었다. 두 가설 다 틀렸다.**

진단 빌드를 구운 뒤 **네 번째 CWJAP 시도에서 그냥 성공했다.** 설정은 한 글자도 안 바뀌었다 —
같은 비밀번호, 같은 채널 12, 같은 공유기다.

```
[AT] "FAIL" (4)                                   ← 1회 (up≈30s)
[AT] "FAIL" (4)                                   ← 2회 (up≈45s) → 여기서 진단 사슬
[AT] "FAIL" (4)                                   ← 3회 (up≈69s)
[AT] "OK" (2)                                     ← ★ 4회째 성공 (up≈87s)
[NET] CWJAP OK — 결합됐다. IP 를 실제로 받았는지 CIFSR 로 확인한다
[NET] 3 CIFSR (IP 를 실제로 받았는가)
[AT] "192.168.50.111" (14)
[NET] ★ IP 확보: 192.168.50.111
[NET] 4 CIPMUX=0
[AT] "OK" (2)                                     ← ★ CIPMUX 가 처음으로 실제 적용됐다
[NET] CIPMUX=0 적용됨 → CIPSTART
[NET] 5 CIPSTART
[AT] "Linked" (6)
[NET] online (CONNECT) + 캐시 비움
[TX] S,0,0110000010,0000000000,86,P1,0D
[AT] "SEND OK" (7)                                 ← 이후 1Hz 로 계속
```

### 그래서 진짜 원인은 무엇이었나

> ⚠⚠ **`[보류 — 전원 부족과 교란됨]`** 아래 문단은 **정상 전원에서 재측정해야 성립한다.**
> 루트가 뒤에 확인한 바: **ESP 전원을 Uno 의 3.3V 핀에서 받고 있었다.**
> 공급 **50 mA**(LP2985-33DBVR) vs ESP8266 송신 **170 mA**(전형) · ESP-01 피크 **300~430 mA**.
> **최소 3.4배, 피크 8.6배 초과다.** 여기에 RX 5V 직결(정격 3.3V)까지 겹쳐 **과전압과 전류부족
> 두 경로로 동시에 혹사**하고 있었다.
> 그러므로 "이 펌웨어는 원래 CWJAP 가 자주 실패한다" 는 **결론으로 남기면 안 된다.**
> 다음 사람이 그것을 사실로 받아들이면 진짜 원인을 또 놓친다. 아래 「전원 가설 검증」 참조.

~~이 구형 펌웨어의 CWJAP 는 원래 잘 실패한다. 여러 번 시도하면 붙는다.~~ **← 보류**

**보류되지 않는 부분(코드 구조의 사실이라 전원과 무관하다):**
옛 코드는 **CWJAP 를 재시도하는 경로가 아예 없었다** — 9초 뒤 결과를 안 보고 CIPMUX→CIPSTART 로
전진해 버렸고, 그 뒤로는 `no ip` 를 받아도 CIPSTART 만 5초마다 영원히 재시도했다.
**CWJAP 가 왜 실패했든(전원이든 펌웨어든), 한 번 실패하면 영구히 못 붙는 구조였다.**
step=4 정체가 정확히 그것이다. 따라서 "응답을 기다리고 실패하면 CWJAP 로 되돌아간다" 는
수정은 **원인이 무엇이든 필요했다.** 이 부분은 유효하다.

### 🔬 전원 가설 검증 — 기존 로그로 할 수 있는 시험을 했다

전원 부족 가설은 **반증 가능한 예측**을 하나 만든다: 공급이 무너지면 ESP 가 **우리가 시키지 않은
순간에 재부팅**해야 하고, 그러면 `[System Ready, Vendor:...]` 배너가 불쑥 찍힌다.

두 실행 로그 전체를 세어 봤다:

| 로그 | `System Ready` | `AT+RST` | 판정 |
|---|---|---|---|
| serial2.log | 1회 | 9회 | 배너는 **부팅 시 1회뿐**, 전부 우리 RST 뒤 |
| serial3.log | 1회 | 8회 | 동일 |

**약 10분의 운용(1Hz TCP 송신 구간 포함) 동안 자발적 재부팅은 0회였다.**

→ 이것이 가르는 것:
- **하드 브라운아웃(전압 붕괴 → ESP 리셋)은 관측되지 않았다.** 그 형태는 배제된다.
- **한계 전원에 의한 RF 열화는 배제되지 않는다.** ESP 는 MCU 를 리셋하지 않고도 결합에 실패할 수
  있다. 전류 요구가 가장 큰 구간이 정확히 **결합·송신**이므로, 50 mA 공급이면 CWJAP 만 골라
  실패시키는 그림이 자연스럽다. **16초를 다 태우고 FAIL** 하는 것도 즉시 거절보다 이쪽에 가깝다.
- `[TX-DROP]`(프롬프트 300ms 타임아웃)이 **송신 직전에만** 났다는 점도 이 가설과 어울린다 —
  CIPSEND 는 전류 피크를 부르는 동작이다.

즉 루트의 전원 지적은 **형태를 좁혀서** 살아남는다: "리셋될 만큼은 아니지만 RF 가 흔들릴 만큼 부족".

### 전원이 정상화되면 측정할 것 (진짜 지표)

**CWJAP 가 몇 번 만에 붙는가.** 지금까지의 기록은 1차 4회째, 2차 4회째였다.
정상 전원에서 **1~2회 만에** 붙으면 → 전원이 원인이었다(펌웨어 특성 아님).
여전히 4회쯤 걸리면 → 그때 비로소 "이 펌웨어는 원래 그렇다"고 말할 수 있다.
**이 숫자 하나가 위 보류를 해제하거나 확정한다.**

### 가설 판정 — ⚠ 아래 표는 **한 번 더 정정됐다.** 「채널 판정 재검토」절이 최종이다

| 가설 | 주장자 | 판정 |
|---|---|---|
| 비밀번호 오타 | 나 (1차) | **틀렸다.** 같은 비번으로 붙었다(사용자가 복붙으로 확인까지 했다) |
| 채널 12 규제도메인 | 루트 (정정) → 내가 수용 | ~~틀렸다~~ → **[확인불가]** (아래 재검토) |
| CWJAP 가 불안정해 재시도가 필요하다 | 나 (2차) | **[확인불가]** — 배제되지 않았을 뿐 확정도 아니다 |

### 🔬 채널 판정 재검토 — **내 단정을 철회한다. 정답은 [확인불가] 다.**

사용자가 반론했다: *"채널을 수정하면 라우터가 리셋된다. 그래서 붙은 것이다."* **이 반론이 타당하다.**

내 근거의 구멍은 이것이다. 나는 "접속이 사용자 조치보다 앞섰다"고 썼는데, 내가 아는 것은
**루트가 나에게 알린 시각**이지 **사용자가 실제로 라우터를 만진 시각**이 아니다.
설정을 바꾸고 나서 알렸다면 순서는 뒤집힌다.

**로그로 확정할 수 있는 것은 여기까지다:**

| 시점(같은 보드 실행) | 사건 | 근거 |
|---|---|---|
| up≈51s | AP 가 **채널 12** 에 있었다 | `+CWLAP:(3,"unknowns_network2.4",-69,...,12)` (serial3.log:81) |
| up≈87s | **접속 성공** | `[AT] "Linked"` (serial3.log:129) |

**즉 채널 관측과 접속 사이에 36초의 공백이 있다.** 라우터 채널 변경+재기동이 그 36초 안에
끝났다면 사용자 가설이 맞고, 안 끝났다면 내 가설이 맞다. **내 로그로는 가를 수 없다.**

루트가 요구한 세 항목에 대한 정직한 답:

1. **접속 시점의 실제 채널 → [확인불가].** 접속 순간에 재스캔하지 않았다.
   내가 인용한 "채널 12" 는 **36초 전 스캔값**이다 — 접속 시점의 증거가 아니다. 이 점이 내 오류다.
2. **라우터 재부팅 흔적 → [확인불가].** 이 펌웨어는 `+CWJAP:n` 을 **아예 내지 않으므로**
   (전수 대조 11번 항목) "AP 못 찾음(:3)" 같은 흔적이 원리적으로 남지 않는다.
   AP 소실을 알 수 있는 다른 줄도 없다.
3. **"채널 12" 의 출처 → 재스캔이 아니라 36초 전 스캔의 인용이다.** 위에 명시했다.

**결론: 같은 창에서 두 변경(라우터 채널+재기동 / 펌웨어 재시도 경로 신설)이 겹쳤고, 로그로 분리할 수 없다.**

> ### ✅ 후속 실측으로 **채널 갈래는 결론이 났다 — 채널은 원인이 아니었다**
>
> 사용자가 채널을 11 로 바꾼 뒤 재스캔한 결과:
> ```
> +CWLAP:(3,"unknowns_network2.4",-67,"fc:34:97:4e:6c:10",11)
> ```
> **채널 11 로 실제로 바뀌었고**(BSSID·암호화 동일, 신호 -67 로 종전과 같은 수준),
> 그럼에도 **CWJAP 는 계속 실패한다.** 직전 빌드는 4시간(`up=14741s`) 동안
> `CWJAP 실패 250회`(카운터 상한)를 찍으며 **단 한 번도 못 붙었다.**
>
> 두 방향에서 동시에 배제된다:
> - **채널 12 에서는 붙었다**(02:15·02:16 두 번). 규제도메인 차단이라면 불가능한 일이다
> - **채널 11 에서는 4시간 전패**. 채널이 원인이었다면 11 로 바꾼 뒤 붙었어야 한다
>
> → **채널 가설은 양방향으로 반증됐다.** 위 `[확인불가]` 는 이것으로 닫힌다.
>   (사용자에게 채널 변경을 시킨 것은 결과적으로 불필요한 조치였다. 되돌릴 필요도 없다.)
>
> ### 🔥 "침묵 → 자력 회복" 의 기전이 밝혀졌다 — **레귤레이터 열보호다. 전원 가설이 오히려 강해진다**
>
> 사용자 답: **"아무것도 안 했다. 리셋만 눌렀다."** 배선·부품 무변경.
> 루트의 반론: *Uno 리셋 버튼은 ESP 전원을 안 끊는데, 전원 고갈로 죽었다면 어떻게 살아났나?*
>
> **그 반론에는 숨은 전제가 있다 — "회복하려면 전원 사이클이 필요하다".** 그게 틀렸다.
>
> [확정: TI LP2985 데이터시트] Uno 의 3.3V 레귤레이터(LP2985)는
> **과전류 제한 → 발열 → 열차단(thermal shutdown) → 냉각 후 자동 재기동** 회로를 갖고 있다.
> 원문: *"If thermal shutdown is triggered, the device turns off. **After the device cools down,
> the internal thermal shutdown circuit turns the device back on.**"*
>
> 이 하나로 관측 전부가 설명된다:
>
> | 관측 | 열차단 가설의 설명 |
> |---|---|
> | ESP 가 **한 바이트도** 안 보냈다 | 레귤레이터가 꺼져 **ESP 에 전원이 없었다** |
> | 내가 **여러 번 재플래시(=Uno 리셋)했는데 소용없었다** | 레귤레이터는 **MCU RESET 과 무관**하다. 리셋으로 안 풀린다 |
> | 사용자 리셋도 소용없었다 | 위와 같다 |
> | **한참 뒤 아무도 안 만졌는데 살아났다** | **냉각 후 자동 재기동** |
> | 원인 | ESP-01 송신 170~430mA ≫ 3.3V 핀 정격 50mA(부품 자체도 150mA) → 과전류 → 발열 |
>
> **즉 루트가 약해졌다고 본 고리가 실은 전원 가설의 가장 강한 증거다.**
> 열차단은 *과전류의 결과*이므로, 침묵→회복 사이클 자체가 과전류를 직접 증언한다.
>
> ### 루트의 두 갈래는 내 로그로 둘 다 반증된다
>
> **(A) Uno/SoftwareSerial 쪽 나쁜 상태였다 → 반증.**
> 침묵 구간에 나는 **`baudscan` 이라는 완전히 다른 스케치**를 올렸다. 업로드는 Uno 를 리셋하고,
> 그 스케치는 **동일한 핀(RX=8/TX=7)** 에 `SoftwareSerial` 을 **새로 초기화**하며 보율마다 `begin()` 을
> 다시 부른다. **그래도 ESP 에서는 한 바이트도 오지 않았다**(우리 송신만 결합으로 되돌아왔다).
> 새 Uno + 새 코드 + 새 시리얼 초기화로도 안 되는 것은 Uno 쪽 상태 문제가 아니다.
>
> **(B) ESP 의 AT wedge 를 깨끗한 AT 시퀀스가 풀었다 → 반증.**
> `baudscan` 은 6개 보율로 **`AT\r\n` 을 3바퀴 이상 반복 송신**했다. wedge 였다면 그중 한 번은
> 반응했어야 한다. 전혀 없었다. **전원이 없는 장치는 어떤 AT 도 받지 못한다.**
>
> → **(A)도 (B)도 아니고, 세 번째 답이 맞다: 그 구간 동안 ESP 는 전원이 없었다.**
>
> ### 🧪 그리고 진단 도구 자신을 검증했다 — **"죽은 탐지기" 규칙을 도구에 적용**
>
> 루트가 정확한 의심을 했다: *"`baudscan` 결과 자체가 틀렸을 수 있다. 그 스케치가 **정상 ESP 를
> 상대로 무엇을 찍는지** 확인한 적이 없지 않은가."* 맞는 지적이다. 검증 안 된 계측기의 침묵은
> 증거가 아니다 — 오늘 밤 네 번 나온 그 유형이다.
>
> **지금 ESP 가 살아 있으므로 그 검증이 가능해졌고, 실제로 했다. 같은 스케치, 같은 핀:**
>
> | | 바이트 | 인쇄가능 | 개행 | OK | raw |
> |---|---|---|---|---|---|
> | **침묵 시점** | 3 | 3 | **0** | ✗ | `AT\x0D` |
> | **지금(정상 ESP)** | **11** | 11 | **3** | **★ 발견** | `AT\x0D\x0D\x0A\x0D\x0AOK\x0D\x0A` |
>
> **도구는 정상이다.** 살아 있는 ESP 를 상대로는 진짜 응답(`OK`)을 정확히 잡아낸다.
> 핀 뒤바뀜 의혹도 해소된다 — 뒤바뀌었다면 지금도 `OK` 가 안 나와야 한다.
> (`SoftwareSerial wifi(8, 7)` = RX 8 / TX 7 로 `client.ino` 와 동일함도 소스로 확인했다.)
>
> **따라서 침묵 시점의 관측은 참이었다: ESP 는 정말로 한 바이트도 보내지 않았다.**
> 그때 읽힌 3바이트 `AT\x0D` 는 ESP 의 에코가 아니라 **우리 송신이 D7→D8 로 결합된 것**이다
> (전원 없는 장치는 에코도 못 한다). 지금 응답이 11바이트인 것이 그 대조군이다.
>
> → 루트가 제기한 "하드웨어 사망 갈래가 잘못된 계측 위에 서 있었을 가능성" 은 **검증으로 닫혔다.**
>   다만 결론은 "사망" 이 아니라 **"열차단으로 전원이 끊겼다 복구됐다"** 로 바뀐다. 모듈 교체는 불필요하다.
>
> **그러면 남는 것은 전원이다.** 결합(association)은 이 모듈에서 **전류를 가장 많이 쓰는 동작**이고,
> ESP 가 한동안 **완전히 침묵했다가 스스로 되살아난** 경과 자체가 한계 전원의 전형적 거동이다.
> 비밀번호는 사용자가 복붙으로 확인했고, AP 는 -67dBm 으로 잘 보이며, 채널도 정상이다.
> **전원을 정상화하기 전에는 다른 갈래를 더 파도 소득이 없다.**

다만 기록해 둘 비대칭이 하나 있다 — 어느 쪽 편도 아니고 사실만이다:
**옛 코드는 CWJAP 실패 후 재시도 경로가 없어 영구 정체였다.** 라우터가 재부팅돼 AP 가 완벽해져도
옛 코드는 `step=4` 에서 `no ip` 만 반복했을 것이다(CWJAP 를 다시 쏘지 않으므로).
즉 **(B) 는 붙기 위한 필요조건이었다.** 충분조건이었는지는 위 36초 때문에 알 수 없다.
(A)가 실제 방아쇠였을 가능성은 열려 있다.

**나도 루트와 같은 성급함을 반복했다.** 루트가 채널을 확신했다가 틀렸고, 나는 재시도를 확신했다.
둘 다 하나의 관측에서 원인을 읽으려 했다. 이번 건의 진짜 교훈은 그것 같다.

교훈이 하나 분명하다. **"16초를 태우고 FAIL" 을 양쪽 다 원인 추정의 근거로 썼는데, 실제로는
그냥 이 펌웨어의 결합 시도가 원래 그렇게 오래 걸리고 자주 실패한다는 뜻이었다.**

## 🐞 소크 6분 만에 잡은 결함 2건 — **펌웨어 어휘가 문서와 다르다**

관측을 시작하자마자 3회 연속 전송 실패 → 복구 사다리가 돌았고, 그 로그가 **죽어 있던 분기 둘**을
드러냈다. 서버 로그와 대조해서 확정했다.

```

       [AT] "ALREAY CONNECT" (14)     ← ★ D 가 빠져 있다
       [AT] "Unlink" (6)              ← ★ CLOSED 가 아니다
       [AT] "Linked" (6) → [NET] online (CONNECT) + 캐시 비움

|---|---|---|

| `CLOSED` | **`Unlink`** | REQ-0036 캐시 비우기 주 방어선이 **죽어 있었다** |

즉 의도한 즉시 분기가 아니라 **타임아웃으로 우회**해서 살아난 것이고, 매 복구마다 불필요한
5초를 태우고 있었다. 되니까 안 보였을 뿐 설계는 죽어 있었다.

→ `isAlreadyConnectLine()` / `isClosedLine()` 두 헬퍼로 **두 세대의 어휘를 함께 받도록** 고쳤다.
  (`ALREADY`·`ALREAY` 동시 수용 / `CLOSED`·`Unlink`·`UNLINK` 동시 수용.
   `CONNECT` 단독은 접두 요구 때문에 여기 안 걸린다 — 옛 오인 버그를 되살리지 않는다.)

→ 열로 설명한다면 **매끄러운 폭주가 아니라 싸이클**에 가깝다:
  가열 → 불안정 → **오프라인 구간이 송신을 멈춰 냉각** → 회복 → 정상 → 반복. **자기제한 되먹임**이다.
→ 열이 아닌 간헐적 사건일 가능성도 **n=6 · 28분 관측으로는 배제 못 한다.**

**살아남는 사실만 적는다: 28분에 6회 끊김, ESP 단독 재부팅 동반, 전부 자동 복구.**
"악화 일로", "곧 실용 불가" 같은 수식은 **근거가 없으므로 쓰지 않는다.**

### 🐞 유실 1건이 드러낸 진짜 결함 — **`sendLine()` 의 성공 판정이 틀렸다**

루트가 서버측 seq 연속성으로 **seq 1240 유실**을 찾았다(내 "누락 0" 은 틀렸다 — **송신측 자기보고**에
기댄 결과다). 장치 로그에서 그 프레임을 찾아보니 결함이 그대로 드러났다:

```
[AT] "\xA6,1239,...,1498,P1,3F" (39)
[AT] "SEND OK" (7)                    ← 1239 는 SEND OK 를 받았다
[TX] S,1240,0110000010,0000000100,1499,P1,30    ← ★ 성공(TX)으로 기록됐다
[AT] "AT+CIPSEND=40" (13)
[TX-RESYNC] 프롬프트 놓침 …                      ← ★ 그런데 1240 의 SEND OK 가 **없다**
```

**`sendLine()` 은 `waitForPrompt()` 성공만으로 `true` 를 돌려준다.** 즉 판정 기준이
**"ESP 가 페이로드를 받아 갔다"** 이지 **"ESP 가 실제로 전송했다"** 가 아니다.
그래서 `>` 프롬프트만 받으면 성공으로 세고 **`seqNo` 를 올린다.** 실제 전송 확인 신호인
**`SEND OK` 를 코드가 한 번도 검사하지 않는다.**

→ 결과: 링크가 그 사이 죽으면 프레임은 사라지는데 **장치는 보냈다고 믿고 다음 seq 로 넘어간다.**
  seq 가 건너뛰므로 **서버만 그것을 알 수 있다.** 이번 유실이 정확히 그 경로다.

⚠ **이것이 "단일 지표는 자기 고장을 증언하지 못한다" 의 교과서적 사례다.**
내 `SEND OK` 카운트와 `[TX]` 로그는 **둘 다 송신측 자기보고**라 이 유실을 원리적으로 못 잡는다.
잡은 것은 **수신측의 독립 계측(seq 연속성)** 이다.

**수정 방향(소크 뒤)**: 성공 판정을 **`SEND OK` 수신**으로 옮긴다. 다만 `sendLine` 이 현재
비동기적으로 즉시 반환하는 구조라 **단순 교체가 아니다** — `SEND OK` 를 기다리면 지연이 늘고,
안 기다리면 seq 증가 시점을 미뤄야 한다. **설계 변경급이므로 별도 판단이 필요하다.**
지금 당장의 영향은 **끊김 구간에서 프레임 1건 유실** 수준이고, §7.3/§7.4 가 명령 계열은 보호한다
(S 프레임은 1Hz 로 재발행되므로 하나 잃어도 다음 프레임이 상태를 덮는다).

### 🐞🐞 소크 종료 시 발견 — **ESP 완전 침묵에서 빠져나올 길이 없다**

사용자가 커패시터 작업을 위해 모듈을 분리한 것으로 보이는 상태에서 드러났다:
```
[DIAG] offline step=2 rx=259286 lines=9220 up=3696s
                                ^^^^^^^^^^ 정지 — ESP 로부터 한 줄도 안 온다
                                           up 은 증가 = AVR 은 정상
grep -c "0 RST" = 1     ← 부팅 때 1회뿐. 3696초 동안 에스컬레이션 0회
```

**코드로 확정된 원인**(`client.ino` netTick 타임아웃 분기):
```c
case NET_CWJAP:
  netStep = NET_CWJAP;   // 답이 없으면 그냥 다시 묻는다. 전진하지 않는다
  break;
```
**30초 대기 상한이 만료돼도 CWJAP 를 다시 쏠 뿐, `AT+RST` 로 올라가는 임계가 아예 없다.**

#### ⚠ 정직하게 — **내 수정이 이 구멍을 만들지 않았다. 그러나 고치지도 않았고, 위치만 옮겼다**

| | 완전 침묵일 때 |
|---|---|
| **옛 코드** | 타이머로 **전진** → CIPMUX → CIPSTART → **step=4 에서 영원히 재시도** ← REQ-0064 의 원래 증상 |
| **내 코드** | **제자리** → **step=2 에서 영원히 재시도** |

**둘 다 RST 로 올라가는 길이 없다.** 내가 없앤 것은 **`busy` 응답에 대한 RST 난사**이고
그건 **응답이 있을 때만** 발동하던 경로다 — **완전 침묵에는 원래도 에스컬레이션이 없었다.**
→ 정체 지점이 **4에서 2로 옮겨졌을 뿐**이다. **"고쳤다" 고 말하면 안 되는 자리다.**

#### 🔧 수정 설계 — 무응답 에스컬레이션 (소크 뒤 적용 목록)
```c
static unsigned long lastRxLineAt;   // handleLine() 진입 시 갱신 (dbgLineCnt 옆에 시각만 추가)
  · 무응답 60초       → AT+RST (netStep = NET_RST)
  · RST 후 또 60초    → **하드웨어 리셋선** (REQ-0063 ②)
  · 그마저 실패       → 로그로 남기고 계속 시도 (사람이 볼 수 있게)
```
비용 4바이트. `dbgLineCnt`(324행)가 이미 줄 수를 세지만 **시각은 안 찍는다**(1151행 `dbgLineCnt++` 뿐).
**시각만 같이 찍으면 된다.**

**⭐ 새 관용구를 만들지 마라 — 이 파일에 이미 같은 패턴이 있다:**
```c
case NET_CIFSR:
  if (++cifsrTries >= 3) { cifsrTries = 0; netStep = NET_CWJAP; }   // 3회 실패 → 상위 단계로
  else                   { netStep = NET_CIFSR; }
```
**`cifsrTries` 가 정확히 이 에스컬레이션 패턴이다.** 같은 모양으로 확장하면 리뷰가 짧아지고
파일의 기존 스타일과 붙는다.
⚠ **단 하나 다르다: `cifsrTries` 는 *횟수*, 이건 *시간* 기준이어야 한다.**
CWJAP 는 대기 상한이 30초라 **횟수로 세면 임계가 대기값에 묶여 버린다.**
→ 코드 주석에 **"cifsrTries 와 같은 취지, 다만 횟수가 아니라 시간 기준"** 이라고 적을 것.

#### 📌 REQ-0063 에 주는 근거 — **가상의 위험이 아니라 실제로 본 상태다**
그동안 "워치독·하드웨어 리셋선" 은 *"있으면 좋다"* 수준의 요구였다.
지금 **소프트웨어만으로는 빠져나올 수 없는 상태**를 눈으로 봤다. 이 로그를 근거로 첨부한다.

**근거를 두 단계로 갈라 적는다 — 그래야 "가정" 이 아니라 "부분 관측" 이 된다:**

| 단계 | 상태 | 근거 |
|---|---|---|
| ① **ESP 가 비정상 상태에 빠진다** | ✅ **관측됨** | **ESP 단독 재부팅** — `AT+RST` 미발신 상태에서 부팅 배너 출현. AVR 은 uptime 연속 |
| ② 그 비정상이 **행(hang)의 형태**를 띤다 | ⚠ **미관측** | 실기에서 직접 본 적 없다 |
| ③ 행이면 장치는 **지금과 똑같이** `step=2` 에 앉는다 | **[추정]** | *"장치 관점에서 모듈 없음과 모듈 무응답이 구분 불가"* — 오늘 3696초가 그 모양이었다 |

**①은 사실이고 ②만 미관측이다.** 즉 REQ-0063 의 근거는 *"일어날 수도 있는 일"* 이 아니라
**"ESP 가 비정상에 빠지는 것은 이미 봤고, 그중 한 형태에 대해 소프트웨어 탈출구가 없음을 확인한 것"** 이다.

### 🔑 가장 강한 발견 — 단일 레일 판별

밤새 갈리지 않던 **"코드냐 하드웨어냐"** 가 여기서 갈렸다.

| 관측 | 함의 |
|---|---|
| **AVR `uptime` 연속**(971→972→1006), 리셋 0회 | **5V 레일은 버텼다** |
| **`AT+RST` 미발신 상태에서 ESP 부팅 배너 출현** | **ESP 3.3V 레일만 무너졌다** |
| 동반 바이트 손상(`AT+CVA\x11\xB1\xA2...`) | 전압 붕괴 시의 UART 손상과 일치 |
| 우리가 보낸 것은 `CIPCLOSE` 뿐 | **코드는 ESP 만 골라 재부팅시킬 수 없다** |

⚠ 근거 표기 주의: **"배너 2 − RST 1 = 자발 1" 같은 뺄셈으로 적지 마라.** 부팅 RST 는 이 로그에
배너를 남기지 않아 뺄 항이 없다. **"RST 미발신 상태에서 배너 출현"** 이 재현 가능한 서술이다.

수치 배경: Uno 3.3V 핀 **50mA**(부품 LP2985 자체는 150mA) vs ESP8266 송신 **170mA**, ESP-01 피크 **300~430mA**.

### 소크가 만들어 준 것 — 계획으로는 못 만들던 표본

§4.2 멱등은 **설계상 인위적으로 만들 수 없었다**(rid 는 서버가 단조증가로 부여하므로).
그런데 **끊김 사고가 §7.3 재전송을 유발해 표본을 만들어 줬다.** `[DUP rid] 6` ×2 가 그것이다.
→ 원장의 `[미검증 — 발동 조건 미도래]` 는 **해제**한다.

### 소크 뒤로 미룬 것 (재플래시가 관측을 무효화하므로 손대지 않았다)

1. **`[RAM]` 로그의 괄호 문구가 틀렸다.** `(서버의 '버린줄' 과 맞아야 한다)` → 실측은 `재동기 : 버린줄 = 다수 : 0`.
   더미는 대개 **ESP 가 명령 모드에서 로컬 소비**해 서버에 도달하지 않는다.
   → 고칠 문구: `(더미는 ESP 가 로컬에서 삼키는 경우가 많아 서버 '버린줄' 과 반드시 맞지는 않는다)`
   ⚠ 이건 "죽은 탐지기" 의 거울상이다 — 안 울리는 게 아니라 **틀린 기대를 운영자에게 주입**한다.
2. **`Error`(대문자 E + 소문자) 어휘 불일치.** 코드는 `ERROR` 만 찾는다. 해당 분기가 로그 전용이라 무해.
3. **`PROMPT_TIMEOUT_MS=300` 은 손대지 않는다.**
   ⚠ **왜 뺐는지 반드시 남긴다** — 안 적으면 다음 사람이 "54초당 1회" 라는 숫자만 보고 값을 올리려 든다.
   재동기는 **끊김의 증상**이라 끊김 창 안에서 폭증한다. 끊김 ±30초를 제외하면 전반 14 : 후반 20 으로
   [추정: 이항 단측 p ≈ 0.15] **잡음과 구분되지 않는다.** **값을 올려도 낫지 않는다.**

### 다음 단계 — 전원 조치와 그 반증 조건

### 🔧 조치 — **순서가 있다. 커패시터가 주(主) 처방이다**

| 순위 | 조치 | 근거 |
|---|---|---|
| **1** | **여분 ESP-01 로 교체해 본다** | 공짜·5분. **개체 불량이면 부품 구매가 통째로 불필요** |
| **2** | **100µF ×3~5 병렬(300~500µF) + 세라믹 0.1µF, ESP 전원핀 *직근*** | ★ **주 처방.** 모자란 건 순간 피크뿐이다 |
| 3 | 그래도 안 되면 별도 3.3V 레귤레이터 500mA↑ | 2가 부족할 때만 |
| — | **RX 분압 1kΩ+2kΩ** | 위와 별개로 **항상 필요**(5V 직결은 정격 초과) |

**왜 커패시터가 주가 되는가**: 평균이 75~80mA 로 정격 150mA 의 절반이라
**피크 사이에 커패시터를 충전할 힘이 충분하다.** 공급원을 바꿀 이유가 약하다.

**용량 근거 — 계산이 아니라 출처다:**
ESP-01 브라운아웃 대책의 관행값은 **470µF, 모듈 최대한 가까이** 로 여러 출처가 일치한다.
[확정: internetofhomethings.com/homethings/?p=396 · letscontrolit.com/wiki/index.php/Power ·
 esp32.co.uk — ESP-01 survival guide]
사용자 보유 부품(100µF/50V ×20, 세라믹 0.1µF ×200)으로 **100µF 를 3~5개 병렬**하면
300~500µF 가 되어 관행값에 든다. **추가 구매가 필요 없다.** 적게 시작해 효과를 보고 늘린다.

> ### ⚠ 앞서 적었던 `ΔV = I·Δt/C` 계산을 **철회한다 — 입력값이 검증되지 않은 것이었다**
> 그 식의 `Δt = 1ms` 는 **출처 없이 넣은 값**이었고, 그 하나가 "1000µF 필요" 라는 결론을 만들었다.
> 실제 송신 구간은 **약 40ms** 로 보고되는데, 같은 식에 넣으면 **C ≈ 37,000µF** 라는 헛값이 나온다.
> → **전류가 40ms 동안 일정하게 흐른다는 전제 자체가 틀렸다. 그 모델은 이 문제에 맞는 도구가 아니다.**
> **근거로 쓰지 마라.** 용량은 위의 관행값(출처 있음)에서 가져온다.

> ### 🔴 대용량 커패시터의 진짜 위험 — 대상이 ESP 가 아니라 **우노 레귤레이터**다
> "인러시 전류로 ESP 가 죽는다" 는 기전은 **성립하지 않는다** — LP2985 는 출력을 약 350mA 로
> 자체 제한하고, ESP 는 커패시터와 **병렬**이라 충전 전류 경로에 있지도 않다.
> [확정: TI E2E 포럼 946105]
>
> **데이터시트가 경고하는 것은 따로 있다:**
> > *Excessive reverse current can damage the LP2985.* PNP 패스 소자의 기생 다이오드가
> > **출력 > 입력** 이 되면 순바이어스되어 **기생 SCR 래치** → 출력→입력 대전류.
> > 큰 출력 커패시터의 역방전을 막으려면 **외부 쇼트키 다이오드**를 쓰라.
> [확정: https://www.ti.com/lit/ds/symlink/lp2985.pdf]
>
> **전원을 끄는 순간이 정확히 그 상황이다** — 5V 는 즉시 떨어지는데 3.3V 쪽 대용량 캡은 전하를 갖고 있다.
> → **죽는 것은 ESP 가 아니라 우노 보드의 3.3V 레귤레이터다.** 저장 에너지가 클수록 나쁘다.
> **이것이 2200µF·1000µF 를 권하지 않고 300~500µF 에서 시작하는 이유다.**

⚠ **반드시 ESP 전원핀 바로 옆에 붙여야 한다.** 배선이 길면 그 구간 저항에 피크 전류가 흘러
**거기서 또 떨어진다** — 커패시터를 멀리 두면 있으나 마나가 된다.

> ### 📖 용어 주의 — **"우노의 3.3V 핀" 이 곧 온보드 LP2985 의 출력이다**
> 사용자가 *"레귤레이터는 없다. 우노 출력을 쓴다"* 고 했는데, **그 우노 출력 자체가 레귤레이터 출력**이다.
> 문서에서 "레귤레이터" 라고만 쓰면 **사야 할 부품**으로 읽힌다.
> → **"우노 온보드 3.3V 레귤레이터(LP2985)"** 로 매번 풀어 쓴다.
>   3순위의 **"별도(외장) 3.3V 레귤레이터"** 와 반드시 구분한다.
> (보드 확인: 포트가 `/dev/cu.usbmodem1101` = 16U2 기반 열거 → **정품 R3 계열**.
>  CH340 클론이면 `usbserial` 로 잡힌다.)

> ### ⚠ 내가 앞서 "레귤레이터가 주(主)" 라고 한 것은 틀렸다
> 근거였던 *"평균 전류가 이미 정격 초과"* 가 **`170mA` 를 평균으로 오인한 결과**였다.
> 실제 평균은 정격의 절반이다. **평균이 모자란 게 아니라 피크가 모자라다** —
> 그건 공급원 교체가 아니라 **전하 저장으로 푸는 문제**다.
> (레귤레이터와 커패시터가 **다른 문제를 푸는 부품**이라는 아래 표는 그대로 유효하다.
>  달라진 것은 **우리 문제가 둘 중 어느 쪽이냐**이고, 답은 피크 쪽이다.)
>
> | 항목 | 값 |
> |---|---|
> | Uno 3.3V 핀 — **공식 문서 표기** | 50mA ⚠ **이 값을 쓰지 마라. 아래 참조** |
> | Uno 3.3V 핀 — **실제 부품(LP2985-33DBVR) 정격** | **150mA** |
> | ESP8266 **정상 동작** | **170mA** [확정: ESP8266EX 데이터시트] |
> | ESP8266 피크 | 300~430mA [확정: 동] |
>
> ### ⚠⚠ `50mA` 는 틀린 숫자다 — 우리가 밤새 이 값으로 계산했다
> `50mA` 는 Arduino 공식 문서 수치이지만 **구형 보드 호환을 위해 보수적으로 못박은 값**이다
> (구형은 3.3V 를 FTDI 칩에서 뽑았고 그게 진짜 50mA 였다).
> [확정: https://forum.arduino.cc/t/q-about-the-new-uno-r3-and-its-lp2985/80272 —
> *"to maintain compatibility with older boards the current was spec'd at 50mA"*]
> **Uno R3 에 실제로 올라간 것은 LP2985-33DBVR 이고 데이터시트 정격은 150mA 다.**
> [확정: https://forum.arduino.cc/t/uno-r3-and-the-lp2985/122756 · TI LP2985 데이터시트]
>
> **산술 정정 — 이 숫자를 세 번 고쳤다. 구매 근거라 경로를 전부 남긴다:**
> ```
> ❌ 1차: 170mA / 50mA  = 3.4배 초과    ← 50mA 가 구형 호환 표기였다
> ❌ 2차: 170mA / 150mA = 1.13배 초과   ← 170mA 를 "평균" 으로 오인했다
> ✅ 3차: 평균 75~80mA / 150mA = 0.5배  ← **초과가 아니라 여유.** 피크만 2~2.9배 초과
> ```
> **`170mA` 는 "정상 동작" 이 아니라 송신 모드 값이다**(90% duty 연속송신 조건 측정).
> ```
> 연결 유지 유휴(associated idle) : 약 75mA   [확정: esp8266.com/wiki — esp8266_power_usage]
> 송신 중                          : 170~200mA
> 피크                             : 300~430mA
> 공급(LP2985 정격)                : 150mA
> ```
> **우리 응용은 38바이트를 1Hz 로 보낸다 — 거의 전 시간이 유휴다.**
> 평균 ≈ 75~80mA 로 **정격의 절반.** 모자란 것은 **순간 피크뿐**이다.
>
> ### 🔑 그리고 이 정정이 **예측 실패를 설명한다 — 예측이 틀린 게 아니라 전제가 틀렸다**
>
> | 기전 | 예측 | 관측 |
> |---|---|---|
> | **열 축적**(평균 초과 전제) | 단조 열화 → 톱니 2주기 | ❌ **반증.** 455·578 로 계속 회복 |
> | **피크 브라운아웃**(평균은 여유) | **간헐 발생. 추세 없음** | ✅ **관측 그대로** |
>
> **평균이 정격의 절반이면 애초에 축적될 열이 없다.** 그래서 톱니가 안 나온 것이고,
> **"단발·간헐" 은 이상 현상이 아니라 이 기전의 정상 예측**이다.
> LP2985 는 전류제한을 내장해 430mA 요구에 **출력을 무너뜨린다** → ESP 브라운아웃 → 즉시 복구.
> [확정: TI LP2985 데이터시트 — 과전류 제한 내장]
>
> **데이터시트와 관측이 다시 서로를 예측한다. 이번엔 맞는 기전으로.**
>
> ### ⚠ 그러나 "전원이 원인" 이라는 판정은 **약해지지 않는다** — 구분이 필요하다
>
> 나는 한때 *"단발 교란이면 전원 근거가 약해진다"* 고 썼다. **틀렸다.**
> **약해지는 것은 「열 축적」이라는 특정 기전이지 「전원」이라는 원인이 아니다.**
> **단일 레일 판별**(AVR uptime 연속 + RST 미발신 배너)은 **기전과 무관한 증거**다 —
> 열이든 피크든 **ESP 쪽 레일만 무너졌다는 사실은 그대로 선다.**
> 오히려 **피크 기전이 단발·간헐을 더 잘 설명하므로 전원 근거는 지금 더 강해졌다.**
>
> **정확한 결론 문장:**
> > 전원이 원인이라는 판정은 유지된다. 바뀐 것은 **기전**이다 —
> > **평균 전류 부족(열)이 아니라 순간 피크 부족(브라운아웃)이다.**
>
> 그리고 둘은 **애초에 다른 문제를 푸는 부품**이다:
> | 부품 | 해결하는 것 | 못 하는 것 |
> |---|---|---|
> | 별도 레귤레이터 | **평균 전류 여유**(공급원 자체를 바꾼다) | μs~ms 순간 피크의 전압 딥 |
> | 벌크 커패시터 | **순간 피크 완충**(전하 저장) | 평균 전류 부족 — 충전할 여유가 없으면 무의미 |
>
> **커패시터는 레귤레이터 뒤에 붙어야 제 일을 한다.** 공급이 모자란 상태에서 커패시터만 달면
> 매 사이클 충전을 못 따라가 효과가 반감된다. **직렬 관계지 병렬 선택지가 아니다.**

**그러면 톱니 관측의 값어치는 무엇인가 — 부품 선택이 아니다. 용도가 다르다:**
- ❌ **부품 선택을 가르지 않는다** — 레귤레이터는 어느 가설이든 필요하다
- ✅ **조치의 효과를 재는 기준이 된다.** 지금 톱니 모양을 기록해 두면 조치 후 재소크에서
  **그 모양이 사라지는지**로 효과를 잰다. 안 재 두면 "좋아진 것 같다" 밖에 못 말한다
- ✅ **열 가설의 반증 조건이 된다.** 조치 후에도 톱니가 남으면 **전원이 원인이 아니다.**
  그때는 다른 곳을 봐야 하고, **그걸 아는 값이 커패시터 몇 개 값보다 크다**

### 📏 조치 효과 판정 기준 — **지금 못박는다. 사후에 정하면 싸운다**

"모양이 사라지는지" 는 기준이 아니라 느낌이다. **숫자 하나로 못박는다:**

```
기준선(조치 전, 지금):   첫 끊김까지 시간 = 972초 (장치측) / 981초 (서버측)
                         ↑ 두 독립 계측이 일치한다. 이것이 비교 대상이다
  ⚠ 측정 조건 — 이걸 안 적으면 조치 후 비교가 사과와 오렌지가 된다:
     · 브라우저 WS 미접속
     · 하행 표본 없음 (R/C/T/M 프레임 0건)
     · 상행 1Hz 단독
     · **전원을 완전히 내렸다 올린 냉각 상태에서 출발** (부팅 직후)
조치 후:                 위 네 조건을 동일하게 맞추고 같은 지표 하나만 비교한다
```

분포도 톱니 주기도 셀 필요 없다. **"첫 끊김까지 몇 초인가" 하나다.**
- **크게 늘거나 끊김이 사라지면** → 전원이 원인이었다. 상시가동 가능
- **972초 근처에 머무르면** → **전원이 원인이 아니다.** 다른 곳을 봐야 한다

### 🔒 사전 등록된 예측 — **관측 전에 적는다. 사후 수정 금지**

⚠ **왜 이걸 적는가:** 우리는 오늘 지표를 **네 번** 바꿨다.
`재동기 빈도 → 끊김 간격 → 세션 지속시간 → 버스트 간격`.
**매번 바꾼 이유는 정당했다**(순환논법 / 경계정의 민감 / 층위 오류). 그러나
**지표를 계속 갈아 끼우면 결국 어떤 지표에서든 원하는 그림이 나온다.** 알려진 자기기만 경로다.
그래서 **버스트 간격을 마지막 지표로 못박고, 결과를 보기 전에 판정선을 적어 둔다.**

**데이터의 실제 구조**(세션 지속시간은 버스트 *안에서만* 짧아진다 — 그래서 그 층위에서는
하강열이 안 보이는 것이 당연했다. 찾는 층위가 틀렸다):
```
[조용 972초] → [버스트: 끊김 6회 / 527초] → [조용 1033초+ (진행 중)]
 ^^^^^^^^^                                    ^^^^^^^^^^^
 첫 조용 구간                                 현재 조용 구간 — 규모가 비슷하다
```

**예측 (작성 시점 up ≈ 2530, 이미 예측 창 안이다):**
| 관측 | 판정 |
|---|---|
| **버스트 2 가 up 2400~2700 사이에 온다** | **열 싸이클 지지** (주기 ≈ 1000초) |
| **up 3000 을 넘도록 안 온다** | **싸이클 반증. 단발 교란(간헐 사건)** |

*"버스트" 의 정의도 지금 고정한다: **300초 이내에 끊김 2회 이상**.*
(버스트 1 은 972~1499 에 6회였다. 단발 끊김 1회는 버스트로 세지 않는다.)

**결과가 나온 뒤에 이 표를 고치지 않는다.**

#### ✅ 판정 결과 — **반증. 표를 고치지 않았다**

```
up 3456 도달 · 버스트 2 없음 · 마지막 끊김 up 1954 (단발, 정의상 버스트 아님)
1954 → 3456 = 1502초 무사고 — 초기 무사고 구간(972초)보다 길다
```
**등록한 반증선 `up 3000` 을 넘겼다. → 열 싸이클 가설 반증. 단발·간헐 사건 확정.**

**그리고 이 반증이 옳은 기전을 찾아 줬다** — 위 「전류 정정」 절 참조.
평균이 정격의 절반이므로 **축적될 열이 없고**, 따라서 톱니는 애초에 나올 수 없었다.
**간헐 발생은 피크 브라운아웃 기전의 정상 예측이다.**

> **사전 등록의 값어치가 여기서 나왔다: 예측이 맞았다면 우리는 틀린 기전(열 축적)을 확신했을 것이다.**
> 반증당했기 때문에 전제(평균 전류)를 다시 봤고, 거기서 `170mA` 오인을 찾았다.
> 경로를 그대로 남긴다: **예측 반증 → 전제 재검 → 기전 교체.**

### 🔍 그런데 부품을 사기 전에 5분이면 되는 판별이 있다 — **여분 ESP-01**

우리 분석은 **레일(전원) 설명으로 수렴하면서 개체 변수를 건너뛰었다.**
사용자에게 **여분 ESP-01 모듈이 있다면 그것부터 바꿔 보는 것이 맞다:**
- **바꿨더니 972초가 재현된다** → **레일 문제 확정.** 부품 구매로 간다
- **바꿨더니 안 끊긴다** → **이 모듈 개체 불량.** **구매가 아예 불필요하다**

공짜이고 5분이며, 맞으면 구매 자체가 없어진다. **부품 주문보다 먼저 물어야 할 것이었다.**

### 🔧 `sendLine()` 성공 판정 수정 — 설계(적용은 소크 뒤)

**문제**(위 결함 절 참조): `waitForPrompt()` 성공만으로 `true` 를 돌려주므로
**"ESP 가 페이로드를 받아 갔다"** 를 **"전송됐다"** 로 오인한다. `SEND OK` 를 검사하지 않는다.

**세 안을 비교했다:**

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 동기 대기 | `SEND OK` 를 그 자리에서 기다림 | 가장 단순. `ok` 가 진실이 됨 | **매 전송마다 블로킹**. 이 코드의 "delay 로 흐름을 막지 않는다" 원칙 위반 |
| B. 완전 비동기 | 확인 시 커밋. 전송/커밋 분리 | 블로킹 0 | 상태 증가, 스냅샷 보관 필요 |
| **C. 다음 전송 직전 확인** | 직전 전송의 `SEND OK` 도착 여부를 다음 사이클에 판정 | 블로킹 0, 상태 최소 | 감지가 **1초(하트비트 1주기) 지연** |

**채택: C.** 근거 — 이 노드의 하트비트가 1Hz 라 **1주기 지연은 실질 손해가 없고**(다음 S 프레임이
어차피 상태를 덮는다), 블로킹을 안 늘리는 것이 이 코드의 설계 원칙이다.
A 는 `PROMPT_TIMEOUT_MS` 위에 또 하나의 대기를 얹어 최악 지연을 키운다 — 이미 프롬프트 대기가
버스트로 몰리는 것을 봤으므로 그 위에 더 얹는 것은 나쁘다.

**설계 스케치:**
```c
static bool     sendAwaitingOk = false;   // 직전 프레임의 SEND OK 를 기다리는 중
static uint16_t pendingSeq;               // 확인되면 커밋할 seq
static uint16_t pendingOcc, pendingRes, pendingTmask;

// sendLine(): 페이로드를 쓴 뒤
sendAwaitingOk = true;                    // "보냈다" 가 아니라 "썼다"
// 반환값의 의미를 바꾼다: "썼다" (커밋 판단 근거가 아니다)

// handleLine(): SEND OK 를 **처음으로 검사한다**
if (sendAwaitingOk && strstr(s, "SEND OK")) { sendAwaitingOk = false; commitSend(); }
if (sendAwaitingOk && (strstr(s,"SEND FAIL") || isErrorLine(s))) { sendAwaitingOk = false; noteSendResult(false); }

// 다음 전송 직전: 아직 기다리는 중이면 직전 것은 실패로 확정한다
if (sendAwaitingOk) { sendAwaitingOk = false; noteSendResult(false); }   // seq 커밋 안 함 → 같은 seq 재전송
```
**핵심 불변식**: `seqNo` 는 **`SEND OK` 를 받은 뒤에만** 증가한다. 그러면 이번에 잃은 seq 1240 은
재전송되고, **서버의 seq 연속성이 곧 장치의 진실**이 된다.

⚠ 함께 고칠 것: `isErrorLine()` 을 만들어 **`ERROR`/`Error` 를 함께** 잡는다(어휘 불일치 일곱째).
지금은 `ERROR` 만 찾아 이 판정에서 `Error` 를 놓친다.

#### ⚠ 이 불변식이 만드는 엣지 케이스 — 설계에 반드시 포함한다

> `seqNo` 는 `SEND OK` 를 받은 뒤에만 증가한다

**장치는 "전송 실패" 와 "전송은 됐는데 `SEND OK` 를 놓쳤다" 를 구분할 수 없다.**
후자면 프레임은 서버에 도착했는데 장치는 실패로 믿고 **같은 seq 로 다시 보낸다.**
```
장치가 보는 것: S,1240 송신 → SEND OK 못 봄 → 실패 판정 → S,1240 재송신
서버가 보는 것: S,1240(uptime 1499) · S,1240(uptime 1500)   ← 중복. 구멍이 아니다
```
**프롬프트 놓침이 55회 난 링크다. `SEND OK` 놓침도 당연히 난다 — 드문 경우가 아니다.**

**즉 이 수정은 "조용한 유실" 을 "명시적 중복" 으로 바꾸는 것이다.** 그게 옳은 교환이다
(중복은 서버가 버리면 되지만 유실은 아무도 모른다). **다만 두 가지를 같이 해야 성립한다:**

**① 장치 — 재전송은 반드시 바이트 동일해야 한다. 지금 코드는 그렇지 않다.**
현재 `sendStatus()` 는 호출될 때마다 **프레임을 새로 만든다**(`millis()/1000` 이 들어가므로 uptime 이 바뀐다).
그대로 재전송하면 **"같은 seq 인데 내용이 다른 두 프레임"** 이 되어 서버가 뭘 믿을지 모른다.
→ **직전에 보낸 바이트를 그대로 보관했다가 재전송한다:**
```c
static char lastFrame[64];      // 마지막으로 전선에 쓴 줄 (바이트 그대로)
static bool lastFrameValid = false;
// sendLine(): 페이로드를 쓰기 직전에 lastFrame 에 복사
// 재전송 시: sendStatus() 를 다시 부르지 않고 sendLine(lastFrame) 을 부른다
```
RAM 비용 **+64B**. 현재 여유 1081B / 실측 최저 884B → 여전히 임계 400B 의 2배 이상. **감당된다.**

**② 서버 — 연속성 검사가 `b == a`(중복)를 `b != a+1`(구멍)과 갈라야 한다.**
지금 도구는 `b != a+1` 하나로 판정하므로 **중복을 유실로 오보한다.**
(루트가 socket-engineer 에게 전달하기로 했다.)

⚠ **이걸 안 하면 결과가 고약하다:** 유실을 없애려 넣은 수정이 **중복을 유실로 보고**하게 만들어
*"고쳤는데 더 나빠 보인다"* 가 되고, **다음 사람이 수정을 되돌린다.**

#### 📐 수정 검증 기준 — **유실↔중복 자리바꿈**

서버측 독립 계측이 이 결함의 **서명(signature)** 을 아주 깨끗하게 잡아냈다:
```
수신 1560프레임 · seq 677~2238 · 기대 1562 · 유실 2

09:01:22 seq1239 → 09:01:51 seq1241   유실 1   (uptime 1498→1527, 공백 29초)
09:08:58 seq1621 → 09:09:05 seq1623   유실 1   (uptime 1953→1959, 공백  6초)
```
**두 건 다 세션 경계. 매번 정확히 1개. 세션 내부 유실 0.**
그리고 **공백이 29초와 6초로 크게 다른데도 둘 다 1개**다
→ 끊긴 동안 프레임이 쌓여 유실되는 게 아니라 **끊기는 순간의 그 1개**다.
이 모양은 `SEND OK` 미검사 기전 말고는 잘 설명되지 않는다.

**따라서 수정이 먹혔는지는 이 자리바꿈 하나로 판정한다:**
| | 경계당 유실 | 경계당 중복 |
|---|---|---|
| **지금(수정 전)** | **1** | 0 |
| **수정 후 기대** | **0** | **1** |

**유실이 중복으로 바뀌면 성공이다.** 중복은 서버가 버리면 되지만 유실은 아무도 모른다.
⚠ 서버 도구가 **`b == a`(중복)과 `b != a+1`(구멍)을 갈라 찍어야** 이 판정이 성립한다
(안 그러면 중복을 유실로 오보해 *"고쳤는데 더 나빠 보인다"* 가 된다).

#### 적용 순서 — **전원 먼저, 그다음 코드. 동시에 하지 않는다**

두 변수를 같이 바꾸면 972초가 좋아져도 **어느 쪽 덕인지 못 가른다.**
전원이 지금 **지배적 원인**이고, 이 코드 결함은 **끊김 구간에서만 발현**하므로 순서가 분명하다.
1. 전원 조치 → 재소크 → **첫 끊김까지 시간**으로 판정
2. 그다음 `sendLine()` 수정 적용 → 재소크 → **중복/유실 계수**로 판정

**적용 시점**: 위 순서에 따라. **재플래시가 관측을 무효화하므로 지금은 적용하지 않는다.**

**이 시험은 전원을 고친 뒤에만 할 수 있다.** 그래서 소크를 13분 46초에 끝냈다 —
**위험해서가 아니라 더 얻을 정보가 없어서**다. (LP2985 의 열차단은 보호 회로이며 자동 복귀한다
[확정: TI 데이터시트]. 계속 돌려도 부품이 죽을 가능성은 낮다. 손상 위험을 종료 근거로 삼지 않는다.)

## ✅✅ 소크 개시 — `T0 = 08:49:20`. 막혀 있던 구멍이 전부 닫혔다

### 1) 링크를 끊던 범인을 잡았다 — 프롬프트 타임아웃 스트림 어긋남

**증상**: 약 4분마다 링크가 끊겼다(`up=132s` 접속 → `up=359s` 끊김, 189프레임).
**원인**: `AT+CIPSEND=<n>` 뒤 300ms 안에 `>` 를 못 받으면 페이로드를 안 쓰는데
**ESP 는 여전히 n바이트를 기다린다.** 그래서 다음 `AT+CIPSEND=` 가 **페이로드로 먹힌다.**
```
[AT] "\xA6,189,0110000010,0000000000,356,P1,33AT+CIPSEND=38" (50)   ← 두 줄이 붙은 증거
```
**수정**: 타임아웃 상향이 아니라 **약속한 길이만큼 `#` 을 채우고 `\n`** 으로 진행 중인 CIPSEND 를
종결시켜 명령 모드로 되돌린다. `#` 은 어떤 타입 문자(S·A·R·C·T·M)도 아니라 **서버가 반드시 버린다.**

**전후 대조 (실측):**
| | 지속 | SEND OK | 재동기 | 오프라인 |
|---|---|---|---|---|
| 수정 전 | **359초에 끊김** | 189 | — | **1회** |
| 수정 후 | **706초+ 무끊김** | 614 | **13회 전부 흡수** | **0회** |

발동 순간 원문 — **실패가 1회에서 멈춘다**(예전엔 3회로 번져 오프라인):
```
[TX-RESYNC] 프롬프트 놓침 → 더미 36바이트로 스트림 복구
[NET] 전송 실패 1/3        ← 여기서 멈췄다
[AT] "###################################" (35)
[AT] "Error" (5)            ← ESP 가 명령 모드였다 → 더미를 로컬에서 소비(무해)
[TX] S,20,...               ← 정상 복귀
```

### 2) `+IPD` 수신 경로 — 실기 첫 실행, 첫 시도에 전 구간 성공

```
[AT] "+IPD,14:R,1,B3,u17,61" (21)      ← 하행 수신
[TX] A,1,B3,0,31                        ← ACK 송신
[TX] S,678,0110000010,0000000100,779,P1,32
                     ^^^^^^^^^^         ← reserved 8번째 비트(B3) 켜짐
```
서버측 대조(socket-engineer): `→ARD R,1,B3,u17,61` / `←ARD A,1,B3,0,31`, **rid 1 일치, 재전송 0건.**
→ **브라우저 예약 → 서버 → 아두이노 → 반영 → ACK 전 구간이 실기에서 처음으로 닫혔다.**

**`+IPD` 어휘 실측(여덟 번째) — 이번엔 문서와 일치했다:**
접두 `+IPD,` / 길이필드 **1개**(링크ID 없음, CIPMUX=0 반영) / 구분자 `:` /
**길이에 LF 포함**(`14` = 본문 13 + LF) / **CR 없음**.

### 3) `[RAM] 최저 여유 884 B` — RX_CAP 판단이 실제 최심부에서 검증됐다

수신 경로(`processCommand`)가 **처음 실행되며 가장 깊은 스택을 밟았다**(그 전 946B → 884B).
ISR 보정(−17B) 하면 **867B**, 재검토 임계 400B 대비 **2.2배 여유**.
→ **RX_CAP 72→96 은 옳았고, 그 근거가 이제 추정이 아니라 실측이다.**

### 4) 소크 일정 (socket-engineer 와 확정)

| 시점 | 시각 | 내용 |
|---|---|---|
| T0 | **08:49:20** | B3 예약 왕복 확인 = 소크 개시 |
| T0+5분 | 08:54:20 | A1 예약→취소 |
| T0+60분 | 09:49:20 | A2 예약→취소 **+ `M` 1회**(§12B.2 예약된빈칸우선) |
| T0+110분 | 10:39:20 | A3 예약→취소 |
| **종료** | **10:49:20** | 2시간 |

**하행을 일정으로 박은 이유**(socket-engineer 지적): §7.4 재하달은 **재접속할 때만** 돈다.
즉 **소크가 잘 될수록(끊김 0) 하행 표본이 최초 1건뿐**이 된다 — **성공이 계측을 굶긴다.**
게다가 초반 표본 하나로는 **후반 열화**를 원리적으로 못 잡는다.

### 5) §4.2 멱등은 **의도적으로 [미검증]으로 남긴다**

같은 rid 재전송을 요청했으나 **설계상 만들 수 없다**: `wire_rid` 는 서버가 단조증가로 부여하므로
(§4.1) 예약을 한 번 더 보내면 새 rid 다. **같은 rid 가 두 번 나가는 경로는 §7.3 재전송뿐**이고
그건 **ACK 가 1.5초 안에 안 올 때만** 발동한다. 내 요청이 설계를 잘못 읽었다.
→ 인위적 훅(ACK 한 번 버리기)은 **넣지 않는다** — 재플래시가 소크를 무효화하고, 그건 실기 조건도 아니다.
→ 2시간 중 자연 발생하면 대조한다: 서버 `↻ 재전송(wire_rid=N)` ↔ 장치 `[DUP rid] N`.
→ **안 나오면 "2시간 동안 ACK 유실 0건" 이 결과이고, §4.2 는 `[미검증 — 발동 조건 미도래]` 로 적는다.**
  **"검증됐다"고 쓰지 않는다.** 안 걸린 분기는 검증된 적이 없다 — 오늘 밤 여덟 번 배운 것이다.

### 6) 소크 중에는 고치지 않기로 한 것

- **재동기가 54초에 한 번꼴로 잦다.** `PROMPT_TIMEOUT_MS=300` 이 이 펌웨어에 빠듯하다는 신호다.
  흡수는 되고 있으므로 **2시간 빈도 데이터를 근거로 소크 뒤 판단**한다
- **`Error`(대문자 E + 소문자) 어휘 불일치(일곱 번째).** 해당 분기가 로그 전용이라 무해하다
- 이유는 같다: **소크 중 재플래시는 관측을 무효화한다.**

### 여기서 나온 것 셋 — 수정은 소크 뒤로 미룬다(지시대로 재플래시하지 않는다)

**🔴 (가) `+IPD,` 가 한 번도 안 나왔다 = 수신 경로가 실기에서 한 번도 검증되지 않았다.**
서버→장치 방향(R 예약 / C 취소 / T 테스트 / M 시뮬)이 **전부 미검증**이다. 지금까지 장치는
S 프레임을 보내기만 했다. 프레임 파싱·체크섬·멱등 캐시·ACK 송신 전부가 미실행 코드다.
→ **소크 중에 서버가 R 이나 M 을 한 번 내려 주면 그 자리에서 검증된다.** socket-engineer 에게
   요청할 가치가 크다. 2시간을 보내기만 하고 끝내면 절반만 검증한 것이 된다.

**⚠ (나) `DISCONNECT` 가 없어 와이파이 끊김을 즉시 알 수단이 없다.**
공유기가 죽으면 장치는 그것을 모르고, `netHasIp` 도 참으로 남는다. 자기교정 경로는 있다
(전송 3회 실패 → CIPCLOSE 사다리 → CIFSR 재확인 → `no ip` 면 CWJAP). 즉 **복구는 되지만
감지가 늦다**(약 4초 + 사다리 시간). 구형 펌웨어에 대안 문구가 없으므로 이대로 두는 것이 맞다고 본다.
개선하려면 CIFSR 주기 점검을 온라인 중에도 도는 방법이 있는데, 이득 대비 복잡도가 커서 권하지 않는다.

**⚠ (다) `link is not valid` 미관측 — REQ-0049 의 즉시-오프라인 경로가 미검증이다.**
이 문구는 신형 어휘일 가능성이 높다. 구형에서 같은 상황에 무엇을 내는지는 아직 모른다.
다만 **주 경로(3회 연속 실패 계수)가 실기에서 실제로 동작하는 것을 이미 확인했으므로**
(로그: `전송 3회 연속 실패 → 오프라인 전환` → 사다리 → 재접속 성공) 무방비는 아니다.

[AT] "\xA6,104,...,220,P1,36AT+CIPSEND=38" (50)   ← 페이로드 에코와 다음 명령이 한 줄로 붙었다
```
`waitForPrompt()` 가 300ms 안에 `>` 를 못 받으면 페이로드를 안 쓰는데, **ESP 는 여전히 N바이트를
기다리고 있다.** 그래서 다음에 보낸 `AT+CIPSEND=38\r\n` 이 **페이로드로 먹힌다.** 위 병합 줄이 그 증거다.
로그에서 이 패턴이 5회 나왔고 매번 1~2 프레임을 잃고 복구됐다. 치명적이진 않지만
**전송 실패 3회 연속의 주된 발생원**이다(= 불필요한 재접속 유발).
고치는 방향은 프롬프트 타임아웃 상향이 아니라, 타임아웃 시 **더미 페이로드로 진행 중인
CIPSEND 를 종결**시키는 것이다. 소크 뒤 별도 제안하겠다.

## 🔬 소크 중단 — **ESP 모듈이 침묵한다. 하드웨어 고장이다(통제 시험으로 확정)**

02:19:54 재플래시 직후부터 `rx` 는 증가하는데 `lines=0`, `[AT]` 출력 0 인 상태가 지속됐다.
가설이 셋 있었고(코드 회귀 / 보율 / 물리), **추측 대신 통제 시험으로 갈랐다.**

### 시험 설계 — client.ino 와 무관한 독립 스케치

`arduino/baudscan/baudscan.ino` (5.4KB, 전혀 다른 코드)로 보율을 훑었다.
이 시험이 "직전 빌드 재플래시" A/B 를 **포함한다**: 완전히 다른 코드에서도 같은 증상이면
client.ino 의 최근 변경은 원인일 수 없다.

### 결과 — 3회 반복, 바이트 단위로 완전히 동일

| 보율 | 바이트 | 인쇄가능 | raw |
|---|---|---|---|
| **9600** | 3 | **3 (전부)** | **`AT\x0D`** |
| 19200 | 2 | 0 | `\x00\x86` |
| 38400 | 2 | 1 | `x\xF8` |
| 57600 | 1 | 0 | `\x00` |
| 4800 | 3 | 0 | `\xF7\xF5\xF8` |
| 2400 | 1 | 0 | `\xFF` |

**9600 에서만 깨끗한 텍스트가 나오는데, 그 텍스트가 우리 자신이 보낸 `AT\r\n` 의 앞 3바이트다.**
나머지 보율의 쓰레기는 같은 신호를 틀린 속도로 디코딩한 결과다.

→ **D8 이 D7 의 송신을 결합(coupling)으로 주워 읽고 있을 뿐, ESP 는 단 한 바이트도 보내지 않는다.**

### 이것으로 동시에 확정된 것 셋

1. **코드 회귀 아님.** 독립 스케치도 동일 → `isAlreadyConnectLine`/`isClosedLine` 추가는 무죄다.
   (루트의 스택 가설도 함께 기각된다. 논증이 아니라 관측으로 갈랐다.)
2. **보율 문제 아님.** 9600 디코딩은 완벽하다.
3. **ESP 발신량 0.** — 그래서 client.ino 의 `rx` 증가폭이 **명령 길이와 정확히 일치**(+58 ↔ 57B)했던 것이다.
   ⚠ 나는 이 단서를 일찍 보고도 "ESP 가 정상 타이밍으로 응답 중"이라고 **거꾸로 읽었다.**
     같은 데이터를 세 번째로 잘못 읽은 셈이다. 기록해 둔다.

### 원인 1순위 — 5V 과전압

사용자가 분압 저항을 빼고 **ESP 의 3.3V RX 핀에 Uno 의 5V 를 직결**해 운용해 왔다(루트 전달).
정격 초과다. 한동안 버티다 죽는 것이 이 고장의 전형적 경과이며, 지금 경과가 정확히 그렇다.

### 사용자 조치

1. ESP 모듈의 **3.3V·GND 실측** — 3.3V 가 안 나오면 전원/레귤레이터 문제
2. **ESP TX → Uno D8** 배선 확인 — 빠짐/접촉불량이면 지금 증상 그대로다
3. 둘 다 정상이면 **모듈이 손상된 것이다. 교체한다.**
   ⚠ **교체품을 물리기 전에 분압을 먼저 넣어라**(Uno TX 5V → ESP RX: 1kΩ+2kΩ ≈ 3.3V).
     안 넣으면 새 모듈도 같은 길을 간다. 이번 고장이 그 증거다.

### 상태

- 보드에는 **client.ino 최신본을 다시 올려 뒀다.** 하드웨어가 살아나면 자동으로 붙는다
- **2시간 소크는 시작되지 않았다.** 하드웨어 복구 시점부터 새로 잡는다
- `arduino/baudscan/` 은 남겨 둔다 — 같은 증상이 또 나오면 2분 만에 같은 판정을 낼 수 있다

### REQ-0063 에 주는 함의

이 사건은 **하드웨어 리셋선(REQ-0063 ②)만으로는 부족하다**는 것을 보여 준다.
리셋선은 AT 계층 wedge 를 풀지만 **죽은 모듈은 못 살린다.** 상시가동을 진지하게 하려면
전원 라인 자체를 끊었다 넣는 수단(MOSFET/로드스위치)이 필요한지 그 REQ 재개 때 같이 판단해야 한다.
그리고 **분압은 선택이 아니라 필수**라는 것이 이번에 비용을 치르고 확인됐다.

## 📥 수신 경로(`+IPD`) 정적 감사 — 하드웨어 없이 할 수 있는 것을 먼저 했다

루트가 합격기준에 수신 경로 4항목을 추가했다(`+IPD` 1회 이상 / 왕복 / 어휘 실측 / 소크 중 1회).
실측은 하드웨어를 기다려야 하지만, **코드 감사는 지금 할 수 있다.** 실측 때 무엇을 볼지도 정해진다.

`net/` 쪽 협조가 필요한 부분은 **REQ-0066 으로 socket-engineer 에게 발행**해 뒀다(실기 세션에
진짜 예약을 내려 달라는 요청). 하드웨어가 살아나면 내가 신호를 보내기로 했다.

### 감사 결과 — 좋은 소식이 대부분이다

| 점검 | 판정 |
|---|---|
| `+IPD,<len>:` vs `+IPD,<id>,<len>:` 형식 차이 | ✅ **무관하다.** 코드는 `+IPD,` 이후 **첫 `:` 뒤**를 취한다. 두 형식 모두 통과 |
| `+IPD` 앞에 개행이 없어 앞 줄과 붙는 경우(`SEND OK+IPD,30:R,...`) | ✅ `strstr` 이라 위치 무관 |
| 한 TCP 세그먼트에 프레임이 여러 개 | ✅ 줄 조립이 `\n` 으로 가르고, `+IPD` 없는 뒷줄도 타입문자 검사로 처리된다 |
| 송신 중 도착(`inSend`) | ✅ `pendLine` 으로 미뤘다가 처리. 두 번째 줄은 버리되 §7.3 재전송이 받는다 |
| `waitForPrompt()` 중 도착 | ✅ 그 루프도 `feedRxChar` 로 넘겨 보존한다 |
| 버퍼 용량 | ⚠ **여유가 0 이다.** `+IPD,63:`(8자) + 프레임 63자 = 71자 = `RX_CAP-1` 과 정확히 같다. 딱 맞아 통과하지만 `+IPD,0,63:`(10자) 형식이면 **넘쳐서 통째로 버려진다**(`[DROP-OVF]` 로는 보인다). 실제 프레임은 25~30자라 실무 위험은 낮다 |

### 🐞 그리고 실제 결함을 하나 찾았다 — **내가 넓힌 것이다**

링크 상태 판정(`ALREAY CONNECT` / `Unlink` / `Linked`)이 **`+IPD` 페이로드를 분리하기 전에** 돈다.
그래서 서버가 보낸 프레임 안에 그 단어가 섞이면(예: userid 가 `Unlink...`) **그 줄이 링크 이벤트로
오인돼 프레임이 통째로 삼켜진다.** 게다가 오인된 김에 `netOnline` 까지 뒤집힌다.

⚠ **이 위험은 내가 `Unlink` 를 판정어에 추가하면서 넓어졌다.** `CLOSED`(전부 대문자)보다
`Unlink` 가 사람 아이디에 섞일 확률이 훨씬 높다. 내 수정이 만든 부작용이므로 내가 막는다.

→ `const bool dataLine = (strstr(s, "+IPD") != NULL);` 을 두고 링크 상태 판정 셋을 전부
  `!dataLine &&` 로 막았다. **데이터 줄은 링크 상태로 해석하지 않는다.**
  컴파일 통과 — flash **15484 B (48%)** / RAM **893 B (43%)**.

⚠ **아직 굽지 않았다.** 보드가 죽어 있어 지금 구워도 관측이 안 된다.
  하드웨어가 복구되면 **이 빌드로 한 번에 구워** 소크를 시작한다(소크 중 재플래시는 관측을 무효화한다).

### 🔧 후속 조치 2건 (루트 지적 반영) — 하드웨어 복구 시 이 빌드로 한 번에 굽는다

**(1) 결함을 개별이 아니라 유형째로 닫았다.**
루트 지적: *"개별 키워드를 하나씩 막으면 다음에 추가되는 키워드에서 또 뚫린다."* 맞다.
페이로드에 섞일 수 있는 것은 `Unlink` 만이 아니다 — `busy`·`no ip`·`ERROR`·`SEND FAIL` 은
**소문자라 자유 필드에 섞일 확률이 오히려 더 높다.**

→ 가드를 늘리는 대신 **순서를 뒤집었다.** `+IPD` 처리를 `handleLine` **맨 앞**으로 올려서
  **데이터 줄은 AT 해석부에 도달조차 하지 않는다.** 프레임 검사부는 `handleFrameLine()` 으로
  묶어 `+IPD` 경로와 평문 경로가 공유한다(한 세그먼트에 프레임이 여러 개일 때 뒷줄이 평문으로 온다).
  `dataLine` 개별 가드 3개는 불필요해져서 제거했다. **코드가 오히려 58B 줄었다.**

  트레이드오프 기록: `Unlink+IPD,...` 처럼 붙어 오면 이제 AT 쪽을 놓친다. 그러나 링크 이벤트를
  놓치는 것은 전송 실패 감지(REQ-0049)가 받아 주는 반면, **데이터를 링크 이벤트로 오인하면
  상태가 오염된다.** 놓치는 쪽이 안전하다.

**(2) `RX_CAP` 72 → 96. 그리고 그 판단을 관측으로 검증하게 만들었다.**
여유 0 은 설계로서 불안하다는 지적을 받아들였다. 수신 줄은 `+IPD` 접두를 **포함한 통짜**로
버퍼에 담기므로 `+IPD,0,63:` 형식이면 73자 → 넘쳐서 **예약이 조용히 사라진다.**
그 형식을 쓰는지는 아직 실측하지 못했다(`+IPD` 0건). 즉 "안 넘친다"는 **가정**이었다.

근거를 숫자로 대려 했으나 `-fstack-usage` 는 이 툴체인에서 **.su 파일이 비어 나왔다**(실패를 기록해 둔다).
그래서 추정으로 때우지 않고 **계측을 넣었다**:
- `ramProbe()` 를 가장 깊은 두 지점(`processCommand` 수신 / `sendLine` 송신)에서 호출해
  `__heap_start` ~ 현재 스택 포인터 사이의 최저 여유를 기록한다
- `[RAM] 최저 여유 <n> B` 를 **1분에 한 줄** 찍는다. `[DIAG]` 는 오프라인 전용이라
  정작 소크(=계속 온라인) 동안 아무것도 안 보이기 때문이다
- ⚠ 이것은 "계측 지점에서 관측된 최저치"이지 이론적 최악값이 아니다. 그래도 추정보다 낫고
  2시간이면 실제 최악에 매우 가까워진다

빌드: flash **15554 B (48%)** / RAM **965 B (47%)**, 여유 **1083 B**.
(RX_CAP +24B × 버퍼 3개 = +72B — 예측과 정확히 일치했다.)
**소크 로그의 `[RAM]` 줄이 이 판단이 옳았는지 답한다.** 여유가 400B 밑으로 내려가면 재검토한다.

#### ⚠ `ramProbe()` 가 **구조적으로 못 보는 것** — ISR 프레임 (루트 지적, 실측으로 수치화)

프로브는 메인 루프에서만 돈다. 그런데 **진짜 최저 여유는 ISR 안에서 발생한다** —
`processCommand` 가 가장 깊이 들어간 순간에 SoftwareSerial 의 RX 인터럽트가 걸리면
그 ISR 프레임이 측정치 **위에** 얹히는데, 프로브가 도는 시점은 이미 ISR 이 반환한 뒤다.
즉 **`[RAM]` 이 찍는 값보다 실제 최저는 항상 낮다.**

루트는 이를 `[추정: 수십 바이트]` 로 남겼는데, **디스어셈블리에서 직접 셌다.**
(`avr-objdump -d client.ino.elf`, AVR-GCC 7.3.0)

| ISR | 벡터 | push | 하드웨어 복귀주소 | 지역프레임 | 중첩 호출 | 합계 |
|---|---|---|---|---|---|---|
| **SoftwareSerial RX** | `__vector_3` (PCINT0/1/2) | **15** | 2 | 0 (SP 조정 없음) | **0건** (리프) | **17 B** |
| millis() | `__vector_16` (TIMER0_OVF) | 9 | 2 | 0 | — | 11 B |

**classic AVR(우리 보드 = ATmega328P)에서는** ISR 진입 시 I 비트가 내려가 핸들러가 `RETI` 로
빠져나올 때까지 인터럽트가 막히므로 **핸들러가 중첩되지 않는다.**
따라서 **최악값은 합이 아니라 둘 중 큰 쪽 = 17 B** 다.
[확정: avr-libc 매뉴얼 `avr_interrupts` — *"interrupt handlers normally do not nest"*]

⚠ **이 문장을 "AVR 은 중첩되지 않는다" 로 넓혀 읽지 마라.** 계열마다 다르다 —
예컨대 **ATmega4809(megaAVR-0)는 ISR 진입 시 I 비트를 지우지 않고** 별도 플래그(`CPUINT.STATUS`)로
중첩을 막는다. 그러면 위 `max()` 논리의 전제가 달라진다.
보드를 megaAVR-0 나 AVR-Dx 계열로 옮기면 **이 17B 계산을 다시 해야 한다.**
재확인 방법은 위 표와 같다: `avr-objdump -d <elf>` 로 `__vector_*` 프롤로그의 push 를 세면 된다.

→ **보정: 실제 최저 여유 ≈ `[RAM]` 표시값 − 17 B.**
   임계값 400B 는 이 17B 를 흡수하고도 충분하므로 **그대로 둔다.**
   ⚠ 다음 사람에게: `[RAM]` 400 을 문자 그대로 "400바이트 남았다"로 읽지 마라. 383 이다.
   (스택 페인팅(0xA5) 워터마크가 정석이지만 17B 보정으로 충분한 지금은 과하다.
    소크에서 400B 근처로 내려가면 그때 넣는다.)

### 실측 때 확인할 것 (합격기준 3번 — 어휘 실측)

`[AT]` 로깅이 모든 줄을 그대로 찍으므로 **첫 `+IPD` 줄의 원문이 바로 답**이 된다. 볼 것:
`+IPD,` 인가 다른 철자인가 / 길이 필드가 하나인가 둘인가 / 구분자가 `:` 인가 / 페이로드에 CR 이 붙는가.
`ALREAY`·`Unlink` 처럼 다를 수 있고, **이 경로는 한 번도 안 걸려봐서 발견될 기회조차 없었다.**

### 이 빌드 이전의 관측(참고 — 재시작 전 6분)

붙은 뒤 프레임이 1Hz 로 정상 전달됐다: 서버 로그 `←ARD S,0..125,...` 연속.
그 사이 링크 손실 1회 → **복구 사다리가 자력으로 되살렸다**(약 15초). 오프라인 카운트 0.
즉 복구 자체는 실기에서 이미 증명됐다 — 위 어휘 수정으로 그 복구가 **5초 빨라질** 뿐이다.

| 서버 구동 | ✅ 떠 있다. `srv_hw` PID 81847 이 **9991·9900 둘 다 LISTEN** |

**즉 서버·주소·포트·보드는 전부 정상이다. 원인은 client.ino 하나다.**

[DIAG] offline step=4 rx=1073 lines=47 up=105s

`rx` 가 늘고 있다 = **ESP 는 살아 있고 AT 응답도 정상**이다. 죽은 게 아니라 **IP 가 없다.**

## 근본 원인 — 두 겹이다

### (1) `handleLine` 이 WIFI 상태줄을 통째로 버린다

```c
// client.ino, handleLine 안
if (strncmp(s, "WIFI", 4) == 0) return;
```

여기 `WIFI GOT IP`(성공 신호)와 `WIFI DISCONNECT`(끊김 신호)가 **전부 포함된다.**
`WIFI CONNECTED` 를 TCP `CONNECT` 로 오인하지 않으려던 조치인데, **와이파이 상태 정보까지 같이 버렸다.**
그래서 코드에는 "와이파이가 붙었는가"를 알 수단이 **아예 없다.**

⚠ 고칠 때 **저 `return` 은 반드시 유지하라.** 지우면 `WIFI CONNECTED` 가 `isConnectLine` 까지
흘러가 "붙지도 않았는데 online" 이 되는 옛 버그가 되살아난다. **읽되 흘려보내지 않는 형태**여야 한다.

### (2) 부팅 순서가 타이머로만 진행한다

```c
default:
  netStep = (uint8_t)(sent + 1);   // 부팅 순서 진행 (RST→CWMODE→CWJAP→CIPMUX→CIPSTART)
```

`NET_WAIT[NET_CWJAP] = 9000`. CWJAP 를 쏘고 **9초 뒤 성공 여부와 무관하게** CIPMUX→CIPSTART 로 간다.
AP 결합이나 DHCP 가 9초 안에 안 끝나면 **IP 없이 CIPSTART** 를 쏘고 ESP 가 `no ip` 로 답한다.

그리고 `no ip` 를 해석하는 코드가 없으므로 `NET_CIPSTART` 분기가 5초마다 CIPSTART 만 영원히 재시도한다.
→ **로그의 step=4 정체가 정확히 이것이다.**

## 이 조합의 진짜 해악 — 증상이 원인을 가린다

진짜 원인이 `+CWJAP:3`(AP 못 찾음)이든 `+CWJAP:2`(비번 틀림)이든, 화면에는 **`no ip` 만 무한 반복**된다.
그 사유 줄이 로그 어딘가에 한 번 스쳐 지나갔어도 아무도 못 본다. **먼저 원인이 보이게 만들어라.**

## ESP-AT 공식 응답 (확정 — 근거 있음)

[확정: https://raw.githubusercontent.com/espressif/esp-at/release/v2.2.0.0_esp8266/docs/en/AT_Command_Set/Wi-Fi_AT_Commands.rst]

- 성공: **`WIFI CONNECTED` → `WIFI GOT IP`** 두 줄
- 실패: `+CWJAP:1` 접속 시간초과 / `+CWJAP:2` 비밀번호 틀림 / `+CWJAP:3` AP 를 못 찾음 / `+CWJAP:4` 접속 실패
- 이스케이프가 필요한 특수문자는 `,` `"` `\` **뿐**이다.
  → 현재 `WIFI_PASS` 의 `!` `_` 는 **이스케이프 대상이 아니다.** 그쪽은 원인이 아니니 파고들지 마라.

## 요구하는 변경 (형태는 네 판단에 맡긴다)

1. **WIFI 상태줄을 읽어라** — `GOT IP` 면 "IP 확보" 플래그를 세우고, `DISCONNECT` 면 내린다. **단 return 은 유지.**
2. **IP 를 확인한 뒤에만 CIPSTART 로 진행하라** — 오래 걸리면 오래 기다려라. 틀린 순서로 가지만 마라.
   `GOT IP` 가 오면 9초 대기창을 끝까지 기다리지 말고 즉시 다음 단계로 가면 부팅이 빨라진다.
3. **`+CWJAP:n` 을 사람이 읽는 문장으로 찍어라** — 이게 이번 건의 핵심 산출물이다.
4. **`no ip` 를 받으면 CIPSTART 재시도가 아니라 CWJAP 로 되돌아가라.**
5. **진단 스캔 권장** — CWJAP 가 2회쯤 연속 실패하면 `AT+CWLAP` 을 **한 번만** 쏴서 주변 AP 목록을 찍어라.
   설정한 SSID 가 목록에 보이는지가 "비번 문제냐 / 애초에 그 AP 가 없느냐" 를 즉시 가른다.
   ⚠ `RX_CAP=72` 라 긴 줄은 잘린다. SSID 만 보이면 되므로 그대로 둬도 되지만, 잘림을 감안해 판단하라.

사용자 지시: **"2시간 이상 정상동작이 확인될 때까지 계속 테스트하고 수정을 반복하라."**

- 굽는 것: `arduino-cli upload -p /dev/cu.usbmodem21201 --fqbn arduino:avr:uno`
- 빌드: 폴더명 ≠ 스케치명이라 원본 경로로는 거부된다. 종전처럼 `/tmp` 사본으로 컴파일하라.
- 시리얼: 115200. **Arduino IDE 시리얼 모니터가 열려 있으면 포트 충돌**이 난다 —
  업로드가 실패하면 그것부터 의심하고 사용자에게 닫아 달라고 요청하라.
- ⚠ **워치독(REQ-0063 ①)은 이번 REQ 범위가 아니다.** 지금 켜면 벽돌 루프 위험이 겹쳐
  원인 분리가 불가능해진다. 이 건이 끝난 뒤 REQ-0063 으로 돌아가라.
