### 설계 원칙 — 평균이 아니라 **최대 공백**을 센다

"2시간 안 끊겼다"를 증명하지 못하게 만드는 것은 정보 부족이 아니라 **모호함**이다.
조용한 로그와 죽은 서버가 똑같이 보인다. 그래서 세 가지를 넣었다.

1. **세션 장부** — 붙고 끊긴 순간을 지속시간·프레임수와 함께 한 줄로 닫는다.
2. **주기 보고(60초)** — 아무 일이 없어도 60초마다 한 줄. **이 줄이 없으면 "2시간 무사고"와
   "1분 만에 멈춤"이 같은 모양이다.** 서버가 살아 있다는 것 자체가 관측 대상이다.
3. **종료 요약** — `Ctrl-C`(SIGINT/SIGTERM)에 한 줄 총평을 남기고 정상 종료(코드 0).

지표는 **프레임 수신 간 최대 공백**이다. 평균은 링크가 반쯤 죽어도 예쁘게 나온다.
공백은 **체크섬 검사보다 먼저** 잰다 — 깨진 줄도 "링크가 살아 있었다"는 증거다.
그리고 **세션 경계를 넘지 않는다** — 끊겨 있던 시간은 공백이 아니라 `링크없음` 으로 따로 센다.

### 구현 — `조별과제샘플/server.cpp`

- 세션 계측: `+ARD … 세션#N` / `-ARD 세션#N 종료(사유) — 지속·프레임·최대공백`.
  종료 경로가 **둘(수신 실패·송신 실패)**이라 `end_ard_session()` 하나로 모았다.
  한쪽만 계측하면 "끊겼는데 세션이 열려 있는" 장부가 생긴다. 사유도 구분한다
  (`상대가 닫음` / `수신 오류` / `송신 실패` / `새 연결로 대체` / `서버 종료`).
- 누적 지표: 프레임 수, 최대공백(+발생시각), 링크없음 시간, 오프라인 판정 횟수(§3.4).
- **재부팅 감지를 원인별로 나눠 센다**: `새연결` vs `uptime추론`.
- 종료 신호 처리: 핸들러는 플래그만 세운다(비동기 안전). `<csignal>` 을 공통 include 로 올렸다 —
  기존 `signal.h` 는 POSIX 분기에만 있어 그대로 두면 **윈도우 빌드가 깨진다.**
- `no_disk` 가 `ensure_log_exists()` 도 막게 했다. 시험 인스턴스가 `data_log.json` 을
  만들어 버리던 것을 고쳤다(이름값을 하게).

### REQ-0062 와 맞물리는 지점 — 요청대로 근거를 잇는다

이 관측은 REQ-0062 에서 내가 **주장으로만 남긴 두 가지를 실측으로 바꾼다.**

1. **`MAX_FWD` 하한의 근거.** REQ-0062 에서 "한 TCP 연결 안 침묵에는 코드상 상한이 없다
   (`OFFLINE_MS` 는 표시만 하고 연결을 닫지 않는다)"고 적고 86400 을 세웠다.
   이제 **최대공백이 실제 숫자로 찍힌다** — 소크가 끝나면 그 값이 임계 선택의 실측 근거가 된다.
2. **"새 연결이 1차 신호"라는 §7.4 의 주장.** `새연결 N / uptime추론 M` 비율이 그대로 검증이다.
   추론이 자주 걸린다면 "MCU 만 리셋되고 소켓이 살아남는" 경우가 드물지 않다는 뜻이다.

**단, 2시간 소크는 seq 랩(18.2시간)을 지나지 못한다** ⚠ — 이 소크로는 REQ-0062 의 수정이
증명되지 않는다. 그건 이미 `--selftest`(65530→0 주입)와 실제 TCP 주입으로 증명해 뒀다.
**소크가 증명하는 것은 "장시간 연결 안정성"이지 "랩 판정"이 아니다.** 둘을 섞지 말 것.

### 검증 — 압축 시나리오를 실제 TCP 로 돌렸다

`g++ -O2 -Wall` 무경고. 포트만 옮긴 사본(19991)에 95초짜리 시나리오를 주입했다:
정상 프레임 → **의도적 6초 침묵** → 복귀 → **재부팅 프레임** → 끊기 → 3초 공백 → 재접속 → 유지.

```
01:57:58  +ARD 아두이노 접속 — 세션#1
01:58:17  -ARD 세션#1 종료(수신 오류) — 지속 00:00:18 · 프레임 12 · 최대공백 7.0초
01:58:17  ! 아두이노 오프라인 판정(3.5초 무프레임) — 누적 1회
01:58:20  +ARD 아두이노 접속 — 세션#2
01:58:42  ⏱ 소크 00:01:00 · 세션 2회(현재 #2 연결중 00:00:22) · 프레임 35 ·
          최대공백 7.0초@01:58:09 · 재부팅감지 3(새연결 2 / uptime추론 1) · 오프라인 1회 · 링크없음 00:00:19
01:59:10  -ARD 세션#2 종료(수신 오류) — 지속 00:00:50 · 프레임 50 · 최대공백 1.0초
01:59:18  ▣ 소크 종료 · 소크 00:01:35 · 세션 2회(현재 끊김) · 프레임 62 ·
          최대공백 7.0초@01:58:09 · 재부팅감지 3(새연결 2 / uptime추론 1) · 오프라인 2회 · 링크없음 00:00:27
```

완료 기준 대조: **(1)** 세션 개설·종료 시각과 지속시간 ✅ **(2)** 최대공백 7.0초 —
주입한 6초 침묵이 1초 주기와 합쳐진 값으로 정확히 잡혔다 ✅ **(3)** 재부팅 감지 3회를
원인별로 ✅ (시나리오와 정확히 일치: 접속 2회 + uptime 역행 1회) **(4)** 종료 한 줄 요약 ✅
`--selftest` 12케이스도 회귀 없이 통과 ✅

> 종료 경로는 PID 를 정확히 지정해 따로 확인했다 — `kill -INT` → 요약 출력 후 **종료 코드 0**.
> (앞선 시험에서 나온 코드 144 는 `pkill -f` 가 백그라운드 래퍼까지 잡은 것이었다. 서버가 아니다.)

**추가 검증 — 조용한 링크.** 위 시나리오는 프레임이 흐르는 동안 주기 보고가 떴다. 그런데 이 줄의
존재 이유는 **아무것도 안 올 때**다(그때 `select` 는 `SELECT_TICK_MS` 로만 깨어난다). 그 경우를
따로 돌렸다 — 클라이언트를 하나도 붙이지 않고 65초:

```
02:03:16  ⏱ 소크 관측 시작 — 60초마다 요약, 종료(Ctrl-C) 시 한 줄 총평
02:04:16  ⏱ 소크 00:01:00 · 세션 0회(현재 끊김) · 프레임 0 · 최대공백 0.0초@- ·
          재부팅감지 0(새연결 0 / uptime추론 0) · 오프라인 0회 · 링크없음 00:01:00
```

**정확히 60초 뒤에 떴다.** 이것이 "2시간 무사고"와 "1분 만에 멈춤"을 가르는 줄이다.
덤으로 `no_disk` 수정도 확인됐다 — 이 실행에는 `data_log.json 을 만들었다` 줄이 없다.

**아직 실행으로 못 본 경로 하나 (숨기지 않는다):** 세션 종료 사유 중 **`송신 실패`** 는
재현이 어려워(상대가 사라진 순간 recv 가 먼저 걸린다) 실행 검증을 못 했다. 대신 코드 감사로
확인했다 — `ard = BAD_SOCK` 대입 지점 3곳이 각각 `end_ard_session()` 과 1:1 이고,
송신 실패 후에는 `ard` 가 `BAD_SOCK` 이라 같은 루프의 recv 분기를 건너뛰므로 **이중 계상이 불가능**하다.
(설령 두 번 불려도 `sess_start_ms`/`link_down_since` 가드가 각각 막는다.)

### 루트/오케스트레이터가 판단할 것 ⚠

- **`srv_hw`(PID 81847)는 죽이지 않았다.** 지시대로 먼저 보고한다. 다만
  그 프로세스는 **2026-08-14 23:05:41 기동**으로, **REQ-0062 의 seq 랩 수정(오늘 01:40)과
  이번 관측 코드가 둘 다 들어 있지 않다.** 지금 그것에 소크를 붙이면
  **고치기 전의 서버를 2시간 측정하는 셈**이고, 관측 로그도 나오지 않는다.
  소크를 하려면 **재빌드한 바이너리로 재기동해야 한다** — 아두이노 시험이 붙어 있을 수 있으니
  중단 시점은 그쪽이 정하라. 내 쪽 시험은 전부 포트를 옮긴 사본(19991)으로 했다.
- 소크 종료 후 그 한 줄(`▣ 소크 종료 · …`)을 나에게 주면 최대공백 값을 §7.4 의
  `MAX_FWD` 근거로 명세에 반영하겠다.

실기 로그(`/tmp/parking-soak.log`)에서 이상이 보였다. 최대공백 **6.2초**가 기록됐는데
(`OFFLINE_MS` 3.5초의 두 배가 넘는다) **`오프라인 0회`** 였다. 그리고 세션#3 은 02:19:5x 이후
프레임이 한 장도 안 오는데 **16분 넘게 "연결중"** 으로 남아 있었다.

**재현**(포트 옮긴 사본): 프레임 2장 보내고 **소켓을 연 채 12초 침묵** → 오프라인 판정 **0회**.

### 원인 — 엣지를 잡을 수 없는 구조였다

```cpp
bool was_online = device_online();   // 루프 맨 위
...                                   // 사이에 블로킹 없음(수 μs)
if (was_online && !device_online())   // 루프 맨 아래
```

두 시점의 간격이 마이크로초라 **3.5초 경계는 언제나 두 반복 "사이"에서 넘어간다.**
경계를 넘은 반복에서는 `was_online` 이 이미 false다 → **엣지가 잡히는 반복이 존재하지 않는다.**
지금까지 이 줄이 떴던 건 **소켓이 닫힐 때뿐**이었고, 그건 `ard==BAD_SOCK` 때문에 값이 뒤집힌
부작용이지 "무프레임 판정"이 아니었다. 즉 **§3.4 의 오프라인 판정은 사실상 동작한 적이 없다.**

### 피해는 로그가 아니라 화면이다 ⚠

이 자리의 `push_snapshot()` 이 브라우저에 "센서 끊김"을 알리는 **유일한 경로**다.
장치가 조용하면 다른 이벤트도 없으므로 push 가 아예 일어나지 않는다 →
**화면이 마지막 상태를 계속 진짜처럼 보여 준다.** 이 프로젝트가 반복해서 잡아온
"실패(무동작)가 성공처럼 보이는" 모양 그대로다. 하필 지금 9991 에서 벌어지고 있는 상황
(ESP 가 조용히 멈췄는데 소켓은 열려 있음)이 정확히 이 경우다.

### 수정 — 평범한 엣지 검출로 바꿨다

직전 상태를 멤버(`ard_online`)로 들고 매 반복 비교한다. **복귀도 대칭으로 찍는다**(플래핑이 보이게).

```
02:38:44  = 아두이노 온라인 복귀
02:38:49  ! 아두이노 오프라인 판정(3500ms 무프레임) — 누적 1회      ← 소켓은 열린 채 8초 침묵
02:38:53  = 아두이노 온라인 복귀                                      ← 프레임 재개
02:38:56  ! 아두이노 오프라인 판정(3500ms 무프레임) — 누적 2회      ← 세션 종료
```

`--selftest` 회귀 없음. **이 수정은 아직 실서버에 반영되지 않았다** — `srv_parking`(PID 76096)을
건드리지 말라는 지시를 받았으므로 교체하지 않았다. 재기동 시점은 오케스트레이터가 정한다.
