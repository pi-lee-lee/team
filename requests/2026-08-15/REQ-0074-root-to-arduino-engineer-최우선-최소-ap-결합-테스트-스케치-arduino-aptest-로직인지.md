# REQ-0074 · 🔴 최우선: 최소 AP 결합 테스트 스케치 (arduino/aptest) — 로직인지 하드웨어인지 가른다. REQ-0073 보다 먼저

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

사용자가 제안했고 **나는 이것이 지금 할 수 있는 가장 좋은 실험이라고 본다.**

> "왜 하드웨어 문제가 메인인가? 난 지금 **코드의 복잡한 로직이 더 문제처럼** 보이는데?
>  **라우터 테스트용 스케치 파일 하나 만들어서** 테스트해 볼까?"

## 왜 이게 옳은가 — 지금 우리는 변수를 못 가르고 있다

`client.ino` 는 2000행이 넘고, 10칸 센서 · 프레임 조립 · 예약 프로토콜 · ACK 재전송 ·
복구 사다리 0~6단 · 시뮬레이션이 **전부 같은 루프 안**에 있다. 이 상태로는
**"AP 결합이 12초에 끊긴다"가 무선의 사실인지 우리 코드가 만든 사실인지 구분할 수 없다.**

지금까지 하드웨어(전원)를 유력하게 본 근거는 전부 **정황**이었다:
Uno 3.3V 핀 50mA 공급 vs ESP 피크 300~430mA, RX 5V 직결, 실패 구간의 시리얼 쓰레기.
반면 **라우터 재기동이 두 번 다 즉시 해결했다** — 이건 정황이 아니라 직접 관측이고,
전원 가설로는 설명되지 않는다. **사용자 지적이 맞다. 하드웨어를 메인에 두지 마라.**

## 요청 내용 — 최소 스케치를 만들어라 (REQ-0073 보다 이게 먼저다)

`arduino/aptest/aptest.ino` (네 소유 경로다. `client.ino` 는 **한 줄도 건드리지 마라** —
지금 굽혀 있는 펌웨어이고 되돌아갈 기준선이다.)

### 단계 1 — 결합만. TCP 없음. 이게 핵심이다

하는 일이 이것뿐이어야 한다:

1. `AT+RST` → `AT+CWMODE=1` → `AT+CWJAP` (SSID/PW 는 client.ino 와 동일하게)
2. 붙으면 `AT+CIFSR` 로 IP 확인하고 **그 뒤로는 5초마다 `AT+CIPSTATUS`(또는 `AT+CIFSR`) 한 번씩만**
3. 매 확인마다 한 줄: `[T+123s] 결합유지 · IP 192.168.50.111`
4. 결합이 풀린 순간: `[T+12s] ★ 결합 소실 — 유지시간 12s` 를 찍고 **그대로 멈춰라**
   (자동 재시도 하지 마라. 재시도는 이번 실험이 없애려는 바로 그 변수다)

**하지 말 것 — 이게 실험의 전부다:**
- 센서·슬롯·프레임·예약·ACK·시뮬레이션 **전부 없음**
- 복구 사다리 **없음**
- TCP(`CIPSTART`/`CIPSEND`) **없음** ← 단계 1 에서는 반드시 없어야 한다
- 재시도 로직 **없음**
- 200행을 넘기면 그건 이미 실험이 아니다. **짧을수록 좋다.**

### 단계 2 — 단계 1 이 통과하면 TCP 를 하나만 얹는다

`CIPSTART` 로 서버(9991)에 붙고 **1Hz 로 고정 문자열 한 줄**만 보낸다.
프레임 문법을 맞출 필요 없다 — 서버가 버려도 된다. 보고 싶은 것은 **연결이 유지되는가** 뿐이다.

### 판정표 — 결과가 무엇을 뜻하는지 미리 못 박는다

| 단계 1 결과 | 결론 |
|---|---|
| **몇 분~몇 시간 결합 유지** | **하드웨어·AP 는 무죄. `client.ino` 로직이 범인이다.** 그러면 다음 일은 client.ino 를 이 최소 스케치 쪽으로 깎아 내려가며 이분탐색하는 것이다 |
| **12초 근처에서 소실** | 우리 로직은 무죄. AP 또는 전원이다. 그 뒤에 단계 2, 그리고 전원 분리 실험으로 갈린다 |
| 결합 자체를 못 함(CWJAP FAIL 반복) | AP 가 이 MAC 을 막고 있다 — 사용자의 차단 가설(REQ-0073)이 확증된다 |

**이 표를 스케치 머리 주석에 그대로 넣어라.** 결과를 보고 나서 해석을 지어내지 않기 위해서다.

## 실행 방식

- **네가 굽지 마라. 포트를 열지 마라.** 지금 사용자의 Arduino IDE 시리얼 모니터가
  `/dev/cu.usbmodem101` 을 잡고 있다(pid 99973). 컴파일 검증까지만 하고 **사용자가 굽는다.**
- 사용자가 IDE 에서 바로 열 수 있게 **경로와 여는 법을 결과 노트에 한 줄로** 적어라.
- SSID/PW 를 스케치 안에 하드코딩하는 것은 이번 실험에서는 허용한다(짧을수록 좋다).
- ⚠ 이 스케치를 구우면 `client.ino` 가 지워진다. **되돌아오는 법**(원본을 다시 굽기)도
  결과 노트에 적어 사용자가 막히지 않게 하라.

## REQ-0073(백오프)은 어떻게 되나

**취소하지 않는다. 순서만 뒤로 간다.** 백오프는 어느 가설이 맞든 필요한 개선이다
(라우터를 두들기지 않는 것은 그 자체로 옳다). 다만 **이 실험 결과가 나오기 전에는
client.ino 를 더 복잡하게 만들지 마라** — 지금 의심받는 것이 바로 그 복잡도다.
단계 1 결과를 보고 내가 다시 지시한다.

## 왜 필요한가

client.ino 2000행 안에서 센서·프레임·예약·사다리·시뮬이 한 루프에 섞여 있어 '12초 결합 소실'이 무선의 사실인지 우리 코드가 만든 사실인지 구분할 수 없다. 사용자가 코드 복잡도를 의심하고 있고, 라우터 재기동이 두 번 다 즉시 해결한 관측은 전원 가설로 설명되지 않는다. 변수를 하나로 줄이는 실험이 필요하다.

## 무엇을 보게 되는가

붙으면 5초마다 한 줄씩:
```
[T+5s] 결합유지 · IP 192.168.50.111
[T+10s] 결합유지 · IP 192.168.50.111
```
풀리면 한 번 찍고 **그 자리에서 멈춘다**(재시도하지 않는다):
```
[T+12s] ★ 결합 소실 — 유지시간 12s
```

### 판정 (스케치 머리 주석에도 같은 표가 있다)

| 결과 | 결론 |
|---|---|
| 몇 분~몇 시간 유지 | **하드웨어·AP 무죄 → `client.ino` 로직이 범인.** 최소 스케치 쪽으로 깎아 내려가며 이분탐색 |
| **12초 근처** 소실 | 우리 로직 무죄 → **AP 또는 전원.** 다음은 단계 2(TCP), 그다음 전원 분리 실험 |
| 결합 자체 실패 | **AP 가 이 MAC 을 막고 있다** → 차단 가설(REQ-0073) 확증 |

⚠ 확인 주기가 5초라 **소실 시각의 해상도는 ±5초**다. 다만 모듈이 비동기 `WIFI DISCONNECT` 를
내면 그건 즉시 잡아 정확한 시각을 찍는다(구형 ai-thinker 는 안 낼 가능성이 높다 — REQ-0064 실측).
그래서 "12초"와 "15초"를 구분하려 들지 마라. 우리가 가르려는 것은 **초 단위냐 분 단위냐**다.

## 설계에서 신경 쓴 것 세 가지

1. **없는 것이 내용이다.** TCP·재시도·센서·프레임·예약·ACK·사다리·시뮬 전부 뺐다.
   특히 **재시도를 뺀 것**이 중요하다 — 재시도는 이번 실험이 없애려는 바로 그 변수다.
2. **판정표를 코드 안에 먼저 박았다.** 결과를 본 뒤에 해석을 지어내지 않기 위해서다.
3. **블로킹으로 짰다(의도).** 평소 기준(`delay` 로 흐름을 막지 않는다)을 여기서만 접었다.
   할 일이 하나뿐이라 루프를 막아서 놓치는 것이 없고, 한눈에 다 읽히는 쪽이 낫다.

## ⚠ 발견: `client.ino` 머리 주석의 배선 설명이 **틀렸다** (이번에 고치지 않았다)

```
client.ino:9   * 배선 : D7 = ESP TX → Uno(RX) / D8 = Uno(TX) → ESP RX
client.ino:80-82  PIN_ESP_RX = 8;  PIN_ESP_TX = 7;  SoftwareSerial wifi(8, 7);
```
**둘이 서로 반대다.** 실제로 동작하는 것은 코드 쪽(핀 8 이 Uno 의 수신, 핀 7 이 송신)이므로
aptest 는 **코드를 복사**했다. 주석을 믿고 배선을 바꾸면 멀쩡한 배선을 망가뜨린다.
`client.ino` 를 건드리지 말라는 지시라 **고치지 않고 보고만 한다** — 다음에 그 파일을
열 때 주석을 코드에 맞추는 것이 좋겠다.

## A2 (ESP 하드웨어 리셋선) 은 어떻게 되나

aptest 는 A2 를 **INPUT(하이임피던스) 그대로** 둔다 = 모듈을 리셋으로 잡지 않는다.
**배선을 뽑을 필요 없다.** 그대로 두고 구우면 된다.

## 이번 결과가 무엇을 못 말하는지 (미리 못 박는다)

- 이 스케치가 오래 버텨도 **전원 문제가 없다는 증명은 아니다.** aptest 는 TCP 를 안 쓰므로
  송신 전류 피크가 client.ino 보다 훨씬 작다. "결합만 하면 조용하니까 버틴다"일 수 있다.
  그래서 단계 2(TCP 1Hz)가 판정에 필요하다 — 거기서 갈린다.
- 반대로 12초에 끊겨도 **AP 냐 전원이냐는 아직 안 갈린다.** 그건 전원 분리 실험의 몫이다.
