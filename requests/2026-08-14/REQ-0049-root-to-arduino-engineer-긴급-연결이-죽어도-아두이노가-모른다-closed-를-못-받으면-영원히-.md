# REQ-0049 · 긴급: 연결이 죽어도 아두이노가 모른다 — CLOSED 를 못 받으면 영원히 죽은 소켓에 쓴다

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

## 실기 증상 (사용자 보고)

> `seq` 1000 근처에서 아두이노 접속이 끊긴다. 하지만 **아두이노는 계속 송신 중**이고 서버는 수신하지
> 못한다. 웹에서 테스트 모드를 켜면 "센서가 연결되어 있지 않다"고 응답한다.

`seq` 1000 은 1Hz 에서 약 17분이다. 즉 **17분쯤 돌다가 TCP 가 죽는데 아두이노가 눈치를 못 챈다.**

## 원인 — 루트가 코드로 확인했다

**`netOnline = false` 가 되는 곳이 파일 전체에 딱 하나다** — `CLOSED` 줄을 받았을 때(850행)뿐이다.

```
client.ino:850   if (strstr(s, "CLOSED")) { netOnline = false; ... }
```

그러니 **`CLOSED` 가 오지 않거나 놓치면 `netOnline` 은 영원히 true** 다. 그 뒤로는:

- `netTick()` 이 첫 줄에서 `if (netOnline) return;` 으로 빠져 **CIPSTART 재시도를 하지 않는다**
- `statusTick()` 은 계속 `sendStatus()` 를 부른다 → **죽은 소켓에 계속 쓴다**
- `waitForPrompt()` 가 매번 타임아웃 → `[TX-DROP]` 만 쌓인다
- 서버는 3.5초 무프레임으로 오프라인 판정 → **화면이 "센서 미연결"**

증상 셋이 전부 여기서 나온다. **TCP 가 왜 죽었는지와 무관하게 이건 고쳐야 한다** —
장시간 운전에서 링크는 언젠가 죽고, 그때 스스로 복구하지 못하면 사람이 재부팅해야 한다.

## 고칠 것

### ① 전송 실패가 누적되면 오프라인으로 전환한다 (주 방어선)

`sendLine()` 이 실패하면(프롬프트 타임아웃) **연속 실패 횟수를 센다.**
**N회 연속 실패 → `netOnline = false` → CIPSTART 재시도**로 들어간다.
성공하면 카운터를 0 으로 되돌린다.

**N 을 지어내지 마라 — 근거가 이미 있다.** 명세 §3.4 는 **서버가 3.5초 무프레임이면 오프라인으로
판정**한다. 즉 **서버가 이미 우리를 죽었다고 볼 시점이면 우리도 그렇게 봐야 한다.**
하트비트가 1Hz 이고 실패마다 `SEND_FAIL_BACKOFF_MS`(500ms)가 걸리니 **3회 연속**이면 그 근방이다.
네가 계산해서 정하고 **근거를 주석에 남겨라.**

`CLOSED` 경로는 그대로 둔다 — 그게 정상적인 통보이고 더 빠르다. 이건 통보가 안 올 때의 그물이다.

### ② 명시적 오류 응답도 받아들여라 (보조, 더 빠름)

CIPSEND 가 죽은 링크에서 실패하면 ESP 는 보통 `link is not valid` / `SEND FAIL` / `ERROR` 를 낸다.
지금 `handleLine()` 은 이들에 아무 반응이 없다. **송신 직후 이런 줄이 오면 즉시 오프라인**으로 보는 것이
①보다 빠르다.

⚠ 다만 **`ERROR` 만으로 판단하지 마라.** AT 명령이 실패할 때도 나오는 흔한 응답이라
연결과 무관한 상황에서 오프라인으로 떨어질 수 있다. `link is not valid` / `SEND FAIL` 처럼
**전송 실패를 특정하는 문구**를 우선하고, 무엇을 넣었는지와 근거를 적어라.
**확신이 없으면 ①만 하고 ②는 넘겨라** — ①만으로도 복구는 된다.

### ③ 복구되는 것을 로그로 보이게

`[NET] 전송 3회 연속 실패 → 오프라인 전환, 재접속 시도` 같은 줄이 있어야
현장에서 "죽었다가 살아났다"를 읽을 수 있다. 지금은 `[TX-DROP]` 만 반복돼서
**끊긴 것인지 원래 그런 것인지 구분이 안 된다.**

## 하지 말 것

- **주기적 `AT+CIPSTATUS` 폴링으로 해결하지 마라.** 9600bps 링크에 왕복을 더하는 것이고,
  ①이 같은 문제를 공짜로 푼다.
- 타이밍·핀·보율은 건드리지 마라.

## 참고 — 왜 TCP 가 죽었는지는 별개 문제다

원인 후보(ESP-01 AT 펌웨어의 장시간 불안정, 힙 소진, 공유기, 윈도우 쪽)는 아직 모른다.
①이 들어가면 **원인을 몰라도 스스로 복구**된다. 원인 추적은 그다음이고, ③의 로그가 그 실마리가 된다.

서버가 죽은 소켓을 계속 들고 있는 것도 별개로 볼 것이 있는데, 그건 루트가 socket-engineer 와 본다.

## 검증

하네스로:
- 프롬프트가 안 오는 상황을 N회 연속 만들면 `netOnline` 이 false 가 되고 CIPSTART 재시도로 들어간다
- 중간에 한 번 성공하면 카운터가 0 으로 돌아간다 (한두 번 실패로 끊지 않는다)
- `CLOSED` 경로는 그대로 동작한다 (회귀)
- 재접속 후 정상 전송으로 복귀한다
- 컴파일 + 플래시·RAM

**REQ-0047 을 먼저 끝내고 이걸 해도 되고, 합쳐도 된다. 네가 정해라** — 같은 파일이고 빌드가 겹친다.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

실기에서 17분쯤 뒤 링크가 죽는데 아두이노가 모르고 계속 죽은 소켓에 쓴다. 사람이 재부팅해야 복구되므로 장시간 시연이 불가능하다. netOnline=false 가 되는 경로가 CLOSED 하나뿐인 것이 구조적 원인이고, TCP 가 왜 죽었는지와 무관하게 이 그물은 있어야 한다.

### N = 3 의 근거 (기준 2)

명세 §3.4 가 **서버는 3.5초 무프레임이면 오프라인으로 본다**고 정했다.
**서버가 이미 우리를 죽었다고 볼 시점이면 우리도 그렇게 봐야 한다** — 그게 기준점이다.
실패 1회의 주기를 코드에서 계산했다:

| 상황 | 주기 |
|---|---|
| 하트비트만 있을 때 | 대기 1000 ms + 프롬프트 타임아웃 300 ms = **약 1300 ms** |
| 변화가 밀려 있을 때 | 백오프 500 ms + 프롬프트 타임아웃 300 ms = **약 800 ms** |

→ **3회 연속이면 마지막 성공 프레임으로부터 약 2.4초(변화 주도) ~ 3.9초(하트비트만)** 다.
   서버의 3.5초 판정을 정확히 걸친다.

- **2회(1.6~2.6초)는 이르다** — 서버가 아직 살아 있다고 보는 동안 우리가 스스로 링크를 끊는다.
  `busy p...` 같은 일시적 실패 두 번으로 재접속에 들어가는 것은 손해다.
- **4회(3.2~5.2초)는 늦다** — 서버가 이미 포기한 뒤에도 죽은 소켓에 계속 쓴다.

### ① 연속 실패 카운터 — 세는 곳을 **하나로** 못 박았다

사용자가 준 단서(`seq 1734` 고정, 서버는 1733)가 결정적이었다. `statusTick()` 은 성공 시에만
`seq` 를 올리므로 **같은 seq 반복 = `sendStatus()` 가 계속 false = `waitForPrompt()` 매번 타임아웃**이다.
즉 **실패는 이미 정확히 감지되고 있었고 그 값을 버리고 있었을 뿐이다.** 그래서 훅은 `sendLine()` 의
반환값 하나로 끝난다.

```c
// sendLine() 끝
noteSendResult(ok);      // ok=true → streak=0 / false → streak++ , 3 이면 goOffline()
```

**⚠ 여기서 설계 판단이 하나 있었다: 세는 곳은 `sendLine()` 한 곳뿐이어야 한다.**
수신된 오류 문구(`SEND FAIL` 등)로도 세면 **한 번의 실패가 두 번 계수된다** — `sendLine()` 이
false 를 반환하고, 그 송신에 대한 오류 줄이 곧 도착하기 때문이다(송신 중 도착분은 `pendLine` 에
미뤄졌다가 다음 루프에 처리된다). 그러면 N=3 이 사실상 1.5 가 되어 **위 계산 근거가 무너진다.**
그래서 ②는 세지 않는다(아래).

`goOffline()` 은 `netOnline=false`, 카운터 0, `netStep=4`(CIPSTART 재시도)로 만든다.
**멱등 캐시는 비우지 않는다** — 이 판정은 추정이고, 링크가 실은 살아 있었다면 재시도에
`ALREADY CONNECTED` 가 와서 그대로 복귀한다. 그때 캐시를 비웠다면 **살아 있는 연결의
멱등성(REQ-0035 [18]-4)이 깨진다.** 캐시는 실제 연결 생명주기 신호인 `CLOSED`/`CONNECT` 에서만
비운다(REQ-0036). 하네스 [28] 이 그 회귀를 지킨다.

### ② 오류 응답 — 넣었고, `ERROR` 도 **안전하게** 쓸 수 있게 됐다 (기준 6)

루트가 "`ERROR` 는 관계없는 AT 실패에도 나오니 조심하라"고 했는데, 코드를 보니 **그 위험이
구조적으로 없다**는 것을 확인했다:

> `netTick()` 은 `if (netOnline) return;` 으로 시작한다. 즉 **온라인 중에는 AT 명령이
> `AT+CIPSEND=` 하나뿐이다.** 따라서 **온라인 중에 오는 오류 응답은 반드시 CIPSEND 에 대한 것**이다.

그래서 오류 문구 처리를 `if (netOnline)` 안에 두고, 판정을 둘로 나눴다:

| 문구 | 처리 | 근거 |
|---|---|---|
| `link is not valid` | **즉시 오프라인** | 모듈이 링크가 무효라고 **명시**한 것이라 모호하지 않다 |
| `SEND FAIL` · `ERROR` · `busy` | **로그만** | "이 송신이 실패했다"는 뜻이지 링크 사망의 확증은 아니다. 대응되는 `sendLine()` 실패가 이미 카운터를 올리므로 3회면 잡힌다 |

즉 **②는 빠른 경로를 하나 추가할 뿐이고 임계값 판단은 ①이 단독으로 한다.** 로그만 남기는 쪽도
값을 한다 — 실제로 어떤 문구가 오는지 현장 로그에 그대로 찍힌다.

⚠ **문구는 여전히 추정이다.** REQ-0042 의 `[AT]` 전체 로깅이 올라간 빌드에서 그 순간의 로그가
오면 확정해서 좁힐 수 있다. 지금은 문구를 몰라도 ①로 복구된다는 것이 핵심이다.

### ③ 로그 (기준 4)

```
[NET] 전송 실패 1/3
[NET] 전송 실패 2/3
[NET] 전송 실패 3/3
[NET] 전송 3회 연속 실패 → 오프라인 전환, 재접속 시도
[NET] 4 CIPSTART
[NET] online (ALREADY CONNECTED)
```

예전에는 `[TX-DROP]` 만 반복돼서 **"끊긴 것"과 "원래 조용한 것"이 구분되지 않았다.**
이제 실패가 누적되는 것과 복구가 시작되는 것이 로그에 그대로 보인다.

### 하네스 (기준 7) — **117 PASS / 0 FAIL** (95 → 117)

가짜 ESP 에 **`refusePrompt` 스위치**를 넣어 실기 증상을 재현했다 — CIPSEND 에 `>` 를 주지 않고
`ERROR` 만 돌려준다. 그러면 `waitForPrompt()` 가 매번 타임아웃하며 seq 가 고정된다.

```
[25] refusePrompt → 연속 실패 → netOnline=false, netStep=4, seq 고정 확인
     → refusePrompt 해제 → 스스로 재접속 → 다시 S 프레임 송신
[26] 실패 2회에서는 온라인 유지 (한계 3) → 한 번 성공 → streak 0 복귀
[27] ERROR 하나로는 오프라인 안 됨 + 카운터도 안 오름(이중 계수 방지) + 로그에는 남음
     link is not valid → 즉시 오프라인 → 복귀
[28] CLOSED 회귀 — 오프라인 + 캐시 비움 둘 다 유지
```

**[25] 는 `seq` 가 고정되는 것까지 단언한다** — 실기에서 사용자가 본 것과 같은 성질이
하네스에서도 재현된다는 뜻이다.

**RAM +39 B 의 내역을 정확히 확인했다** (`avr-nm` 으로 심볼을 훑었다). `sendFailStreak` 는 1바이트고
디버그 문자열은 `F()` 라 PROGMEM 이다. 범인은 **`strstr()` 에 넘긴 문자열 리터럴**이다 —
AVR 에서 `strstr`/`strcmp` 의 인자는 RAM 포인터여야 하므로 그 리터럴들이 `.data` 에 앉는다:

```
"link is not valid"  18 B   (17자 + NUL)
"SEND FAIL"          10 B
"ERROR"               6 B
"busy"                5 B
                   ─────
                     39 B   ← 관측된 증가분과 정확히 일치
```

기존 코드도 같은 방식이다(`"ALREADY CONNECT"`, `"CLOSED"`, `"+IPD,"`, `"WIFI"`, `"CONNECT"`).
**RAM 이 빡빡해지면 `strstr_P()` + `PSTR()` 로 옮기는 것이 지렛대**라는 것을 적어 둔다 —
지금은 여유가 1216 B 라 하지 않았다(코드가 늘고 기존 패턴과 어긋난다).
가장 큰 RAM 소비자는 `Serial` 객체 157 B, 줄 버퍼 3개 × 72 B, SoftwareSerial 수신 버퍼 64 B,
`simNextAt` 40 B, 멱등 캐시 40 B 다. (`simNextAt` 40 B 는 REQ-0047 에서 사라진다.)

### 검증하지 않은 것

- ⚠ **실기 검증은 사용자 몫이다.** 17분 뒤 실제로 복구되는지는 올려서 돌려 봐야 안다.
- **왜 TCP 가 죽는지는 여전히 모른다.** ①은 원인을 몰라도 복구시키는 그물이고,
  원인 추적은 ③의 로그가 실마리가 된다.
- `link is not valid` 문구가 이 모듈에서 실제로 나오는지 미확인(추정).
