web-engineer 가 **같은 계열의 결함**을 올렸다(REQ-0033). 같은 파일을 고치므로 한 번에 처리해라.

  원인도 안 보인다. **"안 보이게 하기"는 이 계열 문제의 해법이 아니다.**

web-engineer 가 화면에 넣은 임시 방어(마지막으로 알던 무장 상태를 기억해 경고)는 유지하되,
**폴백 상태에서 새로 연 브라우저**는 그것으로 못 막는다는 지적이 정확하다.
시연 중 WS 가 끊기고 누가 새로고침하면 바로 그 상태가 된다.

`docs/net/parking-protocol.md` §9.1 예시 JSON 도 같이 갱신하고 §13 에 기록해라.
완료 기준에 다음을 더한다: **무장+주입 상태에서 실제 `data_log.json` 을 열어 두 필드가 실린 것을 보여라.**

## 판정: (a) 채택

REQ-0032 의 `## 처리 결과` 에 근거를 적었다. 요지만 옮긴다:

**멱등 캐시가 지키려는 것(§7.3 재전송의 중복 적용 방지)은 구조적으로 한 연결 안에서만 일어난다.**
타임아웃 1500ms · 최대 2회가 전부 살아 있는 연결 위에서 끝나고, 연결이 끊기면 §7.4 가
**새 `wire_rid` 로 재하달**하도록 이미 정해 두었다. 따라서 연결 경계에서 캐시를 비워도 **잃는 보호가 없다.**

(b)(c) 는 기각했다. 특히 (b) 는 확률만 낮추는데, 이 버그는 증상이 "조용한 성공"이라
**재현 확률을 낮추는 것이 오히려 더 나쁘다** — 드물게 나는 버그가 더 오래 산다.

## 할 것

1. **명세 §4.2 에 규칙 추가** — "아두이노는 새 TCP 연결이 맺어지면 멱등 캐시를 비운다."
   근거(재전송은 한 연결 안에서만 일어난다 / 새 연결 = 새 rid 공간 / §7.4 와 개념 일관)를 같이 적어라.
   §13 개정 이력에도 넣어라. 이 결함이 어떻게 드러났는지(실패가 성공으로 보였다)도 한 줄 남기면 좋겠다.
2. **`net/fake_arduino.py` 반영** — 이제 우회가 아니라 명세 구현이므로 넣는 것이 맞다.
3. **REQ-0029 검증을 다시 하라** — 아두이노를 수동 재시작해서 rid 공간을 맞췄던 부분이 있다면,
   이번엔 **서버만 재시작하고 가짜 아두이노는 그대로 둔 채** 통과하는지 확인해라. 그게 이 수정의 요점이다.

## 네가 잘한 것 하나

`fake_arduino.py` 에 우회를 넣지 않은 판단이 옳았다. **"내 가짜 아두이노만 캐시를 비우게 하면
실기에는 남아 있는 버그가 내 시험에서만 사라진다"** — 검증 도구를 고쳐 증상을 지우고 싶은 유혹이
가장 큰 자리인데 정확히 반대로 갔다.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

개발 중 서버 재시작은 상시로 일어나고, 그때마다 최대 8개 명령이 조용히 삼켜지면서 result=0 으로 성공처럼 보인다. 예약(R/C)도 같은 rid 공간을 쓰므로 테스트 모드만의 문제가 아니다.

### ③ 재현 조건 그대로 — 서버만 재시작

**세션 1**(rid 1·2·3 소모): 무장 → `A3` 주입 → 해제, 전부 `result=0`.

**서버만 종료 후 재시작**(가짜 아두이노는 계속 켜 둠 — 이게 원래 실패하던 조건):

```
→ {"type":"test_arm","rid":"n1"}          ack rid=n1  slot=None  result=0
→ {"type":"test_set","slot":"B4",...}     ack rid=n2  slot=B4    result=0
   armed = True · override_count = 1
   B4 occupied=1 overridden=1
=> 서버만 재시작해도 정상 동작: True
```

아두이노 로그 — **재접속 때 낡은 3건을 버린 것**이 보인다:

```
10:11:20  + 서버 접속 ... · 멱등 캐시 비움(0건)
10:11:40  + 서버 접속 ... · 멱등 캐시 비움(3건)     ← 이 3건이 버그의 원인이었다
```

**수정 전에는** 여기서 무장이 통째로 삼켜지고 `A1` 요청에 `A3` ACK 가 `result=0` 으로 왔다.
지금은 세션 2 로그에 `캐시 적중` 이 한 건도 없다.

### ④ 캐시를 비워도 연결 안 멱등성은 그대로

`--drop-rate 1.0` 으로 ACK 를 전부 버리게 하고 예약:

```
10:12:32  ✗ ACK 유실시킴 — 예약은 반영된 상태: A,4,B1,0,36
10:12:33  = rid 4 재수신 → 멱등 캐시 적중, 재적용 없이 같은 ACK 재전송 ('B1', 0)
10:12:35  = rid 4 재수신 → 멱등 캐시 적중, 재적용 없이 같은 ACK 재전송 ('B1', 0)
```

**같은 연결 안에서는 캐시가 정확히 제 일을 한다.** 브라우저는 `ack_timeout` 을 받았다.
루트가 보탠 논거대로 **잃는 보호가 없다**는 것이 실측으로 확인됐다 —
재전송은 살아 있는 연결 위에서만 일어나므로 연결 경계에서 비우는 것과 겹치지 않는다.

### (REQ-0033) `data_log.json` — 실제 파일

무장 + `B4` 주입 상태에서 연 실물이다:

```json
[
  {"ts":1786669926770,"device_id":"P1","uptime":50,"seq":48,
   "occupied":"0100111110","reserved":"0000000000",
   "test_mode":{"armed":true,"override_count":1},
   "slots":[ ... {"id":"B4","occupied":1,"reserved":0,"overridden":1}, ... ]}
]
```

**폴백으로 넘어간 브라우저도 이제 `B4` 가 주입값임을 알 수 있다.**

구현에서 하나 더 손댔다: `data_log` 는 §9.4 에 따라 **내용이 바뀔 때만** 쓰는데,
변경 감지 키에 점유/예약 비트만 있었다. **테스트 상태를 키에 넣지 않으면 무장·주입이
파일에 반영되지 않고 폴백 화면이 낡은 "해제" 상태를 계속 보여 준다** — 개정 4가 막으려는
바로 그 증상이 다른 경로로 되살아난다. 키에 `armed` 와 오버라이드 마스크를 넣었다.

### ⑤ 회귀

```
[§7.5-3] 무장 → A1 빈자리 주입 → 예약 → 입차 주입 → 해제
   입차후 A1 occ=1 res=1 ovr=1
   해제후 A1 occ=0 res=1 ovr=0        ← 되돌림에도 예약 생존: True
빌드 -Wall -Wextra 0경고 · --selftest 18/18 통과
```

### 명세 변경 (v1.3)

- **§4.2** — "새 TCP 연결에서 멱등 캐시를 비운다" + 근거(재전송은 한 연결 안에서만 일어난다 /
  새 연결 = 새 rid 공간 / §7.4 와 개념 일관) + 기각한 대안(rid 대역 분리는 확률만 낮춘다).
  **증상이 "조용한 성공"이라 드물게 나면 오히려 더 오래 산다**는 점을 적었다.
- **§9.1** — `test_mode` · `slots[].overridden` 추가. **§12A.6 이 폴백 경로에서만 빠져 있었다**는
  경위와, "무장 중 파일 쓰기 중단"이 해법이 아닌 이유(안 보이게 하는 것은 해법이 아니다)를 남겼다.
- **§13** — 개정 4 항목. 두 결함 다 **"실패가 성공처럼 보이는"** 종류라 자동 검증으로 안 잡힌다는 점을 기록했다.

### 미검증

- **Windows 빌드 여전히 불가.** 이번 변경도 플랫폼 무관이지만 확인 못 했다.

  arduino-engineer 반영이 필요하다 — 내가 확인할 수 없는 부분이다.

  나는 **파일에 필드가 실린 것까지** 확인했다.
