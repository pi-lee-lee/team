# REQ-0032 · 명세 결함: 서버 재시작 시 wire_rid 재사용으로 아두이노 멱등 캐시가 새 명령을 삼킨다

**요청자** `socket-engineer` → **담당** `root`

## 요청 내용

상세와 실측 로그는 아래 '재현' 절에 적는다(발행 명령에 로그를 넣으면 길어서 잘린다).

## 재현 — REQ-0029 검증 중 실제로 겪었다

**증상**: 서버를 재시작한 뒤 브라우저에서 테스트 모드를 켰는데 **무장이 되지 않았다.**
그리고 `A1` 에 주입했는데 ACK 가 **`A3`** 를 담아 왔다. `A3` 는 그 세션에서 건드린 적이 없는 자리다.

**원인**: `wire_rid` 는 서버가 발급하고 **서버 재시작 시 1부터 다시 시작한다**(§4.1).
그런데 아두이노는 재부팅하지 않았으므로 **§4.2 멱등 캐시(최근 8건)가 그대로 살아 있다.**
새 서버의 rid 1,2,3… 이 옛 세션의 rid 1,2,3… 과 충돌해 **전부 "재수신"으로 판정**된다.

아두이노(`fake_arduino.py`) 로그 — 세 명령이 연속으로 삼켜졌다:

```
10:01:43  = rid 1 재수신 → 멱등 캐시 적중, 재적용 없이 같은 ACK ('??', 0)
10:01:44  = rid 2 재수신 → 멱등 캐시 적중, 재적용 없이 같은 ACK ('A3', 0)
10:01:45  = rid 3 재수신 → 멱등 캐시 적중, 재적용 없이 같은 ACK ('??', 0)
```

브라우저가 받은 것 — **성공했다고 나온다.** 실제로는 아무것도 적용되지 않았다:

```
{"type":"ack","rid":"q1","slot":"A3","result":0,"message":"테스트 값을 적용했습니다"}
                        ^^^^ 요청한 자리는 A1 이었다
```

**최대 8개 명령**(캐시 크기)이 이렇게 삼켜진다.

## 왜 위험한가

- **실패가 성공으로 보인다.** `result=0` 이 돌아오므로 서버도 브라우저도 정상으로 처리한다.
  타임아웃도 오류도 없다 — 로그를 파고들기 전까지는 원인을 알 수 없다.
- **개발 중 서버 재시작은 상시로 일어난다.** 코드를 고칠 때마다 밟는다.
  아두이노는 계속 켜 둔 채 서버만 다시 띄우는 것이 자연스러운 작업 흐름이라 더 자주 걸린다.
- 예약(`R`/`C`)도 같은 rid 공간을 쓰므로 **테스트 모드만의 문제가 아니다.**
  재시작 직후 예약이 조용히 무시되고 옛 자리의 ACK 가 올 수 있다.
- 나는 `fake_arduino.py` 를 재시작해서 우회했지만, **실기 아두이노는 그렇게 못 한다.**

## 이것이 명세 문제인 이유 — 내가 단독으로 못 고친다

§4.2(멱등 캐시)와 §4.1(rid 발급)이 맞물린 지점이고, 고치는 위치에 따라 **아두이노 구현이 바뀐다**.
`client.ino` 는 `arduino-engineer` 소유다. 명세는 얼려 있으므로 §12 절차대로 올린다.

## 선택지 (루트가 정한다)

**(a) 아두이노가 새 TCP 연결에서 멱등 캐시를 비운다** — 내가 보기에 가장 맞다.
새 연결 = 새 서버 세션 = 새 rid 공간이다. 재전송은 **같은 연결 안에서만** 일어나므로
§4.2 의 목적(재전송이 두 번 적용되지 않게)은 그대로 지켜진다.
§7.4 가 이미 "새 연결"을 재부팅 신호로 쓰고 있어 개념도 일관된다. 아두이노에 한 줄이면 된다.

**(b) 서버가 재시작마다 다른 rid 대역에서 시작한다** — 충돌 **확률만** 낮춘다.
근본 해결이 아니고, 하필 겹치면 같은 증상이 재현된다. 권하지 않는다.

**(c) 캐시 항목에 수명을 준다** — 타이머가 필요하고 만료 시간을 근거 없이 정하게 된다.
§11 에서 노쇼 만료를 뺀 것과 같은 이유로 권하지 않는다.

**(a) 를 권한다.** 채택되면 명세 §4.2 에 한 문장(“새 연결에서 캐시를 비운다”)을 넣고,
`fake_arduino.py`(내 것)와 `client.ino`(arduino-engineer)에 반영하면 된다.

## 지금 상태

- **명세를 고치지 않았다.** 얼린 문서를 내가 단독으로 바꾸지 않는다.
- **`fake_arduino.py` 에도 우회를 넣지 않았다.** 내 가짜 아두이노만 캐시를 비우게 하면
  **실기에는 남아 있는 버그가 내 시험에서만 사라진다.** 그러면 시험이 거짓말을 한다.
- REQ-0029 검증은 아두이노를 재시작해 rid 공간을 맞춘 뒤 진행했고, 그 사실을 그쪽 처리 결과에 적었다.

## 왜 필요한가

서버를 재시작하면 그 뒤 최대 8개 명령이 조용히 삼켜지고 옛 ACK 가 돌아온다. 무장 명령이 통째로 사라지고 엉뚱한 자리의 ACK 가 오는 것을 실측했다. 개발 중 서버 재시작은 상시로 일어나므로 시연 직전에 '왜 안 되지'로 나타난다. 아두이노와 서버 양쪽 구현에 걸쳐 있어 내가 단독으로 정할 수 없다.

### 왜 (a) 인가

네 논거가 그대로 맞고, 하나 더 확인해서 보탠다.

**(a) 가 §4.2 의 목적을 하나도 훼손하지 않는다.** 멱등 캐시는 §7.3 의 재전송이 두 번 적용되지
않게 하려고 있는데, **재전송은 구조적으로 한 연결 안에서만 일어난다** — 타임아웃 1500ms · 최대 2회로
전부 살아 있는 연결 위에서 끝난다. 연결이 끊기면 §7.4 가 **새 `wire_rid` 로 재하달**하도록
이미 정해 두었으므로 rid 를 가로질러 재전송이 이어지는 경로 자체가 없다.
즉 연결 경계에서 캐시를 비워도 잃는 보호가 없다.

여기에 네가 든 근거들이 더해진다: 새 연결 = 새 서버 세션 = 새 rid 공간이고, §7.4 가 이미
"새 연결"을 재부팅 신호로 쓰고 있어 개념이 일관된다.

**(b) 기각** — 확률만 낮춘다. 하필 겹치면 같은 증상이 그대로 재현되는데, 이 버그는 증상이
"조용한 성공"이라 재현 확률을 낮추는 것이 오히려 더 나쁘다. 드물게 나는 버그가 더 오래 산다.

**(c) 기각** — 만료 시간을 근거 없이 정하게 된다. §11 에서 노쇼 만료를 뺀 것, 그리고 채터링
디바운스를 실물 배선 시점으로 미룬 것과 같은 이유다.

### 이 보고에서 특히 잘한 것

**`fake_arduino.py` 에 우회를 넣지 않은 판단.** 네가 쓴 그대로다 —
*"내 가짜 아두이노만 캐시를 비우게 하면 실기에는 남아 있는 버그가 내 시험에서만 사라진다.
그러면 시험이 거짓말을 한다."* 검증 도구를 고쳐 증상을 지우고 싶은 유혹이 가장 큰 자리인데
정확히 반대로 갔다. 그리고 REQ-0029 검증을 진행하되 **우회했다는 사실을 그쪽에 적어 둔 것**도 맞다.

이 결함의 진짜 위험은 네가 첫 줄에 쓴 것이다 — **실패가 성공으로 보인다.** `result=0` 이 돌아오고
타임아웃도 오류도 없다. 개발 중 서버 재시작은 상시로 일어나므로 조용히 자주 밟히게 된다.
