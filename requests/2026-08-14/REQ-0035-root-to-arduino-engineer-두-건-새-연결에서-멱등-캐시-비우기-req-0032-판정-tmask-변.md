# REQ-0035 · 두 건: 새 연결에서 멱등 캐시 비우기(REQ-0032 판정) + tmask 변화 시 즉시 전송

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

## ① 새 TCP 연결에서 멱등 캐시를 비운다 — REQ-0032 판정 (a)

socket-engineer 가 REQ-0029 검증 중 **실측으로 잡은 명세 결함**이다. 전문은 REQ-0032 를 읽어라.

요지: `wire_rid` 는 서버가 발급하고 **서버 재시작 시 1부터 다시 시작한다.** 아두이노는 재부팅하지
않았으므로 §4.2 멱등 캐시가 살아 있어, 새 서버의 rid 1,2,3… 이 옛 세션 것과 충돌해
**전부 "재수신"으로 판정된다.** 최대 8개 명령이 삼켜지고 옛 ACK 가 돌아온다.

**가장 나쁜 점: `result=0` 이라 성공으로 보인다.** 타임아웃도 오류도 없다.
`A1` 에 주입했는데 `A3` ACK 가 오고 브라우저는 "적용됐습니다"를 띄웠다.
예약(`R`/`C`)도 같은 rid 공간이라 테스트 모드만의 문제가 아니다.

**판정 (a): 새 TCP 연결이 맺어지면 멱등 캐시를 비운다.**

근거 — **캐시가 지키려는 것을 하나도 잃지 않는다.** §7.3 재전송은 타임아웃 1500ms · 최대 2회로
**전부 살아 있는 연결 위에서 끝나고**, 연결이 끊기면 §7.4 가 새 `wire_rid` 로 재하달하도록
이미 정해 두었다. rid 를 가로질러 재전송이 이어지는 경로 자체가 없다.
§7.4 가 이미 "새 연결"을 재부팅 신호로 쓰고 있어 개념도 일관된다.

socket-engineer 가 명세 §4.2 와 `fake_arduino.py` 를 맡는다(REQ-0034). 너는 `client.ino` 다.

## ② tmask 변화 시 즉시 전송 — **넣어라**

네 판단 요청을 승인한다. 한 줄이 맞다.

**이유**: 그 1초는 "자기교정되니 괜찮다"로 넘길 수 있는 종류가 아니다. §12A.4 가 무장의 진실을
`tmask` 로 정한 것은 **화면이 무장 사실을 늦게 아는 구간을 없애기 위해서**인데, 지금 구조는
바로 그 구간을 최대 1초 남긴다. 무장 직후 1초 안에 주입하면(사람이 충분히 할 수 있는 속도다)
**주입값이 경고 없이 그려지는 프레임**이 생긴다.

비용은 사실상 0 이다 — 무장·해제·주입은 사람이 누르는 드문 사건이라 전송 횟수가 늘지 않는다.
`changed` 비교에 `tmask` 를 넣어라.

**네가 "내 하네스는 이걸 못 본다"고 밝힌 것이 이 보고에서 가장 값진 부분이다.**
못 보는 것을 아는 채로 적는 것과 안 적는 것은 다르다. 검증은 루트가 맡는다 —
서버·웹이 서면 CDP 하네스로 **토글에서 화면 배너까지 걸리는 시간**을 재겠다.
즉시 전송이 되면 수백 ms, 안 되면 1초 근처로 나온다. 그게 이 한 줄의 유일한 실측 검사다.

## ③ 하네스가 진짜 결함을 잡은 건 — 기록해 둔다

`readSlotSensor()` 가 `testArmed` 를 안 보던 것을 하네스가 잡았고, **해제 상태의 주입값이
`tmask` 없이 전선에 나가는** §12A.6 위반 경로였다. REQ-0027 md 에 "REQ-0030 에서 갱신됨"을
표시해 둔 것도 맞다 — 나중에 REQ-0027 만 읽고 판단하는 사고를 막는다.

내가 REQ-0027 때 하네스를 유지하라고 한 판단의 근거가 이걸로 실증됐다.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

①은 개발 중 서버 재시작마다 밟히는데 증상이 "조용한 성공"이라 원인을 찾기 어렵고, 예약까지 같은 rid 공간이라 테스트 모드에 국한되지 않는다. ②는 무장 직후 1초 안에 주입하면 주입값이 경고 없이 그려지는 프레임이 생기는데, 그 경고가 이 설계 전체의 존재 이유다.

### ① 새 연결에서 캐시 비우기

`CONNECT` 를 받는 자리에서 `cacheClear()` 를 부른다.

```c
// ALREADY CONNECTED 는 기존 연결이 그대로 살아 있다는 뜻 — 새 연결이 아니므로 캐시를 지킨다
if (strstr(s, "ALREADY CONNECT")) { netOnline = true;  return; }
// CONNECT 는 새 TCP 연결 → 서버가 재시작했을 수 있으므로 비운다
if (strcmp(s, "CONNECT") == 0)    { netOnline = true;  cacheClear();  return; }
```

**`ALREADY CONNECTED` 와 `CONNECT` 를 가른 것이 이 변경의 유일한 판단 지점이다.**
`AT+CIPSTART` 를 이미 연결된 상태에서 또 쏘면 ESP-01 은 `ALREADY CONNECTED` 를 돌려준다.
그건 **새 연결이 아니다** — 서버도 그대로다. 여기서 캐시를 비우면 재접속을 시도할 때마다
살아 있는 연결의 멱등성이 깨진다. 우리 `netTick()` 이 CIPSTART 를 5초마다 재시도하므로
실제로 밟히는 경로다. 하네스 [18]-4 가 이걸 지킨다.

`cacheHead`/`cacheCount` 를 0 으로 되돌리는 것뿐이라 비용은 없다.

### ② `tmask` 즉시 전송

```c
uint16_t tmaskNow = testArmed ? ovrActive : TMASK_ABSENT;   // 0xFFFF = 필드 없음
bool changed = (occMask != sentOcc) || (resMask != sentRes) || (tmaskNow != sentTmask);
```

`tmask` 는 10비트뿐이라 `0xFFFF` 를 **"필드 없음(=해제)"** 표식으로 쓸 수 있다 — 어떤 실제 값과도
겹치지 않으므로 "해제 ↔ 무장·오버라이드 없음(`0000000000`)" 전이도 변화로 잡힌다.
이 구분이 없으면 무장했는데 주입이 하나도 없는 경우가 "안 바뀜"으로 새어 나간다.
전송 성공 시에만 `sentTmask` 를 갱신한다(`sentOcc`/`sentRes` 와 같은 규칙 — 못 나간 프레임은 반영하지 않는다).

### 하네스 (기준 5) — **62 PASS / 0 FAIL** (49 → 62)

**[17] `tmask` 즉시 전송 — 판별력을 만들려고 세 가지를 했다.**

1. **모든 칸의 시뮬을 얼렸다**(`freezeAllSims()`). 안 그러면 시뮬이 제멋대로 `occupied` 를 바꿔
   그 때문에 나간 `S` 를 "`tmask` 때문에 나갔다"고 오독한다.
2. **하트비트가 막 나간 직후로 정렬했다**(`alignToHeartbeat()`). ⚠ 이게 없으면 시험이 성립하지 않는다 —
   임의 지점에서 관측 창을 열면 다음 하트비트까지 남은 시간이 [0, 1000) ms 중 아무 값이라,
   하필 창 안에서 하트비트가 터지면 **즉시 전송이 없어도 통과한다.**
   `lastStatusAt` 은 전송할 때마다 리셋되므로 `S` 가 하나 나오는 순간까지 돌리면
   다음 하트비트까지 꼬박 1000 ms 가 남는 지점에 선다.
3. **하트비트 주기보다 짧게만 돌렸다.** 무장 직후 `spin(30)` = **463 ms** 경과 구간에서
   `S` 가 1개 늘었다. 경과 시간을 단언에 넣어 "구간이 정말 짧았는가"까지 검사한다.

해제 방향도 같은 정렬을 거쳐 본다 — `occupied` 는 하나도 안 바뀌는데 `tmask` 필드가 사라지는
프레임이 463 ms 안에 나갔다.

**처음 판본은 2번이 빠져 있었고, 그래서 대략 1/3 확률로 잘못된 이유로 통과했다.**
[2]/[3] 에서 밟았던 것과 같은 종류의 결함이다 — "통과했다"와 "통과할 수밖에 없었다"는 다르다.

**[18] 캐시 비우기 — 같은 rid 에 다른 명령을 태워 구별한다.**

```
1) rid 90 → A3 주입      ACK A,90,A3,0,0A
2) 같은 연결, rid 90 → B2 주입   ACK A,90,A3,0,0A   ← 캐시가 이긴다(멱등 유지, 기준 2)
3) "CONNECT" 수신 후 rid 90 → B2  ACK A,90,B2,0,08   ← 새 명령으로 처리됨(기준 1)
                                   + tmask 비트 6 이 실제로 켜졌다
4) "ALREADY CONNECTED" 후 rid 91 → B1  ACK A,91,A4,0,0C  ← 캐시 유지(비우지 않는다)
```

같은 rid 로 **다른 자리**를 보내는 것이 요점이다. 같은 명령을 두 번 보내면 캐시가 이겼는지
새로 처리했는지 ACK 가 같아서 구별이 안 된다.

**처음 돌렸을 때 [18] 5건이 실패했는데, 원인은 내 테스트였다.** 무장에 `rid 50` 을 재사용했더니
멱등 캐시가 정상 동작해서 무장 명령 자체가 삼켜졌고(→ 뒤이은 주입이 전부 `result=4`),
스케치는 옳게 행동한 것이었다. 새 rid(80)로 바꾸고, 무장이 실제로 걸렸는지 사전 조건으로
단언하도록 고쳤다. 같은 함정을 다음 사람이 밟지 않게 테스트에 주석으로 박아 뒀다.

### 검증하지 않은 것

- ⚠ **실기 검증은 여전히 불가능하다.** 보드가 없다.
- **③ 의 타이밍은 하네스가 못 잰다.** [17] 이 재는 것은 **가상 시각 463 ms** 이고, 가상 시계는
  `millis()` 호출 수에 비례해 흐른다. 즉 이 테스트가 증명하는 것은
  **"하트비트를 기다리지 않고 변화 경로로 나갔다"는 인과**이지 실제 벽시계 지연이 아니다.
  실측은 루트의 CDP 하네스(토글 → 배너까지의 시간) 몫이다. 그렇게 알고 적는다.
- **실제 서버 재시작 시나리오.** [18] 은 `CONNECT` 문자열을 하네스가 직접 밀어 넣은 것이다.
  ESP-01 이 재접속 때 실제로 어떤 문구를 어떤 순서로 올리는지는 실기에서만 확인된다.
  (`CONNECT` 를 단독 줄로 올린다는 전제에 기대고 있다 — 이 전제가 틀리면 캐시가 안 비워진다.)
