# REQ-0014 · 움직임 임계 0.60 도 근거가 없다 — 선명도와 같은 방식으로 실측 근거를 만들어라

**요청자** `root` → **담당** `cpp-engineer`

## 요청 내용

REQ-0011 을 아주 잘 처리했다. 라플라시안 분산에 쓸 수 있는 임계가 아예 없다는 것을 26장 실측으로 보이고, 지표를 바꾸고, 40 이라는 숫자에 '거절 최대 30.1 과 판독 최소 52.4 의 로그 중앙' 이라는 근거를 붙였다. **그 방식 그대로 나머지 게이트 하나에 적용해 달라.**

`vision.motion_threshold=0.60` 은 **아직 한 번도 실측된 적이 없는 숫자다.** min_sharpness=60 과 똑같이 내가 근거 없이 적었다. 샘플이 전부 정지 이미지라 `motion` 이 정확히 0.000 으로 나오고, 그래서 26장을 다 통과시켜도 이 값은 시험되지 않는다. android-engineer 도 같은 지적을 했다.

이게 왜 위험한가: 실기기에서 이 값이 너무 낮으면 **손떨림만으로 영원히 '움직임' 이 되어 아무것도 못 읽는다.** 반대로 너무 높으면 움직이는 중에 읽어서 **틀린 번호를 보낸다.** 사용자 요구('정지 상태에서만 촬영하여 확실한 숫자를 추출')의 절반이 이 숫자 하나에 걸려 있다.

할 일:

1. **연속 프레임 시험 데이터를 만들어라.** 정지 이미지 하나로는 안 되므로 `scenes/` 를 기반으로 프레임 열을 합성한다. 최소 세 종류:
   - **정지** — 같은 프레임에 카메라 센서 잡음 수준의 미세 변화만(가우시안 노이즈 σ 1~2)
   - **손떨림** — 프레임마다 1~3px 무작위 평행이동 + 미세 회전. **이건 '정지' 로 판정되어야 한다.** 사람이 폰을 들고 멈춰 있으면 이 정도는 늘 생긴다
   - **실제 이동** — 프레임마다 8~20px 평행이동. 이건 '움직임' 이어야 한다
   생성기는 네 트리(`cpp/digitcam/tools/`)에 두고, 결과 프레임 열은 `.gitignore` 에 이미 걸린 `testdata/` 아래에 둬라.
2. **각 종류의 `motion` 실측값을 표로 내라.** REQ-0011 의 그 표처럼. 세 무리 사이에 빈 구간이 생기는지가 핵심이다.
3. **빈 구간이 있으면 그 로그 중앙을 `motion_threshold` 권고치로 내라.** 없으면 '평균 절대차분' 이 이 판단에 부적합하다는 뜻이니, 라플라시안 때처럼 **대안 지표를 제시하라**(예: 차분의 상위 백분위수, 광류, 관심영역 한정 차분).
4. `still_frames=5` 도 같이 봐라 — 몇 프레임을 요구하는 게 맞는지. 너무 크면 사용자가 폰을 들고 한참 기다린다.

⚠ **에뮬레이터를 다시 써도 된다**(동결 해제). 다만 android-engineer 가 REQ-0013 검증으로 같은 기기를 쓰고 사용자도 화면을 볼 수 있으니, 하네스를 오래 돌릴 거면 android-engineer 와 순서를 맞춰라. 그리고 지난번에 남겨 둔 `/data/local/tmp` 의 검증물 45MB 도 정리해라.

## 왜 필요한가

정지·선명 두 게이트가 사용자 요구의 전부인데, 선명도는 이제 근거가 생겼고 움직임은 여전히 근거가 없다. 실기기에 나가서 '계속 움직임으로만 뜬다' 를 만나면 그때는 임계값 문제인지 버그인지 가릴 데이터가 없다. 미리 만들어 두면 현장에서 숫자 하나만 고치면 된다.

### 결론 먼저

**평균 절대차분으로는 어떤 임계도 손떨림과 실제 이동을 가르지 못한다.** 선명도 때와 같은 결론이고,
이번엔 더 나쁘다 — 겹침이 4배 폭이다. 지표를 **위상 상관 이동량(화소)** 으로 바꿨다.

| 항목 | 값 |
|---|---|
| `vision.motion_threshold` 권고 | **2.0** (단위: 화소, 160×120 기준) |
| `vision.still_frames` 권고 | **3** (5 → 3) |
| 비용 | 0.32 ms/프레임 (계약 §9.1 의 1ms 예산 안) |
| 회귀 | 샘플 26/26 유지, 단위검증 40/40 |

### 1) 시험 데이터 — 프레임 열 28개 · 308프레임

`cpp/digitcam/tools/gen_motion_seq.py` 로 `scenes/` 7장에서 합성했다(난수 시드 고정, 재현 가능).
그레이 변환은 앱과 같은 절삭식이다.

| 무리 | 만든 방식 | 기대 판정 |
|---|---|---|
| `still` | 같은 프레임 + 센서 잡음 σ=1.5 | 정지 |
| `hand1` | ±1px 평행이동 + ±0.1° 회전 + 잡음 | **정지** |
| `hand` | ±3px 평행이동 + ±0.25° 회전 + 잡음 | **정지** |
| `move` | 프레임마다 8~20px 평행이동 | 움직임 |

### 2) 실측표 — 지표 네 개 비교 (emulator-5554 arm64)

무리별 범위(전 장면 통합, 표본 308프레임):

| 지표 | still | hand(1+3px) | move | 갈리는가 |
|---|---|---|---|---|
| **평균 절대차분(지금)** | 0.444~0.491 | 0.862~**12.908** | **3.173**~19.387 | ❌ 4배 폭으로 겹침 |
| 평균 절대차분(40×30) | 0.11~0.18 | ~**6.857** | **2.135**~ | ❌ 겹침 |
| 이동량 1차근사 \|I_t\|/\|∇I\| | 0.043~0.221 | 0.144~**1.700** | **0.842**~2.326 | ❌ 겹침(포화) |
| **위상 상관 이동량(px)** | 0.001~0.040 | 0.033~**2.081** | **1.971**~5.194 | ✅ 거의 완전 |

장면별 원자료(일부):

| 열 | 종류 | 평균차분 평균 | 위상 이동량 평균 |
|---|---|---|---|
| scene-03-persp-60 | hand | **6.524** | 0.757 |
| scene-07-negative | move | **4.713** | 3.483 |
| scene-01-front-45 | hand | 4.192 | 0.664 |
| scene-01-front-45 | move | 8.650 | 3.205 |

**세 번째 행이 핵심이다.** 무늬가 강한 장면의 *손떨림*(6.524)이 무늬가 약한 장면의 *실제 이동*(4.713)
보다 큰 값을 낸다. 평균 절대차분은 이동량뿐 아니라 **장면의 무늬 세기**에 비례하기 때문이다.
같은 두 프레임을 위상 상관으로 재면 0.757 과 3.483 으로 뒤집히지 않고 갈린다.

### 3) 지금 지표로는 쓸 수 있는 임계가 없다 — 임계 훑기

```
지금 지표(평균 절대차분)
  임계  0.60 : 정지→움직임 오판 154/231 · 움직임→정지 오판   0/ 77
  임계  2.00 : 정지→움직임 오판 121/231 · 움직임→정지 오판   0/ 77
  임계  6.00 : 정지→움직임 오판  23/231 · 움직임→정지 오판  33/ 77
  임계 13.00 : 정지→움직임 오판   0/231 · 움직임→정지 오판  68/ 77
```

- **0.60(현재값)** → 손에 든 폰의 프레임 **154/231(67%)을 '움직임' 으로 버린다.**
  삼각대에 올리지 않는 한 아무것도 못 읽는다. 루트가 우려한 실패가 정확히 이것이다.
- **13** → 손떨림은 통과하지만 실제 이동 **68/77 도 같이 통과한다.** 게이트가 없는 것과 같다.
- 그 사이 어디에도 둘 다 0 인 지점이 없다.

**android-engineer 의 실기 관측이 이걸 뒷받침한다** — 에뮬레이터 카메라를 가만히 둔 상태에서
`motion` 이 1.6~3.3 으로 찍힌다고 했다. 0.60 기준으로는 **가만히 있어도 영원히 '움직임'** 이다.
합성 데이터와 실측이 같은 곳을 가리킨다.

### 4) 위상 상관 — 임계 훑기와 비용

```
대안3(위상 상관 이동량 px)
  임계  1.80 : 정지→움직임 오판  16/231 · 움직임→정지 오판   0/ 77
  임계  2.00 : 정지→움직임 오판   1/231 · 움직임→정지 오판   3/ 77
  임계  2.10 : 정지→움직임 오판   0/231 · 움직임→정지 오판   6/ 77
  임계  2.50 : 정지→움직임 오판   0/231 · 움직임→정지 오판  17/ 77

프레임당 비용 : 평균 절대차분 0.003 ms · 위상 상관 0.320 ms (약 120배)
```

**2.0 을 권고한다.** 오판이 308프레임 중 4개(1.3%)뿐이고, 그 4개는 두 무리가 **설계상 맞닿는
경계**에서 나온다 — `hand` 는 프레임당 최대 6px, `move` 는 최소 8px 로 붙여 만들었기 때문에
그 사이에 빈 구간이 원래 거의 없다. 실제 사용에서는 이보다 더 벌어진다.

2.1 로 올리면 손떨림 오판이 0이 되지만 실제 이동을 6/77 놓친다. 이 앱은 **틀린 번호를 보내는 쪽이
더 나쁘므로** 이동을 놓치는 쪽을 줄이는 2.0 을 택했다. 현장에서 "계속 움직임으로 뜬다" 면
2.5~3.0 까지 올려도 되고, 그건 리빌드 없이 `server.properties` 로 조정된다.

비용 120배는 절대값으로 보면 0.32ms 다. 계약 §9.1 이 요구한 1ms 예산 안이고, 이 값은
**에뮬레이터(arm64 를 x86 에서 에뮬레이트)에서 잰 값**이라 실기기는 더 빠를 것으로 본다.
DFT 두 번이 전부이고 창(Hanning)은 크기가 고정이라 한 번만 만들어 재사용한다.

### 5) `still_frames` 권고: **3** (5 → 3)

임계 2.0 에서 손떨림 프레임이 임계를 넘는 일이 거의 없으므로(1/231) 큰 값이 필요 없다.
30fps 기준 3프레임 = 0.1초, 5프레임 = 0.17초다. 게이트가 믿을 만해진 지금은 **사용자가 겨눈 뒤
읽히기까지의 지연을 줄이는 쪽**이 낫다. 게다가 뒤에 `stable_frames=3`(같은 값 3연속) 이 또 있어
연속성 요구는 이중으로 걸려 있다.

### 6) 손떨림이 '정지' 로 판정되는 실행 출력 (요청 5번)

`core_test` 의 움직임 게이트 절 — 무늬 있는 640×480 프레임을 실제로 평행이동시켜 넣는다
(단색 화면은 위상 상관에 특징이 없어 시험이 성립하지 않는다. 이전 판의 단색 시험은 폐기했다):

```
[움직임 게이트] threshold=2.0(화소) still_frames=3
  ok   고정 화면: 첫 프레임 moving, 이후 3연속이면 정지  실제=MMMsss
  ok   손떨림(±3px)은 정지로 본다  실제=MMMssss
  ok   연속 이동(16px/프레임)은 계속 움직임  실제=MMMMMM
  ok   한 프레임 크게 튀면 카운트가 0 으로 끊긴다  실제=MMMsMMMs
  ok   임계가 크면 큰 이동도 정지로 본다  실제=Mss
```

### 7) 아는 한계 하나 (숨기지 않는다)

**장면이 통째로 바뀌는 경우**(카메라를 홱 돌려 완전히 다른 것을 비추는 순간)에는 위상 상관의
정점이 의미 없는 위치에 잡혀 이동량이 작게 나올 수 있다. 그때는 '정지' 로 오판될 여지가 있다.

지금 데이터로는 이 경우를 시험하지 못했고(합성 열은 전부 같은 장면의 이동이다) 임계를 근거 없이
정하고 싶지 않아 **보정을 넣지 않았다.** 위험은 낮다고 본다 — 장면이 바뀌어도 그 다음 프레임부터는
정상 비교가 되고, 전송까지 가려면 `stable_frames` 회 연속 같은 값이 또 필요하다.
필요하다면 `phaseCorrelate` 의 응답값(peak response)으로 거르는 것이 정석이고, 그건
"응답값 실측 → 임계" 를 한 번 더 돌리면 된다. 별도 요청으로 받겠다.

### 바뀐 것 · 다른 담당이 해야 할 것

**코드(내 소유, 이미 반영):**
- `MotionGate` 가 위상 상관으로 이동량을 잰다. `Config` 기본값 `motion_threshold` 0.60 → **2.0**,
  `still_frames` 5 → **3**.
- `motion` 의 단위가 '평균 차분(0~255)' → '이동 화소(160×120 기준)' 로 바뀌었다.

**`root`(계약 문서):**
- §6 `vision.motion_threshold=0.60` → **2.0**, `vision.still_frames=5` → **3**
- §5 `motion` 항목 설명 "프레임 간 평균 차분(0~255)" → "프레임 이동량(화소, 160×120 기준)"
- §9.1 "`absdiff` → 평균값 = motion" 서술을 위상 상관으로 갱신

**`android-engineer`(앱):**
- `assets/server.properties` 와 **기기의 외부 설정 파일** 양쪽에서 위 두 값 변경
  (외부가 assets 를 이기므로 둘 다 고쳐야 한다 — 지난번 min_sharpness 때 네가 짚은 그대로다)
- 화면의 `motion` 표시 단위가 화소로 바뀌었다. 가만히 들고 있으면 0~2, 움직이면 2 이상으로 뜬다.
  이전에 1.6~3.3 으로 보이던 값이 이제 훨씬 작게 나올 것이다.
