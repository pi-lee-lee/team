# REQ-0039 · WS 가 살아 있는데 폴백 404 를 빨간 오류로 띄운다 — 첫 실행이 고장처럼 보인다

**요청자** `root` → **담당** `web-engineer`

## 요청 내용

## 재현 (루트가 브라우저로 실측)

`data_log.json` 이 없는 상태로 서버를 띄우고 접속했다. 결과:

- 오른쪽 위: **"WebSocket 연결됨"** ← 정상이다
- 알림: **"예비 경로(data_log.json)도 읽지 못했습니다: HTTP 404"** ← 빨간 오류
- 배너: "센서 끊김 (장치 미연결)" ← 이건 맞다(아두이노가 없다)

**사용자가 이걸 "소켓 접속 오류"로 읽었다.** 하필 접속하는 순간에 빨간 것이 떠서 그렇다.

## 원인 — 두 개의 옳은 설계가 만나서 생긴다

- `startPolling()` 이 **WS 접속 전부터** 돈다(1323행 주석: "연결될 때까지는 예비 경로가 화면을 채운다").
  그 판단 자체는 맞다.
- 서버는 상태가 바뀔 때만 `data_log.json` 을 쓴다(§9.4). 아두이노가 없으면 한 번도 안 쓴다.

즉 **갓 띄운 서버의 정상 상태**인데 화면은 오류로 보고한다.

## 고칠 것

**폴백 실패를 오류로 올릴지는 "지금 WS 가 살아 있는가"로 판단해라.**

| 상황 | 지금 | 바꿀 것 |
|---|---|---|
| WS 연결됨 + 폴백 404 | 빨간 오류 | **오류로 띄우지 않는다.** 폴백은 지금 화면을 채우고 있지도 않다 |
| WS 끊김 + 폴백 404 | 빨간 오류 | **그대로 오류** — 이때는 진짜로 화면을 채울 것이 없다 |

**404 를 다른 실패와 구분해라.** 404 는 "파일이 아직 없다"이고 정상 기동 구간에서 나온다.
연결 거부·파싱 실패는 성격이 다르다. 문구도 갈라라 — 404 는 "아직 기록 없음" 쪽이 맞다.

그리고 **빈 배열 `[]` 을 받았을 때 오류로 처리하지 마라.** socket-engineer 가 기동 시
`[]` 로 파일을 만들도록 요청을 냈다(REQ-0038). "기록 0건"은 정상 상태이지 실패가 아니다.
지금 코드가 `[]` 에서 어떻게 되는지 확인하고, 필요하면 같이 고쳐라.

> 서버 쪽 수정만으로는 부족해서 양쪽에 낸다 — 옛 서버를 쓰거나 파일이 지워진 경우가 남는다.

## 판단 기준

이 계열에서 지켜온 원칙 그대로다: **정상 상태를 오류로 보고하면 안 된다.**
문제 없는 첫 실행에서 빨간 것이 뜨면 사용자가 오류 표시 자체를 안 믿게 되고,
그러면 §12A.6 처럼 **정말 봐야 할 경고**도 같이 흘려보낸다.

동시에 반대 방향으로 가지도 마라 — WS 도 죽고 폴백도 못 읽는 상태는 **정말 아무것도 모르는
상태**이고 그건 크게 보여야 한다. "실시간인 척하지 않는다"는 원칙이 여기도 적용된다.

## 검증

브라우저에서 실제로 확인하고 스크린샷과 함께 적어라:

1. `data_log.json` 없는 서버에 접속 → **빨간 오류 없이** WS 연결됨으로 뜬다
2. 서버를 죽여 WS 를 끊고 파일도 없는 상태 → **오류가 뜬다**(이건 진짜다)
3. `[]` 파일이 있는 경우 → 오류 아님, "기록 없음"으로 표시
4. 정상 데이터가 있는 폴백 → 지금처럼 동작(회귀 없음)
5. 기존 기능 회귀 없음 (예약·취소·테스트 모드·센서 끊김 표시)

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

문제 없는 첫 실행에서 빨간 오류가 뜬다. 사용자가 실제로 이것을 소켓 접속 오류로 오해했다. 오류 표시가 정상 상태에서 뜨기 시작하면 사용자가 오류 자체를 믿지 않게 되고, 테스트 모드 경고처럼 정말 봐야 할 것도 흘려보낸다.

## 대상 파일

- `조별과제샘플/index.html`
## 완료 기준

1) WS 가 연결된 상태의 폴백 404 는 빨간 오류로 뜨지 않는다
2) WS 가 끊긴 상태의 폴백 실패는 그대로 오류로 뜬다
3) 404 와 다른 실패(연결 거부·파싱 실패)를 구분하고 문구가 다르다
4) 빈 배열 [] 을 오류로 처리하지 않는다
5) 위 5가지를 브라우저에서 실제로 확인한 스크린샷/판독 결과
확인한 것과 코드 검토만 한 것을 갈라서 적어라.

### 핵심 — 폴백 실패의 의미는 "지금 WS 가 살아 있는가"에 달려 있다

`pollOnce()` 를 결과 **분류**와 **보고**로 갈랐다. 분류는 여섯 가지다:

| 종류 | 언제 |
|---|---|
| `ok` | §9.1 배열에서 스냅샷을 만들었다 |
| `missing` | HTTP 404 — 파일이 아직 없다 |
| `empty` | 유효한 배열인데 항목이 0건 |
| `parse` | JSON 이 아니거나 최상위가 배열이 아니거나 §9.1 형태가 아님 |
| `http` | 404 아닌 HTTP 실패 |
| `network` | fetch 자체 실패(연결 거부 등) |

`res.json()` 을 버리고 `res.text()` + `JSON.parse()` 로 바꿨다. `res.json()` 을 쓰면
**"파일 없음"과 "형식이 깨짐"이 같은 예외로 합쳐져** 문구를 가를 수가 없다.

보고 규칙:

| | WS 살아 있음 | WS 끊김 |
|---|---|---|
| `missing`(404) | **아무 말도 안 한다** | 빨간 오류 "서버와 끊겼고 예비 파일(data_log.json)도 아직 없습니다 — 지금 표시할 상태가 없습니다" |
| `empty`(`[]`) | **아무 말도 안 한다** | 빨간 오류 "서버와 끊겼고 예비 기록이 0건입니다 — …" |
| `parse` | 파란 안내 "예비 경로에 문제가 있습니다: … — 지금은 WebSocket 으로 받고 있어 **화면에는 영향이 없습니다**" | 빨간 오류 "예비 파일을 해석할 수 없습니다: …" |
| `http`/`network` | 파란 안내(위와 같음) | 빨간 오류 "예비 경로를 읽지 못했습니다: …" |

`[]` 은 이제 **어느 경우에도 파싱 실패로 취급하지 않는다.** 전에는 `snapshotFromLog()` 가
`null` 을 돌려주고 그걸 `throw '빈 로그'` 로 받아 빨간 오류가 됐다(REQ-0038 이 기동 시 `[]` 를
만들면 **매번 첫 화면에 빨간 것이 떴을 것**이다).

### 검증하다가 잡은 두 가지 — 코드만 봤으면 못 봤다

**(1) 재연결마다 같은 오류가 다시 뜬다.** 첫 구현은 "WS 가 끊기면 다시 판단하게" 하려고
`onclose` 에서 억제 플래그를 지웠다. 그런데 `onclose` 는 **재연결 시도가 실패할 때마다** 불린다
→ 12초 동안 같은 빨간 줄이 반복됐다(실제로 두 번 찍힌 스크린샷을 보고 알았다).
억제 열쇠를 `연결상태:종류`(`down:missing` 등) 복합키로 바꿔 해결했다. 상태가 진짜로 바뀌면
열쇠가 달라져 한 번 더 알리고, 재시도 실패가 반복돼도 열쇠가 같아 다시 뜨지 않는다.

**(2) 첫 폴링이 WS 핸드셰이크를 이기면 시작하자마자 빨간 것이 뜬다.** `startPolling()` 이
`connect()` 보다 먼저 돌기 때문에, 404 응답이 WS `onopen` 보다 빨리 오면 그 순간 `link` 는 아직
`'connecting'` 이다. 루트가 본 증상이 바로 이 창에서 나온다.
→ `link === 'connecting'` 이면 **판단을 미룬다**(아직 폴백이 필요한 상황인지 모르는 시점이다).
3초 뒤 다음 폴링에서는 `ws` 또는 `reconnecting` 으로 정해져 있다.
WS 응답을 1200ms 늦춰 404 가 확실히 먼저 오게 만든 뒤에도 빨간 것이 뜨지 않는 것을 확인했다.

### 요청 범위 밖이지만 같은 결함이라 함께 고친 것 ⚠

검증 중 **정상 데이터가 있는 폴백**에서 이 배너를 봤다:

> ⚠ 센서 끊김(추정) — 파일의 마지막 기록이 오래되었습니다

파일 기록이 22초 전 것이었을 뿐인데 **고장을 추정해서 말하고 있었다.**
§9.4 는 서버가 **상태가 바뀔 때만** 파일을 쓴다고 정한다 — 차가 드나들지 않는 주차장에서는
몇 분 된 기록이 **정상**이다. 파일 나이로 장치 고장을 추정하는 것은 근거가 없다.
이 REQ 가 고치라는 것과 정확히 같은 결함(정상 상태를 고장으로 보고)이라 함께 고쳤다:

> 이 값은 파일에 기록된 2분 전 상태입니다. 서버는 상태가 바뀔 때만 기록하므로(§9.4)
> 오래된 것 자체가 고장은 아닙니다 — 다만 실시간은 아닙니다.

빨간 경고에서 **중립 안내(`banner--note`)** 로 낮췄다. "실시간이 아니다"는 계속 말하되
진단은 하지 않는다. 장치가 진짜로 끊긴 경우(`device.online === false`)의 빨간 배너는 그대로다.

### 브라우저에서 실제로 확인한 것 (Google Chrome 151.0.7922.109 headless)

이번에는 **실제 HTTP 서버**를 띄워 확인했다. `python3 -m http.server` 로 픽스처 디렉터리를
서빙하고 브라우저가 진짜 `fetch` 로 진짜 404 / `[]` / 깨진 JSON / 정상 데이터를 받게 했다.
파일 픽스처는 내 소유 경로(`public/**`)에 두었다 — `.json` 은 내 확장자가 아니지만 경로가 확장자를
이기므로 그 자리가 규칙에 맞는 유일한 위치다. 검증 후 정리했다(빈 디렉터리 하나는 REQ-0040).

| # | 상황 | 결과 |
|---|---|---|
| 1 | WS 연결됨 + **실제 404** | 빨간 것 없음. 알림은 초록 "서버에 연결되었습니다" 하나 |
| 2 | WS 연결이 1200ms 늦음 + 404 가 먼저 도착 | 빨간 것 없음 (순서 경쟁 방어 확인) |
| 3 | WS 끊김 + 404, **12초 관찰** | 빨간 오류 **정확히 한 번**, 재연결 3회에도 반복 없음 |
| 4 | WS 연결됨 + `[]` | 아무 메시지 없음 |
| 5 | WS 끊김 + `[]` | 빨간 오류 "예비 기록이 0건입니다" (404 문구와 다름) |
| 6 | WS 끊김 + 깨진 JSON | 빨간 오류 "해석할 수 없습니다: JSON 으로 읽히지 않습니다" |
| 7 | WS 연결됨 + 깨진 JSON | **파란 안내** "…화면에는 영향이 없습니다" |
| 8 | WS 끊김 + 정상 데이터 | 격자가 파일 값으로 그려지고 **오류 0건**, 나이 안내는 중립 문구 |
| 9 | 회귀: 예약(요청됨→확정→입차 완료·내 예약) | 이상 없음 |
| 10 | 회귀: 테스트 모드 무장 + 주입 + 장치 끊김 | 두 배너 스타일 그대로(빨강/빗금), 주입 표시 유지 |

**WS 를 어떻게 "살아 있게" 만들었나**: 서버(9900)가 아직 없어 `WebSocket` 만 가짜로 바꿨다.
앱 코드는 손대지 않았고 `link='ws'` 는 **앱이 자기 `onopen` 으로 스스로 정한다.**
`data_log.json` 요청은 진짜 HTTP 로 나간다 — 즉 **판단 분기와 fetch 경로는 모두 실물**이고
가짜인 것은 소켓 하나뿐이다. 그 하네스는 검증 사본에만 있고 배포 파일에는 없다.

### 확인하지 **못한** 것

- **실제 `server.cpp` 와의 WebSocket 왕복.** 위 1·2·4·7 의 "WS 연결됨"은 가짜 소켓으로 만든 것이다.
  진짜 서버가 서면 다시 확인해야 한다. 3·5·6·8(WS 끊김 쪽)은 소켓도 진짜로 죽어 있는 상태였다.
- 404 아닌 HTTP 실패(5xx)와 `network` 분기는 **코드 검토만** 했다. `http.server` 로 5xx 를
  만들 방법이 없었다. 두 경우 모두 `parse` 와 같은 보고 경로를 타므로 7번이 그 경로를 대신 확인한다.
