# REQ-0021 · 검토 전용: server.cpp 의 Windows 분기(#ifdef _WIN32)를 눈으로 검증하라 — 이 팀에서 컴파일이 불가능하다

**요청자** `root` → **담당** `cpp-engineer`

## 요청 내용

## 이건 검토 요청이다 — 파일을 고치지 마라

**`조별과제샘플/server.cpp` 는 socket-engineer 소유다.** 훅이 네 편집을 막을 것이고 그게 맞다.
너는 **읽고 결함 목록만 만든다.** 고치는 것은 socket-engineer 다.
발견한 것을 이 요청의 처리 결과에 적으면 루트가 socket-engineer 에게 수정 요청을 발행한다.

## 왜 너에게 오는가

socket-engineer 가 REQ-0017 로 이 서버를 크로스 플랫폼으로 재작성했다.
macOS/POSIX 경로는 **실행 검증 8/8 을 통과**했고 루트가 독립 재현까지 마쳤다.

그런데 **Windows 분기는 컴파일조차 해 보지 못했다.** macOS 에 그 헤더가 없다.
이 데모의 원본이 Winsock 이었으므로 **실제 제출·시연 환경이 Windows 일 가능성이 높다.**
즉 지금 유일하게 검증되지 않은 경로가 하필 가장 중요한 실행 환경이다.

컴파일러가 못 잡아 주므로 **사람이 읽어서 잡는 수밖에 없다.** C/C++ 전문가인 네가 적임이다.

## 봐야 할 것

**1) Winsock API 시그니처와 타입**
- `WSAStartup`/`WSACleanup` 호출과 실패 처리
- `SOCKET` vs `int`, `INVALID_SOCKET` vs `-1`, `closesocket` vs `close`
- `setsockopt` 의 옵션값 타입 — 윈도우는 `const char*`, POSIX 는 `const void*`
- `send`/`recv` 의 길이 인자 타입 (`int` vs `size_t`)
- `accept` 의 주소 길이 인자 — 윈도우 `int*`, POSIX `socklen_t*`
- `select` 의 첫 인자(nfds)는 윈도우에서 무시되지만 POSIX 에선 필수
- 논블로킹 전환: `ioctlsocket` vs `fcntl(O_NONBLOCK)`
- 에러 코드: `WSAGetLastError()`/`WSAEWOULDBLOCK` vs `errno`/`EAGAIN`·`EWOULDBLOCK`
  (POSIX 에서 이 둘이 같은 값일 수도 다를 수도 있다 — 둘 다 검사하는지 봐라)

**2) 원자적 파일 교체 — 명세 §9.3**
`MoveFileExA("data_log.json.tmp","data_log.json", MOVEFILE_REPLACE_EXISTING)` 가
- 올바른 헤더(`<windows.h>`)와 함께 있는지
- 반환값(BOOL)을 검사하는지
- "먼저 지우고 rename" 으로 흉내내지 않았는지 (그 틈에 읽은 클라이언트가 404 를 받는다)
- POSIX 쪽 `rename()` 과 동작이 실제로 같은지

**3) 시간 함수**
`GetTickCount64()` 는 `<windows.h>` 가 필요하고 `ULONGLONG` 을 돌려준다.
POSIX 쪽과 **단위(ms/s)가 같은지** 확인해라. 여기가 어긋나면 ACK 타임아웃 1500ms 와
하트비트 3.5초 판정이 윈도우에서만 엉뚱하게 돈다 — 그리고 그건 증상이 아주 헷갈린다.

**4) 헤더 가드와 매크로 충돌**
- `<windows.h>` 가 `min`/`max` 매크로를 정의해서 `std::min`/`std::max` 를 깨뜨리는 고전적 문제.
  `NOMINMAX` 를 정의했는지, 아니면 `(std::min)(...)` 로 감쌌는지
- `winsock2.h` 를 `windows.h` **보다 먼저** include 했는지 (순서가 바뀌면 `winsock.h` 와 충돌한다)
- POSIX 전용 헤더가 `#ifdef` 밖에 새어 나와 있지 않은지

**5) 그 밖에 눈에 걸리는 것**
크로스 플랫폼과 무관해도 실제 결함이면 적어라. 다만 취향 차이는 적지 마라 —
"내가 다르게 짰을 것 같다"와 "이건 틀렸다"는 다르다.

## 판정 근거를 붙여라

각 지적에 **줄 번호와, 왜 윈도우에서 문제가 되는지**를 적어라.
확신이 없으면 "확실"과 "의심"을 구분해서 표시해라 — 확신 없는 지적을 확신처럼 적으면
socket-engineer 가 멀쩡한 코드를 고치게 된다.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

Windows 분기는 이 팀의 어떤 머신에서도 컴파일할 수 없어 자동 검증이 불가능하다. 원본이 Winsock 전용이었으므로 실제 제출 환경은 Windows 일 가능성이 높고, 그 경로에 오타 하나만 있어도 사용자는 서버를 아예 띄우지 못한다. 컴파일러가 못 잡는 것을 사람이 잡는 수밖에 없고, 작성자 본인보다 제3자가 잡을 확률이 높다.

## 지적 목록

### ■ 확실 1 — 소스가 UTF-8 인데 `/utf-8` 도 BOM 도 없다 → 한글이 깨진다 (줄 11, 339~342, 431, 536, 544)

파일 첫 3바이트가 `2f 2f 20`(`// `)로 **BOM 이 없다**(`xxd` 확인). 그런데 줄 11 의 빌드 명령은

```
cl /EHsc /std:c++14 server.cpp ws2_32.lib
```

로 `/utf-8` 이 없다. MSVC 는 BOM 없는 소스를 **시스템 ANSI 코드페이지**로 해석한다. 한국어 윈도우면
CP949 다. 그러면 UTF-8 로 저장된 한글 리터럴이 CP949 로 재해석되어 그대로 깨진다:

| 줄 | 리터럴 | 어디로 나가는가 |
|---|---|---|
| 339~342 | `"예약되었습니다"` `"이미 주차된 자리입니다"` … | `send_ack` → WS JSON → **브라우저 화면** |
| 431 | `"센서가 응답하지 않습니다"` | `send_err` → 브라우저 |
| 536, 544 | `"알 수 없는 요청입니다"` `"센서가 연결되어 있지 않습니다"` | 브라우저 |

시연 화면의 안내 문구가 통째로 깨진다. **컴파일은 되므로 아무도 못 잡고 시연장에서 처음 보인다.**

- **의심(같은 원인, 더 나쁜 증상)**: CP949 의 트레일 바이트 범위에는 `0x5C`(`\`)가 포함된다.
  한글 주석의 UTF-8 바이트가 CP949 로 재해석되다가 줄 끝이 `0x5C` 로 끝나면 그 주석이 **다음 줄을
  집어삼킨다**(줄 연속). 이 파일은 주석이 거의 전부 한글이라 표본이 많다. 실제로 터질지는 바이트
  조합에 달렸고 여기서는 확인할 수 없다. 터지면 `C2001`/`C2143` 같은 엉뚱한 에러로 나타난다.
- **고치는 법**: 빌드 명령에 `/utf-8` 추가(줄 11 주석도 같이), 또는 파일을 UTF-8 with BOM 으로 저장.
  전자가 낫다 — BOM 은 POSIX 쪽 도구를 성가시게 한다.

### ■ 확실 2 — `<ctime>`/`<time.h>` 를 include 하지 않는다 (줄 174~175)

```cpp
174:    time_t tt = (time_t)t;
175:    char ts[16]; strftime(ts, sizeof(ts), "%H:%M:%S", localtime(&tt));
```

`time_t`·`strftime`·`localtime` 은 `<ctime>`(또는 `<time.h>`)이 있어야 한다. 그런데 이 파일의
include 목록(19~28) 어디에도 없다. **POSIX 는 줄 43 의 `<sys/time.h>` 가 `<time.h>` 를 끌어와
우연히 통과한다** — 그래서 macOS 빌드가 조용히 성공한 것이다. 그 include 는 `#else` 안에 있으므로
Windows 분기에는 없다.

- 표준상 명백한 누락이라는 점은 **확실**하다.
- 다만 MSVC 에서 실제로 빌드가 깨지는지는 **의심**으로 둔다. `<windows.h>` 나 `<iostream>` 계열이
  `<time.h>` 를 전이적으로 끌어올 수 있고, 그건 SDK·MSVC 버전에 따라 갈린다. 즉 **어떤 머신에서는
  되고 어떤 머신에서는 `C3861: 'strftime': 식별자를 찾을 수 없습니다` 로 죽는다.** 제출 환경이
  어느 쪽인지 모르는 상태로 두면 안 되는 종류의 의존이다.
- **고치는 법**: 파일 상단 공통 include 에 `#include <ctime>` 한 줄.

### ■ 의심 1 — `FD_SETSIZE` 가 윈도우에선 64 다 (줄 692~700)

`fd_set` 에 리스너 2 + 아두이노 1 + `conns` 전부를 넣는다. POSIX 의 `FD_SETSIZE` 는 1024 지만
**윈도우는 기본 64** 다. 그리고 윈도우 `FD_SET` 은 배열이 꽉 차면 **조용히 무시한다**(에러도 없다).
64 를 넘는 순간 그 소켓은 영원히 읽기 준비 상태가 되지 않아 **그 브라우저만 멈춘 것처럼 보인다.**

실제로 터질 확률은 낮다고 본다 — 정적 응답이 `Connection: close` 라(줄 595, 625) 동시 연결이
쌓이지 않는다. 다만 브라우저는 호스트당 6개까지 병렬로 열고 WS 는 계속 붙어 있으므로,
시연 중 여러 대가 붙으면 닿을 수 있는 숫자다. 필요하면 `<winsock2.h>` **앞에**
`#define FD_SETSIZE 256` 을 두면 된다(순서가 바뀌면 효과가 없다).

### ■ 의심 2 — `MoveFileExA` 실패 시 원인을 알 수 없다 (줄 395~402)

요청서가 지목한 네 가지는 **전부 맞게 돼 있다**:

| 확인 항목 | 결과 |
|---|---|
| `<windows.h>` 와 함께 있는가 | ✅ 줄 34 |
| 반환값(BOOL) 검사 | ✅ `if (!MoveFileExA(...))` |
| "먼저 지우고 rename" 흉내 | ✅ 아님. `MOVEFILE_REPLACE_EXISTING` 한 번으로 처리 |
| POSIX `rename()` 과 동등한가 | ✅ 같은 디렉터리(같은 볼륨)라 원자적 교체로 동작한다 |

남는 문제는 **실패했을 때다.** 윈도우에서 `MoveFileEx` 는 대상 파일을 **다른 프로세스가 열고 있으면
공유 위반으로 실패한다**(POSIX `rename()` 은 열려 있어도 성공한다). 이 서버는 단일 스레드라
자기 자신의 `serve_file`(줄 578)과 겹칠 일은 없지만, **백신 실시간 검사·편집기·동기화 클라이언트**가
`data_log.json` 을 잠깐 잡는 것은 윈도우에서 흔하다.

그때 이 코드는 `logf("!", "MoveFileEx 실패")` 만 남기고 넘어간다. `GetLastError()` 를 안 찍으므로
`ERROR_SHARING_VIOLATION(32)` 인지 `ERROR_ACCESS_DENIED(5)` 인지 알 수 없고, `data_log.json` 은
**조용히 옛 내용을 유지한다.** 로그 메시지에 오류 코드를 붙이는 것만으로 진단이 가능해진다.
(POSIX 쪽 `rename` 실패 로그도 `errno` 를 안 찍는 건 마찬가지다.)

### ■ 의심 3 — `size_t` → `int` 축소 경고 (줄 673, 726, 758)

윈도우의 `bind`/`recv` 는 길이 인자가 `int` 다. `sizeof(a)`·`sizeof(b)` 는 `size_t` 이므로 x64 빌드에서
`C4267: 'size_t'에서 'int'로 변환하면서 데이터가 손실될 수 있습니다` 경고가 뜬다. **값이 전부 작은
상수라 실제 손실은 없다.** 경고를 없애려면 명시적 `(int)` 캐스트를 붙이면 된다. 기능 결함은 아니다.

## 요청서가 지목한 영역별 확인 (문제 없는 것도 명시한다)

### 1) Winsock API 시그니처와 타입 — **확인함, 문제 없음**

| 항목 | 줄 | 판정 |
|---|---|---|
| `WSAStartup`/`WSACleanup` | 809~811, 818~820 | ✅ `MAKEWORD(2,2)`, 실패 시 return 1. `WSACleanup` 은 `run()` 이 무한 루프라 실질적으로 도달하지 않지만 프로세스 종료가 정리하므로 결함 아님 |
| `SOCKET` vs `int` | 36, 50 | ✅ `sock_t` 로 추상화 |
| `INVALID_SOCKET` vs `-1` | 37, 51 | ✅ `BAD_SOCK` 로 통일, 비교도 전부 `== BAD_SOCK` |
| `closesocket` vs `close` | 38, 52 | ✅ |
| `setsockopt` 옵션 타입 | 670 | ✅ `(const char*)&opt` — 윈도우가 요구하는 형태이고 POSIX 의 `const void*` 는 이걸 그대로 받는다. **양쪽 다 맞는 유일한 형태다** |
| `send` 길이 타입 | 261~266 | ✅ `#ifdef` 로 갈라 `(int)` 캐스트 |
| `accept` 주소 길이 | 710, 721 | ✅ `NULL, NULL` 이라 `int*`/`socklen_t*` 문제가 아예 없다 |
| `select` 첫 인자 | 704 | ✅ `(int)mx + 1`. 윈도우는 무시하고 POSIX 는 올바른 값 |
| 논블로킹 전환 | — | ✅ **쓰지 않는다.** `select` 로 준비된 fd 에만 `recv` 를 한 번씩 하므로 블로킹 소켓으로 충분하다. `ioctlsocket`/`fcntl` 이 필요 없는 설계다 |
| 에러 코드 | 39, 53, 674 | ✅ `sockerr()` 로 갈랐고, 쓰는 곳은 bind 실패 로그 한 곳뿐. 논블로킹을 안 쓰므로 `EAGAIN`/`WSAEWOULDBLOCK` 분기 자체가 없다 |

`send_raw`(258~270)가 `w <= 0` 을 전부 "포기"로 처리하는 것은 블로킹 소켓 전제에서 맞다.

### 2) 원자적 파일 교체 — **확인함, 구현은 맞음** (진단 로그만 위 의심 2)

### 3) 시간 함수 — **확인함, 단위 일치. 다만 원점이 다르다는 점을 적어 둔다**

- `GetTickCount64()`(156)는 `<windows.h>` 로 선언되고 **ms** 를 돌려준다. POSIX(158~159)도 ms.
  **단위는 일치한다.** ACK 타임아웃 1500ms·오프라인 3500ms 판정이 윈도우에서만 어긋날 일은 없다.
- `epoch_ms()`(162~171)도 양쪽 ms 이고 윈도우 쪽 FILETIME→Unix epoch 변환 상수
  `116444736000000000` 과 `/10000` 이 **정확하다**.
- ⚠ **주의(현재는 결함 아님)**: 윈도우에서 `now_ms()` 는 **부팅 후 경과 ms**(단조), `epoch_ms()` 는
  **Unix epoch ms** 로 원점이 다르다. POSIX 에서는 둘이 같은 값이라 **섞어 써도 티가 안 난다.**
  지금 코드는 섞지 않는다 — 확인했다:
  `ard_last_ms`(469)↔`device_online`(250), `sent_ms`(413)↔`tick`(424) 모두 `now_ms` 끼리,
  `reserved_at`(492)·스냅샷 `ts`(313)·로그 `ts`(363)는 전부 `epoch_ms`.
  다만 나중에 누가 `reserved_at` 과 `now_ms()` 를 빼는 코드를 넣으면 **윈도우에서만** 40년짜리 값이
  나온다. 두 함수 이름이 비슷해서 실수하기 쉬우니 주석 한 줄을 붙여 두는 편이 안전하다.

### 4) 헤더 가드와 매크로 충돌 — **확인함, 문제 없음**

- `winsock2.h`(32) → `ws2tcpip.h`(33) → `windows.h`(34) **순서가 맞다.** 이게 뒤집히면
  `windows.h` 가 옛 `winsock.h` 를 끌어와 `sockaddr_in` 재정의 충돌이 난다. 제대로 돼 있다.
- `NOMINMAX` 는 정의돼 있지 않지만 **이 파일은 `std::min`/`std::max` 를 쓰지 않는다**(grep 확인).
  지금은 무해하다. 나중에 누가 쓰면 그때 윈도우에서만 깨진다 — 예방적으로 `#define NOMINMAX` 를
  `<windows.h>` 앞에 두는 것을 권한다(비용 0).
- POSIX 전용 헤더(41~49)는 전부 `#else` 안에 있다. **밖으로 샌 것 없다.**
  단, 위 확실 2 처럼 **헤더가 아니라 의존이 샜다** — `<sys/time.h>` 가 덤으로 주던 `<time.h>` 를
  공통 코드가 쓰고 있다.
- `#pragma comment(lib, "ws2_32.lib")`(35)은 MSVC 전용이다. 줄 11 의 `cl` 빌드와 맞으므로 문제
  없지만, MinGW/clang 으로 빌드하면 무시되므로 `-lws2_32` 가 따로 필요하다(정보).

## 그 밖에 눈에 걸린 것 (플랫폼 무관, 실제 결함)

### ● WS 프레임 길이에 상한이 없다 (줄 634~646) — 확실(기전) / 의심(실효 위험)

클라이언트가 보낸 길이를 그대로 믿는다. `len = 127` 경로에서 64비트 길이를 받아
`if (c.inbuf.size() < off + 4 + len) return true;` 로 **데이터가 다 올 때까지 기다린다.**
악의적 클라이언트가 "4GB 프레임" 이라고 선언하고 조금씩 흘려보내면 `c.inbuf` 가 **무한히 커진다**
(연결당 메모리 고갈). 산술 오버플로는 없다 — `off+4+len` 이 64비트로 계산되므로 32비트 빌드에서도
검사가 뚫리지는 않는다. 그 점은 안전하다.
데모 환경에서 실제 위험은 낮지만, 상한 한 줄(`if (len > 64*1024) return false;`)이면 끝난다.

### ● `user_id` 길이를 검증하지 않는다 (줄 532, 417) — 확실

`on_ws_message` 가 브라우저 JSON 의 `user_id` 를 길이 검사 없이 받아 `dispatch` 로 넘기고,
`snprintf(buf, 64, "R,%u,%s,%s,", ...)` 로 조립한다. `snprintf` 라 **메모리 안전 문제는 없다**(잘린다).
다만 잘린 뒤 체크섬이 붙으므로 **형식상 유효하지만 내용이 잘린 라인**이 나가고, 명세 §2.1 의
64B 상한도 넘을 수 있다(63B + 체크섬 2B + LF). 아두이노가 거절 → 재전송 3회 → `ack_timeout` 으로
끝나서 증상이 "가끔 예약이 안 된다" 로 보인다. `slot` 은 `slot_index` 로 검증하는데(539) `user_id` 만
빠져 있다.

### ● 연속 프레임(opcode 0x0)을 조용히 버린다 (줄 655~661) — 의심(실효 낮음)

`0x8`(close)·`0x9`(ping)·`0x1`(text)만 처리하고 continuation 은 무시한다. 브라우저가 작은 JSON 을
쪼갤 일은 없어서 실제로 문제될 확률은 낮다. 적어만 둔다.

## 정리

**빌드를 막을 수 있는 것**: 확실 2(`<ctime>`), 확실 1의 의심 갈래(주석 파싱).
**빌드는 되는데 시연에서 보이는 것**: 확실 1(한글 깨짐) — 이게 가장 확률이 높고 눈에 띄는 결함이다.
**조용히 잘못 도는 것**: 의심 1(FD_SETSIZE 64), 의심 2(MoveFileEx 실패 무시).

Winsock 시그니처·타입·헤더 순서·시간 단위·원자적 교체 로직 자체는 **읽은 범위에서 정확하다.**
`#ifdef` 로 갈라야 할 곳(send 길이 타입, closesock, 에러 코드, 시간)은 빠짐없이 갈려 있고,
`setsockopt` 의 `(const char*)` 처럼 양쪽 모두 만족하는 형태를 고른 것도 맞다.
고쳐야 할 것은 대부분 **빌드 설정 한 줄과 include 한 줄**이다.

수정은 socket-engineer 몫이다. 파일은 건드리지 않았다.
