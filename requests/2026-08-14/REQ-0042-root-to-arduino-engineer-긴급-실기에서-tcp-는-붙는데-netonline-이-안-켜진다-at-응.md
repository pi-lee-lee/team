# REQ-0042 · 긴급: 실기에서 TCP 는 붙는데 netOnline 이 안 켜진다 — AT 응답 전부를 찍게 만들어라

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

## 실기 증상 (사용자 보고 · 윈도우 서버)

```
서버:    14:47:44  +ARD 아두이노 접속          ← 딱 한 번
         14:47:44  ⟳ 재부팅 감지(새 연결) — 살아 있는 예약 0건 재하달
         이후: +WS 업그레이드 완료 만 반복       ← ←ARD 프레임이 하나도 없다
아두이노: 배너 이후 아무 로그 없음
웹:      "장치가 연결되어 있지 않습니다"
```

**`+ARD` 가 찍혔다 = ESP 가 TCP 접속에 성공했다.** 그런데 아두이노는 `S` 를 한 장도 안 보낸다.
`statusTick()` 이 `if (!netOnline || ...) return;` 로 빠지는 것이고, 즉 **`netOnline` 이 false 로 남아 있다.**
`[TX]`/`[TX-DROP]` 도 없으니 `sendStatus()` 자체가 호출되지 않는다.

정리하면 **Uno→ESP 방향은 정상**(명령이 먹혀서 접속됐다), **ESP→Uno 응답을 못 읽거나 못 알아본다.**

## 유력한 가설 — 옛 원본과의 판정 차이

| | 접속 판정 |
|---|---|
| 옛 원본(현장에서 붙는다) | 원시 스트림에서 **`CONNECT` 부분문자열** 검색 — `WIFI CONNECTED` 안의 것도 걸린다 |
| 지금(694~695행) | `strncmp(s,"WIFI",4)==0` 이면 **먼저 return**, 그다음 `strcmp(s,"CONNECT")==0` **정확일치** |

옛 코드는 `WIFI CONNECTED` 를 TCP 접속으로 **오인**해서 online 이 됐고, 그 시점엔 CIPSTART 도
성공해 있어 결과적으로 동작했을 수 있다. 우리는 그 오인을 일부러 고쳤는데, **이 모듈이 정확한
`CONNECT` 줄을 내지 않으면**(예: 구형 AT 펌웨어의 `Linked`, 또는 다른 형태) 새 코드는 영원히 오프라인이다.

**다만 이건 가설이다. 루트가 이미 두 번 틀렸다(핀·타이밍·CR·전원 전부 아니었다).
추측으로 고치지 말고 먼저 보이게 만들어라.**

## 1순위 — 모든 AT 줄을 찍어라 (이게 이 요청의 핵심)

지금 `[AT]` 출력은 **`WIFI` 로 시작하는 줄에만** 걸려 있다(667~672행). 그래서 모듈이 무엇을
내는지 아무도 모른다. **`handleLine()` 진입 지점에서 받은 줄을 전부 찍어라.**

- `DEBUG` 로 감싸되 기본은 켬. 현장 진단이 목적이다.
- **보이지 않는 문자가 문제일 수 있으므로** 길이도 같이 찍어라 — 예: `[AT] "CONNECT" (7)`.
  눈으로는 같아 보여도 뒤에 공백이나 다른 바이트가 붙어 있으면 정확일치가 깨진다.
- 버려지는 줄(체크섬 불일치·과대길이·오버플로)도 **버렸다는 사실이 보여야 한다.**
  지금은 조용히 사라져서 "아무 로그 없음"과 구분이 안 된다.

## 2순위 — 판정을 넓히되 옛 버그를 되살리지 마라

`WIFI CONNECTED` 를 TCP 접속으로 보는 것은 **틀린 동작이다.** 그 제외는 유지해라.
그 위에서 알려진 변형을 받아들여라:

- `CONNECT` (정확일치) — 지금대로
- `ALREADY CONNECT...` — 지금대로
- **`Linked`** — 구형 AT 펌웨어의 접속 성공 응답
- 앞뒤 공백이나 `0,` 같은 접두가 붙어 오는 경우

**어떤 변형을 넣었는지와 근거를 처리 결과에 적어라.** 로그가 오면 그중 무엇이었는지 확정한다.

## 3순위 — 상태 기계가 어디까지 갔는지 보여라

`netSendStep()` 이 명령을 보낼 때마다 무엇을 보냈는지 한 줄 찍어라(`[NET] 4 CIPSTART` 정도).
지금은 5초마다 CIPSTART 를 재시도하는지조차 로그로 확인할 수 없다.

## 하지 말 것

- **타이밍·핀·보율을 바꾸지 마라.** 전부 확인했고 원인이 아니다. TCP 가 붙은 것이 증거다.
- 옛 원본의 부분문자열 스캔으로 되돌리지 마라 — `WIFI CONNECTED` 오인이 되살아난다.

## 검증

실기는 사용자만 할 수 있다. 네 하네스로는:
- 모든 줄이 찍히는지 (기존 케이스 회귀 없이)
- 넣은 변형들이 각각 `netOnline` 을 켜는지
- `WIFI CONNECTED` 는 **여전히 안 켜는지** ← 이게 회귀 방지의 핵심
- 컴파일 통과 + 플래시/RAM

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

실기에서 TCP 는 붙는데 프레임이 안 나간다. 원인을 좁히려면 모듈이 실제로 무엇을 응답하는지 봐야 하는데, 지금 스케치는 WIFI 로 시작하는 줄만 찍어서 현장 진단이 불가능하다. 루트가 코드만 보고 세 번 추측했고 전부 빗나갔다 — 관측 가능하게 만드는 것이 먼저다.

## 완료 기준

1) handleLine() 이 받은 모든 줄을 길이와 함께 찍는다
2) 버려지는 줄도 버렸다는 사실이 로그에 남는다
3) netSendStep() 이 보낸 단계를 찍는다
4) CONNECT 변형(Linked 등)을 받아들이고 무엇을 왜 넣었는지 적었다
5) WIFI CONNECTED 는 여전히 netOnline 을 켜지 않는다 (하네스 케이스로 증명)
6) 타이밍·핀·보율을 바꾸지 않았다
7) 컴파일 통과 + 플래시/RAM
실기 검증은 사용자 몫이다 — 했다고 적지 마라.

## 처리 결과

담당 `arduino-engineer` · 2026-08-14

지시대로 **추측으로 고치지 않고 보이게 만드는 것**을 1순위로 했다. 컴파일 통과, 하네스 82 PASS / 0 FAIL.
**바로 올려서 시리얼 모니터(115200) 로그를 받아 달라.**

### ⚠ 먼저 읽어라 — 로그 보기 전에 가설 하나가 이미 약해진다

`netTick()` 을 다시 읽고 나온 것이다. **가설 C(접속 문구를 못 알아본다)만으로는 증상이 설명되지 않는다.**

- `netTick()` 은 오프라인인 동안 **5초마다 CIPSTART 를 재시도**한다(4단계로 되돌아간다).
- 이미 TCP 가 붙어 있는 상태에서 CIPSTART 를 또 쏘면 ESP-01 은 **`ALREADY CONNECTED`** 를 낸다.
- 그리고 그 문자열은 **고치기 전 코드에서도 이미 받아들이고 있었다**(`strstr(s,"ALREADY CONNECT")`).

즉 모듈의 응답을 **읽고 있기만 했다면**, `CONNECT` 를 한 번 놓쳤더라도 **첫 재시도(≈5초) 안에
`netOnline` 이 켜졌어야 한다.** 실제로는 몇 시간 동안 안 켜졌다.

→ **원인은 (C)보다 (A) 또는 (B) 쪽일 가능성이 높다.** 그래서 이번 판에서 판정 문자열을 넓히는 것보다
   **카운터를 넣는 것**을 더 중요하게 봤다. 판정 확장은 2순위 지시라 같이 넣었지만, 그것만으로는
   증상이 안 풀릴 수 있다는 뜻이다.

### 로그를 이렇게 읽어라 — `[DIAG]` 한 줄이 원인을 셋으로 가른다

3초마다 이런 줄이 나온다:

```
[DIAG] offline step=5 rx=2959 lines=338 up=116s
```

| 보이는 것 | 뜻 | 다음에 볼 곳 |
|---|---|---|
| **`rx=0`** | ESP→Uno 로 **바이트가 아예 안 온다** | D7 배선, ESP TX 레벨(3.3V), 모듈 전원. **접속 문구 문제가 아니다** |
| **`rx>0, lines=0`** | 바이트는 오는데 **줄이 안 끊긴다** | 줄 종단이 LF 가 아닐 수 있다. ⚠ 이 경우 `[AT]` 로그가 **한 줄도 안 나온다** — `[DIAG]` 가 유일한 단서다 |
| **`lines>0, online=0`** | 줄은 오는데 **문구를 못 알아본다** (가설 C) | `[AT]` 로그에 실제 문구가 그대로 찍혀 있다 |

`step=` 은 접속 상태 기계가 어디까지 갔는지다(5 = CIPSTART 를 보내고 응답 대기 중).

### 넣은 것

**1순위 — 받은 줄을 전부 찍는다**

`handleLine()` 진입점에서 모든 줄을 길이와 함께 찍는다. 인쇄 불가 문자는 `\xHH` 로 편다.

```
[AT] "CONNECT" (7)
[AT] "CONNECT \x01" (9)      ← 눈으로는 같아 보이지만 다른 줄이다
```

버려지는 것도 남는다:
- `[DROP-OVF]` — 72바이트를 넘어 버린 줄 (예전에는 **조용히 사라져서** "아무 로그 없음"과 구분이 안 됐다)
- `[CKSUM NG]` — 체크섬 불일치 (기존)

**2순위 — 접속 판정 확장** (넣은 것과 근거)

| 받아들임 | 근거 |
|---|---|
| `CONNECT` (정확일치, 대소문자 무시) | 표준 AT 펌웨어(≥0.50)의 CIPSTART 성공 응답 |
| `Linked` / `LINKED` | **구형 AT 펌웨어(0.2x)** 가 같은 자리에서 내는 응답 |
| `0,CONNECT` 등 `<0-4>,` 접두 | CIPMUX=1 형식. 우리는 CIPMUX=0 이지만 모듈에 상태가 남아 있을 수 있다 |
| 앞뒤 공백·CR | 모듈에 따라 붙어 온다 |
| `ALREADY CONNECT...` | 기존 유지 |

**부분문자열 검색으로 되돌리지 않았다.** 대신 (1) `WIFI` 로 시작하는 줄을 먼저 걸러내고
(2) **길이를 정확히 맞춰** 비교한다. **길이 검사가 안전장치의 핵심이다** — `CONNECTED`(9)는
`CONNECT`(7)와 길이가 달라 통과할 수 없고, `NO CONNECT`·`CONNECT FAIL` 도 마찬가지다.

**3순위 — 상태 기계 로그**: `[NET] 4 CIPSTART` 형태로 무엇을 보냈는지 찍는다.
5초마다 CIPSTART 를 재시도하는지 로그로 보인다.

### 하네스 — **82 PASS / 0 FAIL** (76 → 82)

**[22] 접속 판정 변형 15종을 표로 돌린다.** 켜져야 할 7종과 **켜지면 안 되는 8종**을 같이 넣었다:

```
켜짐   CONNECT / connect / Linked / LINKED / 0,CONNECT / "  CONNECT  " / ALREADY CONNECTED
안켜짐 WIFI CONNECTED ★ / WIFI GOT IP / WIFI DISCONNECT / CONNECTED / NO CONNECT
       / CONNECT FAIL / OK / busy p...
```

`WIFI CONNECTED` 는 별도 단언으로 한 번 더 못 박았다 — **되살리면 안 되는 버그**라서다.
`NO CONNECT` 와 `CONNECT FAIL` 을 넣은 이유는, 부분문자열 방식으로 되돌리면 이 둘이
**실패 응답인데 성공으로 읽히기** 때문이다. 확장이 그 방향으로 새지 않았음을 지킨다.

**[23] 로그 형식 자체를 검사한다.** 이 요청의 산출물이 로그이므로 로그를 시험한다:
- `"CONNECT \x01"` 을 넣으면 `[AT] "CONNECT \x01" (9)` 로 찍히고, 접속으로 인정되지 않는다.
  덤으로 그 줄은 첫 글자가 `C` 라 §6.2 의 타입 문자 검사를 통과해 `[CKSUM NG]` 까지 간다 —
  명세대로다. **눈으로 CONNECT 로 보이는 줄이 왜 안 먹었는지가 로그만으로 설명된다.**
- 90바이트 줄 → `[DROP-OVF]` 가 남는다.
- 오프라인 구간에서 `[DIAG]` 가 나온다.

**하네스 실패 2건이 또 내 테스트 결함이었다.** (1) `[DIAG]` 를 못 찾았는데 `substr(npos)` 를 불러
프로세스가 abort 했다. (2) 가짜 ESP 가 CIPSTART 에 즉시 CONNECT 를 돌려줘서 관측할 오프라인 구간이
아예 안 생겼다 — `netStepWait` 를 밀어 두고 재시험하도록 고쳤다. 스케치 결함은 아니었다.

### 사용량 (기준 7)

| 빌드 | 플래시 | 전역 RAM |
|---|---|---|
| REQ-0036 직후 | 10040 B (31%) | 773 B (37%) |
| **지금 (진단판)** | **11070 B (34%)** | **793 B (38%)** |
| 차이 | +1030 B | +20 B |

**이건 진단용 빌드다.** 원인이 잡히면 로그 양을 줄이자고 요청해도 된다.
`DEBUG 0` 으로 빌드하면 전부 빠지지만, 지금은 켜 두는 것이 목적이다.

### 하지 말라는 것은 하지 않았다 (기준 6)

- **타이밍·핀·보율 전부 그대로다.** `NET_WAIT`, `PIN_ESP_RX/TX`, `wifi.begin(9600)`,
  `Serial.begin(115200)` 어느 것도 건드리지 않았다.
- 부분문자열 스캔으로 되돌리지 않았다.

### ⚠ 이 빌드가 만들 수 있는 혼선 하나

**추가한 로그 자체가 변수다.** SoftwareSerial RX(9600)는 타이밍에 예민하고, 이 빌드는
하드웨어 Serial(115200) 출력을 크게 늘렸다. 두 시리얼이 서로 간섭할 수 있는 조합이다.

→ **올린 뒤 증상이 *달라지면*, 그것이 고쳐진 것인지 로그 때문에 바뀐 것인지 먼저 의심해라.**
   특히 `rx` 카운터가 늘긴 하는데 값이 이상하거나 깨진 줄이 많이 보이면 이쪽을 의심할 근거가 된다.
   보율은 지시대로 건드리지 않았다(루트가 이미 배제했고, 추측으로 만지면 변수가 하나 더 는다).

### 검증하지 않은 것

- ⚠ **실기 검증은 사용자 몫이다. 나는 보드가 없다.** 위 변형들이 실제 모듈의 응답과 맞는지는
  로그가 와야 안다. **`Linked` 를 넣은 것도 근거 있는 추정이지 확인된 사실이 아니다.**
- 하네스의 "모듈 응답"은 전부 내가 밀어 넣은 문자열이다.
