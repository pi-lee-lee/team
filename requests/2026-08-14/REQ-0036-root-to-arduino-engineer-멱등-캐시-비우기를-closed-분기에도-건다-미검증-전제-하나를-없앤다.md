# REQ-0036 · 멱등 캐시 비우기를 CLOSED 분기에도 건다 — 미검증 전제 하나를 없앤다

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

## 승인한다. 루트가 코드로 검증했다

네 제안의 근거를 `client.ino` 에서 직접 확인했다. 전부 맞다:

```
317: static bool netOnline = false;                                    ← 초기값
674: if (strstr(s, "ALREADY CONNECT")) { netOnline = true;  return; }
676: if (strcmp(s, "CONNECT") == 0)    { netOnline = true;  cacheClear(); }
677: if (strstr(s, "CLOSED")) {
678:   netOnline = false;                                              ← 런타임에 false 가 되는 유일한 곳
721: if (netOnline) return;                                            ← netTick 의 첫 줄
```

**따라서 논리가 성립한다**: 재접속은 `netOnline == false` 를 요구하고, 그 값은 `CLOSED` 분기에서만
false 가 된다. `CLOSED` 탐지가 실패하면 `netTick()` 이 721행에서 즉시 반환하므로 **CIPSTART 자체가
안 나가고, 새 서버와 연결될 일도 없다.** 스테일 캐시 문제가 발생할 조건이 만들어지지 않는다.

뒤집으면 네가 쓴 그대로다 — **재접속이 실제로 일어났다면 `CLOSED` 는 반드시 탐지된 것이다.**

## 왜 이게 개선인가 — 전제를 하나 줄인다

지금은 독립된 전제가 **둘**이다:
1. ESP-01 이 `CLOSED` 를 올린다 — **재접속 기능 전체가 이미 여기 의존한다**
2. ESP-01 이 `CONNECT` 를 **정확히 그 문자열의 단독 줄로** 올린다 — 캐시 비우기만 여기 의존한다

캐시 비우기를 1번에 묶으면 **2번이 캐시 비우기의 전제에서 빠진다.** 새 위험을 지는 게 아니라
이미 지고 있는 위험 안으로 들어가는 것이다. 그리고 실패 모드가 달라진다 —
1번이 틀리면 **재접속이 아예 안 돼서 눈에 보이고**, 2번이 틀리면 REQ-0032 의 "조용한 성공"이다.

**탐지 방식의 견고함 차이도 확인했다**: `CLOSED` 는 `strstr`(부분일치)이고 `CONNECT` 는
`strcmp`(정확일치)다. CIPMUX 모드의 `0,CLOSED` 나 앞뒤 공백 같은 형식 변화에 전자가 관대하다.

## 할 것

1. `CLOSED` 분기(677~678행)에 `cacheClear()` 추가.
2. **`CONNECT` 쪽 `cacheClear()` 는 그대로 둬라** — 첫 연결과 이중 방어. 네 판단대로다.
3. 하네스에 케이스 추가:
   - `CLOSED` 만 오고 `CONNECT` 가 안 오는 경우에도 캐시가 비워지는가
   - 같은 연결 안에서의 멱등성은 여전히 유지되는가 (회귀)
   - `ALREADY CONNECT` 로는 여전히 안 비워지는가 — CIPSTART 재시도마다 캐시가 날아가면
     살아 있는 연결의 멱등성이 깨진다. 네가 REQ-0035 에서 지킨 [18]-4 그대로다.
4. 주석에 **왜 두 곳에서 비우는지**를 남겨라. 한 곳이 중복으로 보여 나중에 누가 지울 수 있다.

## 이 제안 자체에 대해

요청받지 않은 상태에서 **검증 불가능한 전제를 없앨 방법을 찾아 올린 것**이 좋았다.
게다가 코드를 고치지 않고 근거만 정리해서 판단을 요구한 것도 맞다 — 얼린 명세 밖의 구현 세부지만
안전 성질이 걸린 부분이라 루트가 알아야 했다.

명세 변경은 필요 없다. §4.2 는 "새 연결에서 비운다"고만 하고 **탐지 방법을 지정하지 않는다** —
구현이 더 견고한 지점을 고르는 것은 네 재량 안이다.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

캐시 비우기가 지금은 "CONNECT 가 정확히 단독 줄로 온다"는, 실기에서만 확인 가능하고 틀리면 조용히 실패하는 전제에 걸려 있다. CLOSED 는 재접속 기능 전체가 이미 의존하는 전제이므로 거기 묶으면 새 위험 없이 전제 하나가 사라진다.

## 대상 파일

- `조별과제샘플/client.ino`
## 완료 기준

1) CLOSED 분기에서 캐시가 비워진다
2) CONNECT 쪽도 유지된다 (첫 연결·이중 방어)
3) ALREADY CONNECT 로는 비워지지 않는다 (회귀 — 살아 있는 연결의 멱등성)
4) 하네스에 위 3가지 케이스가 있고 PASS/FAIL 수를 적는다
5) 두 곳에서 비우는 이유가 주석에 있다
6) arduino-cli 컴파일 통과 + 플래시·RAM
CLOSED 문구 자체가 실기에서 맞는지는 여전히 미검증이다 — 그 사실을 적어라.

### 바뀐 것

```c
if (strstr(s, "CLOSED")) {
  netOnline = false;
  cacheClear();                     // ★ 주 방어선
  netStep = 4; netStepAt = millis(); netStepWait = 1000;
  return;
}
```

`CONNECT` 쪽은 손대지 않았다. 위에 **왜 두 곳인지**를 문단으로 남겼다(기준 5) — 지켜야 할 성질,
`CLOSED` 가 주 방어선인 이유(재접속이 `netOnline==false` 를 요구하고 그 값은 여기서만 false 가 된다),
`CONNECT` 를 남기는 이유(부팅 후 첫 연결은 `CLOSED` 를 안 거친다 + 이중 방어),
그리고 `ALREADY CONNECTED` 에서는 비우면 안 되는 이유(살아 있는 연결 + 5초 CIPSTART 재시도)를 적었다.

**주석 오류를 하나 같이 고쳤다.** `ALREADY CONNECT` 줄에 *"새 연결이 아니므로 캐시를 지키지 않는다"*
라고 적혀 있었는데, 이건 읽는 사람에 따라 **"비운다"로 읽힌다.** 실제 코드는 비우지 않는다.
`// 새 연결이 아니다 → 캐시 유지` 로 바꿨다. 캐시를 비우는 조건을 다루는 자리라 이 모호함은
그대로 두면 언젠가 코드를 반대로 고치게 만든다.

### 하네스 (기준 4) — **72 PASS / 0 FAIL** (62 → 72)

**[19] `CLOSED` 만으로 비워지는가 — 판별력의 핵심은 `CONNECT` 를 일부러 안 주는 것이다.**

가짜 ESP 는 `AT+CIPSTART` 에 `CONNECT` 를 붙여 준다. 그래서 `CLOSED` 를 넣고 **`netTick()` 이
재시도하기 전에** 캐시를 확인해야 한다. `CLOSED` 직후 `netStepWait = 1000 ms` 로 걸리므로
`spin(3)`(≈33 ms) 안에서는 CIPSTART 가 절대 안 나간다 — 즉 이 구간에 `CONNECT` 가 도달할 수 없다.
그 시점에 `cacheCount == 0` 이면 비운 주체는 `CLOSED` 하나뿐이다.
(캐시에는 직전에 rid 100·101 을 넣어 뒀으므로, `CLOSED` 에 `cacheClear()` 가 없으면 이 단언은 반드시 실패한다.)

**[20]** 재접속 뒤 같은 rid 101 에 **다른 자리**(B4)를 태워 `A,101,B4,0,37` 이 나오는 것을 본다 —
캐시가 비워졌다는 실제 결과다. 같은 명령을 다시 보내면 구별이 안 되므로 자리를 바꾼다.

**[21]** `ALREADY CONNECTED` 회귀. `cacheCount > 0` 를 직접 보고, 이어서 같은 rid 110 에
다른 자리를 태워도 **옛 ACK(A1)가 그대로** 나오는 것을 확인한다. `netTick()` 이 CIPSTART 를
5초마다 재시도하므로 여기서 비우면 살아 있는 연결의 멱등성이 재시도마다 깨진다.

### 검증하지 않은 것 — **전제가 사라진 게 아니라 하나로 줄었다**

- ⚠ **`CLOSED` 문구 자체가 실기에서 맞는지는 여전히 미검증이다.** 보드가 없다.
  하네스에서는 내가 `"CLOSED\r\n"` 을 직접 밀어 넣은 것이라, ESP-01 이 실제로 그 문구를 올리는지는
  확인되지 않았다. 이 전제는 그대로 남는다.
- **다만 성질이 달라졌다.** 이 전제는 이제 **캐시 비우기만의 것이 아니라 재접속 기능 전체가
  이미 지고 있는 것**이다. 그리고 틀렸을 때 증상이 다르다 —
  `CLOSED` 를 못 읽으면 **재접속이 아예 안 된다**(눈에 보이는 고장).
  옛 구조에서 `CONNECT` 를 못 읽으면 REQ-0032 의 **"조용한 성공"**이었다.
- `CONNECT` 전제는 이제 **캐시 비우기의 필요조건이 아니다.** 이중 방어로만 남아 있어서,
  그 문구 가정이 깨져도 캐시 비우기는 `CLOSED` 로 성립한다.
- 실기 판별법은 그대로다: **서버 재시작 후 한 칸에 주입했는데 다른 칸 ACK 가 오면** 이 전제를 의심한다.
  루트가 `docs/parking-status.md` 에 적어 뒀다.

### 처리 완료 · arduino-engineer · 2026-08-14T10:22:48+0900

CLOSED 분기에 cacheClear() 추가(주 방어선), CONNECT 쪽은 이중 방어로 유지, ALREADY CONNECT 는 그대로 유지. 두 곳인 이유를 주석 문단으로 남김. ALREADY CONNECT 주석이 '캐시를 지키지 않는다'로 반대 의미로 읽히던 것도 수정. 컴파일 10040B/31%·RAM 773B/37% 경고0. 하네스 72 PASS/0 FAIL(62→72) — [19]는 CONNECT 를 일부러 안 주고 CIPSTART 재시도 전(33ms)에 cacheCount==0 을 확인해 판별력을 만들었다. CLOSED 문구 자체는 실기 미검증이나 이제 재접속 기능 전체가 이미 지던 전제로 흡수됐고 실패가 조용한 성공에서 눈에 보이는 고장으로 바뀌었다
