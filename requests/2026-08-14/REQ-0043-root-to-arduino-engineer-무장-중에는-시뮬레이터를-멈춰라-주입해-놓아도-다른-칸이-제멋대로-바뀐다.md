## 요청 내용

## 실기 증상 (사용자 보고 — 실물 아두이노에서 처음 확인됨)

> 테스트 모드가 켜져도 랜덤 데이터가 계속 송신된다.

맞는 지적이고 **명세의 공백**이다. 루트가 §12A 지시를 쓸 때 빠뜨렸다.

`readSlotSensor()` 는 이렇게 되어 있다:

```c
if (testArmed && 오버라이드 있음) return 주입값;
if (srcReal)                      return readRealSensor(i);
simAdvance(i);                    // ← 무장 중에도 계속 전진한다
```

무장은 **"주입을 받아들이는 상태"** 로만 정의돼 있고 시뮬레이터를 멈추라는 규정이 없다.
그래서 `A1` 을 주입해 놓아도 `A3`·`B2` 가 제멋대로 뒤집혀 **시험 자체가 성립하지 않는다.**

## 고칠 규칙

> **무장 중에는 시뮬레이터가 전진하지 않는다.** 주입되지 않은 시뮬 칸은 **마지막 값을 유지**한다.
> **실물 센서 칸은 계속 읽는다** — 그건 진실이고 가릴 이유가 없다.

즉 계층은 그대로 두고 `simAdvance()` 호출만 무장 중에 건너뛴다. 칸별 소스 분리(실물/시뮬)는
유지된다 — "3칸은 실물, 7칸은 시뮬" 상태에서 무장하면 실물 3칸은 계속 살아 움직이고
시뮬 7칸만 얼어붙는다. 그게 맞는 동작이다.

**해제하면 시뮬레이터가 다시 돈다.** 얼어 있던 값에서 이어가든 새로 시작하든 네 판단이다 —
다만 해제 순간에 10칸이 한꺼번에 튀지 않게 해라(§ 시뮬레이터의 `SIM_MIN_GAP_MS` 취지).

## 하지 말 것 — tmask 에 손대지 마라

얼어 있는 시뮬 칸을 **"주입됨"으로 표시하지 마라.** 주입한 적이 없는데 주입값이라고 하면 거짓이다.
전역 무장 배너가 이미 "지금 보이는 점유 상태는 진짜가 아닐 수 있습니다"라고 말하고 있고,
그걸로 충분하다. `tmask` 는 지금처럼 **실제로 주입된 칸만** 가리킨다.

## 참고 — 명세도 같이 고친다

socket-engineer 에게 §12A 에 이 규칙 한 줄을 넣도록 별도 요청을 냈다. 네 구현이 먼저 나와도 되고
명세가 먼저 나와도 된다 — 규칙 문장은 위와 동일하다.

## 검증

하네스로:
- 무장 중 시뮬 칸의 값이 시간이 지나도 안 바뀐다
- 무장 중 실물 칸(`srcReal`)은 계속 읽힌다
- 주입한 칸은 주입값을 낸다
- 해제하면 시뮬이 다시 움직인다
- `tmask` 는 주입된 칸만 가리킨다 (얼어 있는 칸은 포함되지 않는다)

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

실물에서 테스트 모드를 켜 봤더니 주입하지 않은 칸이 계속 랜덤하게 바뀌어 시험이 성립하지 않는다. 테스트 모드의 목적은 값을 사람이 통제하는 것인데 그 아래에서 시뮬레이터가 계속 돌면 목적이 무너진다.

## 완료 기준

1) 무장 중 simAdvance 가 전진하지 않는다 — 시뮬 칸 값이 유지된다
2) 무장 중에도 실물 센서 칸은 계속 읽힌다
3) 주입 칸은 주입값을 낸다
4) 해제하면 시뮬이 재개되고, 재개 순간 여러 칸이 한꺼번에 튀지 않는다
5) tmask 는 실제 주입된 칸만 가리킨다 (얼어 있는 칸 제외)
6) 하네스 케이스 추가 + PASS/FAIL 수, 컴파일 통과 + 플래시/RAM

### 지금 `client.ino` 에 들어가 있는 것

1. `readSlotSensor()` 에 **`if (!testArmed) simAdvance(i);`** — 무장 중 시뮬 정지.
   실물 센서 칸(`srcReal`)은 그 앞에서 반환하므로 무장 중에도 계속 읽힌다.
2. **`simResume()`** — 해제 시 각 칸의 마감을 "방금 지금 상태가 된 것처럼" 다시 잡는다
   (점유 20~60초 / 빈 칸 8~25초). `processTest()` 의 `top=='D'` 에서 부른다.
3. `[SIM] 정지 — 무장됨` / `[SIM] 재개` 디버그 두 줄.
4. `tmask` 는 **손대지 않았다** — 얼어 있는 칸은 들어가지 않는다(지시대로).

컴파일 통과: **11356 B (35%) / RAM 793 B (38%)**, 경고 0. 하네스 **95 PASS / 0 FAIL**.

### ⚠ 중단으로 **끝내지 못한 검증** 하나

`[24]-(f)`(해제 후 7초간 한 칸도 안 바뀐다)가 **`simResume()` 이 없으면 실제로 실패하는지**를
변이 시험으로 확인하던 중이었다. `simResume()` 호출을 잠시 빼고 돌려 보려던 참에 중단 지시가 왔다.
**호출은 즉시 원복했고**(깨진 상태를 남기지 않으려고) 컴파일·하네스로 정상 상태를 확인했지만,
**변이 시험 자체는 돌리지 못했다.**

→ 즉 그 시험의 판별력은 **추론으로는 성립하지만**(최소 체류시간이 8초이므로 재개 처리가 없으면
   1.5초 간격으로 4~5칸이 뒤집혀 반드시 실패한다) **경험적으로 확인된 것은 아니다.**
   이 구현이 살아남는다면 그 확인을 먼저 해야 한다.

### 새 설계(버튼식 시뮬)로 갈 때 짚어야 할 것

루트 말대로 **자유 실행이 없어지면 1번(무장 중 정지)은 불필요**해지고, 오히려 그 게이트가
**무장 중에 버튼을 막는다.** 지우는 것이 맞다. 그 외에 같이 검토해야 할 것들:

- **`simNextAt[SLOT_N]` 40바이트와 `SIM_*_MS` 상수들이 통째로 필요 없어진다** — RAM 이 줄어든다.
- **⚠ `occupied=1, reserved=1` 시연 경로가 같이 사라진다.** 지금 그 조합은 자유 실행 시뮬의
  "예약이 잡히면 4~12초 뒤 그 차가 들어온다"(`ARRIVE_MIN_MS`/`ARRIVE_MAX_MS`)로만 만들어진다.
  버튼식으로 바꾸면 그 경로가 없어져 **REQ-0018 완료기준 6이 다시 도달 불가**가 된다.
  버튼이 "예약됐지만 비어 있는 칸"을 우선해서 채우도록 규칙에 넣지 않으면, §1.1 마지막 행은
  아무도 화면에서 못 본다. **명세를 다시 얼릴 때 이 한 줄을 넣어 달라.**
- "한 번 누르면 한 칸만 바뀐다"가 규칙이면 그건 지금의 `SIM_MIN_GAP_MS` 취지와 같다 —
  버튼 한 번에 정확히 한 칸을 고르는 형태가 자연스럽다.
