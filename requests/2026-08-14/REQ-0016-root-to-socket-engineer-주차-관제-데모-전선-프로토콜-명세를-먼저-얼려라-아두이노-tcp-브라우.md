# REQ-0016 · 주차 관제 데모: 전선 프로토콜 명세를 먼저 얼려라 (아두이노 TCP + 브라우저 WebSocket)

**요청자** `root` → **담당** `socket-engineer`

## 요청 내용

## 배경
`조별과제샘플/` 에 client.ino / server.cpp / index.html 3종 데모가 있다(현재 코드는 그대로 두고 읽어라).
지금 구조: 아두이노가 3초마다 150바이트 JSON 을 ESP-01 에 AT 명령으로 밀어넣고, 서버는
data_log.json 에 무한 append, index.html 은 10초마다 그 파일을 폴링한다.

이걸 **2열 5행(총 10칸) 주차 관제 실시간 시스템**으로 바꾼다. 센서는 아직 없으므로 가상으로 만든다.
브라우저에서 예약이 발생하면 서버가 즉시 아두이노로 내리고, 아두이노가 예약을 반영한 뒤
반영된 상태를 되돌려 보낸다.

## 이 요청의 범위 — 구현이 아니라 명세다
`docs/net/parking-protocol.md` 하나만 쓴다. server.cpp 는 아직 건드리지 마라.
아두이노/웹 담당에게 이 문서를 얼린 뒤 병렬로 요청을 뿌릴 것이다. 명세 없이 셋을 동시에
풀면 서로 안 맞는 포맷 세 개가 나온다.

## 루트가 정한 것 (협상 대상 아님 — 그대로 문서에 박아라)

### 토폴로지 — 서버 프로세스 하나, 리스너 둘
- **TCP 9991** — 아두이노 전용. 줄바꿈(\n) 구분 **압축 ASCII 라인**. JSON 아니다.
- **HTTP 9900** — 같은 프로세스가 index.html 과 data_log.json 을 정적 서빙하고,
  `GET /ws` 를 **WebSocket(RFC 6455)** 으로 업그레이드한다.
  → 브라우저는 raw TCP 를 못 쓴다. 그래서 웹 쪽만 WebSocket 이다.
  → 서버가 직접 서빙하므로 `python -m http.server` 가 필요 없어지고 CORS 문제도 사라진다.
  → 외부 라이브러리 금지. 핸드셰이크(SHA-1+base64)와 프레임 파싱을 직접 구현한다.

### 자리 ID — 이것이 세 도메인의 공통 언어다
- 2열 × 5행 = 10칸. ID 는 **`A1 A2 A3 A4 A5 B1 B2 B3 B4 B5`**.
  A 가 1열, B 가 2열, 숫자가 행(1이 맨 위).
- **전선 인덱스 순서는 항상 A1,A2,A3,A4,A5,B1,B2,B3,B4,B5 (0~9)**. 어디서도 뒤집지 않는다.

### 자리 상태 — 직교하는 두 값
- `occupied` (센서 진실값, 0/1) 과 `reserved` (예약 플래그, 0/1) 는 **별개**다.
  하나로 합치지 마라 — 예약해 둔 자리에 차가 들어오는 정상 시나리오를 표현 못 한다.

### 아두이노 → 서버 (TCP 9991, 압축 라인)
최소 다음 두 종류. 필드 구분자와 정확한 문법은 네가 정하고 문서에 BNF 로 못 박아라.
- **상태 프레임** — seq, 10칸 occupied 비트열, 10칸 reserved 비트열, uptime, device_id
- **예약 ACK** — 예약 요청의 `rid` 를 그대로 되돌려 담고, 결과(성공/이미점유/잘못된자리)를 싣는다.
  ACK 는 상태 프레임과 **구분되는 별도 타입**이어야 한다. 서버가 rid 로 원 요청과 짝지어야
  브라우저에 "요청됨 → 확정됨"을 보여줄 수 있다.

전송 타이밍은 **변화가 있을 때 즉시(디바운스 허용) + 변화가 없어도 주기적 갱신**이다.
3초 고정 주기는 실시간이 아니다. 구체 주기는 아래 대역폭 산식을 근거로 네가 정해라.

### 서버 → 아두이노 (TCP 9991)
- **예약 요청** — rid, 자리ID, user_id
- **예약 취소** — rid, 자리ID

### 서버 ↔ 브라우저 (WebSocket, JSON)
사람이 디버깅할 곳이므로 여긴 JSON 이다(전선이 좁은 쪽만 압축한다).
- 서버→브라우저: 전체 상태 스냅샷, 예약 ACK(rid 포함), 오류
- 브라우저→서버: 예약 요청(자리ID, user_id, rid), 예약 취소
- 상태 스냅샷의 각 자리 객체에 **`user_id`, `reserved_at` 자리를 지금 만들어 둔다**.
  사용자 고유값 체계가 아직 없으므로 값은 null 이어도 되지만 **필드는 존재해야 한다.**
- 아두이노 연결 여부(`device.online`)도 스냅샷에 넣어라. 브라우저가 "센서 끊김"을 알아야 한다.

### data_log.json — 요구사항이지 구현 디테일이 아니다
- WebSocket 푸시가 있다고 이 파일을 빼지 마라. 사용자가 명시적으로 요구했다.
- **최신 2건만 유지**하고 계속 덮어쓴다. 최신이 먼저 오는 배열.
- 여러 클라이언트가 동시에 읽는다. 사용자가 "파일을 복사 분할"을 고려하라 했는데,
  그 문제의 정석 해법은 **임시파일에 다 쓰고 원자적 rename** 이다. 독자는 항상 옛 파일 전체
  아니면 새 파일 전체를 보고, 반쯤 쓰인 파일을 볼 수 없다. 잠금도 복사본도 필요 없다.
  문서에 이 근거를 적어라. **윈도우 주의**: 대상이 있으면 `rename()` 이 실패한다 —
  `MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)` 를 써야 한다.

### 대역폭 — 명세에 산식을 적어라
아두이노와 ESP-01 사이는 SoftwareSerial 9600bps(초당 약 960바이트)다. 이게 병목이다.
현행 150바이트 JSON 을 10칸으로 확장하면 감당이 안 된다. 압축 라인이 몇 바이트이고
9600bps 에서 한 프레임에 몇 ms 가 걸리며, 네가 정한 주기에서 채널 점유율이 몇 %인지
**숫자로 계산해서 문서에 남겨라.** 여유가 충분하면 모듈 보율은 건드리지 않는 것이 정답이다
(AT+UART_DEF 는 플래시에 영구 기록되어 9600 을 가정한 다른 스케치와 어긋난다).

## 왜 필요한가

아두이노·서버·웹 세 도메인이 같은 전선 포맷에 합의해야 한다. 명세를 얼리기 전에 셋을 병렬로 풀면 서로 안 맞는 포맷 세 개가 나오고 요청을 한 바퀴 더 돌려야 한다. 특히 자리 ID 체계와 예약 ACK 의 rid 상관관계는 셋 다 같은 것을 봐야 성립한다.

docs/net/parking-protocol.md 가 존재하고 다음을 모두 담는다:

3) 서버↔브라우저 WebSocket JSON 스키마 — 양방향 전체, user_id/reserved_at 필드 포함, 실제 예시 메시지
4) data_log.json 의 정확한 형태 (최신 2건 배열) 와 원자적 교체 방식 + 윈도우 주의사항
5) 9600bps 대역폭 계산: 프레임 바이트 수 → 전송 ms → 채널 점유율 %, 그리고 그 근거로 정한 전송 주기
6) 예약 한 건의 전체 시퀀스 다이어그램 (브라우저 클릭 → WS → 서버 → TCP → 아두이노 → ACK → 서버 → WS → 브라우저)
7) 오류·예외 처리: 아두이노 미연결 중 예약, 이미 점유된 자리 예약, ACK 무응답 타임아웃
문서를 다 쓰면 req.sh done 으로 닫고 루트에게 포인터를 보내라. server.cpp 구현은 그 다음 요청으로 별도 발행한다.

### 루트가 정한 것은 그대로 박았다

포트 9991/9900, 압축 ASCII vs JSON 분리, 자리 ID 와 인덱스 순서, `occupied`/`reserved` 직교,
외부 라이브러리 금지, `data_log.json` 유지 + 최신 2건 + 원자적 rename, 보율 미변경.

### 내가 정한 것 (루트가 "네가 정하라"고 한 부분)

- **구분자 쉼표, 타입 문자 1글자, XOR 체크섬 2자리 대문자 hex.**
  체크섬 범위를 **"첫 바이트부터 체크섬 앞 쉼표까지(그 쉼표 포함)"** 로 못 박고 누적 XOR
  중간값까지 예시로 넣었다(§2.2). 세 구현자가 각자 만들므로 1바이트만 어긋나도 전부 실패한다.
- **하트비트 1 Hz + 변화 시 즉시(디바운스 100 ms), 타이머 하나·전송하면 리셋.**
  근거는 §3 의 계산이다(최대 프레임 61.46 ms → 6.15% 점유, 최악 14.90%).
- 줄 최대 64바이트, 모르는 타입 문자는 조용히 버림.

### 루트가 veto 할 수 있는 판단 3개 (명시해 둔다)

1. **`result=2`(이미 예약됨)를 추가했다.** 루트는 성공/이미점유/잘못된자리 3종을 나열했는데,
   `occupied` 와 `reserved` 가 직교하므로 **"비었지만 남이 예약한 자리"** 가 실제로 생긴다.
   원래 목록으로는 표현이 안 돼서 값을 하나 늘렸다(§2.4).
2. **rid 를 두 이름공간으로 나눴다**(§4.1). 브라우저 rid 는 불투명 문자열, 전선 rid 는 서버가
   발급하는 uint16, 서버가 매핑표로 번역한다. 이유: **브라우저 둘이 같은 rid 를 고르면 ACK 가
   엉뚱한 브라우저에게 간다.** 아두이노는 받은 uint16 을 그대로 되돌려 담으므로 루트의
   "rid 를 그대로 되돌려 담는다"는 지켜진다. 전선도 더 짧아진다.
3. **예약의 durable owner 를 서버로 정했다**(§7.4). 아래 참조.

### 루트 지시에 없던 구멍 3개를 메웠다

- **아두이노 재부팅 시 예약 소실**(§7.4). 루트 모델은 아두이노가 `reserved` 를 들고 있는데,
  재부팅하면 사라진다. 그런데 브라우저는 계속 예약을 보여 준다 — 두 세계관이 **조용히** 갈라진다.
  `uptime` 감소 / `seq` 역행 / 새 연결로 재부팅을 감지하고, **서버가 살아 있는 예약을 전부
  다시 내린다.** 근거: 센서 진실값(`occupied`)의 주인은 아두이노지만 사람의 약속(`reserved`)의
  주인은 서버다. 전원이 끊겨도 서버는 안 잃는다.
- **SoftwareSerial 은 송신 중 수신을 잃는다**(§6.3). AVR `SoftwareSerial.write()` 는 인터럽트를
  끈 채 블로킹하고, 상태 프레임 하나가 57~61 ms 다. 그동안 들어온 예약 바이트는 **지연이 아니라
  유실**이다. 그래서 ACK 타임아웃 1500 ms + 재전송 2회(§7.3), 그리고 재전송이 안전하려면
  **아두이노가 rid 에 멱등**이어야 한다(§4.2, 최근 8건 캐시 → 같은 ACK 재전송, 재적용 금지).
  이 둘은 편의가 아니라 **정확성 요구**다.
- **AT 잡음과 `+IPD` 프레이밍**(§6.2). 서버 데이터는 `+IPD,<len>:` 로 오고 `OK`/`SEND OK`/`busy p...`
  가 같은 시리얼에 섞인다. "LF 로 구분한다"만 적으면 현행 `client.ino` 의 `"pin":` 스캐너 같은
  것이 또 나온다. 그래서 **LF 자르기 → `+IPD` 접두 제거 → 타입 문자 확인 → 체크섬 확인 → 나머지
  전부 폐기** 를 규칙으로 못 박았다. 체크섬이 3바이트를 쓰는 값을 하는 지점이 여기다.

### 검증 — 명세만 쓰는 요청이지만 검증할 수 있는 것은 했다

- **예제 라인 8개 전부를 BNF 정규식 + 체크섬 + 길이 상한에 통과시켰다. 8/8 PASS.**
  결과를 §2.5 에 붙였다. 문법과 예제가 어긋난 명세가 얼면 셋이 각자 다르게 해석한다.
- **WS 핸드셰이크 자가검증 벡터를 실제로 계산**했다(§5.1).
  `dGhlIHNhbXBsZSBub25jZQ==` → `s3pPLMBiTxaQ9kYGzzhZRbK+xOo=` — RFC 6455 예제와 일치.
  cpp 구현자가 이 한 줄로 SHA-1+base64 를 자가진단할 수 있다.
- **스냅샷 크기를 실측**했다. 처음에 "약 780바이트"로 어림했는데 **실제 845바이트**여서 고쳤다.
  125바이트를 720바이트 초과 → **16비트 확장 길이 필수**. ack(82B)만 시험하고 넘어가면
  첫 스냅샷에서 깨진다는 경고를 함께 적었다(§5.2, §5.3).
- 대역폭은 AT 오버헤드(`AT+CIPSEND=<len>\r\n` 15~16 B)를 **포함해서** 계산했다. 페이로드만
  세면 과소평가된다. 6.15% 가 **제외하는 것**(수신 `+IPD`, AT 응답)도 명시했다.

### 검증하지 않은 것 (정직하게)

- **실제 하드웨어로 돌린 것이 아니다.** 9600bps 계산은 8N1 이론값(10비트/바이트)이고,
  ESP-01 의 실제 처리 지연·`busy p...` 재시도는 포함하지 않았다. 여유가 94% 라 문제되지
  않을 것으로 보지만 **측정한 값이 아니다.**
- **WebSocket 서버를 구현해서 브라우저를 붙여 본 것이 아니다.** 핸드셰이크 벡터만 계산으로 확인했다.
- 예약 시퀀스는 문서상 설계다 — 세 도메인이 붙기 전까지는 왕복이 실증되지 않는다.
