# REQ-0030 · 테스트 모드 수신부: T 프레임 처리 + tmask 송신 (그릇에 외부 진입점을 붙인다)

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

## 명세가 얼렸다 — `docs/net/parking-protocol.md` v1.2

REQ-0027 로 만든 그릇(`slotOverrideSet/Clear/ClearAll/slotSourceSet`)에 **드디어 호출자가 생긴다.**
서버가 전선으로 내리는 `T` 프레임이 그것이다.

명세 §2·§12A 를 읽어라. 여기 옮기지 않는다.

## 할 것

1. **`T` 수신 처리** — §6.2 의 기존 4단계(LF 분할 → `+IPD` → 타입 문자 → 체크섬)에 `T` 를 추가한다.
   기존 `R`/`C` 경로와 같은 파서를 타야 한다.
2. **`A` ACK 로 응답** — `rid` 재사용. **rid 멱등 캐시(§4.2)가 `T` 에도 적용되어야 한다.**
   서버는 ACK 를 못 받으면 같은 rid 로 재전송하는데, 멱등하지 않으면 오버라이드가 두 번 적용된다.
3. **`S` 프레임에 `tmask` 를 실어 보낸다** — 무장 중일 때. 해제 상태면 필드를 생략한다(옛 형식).
   **이게 이번 개정의 핵심이다**: 무장 여부의 진실은 ACK 가 아니라 네가 매 프레임 보내는 이 값이다.
4. **재부팅하면 오버라이드가 사라진다.** 예약(§7.4)과 반대다 — 서버가 다시 내리지 않는다.
   네가 별도로 할 일은 없고, **부팅 시 무장 해제 상태로 시작**하기만 하면 된다.

## 판단 2건에 답한다

지우지 마라. 요청에 없던 산출물이지만 **지금까지 없던 검증을 하나 메웠다** — 네가 짚은 그대로,
그전까지는 "내가 만든 라인의 체크섬이 맞다"만 확인했고 "받은 라인을 제대로 푸는가"는 아무도
확인하지 않았다. 호스트 테스트 [6]이 `+IPD,15:R,42,B3,u17,56` → `A,42,B3,0,06` 을 실제 파서로
통과시켜 명세 §8.1 과 바이트 일치시킨 것이 그 구멍을 닫았다.

**이번 `T` 처리도 같은 하네스로 시험해라.** 실기가 없는 동안 이게 가장 강한 증거다.

### ② 실물 센서 채터링 — **지금 넣지 마라. 센서 배선 시점으로 미룬다.**

### ⚠ 먼저 보고할 것 — `readSlotSensor()` 의 **의미**가 바뀌었다

REQ-0027 처리 결과에는 우선순위를 "오버라이드 > 소스"라고 적었다. **거기에 무장 조건이 빠져 있었다.**

```c
if (testArmed && (ovrActive & (1 << i))) return (ovrValue >> i) & 1;   // ← testArmed 가 새로 들어갔다
```

§12A.2 는 *"무장(`A`) 중일 때만 칸별 주입(`S`)이 적용된다"* 고 못 박는데, REQ-0027 판본은
`ovrActive` 만 보고 `testArmed` 를 보지 않았다. 실사용에서는 `T,S` 가 무장 검사를 하고 `T,D` 가
전 칸을 지우므로 두 해석이 같은 결과를 낸다. 그래도 고친 이유는 **안전 방향**이다:
해제 상태에서 주입값이 `occupied` 에 실리면 **`tmask` 가 안 붙은 채로** 전선에 나가고,
서버·화면은 그것을 실측으로 믿는다 — §12A.6 이 막으려는 바로 그 사고다.
이제 "해제 = 현실로 복귀"가 `ClearAll` 호출에 기대지 않고 **구조적으로** 성립한다.

**REQ-0027 의 처리 결과를 읽는 사람은 이 항목으로 갱신해서 봐야 한다.**
시그니처와 호출부는 여전히 그대로다(기준 8 은 만족).

### 구현

**`T` 수신** — 새 파서를 만들지 않았다(§2.4 "따로 만들지 마라"). `handleLine` 의 타입 문자 검사에
`T` 를 더하고, `processCommand` 가 필드 수만 타입별로 다르게 본다(`R`=5, `C`=4, **`T`=6**).
`+IPD` 추출·체크섬 검증·멱등 캐시·ACK 생성이 전부 기존 경로 그대로다.

**`processTest()`** — `top` 별 분기. 판단이 필요했던 자리 둘:

- **값 검사를 무장 검사보다 먼저** 한다. 깨진 프레임은 장치 상태와 무관하게 깨진 프레임이므로
  `tval` 이 `0`/`1` 이 아니면 무장 여부와 상관없이 `result=3`(slot `??`)이다.
  그 다음에 무장을 보고 `result=4`(slot 은 그 자리)를 낸다. 명세가 순서를 정하지 않아 이렇게 정했다.
- **`result=3` 이면 slot 은 항상 `??`** 다(§2.4 개정 2). 자리를 이미 알아냈어도 `result=3` 으로
  떨어지면 `??` 로 되돌린다.

**`tmask`** — `ovrActive` 를 그대로 실는다. 정의가 "그 칸의 `occupied` 가 주입된 값인가"라
`ovrActive` 와 정확히 같은 것이다. 해제 중에는 **필드를 통째로 생략**한다(§2.4 "필드 없음 = 해제").
`-` 를 명시하는 형식도 허용되지만 생략이 2바이트 싸고 옛 형식과 같아서 그쪽을 골랐다.

**재부팅** — `setup()` 에서 `testArmed = false; slotOverrideClearAll();` 을 명시적으로 부른다.
전역이라 어차피 0 이지만 §12A.3(예약과 정반대로 재하달하지 않는다)을 코드에 남겨 두려고 적었다.

### 송신 버퍼 (기준 5)

| 항목 | 값 |
|---|---|
| 전선 한 줄 상한 (§2.1-6) | 64 B (LF 포함) → 문자열 63자 + NUL = **64** |
| 최장 `S` (devid 8자, `tmask` 포함, §2.5) | 61 B (LF 포함) → 60자 + NUL = **61 B 필요** |
| 현재 버퍼 | `char buf[64]` → **여유 3 B** |
| 우리 devid `"P1"`(2자) 기준 실제 최장 | 55 B (LF 포함) |

`char buf[64]` 는 **규격 상한과 정확히 같은 크기**라 우연이 아니고, 넓힐 이유가 없다.
넘칠 일은 없지만 `snprintf` 반환값을 검사해 넘치면 프레임을 버린다(잘린 줄을 내보내지 않는다).
근거를 `sendStatus()` 위 주석에 남겼다. 하네스 [10] 이 이 61 B 를 실제로 재어 확인한다.

### 검증하지 않은 것

- ⚠ **실기 검증은 여전히 불가능하다.** 보드가 없다. 컴파일과 호스트 실행까지다.
- **타이밍.** 가상 시계는 `millis()` 호출마다 1 ms 씩 흐른다. "1Hz 가 정말 1000 ms 인가",
  "`>` 프롬프트가 300 ms 안에 오는가"는 여기서 확인되지 않는다.
- **실제 서버와의 TCP 왕복.** `net/fake_arduino.py` 와 라인 문법을 맞춰 본 것이지
  두 프로세스를 붙여 본 적은 없다.

### 판단이 필요한 것 — `tmask` 변화가 즉시 전송을 트리거하지 않는다

`statusTick()` 의 변화 감지는 `occMask`/`resMask` 만 본다. `testArmed` 와 `ovrActive` 는 안 본다.
그래서 다음 두 경우 **최대 1000 ms 동안** 서버가 무장 사실을 모른다:

- `T,A` 무장만 하고 주입은 아직 없을 때 (`tmask` 가 없음 → `0000000000` 으로 바뀌지만 비트는 그대로)
- `T,S` 가 주입한 값이 마침 현재 값과 같을 때 (`occupied` 가 안 바뀐다)

§12A.4 가 "무장의 진실은 `tmask`" 라고 정했으므로, 그 1초 동안 화면은 §12A.6 경고를 띄울 수 없다.
다음 하트비트에 저절로 맞춰지므로 **자기교정되고 상한이 1초로 묶여 있다** — 그래서 막지는 않는다.
고친다면 `changed` 비교에 `tmask` 상당값(`testArmed` + `ovrActive`)을 더하는 한 줄이면 된다.
요청에 없어서 넣지 않았다. 넣을지는 루트가 정해 달라.

(내 하네스는 이걸 못 본다 — `spin(300)` 이 매번 하트비트를 넘어가서 항상 통과한다.
 못 보는 것을 아는 채로 적는다.)

### 그 밖

- 센서 도착 절차 주석 4번 항목이 **낡아서 고쳤다.** "`slotOverrideSet(i,1)` 을 쓰면 된다 /
