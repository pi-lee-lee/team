# REQ-0023 · server.cpp Windows 분기 결함 8건 반영 (cpp-engineer 검토 REQ-0021) — 한글 깨짐이 최우선

**요청자** `root` → **담당** `socket-engineer`

## 요청 내용

## 배경

cpp-engineer 가 REQ-0021 로 Windows 분기를 정적 검토했다. **전문은 그 요청의 `## 처리 결과` 를 읽어라** —

**루트가 상위 2건을 실측으로 재확인했다.** 나머지는 cpp-engineer 의 판단을 신뢰한다.

## 우선순위 — 위에서부터 처리해라

### 1순위 · 한글이 깨진다 (확실, 루트 재확인) ⚠

```
$ head -c 3 server.cpp | xxd
00000000: 2f2f 20                                  // ←BOM 없음
줄 11: cl /EHsc /std:c++14 server.cpp ws2_32.lib   ←/utf-8 없음
```

BOM 없는 UTF-8 소스를 MSVC 는 **시스템 ANSI 코드페이지(한국어 윈도우면 CP949)**로 해석한다.
줄 339~342 의 `"예약되었습니다"` `"이미 주차된 자리입니다"` 등은 **브라우저 화면에 그대로 나가는 문구**다.

**컴파일은 통과한다. 그래서 아무도 못 잡고 시연장에서 처음 보인다.** 그게 이걸 1순위로 두는 이유다.

고치는 법: 줄 11 빌드 명령 주석에 `/utf-8` 추가. BOM 저장은 하지 마라 — POSIX 도구를 성가시게 한다.
README 나 실행 안내에도 이 플래그가 들어가야 한다(사용자가 그 명령을 그대로 복사해 쓴다).

### 2순위 · `<ctime>` 누락 (확실, 루트 재확인)

줄 174~175 가 `time_t`/`strftime`/`localtime` 을 쓰는데 공통 include 에 `<ctime>` 이 없다.
**POSIX 는 줄 43 `<sys/time.h>` 가 우연히 끌어와 통과한다** — 그 include 는 `#else` 안이라 Windows 에는 없다.

루트가 최소 예제로 재현했다:

```
<sys/time.h> 없이 → error: unknown type name time_t
<sys/time.h> 넣으면 → exit=0
```

즉 macOS 빌드 성공은 **우연**이다. MSVC 에서는 SDK 버전에 따라 되기도 하고 `C3861` 로 죽기도 한다.
**어느 쪽인지 모르는 채로 제출 환경에 넘기면 안 되는 종류의 의존이다.**
고치는 법: 공통 include 에 `#include <ctime>` 한 줄.

### 3순위 · `user_id` 길이 미검증 (확실, 플랫폼 무관)

줄 532/417. `slot` 은 `slot_index` 로 검증하는데 `user_id` 만 빠졌다.
`snprintf` 라 **메모리 안전 문제는 없다**(잘린다). 문제는 잘린 뒤 체크섬이 붙어
**형식상 유효하지만 내용이 잘린 라인**이 나가고 명세 §2.1 의 64B 상한을 넘을 수 있다는 것이다.
증상은 "가끔 예약이 안 된다"로 보인다 — 재전송 3회 후 `ack_timeout`.
명세 §2.3 의 `userid ::= 0*8(ALPHA/DIGIT/"_"/"-")` 에 맞춰 서버가 먼저 거절해라.

### 4순위 · WS 프레임 길이 상한 없음

줄 634~646. 클라이언트가 선언한 길이를 그대로 믿어 `inbuf` 가 무한히 커질 수 있다.
산술 오버플로는 없다(64비트 계산) — 그 점은 cpp-engineer 도 안전하다고 확인했다.
데모 환경에서 실제 위험은 낮지만 **한 줄이면 끝난다**: `if (len > 64*1024) return false;`

### 5순위 · 진단이 안 되는 실패 로그

줄 395~402. `MoveFileExA` 실패 시 `GetLastError()` 를 안 찍어
`ERROR_SHARING_VIOLATION(32)` 인지 알 수 없고 `data_log.json` 이 **조용히 옛 내용을 유지**한다.
윈도우에서 백신·편집기가 파일을 잠깐 잡는 것은 흔하다. POSIX `rename` 실패 로그의 `errno` 도 마찬가지.
**구현 자체는 맞다** — cpp-engineer 가 네 가지 확인 항목을 전부 통과시켰다. 로그만 보강해라.

### 6~8순위 · 예방적 (판단은 네게 맡긴다)

- `FD_SETSIZE` 가 윈도우에선 기본 64 다. `FD_SET` 은 넘치면 **조용히 무시**한다.
  `Connection: close` 라 쌓이지 않지만 브라우저가 여러 대 붙으면 닿을 수 있다.
  넣으려면 `<winsock2.h>` **앞에** `#define FD_SETSIZE 256` — 순서가 바뀌면 효과가 없다.
- `#define NOMINMAX` — 지금은 `std::min/max` 를 안 써서 무해하다. 비용 0 의 예방책이다.
- `size_t`→`int` 축소 경고(C4267, 줄 673/726/758) — 값이 작은 상수라 **실제 손실 없다.**
  경고만 지우려면 명시적 캐스트.

## 확인된 것도 기록해 둔다 (다시 안 봐도 된다)

cpp-engineer 가 요청 4개 영역을 전부 훑고 **문제 없음**을 명시했다:
Winsock 시그니처·타입 전 항목(`setsockopt` 의 `(const char*)` 는 양쪽 다 맞는 유일한 형태),
헤더 순서(`winsock2.h`→`ws2tcpip.h`→`windows.h` 가 맞다), 원자적 교체 구현,
시간 함수 단위 일치(FILETIME 변환 상수까지 검산).

한 가지 **주의만 남겨라**: 윈도우에서 `now_ms()`(부팅 후 경과)와 `epoch_ms()`(Unix epoch)는 **원점이 다른데
POSIX 에서는 같은 값이라 섞어 써도 티가 안 난다.** 지금 코드는 섞지 않는다(cpp-engineer 가 전부 대조함).
나중에 누가 `reserved_at` 에서 `now_ms()` 를 빼면 **윈도우에서만** 40년짜리 값이 나온다.
두 함수에 주석 한 줄을 붙여 둬라.

### 1순위 · 한글 깨짐 ✅

빌드 명령에 **`/utf-8`** 을 넣고, **왜 필요한지**를 그 자리에 적었다. 플래그만 적으면
다음 사람이 "왜 붙어 있지" 하고 지운다:

```
//   Windows     : cl /EHsc /std:c++14 /utf-8 server.cpp ws2_32.lib
//                 ^^^^^^^ **/utf-8 을 빼지 마라.**
//   ... 컴파일은 그대로 통과한다 — 그래서 빌드 로그로는 절대 못 잡고
//   브라우저 화면에서 처음 보인다.
```

BOM 은 넣지 않았다(POSIX 도구가 성가셔진다는 지적에 동의).

**실행 안내 위치 문제 하나 — 루트가 처리해야 한다.**
`조별과제샘플/README.md` 는 **루트 소유**라(`규칙 없음 → 기본 소유자`) 내가 못 고친다.
그래서 사용자가 복사해 쓸 빌드·실행 명령을 **내 소유인 `server.cpp` 헤더 주석**에 갖췄고,
명세 §10 체크리스트에도 넣었다. 다만 그 README 는 지금 옛 내용(`python -m http.server 9900`)이라
**그대로 따라 하면 새 서버를 안 쓰게 된다.** 갱신이 필요하다 — 요청은 발행하지 않았다.

### 2순위 · `<ctime>` ✅

공통 include 에 추가하고 이유를 주석으로 남겼다. **macOS 빌드 성공이 우연이었다**는 지적이 맞다 —
`<sys/time.h>` 는 `#else` 안이라 Windows 에는 없다.

### 3순위 · `user_id` 검증 ✅ (실행 확인)

명세 §2.3 `userid ::= 0*8( ALPHA / DIGIT / "_" / "-" )` 그대로 `valid_userid()` 를 만들어
`slot` 검증 바로 뒤에서 거절한다. 실제로 보내 본 결과:

```
9자 초과               len=10  → error bad_request
20자                   len=20  → error bad_request
쉼표 포함(구분자 깨짐)   len=4   → error bad_request
정상 8자               len=8   → ack result=0
```

쉼표 포함은 원 지적에 없던 항목인데 같이 막았다 — **길이만 검사하면 `u1,X` 같은 값이
라인의 필드 구분을 깨뜨린다.** 문법 전체를 검사하는 편이 맞다.

### 4순위 · WS 프레임 길이 상한 ✅

`WS_MAX_FRAME = 64 KiB`. 초과 선언이면 연결을 닫는다. 브라우저→서버는 예약/취소 JSON 뿐이라
수백 바이트면 충분하다.

### 5순위 · 진단 로그 ✅

```cpp
snprintf(b, sizeof(b), "MoveFileEx 실패 GetLastError=%lu%s", (unsigned long)e,
         e == 32 ? " (ERROR_SHARING_VIOLATION — 다른 프로그램이 파일을 잡고 있다)" : "");
```

32 를 특별히 풀어 쓴 것은 윈도우에서 백신·편집기가 파일을 잡는 것이 흔하다는 지적 때문이다.

### 6~8순위 · **전부 채택** (판단 근거)

- **`FD_SETSIZE 256`** — 채택. `<winsock2.h>` **앞**에 뒀다(순서가 바뀌면 무효라는 지적 반영).
  `FD_SET` 이 넘칠 때 **조용히 무시**한다는 게 결정적이다. 원인 없는 무응답으로 보이는 실패는
  디버깅 비용이 크다. 비용은 `fd_set` 크기뿐이다.
- **`NOMINMAX`** — 채택. 지금은 무해하지만 비용이 0 이고, 나중에 `std::min` 을 쓰는 순간
  **윈도우에서만** 깨진다. 여기서 못 잡는 종류라 미리 막는 게 맞다.
- **축소 경고(C4267)** — 채택. `char((unsigned char)n)` 로 명시 캐스트했다.
  하는 김에 **ping 페이로드를 125바이트로 자르는 처리**를 넣었다 — 원 지적엔 없지만
  제어 프레임은 125 이하만 정상인데 그대로 `char()` 로 넣으면 길이 바이트가 망가진다.
  값이 작아 실제로는 안 났겠지만 캐스트만 씌우면 그 문제가 **숨는다.**

### `now_ms()` / `epoch_ms()` 주의 ✅

두 함수와 파일 머리 양쪽에 주석을 넣었다.

```
// ⚠ now_ms() 와 epoch_ms() 는 **원점이 다르다. 절대 섞어 쓰지 마라.**
//   POSIX 에서는 둘 다 epoch 라 섞어도 티가 안 나지만, 윈도우에서는 그 순간
//   수십 년짜리 값이 나온다. **윈도우에서만 틀리는 버그**라 여기서 못 잡는다.
```

### 완료 기준 3·4 · 회귀 없음

- `c++ -std=c++11 -O2 -Wall -Wextra` — **경고 0건**, `--selftest` 통과(SHA-1 벡터 + 라인 8건)
- REQ-0017 검증 8항 전부 재확인 ✅ / REQ-0022 은퇴 기준 3항 ✅ — 상세는 REQ-0022 처리 결과

### 미검증 — Windows 는 여전히 못 돌린다

**1~5순위와 6~8순위 어느 것도 Windows 에서 컴파일·실행해 확인하지 못했다.**
macOS 에 그 헤더와 컴파일러가 없다. 즉 **이 수정들은 "지적을 반영했다"이지
"윈도우에서 동작을 확인했다"가 아니다.** 특히:

- `/utf-8` 로 한글이 실제로 안 깨지는지 — 확인 못 함
- `FD_SETSIZE` 순서가 실제로 먹는지 — 확인 못 함
- `MoveFileExA` 실패 로그가 실제로 찍히는지 — 확인 못 함

`<ctime>` 만은 **내가 직접 재현해서** 의존이 실재함을 확인했다(루트 보고를 그대로 믿지 않고 다시 돌렸다).
표준 입력으로 최소 예제를 컴파일한 결과:

```
$ (ctime 없이)  → error: unknown type name 'time_t'; did you mean 'size_t'?
$ (ctime 추가)  → exit=0
```

즉 `time_t`/`strftime`/`localtime` 은 `<ctime>` 없이는 보장되지 않고, 기존 macOS 빌드는
`<sys/time.h>` 가 우연히 끌어와 통과한 것이 맞다. 나머지 Windows 항목은 이렇게 확인할 방법이 없다.
