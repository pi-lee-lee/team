# REQ-0022 · 명세 개정 2 + 서버 구현: 예약 은퇴 규칙(occupied 1→0 소진) · result=3 의 slot 은 '??'

## 요청 내용

## 배경 — arduino-engineer 가 명세 v1 의 진짜 결함을 찾았다 (REQ-0020)

**`reserved` 를 끄는 경로가 서버의 `C` 뿐이라, 예약한 차가 들어왔다 나가도 그 칸은 영원히 예약 상태로 남는다.**
이후 그 칸의 모든 `R` 은 영원히 `result=2`. 오래 돌리면 **10칸이 하나씩 죽어 전 칸이 예약 불가**가 된다.

## 개정 ① — 예약 은퇴는 **서버**가 한다 (§7 에 새 항)

### 규칙 (이 한 줄이 전부다)

> **예약된 자리(`reserved=1`)에서 `occupied` 가 1→0 으로 바뀌면 그 예약은 소진된 것이다.
> 서버가 `C` 를 내려 은퇴시킨다.**

**`fulfilled` 같은 별도 플래그를 두지 마라.** 서버는 점유된 자리의 `R` 을 `result=1` 로 거절하므로
`reserved=1 ∧ occupied=1` 은 **예약자 입차 이후에만** 성립한다. 그래서 위 전이가 곧 이행 판정이다.

아두이노는 **변경 없다.** §7.4 "사람의 약속의 주인은 서버"가 그대로 유지된다 —
arduino-engineer 가 스스로 끄지 않고 올린 판단이 옳았다.

### 반드시 같이 명세에 박아야 할 것 두 가지 ⚠

이 둘이 빠지면 은퇴 로직 자체가 새로운 버그를 만든다.

**(1) 재부팅 시 `occupied` 기준선을 초기화한다.**
전이 감지는 직전 `S` 프레임의 `occupied` 와 비교해서 한다. 그런데 §7.4 재부팅으로
아두이노의 `occupied` 가 초기화되면, **낡은 기준선 때문에 재부팅 직후 첫 프레임에서
있지도 않은 1→0 전이가 감지되어 방금 재하달한 예약을 곧바로 은퇴시킬 수 있다.**
재부팅을 감지하면(새 연결 / `uptime` 감소 / `seq` 역행) **기준선을 새 프레임 값으로 리셋**하고,
그 프레임에서는 전이 판정을 하지 않는다.

**(2) 은퇴는 ACK 결과와 무관하게 서버 쪽에서 확정한다.**
`C` 의 ACK 가 §7.3 타임아웃으로 실패해도 **서버는 그 예약을 은퇴 처리한다.**
"ACK 를 못 받았으니 예약을 살려 둔다"로 만들면 **죽은 자리 버그가 은퇴 경로로 되돌아온다.**
아두이노 쪽 `reserved` 비트는 다음 `S` 프레임에서 어차피 서버가 다시 보게 되고,
어긋나 있으면 그때 다시 `C` 를 내리면 된다. **서버가 진실의 주인이다** — §7.4 와 같은 원리다.

## 개정 ② — `result=3` 의 `slot` 필드는 `??` (§2.3, §2.4)

BNF 에 유효 자리만 있어서 "잘못된 자리 ID" 를 담을 값이 없었다.

- **BNF 확장**: `slot ::= ("A"/"B")("1".."5") / "??"`
- `result=3` 인 ACK 의 `slot` 은 **항상 `??`** 다. 받은 토큰을 되비추지 않고, 유효한 자리를 지어내지도 않는다.
- **ACK 를 생략하는 선택지는 기각했다.** 침묵은 재전송 3회와 4.5초를 태우고,
  무엇보다 **의도적 거절과 링크 장애를 구분할 수 없게 만든다.**
- **근거**: 상관 키는 `rid` 다. 서버는 §4.1 매핑표에 원래 자리를 들고 있으므로
  ACK 의 `slot` 에 서버가 필요로 하는 정보가 없다. 폭 2자 고정이라 파서도 단순해진다.
- 브라우저에게는 서버가 **매핑표의 원래 자리**를 담아 보낸다(`??` 를 그대로 흘리지 마라).

## 개정 ③ — §11 에 v1 한계를 명시

**노쇼 만료는 v1 에 넣지 않는다.** §11 "아직 정하지 않은 것"에 다음 취지로 한 항 추가:

> 예약자가 끝내 오지 않으면 그 예약은 `C`(사용자 취소) 전까지 남는다. 만료 시각을 두지 않은 이유는
> (1) 만료 시간을 근거 없이 정하게 되고, (2) **노쇼 예약은 사용자가 취소로 스스로 회복할 수 있는
> 반면 입차 후 출차한 예약은 누구도 회복할 수 없어** 성격이 다른 문제이기 때문이다.
> 회복 불가능한 쪽만 v1 에서 닫았다. 만료가 필요해지면 `expires_at` 을 자리 객체에 더하는 순수 추가 변경이다.

**WS 스키마는 얼린 채로 둔다.** `expires_at` 을 지금 넣지 마라 — web-engineer 가 REQ-0019 작업 중이라
도중 변경이 내려간다.

### 완료 기준 5 · 서버 구현과 실행 검증

**a. 예약 → 입차 → 출차 → 은퇴** ✅ (WS 스냅샷을 그대로 관찰)

```
→ reserve B3 u1              → ack result=0
   B3 occupied=0 reserved=1 user=u1     ← 예약됨
   B3 occupied=1 reserved=1 user=u1     ← 입차 (예약자가 들어옴)
   B3 occupied=0 reserved=0 user=None   ← 출차 → **은퇴됨**
```

서버 로그:

```
02:04:56  ⏏ 예약 소진(occupied 1→0) — B3 은퇴시킨다 (user=u1)
02:04:56  →ARD C,2,B3,2C
```

**b. 같은 자리를 다시 예약할 수 있다** ✅ ← **이 개정의 요점**

```
→ reserve B3 u2              → ack result=0      ← 개정 전이라면 영원히 result=2
   B3 occupied=0 reserved=1 user=u2
```

**c. 재부팅 직후 재하달된 예약이 잘못 은퇴하지 않는다** ✅

A4 를 예약하고 **입차시킨 뒤**(occupied=1) 재부팅시켰다. 재부팅으로 아두이노의 occupied 는 0 이 된다 —
**기준선을 안 지웠다면 여기서 1→0 전이로 보여 방금 재하달한 예약을 죽인다.**

```
   A4 occ=1 res=1 uptime=11
   ── 재부팅 (uptime 11→1) ──
   A4 occ=0 res=1 uptime=1  ← 재부팅 후, 예약 살아있음
   A4 occ=1 res=1 uptime=3  ← 재입차
   ...(두 번째 재부팅도 동일)
재부팅 후 reserved 전부 1: True
```

서버 로그가 재접속마다 기준선을 세우고 판정을 건너뛴다:

```
02:07:50  ⟳ 재부팅 감지(새 연결) — 살아 있는 예약 1건 재하달
02:07:50  = 은퇴 기준선 설정 — 이 프레임은 전이 판정을 건너뛴다
```

### ⚠ 구현 중 내가 만든 버그 하나 — 테스트가 우연히 통과했다

첫 구현에서 **`base_valid` 를 `uptime`/`seq` 역행 경로에서만 껐고 `accept`(새 연결) 경로에서는
끄지 않았다.** 그런데 c 시험이 **통과했다.** 우연이었다:

- 새 연결에서는 `ard_uptime` 을 -1 로 초기화하므로 `reboot` 판정이 **false** 가 된다
  → 낡은 기준선으로 전이 판정이 그대로 돌았다.
- 그런데 재하달 `R` 이 `accept` 시점에 이미 나가 있어서 **그 자리에 미결 요청이 있었고**,
  은퇴 조건의 `!has_pending_for()` 가 우연히 막아 줬다.
- ACK 가 첫 `S` 프레임보다 먼저 도착했다면 그 방어도 없어 **예약이 죽었을 것이다.** 타이밍 경쟁이었다.

로그를 읽다가 "기준선 설정" 줄이 재접속 때 안 찍히는 것을 보고 코드를 다시 확인해 찾았다.
**시험 통과를 근거로 넘어갔으면 그대로 남았을 버그다.** `accept` 에서 `base_valid=false` 로 고치고
재검증했더니 이제 재접속마다 결정적으로 기준선이 서고, 통과가 우연이 아니게 됐다.
