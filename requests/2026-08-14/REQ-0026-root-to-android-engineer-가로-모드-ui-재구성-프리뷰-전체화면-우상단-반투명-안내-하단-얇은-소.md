# REQ-0026 · 가로 모드 UI 재구성: 프리뷰 전체화면 + 우상단 반투명 안내 + 하단 얇은 소형 버튼 바

**요청자** `root` → **담당** `android-engineer`

## 요청 내용

## 사용자 지적 — 근거를 실측으로 붙인다

REQ-0025 의 가로 레이아웃(프리뷰 왼쪽 / 컨트롤 오른쪽)을 쓰고 나온 지적이다.

루트가 실제 스크린샷(2400x1080)을 픽셀로 재 봤다:

```
프리뷰/패널 경계 x ≈ 1456
  프리뷰      1456px = 59.9%
  버튼 패널    944px = 39.3%      ← 화면 폭의 40% 가까이를 버튼이 먹는다
```

사용자 표현은 "화면의 반"이고 실측은 39.3% 다. **지적의 취지는 정확하다** — 카메라로 번호판을
겨누는 앱에서 화면의 40%가 버튼인 것은 맞지 않다. 버튼 하나하나도 너무 크다.

## 요구 (사용자 원문 취지)

1. **버튼 크기를 줄여라.** 지금 너무 크다.
2. **우측 영역을 줄여라.** 화면의 반이나 차지할 이유가 없다.
3. 촬영 시 **우상단에 배경을 투명하게 해서 텍스트 안내를 출력**한다.
4. **하단에 길게, 작은 버튼으로 각 버튼이 노출**되는 형태가 적절해 보인다.
5. 가로 모드에 어울리는 UI 로 최적화.

즉 **좌우 분할을 버리고, 프리뷰를 전체화면으로 깔고 그 위에 오버레이**하는 구성이다.
세로 레이아웃이 이미 그런 형태(상단 반투명 안내 + 하단 버튼 줄)이므로 방향이 어긋나지도 않는다.

## 구성 지침

```
┌─────────────────────────────────────────────────┐
│                              ┌────────────────┐ │  ← 우상단 오버레이
│                              │ 정지 · 불안정   │ │    반투명 배경
│         프리뷰 전체화면        │ conf 0.00 …    │ │    폭은 화면의 일부만
│         (match_parent)       └────────────────┘ │
│                                                 │
│                                                 │
│ ┌─────────────────────────────────────────────┐ │  ← 하단 얇은 바
│ │ ⟳가로  설정  다시읽기  샘플  ◀  ▶            │ │    작은 버튼 한 줄
│ └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

- `PreviewView` 를 **화면 전체**에 깐다. 좌우 분할 컨테이너를 없앤다.
- **안내 텍스트: 우상단.** 배경은 **반투명**(완전 불투명 패널 금지, 완전 투명도 금지 — 아래 가독성 참조).
  폭을 제한해라 — 화면 폭 전체로 늘어나면 오버레이의 의미가 없다.
- **버튼: 하단 한 줄.** 6개(`⟳ 가로`·`설정`·`설정 다시 읽기`·`샘플 모드`·`◀`·`▶`)가 전부 보여야 한다.
  메뉴나 오버플로로 숨기지 마라 — 사용자가 "각각의 버튼들이 노출되는 것"을 명시했다.
  라벨이 길면 줄이거나 아이콘화해도 된다(단 접근성 라벨은 유지).
- **세로 레이아웃은 건드리지 마라.** 이번 요구는 가로 모드에 대한 것이다.

## 반드시 지킬 것 두 가지 ⚠

### 1) 가독성 — 오버레이의 함정이 여기다

프리뷰 위에 글자를 얹으면 **밝은 장면에서 흰 글자가 사라진다.** 사용자가 "배경을 투명하게"라고
했지만 그건 *불투명 패널이 화면을 가리지 말라*는 뜻이지 *읽을 수 없게 만들라*는 뜻이 아니다.

반투명 스크림(어두운 반투명 배경)이나 그라디언트, 또는 텍스트 그림자를 써서
**밝은 장면과 어두운 장면 양쪽에서 읽히는지 실제로 확인해라.** 샘플 모드의 밝은 실내 장면과
어두운 장면 각각에서 스크린샷을 찍어 판단하면 된다.

### 2) 터치 영역은 줄이지 마라

버튼이 **보이는 크기**는 줄이되, **터치 영역은 48dp 아래로 내려가면 안 된다**(안드로이드 접근성 기준).
시각적으로 작아 보이게 하면서 패딩으로 터치 영역을 확보해라. 작은 버튼이 안 눌리는 UI 는
"작아서 좋다"가 아니라 그냥 고장이다.

## 인셋 — 가로에서 더 까다롭다

전체화면 오버레이가 되면 인셋 처리가 REQ-0025 보다 중요해진다. 가로에서는 노치가 **한쪽 옆면**에
오고 제스처 바가 아래에 온다. 우상단 오버레이가 노치에, 하단 바가 제스처 바에 물리지 않게 해라.
REQ-0015 에서 고친 문제와 같은 성격이므로 그때 쓴 방식을 재사용하면 된다.

## 참고

방향 기본 가로 · 사이클 버튼 전환 · 기울기 무시 · 선택 보존 · 인식 동작.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

카메라로 번호판을 겨누는 앱에서 화면 폭의 39.3%가 버튼 패널이면 피사체를 담을 공간이 그만큼 줄어든다. 가로 모드는 원래 넓은 화각을 쓰려고 쓰는 것인데 지금 구성은 그 이점을 스스로 깎아먹는다. 세로 레이아웃은 이미 오버레이 형태이므로 가로만 좌우 분할인 것은 일관성도 떨어진다.

### 1) 프리뷰가 화면 전체를 채운다 — 통과 (숫자로)

스크린샷(2400×1080)을 픽셀로 재서 루트 실측과 같은 방식으로 비교한다.

| | 이전(REQ-0025) | 지금 |
|---|---|---|
| **완전 불투명 패널** | 폭의 **39.3%** (944px) | **0%** — 없다 |
| 프리뷰가 차지하는 영역 | 폭의 59.9% | **100% (2400×1080 전체)** |

오버레이가 덮는 면적(전부 반투명, 프리뷰가 비쳐 보인다):

```
정보 패널  x 1519..2400, y 0..296   →  881×296 = 화면 면적의 10.1%
하단 버튼 바  y 874..1080            →  높이 206px = 화면 높이의 19.1%
```

경계값은 스크린샷의 밝기 급변 지점을 검출해 얻었다(`y=8` 행에서 x=1519, `x=W-60` 열에서 y=296,
여러 열의 중앙값으로 바 상단 y=874).

### 2) 우상단 반투명 안내 — 통과

`layout_gravity="top|end"`, 배경 `#B3000000`(70% 검정 스크림) + 글자 그림자.
폭은 `wrap_content` + `maxWidth=380dp` 로 제한했다 — 화면 폭 전체로 늘어나면 오버레이의 의미가 없다.

### 3) 버튼 6개가 하단 한 줄에 전부 보이고 눌린다 — 통과

`⟳ 세로` · `설정` · `다시읽기` · `샘플 모드` · `◀` · `▶` 여섯 개가 한 줄에 있다.
메뉴·오버플로로 숨기지 않았다. 라벨만 줄였다(`설정 다시 읽기` → `다시읽기`, 뜻은 같다).

**`input tap` 으로 실제 동작을 확인한 것 (요구는 3개, 5개 확인):**

| 버튼 | 탭 좌표 | 관측된 결과 |
|---|---|---|
| `샘플 모드` | (1661, 945) | 샘플 모드 진입 — `[샘플판정] PASS 1/26 … 800가4568 conf 0.87` |
| `▶` | (2266, 945) | 샘플 1 → 2 (`kor8-hwamul-plain.png` 로드 로그) |
| `◀` | (2022, 945) | 샘플 2 → 1 (`kor8-hwamul-band.png` 로드 로그) |
| `샘플 모드`(재탭) | (1661, 945) | 샘플 모드 해제, 카메라 복귀 |
| `⟳ 세로` | (343, 945) | `cur=2400x1080` → `cur=1080x2400` 세로 전환 |

`◀`/`▶` 는 가장 좁은 버튼(weight 0.6)인데 정상 동작한다.

### 4) 터치 영역 48dp 이상 — 통과

레이아웃 값이 명시적이다. 여섯 버튼 모두:

```xml
android:layout_height="48dp"
android:minWidth="48dp"
```

**렌더링 결과로도 교차 확인했다.** 바 높이를 레이아웃에서 예측하면
`상단패딩 3dp(8px) + 버튼 48dp(126px) + 하단패딩 3dp(8px) + 제스처바 인셋 63px = 205px` 이고,
스크린샷 실측 바 높이는 **206px** 다. 버튼이 48dp 보다 작았다면 바가 그만큼 짧아졌을 값이다.

시각적으로 얇아 보이게 만든 것은 글자 크기(12sp)와 좌우 패딩(2dp)이고, **터치 높이는 건드리지 않았다.**

> `uiautomator dump` 는 쓰지 못했다 — `ERROR: could not get idle state`. 카메라 프리뷰와 상태
> 텍스트가 매 프레임 갱신되어 창이 idle 상태가 되지 않는다. 그래서 레이아웃 값 + 렌더 높이
> 교차검증 + 실제 탭 동작으로 대신했다(요청이 "레이아웃 값 또는 uiautomator bounds" 를 허용).

### 5) 밝은 장면·어두운 장면 양쪽 가독성 — 통과

**먼저 최악의 경우를 계산했다.** 스크림 알파가 고정이므로 프리뷰가 순백(255)일 때가 최악이고,
그 값은 계산으로 확정할 수 있다(WCAG 상대휘도 기준):

| 요소 | 순백 위에서의 배경 밝기 | 흰 글자 대비비 |
|---|---|---|
| 정보 패널 (`#B3000000`) | 77 | **8.5 : 1** |
| 버튼 (`#B3000000` 바 + `#73000000` 버튼) | 42 | **14.3 : 1** |

WCAG AA 일반 텍스트 기준이 4.5:1 이므로 **가장 밝은 장면에서도 기준을 넘는다.**

**실측으로도 확인했다.** 에뮬레이터 가상 장면의 밝은 창(원본 밝기 207) 위에 걸친 버튼들:

```
⟳세로 버튼 : 배경 24 / 글자 255
설정 버튼   : 배경 15 / 글자 255
```

어두운 목재 벽(원본 밝기 98) 위의 정보 패널: `배경 18 / 글자 255`.
한 프레임 안에서 바가 밝은 창과 어두운 벽을 동시에 가로지르므로 양쪽이 같이 확인된다.

처음 만든 버전은 버튼 배경을 흰색 반투명(`#4DFFFFFF`)으로 뒀는데, 밝은 창 위에서 밝은 회색 버튼 +
흰 글자가 되어 대비가 무너졌다. 스크린샷을 보고 어두운 스크림(`#73000000`)으로 바꿨다 —
요청이 경고한 함정이 버튼에서 그대로 재현된 것이다.

### 6) 노치·제스처 바에 물리지 않음 — 통과

가로에서는 노치가 **옆면**에 오므로 위아래만 처리하면 안 된다. `displayCutout()` 인셋을
`systemBars()` 와 함께 받아 큰 쪽을 쓴다 — 정보 패널은 위·오른쪽, 버튼 바는 좌·우·아래.

이 기기의 가로 인셋은 `overrideNonDecorInsets=[132,0][0,63]`(왼쪽 132, 아래 63)이고,
바 왼쪽 패딩이 그만큼 밀려 첫 버튼이 왼쪽 인셋 영역 밖에서 시작한다(첫 버튼 좌표 x=343).
하단 제스처 바 영역에도 버튼이 걸치지 않는다(버튼 하단 1008px, 화면 1080px).
