# REQ-0024 · REQ-0020 ② 지금 반영하라 — result=3 의 slot 을 '??' 고정 + ACK 필수

**요청자** `root` → **담당** `arduino-engineer`

## 요청 내용

## 판정: 지금 반영해라. 명세 본문 갱신을 기다리지 마라.

네가 REQ-0020 답신에서 지적한 것이 맞다 — 지시대로 코드를 안 건드린 결과
`client.ino` 가 **판정과 어긋난 상태로 남아 있다.** 그리고 "다음에 손댈 때"는 대개 오지 않는다.
`## ⚠ 미반영 항목` 을 남긴 판단이 좋았다. 그걸 지금 소진하자.

**기다릴 이유가 없다.** REQ-0022 로 socket-engineer 가 하는 것은 **이미 내려진 결정을 문서에 적는 일**이다.
BNF 는 `slot ::= ("A"/"B")("1".."5") / "??"` 로 확정됐고 바뀌지 않는다.
기다리면 코드가 틀린 줄 알면서 틀린 채로 있는 구간만 길어진다.

## 반영할 것

- `result=3` 인 ACK 의 `slot` 필드는 **항상 `??`**
- 받은 토큰 되비추기 제거, 그 용도로만 쓰이던 `isAlnum()` 도 같이 제거
- **표현 불가를 이유로 ACK 를 생략하지 마라** — 침묵은 재전송 3회와 4.5초를 태우고,
  무엇보다 의도적 거절과 링크 장애를 구분할 수 없게 만든다

REQ-0018 md 끝에 네가 적어 둔 교체 블록 그대로면 된다. 반영하고 그 절을 해소 처리해라.

## 겸사겸사

`net/fake_arduino.py` 가 이제 있다. 네 스케치와 같은 프로토콜의 독립 구현이다.
`??` 를 넣은 뒤 그 스크립트로 한 번 대조해 두면 좋겠다 — 강제는 아니다.

**명령을 엮지 마라(a && b).** 하나씩 실행한다.

## 왜 필요한가

코드가 판정과 어긋난 채로 남으면 나중에 통합 시험에서 result=3 경로가 명세와 다르게 동작하고, 그때는 왜 다른지 아무도 기억하지 못한다. 6줄짜리 교체라 지금 하는 비용이 가장 싸다.

### 바뀐 것 — `processCommand()` 의 `if (idx == 0xFF)` 블록 하나

```c
  if (idx == 0xFF) {
    // §2.4 result=3 — 잘못된 자리 ID / 해석 불가.
    // REQ-0020 ② 판정: slot ::= ("A"/"B")("1".."5") / "??". 고정 표식을 쓰고 ACK 를 생략하지 않는다.
    // 되비추지 않는 이유: 상관 키는 rid 이고, 서버가 §4.1 매핑표에 원래 자리를 이미 들고 있다.
    // 침묵하지 않는 이유: 재전송 3회·4.5초를 태울 뿐 아니라, 의도적 거절과 링크 장애를
    //                     서버가 구분할 수 없게 되어 "센서가 죽었다"고 오해한다.
    s0 = '?';
    s1 = '?';
    result = 3;
#if DEBUG
    Serial.print(F("[BAD SLOT] rid=")); Serial.println(rid);
#endif
  } else {
```

- **`return` 이 사라진 것이 이 변경의 핵심이다.** 예전에는 이 경로에서 함수를 빠져나가 ACK 가 안 나갔다.
  지금은 반드시 `cachePut()` → `sendAck()` 로 흘러간다. 멱등 캐시에도 `result=3` 이 정상적으로 들어가므로
  같은 rid 로 재전송이 와도 같은 `A,...,??,3,..` 를 다시 낸다.
- `isAlnum()` 은 유일한 호출자를 잃어 **삭제**했다. `--warnings all` 로 재컴파일해 미사용 경고가 없음을 확인했다.
- `slotTok` 은 남겼다 — `idx` 를 구하는 `slotIndexOf(slotTok[0], slotTok[1])` 에서 여전히 쓴다.
- `[DROP] slot 표현 불가 — ACK 없음` 디버그 줄은 이제 거짓말이라 `[BAD SLOT] rid=<n>` 으로 바꿨다.
- 버퍼·`snprintf` 포맷은 손대지 않았다. `%c%c` 라 `??` 가 그대로 들어간다.

### 체크섬 (기준 5)

**[R1] `result=3` — 해석 불가한 자리 ID, rid=42**

```
대상  : "A,42,??,3,"
바이트: 41 2C 34 32 2C 3F 3F 2C 33 2C
누적  : 41 6D 59 6B 47 78 47 6B 58 74
체크섬: 74
라인  : A,42,??,3,74        (13바이트, LF 포함)
```

경계값 둘도 같이 계산했다(길이가 §2.5 범위 안에 있는지 확인하려고):

```
A,7,??,3,45         (12바이트)  ← 최단
A,65535,??,3,42     (16바이트)  ← rid 최대. A 프레임 최장이지만 64바이트 한도(§2.1-6)에 한참 못 미친다
```

### `net/fake_arduino.py` 와 교차 대조 (겸사겸사 항목 — 했다)

socket-engineer 의 독립 구현을 import 해서 `cksum()`/`build()`/`verify()` 로 대조했다.

```
A,42,??,3,74                       아두이노=74  소켓=74  OK  (13B)
A,7,??,3,45                        아두이노=45  소켓=45  OK  (12B)
A,65535,??,3,42                    아두이노=42  소켓=42  OK  (16B)
A,7,A1,0,36                        아두이노=36  소켓=36  OK  (12B)
A,43,B3,1,06                       아두이노=06  소켓=06  OK  (13B)
S,0,0110000010,0000000000,13,P1,01 아두이노=01  소켓=01  OK  (35B)
```

`build(prefix)` 가 만든 줄도 내 줄과 문자 단위로 같았다. 그리고 **`verify()` 가 `??` 줄을 받아들인다**:

```
A,42,??,3,74     verify -> ['A', '42', '??', '3']
A,7,??,3,45      verify -> ['A', '7', '??', '3']
A,65535,??,3,42  verify -> ['A', '65535', '??', '3']
```

즉 `??` 표식이 소켓 쪽 파서에서 걸러지지 않는다는 것까지 확인됐다. 새 표식을 넣고 상대 구현이
그걸 버리면 아무 의미가 없는데, 그 위험이 닫혔다.

### 검증하지 않은 것

- ⚠ **실장 검증 미실시.** 여전히 보드가 물려 있지 않다. 컴파일과 프로토콜 라인 대조까지만이다.
- 위 대조는 **라인 문법·체크섬 수준**이다. 실제 TCP 연결을 맺고 `fake_arduino.py` 와 주고받아 본 것은 아니다.
- `result=3` 경로 자체는 서버가 §5.3 `bad_request` 로 먼저 거르므로 통합 구동에서 도달하지 않는
  방어 경로다. 그래서 이 변경은 **동작이 바뀌는 것을 관측할 수 없고**, 명세 일치만 확보한다.
