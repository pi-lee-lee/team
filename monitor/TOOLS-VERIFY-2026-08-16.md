## 2. `tick.py` — 빠진 Edit 을 복원했다

루트가 예고한 대로 **마지막 Edit 1건(02:37Z, 228자)이 빠져 있었다.** 증상으로 특정했다:

- 인수인계의 판정창은 **11:27~15:27** 인데, 복원본의 `TRACK` 은 `esplink_tap`(11:13:20~)이었다
- 14:54 시점 인수인계 수치가 **3.46h** 였다 → 시작이 11:27 이어야 나오는 값
  (11:13:20 시작이면 3.68h). 즉 **빠진 Edit 은 11:27 창 추가 + TRACK 변경**이다

복원한 것:

1. `WINDOWS` 에 `judge=2026-08-16T11:27:00..2026-08-16T15:27:00` 추가(확정·닫힘)
2. `WINDOWS` 에 `after_judge=2026-08-16T15:27:00..` 추가 — 판정창 뒤 사건을 섞지 않기 위해
3. `TRACK = "judge"` 로 변경 → 이제 `진행 4.00h / 4.0h (100%)` 로 정확히 닫힌다

추가로 **내가 고친 것 하나**(빠진 Edit 과 무관, 규칙 #4 위반이라 고침):

4. 시리얼 보고가 `raw 0B · 0줄 · tap 살아있음` 으로 나왔다. 이 `0` 은 **"안 쌓였다"가 아니라
   "파일이 unlink 돼 못 읽는다"** 인데 둘이 구분되지 않았다. 세 갈래로 갈라 출력하게 고쳤다.

## 4. 루트에게 물을 것 — `monitor/out*` 을 인덱스에 둘 것인가

지금 `git add monitor/` 로 **산출물까지 인덱스에 올라가 있다**(`out-report.*`, `out/*`,
`out-history.tsv` 등). 이것들은 tick 마다 다시 쓰이므로 인덱스가 계속 흔들린다.

보호가 필요한 것은 **도구 소스 9개**이지 매번 재생성되는 산출물이 아니다.
`.gitignore` 는 루트 소유이므로 **내가 정하지 않는다.** 판단만 요청한다.
(단 `.gitignore` 로 무시하면 그 순간 `git clean` 취약해진다 — 이번 사고가 정확히 그 경로였다.
 그래서 "무시하자"가 자동으로 정답은 아니다.)
