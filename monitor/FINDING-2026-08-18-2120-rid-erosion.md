# 발견 · **`rid` 자릿수가 자라 크기 이득을 잠식한다 — 그리고 `N=3` 의 이득은 *이미* 사라졌다** (2026-08-18 21:20)

**socket 가설**(자료 전 등록): *"ACK 길이가 `rid` 자릿수를 따라 자란다. `N=3` 은 `rid ≤ 999` 에서만 대역 밖."*
**→ 내 시리얼로 검증했다. 가설은 맞고, 시점 판단만 틀렸다.**

## 1. 실측 — **창 안에서 저절로 자란다**
`ack=4` 거래의 `tx` 를 시간순 5등분:
```
창 I   19:23:54  tx 93  (seq≈32)     19:28:32  97     19:33:18  97
       19:39:10  98    19:43:40  **99** (seq≈999)          → **+6B**
창 J   21:16:27  tx **75** (seq≈127)  21:16:58  **79**  이후 79 유지 (seq≈267)  → **+4B**
```
> ### **설정을 아무것도 안 바꿨는데 지표가 움직인다.** 창이 길어지면 진입률이 저절로 오른다.

## 2. 🔴 그래서 `N=3` 제안을 **지금 상태로 재계산하면 안 통한다**
```
창 J 현재 : ack=0 tx=23 · ack=4 tx=**79**   →  ACK 1건당 **14.0B** (초반 13.0B 가 아니다)
  N=4 → 23 + 56 = 79  → CIPSEND 80  🔴 >=64
  N=3 → 23 + 42 = **65** → CIPSEND **66**  🔴 **여전히 >=64**
  N=2 → 23 + 28 = 51  → CIPSEND 52  ✅ 대역 밖
```
> ### 🔴 **socket 의 표에서 "rid 4자리 → N=3 은 65B, 이득 소멸" 칸에 *이미 들어와 있다*.**
> **`N=3` 은 "나중에 무너지는" 것이 아니라 **지금 이 창에서 이미 안 통한다**.**
⚠ **내가 50초 시점에 13.0B 로 재고 "N=3 이면 62B" 라고 쓴 것을 정정한다** — **그때는 창 초반이었다.**
**같은 창의 초반 값으로 설계 결정을 하면 안 된다.**

## 3. 🔑 손잡이는 셋이고 **크기 축은 둘이 곱해진다**
```
① 하행 건수 상한 N     → 총합에 **N × (ACK 크기)**       (socket)
② rid 표현 폭          → ACK 1건당 **1B/자릿수**, **N배로 곱해진다**  (socket)
③ S 프레임 크기        → hex 로 39 → 23B 로 이미 줄였다   (arduino · 효과 확인됨)
```
**③은 했고 효과가 있었다(−16B). 그런데 ①②의 곱이 그걸 도로 먹었다.**
🔑 **`rid` 를 3자리로 묶으면(`% 1000`) ACK 이 13B 로 고정되고, `N=3` 이 62B 로 다시 대역 밖이 된다.**
⚠ **추정이다** — `rid` 순환이 서버 짝짓기에 미치는 영향은 **socket 영역**이다.

## 4. 이 창에서 하지 않을 것
**규약을 안 바꾼다.** 지금 바꾸면 이 창이 어느 것과도 비교가 안 된다. **다음 창 손잡이로만 적는다.**

## 5. 🔴 결론 문장에 붙일 범위
> **"hex 가 프레임을 반으로 줄였다"는 참이다.**
> **"hex 가 위험 대역 진입을 줄였다"는 거짓이다 — 진입률 92.1% → 95.2%.**
> **묶는 조건은 `S` 가 아니라 `N × ACK크기` 이고, 그 둘 다 socket 의 손잡이다.**

# 6. 🔮 **자연 실험 — `rid` 가 이 창 안에서 1000 을 넘는다. 넘기 *전에* 등록한다** (21:21:48)

```
현재 ACK rid : 1 → **984**    자릿수 분포 {1자리 9 · 2자리 90 · **3자리 921**}
현재 ack=4 tx = 79   →  ACK 1건당 (79−23)/4 = **14.0B** (rid 3자리)
```

## 🔮 예측 (자료 전 · 반증 가능 · 몇 분 안에 판정된다)
> ### **`rid` 가 1000 을 넘으면 ACK 이 15B 가 되어 `ack=4` 의 `tx` 가 `79 → 83` 으로 오른다.**
```
검산 : 23 + 4×15 = 83   →  CIPSEND 84
```
**반증**: `tx` 가 79 에 머물면 **"ACK 길이가 rid 자릿수를 따른다"는 모델이 틀렸다.**

🔑 **이건 우리가 만든 자극이 아니라 *시간이 만드는* 실험이다.** 설정을 아무것도 안 바꾸는데
**지표가 계단으로 움직인다** — 그 계단을 실제로 보면 모델이 확정된다.

⚠ **그리고 이것이 §5 결론을 강화한다**: **hex 로 번 −16B 는 `rid` 자릿수 하나가 4번 오르면
(4건 × 4B) 전부 상쇄된다.** **단조 증가 `rid` 는 이 상쇄를 *영구적으로, 되돌릴 수 없이* 진행시킨다.**

## 6.1 ⚠ 부수 관측 — **`rid` 가 완전 단조는 아니다**
`ACK` 줄의 `rid` 는 **엄밀히 단조 증가가 아니다**(되감김 검출됨).
**한 배치 안에서 순서가 섞이거나 재전송이 끼는 것으로 보인다** — ⚠ **추정이다.**
🔑 **socket 의 "지금은 단조라 늦은 ACK 이 아무 데도 안 맞고 무해하다" 는 전제에 걸린다.**
**완전 단조가 아니면 그 무해성 논거를 다시 봐야 한다** — **socket 영역이라 확인만 넘긴다.**

# 7. ✅ **예측 적중 — 계단이 왔다. 값까지 정확히** (21:24:07 판정)

**등록 시각 21:21:48 · 사건 시각 21:21:52 · 판정 21:24:07.** **등록이 사건보다 4초 앞선다.**
```
🔮 등록한 예측 : rid 가 1000 을 넘으면 ack=4 의 tx 가 79 → **83**

실측
  rid < 1000   : ack=4  tx 중앙값 **79**  (표본 237)
  rid >= 1000  : ack=4  tx 중앙값 **83**  (표본 102)   분포 {83: 101 · 80: 1}
  rid 4자리 첫 도달 : **21:21:52**        ACK rid 1 → 1,429
```
> ### ✅ **79 → 83. 예측값과 정확히 같다. 102 표본 중 101 이 83 이다.**
> ### **"ACK 길이는 `rid` 자릿수를 따르고, 1B/자릿수가 `N` 배로 곱해진다" — 확정.**

## 7.1 🔴 그래서 이 창에서 **hex 의 이득이 실시간으로 깎이는 것을 봤다**
```
hex 가 번 것        : S 39 → 23B          **−16B**
rid 3→4자리가 먹은 것 : ACK 14 → 15B ×4    **+4B**   ← **8분 만에**
남은 이득           : −12B
```
**같은 창 안에서, 아무 설정도 안 바꾸고, 이득의 1/4 이 사라졌다.**
🔮 **5자리(rid 10,000)가 되면 또 −4B.** **`rid` 는 단조 증가라 이 잠식은 되돌아오지 않는다.**

## 7.2 🔑 이것이 오늘 가장 강한 확인인 이유
```
① 사건 **전**에 값을 적었다 (등록 21:21:48 · 사건 21:21:52)
② 방향이 아니라 **값**을 맞혔다 (83)
③ 표본이 101/102 로 한쪽에 몰렸다 — 잡음이 아니다
④ 두 계측기가 각각 절반을 댔다 — **socket 의 발행 rid** + **내 시리얼의 tx 바이트**
```
⚠ **우리가 만든 자극이 아니라 *시간*이 만든 실험이다.** 손댈 것이 없어 교락이 없다.

## 7.3 ✅ 되감김도 socket 이 원인을 확정했다 — **내 관측은 맞고 해석이 달랐다**
```
socket 실측 : 되감김 11건 · 폭 전부 −7~−11 · **같은 rid 두 번 온 것 0건** · 재전송 13
```
**발행은 단조이고, 재전송이 큐 뒤에 붙어 *도착 순서*가 뒤섞인 것이다.**
🔑 **내 것은 "장치가 답한 순서", socket 것은 "발행 순서" — 다른 것을 보고 있었다.**
**"같은 것을 보고 있는지부터 갈라라"가 또 맞았다.**
✅ **그리고 그 지적이 socket 의 설계에 유도값을 하나 줬다**:
**rid 재사용 격리 시간 ≥ `ACK_TIMEOUT × ACK_MAX_TRIES` = 7.2초.**
