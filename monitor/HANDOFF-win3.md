## 2.8 🔴 상행 주기는 **1Hz 가 아니라 약 1.11s** — `2s` 공백은 **맥놀이**다

국면1(무주입) 실측. **이걸 모르고 공백을 세면 11% 가 가짜 양성이다.**

```
간격 평균 = 1.112s   (663s / 596 간격)
분포      = 1s 590건 · 2s 77건 · **3s 이상 0건**
`2s` 사이 프레임 수 = 9 에 82% 몰림
```

주기 1.11s 를 **1초 해상도로 표본화**하면 9프레임마다 한 번 `2s` 로 읽힌다.
**장치는 국면1 동안 한 번도 안 멈췄다.**

- ⚠ **"1Hz" 를 상수로 인용하지 마라.** 최대공백·3500ms 오프라인 판정의 여유가 달라진다.
- 🔑 **기저에 `>=3s` 가 0건**이라, WS 블로킹 1초 정지는 (1.11+1.0) → **`>=3s` 로 튄다.**
  → 도구 `monitor/frame_gaps.py` 문턱을 **`>=3s`** 로 두고 맥놀이 진단을 붙였다.
- 국면2 에서 볼 것: **`>=3s` 공백이 주입 시각에 몰리는가** + **`+WS 업그레이드 완료` 가
  300s 로 규칙적인가**(불규칙한 줄은 **주입기가 아니다** — 남의 부하다).

### 🔴🔴 `2s` 칸에는 **두 가지가 섞인다** — 판정문에 이 문장을 그대로 넣어라

| | 무엇 | 사건인가 |
|---|---|---|
| ① | **맥놀이** — 1초 해상도 × 1.113s 주기, 약 9프레임마다 | **아니다**(아티팩트) |
| ② | **`skip`** — 2단계 게이트가 한 주기를 실제로 건너뜀(`64fc70b` 부터) | **진짜 사건** |

**무늬가 같다. 서버 로그만으로는 원리적으로 못 가른다** — `Δuptime` 도 같은 맥놀이를 타고
`seq` 는 둘 다 연속이다. **가르는 유일한 표지는 시리얼의 `[TX-WAIT] … 건너뛴다` 와 `[CNT] skip=`.**

> 🔴 **링크가 나빠질수록 `skip` 이 늘고 그만큼 `2s` 가 는다. 그것을 "맥놀이가 더 보인다"로
> 읽으면 정확히 거꾸로다 — 병리가 시작되는 신호를 아티팩트로 처리하는 것이다.**

✔ `frame_gaps.py` 는 **맥놀이 검정 전에 `skip` 을 빼고 뺀 건수를 찍는다.**
✔ `>=3s` 문턱의 근거는 **"기저 2s 가 전부 아티팩트라서"가 아니다** —
  **`skip` 은 `2s` 를 만들지 `3s` 를 안 만들고, 기저에 `>=3s` 가 0건**이기 때문이다.

### 🔑 2단계 게이트가 실기에서 도는 것이 원문으로 확인됐다 (n=1)

```
00:39:54  [TX] S,904,…,1012 · AT+CIPSEND=39
00:39:55  [TX-WAIT] 앞 전송의 SEND OK 를 아직 못 봤다 — 이번 주기는 건너뛴다
00:39:55  "SEND OK"                      ← 앵커의 SEND OK 가 지연 도착
00:39:56  [TX] S,905,…,1014              ← seq 연속 · uptime +2
```

**A 창 병리가 시작되던 바로 그 모양**(앵커 `SEND OK` 가 같은 초에 안 오고 다음 주기가 먼저 도래)
인데, 옛 칩에서 `[TX-RESYNC]` → `실패 1/3` 로 가던 자리를 **게이트가 건너뛰고 지나갔다.**
`okto=0` 이므로 **상한이 아니라 `SEND OK` 도착으로 풀렸다.** `seq` 904→905 **연속 — 프레임 손실 없음.**

🔴 **그래도 "막았다"로 쓰지 마라**(arduino 가 스스로 그은 선). 옛 칩에서 `SEND OK` 가 늦었다고
**반드시** 프롬프트를 놓치는 것은 아니다. 받칠 수 있는 것은
**"병리가 시작되는 모양이 왔고 게이트가 실패를 계상하지 않고 처리했다"** 까지고 **n=1** 이다.

주입 시각을 socket 의 주입기 로그에서 가져오면 **서로 다른 출처의 시각을 빼는 것**이고,
그건 CLAUDE.md 가 경고하는 그 형태다. 게다가 주입기의 `→ 주입` 은 **WS 요청 시각**이고
서버가 전선에 내보낸 시각은 그 뒤다 — 보통 같은 초지만 **보장은 없다.**
→ **`auto` 는 같은 서버 로그의 `→ARD T,` 에서 뽑는다. 시계가 하나다.**

⚠ **그러면 socket 의 `~/parking-logs/downlink-inject.log` 는 분모용이다** —
서버 로그에 `→ARD T` 가 **없을 때** 이유를 말해 주는 유일한 기록이다:
`= 미주입`(서버 거절 · **D0~D3 어디도 아니다**) / `! 이상` / **주입기가 죽어 시도조차 없었나**.
형식 `YYYY-MM-DD HH:MM:SS␣␣<표지>␣<본문>` → ISO 는 `line[:10]+"T"+line[11:19]`.

⚠ `coincidence.py` 는 **인자 없이 돌리면 A 창을 재현**한다(교정용). 기본값을 고치지 마라.

### 참고 — `00:21:21` 주입은 **프레임 공백을 만들지 않았다**

옛 주입기(WS 를 붙들던 판)로 넣은 그 1건을 `auto` 로 재 봤다:
`>=3s` 공백 **0건**, 간격 평균 1.119s, 맥놀이 그대로.
→ **그 끊김(00:21:22)은 프레임 정지를 동반하지 않았다.** 즉 socket 이 걱정한
**블로킹 1초 경로와는 다른 기전**이다. n=1 이라 단정하지 말고, 국면2 에서 같이 본다.

## 2.9 🔴 기전 C 감시 — **자동이다. 내가 죽어도 잡힌다**

루트 지시(02:0x): *"`정지 감지` 줄이 하나라도 새로 뜨면 즉시 보고해라 — 전제가 깨졌다는 신호다."*
**약속으로 두면 내 세션이 죽는 순간 사라진다.** 그래서 요약기가 5분마다 판정한다.

**판정 기준** (파일: `monitor/ALERT-win3-stall.md`, 5분마다 갱신):

```
정지 감지 <= 하행(+IPD)   →  ✅ 알려진 경로 (하행 1건당 거의 1건)
정지 감지 >  하행(+IPD)   →  🔴🔴 전제가 깨졌다
```

**왜 `> 하행` 이 기준인가**: 기전 C 는 **하행 ACK 가 방아쇠**이므로 하행 1건당 거의 1건이
**정상 거동**이다. 그 수를 **넘는 순간**이 *"하행 없이도 발동한다"* 의 증거다
(arduino 가 `drainPending()` 말고 `sensorTick()` 등 다른 경로를 의심하며 확인 중이었다).

🔴 **전제가 깨지면 지금 도는 무주입 λ 측정이 오염된다.** 그 경우:
1. 이 파일이 **"전제가 깨졌다"** 로 바뀐다
2. 원문을 열어라: `grep -a -n '정지 감지' monitor/serial-win3.log`
3. **루트와 arduino 에게 즉시 알려라**
4. 판정에서 해당 사건들을 **기전 C 로 따로 뺀다** (A·B 와 같은 표 금지)

현재 상태(02:0x): `정지 감지 1` = `하행 1` → **알려진 경로. 전제 유지 중.**

⚠ `stall` 은 `WIN3-STATUS.md` 표와 `win3-pulse.tsv` 의 `stall` 칸에도 매 주기 찍힌다.

### 🔑 "구운 뒤 정상 동작" 판정 — **닫혔다** (00:23:08)

창2 에서 부팅·Wi-Fi 결합·CIFSR 까지만 확인됐고 **TCP 접속과 상행이 미확인**이었다.

→ **`64fc70b` 정상 동작 확인.**

### 🔴 A 창·창2 와 **합산 금지**

1. **socket 이음매 1** 이 아두이노 **상행 경로**(`DeviceEvent` 4/6)를 건드렸다 — 재고 있는 그 경로다.
2. **펌웨어가 두 번 바뀌었다** (`fa52a51` → `539ac53` → `64fc70b`).

> **창3 은 펌웨어와 서버가 같이 바뀐 구성이다. λ 가 달라져도 이 창 하나로는
> 어느 쪽 효과인지 못 가른다.** 루트가 그 대가를 알고 정했다.
> A 가 애초에 그 비교를 못 받쳐서(검정력 0.49) 잃는 것은 적지만 **"못 가른다"는 사실은 남긴다.**

⚠ **"2단계가 자해를 줄일 것"이라고 쓰지 마라.** 구운 뒤 자해가 줄어도 다른 이유일 수 있다.
🔴 **3배·2배 변화는 처음부터 못 잡는다**(λ≈3.13/h 기준 ~13h·30h+ 필요). **지금 적어 두는 것이지
창을 닫고 나서 쓰는 변명이 아니다.** 5배를 겨눈다면 ~24건 · ~8시간이 필요하다.

## 4. 새 펌웨어가 내는 **새 로그 줄** — 파서에 없으면 조용히 0 이 된다

| 새 줄 | 세는 것 |
|---|---|
| `[TX-WAIT] 앞 전송의 SEND OK 를 아직 못 봤다 — 이번 주기는 건너뛴다` | `skip` |
| `[TX-WAIT] ★ SEND OK 상한 초과 → 대기를 푼다` | `okto` |
| `[CNT] up= drop= esprst= resync= sendfail= okto= skip= online=` (60초 주기) | 누계 |

⚠ **`[CNT]` 는 누적값이다. 구간값으로 읽지 마라**(원장 6.8).
⚠ **`okto` 를 옛 "미도달 0.33%" 와 견주지 마라** — 그 값은 2단계 **없는** 칩에서 나왔고
2단계는 송신 타이밍 자체를 바꾼다. **새 칩에서 기대치를 새로 잡는 것이 첫 일이다.**

### 🔴 `resync_gap.py` 를 이 칩 자료에 **그대로 쓰지 마라**

N/P 를 "다음 송신 주기가 `[TX]` 냐 `[TX-RESYNC]` 냐"로 가르는데, 이 칩에는
**셋째 결말 `skip`** 이 있다. 지금 코드는 skip 을 주기 시작으로 인식하지 못해
**그 앵커를 조용히 N 으로 떨어뜨린다.**
→ **N / P / S 3칸**으로 늘린 뒤 써라. 그렇게 고치면 **A 와 다른 계측기**다 — 같은 표 금지.

### 🔴 `SEND_OK_TIMEOUT_MS` 관련 — arduino 가 내 물음에 답했다

*"프롬프트 대기와 `SEND OK` 대기가 같은 타이머인가?"* → **다른 타이머고, `SEND OK` 게이트가
`CIPSEND` 보다 앞에 있다.** 상한 2000ms 가 내가 A 에서 잰 병리 분포(2~3s) **한가운데**라
**일부만 걸린다.** (근거: `monitor/MEASURE-2026-08-16-2350-sendok-final.md`)

## 5. 하행 도달 — **4칸. 정의는 미리 박혀 있다**

전체 정의 `monitor/RECIPE-newbaseline-t0.md` **§8**. 사슬:

```
① 서버 송신   →ARD T,<seq>,S,…          (parking-server.log)
② 장치 수신   [AT] "+IPD,<n>:T,<seq>,…"  (serial-win3.log)   🔑 여기가 핵심
③ 서버 수신   ←ARD A,<seq>,…            (parking-server.log)
```

| 칸 | 조건 |
|---|---|
| **D0 도달** | ①②③ 이 seq 일치로 모두 있음 |
| **D1 받았는데 응답 없음** | ①② 있고 ③ 없음 |
| **D2 못 받음** | ① 있고 ②③ 없음 |
| **D3 미실행** | ①이 없음 — **측정 안 됨. 건강이 아니다** |

- 🔴 **`result=4` 는 실패가 아니라 기대값이다.** 무장 안 한 `T,S` 는 장치가 거절하고
  **아무 상태도 안 바꾼다** — 그래서 기준선을 안 흔든다. **D1/D2 로 세지 마라.**
- 🔴 **socket 의 `미주입`(장치 오프라인이라 서버가 전선에 안 내보냄)은 D3 쪽.**
  **도달률 분모 = 시도 − 미주입.**
- 🔴 **socket 의 "응답 없음 N건" 은 D1+D2 의 합이다.** 그쪽은 ①③만 본다.
  **②는 내 시리얼에만 있다.** "장치가 못 받았다"로 읽지 마라.
- **짝짓기는 `seq` + 인스턴스.** ⚠ 이번 인스턴스에서 **장치 seq 가 `S,0` 부터 다시 시작**한다
  (방금 리셋됐다). A 창·창2 의 seq 와 겹친다. socket 의 `rid` 는 그쪽 로그 대조용으로만.
- 🔴 **주입은 측정 대상을 늘린다** — ACK 하나가 장치 TX 하나이고, 링크 끊김의 유력 기전이
  바로 장치 TX 순간이다. 5분 주기면 자연 송신 대비 **약 0.4%**. **작지만 0 이 아니다.**
- 독립 기록: `~/parking-logs/downlink-inject.log`(서버 로그가 잘려도 남는다).
