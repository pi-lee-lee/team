# 🔴🔴 발견 — 슬롯 판에서도 **하행이 UART 에서 깨졌다**. 그리고 **서버 쪽 계수로는 안 보인다**

> `monitor-engineer` 2026-08-17 20:5x · 창 A(`slot2`) · 주입 구간
> 원문 근거: `monitor/serial-winA.log` `20:43:38~20:43:42`
> 사전 등록: `PREREG-2026-08-17-windowA-slot-only.md` §2.9

## 1. 원문 — 사슬이 아니라 **프레임 파괴**다

```
20:43:40  [AT] "AT+CIPSEND=39"                     ← 장치가 명령을 내고 프롬프트를 기다린다
20:43:41  [TX] S,875,...                            ← 상행 시작
20:43:41  [SLOT] n=901 tx=38 ack=0 due=0 r=1
20:43:41  [AT] "+IPD,16:T,1AT+CIPSEND=39" (24)     🔴 하행이 잘리고 **장치 자기 명령이 끼어들었다**
20:43:41  [SLOT-OOW] +116ms
20:43:41  [CKSUM NG] T,1AT+CIPSEND=39              🔴 체크섬 실패 = 프레임 파괴
20:43:42  [AT] "+IPD,16:T,153,S,A1,1,5D"           ← 그 다음 것은 정상
```

**직전 두 건은 깨끗했다**: `20:43:38 rid151 +177ms` · `20:43:39 rid152 +171ms`.
위상이 슬롯당 약 6ms 씩 내려오다가 **116ms 에서 처음 깨졌다.**

## 2. 안전 경계 — **`due + txTime` 이 아니다.** 다만 **폭은 못 쟀다** (20:5x 정정)

### 🔴🔴 철회: ~~위험 구간 ∈ [116, 171)ms~~ — **두 수 다 도착 시각이 아니다**

arduino 가 자기 계측기 소스를 열어 잡았다(`client.ino:909`). `[SLOT-OOW]` 의 시각은
**`handleLine` 에서 찍힌다.** 그런데 **송신 중(`inSend`)에 완성된 줄은 `pendLine` 에 갇혔다가
송신이 끝난 뒤 `drainPending()` 에서야 `handleLine` 에 간다.**

```
송신 중 도착  →  pendLine 에 지연  →  오프셋이 **송신 후 시각**으로 찍힌다
송신 후 도착  →  즉시 처리        →  오프셋이 실제 시각
⇒ 두 경우가 출력에서 구별되지 않는다
```
> ### 🔴 **재려던 사건이 바로 그 이유로 늦게 찍힌다. 계측 지점이 그 구간을 밀어낸다.**
> **그래서 `oow` 오프셋으로 위험 구간을 정할 수 없다.** `116` 도 `171` 도 **처리 시각**이다.

⚠ 그리고 §4 의 *"116ms 미만 정상 도착 0건"* 도 **발견이 아니라 계측 산물**이다 —
그 구간 도착은 늦게 찍히므로 **분포에서 원리적으로 비어 있다.** 아래 §4 에 그대로 표시했다.

### ✅ 그래도 남는 것 — **모델이 페이로드 시간만 센다는 것은 참이고, 근거가 둘 늘었다**

1. 🔴 **모델에 `AT+CIPSEND=39\r\n` 16바이트(≈17ms)가 안 들어 있었다** — arduino 자진 확인.
   `txTime` 은 **페이로드만** 셌다.
2. **프롬프트(`>`) 대기 구간도 UART 점유다**(`waitForPrompt` 상한 300ms · 정상시 `promptms=3ms`).
3. **원문이 그 겹침을 직접 보여 준다** — 하행 수신 도중 우리 `AT+CIPSEND` 가 시작돼
   나머지 하행 바이트가 사라지고 우리 명령 에코가 이어붙었다.

```
말할 수 있는 것 : 위험 구간 ⊋ [due, due + 페이로드시간]  — **폭은 미측정**
말할 수 없는 것 : 그 폭이 몇 ms 인가
```
🔴 **`cap`·가드·수신 창 계산에 페이로드 시간만 쓰면 안전 여유가 과대평가된다** — 이 결론은 유효하다.
**다만 "3배"라는 수는 철회한다.**

### 폭을 재는 방법 (다음 굽기 · arduino 가 넣기로 했다)

`[SLOT-OOW]` 의 시각을 **"줄 완성"에서 "그 줄의 첫 바이트 수신"으로 옮긴다**
(`feedRxChar` 에서 `rxLen==0` 일 때 시각을 잡는다). 그러면 `inSend` 지연이 안 섞이고
**처음으로 진짜 도착 시각을 재게 된다.** 그때 위험 구간을 실측으로 정한다.
⚠ **그 전의 모든 오프셋 수치는 잠정이다.**

## 3. 🔴🔴 그리고 이 손실은 **서버 쪽 계수로는 보이지 않는다**

```
socket 계수 : ACK 없음 0 · 미주입 0 · result≠4 0 · 유실 0        ← 손실이 안 보인다
내 시리얼   : rid 1~403 **빠진 번호 0** · 중복 1(rid 388) · CKSUM NG 1
```
**깨진 프레임은 서버가 재전송해서 다음 위상에 정상 도착했다.** 그래서:
- 서버 쪽에서는 **모든 주입이 결국 ACK 됐다** → "유실 0"
- 시리얼 쪽에서는 **파괴가 한 건 있었다** → `[CKSUM NG]`

> ### 🔑 **재전송이 손실을 지운다. 한쪽 계수만 보면 "무손실"로 보인다.**
> 이것이 창4 판정에서 *"재전송을 자극에서 빼야 한다"* 고 적은 것의 **뒷면**이다.
> 그때는 **재전송이 원인을 부풀린다**는 문제였고, 이번엔 **재전송이 결과를 지운다.**

⚠ 그러므로 **손실률을 서버 로그로만 재지 마라.** 두 쪽을 같이 봐야 한다:
```
서버: 발신 수(신규 seq) · 재전송 수 · ACK 수
장치: +IPD 정상 수 · CKSUM NG 수 · rid 빠짐/중복
```

## 4. 표본과 범위 — **한 건이다**

| | 값 |
|---|---|
| 정상 도착 | **404건**(rid 1~403 · 빠짐 0 · 중복 1) |
| 파괴 | **1건** (`20:43:41` · 오프셋 116ms) |
| 그 위상을 지난 슬롯 수 | 🔴 **정확히 모른다** — 아래 |

🔴 **비율로 쓰지 마라(`1/404` 아니다).** 분모는 "전체 도착"이 아니라 **"위험 구간에 착지한 도착"** 이고,
그 수는 **직접 셀 수 없다** — 착지한 것들이 파괴돼 `+IPD` 로 안 남기 때문이다(누락 편향).
관측된 것: **위험 구간을 스치는 위상이 한 번 지나갔고, 그때 한 건이 깨졌다.**

⚠ ~~그리고 `116ms` 아래 오프셋의 **정상 도착이 전 구간에서 0건**이다~~
→ 🔴 **철회(§2)**: 그것은 **계측 산물**이다. 송신 중 도착은 `pendLine` 지연으로 **늦게 찍히므로**
  낮은 오프셋 칸은 **원리적으로 빈다.** *"다 깨졌다"* 와 *"착지한 적이 없다"* 를 못 가르는 것은 맞지만,
  **이유가 내가 처음 쓴 것보다 깊다 — 계측기가 그 구간을 볼 수 없다.**
  가르는 방법: ① `[SLOT-OOW]` 시각을 **첫 바이트 수신**으로 옮긴 뒤(arduino 가 넣는다)
  ② 주입 주기를 슬롯과 **의도적으로 다르게**(`1.15s`) 해서 위상을 30초에 한 바퀴 훑고
  ③ 그 구간의 **발신 수와 `CKSUM NG` 수를 같이** 센다.

## 5. 이 창의 판정에 미치는 영향

- 🔴 **"슬롯 규율만으로 하행이 안전하다"는 성립하지 않는다.** 서버가 창을 안 지키면 깨진다 —
  창 A 는 그 조건이고, **깨졌다.** → **(가) 큐가 필요하다는 실측 근거**다(예측 ① 방향과 일치).
- ✅ **다만 링크는 안 끊겼다**: `esprst 0`·`drop 0`·`전송 3회 연속 실패 0`·배너 0·`0.0.0.0` 0.
  창4 의 사슬(→모듈 리셋)은 **재현되지 않았다.** **파괴는 프레임 한 줄에서 멈췄다.**
  🔑 그것 자체가 개선이다 — 창4 에서는 같은 종류의 손상이 **리셋까지** 갔다(원장 7.99).
  ⚠ 단 표본 1건이고 부하가 다르다. **"고쳤다"로 쓰지 마라.**
- ⚠ `smiss 0` · `ssovf 0` — `ssovf` 는 여전히 **분모 없음**(하행 28B 단발).
