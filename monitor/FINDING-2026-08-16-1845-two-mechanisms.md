**5건 중 자해 2 · ESP 리셋 3.** 한 구성·한 세션·1.75시간이다.

## 0-정정. 🔴 앞선 판의 "자해 2 : 리셋 3" 은 틀렸다 (2026-08-16 18:58)

**무엇이 틀렸나**: 사건을 `자해`/`리셋` **둘 중 하나로 강제**했다. 그래서 `17:41:05` 이
`busy`×12 만 보고 `자해` 칸에 들어갔는데, **원문에는 IP 소실 표지가 같이 있었다**
(`17:41:09 CIFSR 3회에도 IP 가 없다 → CWJAP 부터 다시`). 라벨을 강제하느라 증거를 지웠다.

**왜 못 봤나**: 1차 판별자를 `CIFSR → 0.0.0.0` **문자열 하나**로 잡았다. 그런데
`18:48:12` 리셋에서 **`AT+CIFSR` 응답 자체가 가비지**로 깨져 그 문자열이 안 찍혔다.
→ **`0.0.0.0` 은 정밀하지만 완전하지 않다.** 리셋이 심할수록(UART 가 깨질수록) 놓친다.
   펌웨어 자신의 결론 줄 `CIFSR 3회에도 IP 가 없다` 를 OR 로 더해야 한다.

**정정된 계수** (16:59:54~18:58, 1.97h, 6건):

|---|---|---|
| A. 순수 자해 (`busy`, IP 유지) | **1** | 17:05:23 |
| B. 리셋계열 (배너/IP소실) | **4** | 17:21:32 · 18:24:55 · 18:44:56 · 18:48:12 |

   그리고 **A 창(17:53:07~) 안 3건은 전부 리셋계열 · 자해 0 · 혼합 0.**

⚠ `AB.혼합` 을 어느 한쪽으로 밀어 넣지 마라. 겹친 이유(리셋이 `busy` 를 유발했나, 그 반대인가)는

### 2.1 두 판별자를 전수로 검증했다 — 겹치지 않는다

**부트 배너** `[System Ready, Vendor:www.ai-thinker.com]` **전수 4건**:
`16:59:57`(우리 DTR 리셋 = 정상 부팅) · `17:21:32` · `18:24:54` · `18:44:55`.
→ 정상 부팅 1건을 빼면 **리셋 3건과 정확히 일치.** 누락도 초과도 없다.

**`CIFSR → 0.0.0.0` 전수 3건**: `17:21:33` · `18:24:56` · `18:44:57`.
→ **리셋 3건과 3/3 일치. 그리고 정상 부팅(16:59:57)에는 나오지 않는다.**
   🔑 이것이 중요하다 — 매 기동마다 뜨는 값이었다면 판별자로 못 쓴다. **아니었다.**

**`busy` 전수 20건의 분 단위 분포**: `17:41`(12) · `17:05`(6) · `18:03`(2).
→ **리셋 3건(17:21·18:24·18:44)에는 `busy` 가 단 한 건도 없다.** 두 기전이 섞이지 않는다.
→ ⚠ 그리고 `18:03` 의 `busy` 2건은 **3연속 실패에 도달하지 않았다** —
   `busy` 가 났다고 반드시 끊기는 게 아니다. **끊는 것은 `busy` 가 아니라 3진아웃 규칙이다.**
   (기전 A 가 "자해"인 이유가 이것이다. 기전 B 에는 이 논리가 적용되지 않는다.)

### 기전 A — 자해 (LEDGER 3.7 그대로)

```
17:41:01  AT+CIPSEND=40        ← 프롬프트 '>' 를 기다림
17:41:02  TX-RESYNC 프롬프트 놓침 → 더미 40바이트
17:41:02  전송 실패 1/3
17:41:02  "busy s..."          ← 🔑 ESP 는 **살아 있다.** 앞 패킷을 아직 보내는 중이다
17:41:03  … 실패 2/3 · "busy s..."
17:41:05  … 실패 3/3 → 오프라인 전환 → CIPCLOSE
```

ESP 가 `busy s...`(busy sending)로 **또박또박 대답한다.** 소켓은 멀쩡하다.
펌웨어가 그 대답을 침묵과 구분하지 않고 3번 세어 **스스로 끊는다.** REQ-0116 이 겨냥한 것이 이것이다.

### 기전 B — ESP 모듈 리셋 (**새로 확인됨**)

```
18:24:50  AT+CIPSEND=40        ← SEND OK 가 오지 않는다
18:24:52  TX-RESYNC → 실패 1/3
18:24:53  TX-RESYNC → 실패 2/3
18:24:54  [DROP-OVF] 줄이 96바이트를 넘어 버렸다      ← 부트 ROM 쓰레기
18:24:54  "[System Ready, Vendor:www.ai-thinker.com]" ← 🔴 **ESP 부트 배너**
18:24:55  실패 3/3 → 오프라인 전환 → CIPCLOSE
18:24:56  AT+CIFSR → **"0.0.0.0"**                    ← 🔴 **IP 를 잃었다**
```

여기서는 소켓만 죽은 게 아니라 **Wi-Fi 스택이 통째로 날아갔다.** `0.0.0.0` 이 결정적이다 —
소켓 하나의 문제라면 IP 는 남아 있어야 한다.

**순서가 중요하다: 프롬프트 놓침이 배너보다 2~4초 앞선다.** 즉 ESP 는 리셋되기 전에
이미 응답을 멈췄다. → **끊김은 3진아웃의 결과가 아니라 ESP 가 죽은 결과다.**

## 3. 🔴 이것이 REQ-0116 의 전제를 바꾼다

REQ-0116 = "`busy` 를 실패로 세지 않는다 · 더미 주입 중단" (구현 완료, **아직 안 구움**).

1. **효과 범위가 일부다.** 기전 A(**2건**)는 고쳐진다. **기전 B(3건)는 안 고쳐진다** —
   ESP 가 리셋되는 것을 카운터 규칙으로 막을 수는 없다.
   🔴 게다가 **A 창 안(17:53~)에서는 5건 중 2건이 모두 기전 B 이고 기전 A 는 0건**이다.
   지금 자료만 보면 REQ-0116 이 A 창에서 고칠 사건이 없다. (표본 2건 — 단정은 아니다)
2. ⚠ **그리고 위험이 하나 생긴다.** 지금 **ESP 리셋을 탐지하는 유일한 경로가 그 3진아웃**이다.
   `busy` 를 안 세는 것 자체는 옳지만, 리셋 때는 `busy` 가 아니라 **침묵**이 오므로
   3진아웃은 그대로 동작해야 한다. **침묵과 `busy` 를 반드시 갈라서 세라** —
   둘 다 안 세면 ESP 가 죽어도 장치가 모른 채 허공에 쏜다.
3. 더 확실한 탐지기를 붙일 수 있다: **부트 배너 문자열** 또는 **`CIFSR` 이 `0.0.0.0`**.
   둘 다 이 로그에서 실제로 관측됐고 오탐 여지가 좁다.

## 4. 기전 B 의 원인 — 지목하지 않는다. 후보만 적는다

- ESP 리셋이 **둘 다 TX 시도 중**에 일어났다. TX 는 소비 전류가 가장 큰 순간이다.
- LEDGER 4.2 — 옛 두 구간의 변수 중 하나가 **캐패시터(2200µF vs 100µF)** 였다.
- 사용자가 15:26~17:0x 에 **실물을 만졌고 내용은 아직 미상**이다(REQ-0112).

→ **전원이 유력한 후보다. 그러나 이 로그만으로는 확정할 수 없다.**
   확정하려면 arduino 쪽에서 지금 보드의 전원/캐패시터 구성을 확인해야 한다.
   ⚠ 그건 실물 접촉이라 **A 창(~21:53)이 닫힌 뒤**에 해야 한다.

## 5. 다음에 셀 것 — ⚠ pre-A 와 A 를 합산하지 마라
