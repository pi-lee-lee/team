## 2. 기전
```
연타 → 하행 유입 ↑ → ACK 유입 ↑ → **배치 tx 80 → 150B(ack 8)** → 전송 시간 ↑
 → **SEND OK 지연** → 게이트 닫힘 → **슬롯 건너뜀(r=0 ×3)** → 상행 공백 3.5초+
 → 서버 오프라인 판정 → 재접속·재전송 → 하행 유입 ↑ …
```
> ### 🔑 **설계가 *"이벤트가 전송을 만들지 않는다"* 로 없앴다던 고리가 되살아났다.**
> **전송 *횟수* 는 상수인데 *한 번의 크기* 가 커져 시간 축에서 같은 폭주가 난다.**

## 3. 낱말을 가른다 — **셋을 하나로 부르면 대책이 틀린다**
```
끊김의 직접 원인 : **r=0(미전송)** · 그 원인은 **SEND OK 지연**
ackdrop(43→86)  : 같은 뿌리의 **다른 증상**이지 원인이 아니다
ssovf(7→13)     : 같이 올랐지만 **끊김의 원인이라는 증거는 없다**
esprst          : **2 에서 안 늘었다**(우리 DTR 1 + 창 개방 1) → **ESP 리셋 아님. TCP 세션만 끊긴다**
```
✅ 사용자 표현 *"오버플로로 죽었다 살아난다"* 는 **방향이 맞다**(오프라인 시각이 `ackdrop` 급증 구간 안).
🔴 **다만 "오버플로"가 아니라 "배치 비대"** 다.

## 4. 실측 — 배출 능력과 유입
```
[SLOT] ack= 분포(15:22~15:25) : {0:133, 3:1, **8:7**}   ← 배출 상한 **8/슬롯**(관측 최대)
  🔴 8 짜리 배치 7건 중 대부분이 **r=0** → **부하에서 배출률이 떨어진다**
하행 M 배치 도착 : 15:23:10·:14·:15·:17·:18·:19 (6회) → 창당 7~8건 × 6 ≈ **40~48건 / 9초**
tx 최대 **149~150B**
```
⚠ 위 배출률은 **끊긴 구간 포함**이라 **하한**이다.
⚠ `8` 은 **관측 최대이지 설계 상한이 아니다** — arduino 가 코드에서 확정해야 한다.

## 5. 🔴 대책 방향이 뒤집힌다
```
❌ 큐를 키운다 / ACK 을 더 묶는다 → **묶을수록 한 번이 커지고 SEND OK 가 늦어진다** = 고리를 키운다
✅ **한 상행 거래의 최대 크기 상한**이 필요하다
   → arduino 의 `tx` 상한 ↔ socket 의 하행 `cap` 이 **같은 축에서 만난다**. 값은 두 도메인이 정한다
```

## 6. 하행 유실도 같이 있었다 (별개 사건)
`rid 479·480` 은 서버가 **3회씩 보냈는데 장치 도착 0회**다(478 은 2회 · 하한).
**`cksumng` 은 "깨진 것"만 세고 "사라진 것"은 못 센다**(창 A2 의 사각) — **기전 미상.**
