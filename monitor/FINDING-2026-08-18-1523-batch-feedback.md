## 2. 기전
```
연타 → 하행 유입 ↑ → ACK 유입 ↑ → **배치 tx 80 → 150B(ack 8)** → 전송 시간 ↑

 → 서버 오프라인 판정 → 재접속·재전송 → 하행 유입 ↑ …
```
> ### 🔑 **설계가 *"이벤트가 전송을 만들지 않는다"* 로 없앴다던 고리가 되살아났다.**
> **전송 *횟수* 는 상수인데 *한 번의 크기* 가 커져 시간 축에서 같은 폭주가 난다.**

## 3. 낱말을 가른다 — **셋을 하나로 부르면 대책이 틀린다**
```
끊김의 직접 원인 : **r=0(미전송)** · 그 원인은 **SEND OK 지연**
ackdrop(43→86)  : 같은 뿌리의 **다른 증상**이지 원인이 아니다
ssovf(7→13)     : 같이 올랐지만 **끊김의 원인이라는 증거는 없다**
esprst          : **2 에서 안 늘었다**(우리 DTR 1 + 창 개방 1) → **ESP 리셋 아님. TCP 세션만 끊긴다**
```
✅ 사용자 표현 *"오버플로로 죽었다 살아난다"* 는 **방향이 맞다**(오프라인 시각이 `ackdrop` 급증 구간 안).
🔴 **다만 "오버플로"가 아니라 "배치 비대"** 다.

## 10. 🔴 §2 기전 정정 — **"전송 시간 ↑" 만으로는 설명이 안 된다** (arduino 지적)

내가 적은 사슬의 중간 고리는 **`배치 커짐 → 전송 시간 ↑ → SEND OK 지연`** 이었다. **부족하다:**
```
150B 전송 자체 = **156ms**        그런데 `stuck=3` 은 **T2(8000ms) 초과**다
→ 8초 지연을 156ms 로 설명할 수 없다
```
**arduino 가 연결한 것**(원장 §8.6-1): **병리 구간의 `SEND OK` 지연은 2~3초**이고
`SEND_OK_TIMEOUT_MS=2000` 이 **그 분포 한가운데서 풀린다.**
> ### 🔑 **정정된 서술: 큰 배치가 `SEND OK` 지연을 그 병리 구간으로 *밀어넣는다*.**
> **전송 시간이 원인이 아니라, 큰 배치가 ESP 를 지연이 큰 상태로 옮긴다.**
> **내 판정과 arduino 의 옛 관측(§8.6-1)이 여기서 만난다.**
⚠ **"어떻게 밀어넣는가"는 아직 모른다** — 그 자리는 미측정으로 남긴다.

## 11. ✅ 대책의 방향이 셋 다 확인됐다 (arduino 정리)
```
배출을 늘린다 → 배치가 커진다 → SEND OK 지연 → 게이트 닫힘 → 배출 0   (고리가 커진다)
배출을 줄인다 → 큐가 더 넘친다                                        (ackdrop ↑)
**유입을 줄인다 → 고리의 입력이 준다**                                 ← 유일한 출구
```
🔴 **그래서 `ACKQ_N` 을 더 키우는 것은 오답이다** — **큐 확대가 고리의 입력이다. 완화가 아니라 가속이다.**
✅ **socket 의 하행 건수 상한 4 가 `유입 4 < 배출 6` 을 만든다.** **arduino 쪽에 지금 고칠 것이 없다.**
⚠ `BATCH_CAP` 축소도 지금이 아니다 — **유입을 먼저 고치고 그 뒤에 `tx` 분포를 다시 본다**(축을 하나로).

# 16. **무효 범위 축소** — 두 갈래로 회수됐다 (REQ-0214 정정 · REQ-0217 머리절 · socket uptime 분석)

## 16.1 내 자료로 독립 확인한 것 — **20 = 20**
```
서버(socket)  15:09:25 ~ 16:22:29 : 링크 재접속 20건 · uptime 되감김 0 · 점프 0
내 시리얼      같은 구간 `[NET] online (CONNECT)`  →  **정확히 20건** · 첫 건 15:09:25(초까지 일치)
```
🔑 **20건 중 남의 보드에 내줄 자리가 한 건도 없다.**
⚠ **정의는 다르다**(서버=세션 전이 판정 / 내 것=`CIPSTART` 뒤 ESP 의 `CONNECT`). 근거는 "숫자가 같다"가
아니라 **"내 쪽이 20을 이미 다 채웠다"** 이다.
⚠ `0.0.0.0` 은 같은 구간 **17건**뿐 — **단절 계수로 쓰면 3건이 빈다.**

## 16.2 T2 8초 축은 **살아 있다** — 조원이 없던 새벽에도 있다 (루트 근거 · 내가 줄 종류까지 확인)
```
04:04:33 세션#11 종료 … 최대공백 8.4초      04:20:32 세션#16 … 8.4
04:05:02 세션#12 종료 … 최대공백 8.4초      04:38:17 세션#17 … 8.4
04:18:39 세션#15 종료 … 최대공백 8.4초      05:02:37 세션#18 … 8.4
```
✅ **여섯 줄 전부 `세션# 종료` 사건 줄이다**(소크 상태줄이 아니다 — 내가 갈라서 셌다).
→ **T2 8초는 오염이 아니라 우리 결함이다. 이 축은 계속 쫓는다.**
⚠ 다만 **동일성은 추론이다**: 서버 `최대공백`(프레임 간 간격) 과 내 `T2`(SEND OK 대기 8000ms)는
**다른 계측기**다. 8.4 ≈ 8.0+슬롯 정렬로 앞뒤가 맞을 뿐, **새벽 시리얼 로그가 없어 실측 대조는 불가**.

## 16.3 🔴 계측기 함정 — **`재부팅감지` 는 재부팅을 본 적이 없다**
```
재부팅감지 18(새연결 18 / uptime추론 0) · 재연결내역(재부팅 0 / 링크재접속 17 / 미상 1)
```
> **같은 줄이 `재부팅 0` 이라고 말한다.** `재부팅감지` 는 **새 연결을 센 것**이고 `uptime추론` 은 **0건**이다.
🔴 **§15 에서 이것을 "오염으로 무효"라 적은 것은 분류가 틀렸다 — 오염이 아니라 *이름이 내용과 다르다*.**
**"재부팅 17회"는 오늘 한 번도 관측된 적이 없다.**

## 16.4 그리고 `최대공백` 을 셀 때
