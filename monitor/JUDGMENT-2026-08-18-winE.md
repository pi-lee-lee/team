```

[CKSUM NG]          **3건**(전부 [CNT] 정합)      **0건**
하행 도착(내 재고)  294                          **300**(최종 · rid 301~600 · 빠진 번호 0)

> ### 🔴 **`0` 이지만 "자극 없어서 0" 이 아니다.** 하행이 **300건 전부 도착**했다(빠진 rid 0).
⚠ **정정**: 이 판정문 1차 기록에 `256` 으로 적었다. 그것은 **`10:37:33` 중간 시점 값**이고
회차는 `10:39:06` 에 끝났다. **최종은 300** 이다(§4 재고와 일치).
🔴 **중간값을 최종값처럼 쓰지 마라** — 루트가 그 수를 단서 없이 socket 에 옮겨 불일치가 생겼다.
**오늘 `1.206초` 를 `n=1` 표기 없이 옮긴 것과 같은 형태다.** 분모가 커졌으므로 **결론은 더 강해진다.**
> **사전 등록한 그 조건**(*"파괴 0 이면 분모를 같이 찍어 가른다"*)을 **충족한 0** 이다.

**판정선 재확인**: 등록한 것은 *"`[CKSUM NG]` 시각이 `[CNT]` 와 더 이상 정합하지 않는가"* 였다.
**정합을 논할 사건 자체가 없다** → **더 강한 결과다.**

## 1. 다른 칸도 전부 0 이 됐다 — 이것이 더 놀랍다
```
창 D 주입 구간 : skip=21 · ssovf 2→8 · okto 4~5 · smiss=2 · esprst=3 · drop=4 · stuck=2
창 E 10.5분    : **skip=0 · ssovf=0 · okto=0 · smiss=0 · esprst=0 · drop=0 · stuck=0** · online=1
```
🔑 **`skip`(게이트 양보)과 `ssovf`(링버퍼 넘침)가 0 이다.** `[CNT]` 출력이 송신 창으로 옮겨지면서
**수신 구간을 막지 않게 된 결과**로 보인다 — ⚠ **가설이다.** `ssovf` 는 원인이 셋으로 갈려 있었고
(주입 계열 · 재접속 폭풍 · 미상) **이번 0 은 그중 어느 것이 사라졌는지까지는 말하지 않는다.**

⚠ **`esprst`/`drop` 이 0 인 것은 이 창의 유휴가 짧아서일 수 있다**(창 D 는 유휴 46분에 이미 3·4 였다).
**같은 길이로 재기 전에는 "링크가 더 안정해졌다"고 쓰지 마라.**

## 2. 착지 오프셋 — 망이 같으므로 ②의 효과만 남는다
```
창 D : 최소 141 · 중앙 152 · 최대 478
창 E : 최소 **134** · 중앙 **144** · 최대 591
```
**거의 같다**(중앙 −8ms). 🔑 **② 는 착지 위상을 바꾸지 않았다** — 바뀐 것은 **장치가 그 위상에서
무엇을 하고 있었나**다. **`[CNT]` 가 그 구간에서 빠진 것**이 유일한 차이다.

## 3. 남은 확인 (완주 후)
- **완주분 최종 `cksumng`** — 지금은 10.5분 시점이다. 0 이 유지되는지.
- **socket 판별자와의 대조** — 그쪽이 재전송을 갈라 **파괴 0** 을 독립으로 확인하면 **2/2** 다.
  🔑 **그쪽 판별자는 `[CNT]` 시각과 무관**하므로 **내 0 과 독립**이다.
- ⚠ **`[CNT]` 출력 시각이 최대 1.2초 늦어진다**(arduino 예고) — 실측 `[CNT]` 간격이
  `10:29:53 … 10:36:54` 로 **60~61초 유지**다. **주기는 안 밀렸다** ✅(`cntLastAt` 재장전 설계대로).

## 4. ✅ 완주 확정 — **파괴 0/300.** socket 의 "파괴 1건"은 **오탐이다**

```
[CNT] 10:39:55 (최종) : **cksumng=0** · oow=295 · ssovf=0 · skip=0 · smiss=0
                       · esprst=0 · drop=0 · stuck=0 · okto=0 · online=1
내 +IPD 재고          : 도착 rid **300개**(301~600) · **빠진 rid 0** · 중복 1건(rid 520 @10:35:51)
```
socket 은 재전송 2건을 갈라 `10:35:51 늦은 ACK` · **`10:36:47 파괴`** 로 보고했다.
**내 쪽에서 그 시각은 이렇다:**
```
10:36:41 rid 541 · 10:36:43 rid 542 · **10:36:48 rid 543** · 10:36:50 rid 544 …
→ 빠진 rid 없음 · CKSUM NG 없음 · 그 구간 도착이 정상
```
> ### 🔴 **프레임은 온전히 도착했다. 파괴가 아니다.**
> **socket 판별자의 전제**(*"재전송 뒤 `! 모르는 rid ACK` 이 따라오면 늦은 ACK, 없으면 파괴"*)는
> **재시도의 ACK 이 항상 '모르는 rid' 로 찍힌다**고 가정한다. **그 ACK 이 원래 rid 로 정상 정합되면
> `!` 줄이 안 나오고 → 판별자가 "파괴" 로 읽는다.** ⚠ **오탐 경로가 있다.**

🔑 **창 D 에서 3/3 으로 맞았던 판별자가 창 E 에서 1건 오탐을 냈다.** 파괴가 흔할 때는 잘 맞고
**드물어지면 오탐이 상대적으로 커진다** — **개선된 뒤일수록 그 판별자를 단독으로 쓰면 안 된다.**
✅ **두 계측기를 독립으로 쓰기로 한 것이 여기서 값을 했다**(내 사전 등록 §5.6 의 그 문장).

### 4.1 그래서 창 E 최종 판정
```
파괴 : **0 / 하행 300거래**   (분모 있음 · 미주입 0 · 빠진 rid 0)
전(前) 창 D : 3 / 294        (전부 [CNT] 정합)
```
🔴 **`[CNT]` 를 슬롯 창에 묶자 파괴가 사라졌다.** 세 창 연속 정합 증거(B 5 · C 4 · D 3) 위에서
**원인 지목이 검증됐다.**

## 5. ✅ arduino 가설 검증 — **`skip` 도 `[CNT]` 에 붙어 있었다**

가설: *"`[CNT]` 블로킹 동안 `SEND OK` 를 제때 못 읽어 다음 슬롯 게이트가 닫혀 있다 → `skip++`"*
**창 D 주입 구간 실측:**
```
skip 8건 : 10:05:30 · **10:10:43 · 10:10:44** · **10:12:43 · 10:12:44** · 10:13:32 · **10:14:43 · 10:14:45**
[CNT]    : …10:10:42 · 10:12:42 · 10:14:42…
→ **6/8 이 [CNT] 직후 1~3초**(쌍으로 붙는다) · 나머지 2건(10:05:30 · 10:13:32)은 무관
```
✅ **가설 지지.** 그리고 **창 E 는 `skip=0`** 이다.
> ### 🔑 **`[CNT]` 의 피해는 하나가 아니라 둘이었다 — 하행을 깨뜨리고, 우리 `SEND OK` 수신도 늦췄다.**
⚠ **6/8 이지 8/8 이 아니다.** 무관한 2건이 있으므로 **`skip` 전부를 `[CNT]` 탓으로 돌리지 마라.**
✅ socket 쪽에서도 같은 방향의 증거가 나왔다: **늦은 ACK 5 → 1** (`cntTick` 묶기 뒤).
**두 증상이 한 뿌리에서 나왔다**는 것이 서로 다른 계측기 셋(`skip`·`늦은 ACK`·`cksumng`)에서 보인다.

## 6.6 ⚠ 창 E 안의 서버 배포 — **탭을 안 내렸다. 이유를 적는다** (socket `ACK_TIMEOUT` 1500→2400)

**규약 ①(배포 통보 시 관측 정지)에서 의도적으로 벗어났다:**
```
① 서버 배포는 **시리얼 포트·보드를 안 건드린다** — 충돌 위험 0 (굽기와 다른 점)
② 🔴 내리면 다시 열 때 **DTR 리셋**이 나고, 그 리셋이 **지금 쌓는 유휴 누적을 죽인다**
   그 누적이 §6.2-① (esprst·drop 을 창 D 유휴 46분과 비교)의 **유일한 자료**다
③ 변경은 **서버 계수 의미만** 바꾼다 — 장치측 지표에 안 닿는다
```
> 🔑 **규약 ①의 목적은 포트 충돌과 오염 방지다. 이 배포는 둘 다 아니고 오히려 내리는 쪽이 자료를 깬다.**
**대신 배포 시각을 창 안 경계로 표시한다**(서버 `INSTANCE-END`→`INSTANCE` 가 남는다).
⚠ **루트가 다르게 판단하면 따른다.**

### 6.6.1 🔴 `재전송` 도 대조 불가 칸에 들어간다 (§6.2-③ 에 추가)
```
창 A~E : 재전송 = 늦은 ACK + 파괴 (섞임 · 판별자로 갈랐다)
배포 후 : **파괴만 남는다**  → **수가 줄어도 개선이 아니라 세는 범위가 좁아진 것**
```
✅ 대신 **`cksumng` 과 1:1 이 될 수 있고** 그러면 **판별자(§6.4-⓪)가 필요 없어진다** —
**고치는 게 아니라 없애는 쪽으로 닫힌다.** ⚠ **1:1 여부는 배포 후 첫 회차에서 확인한다. "그럴 것이다"로 닫지 않는다.**

### 6.6.2 ✅ 서버 계약값이 로그에 남는다
`= 계약값 — ACK_TIMEOUT · ACK_MAX_TRIES · ack_budget_ms · cap · W_srv` 한 줄이 기동 시 찍힌다.
🔑 **지금까지 나는 socket 통보를 옮겨 적었고 그건 원장에만 남았다 — 이제 자료 자체에 남는다.**
**그 창의 서버 계약값을 판정문이 로그에서 인용할 수 있다.**

## 6.7 🔴🔴 **판정 이후 구간에서 값이 다시 움직였다** — 판정의 범위를 못 박는다 (12:29 확인)

```

```
> ### 🔴 **`esprst=0` 이고 새 부트 배너가 없다 → ESP 모듈 리셋은 안 났다.**
> **사용자가 "esp01 이 리셋된다"고 본 것은 내 로그로 확인되지 않는다.**

⚠ **그러므로 "무엇이 실제로 일어났나"부터 갈라야 한다**(루트 후보 ③ 이 유력해진다):

리셋      ❌ 배제 — esprst 0 · 배너 1건(내 t0 것)

           → **`cmdPending` 구멍(거짓 실패 → 재클릭)이 정확히 그 증상**이다
```
🔑 **그리고 루트의 `0` 은 `-a` 누락이었다** — **오늘 CLAUDE.md 에 넣은 그 함정을 루트가 밟았고,
같은 명령에 `-a` 를 붙이자 131줄이 나왔다.** **`0` 을 보고 "표지가 없다"로 읽으면 안 되는 자리다.**

## 6.9 🔴 **(가)/(나) 판별 — 궤적이 갈랐다. 사용자가 본 "터진다"는 (가)다**

**표본별 증가분(`[CNT]` 표본 차분):**
```
12:35:15  esprst+0  ackdrop+63   ssovf+23     ← 사용자 조작 1차
12:36:16  esprst+0  ackdrop+94   ssovf+35     ← 같은 구간(M 프레임 분당 19~20건)
12:37:16  esprst+0  ackdrop+40   ssovf+13
13:32:25  **esprst+1**  ackdrop+0   ssovf+0   ← 🔴 리셋. **둘 다 안 올랐다 · 그 구간 하행 1건**
14:35:36  esprst+0  ackdrop+29   ssovf+10     ← 사용자 조작 2차
14:40:36  esprst+0  ackdrop+38   ssovf+12
```

> ### ✅ **사용자 조작 구간(12:33~12:37 · 14:35~14:40)은 `esprst` 증가가 0 이다.**
> ### **→ 사용자가 본 "터진다"는 (가) ACK 큐 버려짐이고 ESP 리셋이 아니다.**
> ### 🔴 **(나) 리셋은 13:32 에 1회 · 하행이 사실상 없던 시각 · 조작과 무관하다.**

**그리고 `ackdrop` 과 `ssovf` 는 같이 오른다**(조작 구간 6표본에서 비율 약 2.7:1 로 일정).
→ **같은 뿌리로 볼 근거가 생겼다**(둘 다 "받았는데 못 꺼냄" 계열). ⚠ **비율이 일정하다는 것이지
인과가 확인된 것은 아니다.** 반면 **`esprst` 는 둘과 완전히 어긋난다** — **다른 사건이다.**

### 6.9.1 🔑 이 판별은 **내 USB tap 만이 할 수 있다** (web 확인)
```
(가) 장치가 ACK 을 만들었는데 큐가 넘쳐 버렸다  → 서버는 ACK 못 받음
(나) ESP 가 리셋됐다                            → 서버는 ACK 못 받음
화면·서버가 보는 것 : **둘 다 같다**(error/ack_timeout)
```
**`ackdrop` 도 `esprst` 도 전선에 안 나간다** — 둘 다 `Serial.print`(USB)이고 `S` 프레임에 필드가 없다.
→ **서버가 못 보므로 화면도 못 본다.** 🔴 **화면 문구로는 원리적으로 못 가른다.**

### 6.9.2 web 문구에 실측 근거가 붙는다
화면은 *"장치가 응답하지 않았습니다"* 라고 말한다. **(가)면 더 정확한 말은 "장치가 응답을 만들었지만
버렸다"** 다. **문구는 그대로 두되** — 🔑 **"장치가 응답하지 않았다"를 "장치가 죽었다"로 확장하면 틀린다.**
**이 판정이 그 한 줄의 실측 근거다.**

### 6.9.3 ⚠ 남은 것
```
· "몇 개째"의 정확한 수 — M 프레임 분당 19~20 건에서 ackdrop 이 +94 까지 튄다. **분모는 잡혔다**
· ackdrop 의 정확한 의미(큐 상한? 창 밖 폐기?) — **arduino 확인 필요**. (가)의 코드 위치가 거기 있다
· (나) 13:32 리셋의 원인 — **하행 없이 났다.** 유휴 리셋 계열(창 A2 69분에 2 · 창 D 46분에 3)과 같은 것일 수 있다
```

## 6.10 🔴🔴 `ack_timeout` 앵커로 판별 — **하행은 3회 다 도착했다. 문제는 상행 ACK 이다**

**서버 앵커**: `14:40:17 wire_rid=370` · `14:50:32 wire_rid=399·400·401·402·407·408·409`(무더기)

**내 장치 로그에서 그 rid 들:**
```
rid 370 : 14:40:08 · 14:40:11 · 14:40:15   → **3회 전부 도착**
rid 399 : 14:50:22 · 14:50:26 · 14:50:30   → **3회 전부 도착**
```
> ### 🔴 **서버 재전송 3회가 **전부 장치에 도달**했는데도 ACK 이 안 돌아갔다.**
> ### **→ 문제는 하행이 아니라 **상행 ACK 경로**다.**

**같은 구간 `[CNT]` 차분(14:50:38 표본):**
```
esprst+0 · **ackdrop+31** · ssovf+13 · cksumng+2      (앞 3분은 전부 +0)
```
→ **(나) 리셋 ❌**(esprst 0) · **(가) ACK 큐 버려짐 ✅**(`ackdrop+31` 이 그 순간에만 튄다)

**그리고 그 순간의 파괴 2건은 모양이 다르다:**
```
14:50:26  [CKSUM NG] M,429,72,409,70     🔴 **두 하행이 한 줄에 붙었다**(구분자 유실)
14:50:27  [CKSUM NG] MAT+CIPSEND=98      하행이 잘리고 우리 명령이 끼었다(창 B~D 와 같은 모양)
```
⚠ **첫 번째는 새 모양이다** — **하행이 몰리자 프레임 경계 자체가 깨졌다.**

### 6.10.1 결론
```
사용자가 본 "장치가 응답하지 않았습니다" = 서버가 재전송 3회를 소진하고 보낸 것(web·socket 확인)
그 순간 장치는 : 하행을 **3회 다 받았고** · 리셋되지 않았고(esprst 0) · **ACK 을 버렸다**(ackdrop+31)
→ 🔴 **(가) 확정.** 고칠 자리는 **상행 ACK 큐**이지 하행 경로가 아니다
```
⚠ **`cksumng+2` 는 하행 방향이라 별개 사건**이다 — **같은 순간에 났지만 같은 것이 아니다.**
🔑 **web 문구 "장치가 응답하지 않았습니다"는 정확히는 "장치가 응답을 만들었지만 버렸다"** 이고,
**"장치가 죽었다"로 읽으면 틀린다** — 이 판정이 그 근거다.
