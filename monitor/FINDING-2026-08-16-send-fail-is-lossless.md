양쪽 채널을 **동시에** 본 첫 사례다.

> # 🏷 이 기준선의 이름: **`DEBUG=1` 구성**
>
> 지금 칩은 `DEBUG 1` 로 구워져 있어 **AT 대화가 전부 시리얼로 나간다**(초당 수십 줄).
> `arduino-engineer` 의 후보 ④ 가 *"그 출력 자체가 프롬프트 타이밍을 밀고 있을 가능성"* 이다.
> 즉 **관측이 관측 대상을 바꾸고 있을 수 있다.**
>
> 무효로 보지는 않는다 — 사용자가 실제로 구운 구성이므로 재는 값이 있다.
> 다만 **반드시 "DEBUG=1 구성의 기준선"으로 부른다.** 이 라벨이 없으면 나중에
> `DEBUG=0` 과 비교할 때 변수가 또 둘이 된다(오늘 캐패시터에서 겪은 그것이다).

## 0. 먼저 — 셀 대상을 바꿨다 (arduino-engineer 지적)

원래 계획은 `[LINK] closed reason` 을 세는 것이었다. **실제 캡처에 0건이다.**
그 문자열은 `EspLink.h` 계열에만 있고 지금 칩은 `조별과제샘플/client.ino` 계열이다.

```
[LINK] closed        0건   ← 이걸 셌으면 "끊김 없음 = 건강"으로 오독했다
전송 실패            4건
TX-RESYNC            4건
전송 3회 연속 실패    1건
오프라인 전환         1건
```

**0 을 건강으로 읽을 뻔한 사고를 하나 막았다.** 문자열은 펌웨어 계열마다 다르므로
**계수 대상을 정하기 전에 실제 캡처를 확인해야 한다.**

## 2. 🔑 판정 — 이 끊김은 **무손실**이다

| | 단발 실패 | 3연속 → 끊김·재접속 |
|---|---|---|
| 잃은 프레임 | **0** | **0** |
| seq 연속성 | 유지 | 유지 |
| 서버가 버린 줄 | **0** | **0** |

전 구간 통계로도 **seq 불연속 1건 / 802 프레임**이다.

→ **"링크 끊김 시간당 2.5회"는 자료 손실이 아니다.** 장치가 스스로 닫고 다시 열지만
   **프레임 스트림은 이어진다.** 앞선 판정에서 이것을 "끊김"으로만 세었는데,
   **무엇을 잃는지는 세지 않았다.** 답은 "아무것도"다.

### 🔴 하행은 "괜찮다"가 아니라 **"한 번도 안 돌았다"**

실측했다:

```
서버 → 장치 (→ARD)        0건
시리얼 수신측 [RX]/예약/ACK/R,   0건
```

**표본이 0 이다.** 그러므로 위 무손실 결론은 **상행(장치→서버) 전용**이고,
하행에 대해서는 **좋다고도 나쁘다고도 말할 수 없다.**

⚠ 이 구분이 중요한 이유: 시연에서 **예약 명령이 내려가는 경로가 하행**이다.
즉 **지금 기준선은 가장 위험한 경로를 전혀 관측하지 못하고 있다.**
"12분 동안 문제 없었다"를 하행까지 포함하는 것으로 읽으면 안 된다 —
그 경로는 12분 동안 **한 번도 사용되지 않았다.**

→ 하행을 판정하려면 **누군가 실제로 예약을 걸어야 한다**(웹/폰 경로).
   가만히 쌓기만 해서는 이 칸이 영원히 0 으로 남는다.

## 3. 🔴 펌웨어 로그가 사실과 다르다

시리얼 메시지: *"더미 38바이트로 스트림 복구 **(서버는 이 줄을 버린다)**"*

**서버는 버리지 않았다.**

```
서버 버린줄 0(체크섬 0/과길이 0/모름 0/잡음 0)   ← v0.1·v1.0 두 인스턴스 모두
시리얼 TX-RESYNC 4건
```

`arduino-engineer` 는 `promptResyncs` 가 서버의 "버린 줄(모름)" 과 **1:1 로 짝이 되게
설계**돼 있다고 했다. 관측은 **4 : 0** 이다. 설계 의도와 실제가 어긋난다.

**내 후보 설명(확정 아님)**: `CIPSEND` 프롬프트를 못 봤다는 것은 **전송 모드에 진입하지
못했다**는 뜻이므로, 더미 38바이트는 소켓이 아니라 **ESP 의 AT 명령 해석기**로 들어갔을
수 있다. 그렇다면 서버에는 애초에 아무것도 도착하지 않고 `버린줄 0` 이 맞다.
그리고 그 경우 **펌웨어의 로그 문구가 일어나지 않은 일을 단언**하고 있는 것이다.

→ 이건 내 영역 밖이다. `arduino-engineer` 가 소스로 가릴 일이다.
   다만 **"서버는 이 줄을 버린다"를 근거로 삼는 분석은 전부 재검토가 필요하다.**

## 4. 그래서 어떤 지표를 써야 하나

`arduino-engineer` 제안대로 **미수(near-miss)를 센다.** 지금 자료로는:

```
전송 실패(개별)  4건 / 0.2h
3연속 도달       1건 / 0.2h
비율             4 : 1
```

**끊김만 세면 3연속이 된 것만 보이고 직전까지 얼마나 아슬아슬했는지가 안 보인다.**
다만 **표본이 12분·4건이다. 비율을 인용하지 마라** — 방향만 잡아 두는 값이다.

⚠ **계열 간 비교 금지**: 프롬프트 제한이 옛 계열 **300ms** vs EspLink **40ms** 로 7.5배 다르다
(arduino-engineer). 지금 기준선은 300ms 계열이고, 앞선 `send_fail_x3` 관측은 40ms 계열이었다.
**끊김률이 다르게 나오는 것이 정상이다. 두 값을 같은 축에 올리지 마라 — 상수가 다른 두 계측기다.**

### 🔑 동일 규칙으로 다시 센 결과 — **역전이다**

⚠ 처음에 나는 "제한시간이 짧을수록 실패로 세기 쉬우니 방향이 판정을 강화한다"고 적었다.
논리는 맞지만 **근거로 든 두 숫자의 계수 규칙이 달랐다**(내 "새 연결" vs socket 의 "링크 단절").
루트도 같은 실수를 했다가 철회했다. **그래서 양쪽을 내 규칙 하나로 다시 셌다.**

| 구간 | 길이 | 새 연결(ACCEPT) | 시간당 | |
|---|---|---|---|---|
| 기준선 `300ms` · `DEBUG 1` | 13.925h | 36 | **2.59/h** | — |
| EspLink `40ms` · `DEBUG 0` | 3.983h | 3 | **0.75/h** | **3.4× 적다** |
| ↳ 재부팅 아닌 재연결만 | | 35 → 2 | 2.51 → **0.50/h** | **5.0× 적다** |

단측 포아송: 새 연결 기대 10.30 관측 3 **P=8.3e-03** · 재연결 기대 10.01 관측 2 **P=2.7e-03**

**제한시간이 7.5배 빡빡한 쪽이 3~5배 덜 끊겼다.**
→ "제한시간이 끊김률을 지배한다"(arduino 후보 ①)는 **예측이 정반대다. 기각 방향.**
→ "진단 출력이 프롬프트 타이밍을 민다"(후보 ④)가 **1순위로 올라간다.**

### 🔴 그러나 ④ 를 확정할 수는 없다 — 두 구간이 다른 것이 **넷**이다

1. 펌웨어 계열 (`client.ino` vs `EspLink`)
2. 프롬프트 제한 300ms vs 40ms
3. `DEBUG` 1 vs 0
4. **캐패시터 2200µF vs 100µF** ← 팀 논의 목록에 빠져 있던 것

변수가 넷이므로 이 비교는 **후보 순위를 바꿀 뿐 원인을 지목하지 못한다.**
④ 를 단독으로 가르려면 **다른 셋을 고정하고 `DEBUG` 만 끈 구간**이 필요하다.

⚠ 그리고 `send_fail_x3` 이 세는 것은 **`>` 프롬프트를 제한시간 안에 봤는가 하나뿐**이다.
ESP 의 `SEND FAIL`·`busy`·`ERROR` 는 세지 않는다. 즉 **"링크가 끊겼다"가 아니라
"우리가 못 기다렸다"** 이고, 소스도 이를 추정이라고 명시한다.
