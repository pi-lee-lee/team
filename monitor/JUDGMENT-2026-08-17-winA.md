## 3. 🔴 프레임 파괴 3건 — 그리고 **서버 계수로는 안 보였다**

원문(20:43:41)과 전문은 `FINDING-2026-08-17-2043-slot-collision.md`. 세 건의 **모양이 둘로 갈린다**:

```
20:43:41  T,1AT+CIPSEND=39        ← 하행이 잘리고 우리 명령이 이어붙었다 (ASCII)
20:52:42  T,AT+CIPSEND=40         ← 같은 모양
20:48:35  M\xFF,1109,0110000010,...,P1,3B   🔴 모양이 다르다 — **우리 상행 본문이 입력으로 돌아왔다**
          같은 초 앞줄: [AT] "AT+CIPSEND\x14\xADA\x11\xB1\xB2...A1,1,57" (30)
          → 우리 명령이 **고비트 바이트로 오염**되고 끝에 하행 꼬리(`A1,1,57`)가 붙었다
```
🔑 **세 번째는 고비트 바이트를 포함한다.** arduino 가 예전에 *"상행·하행 한 줄 섞임"* 가설을
**고비트 바이트를 근거로 기각**했는데, **그 기각은 그때 그 가비지에 대한 것이고 이 사건에는
적용되지 않는다**(arduino 본인 확인). **섞임은 실재하고, 고비트 손상까지 동반한다.**

### 계수 대조 — 두 계측기가 **같은 사건을 세고 결과가 갈린다**

```
서버(socket) : 재전송 5건 · 결말 실패 0        → "무손실" 로 보인다
장치(내 쪽)  : CKSUM NG 3 · 중복 도착 1 · +IPD 633(=630+3)
```
> ### 🔑 **재전송이 손실을 지운다. 서버 계수만으로는 "무손실"이 나온다.**
> 창4 에서 *"재전송을 자극에서 빼라"*(원인 부풀림)의 **뒷면**이다 — 이번엔 **결과를 지운다.**

**socket 이 자기 보고를 두 번 정정했다**: `유실 0` → `손실 하한 5건` → 🔴 **`상한 5건`**
(방향이 반대였다 — `재전송` 은 *하행 소실 ∪ ACK 소실 ∪ ACK 지연* 이므로 **하행 손실의 상한**이다).
→ **`5/630 = 0.8%` 로 인용하지 마라.**

### ✅ 재고가 닫혔다 — socket 의 `wire_rid` 와 내 시리얼을 맞췄다

socket 이 재전송 로그에 `rid` 가 있다고 알려 와 **한 건씩 귀속됐다**:

| 서버 재전송 | 내 시리얼에서 본 것 | 귀속 |
|---|---|---|
| `20:43:41` rid 153 | `[CKSUM NG] T,1AT+CIPSEND=39` | **하행 파괴** |
| `20:48:35` rid 397 | `[CKSUM NG] M\xFF,1109,…` | **하행 파괴** |
| `20:52:42` rid 600 | `[CKSUM NG] T,AT+CIPSEND=40` | **하행 파괴** |
| `20:48:24` rid 388 | `+IPD` **2회 도착**(20:48:23·:24) | **ACK 계열**(하행은 정상 도달) |
| `20:49:42` rid 451 | `+IPD` 1회 · 같은 초에 **우리 ACK 에코 손상**(`AX451XA1,h,35`) | **ACK 계열** |
| (2차) `20:55:13` rid 714 · `20:55:33` rid 730 | 둘 다 `+IPD` **2회 도착** | **ACK 계열** |

```
1차 재전송 5 = 하행 파괴 3 + ACK 계열 2      ← **미상 0. 재고가 닫혔다**
2차 재전송 2 = ACK 계열 2 · 하행 파괴 0
→ **하행 손실 = 3/630(1차) · 0/120(2차)** · **ACK 계열 = 3/750**(1·2차 · 3차는 §4.5)
```
🔑 **두 도메인의 독립 계측기가 사건 단위로 짝지어졌다.** 어느 한쪽만으로는 못 낸 결론이다 —
서버는 "무손실"로 보였고, 내 쪽은 "재전송 5 중 1 미상"이었다.

## 3.5 🔴🔴 그 대조가 **내 계측기의 잡음 수준을 처음으로 드러냈다**

`[TX] A,…` (장치가 보낸 ACK)와 바로 뒤 `[AT] " A,…"` (그 에코)를 812건 전수 대조했다:

```
불일치 **34건 / 812 = 4.2%**
모양: `,`→`X` · `A1`→`Aa`/`\x811` · `454`→`h54` · 끝에 `\xFE` 추가 …  = **한두 글자 손상**
```
🔴 **그런데 그 34건 중 서버 재전송과 짝이 맞는 것은 1건(rid 451)뿐이다.**
링크에서 깨졌다면 서버가 그만큼 ACK 를 못 받아 **34번 재전송했어야 한다.** 안 했다.
→ **나머지 33건은 ESP 링크가 아니라 에코/탭 경로에서 깨진 것으로 본다**(추정 · 근거는 위 대비).

> ### ⚠ **즉 내 시리얼 로그 자체가 부하 구간에서 약 4% 문자 손상을 갖는다.**
> 지금까지 이 로그를 **정확한 것으로 취급**해 왔다. 문자열 일치로 세는 모든 칸이 영향을 받는다.

✅ **다행히 이번 판정의 핵심 수치는 안전하다**: `[CKSUM NG]` 는 **장치가 스스로 내린 판정**이고
`[CNT]`·`[SLOT]` 은 손상되면 파싱이 실패해 **조용히 틀리지 않고 빠진다**(형식이 방어한다).
🔴 **그러나 앞으로 "0건"을 낼 때는 이 잡음을 같이 적어야 한다** — 4% 손상률이면
**드문 표지 하나는 손상으로 사라질 수 있다.**

## 4. 🔴 `ssovf=3` — **"28B 하행이면 넘칠 조건이 없다"는 전제가 틀렸다**

주입 시작 전 `ssovf=0` 이었고 주입 중 **3까지 올랐다.** arduino·socket 은 둘 다
*"하행이 28B 단발이라 64B 링버퍼는 시험되지 않는다"* 고 봤다(나도 그 판단을 받아 적었다).
**틀렸다 — 넘쳤다.**

**왜**: 넘침은 **프레임 크기**만의 함수가 아니다. **우리 송신이 읽기 루프를 막는 동안** 들어오는
모든 것(하행 + ESP 자기 응답 `SEND OK`·`OK`·`+IPD` 머리)이 쌓인다. **막힌 시간이 분모다.**

⚠ **`ssovf` 는 하한이다**(읽으면 플래그가 지워진다 · 측정 위치는 `pumpSerialRaw()` 읽기 루프 직후).

### ⚠ `ssovf` 와 `CKSUM NG` 는 **수는 같지만 시각이 어긋난다** — 기전으로 잇지 마라

```
ssovf 0→1 : 20:43:40~20:44:40 구간   ↔ CKSUM NG 20:43:41   ✅ 일치
ssovf 1→2 : 20:49:41~20:50:40 구간   ↔ 그 구간 CKSUM NG **없음**   ❌
ssovf 2→3 : 20:52:41~20:53:41 구간   ↔ CKSUM NG 20:52:42   ✅ 일치
CKSUM NG 20:48:35                    ↔ 그 구간 ssovf 증가 **없음**   ❌
```
**3 대 3 이라 기전을 잇고 싶어지지만 2/3 만 맞는다.** 🔴 **수가 맞는 것을 기전으로 읽지 마라.**

### 4.2 해석 A(타이밍) vs B(연달아 도착) — **갈리지 않는다** (루트 요청 · 실측)

`ssovf` 는 `[CNT]` 주기(60초)에만 읽히므로 **증가한 분(分)만 안다.** 그 세 분과 대조 네 분에서
"같은 초에 하행 2건 이상"(=연달아 도착의 대리값)을 셌다:

```
ssovf↑  20:43:41~20:44:40  도착 50 · 같은초2건+ **1** · CKSUM NG 1
ssovf↑  20:49:41~20:50:40  도착 50 · 같은초2건+ **1** · CKSUM NG 0
ssovf↑  20:52:41~20:53:41  도착 39 · 같은초2건+ **1** · CKSUM NG 1
대조    20:41:41~20:42:40  도착 50 · 같은초2건+ **2** · CKSUM NG 0   ← 더 많은데 안 올랐다
대조    20:45:41~20:46:40  도착 50 · 같은초2건+ 0
대조    20:47:41~20:48:40  도착 49 · 같은초2건+ 0 · 재전송 도착 1 · CKSUM NG 1  ← 안 올랐다
대조    20:50:41~20:51:40  도착 49 · 같은초2건+ 0
```
🔴 **못 가른다.** 대조 한 분이 ssovf 증가 분보다 "같은 초 2건"이 더 많은데도 안 올랐고,
`CKSUM NG`·재전송 도착이 있는데 안 오른 분도 있다. **n=3 으로는 A/B 판정이 안 된다.**
⚠ 그리고 **`overflow()` 는 읽으면 플래그가 지워지므로 이 `3` 은 하한이다** —
`[CNT]` 사이에 여러 번 넘쳐도 1 로 뭉친다. **"정확히 3회"로 읽으면 안 된다.**

**가르려면**: ① 배치 크기를 바꿔 가며 재는 것(창 B) 또는
② **간격을 통제한 연속 2건**을 의도적으로 주입하며 `ssovf` 를 보는 것. **둘 다 창 A 밖이다.**
→ ⚠ **그리고 3차가 이 항목의 쓰임을 좁혔다**(§4.5): 손상이 크게 늘었는데 `ssovf` 는 **3 에서 고정**이었다.
   🔴 **`cap` 을 `ssovf` 로 검증하지 마라** — socket 이 자기 지시(`창 B ssovf 기대치를 192 로`)를 정정했다.
   ✅ 남는 쓰임: **28B 기준선이 `0` 이 아니라 `3`** 이므로 창 B 와 견줄 **기준선이 생겼다**(루트 지적).
   🔑 **arduino 의 버퍼 증설 보류 판단은 결과적으로 옳았고 논거만 틀렸다** —
   *"넘칠 조건이 없다"* 가 아니라 ***"넘침이 이 고장의 기전이 아니다"*** 가 맞는 이유다.

## 4.5 🔴🔴 **3차(주기 1.15s)는 링크를 깨뜨렸다** — 1·2차와 성질이 다르다

주입 주기를 **노드 주기보다 50ms 짧게** 한 것뿐이다. 그것만으로 결과가 갈렸다.

| | 1차(1.2s·630) | 2차(1.2s·120) | **3차(1.15s·290)** |
|---|---|---|---|
| 하행 파괴(`CKSUM NG`) | 3 | 0 | 1 |
| ACK 계열(중복 도착) | 1 | 2 | **15** |
| 미도달(`rid` 없음) | 0 | 0 | **1**(rid 913 · 3회 시도 전부) |
| `[TX-WAIT]` / 슬롯 | 55/634 = 8.7% | 19/122 = 16% | **140/318 = 44%** |
| 상행 최대 공백(내 실측) | 3s | 4s | **10s** |
| 서버측 오프라인 판정 | 0 | 0 | **5회** |
| 서버측 세션 종료 | 0 | 0 | **1회**(`errno=54` · 최대공백 10.2s) |
| `esprst`(모듈 리셋) | 0 | 0 | **0** |

🔑 **내 상행 최대 공백 10초와 서버의 최대 공백 10.2초가 독립적으로 맞는다.** 같은 사건이다.
🔴 **그리고 장치는 안 죽었다** — `uptime` 연속(2084→2095) · `esprst=0`. **깨진 것은 링크다.**

### 기전 — **계단식 악화**이고, `ssovf` 로는 설명되지 않는다

```
20:56:42  drop=1 stuck=1 okto=5  skip=99  ssovf=3 · oow=482
21:03:44  drop=2 stuck=2 okto=13 skip=235 ssovf=**3** · oow=693 · esprst=0
```
🔴 **손상이 크게 늘었는데 `ssovf` 는 3 에서 고정이다.** 내가 §4 에서 세우고 싶어했던
*"넘침 → 파괴"* 가설은 **3차가 죽인다.** 기전은 버퍼 넘침이 아니라 **동시 송수신의 비트/프레이밍 오류**다.

**socket 의 모형 `S`**(두 번째 하행이 첫 번째의 ACK 송신 중 도착 → 그 ACK 가 깨진다)가
**ACK 계열의 급증(0.3% → 5.2%)을 설명한다.** 하행 파괴도 0 은 아니지만(1건) **비율은 ACK 계열이 앞선다.**
→ 🔑 **`W`(좁은 위험 창) 단독으로는 이 계단식 악화가 안 나온다** — 3.5초 무프레임까지 쌓이는 것은
**누적 경로**가 있어야 한다. `rid 913` 의 원문이 그것을 보여 준다(§4.6).

### 4.6 `rid 913` — 몇 ms 창이 아니라 **몇 초짜리 열화 구간**

```
21:00:28  [AT] " S,1652,...,20Hh)*\xA5'KN\x99,S\x82\xC5\x8Ab\xAA\x8AR"   ← 우리 상행이 통째로 깨졌다
21:00:28  [AT] "OK" · "AT+CIPSEND=40"
21:00:29  [TX-WAIT] SEND OK 를 아직 못 봤다 → 건너뜀
```
`SEND OK` 가 오지 않았다 → **디버그 경로가 아니라 ESP 링크에서 깨졌다.** 그 구간에 `rid 913` 의
**3회 시도가 전부 사라졌다.** 재시도가 위상을 옮겨도 다 잃었으므로 **좁은 위험 창으로 설명되지 않는다.**
⚠ `20:48:35` 사건과 **같은 모양**(고비트 + 우리 페이로드 오염)이고 **이것이 세 번째다.**

### ⚠ 4.7 3차에는 **중단 조건을 넘긴 구간이 있다** (socket 자진 신고)

socket 이 시작 전에 등록한 중단 조건(`device_offline` 연속 5건)이 **`21:00:37` 에 충족**됐는데
**주입이 `21:03:14` 까지 약 130건 더 돌았다.** 이유: *"내가 움직일 것으로 기대한 칸(`ACK`·`재전송`)만
폴링하고, 멈추라고 정해 둔 칸(`미주입`)은 한 번도 안 봤다."*

🔴 **판정 처리**: 3차를 **`21:00:37` 로 잘라 두 조각으로 표시한다.**
- `20:56:53~21:00:37` = 등록된 조건 안에서 얻은 자료
- `21:00:37~21:03:14` = **조건을 넘긴 뒤의 자료** — **버리지 않는다**(자료는 유효하다) 그러나
  **"등록된 시험의 결과"로 인용하지 않는다.** 링크가 이미 나빠진 뒤의 구간이다.
🔑 **조건을 적는 것과 그 조건을 보는 감시를 만드는 것은 다르다** — 내가 `zeroguard` 로 배운 것과
같은 형태다(규칙보다 형식). **다음 주입에는 중단 조건이 자동 판정돼야 한다.**

## 5. 링크 사건 — 20:56:12 · 그리고 3차의 것들

```
20:56:12  [DIAG] offline step=6 사다리=0/0 rx=150055 lines=7331 up=1830s
20:56:12  [NET] 6 CIPCLOSE (낡은 소켓 닫기)
20:56:12  [AT] " S,1467,...,P1,3DAT+CIPCLOSE" (51)     ← 우리 S 프레임과 AT 명령이 한 줄에 섞였다
20:56:13  [NET] ALREADY CONNECTED — 낡은 소켓 의심 → CIPCLOSE
[CNT] 20:56:42  drop=1 stuck=1 esprst=0 · online=1(복귀)
```
- `esprst=0` · 배너 0 · `0.0.0.0` 0 → **모듈 리셋이 아니다.**
- `stuck=1` → **정지 감지 경로**다. 창4 의 `09:02`·`09:13`(우리 감지기가 끊은 것)과 **같은 계열**이다.
- **복귀했다**(`online=1`).
🔴 **그러므로 "창 A 는 사건 0" 이 아니다.** 1건이고, **귀속은 우리 코드**다.
⚠ 그 직전 줄에 **AT 스트림 섞임**이 또 보인다 — §3 의 파괴와 같은 방향의 증거다.

## 6. 창4 와 이을 수 있는 지표만 비교 (정의가 안 바뀐 것)

`METRICS-slot-boundary` §5 의 허용 목록: **노출 시간 · `전송 3회 연속 실패` · 리셋 표지**.

| | 창4 (`0fba51f` · 큐 없음) | **창 A** (`slot2` · 큐 없음) |
|---|---|---|
| 신규 하행 | 84거래 | **1,040거래** |
| 리셋계열(배너/`0.0.0.0`/부트ROM) | **6~7건** | **0건** |
| `전송 3회 연속 실패` | 9건 | **0건** |
| `[TX-RESYNC]` | 있음(6+) | **0건** |
| 링크 사건 | 11건(3진아웃 9 + 정지감지 2) | 2건(둘 다 `stuck` 경로 · 복귀) + 서버측 세션 종료 1 |

**창4 의 거래당 리셋 위험(6/84 = 7.1%)이 그대로라면 1,040거래의 기대는 약 74건이다. 관측 0.**
🔑 **방향이 뒤집힐 여지가 거의 없다.**
⚠ **그러나 등가 비교가 아니다**: 하행 종류가 다르고(브라우저 `R`/`C`/`M` vs 주입 `T` 28B),
펌웨어가 다르고, 부하 무늬가 다르다. **"거래당 위험이 같다"는 가정은 검증되지 않았다.**
→ **판정문 문장**: *"같은 판별자로 세면 창4 84거래에 6~7건, 창 A 1,040거래에 0건이다."* 배수는 쓰지 않는다.

## 8. 🔴 계측기 정정 — `[SLOT-OOW]` 오프셋은 **도착 시각이 아니다**

arduino 가 소스를 열어 잡았다(`client.ino:909`): 송신 중(`inSend`) 완성된 줄은 `pendLine` 에
갇혔다가 **송신이 끝난 뒤** `handleLine` 에서 시각이 찍힌다.
→ **위험 구간에 도착한 것이 바로 그 이유로 늦게 찍힌다.**

**철회**: ~~위험 구간 = `[116, 171)ms`~~ · ~~"116ms 미만 정상 도착 0건"이 발견~~
(후자는 **계측 산물**이다 — 그 칸은 원리적으로 빈다).
**남는 것**: **위험 구간은 페이로드 시간보다 넓다** — 모델에 `AT+CIPSEND=39\r\n` 16B(≈17ms)가
빠져 있었고(arduino 확인) 프롬프트 대기도 점유다. **폭은 미측정.**
→ 다음 굽기에서 `[SLOT-OOW]` 시각을 **첫 바이트 수신**으로 옮긴 뒤 처음 잰다.

## 9. 결론 넷

1. ✅ **슬롯 배치는 창4 의 리셋 사슬을 없앴다** — **1,040거래 · 모듈 리셋 0 · 3진아웃 0 · 재동기 0.**
   창4 는 84거래에 리셋계열 6~7건이었다. **이것이 이 창의 가장 큰 소득이다.**
   ⚠ 단 **원인 귀속 불가** — 그 사이 슬롯·가드·ACK 큐·3단 게이트가 **같이** 바뀌었다(축 여섯).
   **말할 수 있는 것은 "이 구성에서 그랬다"** 까지다(socket·arduino 도 같은 정정을 했다).
2. 🔴 **그래도 하행은 깨진다** — 파괴 4건(1차 3 · 3차 1) · 미도달 1건 · ACK 계열 18건.
   **장치 규율만으로는 부족하다. (가) 서버 큐가 필요하다는 실측 근거다.**
3. 🔴🔴 **주기를 노드 주기보다 50ms 짧게 한 것만으로 링크가 깨졌다**(3차) —
   `[TX-WAIT]` 44% · 상행 공백 10초 · 서버 오프라인 판정 5회 · 세션 종료 1회(`errno=54`).
   **장치는 안 죽었다**(`uptime` 연속 · `esprst=0`). **깨진 것은 링크다.**
   🔑 **하행 밀도가 조금만 올라도 무너지는 구간이 실재한다** — 창 B 가 이것을 막아야 한다.
4. 🔴 **기전은 버퍼 넘침이 아니다** — 손상이 크게 늘었는데 `ssovf` 는 3 에서 고정이었다.
   **동시 송수신의 비트/프레이밍 오류**다. → 🔴 **`cap` 을 `ssovf` 로 검증하지 마라**(socket 이
   자기 지시를 정정했다). **배치 바이트별 `CKSUM NG`·하행 손실 곡선**이 그 지표다.
