## 0. 먼저 — 파서를 교정했고, 측정법 오류 하나를 잡았다

**교정**: 같은 도구로 판정창(11:27~15:27)을 돌리면 S프레임 **12,660** 이 나온다.
`soak_stats.py` 의 판정창 값과 정확히 일치 → 파서를 믿어도 된다.

**측정법 오류(잡음)**: 처음에는 "재부팅 시각 이전 30초"로 선행 사건을 셌다. 그런데
**재부팅의 물리적 시각은 알 수 없다** — 우리가 보는 것은 `t0`(끊기기 전 마지막 프레임)와
`t1`(복귀 후 첫 프레임)이고 재부팅은 그 사이 공백 안에 있다.
`t1` 기준으로 세면 **재부팅 뒤의 재접속을 "선행"으로 오계상한다.**

- 잘못된 기준: 폭주 선행 **1/7**, "일부 선행" 4건
- 올바른 기준(`t0` 이전): 폭주 선행 **0/7**, "일부 선행" 2건

**결론이 뒤집혔다.** 처음 숫자를 그대로 보고했으면 되먹임 루프 쪽으로 잘못 끌고 갔을 것이다.

## 2. A 보강 — "ACCEPT 0" 만으로는 약해서 하나 더 봤다

세션이 살아 있는 동안엔 **원래 ACCEPT 가 생기지 않는다.** 그래서 0 이 나오는 건 당연할 수 있다.
그 함정을 피하려고 **끊기기 직전 프레임 흐름이 정상이었는지**를 따로 쟀다.

> 정상 흐름 뒤 예고 없이 끊김 → **바깥에서 꺼진 모양(전원)**
> 끊기기 전에 프레임이 성겨짐 → **장치가 먼저 힘들어한 모양(소프트/링크)**

| t0 | 직전 60초 프레임 | seq 점프 | |
|---|---|---|---|
| 15:30:24 | **52** | 0 | 정상 흐름 |
| 15:58:03 | **55** | 0 | 정상 흐름 |
| 15:59:19 | 26 | 0 | 성김 |
| 16:04:12 | **53** | 0 | 정상 흐름 |
| 16:05:20 | 12 | 0 | 이미 끊긴 상태 |
| 16:06:48 | 18 | 0 | 성김 |
| 16:11:31 | **55** | 0 | 정상 흐름 |

판정창 정상치가 **≈53프레임/분**이다. **4건은 정확히 정상 속도로 흐르다가 그대로 사라졌다.**
`seq 점프 0` — 프레임 유실조차 없었다. **예고가 전혀 없다.**

성긴 3건(26·12·18)은 **직전 재부팅의 회복 구간**에 겹쳐 있다. 독립된 전조가 아니라
앞 사건의 여파다.

## 5. 판정 — 무엇이 배제됐고, 무엇이 남았나

내가 로그로 **배제한 것**은 하나다:

> 🚫 **되먹임 루프 가설은 지지받지 못한다.** 재접속 폭주가 선행하지 않고(0/7),
> 절반 이상이 정상 속도로 흐르던 중 예고 없이 사라졌다(4/7, seq 점프 0).
> 소프트웨어가 스스로 시끄러워지다 무너지는 모양이 **아니다.**

**"그러므로 전원이다"는 내 로그만으로는 안 나온다.** 워치독이나 즉발성 펌웨어 리셋도
**정확히 같은 서명**(전조 없음 · 즉시 리셋 · uptime 초기화)을 남기기 때문이다.
그 구분은 `MCUSR` 레지스터가 하는데, **부트로더가 먼저 지운다**(arduino-engineer 확인).
즉 **현재 구성으로는 원리적으로 관측 불가능한 구분이다.**

### 다른 도메인이 좁혀 준 것 (내 관측이 아니다 — 출처를 밝힌다)

`arduino-engineer` 가 펌웨어 전체(`client.ino` + `EspLink.h` 22KB)를 확인해
**워치독 부재를 확정**했다(`wdt`·`WDTCSR`·`WDIE`·`avr/wdt` 없음).
그리고 이 구간 DTR 은 `serial_tap` 이 포트를 쥐고 있어 배제된다(로그로 확인).

→ 배제를 합치면 남는 후보는 **브라운아웃 · 전원 순단 · 접촉 불량 · 외부 리셋(사람)** 이다.
   **이 좁힘은 소스 검증 덕이지 내 로그 덕이 아니다.**

### 🔑 그리고 15:30 의 "미지수"에 답이 생겼다 — 사용자가 실물 작업 중이었다

루트가 사용자에게 직접 확인했다(REQ-0105 회신): **사용자가 서버를 내렸고 지금도 작업 중이다.**

이것이 §3 의 모순 — *"같은 100µF 로 4시간을 버텼는데 왜 갑자기 무너지나"* — 에 대한
가장 단순한 설명이다. 회로 설계가 모자란 게 아니라 **15:30 부터 사람이 만지고 있었다면**
접촉·전원 경로·배치가 바뀌는 것이 자연스럽다.

⚠ **확정하지 않는다. 무엇을 했는지 아직 모른다.** 가설 목록의 맨 위에 올려 둘 뿐이다.
   `arduino-engineer` 도 같은 방향에서 사용자에게 물을 것을 제안했다(USB 전류 한도·접촉·허브).
   **부품(캐패시터)을 바꾸는 것은 그 답을 들은 뒤여야 한다** — 원인이 접촉이었다면
   "고친 것처럼 보이다가 재발"하는 최악의 형태가 된다.

### 그대로 남기는 한계

1. **표본 7건.** 경향이지 증명이 아니다.
2. **직접 증거가 아니라 "예고의 부재"다.** 부재로 미는 논증은 관측 해상도에 기댄다 —
   시리얼이 죽어 **장치 내부를 못 본다.** 장치측 전조가 서버에만 안 보였을 가능성은 못 지운다.
3. **15:26~15:30 파일 삭제 사고와 첫 재부팅이 겹친다.** 이제는 "사용자 작업"이라는
   공통 원인 후보가 생겼지만, 그래도 **기전을 확인한 것은 아니다.**

### 부수 검증 — 이 구간 자료의 무결성

판정창 S프레임 12,660건을 seq 로 전수 검사했다: **중복 0 · 되감김 0 · device `P1` 단독**
(연속 12,657 / 건너뜀 2). 두 기록자가 있었다면 반드시 나올 흔적이 없다.
→ **집계 대상이 단일 기록자임이 증명됐다.** (앞서 내가 "인스턴스가 섞였다"고 낸 경고는
