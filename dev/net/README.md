# net/ — DigitCam 수신 쪽

앱이 인식한 숫자를 받아 화면에 찍어 보는 **테스트 TCP 서버**와 그 프로토콜 명세가 있다.

| 파일 | 내용 |
|---|---|
| `test_server.py` | 표준 라이브러리만 쓰는 수신 서버. 이것이 앱을 검증하는 기준이다 |
| `../docs/net/digitcam-protocol.md` | 전송 프로토콜 정식 명세(바이트 수준). 서버를 새로 만들 때 이것만 보면 된다 |

계약 원본은 `docs/digitcam-contract.md` §7 이다. **프로토콜을 바꾸려면 루트에게 요청한다.**

---

## 1. 실행

```bash
python3 net/test_server.py            # 0.0.0.0:5500 (기본 — 계약 §6 의 server.port 와 같다)
python3 net/test_server.py 6000       # 포트 지정
python3 net/test_server.py --help     # 옵션
```

> ### ⚠ 5000 번은 쓰지 마라 — macOS AirPlay 가 점유한다 (실측)
>
> 기본값이 5500 인 이유다. 계약 §6 도 5500 으로 정해져 있다(REQ-0008).
> **포트를 직접 5000 으로 바꾸고 싶어지면 이 절을 먼저 읽어라.**
>
> ```
> $ python3 net/test_server.py 5000
> 바인드 실패 0.0.0.0:5000 — [Errno 48] Address already in use
>
> $ lsof -nP -iTCP:5000 -sTCP:LISTEN
> ControlCe 1088 idong-u   11u  IPv4 ... TCP *:5000 (LISTEN)
> ```
>
> **서버가 안 뜨는 것보다 앱 쪽 증상이 고약하다.** 앱이 5000 으로 접속하면
> **AirPlay 에 연결이 성공한다.** 실측했다 — `connect` 가 0 을 돌려주고 `sendall` 도 성공한다.
> 즉 앱 화면에는 **"연결됨"** 이 뜨고 전송도 성공한 것처럼 보이는데, 값은 아무 데도 도착하지 않는다.
> 서버 로그가 비어 있으니 인식기나 전송 코드를 뜯어보게 된다 — 엉뚱한 곳이다.
>
> 포트를 바꿀 때는 서버와 `server.properties` 의 `server.port` 를 **같이** 바꾼다.
> (AirPlay 수신기를 꺼도 되지만 — 시스템 설정 → 일반 → AirDrop 및 Handoff — 포트를 피하는 편이 낫다.
> 사용자 설정을 건드리지 않고, 다른 기기에서도 같은 문제를 안 만난다.)

| 옵션 | 기본 | 설명 |
|---|---|---|
| `port` (위치 인자) | `5500` | 수신 포트. 계약 §6 의 `server.port` 기본값과 같다 |
| `--host` | `0.0.0.0` | 바인드 주소. **폰에서 붙으려면 이대로 둔다** |
| `--max-line` | `65536` | LF 없이 허용하는 최대 바이트. 넘으면 연결을 끊는다 |

종료는 `Ctrl-C`. 누적 접속 수와 줄 수를 찍고 깨끗이 내려간다.

출력 형식:

```
21:11:23.618  + 127.0.0.1:54110   접속 #1 · 동시접속 1
21:11:23.619  ← 127.0.0.1:54110   #1  {"ts":1755080000000,"value":"1234",...}
21:11:24.637  ! 127.0.0.1:54110   미종단 잔여 15 바이트(LF 없음): ...
21:11:24.637  - 127.0.0.1:54110   해제 — 클라이언트가 닫음 · 줄 3 · 172 바이트 · 동시접속 0
```

`+` 접속 · `←` 수신한 줄 · `-` 해제 · `!` 이상(미종단 잔여, 길이 초과).
`!` 가 보이면 그 자체가 진단이다 — 조용히 넘어가지 않도록 일부러 찍는다.

수신 값은 **한국 번호판 문자열**이다(`123가4568`). 한글이 들어간다.

```
21:30:37.131  ← 127.0.0.1:55135  #1  {"ts":1755080001000,"value":"123가4568","conf":0.82,"format":"new","seq":1,"device":"SM-S911N"}
21:30:39.921  ← 127.0.0.1:55140  #1  {"value":"123가4568",...}   → value=123가4568 format=new
```

두 번째 줄처럼 `가` 이 보이면 **깨진 게 아니다.** 송신 측이 한글을 JSON 이스케이프로
보낸 것이고(계약 §7 이 둘 다 허용한다), 서버가 `→` 뒤에 복원값을 덧붙여 준다.

## 2. 노트북 IP 확인 (폰에 넣을 주소)

**서버가 도는 노트북의 Wi-Fi IP** 를 앱 설정에 넣어야 한다.
`0.0.0.0` 이나 `127.0.0.1` 을 넣으면 안 된다 — 그건 폰에서 닿지 않는다.

### macOS (이 프로젝트 환경)

```bash
ipconfig getifaddr en0        # Wi-Fi. 보통 이거 하나면 끝난다
ipconfig getifaddr en1        # en0 이 비어 있으면 다른 인터페이스를 시험
ifconfig | grep "inet "       # 전체 목록에서 눈으로 고를 때
```

`192.168.x.x` 또는 `10.x.x.x` 로 시작하는 사설 IP 가 나온다. 그게 폰에 넣을 주소다.
(`127.0.0.1` 은 루프백이므로 제외.)

### Windows

```
ipconfig
```
"무선 LAN 어댑터 Wi-Fi" 항목의 IPv4 주소.

### Linux

```bash
hostname -I
ip -4 addr show
```

## 3. 앱 쪽 설정

계약 §6 의 `server.properties` 에 위 IP 와 포트를 넣는다.

```properties
server.host=192.168.0.x        # ← 위에서 확인한 노트북 IP (예시일 뿐이다)
server.port=5500               # ← 서버를 띄운 포트와 같아야 한다 (계약 §6 기본값)
server.format=json             # json | plain
```

```bash
adb push server.properties /sdcard/Android/data/com.example.digitcam/files/server.properties
```

푸시한 뒤 앱 화면의 **"설정 다시 읽기"** 를 누르면 앱을 껐다 켜지 않아도 반영된다.

## 4. 붙지 않을 때 — 위에서부터 확인

1. **폰과 노트북이 같은 Wi-Fi 인가.**
   가장 흔한 원인이다. 폰이 LTE/5G 로 붙어 있거나, 노트북이 유선이고 폰이 무선이거나,
   공유기의 2.4GHz/5GHz SSID 가 갈려 있으면 사설 IP 로 서로 못 본다.
   **게스트 네트워크**와 카페·회사 Wi-Fi 는 단말 간 통신(AP isolation)이 막혀 있는 경우가 많다 —
   이때는 같은 SSID 라도 안 된다. 폰 핫스팟에 노트북을 붙이면 대개 해결된다.
2. **서버가 `0.0.0.0` 으로 떠 있는가.** 시작 시 출력에 찍힌다.
   `--host 127.0.0.1` 로 띄웠으면 경고 줄이 나온다.
3. **macOS 방화벽.** 처음 띄울 때 "python3 의 네트워크 연결을 허용하시겠습니까" 창이 뜨면
   **허용**한다. 거부해 두면 조용히 안 붙는다.
   (시스템 설정 → 네트워크 → 방화벽에서 다시 켤 수 있다.)
4. **포트가 같은가. 그리고 5000 을 쓰고 있지 않은가.**
   서버 포트와 `server.port` 가 다르면 당연히 안 된다. 그리고 **5000 이면 앱은 "연결됨"인데
   서버 로그는 비어 있는** 상태가 된다 — AirPlay 에 붙은 것이다(위 ⚠). 이 조합이 가장 헷갈린다.
5. **노트북에서 먼저 자기 자신에게 시험한다**(아래 §5). 여기서 되면 문제는 네트워크 경로에 있다.

### 값은 오는데 한글이 깨져 보일 때 — 터미널부터 의심하라

`123媛4568` 처럼 한글 자리만 깨져 보이면 **서버가 아니라 터미널 로케일** 문제일 수 있다.
서버는 UTF-8 로 찍는데 터미널이 다른 인코딩으로 해석하면 그렇게 보인다. 먼저 확인한다:

```bash
locale                      # LANG / LC_ALL 확인
echo $LANG                  # ko_KR.UTF-8 또는 en_US.UTF-8 이어야 한다
```

`LANG` 이 `C` 나 `POSIX` 면 UTF-8 이 아니다. 그 세션에서만 바꿔 다시 띄운다:

```bash
LANG=en_US.UTF-8 python3 net/test_server.py 5500
```

구분법: **`가` 처럼 `\u` 로 보이는 것은 정상**(§1 참조, 서버가 복원값을 덧붙여 준다).
**`?` 나 `媛` 처럼 깨져 보이는 것은 터미널 로케일** 문제다.
둘 다 서버 버그가 아니다. 서버 자체는 한글 왕복을 검증해 뒀다(명세 §10.6).

## 5. 앱 없이 서버만 시험하기

서버가 도는 상태에서 다른 터미널(또는 이 저장소 안에서):

```bash
printf '123가4568\n' | nc -w 1 127.0.0.1 5500
printf '{"ts":1755080000000,"value":"123가4568","conf":0.82,"format":"new","seq":1,"device":"test"}\n' | nc -w 1 127.0.0.1 5500
```

폰 대신 **다른 기기에서** 시험하려면 노트북 IP 로 보낸다:

```bash
printf '456나7890\n' | nc -w 1 192.168.0.x 5500
```

**한글 조립까지 제대로 되는지** 확인 — 한글 한 글자(`가` = `EA B0 80`) 한복판을
recv 경계로 일부러 갈라서 보낸다. 이게 이 서버의 가장 중요한 시험이다:

```bash
python3 -c "
import socket, time
s = socket.create_connection(('127.0.0.1', 5500), timeout=3)
s.sendall('123가4568\n12가3456\n'.encode())        # 두 줄을 한 번에
time.sleep(0.2)
p = '123가4568\n'.encode()
s.sendall(p[:4]); time.sleep(0.3); s.sendall(p[4:])  # 가(EA|B0 80) 한복판에서 갈라 두 번에
time.sleep(0.3); s.close()
"
```

서버에 `123가4568` / `12가3456` / `123가4568` **세 줄**이 한글이 깨지지 않은 채 찍히면 정상이다.
깨지거나 줄이 합쳐지면 수신 쪽 줄 조립이 틀린 것이다(명세 §8.3).
(`socat` 을 써도 되지만 이 노트북에는 설치돼 있지 않다 — `nc` 로 충분하다.)

## 6. 알아둘 것

- **값은 한글이 섞인 번호판 문자열이다**(`123가4568`). 바이트 수 ≠ 문자 수 —
  신형 8자=10바이트, 구형 7자=9바이트. 고정폭으로 받으면 깨진다(명세 §4.4).
- **json 프레임의 키는 6개**다(`ts` `value` `conf` `format` `seq` `device`).
  `format` 은 `new`(8자) / `old`(7자). 개정 1 의 5키 서버는 `format` 을 모르는 키로 무시하면 된다.
- **빈 줄은 오지 않는다** — 빈 값은 안정화되지 않아 전송 조건에서 걸러진다(계약 §5.1).
  그래도 서버는 빈 줄에 죽지 않는다(명세 §5.2).
- **서버는 아무것도 되돌려 보내지 않는다**(fire-and-forget). 근거는 명세 §2.4.
- **끊긴 동안의 값은 사라진다.** 재전송 큐가 없다 — 설계된 동작이지 버그가 아니다(명세 §2.3).
- **조용한 연결은 정상이다.** 숫자가 안 보이면 보낼 것이 없다. 타임아웃으로 끊지 않는다.
- **`seq` 는 앱을 재시작하면 1 로 돌아가고, 중간에 구멍이 날 수 있다**(끊긴 동안 버린 값).
- 서버를 껐다 켜도 앱이 다시 붙는다. `SO_REUSEADDR` 를 켜 뒀으므로 재기동이 막히지 않는다.
