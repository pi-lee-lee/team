## 🔴 "두 굽기가 달랐다" 를 바이트로 반박했다

루트가 이렇게 읽었다 — 19:14:22 굽기는 IDENTICAL 이었는데 B1 이 200프레임 중 0회였고
19:23:32 뒤에는 4 가 뜬다, 그러므로 두 굽기가 달랐다.

```
cmp <0461441 빌드 hex>  <19:23:32 과 같은 트리 빌드 hex>   →   exit 0
→ 두 굽기의 산출물이 바이트 동일하다. 굽기는 원인일 수 없다
```
그 사이 client.ino 변경은 주석 3줄(배선 출처)이라 hex 에 안 닿는다.

결론("원인을 안 찾는다" · 사용자 지시)은 유지하고 근거만 고쳤다.
안 고치면 다음 사람이 "IDENTICAL 이어도 굽기가 다를 수 있다" 를 근거로 쓴다 —
그건 우리 hex 대조 절차 전체를 무력화하는 문장이다. 비용은 cmp 한 줄이었다.

## ✅ 남는 설명은 하나 — 센서 불량

사용자가 핀을 바꿔 판별했고 센서가 자리를 따라갔다.
→ 핀·배선·코드·전원은 정상. 양쪽 핀 경로(2/4 · 11/10)가 다 동작한다.

## 🔑 그리고 그것이 우리보다 싼 판별이었다 (§124)

나는 진단 굽기(D10: 왕복 µs 를 찍는다)를 설계해 뒀다. 사용자는 부품을 바꿨다.
```
우리 판별 : 코드를 의심한다 → 진단 코드 + 굽기 + 캡처 = 개입 여럿
교체     : 코드·핀·전원을 한꺼번에 배제한다. 우리 쪽 개입 0
```
그것은 사람만 할 수 있어서 우리 후보 목록에 원래 안 들어온다.
"감시할 수 없는 것은 조건으로 적지 마라" 의 거울상이다 — 우리가 할 수 없는 것이 최선일 수 있다.
