센서 블로킹 예산 66ms · 축 셋을 갈랐다 · 원장 §111~§116

사용자 물음 둘("초음파 3개가 달리면?" · "슬롯 방식이 모든 센서를 다루나")에서 나왔고
루트가 계산했다. 그 값이 내 상한 시험(53B/64B)과 정확히 일치했다.

## 🔴 내가 축을 섞었다 — 첫 GUIDE 표가 그것을 저질렀다

```
표에 334ms(슬롯당 누적)와 53.5B 를 나란히 뒀다
🔴 53.5B 는 55.7ms(한 번에 연속)에서 나온 수다. 334ms 에서 나온 수가 아니다
```
루트가 잡았다. 안 갈라 두면 다음 사람이 누적값으로 버퍼를 계산한다.

## 축 셋 — 갈라 적었다 (GUIDE §4 · 원장 §111)

```
① 한 번에 연속 블로킹 (6.96ms × N)  → 🔴 버퍼 넘침 축. 66ms 예산이 이것을 본다
② 슬롯당 누적 블로킹 (41ms × N)     → 루프 지연 축. 버퍼와 무관하다
③ 송신 시작이 밀리는 것              → 송신 기회 상실 축. 계측기는 smiss 다
```

## 예산 — 66ms 가 결정한다

```
버퍼   : 960 B/s × T ≤ 64B  →  T ≤ 66ms      ← 작은 쪽
송신 창 : 읽기 합 + 185ms ≤ 400ms  →  합 ≤ 215ms
```
센서별: analogRead ~100µs · I2C ~1ms · HC-SR04 6.96ms · DHT ~20ms
🔴 DS18B20 ~750ms — 하나도 안 된다. 슬롯 1200ms 를 통째로 먹는다.

→ 그래서 답이 프레임워크가 아니라 훅의 규칙이다: "훅은 즉시 반환한다."
   두 박자로 나누는 본보기를 GUIDE 에 코드로 넣었다. 프레임워크 변경 0.
   🔑 초음파 예시의 200ms 캐시가 같은 모양의 작은 판이다.

## ✅ 루트의 ③ 우려에 답 — canSend 가드가 살아 있다

```
Session.h:53  SLOT_TX_RESERVE_MS = 200
Session.h:54  inTxWindow = (slotUsed + 200 <= 600)   →  송신은 0~400ms 안에서만 시작
```
🔴 초음파가 그 경계를 밀면 아예 안 보낸다. 수신 창을 침범하지 않는다.
→ 대신 smiss 가 오른다. 🔑 [CNT] 에 그 계측기가 이미 있다 — 새로 만들 것이 없다.
설계가 그 교환을 고른 것이다: 하행 유실은 되돌릴 수 없고 상행 지연은 다음 슬롯에 만회된다.

## ⚠ §98 을 정정한다 — "바이트 유실 없음"은 센서 블로킹에만 참이다

```
센서 블로킹   : 인터럽트 살아 있다 → 버퍼에 쌓인다 → 넘치면 잃는다
🔴 송신 185ms : SoftwareSerial 이 cli() 로 인터럽트를 끈다(Config.h:76)
               → 통째로 유실. 버퍼에도 안 남는다
```
수신 창을 비워 둔 이유가 뒤쪽이다. 같은 "수신 손실"로 부르면 대책이 뒤섞인다.

## 🔴 §100 에서 멈춘 자리를 이어 갔다 — 게이트 정렬은 일회성이 아니다

```
게이트 200ms · 슬롯 1200ms → 1200/200 = 6, 정수배다
🔴 정수배면 한 번 정렬된 위상이 계속 정렬된 채로 간다. 흩어지지 않는다
```
🔑 다행히 정렬 지점이 슬롯 시작 근처다(begin() 이 slotStart 를 세우고 첫 readSensors() 가
같은 tick() 안이라 위상차 ≈ 0). 창 앞쪽이라 안전하다.
⚠ 그런데 이건 지금 구성의 우연이다 — 슬롯이 서버 프레임 도착으로 재정렬되면 위상차가 생기고
정렬 지점이 창 안을 떠돈다. 그때 smiss 가 오른다. 그것이 이 축을 볼 유일한 창이다.

## §115 — 되돌릴 수 없는 증상은 예측으로 막는다

D8 조건에 예측을 넣은 이유를 규칙으로 적었다. 우리 "방아쇠는 증상으로" 의 예외이고,
근거가 실측일 때만 쓴다. "되돌릴 수 없다"만으로는 부족하다.
